# 빌드·배포 매뉴얼

GitLab 에서 소스를 클론한 뒤 빌드하고 배포하기까지의 전 과정이다.
**정본은 [`deploy/prod/README.md`](../deploy/prod/README.md) 이고** 이 문서는 제출 규격에 맞춰
한 줄기로 추린 것이다. 함정과 결정 근거는 정본에 있다.

각 절의 마지막에는 **성공 여부를 판단하는 명령**이 한 줄씩 있다. 그 줄이 기대한 값을 내면
다음 절로 간다.

---

## 1. 시스템 구성

### 1.1 노드가 둘이다

| 노드 | 호스트 | 무엇이 도나 |
| --- | --- | --- |
| **`app`** | `j15a506.p.ssafy.io`<br>사설 `172.26.6.235` | postgres · api(Spring Boot) · web(nginx + 프런트 정적파일) · rag-api · similarity-loader · Spark worker② |
| **`data`** | `j15a506a.p.ssafy.io`<br>사설 `172.26.8.249` | minio · mlflow · Spark master·worker① · ai-similarity(유사도 배치) · ingest-weekly(주간 수집) |

**사용자 요청이 닿는 것은 `app` 노드뿐이다.** 인터넷에 열린 포트는 `app` 의 80·443·22 이고
`data` 노드는 사설망으로만 붙는다.

```
브라우저 ──443──▶ web (nginx)  ─┬─ /                 → 프런트 정적파일 (SPA)
                                ├─ /api/             → api:8080
                                ├─ /swagger-ui/      → api:8080
                                ├─ /actuator/health  → api:8080
                                └─ /api/v1/ops/      → 404 (운영자 전용, 밖에서 막는다)
                                         api ──▶ postgres:5432
```

`api` 와 `postgres` 는 호스트 밖에서 닿지 않는다. `api` 는 `127.0.0.1:8080` 에만 바인딩하고
`postgres` 는 포트를 아예 열지 않는다.

### 1.2 서버 사양

**두 노드의 사양이 같다.** CPU 모델만 다르고 코어·메모리·디스크가 동일하다
(AWS EC2, `nvme` 320 G 중 루트 파티션 319 G).

| | `app` (j15a506) | `data` (j15a506a) |
| --- | --- | --- |
| CPU | Intel Xeon Platinum **8175M** @ 2.50GHz | Intel Xeon Platinum **8259CL** @ 2.50GHz |
| 코어 | **4 vCPU** (2코어 × 2스레드) | **4 vCPU** (2코어 × 2스레드) |
| 메모리 | **15 GiB** | **15 GiB** |
| 디스크 | `/dev/root` **309 G** (nvme0n1 320 G) | `/dev/root` **309 G** (nvme0n1 320 G) |
| OS | **Ubuntu 24.04.4 LTS** | **Ubuntu 24.04.4 LTS** |
| 커널 | **6.17.0-1019-aws** | **6.17.0-1019-aws** |

다시 확인할 때 (§2.4 의 Docker 버전도 같이 나온다):

```bash
lsb_release -ds; uname -r; docker --version; docker compose version
```

#### 4 vCPU 를 어떻게 나눠 쓰나

`.env` 의 `SPARK_WORKER_CORES` 는 **`nproc`(4) 이하**여야 한다. 지금 배분:

| 노드 | `SPARK_WORKER_CORES` | 왜 |
| --- | --- | --- |
| `app` | **2** | 같은 노드가 **사용자 트래픽도 받는다**. 나머지를 api·postgres·nginx 가 쓴다 |
| `data` | **3** | 사용자 요청을 안 받아 배치에 더 줄 수 있다 |

| API 문서 | springdoc-openapi | **3.1.0** | `backend/build.gradle` |
| PDF | openhtmltopdf-pdfbox / svg-support | **1.1.28** | `backend/build.gradle` |

패키징 결과는 `backend/build/libs/*.jar` 이고 컨테이너 안에서는 `/app/app.jar` 다.

### 2.2 프런트엔드 / 웹서버

| | 종류 | 버전 | 어디에 박혀 있나 |
| --- | --- | --- | --- |
| **웹서버** | **nginx** (alpine) | **1.27** | `frontend/Dockerfile` 2단계 |
| 빌드 런타임 | Node.js (alpine) | **22** | `frontend/Dockerfile` 1단계, CI 는 `node:22-alpine` |
| 번들러 | Vite | **8** | `frontend/package.json` |
| 언어 | TypeScript | **~6.0.2** | `frontend/package.json` |
| UI | React **19** · React Router **v7** · Tailwind **v4** · shadcn/ui | | `frontend/README.md` |

**프런트는 정적 파일이다.** `npm run build`(= `tsc -b && vite build`) 가 `dist/` 를 만들고
nginx 이미지가 그것을 `/usr/share/nginx/html` 로 복사한다. Node 는 최종 이미지에 없다.

**nginx 설정은 이미지에 굽지 않는다.** compose 가 [`deploy/prod/app/nginx/app.conf`](../deploy/prod/app/nginx/app.conf)
를 읽기 전용으로 마운트한다 — 설정만 고칠 때 프런트를 다시 빌드하지 않기 위해서다.

nginx 설정의 핵심 세 가지(전부 `app.conf` 에 주석과 함께 있다):

| 설정 | 없으면 |
| --- | --- |
| `try_files $uri $uri/ /index.html` | SPA 딥링크(`/analyze` 새로고침)가 404. **Vite dev server 는 알아서 처리해서 로컬에서 안 드러난다** |
| `resolver 127.0.0.11` + `set $api_upstream` (변수 proxy_pass) | api 컨테이너 재생성 후 nginx 가 옛 IP 로 보내 `/api` 만 502·504 |
| `proxy_set_header X-Forwarded-Proto $scheme` | 스프링이 자기를 http 로 알고 Swagger "Try it out" 이 막힌다 (`application-prod.yaml` 의 `forward-headers-strategy: framework` 와 한 쌍) |

## 3. 빌드 시 사용되는 환경변수

### 3.1 빌드 자체는 환경변수를 요구하지 않는다

| 빌드 | 명령 | 환경변수 |
| --- | --- | --- |
| 백엔드 | `./gradlew bootJar -x test` | **없음** |
| 프런트 | `npm ci && npm run build` | **없음** (아래 `VITE_*` 는 전부 선택값) |
| 이미지 | `docker compose build` | `API_TAG` · `WEB_TAG` · `RAG_TAG` — 이미지 **이름**을 정하는 값이라 빌드 내용에는 영향이 없다 |

**DB 접속 정보는 빌드에 필요 없다.** `backend/Dockerfile` 이 `-x test` 로 굽고 테스트는 CI 가
따로 돌린다 — 그래서 이미지 빌드에 DB 가 필요 없다.

### 3.2 프런트 빌드 타임 변수 (`VITE_*`)

Vite 는 빌드 시점에 값을 정적으로 박아 넣는다. **운영 빌드에서는 둘 다 지정하지 않는다.**

| 변수 | 기본값 | 넣으면 |
| --- | --- | --- |
| `VITE_API_BASE_URL` | `/api` | API 주소를 절대 경로로 바꾼다. 운영은 nginx 가 같은 오리진에서 프록시하므로 **비워 둔다** |
| `VITE_USE_MOCK` | `false` | `'true'` 문자열이면 모든 API 호출이 mock 응답으로 간다. **운영에 절대 넣지 않는다** |

원본은 `frontend/.env.example` 이다.

### 3.3 실행 시 환경변수 — `app` 노드

실체는 **`/srv/pickage/app.env`** 이고 체크아웃 안의 `deploy/prod/app/.env` 는 그것을 가리키는
심볼릭 링크다(배포 잡이 매번 다시 건다). 원본은 [`deploy/prod/app/.env.example`](../deploy/prod/app/.env.example).

| 변수 | 필수 | 쓰는 서비스 | 설명 |
| --- | --- | --- | --- |
| `POSTGRES_DB` | ✅ | postgres · api | `pickage` |
| `POSTGRES_USER` | ✅ | postgres · api | `pickage` |
| `POSTGRES_PASSWORD` | ✅ | postgres · api · similarity-loader | **운영에서 처음 만든다** — `openssl rand -base64 24` |
| `API_TAG` · `WEB_TAG` · `RAG_TAG` | ✅ | api · web · rag-api | 이미지 태그(커밋 SHA). 배포 잡이 갈아 끼운다. **셋이 서로 달라도 정상** |
| `MINIO_ROOT_USER` · `MINIO_ROOT_PASSWORD` | ✅ | spark-worker-2 | s3a 용. **루트가 아니라 `data` 노드에서 발급한 서비스 계정 키**를 넣는다 |
| `PRIVATE_IP` | ✅ | spark-worker-2 | 이 노드(app)의 사설 IP `172.26.6.235` |
| `SPARK_MASTER_HOST` | ✅ | spark-worker-2 | data 노드 사설 IP `172.26.8.249` |
| `SPARK_WORKER_CORES` | ✅ | spark-worker-2 | `2` — `nproc` 이하 |
| `SPARK_WORKER_MEMORY` | ✅ | spark-worker-2 | `5g` — **`mem_limit` 6.5g 와 짝이다**(§5.3) |
| `GITHUB_COMMUNITY_TOKEN` | **커뮤니티 쓰려면 필수** | api | 비어 있으면 새로고침이 거절된다 (아래 ⚠) |
| `COMMUNITY_ENABLED` | **커뮤니티 쓰려면 필수** | api | `true`/`false`. 기본 `false`. 현재 운영은 `true` |
| `GMS_API_KEY` · `GMS_BASE_URL` · `GMS_REQUEST_PATH` · `GMS_AUTH_HEADER` · `GMS_AUTH_SCHEME` · `GMS_MODEL` | **커뮤니티·기능비교 쓰려면 필수** | api · rag-api | **여섯 개가 전부 있어야** 실제 GMS 클라이언트가 붙는다. 하나라도 비면 조용히 `FakeCommunitySummarizer` 로 남는다 |
| `PICKAGE_OPS_S3_ENDPOINT` · `_ACCESS_KEY` · `_SECRET_KEY` | 선택 | api | 주간 수집 운영 API. 비면 ops API 만 "설정이 없습니다". **현재 운영은 채워져 있다** |
| `PICKAGE_CURATED_S3_ENDPOINT` · `_ACCESS_KEY` · `_SECRET_KEY` | 선택 | api | curated 로더용. **현재 운영은 채워져 있다** (소비자 코드는 아직 없어 동작에 영향 없음) |

> **현재 `app.env` 는 위 표의 키가 전부 채워져 있다** (2026-09-22 확인). 확인:
> `sudo -u gitlab-runner grep -cE '^[A-Z0-9_]+=x27 /srv/pickage/app.env` → `0`
>
> ⚠ 키 이름에 숫자가 들어가므로(`PICKAGE_OPS_S3_*`) `[A-Z_]` 로만 훑지 않는다.

compose 가 서비스에 넘기는 값 중 `.env` 에 없는 것:

| 변수 | 값 | 어디서 |
| --- | --- | --- |
| `SPRING_PROFILES_ACTIVE` | `prod` | `compose.yaml` 에 박혀 있다 |
| `DB_URL` | `jdbc:postgresql://postgres:5432/${POSTGRES_DB}` | `compose.yaml` 이 조립 |
| `DB_USERNAME` · `DB_PASSWORD` | `${POSTGRES_USER}` · `${POSTGRES_PASSWORD}` | `compose.yaml` |
| `JAVA_TOOL_OPTIONS` | `-XX:MaxRAMPercentage=70` | `compose.yaml` |
| `PICKAGE_DOCS_PATH` | `/var/lib/pickage/docs` | `compose.yaml` |
| `README_SOURCE_ROOT` | `/srv/pickage/docs` | rag-api |
| `PGHOST` · `PGPASSWORD` · `PICKAGE_MINIO_ENV` · `PICKAGE_SIMILAR_PACKAGE_WORK_DIR` | | similarity-loader |

> ### ⚠ `PICKAGE_` 접두사는 장식이 아니다
>
> 백엔드가 읽는 프로퍼티가 `pickage.ops.s3.*` 이고 **스프링이 이름만으로 이어 준다**
> (`PICKAGE_OPS_S3_ACCESS_KEY` → `pickage.ops.s3.access-key`). 이름을 줄이면 **오류가 아니라
> 조용히 기본값으로 떨어져** ops API 가 "설정이 없습니다" 로만 답한다.
> `OpsEnvironmentContractTest` 가 compose 와 코드를 대조한다.

### 3.4 실행 시 환경변수 — `data` 노드

실체는 **`/srv/pickage/data.env`**, 체크아웃 안의 `deploy/prod/data/.env` 는 심볼릭 링크다.
원본은 [`deploy/prod/data/.env.example`](../deploy/prod/data/.env.example).

| 변수 | 필수 | 설명 |
| --- | --- | --- |
| `MINIO_ROOT_USER` · `MINIO_ROOT_PASSWORD` | ✅ | **지금 도는 MinIO 와 같은 값**을 넣는다. 바꾸면 발급한 서비스 계정이 못 쓰게 되어 수집이 멈춘다 |
| `PRIVATE_IP` | ✅ | 이 노드의 사설 IP `172.26.8.249` |
| `SPARK_WORKER_CORES` · `SPARK_WORKER_MEMORY` | ✅ | `3` · `7g` — `mem_limit` 10g 안에 executor 힙 + driver 1g + 데몬이 들어가야 한다 |
| `AI_TAG` | ✅ | 유사도 배치 이미지 태그. `deploy-ai` 잡이 갈아 끼운다 |
| `AI_CORPUS_PREFIX` · `AI_DST_RESULT` · `AI_MODEL_NAME` · `AI_MODEL_ALIAS` | ✅ | 회차마다 바뀌지 않는 고정값. **날짜·모델 버전은 여기 넣지 않는다** — 포인터 둘이 정한다 |
| `AI_DEPENDENTS_PATH` | 선택 | 보완재 관문용. 비면 그 관문만 건너뛴다 |
| `MLFLOW_TRACKING_URI` | ✅ | `http://127.0.0.1:5000` |
| `OSS_SHIFT_UA_CONTACT` | ✅ | 수집기 User-Agent 연락처. **비면 수집기가 시작하지 않는다** |

`.env` 밖에 손으로 두는 것 셋 (커밋되지 않는다):

```bash
cp pipeline/minio/.env.data.example pipeline/minio/.env.data   # MinIO 자격증명 (파일로 읽는다)
sudo mkdir -p /srv/pickage/ingest-work                          # 산출물, 주당 약 10 GB
sudo mkdir -p /srv/pickage/secrets                              # GCP 서비스 계정 키
sudo chown -R 1000:1000 /srv/pickage/ingest-work /srv/pickage/secrets
```

> ⚠ 부모 `/srv/pickage` 를 통째로 `chown` 하지 않는다. 거기에 배포 러너 소유의 `data.env` 가 있다.

> 그것을 읽기 전용으로 마운트해서 443 을 열기 때문이다. 없으면 `up` 이 뜨지 않는다.
>

컨테이너 `app.conf` 가 `include` 하므로 **함께 있어야 한다.**


## 5. 배포 시 특이사항

### 5.1 레지스트리가 없다 — 로컬 이미지 스토어가 곧 롤백 자산이다

서버에서 직접 빌드한다. 그래서 **`docker image prune -a` 와 `docker system prune -a` 는 금지**다.
이전 SHA 태그가 거기 해당해서 한 번 치면 되돌아갈 곳이 하나도 안 남는다.

```bash
docker image prune -f      # dangling 만. 이것만 안전하다
```

배포 잡이 매 배포 끝에 최근 5개 태그만 남기고 정리한다.

### 5.2 롤백은 태그를 되돌리고 다시 올리는 것이 전부다

```bash
cd /srv/pickage/repo/deploy/prod/app
docker images pickage-api --format '{{.Tag}}\t{{.CreatedSince}}'    # 날짜를 보고 고른다
sed -i "s/^API_TAG=.*/API_TAG=<이전 SHA>/" /srv/pickage/app.env
docker compose up -d --no-build --wait
```

`--no-build` 를 빼면 compose 가 지금 소스로 그 태그를 다시 구워서 **이름만 옛날인 이미지**가 된다.

태그를 셋(`API_TAG`·`WEB_TAG`·`RAG_TAG`)으로 나눈 이유가 이것이다 — API 는 멀쩡한데 화면만
깨진 배포가 실제로 생기고 그때 프런트만 되돌린다.

> **⚠ 스키마는 롤백되지 않는다.** Flyway 는 적용만 하고 되돌리지 않는다. 그래서
> `DROP COLUMN`·`RENAME` 이 들어간 배포는 롤백할 수 없다 — 컬럼을 지울 때는 배포를 둘로 나눈다.
>
> **⚠ 롤백은 다음 머지까지만 유효하다.** `develop`·`main` 에 무엇이든 머지되면 배포가 덮어쓴다.

### 5.3 메모리 — 컨테이너에 스왑을 주지 않는다

호스트에는 Swap 2 GiB 가 있지만 **모든 서비스에 `memswap_limit` = `mem_limit` 을 박아** 컨테이너
스왑을 0 으로 막았다. Docker 는 `memswap_limit` 을 안 주면 총량을 `mem_limit` 의 **2배**로 잡는데,
호스트에 스왑을 넣는 순간 그 기본값이 실제로 동작하기 때문이다.

`app` 노드 상한 합계 (총 15 GiB):

```
postgres 2g + api 1.6g + web 0.25g + rag-api 0.5g + similarity-loader 0.5g + worker②(executor 5g + 데몬 ~1g) ≈ 11g
```

> **`SPARK_WORKER_MEMORY` 는 `mem_limit` 과 짝이다.** 그 값이 executor 힙의 상한이 되고 힙·비힙·
> worker 데몬이 같은 cgroup 에 들어간다. **한쪽만 올리면 첫 풀사이즈 executor 에서 OOM Kill** 이다.

✅ 확인 (두 값이 같아야 한다):

```bash
docker inspect pickage-app-postgres-1 --format '{{.HostConfig.Memory}} {{.HostConfig.MemorySwap}}'
```

### 5.4 배치 시각에 배포하지 않는다 (= 배치 시각에 머지하지 않는다)

배포가 배치와 겹치면 Gradle·npm 빌드가 메모리를 더 먹고 컨테이너 스왑이 0 이라 **즉시 OOM Kill**
이다. 커널이 무엇을 죽일지 고를 수 없다 — **Postgres 를 고를 수도 있다.**
배포가 자동이 된 뒤로 이것을 막아 주는 것은 **머지 시각뿐이다.**

### 5.5 그 밖에 알고 있어야 하는 것

| | |
| --- | --- |
| **배포 중 수십 초 끊긴다** | 무중단은 하지 않는다. api 인스턴스가 하나라 블루/그린이 필요하다 |
| **죽고 있는 컨테이너가 `ps` 로는 안 보인다** | `restart: unless-stopped` 라 계속 죽어도 목록에 그대로 보인다. healthcheck 가 없는 spark-worker-2·similarity-loader 는 `(healthy)` 표시도 없다 |
| **nginx 설정만 고쳤으면 다시 빌드하지 않는다** | 설정은 마운트라 컨테이너를 다시 만들지 않는다. `nginx -t && nginx -s reload` 로 끝난다 |

✅ 죽고 있는 것이 있는지 — **전부 `running` 이면 정상**:

```bash
docker inspect -f '{{.Name}} {{.State.Status}} 재시작 {{.RestartCount}}회' $(docker compose ps -aq)
```

### 5.6 배포가 실패하면 서버는 어떤 상태인가

| 어디서 실패했나 | 서버 상태 |
| --- | --- |
| `docker compose build` | 컨테이너는 **그대로 전 버전**. 사이트 멀쩡 |
| `up -d --wait` 시간 초과 | **새 컨테이너로 바뀌었고 healthy 가 아니다.** 사이트가 내려가 있다 |
| `nginx -t` | 컨테이너는 새것, nginx 는 옛 설정. 사이트 멀쩡 |
| 마지막 `curl` | 배포는 적용됨. nginx·TLS 쪽을 본다 |

가장 흔한 실패는 **Flyway** 다. 마이그레이션이 깨지면 api 가 기동에 실패하고 `restart` 때문에
같은 실패를 반복한다. `docker compose logs --since 5m api | head -50` 으로 보고 그다음은 롤백이다.

> ⚠ `/srv/pickage/app.env` 의 태그는 "마지막으로 **성공**한 것" 이 아니라 "마지막으로 **시도**한
> 것" 이다. 되돌릴 때 그 값을 기준으로 삼지 말고 `docker images` 의 날짜를 본다.

### 5.7 하지 말 것

| | 무슨 일이 생기나 |
| --- | --- |
| `docker compose down -v` | **운영 DB 가 사라진다** |
| `docker image prune -a` · `docker system prune -a` | 롤백 대상이 전부 사라진다 |
| `sudo systemctl start nginx` | 호스트 nginx 가 80·443 을 뺏어 다음 `up` 이 실패한다 |
| `ports:` 에서 `127.0.0.1:` 접두사 제거 | TLS 도 인증도 없는 문이 열린다 |
| `.env` 를 커밋 | 운영 DB 비밀번호가 GitLab 히스토리에 영구히 남는다 |
| 적용된 `V__` 마이그레이션 파일 수정 | checksum 불일치로 **운영 앱이 기동에 실패한다** |
| `API_TAG=latest` | 지금 뜬 게 어느 커밋인지 알 수 없고 롤백할 이름이 없어진다 |
| `/srv/pickage/repo` 에서 소스 고치기 | 다음 배포의 `git checkout -f` 가 덮어쓴다 |
| 체크아웃 안의 `.env` 심볼릭 링크를 `sed -i` | 링크가 일반 파일이 되어 태그가 두 곳에서 갈린다 |
