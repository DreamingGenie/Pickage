## 3. 생태계 분석 화면

| | |
| --- | --- |
| 라우트 | `/report/:reportId` — 기본 탭 |
| 부르는 API | `GET /api/packages/dependents` · `/api/packages/downloads` · `/api/packages/version` |

**여기가 MVP 의 중심이다.** 시간을 가장 많이 쓴다. 위에서 아래로 훑어 내려가며 말한다.

### 조작

| # | 무엇을 | 어디를 | 무엇이 보이나 |
| --- | --- | --- | --- |
| 1 | 요약 카드로 focus 이동 | 상단 **한눈에 보기** | 현재 **다운로드 수는 `ajv` 가 더 많다** |
| 2 | 그래프 영역으로 focus 이동 | 의존 그래프 | **`zod` 가 앞지르기 시작한 것**이 보인다 |
| 3 | 아래로 스크롤 | 유지 · 유입 · 이탈 → 이탈 사유 → 어디로 옮겨 갔나 | 유입·이탈과 다른 패키지로 이동한 기록 |

### 말한 것

> 빠르게 보여 드리기 위해 모든 분석이 완료된 페이지로 보여 드리겠습니다.
> 요약 카드를 보면 현재 다운로드 수는 `ajv` 가 더 많습니다.
> 그런데 저는 지금 당장의 수치 말고 **수치가 변하는 흐름**을 보고 싶습니다. 그 아래를 볼까요?
> 의존 그래프를 보니 `zod` 가 앞지르기 시작한 것을 볼 수 있습니다.
> 개발자들의 선택은 점점 `zod` 로 가는 것 같아요.
> 그 아래를 보면 유입과 이탈, 다른 패키지로 이동한 기록까지 확인할 수 있습니다.

**이 장면의 핵심 주장**: 다운로드 수는 같은 프로젝트의 반복 빌드로도 늘어난다.
의존 선언은 같은 버전을 몇 번 내려받아도 **한 건**이라 실제 선택의 움직임을 보여 준다.

### ⚠ 데이터 상태를 미리 확인한다

**고른 패키지가 "데이터 축적 중" 으로 뜨면 시연이 밋밋해진다.** 자료가 모자란 패키지는
그렇게 표시되고, `repo_url` 이 없으면 "미확인" 이다. 발표 전에 직접 눌러 본다.

## 4. 기능 비교 화면

| | |
| --- | --- |
| 라우트 | 같은 `/report/:reportId`, 두 번째 탭 |
| 부르는 API | `GET /api/packages/versions` · `/api/packages/env` · `POST /api/packages/feature-comparison` |
| 뒤에 있는 것 | `rag-api` 컨테이너 → GMS LLM |

### 조작

| # | 무엇을 | 어디를 | 무엇이 보이나 |
| --- | --- | --- | --- |
| 1 | **기능 비교** 탭으로 이동 | 보고서 상단 탭 | |
| 2 | **설치하기 전에 알아 둘 것** 으로 focus 이동 | 환경 · 설치 조건 표 | 설치 전에 확인할 사항 |
| 3 | 아래 **AI 기능 비교** 로 focus 이동 | 차이점 정리 | `zod` 는 TypeScript 중심, `ajv` 는 JSON Schema 중심 |

### 말한 것

> 다음은 기능입니다. Pickage 는 **선택한 버전의 자료를 근거로** 공통점과 차이를 정리합니다.
> 설치 전에 확인할 사항부터 볼 수 있네요.
> 하지만 저는 기능이 뭐가 다른지 궁금합니다. 여러 LLM 이나 인터넷 검색으로는 핵심이 뭔지
> 알기 어렵겠죠. 그래서 Pickage 는 **RAG 와 데이터를 통해 핵심만 두어 문장으로** 정리합니다.
> 보고서에서는 `zod` 는 TypeScript 중심, `ajv` 는 JSON Schema 중심이라는 차이가 보입니다.
> 우리 프로젝트는 `ajv` 가 더 맞을 것 같아요.
> 하지만 아까 생태계 움직임을 봤으니 **미리 마이그레이션 준비를 계획에 반영**할 겁니다.

**이 장면의 핵심 주장**: LLM 은 과거 지식이나 다른 버전의 정보를 섞는다.
Pickage 는 **버전을 고정하고 그 버전의 자료를 근거로** 비교한다.

### ⚠ 실제로 돌리면 가장 위험한 장면이다

외부 LLM(GMS) 을 실제로 부르고 **비동기**라 대기가 생긴다. 발표에서는 완성된 화면으로
넘겨 이 위험을 피했다. 실제로 돌려 보일 거면 같은 조합으로 미리 한 번 돌려 시간을 잰다.

## 6. 내보내기 — PDF 와 HAND-OFF

| | |
| --- | --- |
| 버튼 | 보고서 상단의 **PDF 다운로드** · **HAND-OFF** |
| 부르는 API | `POST /api/report/pdf` → `GET /api/report/pdf/{reportId}/file` · HAND-OFF Markdown |

### 조작

| # | 무엇을 | 어디를 | 무엇이 일어나나 |
| --- | --- | --- | --- |
| 1 | PDF 다운로드 위치를 가리킨다 | 보고서 상단 | → **준비된 PDF 로 전환** |
| 2 | HAND-OFF 위치를 가리킨다 | PDF 옆 | → **준비된 Markdown 으로 전환** |

### 말한 것

> 이렇게 서비스에 대해 알아봤는데요, "그래서 이걸로 어떻게 하라는 거야?" 라는 의문이 드실 겁니다.
> 우리 서비스는 **정보 플랫폼**이기 때문에, 알지 못하는 프로젝트에 어떤 패키지가 어울릴지
> 추천하는 무책임한 행동은 하지 않습니다. 하지만 그 과정에 도움을 드릴 수는 있습니다.
> 보고서를 팀원이나 에이전트와 공유할 수 있게 다운받는 기능입니다.
>
> PDF 를 공유하면 "왜 이 패키지를 검토하는지" 자료를 보며 팀과 논의할 수 있습니다.
> MD 는 **에이전트가 읽기 쉽게 구조화**했습니다. 그래서 프로젝트 폴더에 넣고
> "보고서 보고 어떤 패키지 쓸지 골라줘" 라고 요청할 수 있습니다.

### ⚠ 한글 폰트

PDF 는 자형을 문서에 심어야 한다. **폰트가 없으면 예외 없이 글자만 사라진다.**
미리 만든 PDF 를 쓰더라도 만들 때 한 번은 열어 확인한다.

## 7. 시연하지 않은 것

문서에 있지만 이번 발표에서는 뺐다. 다시 시연할 때 넣을지 판단하라고 적어 둔다.

| | 왜 뺐나 |
| --- | --- |
| **근거 드로어 (Evidence Drawer)** | 해설의 출처를 되짚는 화면. 시간이 모자랐다. `?evidence=` 쿼리로 바로 열 수 있다 |
| **후보 상한(3개) 안내** | 네 번째 후보를 누르면 기존 1개를 해제하라는 안내가 뜬다 |
| **직접 추가 입력** | 추천 후보에 없는 패키지를 직접 넣는 동작 |
| **오류 상태** | 없는 패키지명을 넣으면 `not_found` 로 확정이 막힌다 |
| **운영 뒷면** | Spark worker 둘, 주간 수집 상태. 화면이 아니라 터미널이라 발표에 맞지 않았다 |
