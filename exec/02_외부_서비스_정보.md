# 외부 서비스 정보

가입·발급이 필요한 외부 서비스와, 새 환경에서 붙일 때 필요한 정보다.

**여기에 실제 키 값을 적지 않는다.** 값이 사는 자리만 적는다 — 한 번 커밋된 비밀은
지워도 GitLab 히스토리에 남는다. 값 사본은 팀 노션에 있다.

| 서비스 | 무엇에 | 가입·발급 | 없으면 |
| --- | --- | --- | --- |
| [Google Cloud Platform](#1-google-cloud-platform-bigquery--gcs) | deps.dev 원천 데이터 수집 | **필요** (서비스 계정 키) | 주간 수집이 시작조차 못 한다 |
| [npm registry](#2-npm-registry--ecosystems) | 패키지 메타·다운로드 수 | 불필요 (무인증) | 다운로드 지표가 빈다 |
| [ecosyste.ms](#2-npm-registry--ecosystems) | 키워드·설명 코퍼스 | 불필요 (무인증) | 유사도 코퍼스가 갱신되지 않는다 |
| [GitHub REST API](#3-github-rest-api) | 커뮤니티(이슈·댓글) 수집 | **필요** (PAT) | 커뮤니티 새로고침이 거절된다 |
| [GMS (SSAFY LLM)](#4-gms--ssafy-llm-게이트웨이) | 기능 비교 해설 · 커뮤니티 요약 | **SSAFY 지급** | 해설이 나오지 않는다 |
| [도메인 · Let's Encrypt](#5-도메인과-tls-인증서) | HTTPS | **필요** | 443 이 안 떠 사이트가 안 열린다 |
| [GitLab (SSAFY)](#6-gitlab-ssafy) | 소스 · CI/CD | **필요** | 자동 배포가 없다 |
| [SSAFY GPU 서버](#7-ssafy-gpu-서버) | 임베딩 모델 학습 | **필요** | 모델을 새로 학습할 수 없다 |

**소셜 로그인·결제·포톤 클라우드는 쓰지 않는다.** 서비스에 로그인 기능 자체가 없다.

**MinIO·MLflow·Spark·PostgreSQL 은 외부 서비스가 아니다** — 전부 우리 노드의 컨테이너다
(AWS S3·RDS 를 쓰지 않는다).

## 0. 이름이 비슷한 키·계정 구별

"서비스 계정", "키", "ROOT" 라는 말이 세 곳에서 다른 뜻으로 쓰인다. 포팅할 때 가장 헷갈리는 지점이다.

| 이름 | 무엇 | 발급처 | 사는 자리 | 쓰는 것 | 헷갈리는 이유 |
| --- | --- | --- | --- | --- | --- |
| **GCP 서비스 계정 키** | Google 서비스 계정 `pickage-ingest@…` 의 JSON 키 | GCP 콘솔 IAM | data 노드 `/srv/pickage/secrets/gcp-service-account.json` | 주간 수집(BigQuery 쿼리·GCS 쓰기) | "서비스 계정" 이라는 말을 MinIO 도 쓴다 |
| **MinIO 루트 자격증명** | MinIO 서버의 관리자 계정 | data 노드 `.env` 에서 처음 정한 값 | data 노드 `/srv/pickage/data.env` 의 `MINIO_ROOT_USER`·`MINIO_ROOT_PASSWORD` | data 노드 MinIO 컨테이너 자신, 그 노드의 Spark·수집 컨테이너 | app 노드 `.env` 에 **같은 변수 이름**이 있지만 값은 루트가 아니다(아래) |
| **MinIO 서비스 계정 키 (Spark worker② 용)** | 루트로 발급한 하위 계정 (`mc admin user svcacct add`) | data 노드에서 `mc` 로 발급 | app 노드 `/srv/pickage/app.env` 의 `MINIO_ROOT_USER`·`MINIO_ROOT_PASSWORD` | app 노드 Spark worker② 의 s3a | **변수 이름이 ROOT 인데 값은 서비스 계정 키다.** `spark-env.sh` 가 그 이름을 읽기 때문. 루트 값을 복사해 넣으면 안 된다 |
| **MinIO 로더 계정 키** | 버킷별 권한을 가른 별도 사용자 2개 (`pipeline/minio/policies/similarity-loader.json`, `api-loader.json`) | data 노드에서 `mc` 로 발급 | app 노드 `/srv/pickage/secrets/minio-similarity-loader.env`, `minio-api-loader.env` 의 `PICKAGE_S3_ACCESS_KEY`·`PICKAGE_S3_SECRET_KEY` | similarity-loader · package-env-loader | GCP 키와 같은 `secrets/` 폴더에 산다. 이름을 일부러 `PICKAGE_S3_*` 로 해서 ROOT 값을 넣지 못하게 했다 |
| **GMS API 키** | SSAFY LLM 게이트웨이 키 | SSAFY 지급 | app 노드 `/srv/pickage/app.env` 의 `GMS_API_KEY` (+ 나머지 5개) | api(커뮤니티 요약) · rag-api(기능 비교) | 교체 후 `restart` 로는 반영 안 됨 — `up -d --force-recreate api rag-api` |
| **GitHub PAT** | 개인 액세스 토큰 | 팀원 GitHub 계정 | app 노드 `/srv/pickage/app.env` 의 `GITHUB_COMMUNITY_TOKEN` | api(커뮤니티 수집) | 비면 거절, 만료되면 401 |

**빠르게 가르는 기준**

- 파일이 `.json` 이면 GCP. `.env` 안의 `MINIO_*`·`PICKAGE_S3_*` 면 MinIO. 둘은 서로 아무 관계가 없다.
- `MINIO_ROOT_*` 는 **노드에 따라 뜻이 다르다.** data 노드에서는 진짜 루트, app 노드에서는 루트로 발급한 하위 키.
- `/srv/pickage/secrets/` 에는 GCP 키 1개와 MinIO 로더 키 2개가 함께 산다. 배포 잡이 저장소 밖 경로는 지우지 않기 때문에 거기 두는 것이고, 종류가 같아서가 아니다.
- 로컬 개발에는 이 가운데 아무것도 필요 없다. 로컬 MinIO 는 `pipeline/minio/.env` 의 임의 값, GCP 는 개인 ADC 로 붙는다.

## 1. Google Cloud Platform (BigQuery + GCS)

원천 데이터 전체가 여기서 온다.

| | |
| --- | --- |
| 프로젝트 | `oss-shift-a506` |
| 읽는 데이터셋 | `bigquery-public-data.deps_dev_v1` (공개 데이터셋) |
| 산출물 버킷 | `gs://oss-shift-a506-raw` (US) |
| 켤 API | BigQuery API · Cloud Storage API |
| 쓰는 코드 | [`pipeline/collectors/bigquery/`](../pipeline/collectors/bigquery/) |

**인증 경로가 둘이다.** 파이썬 클라이언트는 `GOOGLE_APPLICATION_CREDENTIALS`, gcloud CLI 는
`CLOUDSDK_AUTH_CREDENTIAL_FILE_OVERRIDE` 를 본다. `pipeline/Dockerfile` 이 둘 다
`/opt/work/secrets/gcp-service-account.json` 을 가리키게 세워 둔다 —
**하나만 세우면 수집 중간(`gcs_sync`)에서 인증 실패한다.**

```bash
# data 노드
sudo mkdir -p /srv/pickage/secrets
# 키 파일을 /srv/pickage/secrets/gcp-service-account.json 으로 둔다
sudo chown 1000:1000 /srv/pickage/secrets/gcp-service-account.json
```

> ### ⚠ 과금이 걸린 유일한 외부 서비스다
>
> BigQuery 는 스캔 바이트로 과금한다. 티어별 대략 — `t0` 52.6 GiB(최초 1회) ·
> `t1` 51 GiB(백필) · `t2` 23 GiB(매주) · `t2m` 35 GiB(월 1회).
>
> **항상 `--plan` 을 먼저 돌린다.** dry-run 만 하고 예산 합계를 보여 준다. 과금은 0 이다.
>
> ```bash
> .venv-bq/Scripts/python pipeline/collectors/bigquery/collect.py --tier t0 --plan
> ```
>
> `maximum_bytes_billed` 를 걸어 두어 초과하면 **BigQuery 가 잡을 거부하고 과금이 안 난다.**
>
> **`deps_dev_v1` 은 공개 데이터셋이지만 쿼리하는 쪽에 결제 계정이 없으면 잡이 거부된다.**
> 스캔 바이트는 쿼리를 던지는 프로젝트에 청구된다 — 새 GCP 프로젝트로 옮길 때 여기서 막힌다.

> ### 서비스 계정과 권한 (2026-09-25 GCP 콘솔·gcloud 로 확인)
>
> | | |
> | --- | --- |
> | 서비스 계정 | `pickage-ingest@oss-shift-a506.iam.gserviceaccount.com` (표시 이름 "Pickage weekly ingest"). **프로젝트에 서비스 계정은 이것 하나뿐이다** |
> | 프로젝트 역할 | `roles/bigquery.jobUser` (쿼리 잡 실행) · `roles/bigquery.dataEditor` (스테이징 데이터셋에 표 생성·삭제) |
> | 버킷 역할 | `gs://oss-shift-a506-raw` 에 `roles/storage.objectAdmin` (extract 잡의 Parquet 쓰기와 `gcloud storage rsync` 읽기). 프로젝트 수준 Storage 역할은 없다 — **버킷 IAM 에 직접 준 것**이라 새 버킷을 만들면 거기에도 다시 줘야 한다 |
> | 스테이징 데이터셋 | `oss-shift-a506.staging` (US). `defaultTableExpirationMs=259200000` = **3일 자동 만료**. 새 프로젝트에서는 이 데이터셋을 이 만료값으로 먼저 만들어야 한다(수집기가 만들지 않는다) |
> | 결제 | 프로젝트에 결제 계정이 연결돼 있다. 없으면 공개 데이터셋 쿼리도 거부된다 |
> | 사람 계정 | 프로젝트 소유자(`roles/owner`) 1명 — 데이터 파트(전진). 열람자(`roles/browser`) + 버킷 `objectViewer` 1명 — 데이터 파트(성승재). **서비스 기동에는 사람 계정이 필요 없다** |
>
> 새 환경에서 재현하는 순서:
>
> 1. 프로젝트 생성 → 결제 계정 연결 → BigQuery API · Cloud Storage API 켜기
> 2. 버킷 생성(US) · 데이터셋 `staging` 생성(기본 표 만료 3일)
> 3. 서비스 계정 생성 → 프로젝트 역할 `bigquery.jobUser` + `bigquery.dataEditor`, 버킷 역할 `storage.objectAdmin`
> 4. 키(JSON) 발급 → data 노드 `/srv/pickage/secrets/gcp-service-account.json` (소유 1000:1000, 600)
> 5. `pipeline/collectors/bigquery/collect.py` 의 상수 `PROJECT`·`BUCKET` 을 새 이름으로 바꾼다 — **환경변수가 아니라 코드 상수다**
> 6. `--plan` 으로 dry-run 이 도는지 확인(과금 0)
>
> **로컬 PC 와 서버는 인증이 다르다.** 서버 컨테이너는 위 키 파일을 `GOOGLE_APPLICATION_CREDENTIALS`
> (파이썬 클라이언트)와 `CLOUDSDK_AUTH_CREDENTIAL_FILE_OVERRIDE`(gcloud CLI) 두 변수로 본다.
> 로컬에서 `.venv-bq` 로 돌릴 때는 그 변수가 없고, `gcloud auth application-default login` 으로 만든
> 사용자 ADC(소유자 계정)로 붙는다. 둘 다 같은 프로젝트에 청구된다.
>
> ✅ 확인(2026-09-25): 서버와 같은 서비스 계정 키만 세운 로컬 세션에서 `collect.py --tier t2 --plan --force` 가
> 최신 스냅샷 조회·GCS 매니페스트 확인·잡 3개 dry-run(23.6 GiB 추정)까지 통과했다. 위 역할만으로 수집 경로가 열린다.

## 4. GMS — SSAFY LLM 게이트웨이

**SSAFY 지급이다.** 팀이 따로 가입하거나 신청하지 않았다. 키 사본은 팀 노션.

| 변수 | 값 (2026-09-22 운영) |
| --- | --- |
| `GMS_API_KEY` | **(비밀)** — 팀 노션 |
| `GMS_BASE_URL` | `https://gms.ssafy.io/gmsapi/api.openai.com` |
| `GMS_REQUEST_PATH` | `/v1/responses` |
| `GMS_AUTH_HEADER` | `Authorization` |
| `GMS_AUTH_SCHEME` | `Bearer` |
| `GMS_MODEL` | `gpt-5.4-mini` |

**GMS 는 OpenAI API 앞에 선 프록시다.** 코드가 `BASE_URL + REQUEST_PATH` 를 그대로 이어 붙이고
헤더 이름·스킴도 값에서 받으므로 **바꿔 끼울 때 이 형태를 지켜야 한다.**

✅ 확인: `docker compose logs --since 5m rag-api` 에 인증 오류가 없고 기능 비교 탭에 해설이 나온다.

## 5. 도메인과 TLS 인증서

| | |
| --- | --- |
| 도메인 | `j15a506.p.ssafy.io` — **SSAFY 제공. 프로젝트가 끝나면 회수된다** |
| 발급 | 호스트의 certbot, `--nginx` 플러그인 (Let's Encrypt) |
| 인증서 경로 | `/etc/letsencrypt/live/<도메인>/` — 컨테이너 `web` 에 읽기 전용 마운트 |
| 만료 | 2026-11-30 |

**포팅하는 쪽은 자기 도메인과 인증서를 직접 준비해야 한다.** 이 저장소의 `deploy/` 문서는
인증서가 이미 있다고 가정하고 시작한다.

### 5.1 발급 절차 (최초 1회, 호스트에서)

```bash
DOMAIN="<자기 도메인>"
sudo apt install -y nginx
```

`/etc/nginx/sites-available/app` 에 80 포트 서버 블록을 만들고 `server_name` 에 도메인을 넣는다
(본문은 `return 200 "nginx ok\n";` 로 충분하다 — 인증서를 받기 위한 발판이다).

```bash
sudo ln -s /etc/nginx/sites-available/app /etc/nginx/sites-enabled/app
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t && sudo systemctl reload nginx
curl -H "Host: $DOMAIN" http://127.0.0.1        # nginx ok 가 나오면 준비 끝
```

```bash
sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d "$DOMAIN"               # 이메일·ToS 동의를 묻는다
```

✅ `Successfully received certificate.` 와 `fullchain.pem` · `privkey.pem` 경로가 나오면 성공.

certbot 이 같이 만드는 `options-ssl-nginx.conf` 와 `ssl-dhparams.pem` 도
**컨테이너 `app.conf` 가 `include` 하므로 함께 있어야 한다.**

### 5.2 ⚠ 그다음 호스트 nginx 를 끈다

```bash
sudo systemctl disable --now nginx
```

여기서 순서가 뒤집힌다 — **인증서를 받을 때까지는 호스트 nginx 가 필요했지만, 서비스를 띄울
때는 방해가 된다.** 컨테이너 `web` 이 80·443 을 받아야 하는데 호스트 nginx 가 쥐고 있으면
`up` 이 실패한다.

> **끄면 certbot 자동 갱신이 멈춘다.** 이 프로젝트는 만료(2026-11-30)가 발표(2026-09-28)보다
> 뒤라 괜찮다. 더 오래 굴리려면 갱신을 **webroot 방식**으로 바꿔야 한다.

**도메인이 바뀌면 같이 고칠 곳**: [`deploy/prod/app/nginx/app.conf`](../deploy/prod/app/nginx/app.conf)
의 `server_name` 2곳과 인증서 경로, `.gitlab-ci.yml` 의 스모크 테스트 `curl` 대상,
[`04_시연_시나리오.md`](04_시연_시나리오.md) 의 시연 주소.

## 6. GitLab (SSAFY)

소스 저장소 + CI/CD. 러너는 **직접 등록한 self-hosted** 로, `app` 에 docker executor(검증)와
shell executor(배포), `data` 에 shell executor(`deploy-ai`) 가 붙어 있다.

**러너가 없으면 파이프라인이 pending 으로 멈춘다** — 잡이 실패하는 게 아니라 아무 일도
일어나지 않아 처음 보면 원인을 찾기 어렵다. `develop`·`main` 은 **보호 브랜치**여야 한다.

등록 절차는 [`deploy/ci/README.md`](../deploy/ci/README.md).

## 7. SSAFY GPU 서버

임베딩 모델(`pickage-similarity`) 학습용. **서비스 기동에는 필요 없다** — 학습된 모델은
MLflow 레지스트리에 있고 유사도 배치가 거기서 가져간다.

| | |
| --- | --- |
| 접근 | **SSH 터널 필수** — MinIO 는 인터넷에 열려 있지 않다 |
| 읽기 | `pickage-raw` · `pickage-curated` |
| 쓰기 | **`pickage-mlflow-artifacts` 만** |
| 자격증명 | 별도 전달. 정책 [`policies/gpu.json`](../pipeline/minio/policies/gpu.json) |

```bash
ssh -N -L 9000:localhost:9000 <user>@j15a506a.p.ssafy.io
```

> **MLflow 아티팩트는 서버를 거치지 않는다** (`--no-serve-artifacts`). 터널이 없으면
> 메타데이터만 올라가고 모델 파일은 안 올라간다. 절차는
> [`pipeline/minio/GPU_ACCESS.md`](../pipeline/minio/GPU_ACCESS.md).
