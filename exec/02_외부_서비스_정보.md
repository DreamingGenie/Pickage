# 외부 서비스 정보

Pickage 가 쓰는 외부 서비스와, 새 환경에서 처음부터 붙일 때 필요한 가입·발급 정보다.

**여기에 실제 키 값을 적지 않는다.** 값이 사는 자리만 적는다 —
문서가 GitLab 에 남고 한 번 커밋된 비밀은 지워도 히스토리에 남기 때문이다.

## 한눈에

| 서비스 | 무엇에 쓰나 | 가입·발급 | 없으면 |
| --- | --- | --- | --- |
| [Google Cloud Platform](#1-google-cloud-platform-bigquery--gcs) | deps.dev 원천 데이터 수집 | **필요** (서비스 계정 키) | 주간 수집이 시작조차 못 한다 |
| [npm registry / downloads API](#2-npm-registry--downloads-api) | 패키지 메타·다운로드 수 | 불필요 (무인증) | 다운로드 지표가 비어 있다 |
| [ecosyste.ms](#3-ecosystems) | 키워드·설명 코퍼스 | 불필요 (무인증) | 유사도 후보 코퍼스가 갱신되지 않는다 |
| [GitHub REST API](#4-github-rest-api) | 커뮤니티(이슈·댓글) 수집 | 선택 (PAT) | 비인증 10회/분으로 폴백 — 기능은 동작 |

| [GitLab (SSAFY)](#7-gitlab-ssafy) | 소스·CI/CD | **필요** | 자동 배포가 없다 (손 배포는 가능) |
| [Jira Cloud](#8-jira-cloud-ssafyatlassiannet) | 이슈 추적 | **필요** (협업 규칙) | 서비스 동작에는 영향 없다 |
| [SSAFY GPU 서버](#9-ssafy-gpu-서버) | 임베딩 모델 학습 | **필요** | 모델을 새로 학습할 수 없다 (기존 모델로 배치는 돈다) |

**소셜 로그인·결제·포톤 클라우드는 쓰지 않는다.** 서비스에 로그인 기능 자체가 없다
(백엔드에 Spring Security 가 없고 운영자 전용 API 는 nginx 가 문 앞에서 404 로 끊는다).

## 1. Google Cloud Platform (BigQuery + GCS)

가장 중요한 외부 의존이다. **원천 데이터 전체가 여기서 온다.**

| | |
| --- | --- |
| 프로젝트 | `oss-shift-a506` |
| 읽는 데이터셋 | `bigquery-public-data.deps_dev_v1` (공개 데이터셋, Open Source Insights) |
| 스테이징 | `oss-shift-a506.staging` (US, 기본 테이블 만료 **3일**) |
| 산출물 버킷 | `gs://oss-shift-a506-raw` (US) |
| 쓰는 코드 | [`pipeline/collectors/bigquery/`](../pipeline/collectors/bigquery/) |
| 필요한 API | BigQuery API, Cloud Storage API |

### 인증 — 경로가 둘이다

```
GOOGLE_APPLICATION_CREDENTIALS          → 파이썬 클라이언트 (BigQuery·GCS)
CLOUDSDK_AUTH_CREDENTIAL_FILE_OVERRIDE  → gcloud CLI (gcloud storage rsync)
```

`pipeline/Dockerfile` 이 둘 다 `/opt/work/secrets/gcp-service-account.json` 을 가리키게 세워 두고
compose 가 `/srv/pickage/secrets` 를 읽기 전용으로 마운트한다.
**둘 중 하나만 세우면 수집 중간(`gcs_sync` 단계)에서 인증 실패한다.**

```bash
# data 노드
sudo mkdir -p /srv/pickage/secrets
# 키 파일을 /srv/pickage/secrets/gcp-service-account.json 으로 둔다
sudo chown 1000:1000 /srv/pickage/secrets/gcp-service-account.json
```

### ⚠ 과금이 걸린 유일한 외부 서비스다

BigQuery 는 스캔한 바이트로 과금한다. 수집기는 **관문 6개**를 두고 그중 셋이 예산을 본다.

| 티어 | 언제 | 대략 스캔량 |
| --- | --- | --- |
| `t0` | 최초 1회, 핵심 4테이블 | 약 52.6 GiB |
| `t1` | Projects 전 스냅샷 백필 | 약 51 GiB |
| `t2` | **매주 화요일** 증분 | 약 23 GiB |
| `t2m` | 월 1회 갱신 | 약 35 GiB |

**항상 `--plan` 을 먼저 돌린다.** dry-run 만 하고 예산 합계를 보여 준다. 과금은 0 이다.

```bash
.venv-bq/Scripts/python pipeline/collectors/bigquery/collect.py --tier t0 --plan
```

`maximum_bytes_billed` 를 dry-run × 1.25 + 512 MiB 로 걸어 두어, 초과하면 **BigQuery 가 잡을
거부하고 과금이 발생하지 않는다.**

### 6.1 도메인 준비 → nginx (최초 1회, 호스트에서)

**아래는 호스트 nginx 로 한다.** 컨테이너 nginx 가 아니다 — §6.3 의 순서를 먼저 읽을 것.

매번 도메인을 치기 번거로우니 변수로 둔다 (선택. 안 쓰면 `$DOMAIN` 자리에 주소를 넣는다).

```bash
DOMAIN="<자기 도메인>"
```

```bash
sudo apt install -y nginx
```

✅ `nginx -v` 가 `nginx version: nginx/1.24.0 (Ubuntu)` 처럼 나오면 설치된 것이다.
**컨테이너의 nginx(1.27-alpine)와 다른 물건이다** — 이쪽은 인증서 발급에만 쓴다.

```bash
sudo systemctl status nginx --no-pager
```

✅ `Active: active (running)`. 꺼져 있으면 `sudo systemctl start nginx`.

```bash
sudo ss -lntp | grep ':80'
```

✅ `LISTEN ... 0.0.0.0:80 ... nginx` 가 보이면 80 을 쥐고 있는 것이다.

도메인 전용 설정 파일을 만든다.

```bash
sudo vi /etc/nginx/sites-available/app
```

```nginx
server {
    listen 80;
    listen [::]:80;

    server_name <자기 도메인>;

    location / {
        return 200 "nginx ok\n";
    }
}
```

**지금은 테스트용으로 `nginx ok` 만 돌려준다.** 이 설정은 인증서를 받기 위한 발판이고
받고 나면 컨테이너의 [`app.conf`](../deploy/prod/app/nginx/app.conf) 가 그 자리를 넘겨받는다.

```bash
sudo ln -s /etc/nginx/sites-available/app /etc/nginx/sites-enabled/app
```

✅ `ls -al /etc/nginx/sites-enabled/` 에 `app -> /etc/nginx/sites-available/app` 이 보여야 한다.
`default` 링크가 있으면 지운다 — `sudo rm /etc/nginx/sites-enabled/default`.

**문법 검사를 먼저 한다.**

```bash
sudo nginx -t && sudo systemctl reload nginx
```

✅ 최종 확인 — `nginx ok` 가 나오면 성공:

```bash
curl -H "Host: $DOMAIN" http://127.0.0.1
```

### 6.2 인증서 발급

```bash
sudo apt install -y certbot python3-certbot-nginx
```

✅ `certbot --version` 이 `2.x.x` 면 된다.

```bash
sudo certbot --nginx -d "$DOMAIN"
```

대화형으로 묻는다 — 이메일(긴급 갱신·보안 공지용), ToS 동의, EFF 메일 수신 여부.

> **TODO — 발급에 쓴 이메일을 팀 노션에 적어 둔다.** 만료 경고가 그 주소로 온다.
> **이 문서에는 적지 않는다** — 저장소에 개인 이메일을 남기지 않는다.

✅ 성공 표시:

```
Successfully received certificate.
Certificate is saved at: /etc/letsencrypt/live/<도메인>/fullchain.pem
Key is saved at:         /etc/letsencrypt/live/<도메인>/privkey.pem
```

`--nginx` 플러그인이 `/etc/nginx/sites-available/app` 을 **직접 고쳐서** 443 블록과 리다이렉트를
넣는다. `sudo cat /etc/nginx/sites-available/app` 으로 확인한다.

certbot 은 `options-ssl-nginx.conf` 와 `ssl-dhparams.pem` 도 같이 만든다.
**컨테이너 `app.conf` 가 그 둘을 `include` 하므로** 없으면 컨테이너 nginx 가 뜨지 않는다.

### 6.3 ⚠ 그다음이 중요하다 — 호스트 nginx 를 끈다

여기서 순서가 뒤집힌다. **인증서를 받을 때까지는 호스트 nginx 가 필요했지만
서비스를 띄울 때는 그것이 방해가 된다.**

```bash
sudo systemctl disable --now nginx
```

컨테이너 `web` 이 80·443 을 받아야 하는데 호스트 nginx 가 쥐고 있으면 **`up` 이 실패한다.**
인증서는 `/etc/letsencrypt` 를 읽기 전용 마운트로 **그대로 읽어 쓴다** — 옮기거나 복사하지 않는다.

이 순서가 [`01_빌드_배포_매뉴얼.md`](01_빌드_배포_매뉴얼.md) §4.3 의 첫 줄과 이어진다.

> ### ⚠ 호스트 nginx 를 끄면 certbot 자동 갱신이 멈춘다
>
> `--nginx`·standalone 갱신이 80 을 못 잡기 때문이다. **이 프로젝트에서는 괜찮다** —
> 인증서 만료가 2026-11-30, 최종 발표가 2026-09-28 이다.
>
> **더 오래 굴릴 거면 갱신을 `webroot` 방식으로 바꿔야 한다.** 컨테이너 nginx 가
> `/.well-known/acme-challenge/` 를 공유 디렉터리에서 서빙하게 하고 certbot 이 거기에 쓰게 한다.
>
> 갱신 설정이 살아 있는지 보려면 **호스트 nginx 를 끄기 전에** 확인해 둔다:
>
> ```bash
> systemctl list-timers | grep certbot && sudo certbot renew --dry-run
> ```

✅ 전체 확인 (만료일이 보이면 인증서가 붙은 것이다):

```bash
echo | openssl s_client -connect "$DOMAIN":443 2>/dev/null | openssl x509 -noout -dates
```

## 10. 외부가 아닌 것 — 우리가 띄운다

혼동하기 쉬워 적어 둔다. 아래는 가입할 곳이 없다.

| | 어디 | 비고 |
| --- | --- | --- |
| MinIO (S3 호환 객체 저장소) | `data` 노드 컨테이너 | AWS S3 를 쓰지 않는다 |
| MLflow (모델 레지스트리) | `data` 노드 컨테이너 | backend store 는 SQLite, 아티팩트는 MinIO |
| Apache Spark | 양 노드 컨테이너 (master 1 + worker 2) | 관리형 서비스 아님 |
| PostgreSQL | `app` 노드 컨테이너 | RDS 아님 |
| Netdata (모니터링) | 양 노드 컨테이너, SSH 터널로만 본다 | Netdata Cloud 에 연결하지 않는다 |
