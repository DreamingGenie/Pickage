# DB 덤프

제출 규격의 "DB 덤프 파일 최신본" 항목이다.

**전체 덤프는 넣지 않는다.** 크기 때문에 올릴 수 없다 — 근거는 §1.
**스키마 덤프**와 저장소에 이미 있는 **표본 데이터**로 대신한다.

| 무엇 | 어디 | 크기 |
| --- | --- | --- |
| 스키마 덤프 | `exec/db/schema.sql` | 수백 KB |
| 표본 데이터 | [`deploy/local/seed/`](../deploy/local/seed/) (기존) | 2 KB ~ 364 KB |
| 전체 데이터 | **제출물에 없다** (§1) | 약 160 GB |

---

## 1. ⚠ 전체 덤프를 넣지 않는 이유

### 1.1 DB 가 약 160 GB 다

| 시점 | `df -h /` | |
| --- | --- | --- |
| 2026-09-13 | 4% 사용 (**300 G 남음**) | **DB 가 비었을 때** |
| 2026-09-15 | 56% 사용 (**137 G 남음**) | curated 적재 후 |

이틀 사이 줄어든 약 160 G 의 대부분이 Postgres 에 들어간 데이터다
([`deploy/prod/README.md`](../deploy/prod/README.md) · [`deploy/ci/README.md`](../deploy/ci/README.md) 의 같은 표).

`package` · `version` 적재만 **5,418만행**(58분)이고, `package_version_snapshot` 은 행이 많아
**파티션 테이블**로 쪼개 두었다.

### 1.2 GitLab 에 올라가지 않는다

gzip 으로 줄여도 수십 GB 규모다. 참고로 이 저장소는 지금 **packed 74 MiB**, 커밋된 최대 파일이
**43 MB** 다. SSAFY GitLab 인스턴스의 `max push size` · `repository size limit` 실제 값과 무관하게
이 규모는 올라가지 않는다.

**Git LFS 로도 안 된다.** 이 저장소에는 LFS 가 설정되어 있지 않고(`.gitattributes` 에 lfs 규칙
없음), 켠다 해도 LFS 저장 공간 한도는 더 작다.

### 1.3 덤프를 만드는 것 자체가 서버에 위험하다

**`/dev/root` 하나뿐이다.** `~/backup` 도 Docker 도 Postgres 도 같은 309 G 를 나눠 쓰고
지금 남은 것이 137 G 다. 거기에 수십 GB 짜리 덤프를 쓰면 **DB 를 지키려고 만든 것이
DB 를 멈춘다.** MinIO·Spark 셔플과도 같은 파티션이다.

크기만 재는 것은 안전하다 — 파일로 떨어뜨리지 않고 바이트 수만 센다.

```bash
cd /srv/pickage/repo/deploy/prod/app
docker compose exec -T postgres psql -U pickage -d pickage -c "select pg_size_pretty(pg_database_size('pickage'));"
docker compose exec -T postgres pg_dump -U pickage pickage | gzip | wc -c
```

### 1.4 애초에 복원할 이유가 없다

제출 규격의 의도는 "평가자가 DB 를 복원할 수 있게" 인데, 이 프로젝트에는 더 나은 길이 셋 있다.

- **스키마는 덤프가 아니라 마이그레이션이 소유한다** (§2). 빈 DB 에 앱을 띄우면 스키마가 잡힌다
- **데이터는 원천에서 다시 수집한다.** 원천은 BigQuery 의 공개 데이터셋(`deps.dev`)이고
  수집기가 저장소에 있다 ([`pipeline/collectors/`](../pipeline/collectors/))
- **화면을 보려는 것이면 시드가 더 낫다** (§4). 목적별로 만들어져 있고 훨씬 가볍다

## 2. 스키마는 마이그레이션이 소유한다

**스키마 정본은 `backend/src/main/resources/db/migration/` 의 SQL 이다.**
앱이 뜰 때 Flyway 가 적용하고 Hibernate 는 `ddl-auto: validate` 로 검증만 한다.

| 파일 | 무엇 |
| --- | --- |
| `V1__init.sql` | 기본 스키마 (`package` · `version` · `snapshot` · `package_snapshot` · `package_version_snapshot` · `similar_package`) |
| `V2` · `V3` | 적재 추적 (`etl_load_execution` · `etl_load_attempt` · `etl_dataset_current` · `etl_snapshot_reference`) |
| `V4` | `similar_package` 인덱스 |
| `V5` | `community_snapshot` |
| `V6` · `V7` | `package_version_snapshot` 파티셔닝·제약 정규화 |
| `V8` · `V9` | `dependent_transition` · `dependent_removal_reason` |
| `V10` | `package_env` |
| `V11` | dependent transition 신선도 |
| `V12` | `available_package` |

> ⚠ **이미 적용된 `V__` 파일을 고치지 않는다.** checksum 불일치로 **운영 앱이 기동에 실패한다.**
> 바꿔야 하면 새 버전 파일을 추가한다.

아래 스키마 덤프는 **제출 규격을 채우고 테이블 모양을 한눈에 보여 주기 위한 사본**이다.
정본이 아니다 — 둘이 어긋나면 마이그레이션이 맞다.

## 3. 스키마 덤프 뜨기

```bash
cd /srv/pickage/repo/deploy/prod/app
docker compose exec -T postgres pg_dump -U pickage -s pickage > ~/schema.sql
```

`-s` 는 **데이터 없이 구조만** 뜬다. 수백 KB 라 그대로 커밋할 수 있다.

> **`-T` 를 빼지 말 것.** `exec -T` 의 `-T` 는 TTY 할당을 끈다. 없으면 출력에 제어문자가 섞여
> **복원할 수 없는 파일**이 나온다. 그리고 그 사실은 복원할 때 알게 된다.

✅ 확인 — 마지막 줄이 `PostgreSQL database dump complete` 여야 한다:

```bash
tail -1 ~/schema.sql && grep -c 'CREATE TABLE' ~/schema.sql
```

내려받아 커밋한다.

```bash
scp -i ~/.ssh/J15A506T.pem ubuntu@j15a506.p.ssafy.io:~/schema.sql exec/db/schema.sql
```

서버에서는 지운다. 작지만 습관을 다르게 두지 않는다.

지금 들어 있는 것 — 2026-09-23, `CREATE TABLE` **246개**(파티션 포함), **444 KB**.
데이터는 한 줄도 없다(`COPY`·`INSERT` 0건).

## 4. 표본 데이터 — 저장소에 이미 있다

목적이 다른 다섯 벌이 [`deploy/local/seed/`](../deploy/local/seed/) 에 있다.
**새로 만들지 않는다.**

| 파일 | 크기 | 규모 | 무엇을 보려고 |
| --- | --- | --- | --- |
| `seed_service_full.sql` | 48 K | 패키지 322 × 스냅샷 130 | **목업을 굴려 보는 상태.** 메인 6개 테이블을 전부 채우고 경계 사례를 일부러 심어 두었다 |
| `seed_mock_parity.sql` | 364 K | 패키지 369 × 스냅샷 130 | **mock 과 같은 숫자.** 화면과 대조 검증 |
| `seed_sample.sql` | 8.4 K | 패키지 3 × 스냅샷 2 | **자료가 모자란 상태** — "데이터 축적 중" 표시 확인 |
| `seed_clear_snapshots.sql` | 2.3 K | 넣지 않음 | 이름만 남기고 스냅샷만 지운다 |
| `seed_reset.sql` | 2.0 K | 넣지 않음 | 실데이터 적재 직전 1회 |

**앞의 셋은 같이 쓸 수 없다** — 전부 기존 행을 비우고 시작한다.

```bash
docker compose exec postgres psql -U postgres -d pickage -f seed/seed_service_full.sql
```

**경로 앞에 `/` 를 붙이지 않는다.** Git Bash 가 윈도우 경로로 바꿔서 `No such file or directory` 가 난다.

> 숫자는 전부 지어낸 값이다. 형태만 맞춰 둔 것이므로 **분석 근거로 쓰지 않는다.**
> 목적별 선택 기준과 주의는 [`deploy/local/README.md`](../deploy/local/README.md).

## 5. 복원 — 빈 DB 에 스키마 + 표본

새 환경에서 화면이 도는 상태까지 가는 가장 짧은 길이다.

```bash
docker compose --profile api up -d          # Flyway 가 스키마를 만든다. 덤프가 필요 없다
docker compose exec postgres psql -U postgres -d pickage -f seed/seed_service_full.sql
```

✅ 확인 — `success` 가 전부 `t` 이고 최신 버전이 `12` 이상이면 스키마가 제자리에 있다:

```bash
docker compose exec -T postgres psql -U postgres -d pickage -c "select version, success from flyway_schema_history order by installed_rank desc limit 3;"
```

스키마 덤프로 만들고 싶으면 (Flyway 없이 구조만):

```bash
psql -U postgres -d pickage -f exec/db/schema.sql
```

> ⚠ **운영 DB 에 시드를 넣지 않는다.** `package` · `version` 과 적재 이력은 PostgreSQL 적재기가
> 소유한다. 적재 실패 복구에 시드를 쓰지 않는다.
>
> 실적재가 한 번 성공한 DB 에서는 `etl_snapshot_reference` 이력 때문에 시드의 `DELETE FROM snapshot`
> 이 **FK 위반으로 멈춘다.** 조용히 덮어쓰지 않는 쪽이 맞다.

## 6. 전체 데이터가 정말 필요하면

**제출물로 옮기는 길은 없다.** 다시 만드는 길만 있다.

| 길 | 어떻게 | 비용 |
| --- | --- | --- |
| 원천에서 재수집 | [`pipeline/collectors/bigquery/`](../pipeline/collectors/bigquery/) — `--plan` 으로 예산 먼저 | BigQuery 스캔 과금. t0 약 52.6 GiB |
| MinIO 의 curated Parquet 에서 재적재 | `data` 노드 MinIO → `pipeline/postgresql` 적재기 | `package`·`version` 기준 58분 |
| 운영 DB 를 직접 조회 | SSH 터널 후 `psql` | 없음 (읽기만) |

```bash
ssh -i ~/.ssh/J15A506T.pem ubuntu@j15a506.p.ssafy.io
cd /srv/pickage/repo/deploy/prod/app && docker compose exec postgres psql -U pickage -d pickage
```

> 전체 덤프를 팀 외부로 옮겨야 하는 상황이 생기면 **§1.3 을 먼저 읽는다** — 서버 디스크를 채울 수 있다.

## 7. 테이블 구성

| 묶음 | 테이블 | 누가 채우나 |
| --- | --- | --- |
| 서비스 본체 | `package` · `version` · `snapshot` · `package_snapshot` · `package_version_snapshot` · `similar_package` | 적재기 (`pipeline/postgresql`) · similarity-loader |
| 확장 | `community_snapshot` · `dependent_transition` · `dependent_removal_reason` · `package_env` · `available_package` | 각 파이프라인 |
| 적재 추적 | `etl_load_execution` · `etl_load_attempt` · `etl_dataset_current` · `etl_snapshot_reference` | **파이프라인이 소유한다.** 시드가 건드리지 않는다 |
| Flyway | `flyway_schema_history` | Flyway |

## 8. ⚠ 덤프에 들어가는 것

**자격증명이 들어가지 않는다.** 이 서비스에는 사용자 계정·로그인이 없고(백엔드에 Spring Security 가
없다), 테이블에 비밀번호·토큰 컬럼이 없다. 담기는 것은 공개 npm 패키지의 메타데이터와 집계 지표다.

스키마 덤프에는 테이블·인덱스·제약만 들어간다. 그나마도 저장소의 마이그레이션 SQL 과 같은 내용이다.
