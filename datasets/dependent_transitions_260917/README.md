## 2. 열

| 열 | 뜻 |
|---|---|
| `period` | `1y` · `3y` · `5y` — 구간 |
| `target` | 대상 패키지 이름 |
| `kind` | `regular` · `peer` · `optional` — 선언 종류 |
| `retained` | **유지** — 양 끝에 선언이 있고, 구간 안에 대표 릴리스가 바뀌었다 |
| `inflow` | **유입** — T1 엔 없고 T2 엔 있다 |
| `inflow_new` | 그중 **T1 때 아직 존재하지도 않던 패키지**. `inflow` 의 부분집합 |
| `outflow` | **이탈** — T1 엔 있고 T2 엔 없다 |
| `unobserved` | **관측 불가** — 양 끝에 선언이 있는데 대표 릴리스가 안 바뀌었다 |
| `t1` · `t2` | 구간의 두 시점. `period` 로 정해지는 상수다 |
| `download_rank` | 상위 10만 표의 순위. 표 밖이면 NULL |
| `in_top100k` | `download_rank IS NOT NULL` |

**대상 × kind × 구간을 모두 담는다.** dependent 가 없으면 행을 빼지 않고 수를 0 으로 둔다 —
빼면 받는 쪽이 "조회 실패"와 "dependent 가 없음"을 구분할 수 없다. 네 수가 전부 0 인 조합이
구간마다 18만개쯤 있다(1y 181,633 / 299,988).

## 3. 범주가 셋이 아니라 넷인 이유

`A` = T1 선언 여부 · `B` = T2 선언 여부 · `M` = 구간 안에 **대표 릴리스가 바뀌었는가**.

| A | B | M | 범주 |
|---|---|---|---|
| T | T | T | **유지** — 릴리스를 내면서도 계속 선언했다 |
| T | T | F | **관측 불가** — 변할 기회 자체가 없었다 |
| F | T | T | **유입** |
| T | F | T | **이탈** |
| F | F | - | 대상 아님 |

`A <> B` 면 `M` 은 반드시 참이다. 대표 릴리스가 안 바뀌었는데 선언이 달라질 수 없다.
그래서 관측 불가는 `A=T, B=T, M=F` 한 칸뿐이다.

**시점 T 의 대표 릴리스** = `published_at <= T` 중 **`ordinal` 최고**. 라인(major)별로 나누지
않는다. `published_at` 은 시점 필터에만 쓰고 대표를 고르는 데는 쓰지 않는다 — 같은 발행시각에
전환점이 둘 이상인 그룹이 1,001개(699 패키지) 있어 발행시각으로 고르면 무엇이 뽑힐지
정해지지 않는다(2026-09-17 실측, 150개 패키지가 잘못된 대표를 잡았다).

### 4-1. 관측 불가를 유지로 세면 숫자가 거짓이 된다

마지막 릴리스가 1년 이내인 패키지는 npm 전수 4,065,913 중 974,770(24.0%) 뿐이다. 나머지는
1년 구간에서 움직일 기회가 없었다.

| 구간 | 유지율 (관측 가능만) | 관측 불가를 유지로 세면 |
|---|---:|---:|
| `1y` | **87.2%** | 98.8% |
| `3y` | **81.8%** | 97.5% |
| `5y` | **78.9%** | 96.4% |

받는 쪽은 **네 수를 모두 화면에 내야 한다.** 관측 불가를 숨기면 나머지 셋의 비율이 거짓이 된다.
기능-08-R03 이 "자료 없음을 이탈로 분류하지 않는다"고 못 박은 것과 같은 이유로
**유지로 분류하는 것도 잘못이다.**

### 4-2. 유입의 대부분은 채택이 아니라 생태계 성장이다

`inflow_new` 는 T1 때 **아직 존재하지도 않던** 패키지의 유입이다. "다른 것을 쓰다가 갈아탔다"가
아니라 "새로 생긴 프로젝트가 처음부터 골랐다"이다.

| 구간 | 유입 | 그중 신생 | 신생 비중 | **전환 유입** | 이탈 |
|---|---:|---:|---:|---:|---:|
| `1y` | 2,293,274 | 2,150,421 | **93.8%** | **142,853** | 134,356 |
| `3y` | 5,975,663 | 5,758,043 | **96.4%** | **217,620** | 190,793 |
| `5y` | 8,572,223 | 8,359,180 | **97.5%** | **213,043** | 179,801 |

**유입 절대수를 "인기 상승"으로 읽으면 안 된다.** 유입이 이탈보다 17배 커 보이지만, 신생을 빼면
1년 구간에서 142,853 대 134,356 으로 거의 같다. 둘을 합쳐 두면 npm 이 커진 것이 그 패키지가
선택받은 것으로 둔갑한다.

## 6. 한계 — 쓰기 전에 읽을 것

**6-1. MVP 의 `delta` 와 다른 지표다.** `delta` 는 첫·마지막 관측의 수 차이일 뿐 누가 남고 누가
떠났는지 모른다. `DEC-DEPENDENCY-DELTA-20260910-01` 에 따라 `delta = 유입 - 이탈` 을 전제하지
않는다. 모집단도 계산도 달라 그 관계가 성립하지 않는다.

**6-2. devDependencies 가 없다.** deps.dev `NPMRequirements` 는 Dependencies·Peer·Optional
셋뿐이다. 개발 도구(eslint·jest·prettier 류)의 유지·유입·이탈을 이 결과로 읽으면 안 된다.
dev 는 npm registry 수집분(S15P21A506-280·-366)에서 별도 회차로 낸다 — **dependent 모집단이
상위 10만이라 여기(npm 전수 406만)와 절대수를 비교할 수 없다.**

**6-3. 생존 편향.** unpublish 된 버전은 과거에 있었어도 보이지 않는다. T1 시점의 선언이 실제보다
적게 잡힐 수 있고, 그만큼 유입이 부풀고 이탈이 줄어든다(수집계획 v2 §2-3).

**6-4. 대상 밖은 알 수 없다.** 상위 10만 밖 패키지는 조회 결과가 0 이 아니라 범위 밖이다.
받는 쪽에서 `OUT_OF_SCOPE` 로 구분한다. 의존자 쪽은 npm 전수 4,065,913 이므로 이 제약은
**대상(target)에만** 걸린다.

**6-5. `package_dependents_260915` 의 `n_dependents` 와 136행 어긋난다.**

`retained + inflow + unobserved` 는 T2 에 그 대상을 선언한 dependent 수이므로 저쪽 `n_dependents`
와 같아야 한다. 299,988행 중 **136행이 다르고, 최대 차는 10이며, 전부 이쪽이 작다.**

원인을 실측했다. `versions_full` 의 `snapshot=2026-08-31` 파티션에 **2026-09-01 00:00:11 ~
02:49:45 에 발행된 릴리스 1,213행(939 패키지)** 이 섞여 있다. BigQuery 추출이 UTC 자정을 세 시간
넘겨 돈 것이다. `build_package_dependents.py` 는 컷오프 없이 전체 ordinal 최대를 대표로 쓰고,
이 빌더는 `published_at <= T2` 를 건다. 그래서 **845개 패키지의 대표 릴리스가 서로 다르다.**

**스냅샷 경계를 지키는 쪽은 이 데이터셋이다.** 두 수를 대조할 때 이 차이(0.045%)는 오류가 아니다.
`react` 가 그 예다.
