# npm 다운로드 수 수집 가능성 검증

작성 2026-08-31 · 대상 OSS Shift 확장 기능 · 상태 **실측 완료**

질문: 매주 전체 npm 패키지의 다운로드 수를 호출해서 이용량 추이를 계산할 수 있는가.

---

## 1. 결론

**전체 패키지 주간 수집은 불가능하다. 한 번 도는 데 약 13일이 걸려서 다음 주가 오기 전에 끝나지 않는다.**

원인은 규모가 아니라 **스코프 패키지**다. `@조직/이름` 형태는 묶음 조회를 지원하지 않아서 하나씩 불러야 한다. 이들이 전체의 38%인데 **호출의 99%를 먹는다.**

**대신 범위를 좁히면 충분히 된다.** 비교 후보군 수천 개 규모면 10분 안에 끝나고, 비스코프 패키지 전체(268만 개)도 4시간이면 1년치 일별 데이터를 받는다.

---

## 2. 확인한 사실

### 공식 문서 (npm/registry `docs/download-counts.md`)

| 항목 | 내용 |
|---|---|
| 묶음 조회 | 한 번에 **최대 128개** |
| 묶음 + 스코프 | **지원 안 함.** `@org/name`은 개별 호출만 |
| 묶음 기간 한도 | 최대 365일 |
| 그 외 조회 기간 한도 | 최대 18개월, 2015-01-10 이후 |
| 버전별 다운로드 | 별도 엔드포인트, **최근 7일만** |
| 데이터 갱신 | UTC 자정 직후 하루 1회 배치 |

### 실측으로 확인한 것

```
128개 묶음 호출     → 200 OK, 14,284 bytes, 0.55초, 128개 전부 값 반환
129개 묶음 호출     → HTTP 400  (한도 확인)
스코프 3개 묶음     → HTTP 400  (문서대로 불가)
범위+묶음 8개 1년치 → 200 OK, 122,218 bytes, 0.4초, 각 365일치
```

`express` 지난주 다운로드 132,879,571건이 정상 반환됐다.

### 요청 제한이 매우 빡빡하다

인증 없이 단일 IP에서 측정한 결과다.

| 동시 실행 | 시도 | 성공 | 429 | 성공률 |
|---|---|---|---|---|
| 1 | 40 | 23 | 17 | 58% |
| 2 | 40 | 2 | 38 | 5% |
| 4 | 40 | 0 | 40 | 0% |

**지속 가능한 속도는 초당 1.5~2건 수준이다.** 처음 20여 건은 빠르게 통과하다가 급격히 429로 막힌다. `Retry-After` 헤더는 `0`으로 와서 대기 시간 안내가 없다. 한 번 막히면 묶음 조회도 같이 막히므로 **엔드포인트 공용 제한**으로 보인다.

> 적절한 후퇴 재시도를 붙이면 이보다 조금 높일 수는 있겠지만, 확인된 근거가 없다. 아래 계산은 초당 1.5건 기준이며, 설령 10배 빨라져도 전체 수집 결론은 바뀌지 않는다.

## 3. 패키지 수와 호출 수

`_all_docs` 오프셋으로 정확히 셌다 (2026-08-31 기준).

| 구분 | 패키지 수 | 비율 |
|---|---|---|
| 전체 | 4,345,252 | 100% |
| **스코프 (`@org/`)** | **1,660,027** | **38.2%** |
| 비스코프 | 2,685,225 | 61.8% |

### 전체를 한 번 도는 데 필요한 호출

```
비스코프 : 2,685,225 ÷ 128 =    20,979 회
스코프   : 1,660,027 ÷   1 = 1,660,027 회
────────────────────────────────────────
합계                         1,681,006 회
```

**스코프가 전체 호출의 98.8%를 차지한다.** 패키지 수로는 38%인데 말이다.

### 소요 시간 (초당 1.5건 기준)

| 범위 | 패키지 | 호출 | 소요 | 판정 |
|---|---|---|---|---|
| 비교 후보군만 | 2,000 | 774 | **9분** | 가능 |
| 인기 상위 | 50,000 | 19,342 | **3.6시간** | 가능 |
| 비스코프 전체 | 2,685,225 | 20,979 | **3.9시간** | 가능 |
| 스코프 전체 | 1,660,027 | 1,660,027 | **12.8일** | 불가 |
| **전체** | 4,345,252 | 1,681,006 | **13.0일** | **불가** |

주간 수집이 되려면 7일 안에 끝나야 하는데 13일이 걸린다. 다음 회차가 이전 회차를 따라잡는다.

## 4. 그래서 어떻게 할 것인가

### 4-1. 주간 전수 수집을 하지 않는다 — 애초에 필요도 없다

이 서비스는 **비교 묶음 안에서** 후보들을 견준다. 화면에 등장할 수 있는 패키지만 모으면 된다. 후보군 2,000개 규모면 9분, 넉넉히 5만 개로 잡아도 3.6시간이다. 주 1회 야간 배치로 충분하다.

### 4-2. 범위 조회를 쓰면 주간 반복이 거의 필요 없다

`/downloads/range/last-year/pkg1,...,pkg128` 한 번이면 **128개 패키지 × 365일** 데이터가 온다. 실측 응답이 8개에 122KB였으니 128개면 약 2MB로 추정된다.

즉 이력은 **최초 1회**에 다 받고, 이후에는 주 1회 최신 7일만 갱신하면 된다. 주간 전수 개념 자체가 필요 없어진다.

### 4-3. 스코프 패키지는 등급을 나눈다

스코프를 전부 포기할 필요는 없다. 비교 후보에 실제로 오른 것만 개별 호출하면 된다. 후보군의 38%가 스코프라 해도 2,000개 중 764개고, 이건 9분 안에 들어간다.

**화면 규칙**: 다운로드 수집이 안 된 패키지는 빈칸으로 두지 말고 "수집 대상 아님"으로 명시한다. 없는 것과 0을 구분한다.

### 4-4. 버전별 다운로드는 버전 고착 기능과 붙는다

`/versions/{package}/last-week`로 버전별 다운로드가 나온다. **최근 7일치만** 되고 개별 호출이지만, 기획서의 버전 고착 기능과 직결된다.

지금 버전 고착은 "선언에서 몇 버전에 묶여 있나"를 본다. 여기에 버전별 다운로드를 더하면 **"실제로 당겨지는 버전은 무엇인가"**가 된다. 선언과 실제가 갈리는 지점이 보인다.

---

## 5. 제품 관점 — 다운로드를 어디에 놓을 것인가

**주의가 필요하다.** 기획서는 차별점을 "선언 흐름은 다운로드와 다르다"에 두고 있고, 화면 규칙에도 *"내려받기 수나 실제 실행량으로 표현하지 않는다"*고 적혀 있다.

다운로드 추이를 대등한 지표로 나란히 놓으면 **npm Trends와 같은 화면**이 되고, 스스로 세운 차별점이 흐려진다.

대신 **두 축이 어긋나는 지점**을 보여주는 데 쓰는 것이 낫다. 이건 두 자료를 모두 가진 쪽만 만들 수 있다.

| 선언 | 다운로드 | 해석 |
|---|---|---|
| 감소 | 유지·증가 | 신규 선택은 끊겼는데 기존 프로젝트가 계속 당긴다 = **레거시 잔존** |
| 증가 | 낮음 | 새로 고르는 중이지만 아직 규모가 안 붙었다 = **신흥** |
| 감소 | 감소 | 실제로 물러나는 중 |
| 유지 | 급증 | 사람 선택이 아니라 기계가 당기는 것(전이 의존·CI) |

첫 줄이 특히 쓸모 있다. **"다운로드는 여전히 많은데 아무도 새로 안 고르는 패키지"**는 다운로드 수만 보면 절대 안 보이고, 선언만 봐도 절반만 보인다. 둘을 겹쳐야 나온다.

이렇게 쓰면 다운로드가 경쟁 지표가 아니라 **선언 지표를 돋보이게 하는 대조군**이 된다.

## 6. ecosyste.ms 확인 결과

대량 자료로 호출 문제를 우회할 수 있는지 확인했다. **다운로드 추이 목적으로는 쓸 수 없다. 다만 다른 두 문제를 푼다.**

### 6-1. 기본 정보

| 항목 | 값 |
|---|---|
| npm 패키지 수 | 5,805,789 (오늘 갱신됨) |
| 요청 제한 | **시간당 5,000건**, 익명 등급 |
| 제한 주체 | `x-ratelimit-consumer: anonymous` — **익명 사용자 공용으로 보인다** |
| 자료 라이선스 | CC BY-SA 4.0 (코드는 AGPL-3) |

npm 공식 API보다 제한이 명시적이고 헤더로 잔여량을 알려준다. 다만 익명 공용이면 다른 사용자 트래픽에 영향받는다.

### 6-2. 다운로드 — 있지만 시계열이 아니다

```
downloads         541,646,708
downloads_period  last-month
```

**단일 시점 값만 있다.** 별도 다운로드 시계열 엔드포인트는 404다.

> **판정**: "이용량 추이"를 만들려는 목적에는 **쓸 수 없다.** 3절의 npm API 등급 수집이 여전히 유일한 경로다.

### 6-3. 공개 덤프 — 크고 오래됐다

| 서비스 | 최신 덤프 | 크기 | 상태 |
|---|---|---|---|
| packages | 2026-02-05 | **59.32 GB** | 7개월 전 |
| repos | 2023-08-30 | **211.24 GB** | 3년 전 |

packages 덤프는 8개 시점(2022-08 ~ 2026-02)이 남아 있다. 각 덤프에 그 시점의 다운로드 값이 들어 있다면 **호출 0회로 8개 시점 추이**를 만들 수 있다는 발상이 가능하지만, 전부 받으면 400GB가 넘는다. 4주 일정에서 다룰 규모가 아니다.

덤프는 전 생태계(13.1M 패키지, 100개 레지스트리) 합본이라 npm만 쓰려 해도 통째로 받아야 한다.

### 6-4. ★ 대신 얻은 것 하나 — 배포 주체 문제가 풀린다

`maintainers` 필드가 있다.

```
express → wesleytodd (보유 패키지 155개), email, packages_count
```

앞서 배포 주체 묶기를 두고 **"deps.dev 컬럼만으로는 계산 불가, 추가 데이터 필요"**라고 판단했는데, 여기서 나온다. 이름의 `@조직` 접두사를 파싱하는 방식보다 정확하고, **스코프가 없는 61.8%의 패키지에도 적용된다.**

후보군 규모(수천 개)라면 시간당 5,000건 안에서 충분히 받는다.

### 6-5. ★ 대신 얻은 것 둘 — 모집단 한계를 검증할 대조군이 생긴다

`repos.ecosyste.ms`는 **npm 패키지가 아니라 GitHub 저장소** 기준으로 의존 관계를 센다.

```
usage/npm/express  →  dependents_count 3,040,730
usage/npm/moment   →  dependents_count 1,361,740
usage/npm/dayjs    →  dependents_count   940,171
```

실제 반환된 저장소를 보면 `wechorg/oidcazure`("using oidc with azure") 같은 **일반 애플리케이션**이다. npm에 배포되지 않은, 우리가 지금 못 보는 바로 그 모집단이다.

두 모집단을 비교하면 이렇게 갈린다.

| 기준 | moment | dayjs | 비율 |
|---|---|---|---|
| npm 패키지 (deps.dev) | 58,287 | 23,541 | **2.48 : 1** |
| GitHub 저장소 (ecosyste.ms) | 1,361,740 | 940,171 | **1.45 : 1** |

**저장소 모집단에서는 dayjs가 moment에 훨씬 가깝다.** 즉 npm 패키지만 보는 우리 시각은 moment를 과대평가하고 있을 가능성이 높다. "라이브러리 저자가 앱 개발자보다 늦게 움직인다"는 가설과 방향이 맞는다.

**한계**: 저장소 자료에는 **시간축이 없다.** 현재 상태 스냅샷이라 신규 선택·이탈 계산에는 쓸 수 없다.

> **쓰는 법**: 주 지표를 대체하지 않는다. **현재 규모를 두 모집단으로 나란히 보여주는 대조 화면**으로 쓴다. 우리 서비스 최대 약점("npm 배포자만 본다")에 대해 감추는 대신 **숫자로 보정 폭을 밝히는** 방식이 된다. 후보군 패키지당 호출 1회면 되므로 비용도 거의 없다.

## 7. 남은 확인 사항

| | 확인할 것 | 이유 |
|---|---|---|
| 1 | 후퇴 재시도를 붙였을 때 npm API의 지속 가능한 실제 속도 | 초당 1.5건은 무대책 기준이다. 등급 규모를 정하는 데 필요 |
| 2 | 128개 × 365일 응답의 실제 크기 | 8개에 122KB였으니 약 2MB 추정. 저장 용량 산정에 필요 |
| 3 | npm의 429가 IP 단위인지 계정 단위인지 | 배치 서버 구성에 영향 |
| 4 | ecosyste.ms 익명 제한이 정말 공용 풀인지 | 공용이면 야간 배치 성공률이 불안정해진다 |
| 5 | 저장소 기준 대조를 후보군 전체로 확대했을 때도 방향이 유지되는지 | 6-5는 3개 패키지 관측이다. 결론으로 쓰기엔 이르다 |
