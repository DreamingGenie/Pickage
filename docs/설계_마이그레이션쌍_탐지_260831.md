# 마이그레이션 쌍 탐지 — 가능성 검증과 전체 설계

작성 2026-08-31 · 대상 OSS Shift · 상태 **소규모 실물 검증 완료, 전체 규모 미검증**

목표: `moment`를 걷어낸 패키지들이 무엇으로 갈아탔는지 계산해서 아래 형태의 결과를 만든다.

```
moment 를 걷어낸 배포 주체 N곳
  → dayjs      58%
  → date-fns   24%
  → luxon       7%
  → 대체 없이 제거 11%
```

---

## 1. 결론 먼저

**계산 방법 자체는 성립한다.** 260개 패키지 표본으로 파이프라인 전 단계를 실제로 돌렸고, 실물 마이그레이션을 잡아냈다.

다만 세 가지를 짚고 간다.

| | 상태 |
|---|---|
| 릴리즈 이력 복원 | **확인** — 단일 스냅샷에서 과거 상태가 복원된다 |
| 라인별 정렬의 필요성 | **확인** — 순진하게 하면 변경이 52% 더 생긴다 |
| 교체 쌍 생성·배수 계산 | **확인** — 실물 쌍을 잡았고 우연 쌍이 걸러진다 |
| 신호 밀도 | **미확정** — 표본이 편향돼 있어 전체 규모 쿼리가 필요하다 |
| peerDependencies 함정 | **신규 발견** — V1 계약을 고쳐야 한다 (아래 5-1) |

## 2. 단계별 가능성 검증 결과

검증 환경: npm 공개 레지스트리에서 변경 피드로 수집한 고유 패키지 5,000개 중 무작위 260개의 전체 버전 이력을 받아 파이프라인을 그대로 실행했다. BigQuery는 사용하지 않았다.

표본 성격: 버전 수 중앙값 19개, 최대 5,964개, 버전 10개 이상이 175개.

### 2-1. 과거 상태를 복원할 수 있는가 → 가능

버전마다 발행 시각과 의존성 목록이 다 들어 있다. 검증 보고서의 릴리즈 4,690만 행 / 패키지 405만 개라는 숫자가 이걸 뒷받침한다. 현재 상태만 담겼다면 405만 행이어야 한다.

### 2-2. 릴리즈를 어떻게 줄 세우느냐가 결과를 바꾸는가 → 크게 바꾼다

같은 표본에 두 방식을 적용했다.

| 정렬 방식 | 전이 수 | 변경된 의존성 항목 수 |
|---|---|---|
| 순진 — semver 순으로 한 줄 | 14,577 | **1,049** |
| 라인별 + 발행시각 순 | 12,649 | **689** |

**순진하게 하면 변경이 52% 더 생긴다.** 늘어난 360건 상당수는 0.x 유지보수 라인과 1.x 라인을 번갈아 비교해서 생긴 가짜다.

앞서 확인한 axios 사례가 원인이다. 0.33.0이 2026-06에 나왔는데 1.0.0은 2022-10에 나왔다. semver 순으로 세우면 2026년 다음이 2022년이 된다.

### 2-3. 교체 쌍이 실제로 잡히는가 → 잡힌다

전이 12,649건 중 의존성 변경이 있는 것이 210건, 그중 제거와 추가가 함께 일어난 것이 28건이었다. 여기서 후보 쌍 553종이 생겼고 배수 필터를 통과한 것이 나왔다.

```
@types/gapi.client.discovery  →  @types/gapi.client.discovery-v1   배수 4,216   3표
```

**이건 실제 이름 변경 마이그레이션이다.** 우연이 아니라 진짜 관계를 잡았다는 뜻이다.

배수 필터에 걸리지 않고 살아남은 다른 패턴도 의미가 있었다.

- `@loaders.gl/core` → `@loaders.gl/loader-utils` + `@loaders.gl/schema-utils` — 패키지 분할
- `prettier` → `eslint-config-prettier` — 역할 이동

### 2-4. 유명 사례가 나왔는가 → 표본이 작아서 안 나왔다

| | 제거 | 추가 |
|---|---|---|
| moment | 1회 | 0회 |
| dayjs / date-fns / undici / request | 0회 | 0회 |

**이건 실패가 아니라 표본 부족이다.** moment를 쓰는 패키지는 58,287개로 전체 405만 개의 1.4%다. 260개를 무작위로 뽑으면 moment를 쓰는 게 3~4개 나오는 게 정상이고, 그중 마침 갈아탄 것이 있을 확률은 낮다.

**전체 규모에서는 표본이 아니라 전수다.** moment의 관측 가능한 채택자 42,196개를 전부 본다. 표본 크기 문제가 아니다.

### 2-5. 신호 밀도는 얼마인가 → 이 표본으로는 확정 못 한다

| 기준 | 전이 | 변경 있음 | 제거+추가 |
|---|---|---|---|
| 전체 | 12,649 | 210 (1.7%) | 28 (0.22%) |
| 상위 5개 제외 | 7,398 | 182 (2.5%) | 25 (0.34%) |

전체 규모로 환산하면 변경 있는 전이 약 78만 건, 교체 이벤트 약 10만 건이다.

**하지만 이 추정은 낮게 잡혔을 가능성이 크다.** 표본이 변경 피드에서 나와서 자동 배포 봇에 치우쳐 있다.

```
kolmafia                  전이 2,474건, 의존성 변경 0건
create-prisma-php-app     전이   822건, 의존성 변경 0건
```

이 둘만으로 전체 전이의 26%를 차지하면서 신호는 0이다. 자동으로 버전만 올리는 배포라 분모만 키운다.

또 실제 npm은 패키지당 릴리즈 중앙값이 3인데 이 표본은 19다. 릴리즈가 많은 쪽에 치우쳤고, 그쪽이 봇과 모노레포다.

> **판단**: 방법의 성립 여부와는 별개 문제다. 밀도는 BigQuery 쿼리 한 번으로 확정해야 하며, 그 전에는 화면 설계를 확정하지 않는다.

## 3. 전체 파이프라인

### 0단계 — 입력 고정

- 스냅샷 날짜 고정
- 컬럼: `package_name, version, upstream_published_at, version_ordinal, dependency_name, dependency_requirement`
- 범위: `System='NPM'`, `IsRelease`, `UpstreamPublishedAt IS NOT NULL`
- **regular `Dependencies` + `PeerDependencies`/`OptionalDependencies`** (뒤 5-1 때문에 비교용으로 함께 읽는다. 분석 대상은 regular만)

모집단 필터를 여기서 건다.

```sql
-- 릴리즈 2개 이상 + 최소 수명 + 폐기 아님
HAVING COUNT(*) >= 2
   AND DATE_DIFF(MAX(published_at), MIN(published_at), DAY) >= 30
```

### 1단계 — 라인별 릴리즈 시퀀스

```sql
-- 메이저 라인. 단 0.x 는 minor 가 호환성을 깨는 자리이므로 minor 까지를 라인으로 본다
line = IF(major > 0, CAST(major AS STRING), CONCAT('0.', minor))

ROW_NUMBER() OVER (
  PARTITION BY package_name, line
  ORDER BY upstream_published_at
)
```

**이 단계가 파이프라인의 급소다.** 2-2에서 확인했듯 여기가 틀리면 뒤가 전부 오염된다.

### 2단계 — 연속 릴리즈 차이

```sql
removed = deps(v_i)     EXCEPT DISTINCT deps(v_{i+1})
added   = deps(v_{i+1}) EXCEPT DISTINCT deps(v_i)
```

산출물: `(package, publisher, line, ts, removed[], added[])`

### 3단계 — 교체 후보 쌍, 표는 쪼개서

곱집합으로 표를 만들지 않는다. **제거 하나가 가진 1표를 그 릴리즈에서 추가된 개수로 나눈다.**

```
제거 moment, 추가 5개  →  각 후보 1/5 표
제거 moment, 추가 1개  →  그 후보 1표
```

깔끔한 릴리즈에 무게가 실리고 대규모 정리 릴리즈는 표가 흩어진다.

### 4단계 — 배수(lift)로 우연 걷어내기

두 숫자를 비교한다.

| | |
|---|---|
| A | X를 뺀 전이 중 Y를 넣은 비율 |
| B | 아무 전이에서나 Y를 넣는 비율 |

```
lift = A / B
```

```
dayjs :  A=31%,  B=0.4%  →  78배    진짜 대체 관계
zod   :  A= 9%,  B=8.2%  →  1.1배   그냥 요즘 다 넣는 것
```

살리는 조건: `lift >= 5` 그리고 `표 >= 최소기준` 그리고 `제거 이벤트 >= 최소기준`.

> 장바구니 분석 알고리즘(FP-Growth 등)은 여기서 쓰지 않는다. "X를 뺀 사람이 뭘 넣었나"는 이미 X를 알고 묻는 질문이라 위 조건부 비율이 더 단순하고 통제하기 쉽다. 알고리즘은 **모르는 쌍을 발굴할 때** 별도로 쓴다.

### 5단계 — 배포 주체로 묶기

```sql
GROUP BY publisher, from_pkg, to_pkg, DATE_TRUNC(ts, MONTH)
-- 한 주체의 한 달 안 같은 전환은 1표
```

publisher 판별:
1. 이름이 `@조직/패키지` → 조직명 (실측상 78%)
2. 아니면 `Links` 의 저장소 주소
3. 둘 다 없으면 개별 취급

> 근거: 실시간 변경 600건이 실제로는 297개 주체였다. 상위 8곳이 34%를 차지했다.

### 6단계 — 대체재 후보군을 데이터가 정하게

"대체 없이 제거"를 세려면 무엇이 대체재인지 알아야 한다. 목록을 사람이 정하지 않는다.

1. 4단계에서 X에 대해 배수가 높게 나온 것들을 모은다 → 대체재 후보군
2. X 제거 이벤트 중 **그 후보군이 하나도 안 들어온 것**을 "대체 없이 제거"로 센다

이 방식의 부수 효과로 **비교군을 미리 정할 필요가 없어진다.** 기획서가 걱정하던 코호트 구성 실패 시나리오가 줄어든다.

### 7단계 — 집계

```sql
SELECT from_pkg, to_pkg,
       SUM(vote) AS votes,
       SUM(vote) / SUM(SUM(vote)) OVER (PARTITION BY from_pkg) AS share
FROM collapsed
GROUP BY from_pkg, to_pkg
ORDER BY from_pkg, votes DESC
```

## 4. 흐름 요약

```
스냅샷 고정
  ↓ 모집단 필터 (릴리즈 2+, 수명 30일+, 폐기 제외)
릴리즈 시퀀스        ← 메이저 라인별 + 발행시각 순   ★급소
  ↓
의존성 차이           removed[] / added[]
  ↓ peer·optional 재분류 제외                        ★신규
전이 이벤트
  ↓ 제거 1표를 추가 개수로 분배
교체 후보 쌍
  ↓ 배수(lift) + 최소 표본
진짜 교체 쌍
  ↓ 배포 주체 + 월 단위로 묶기
표
  ↓ from_pkg 기준 비율
마이그레이션 지도
```

## 5. 함정과 대응

### 5-1. ★신규 — peerDependencies 이동이 제거로 잡힌다

표본에서 `react`가 6회, `react-dom`이 5회 제거로 잡혔다. 실제로는 **버려진 게 아니라 `dependencies`에서 `peerDependencies`로 옮겨진 것**으로 보인다. 라이브러리가 성숙하면 흔히 하는 정리다.

V1 계약은 regular `Dependencies`만 읽기로 되어 있어서 이 이동이 **완전한 제거로 보인다.** 그러면 이탈률이 부풀고, 같은 릴리즈에 뭔가 추가됐으면 있지도 않은 마이그레이션이 만들어진다.

**대응**: 제거로 판정하기 전에 다음 버전의 `PeerDependencies`·`OptionalDependencies`에 그 이름이 있는지 확인한다. 있으면 제거가 아니라 재분류로 표시하고 교체 쌍 생성에서 제외한다.

> **데이터 계약 수정 사항**: non-regular 배열을 분석 대상에는 넣지 않되 **판정용으로는 읽어야 한다.** 지금 계약은 아예 제외하고 있어서 이 구분이 불가능하다.

### 5-2. 조합 폭발

제거 3개 × 추가 5개 = 15쌍이 생긴다. → 3단계의 표 분배로 대응.

### 5-3. 우연히 같이 일어난 변경

요즘 어디서나 추가되는 라이브러리가 대체재로 올라온다. → 4단계 배수로 대응.

### 5-4. 한 조직이 수십 표

모노레포를 한꺼번에 갈아타면 같은 쌍이 수십 개 생긴다. 마이그레이션 지도는 신규 선택보다 **더** 취약하다. 갈아타기는 저장소 전체에 한 번에 하기 때문이다. → 5단계로 대응.

### 5-5. 릴리즈 순서 (2-2에서 실측)

→ 1단계로 대응.

### 5-6. 제거와 추가가 다른 릴리즈에 나뉨

v2.3에서 빼고 v2.5에서 넣으면 놓친다. 창을 넓히면 잡히지만 잡음도 는다.

**대응**: 같은 릴리즈를 기본값으로 하고, 창을 넓힌 결과는 **별도 등급으로 표시**한다. 섞지 않는다.

## 6. 결과가 맞는지 확인하는 법 — 정답지

이미 답이 알려진 마이그레이션을 넣어서 상위에 나오는지 본다.

| 정답 쌍 | 근거 |
|---|---|
| `request` → `axios` / `got` | request 2020년 공식 폐기 |
| `node-sass` → `sass` | 공식 권고 |
| `tslint` → `eslint` | TypeScript 팀 공식 종료 |
| `enzyme` → `@testing-library/react` | React 18 미지원 |
| `moment` → `dayjs` / `date-fns` | 유지보수 모드 선언 |

**5개 중 5개가 상위에 나오면 파이프라인이 맞다.** 안 나오면 어딘가 틀렸다.

이 검증은 발표 자료로도 그대로 쓴다. "알려진 사례 5개를 전부 재현했습니다"가 방법론 슬라이드가 된다.

## 7. 말할 수 없는 것

정직하게 화면과 문서에 적는다.

- **선언에서 뺐다고 코드에서 안 쓰는 건 아니다.** 다른 라이브러리를 통해 딸려 올 수 있다.
- **같은 릴리즈에 있다고 인과는 아니다.** 배수로 크게 줄지만 없어지지 않는다.
- **왜 갈아탔는지는 모른다.** 성능인지 용량인지 유지보수 중단인지 데이터에 없다.
- **관측 모집단은 npm에 공개된 패키지의 저자들이다.** 실무 앱 팀은 대부분 배포하지 않는다.
- 날짜 라이브러리의 "대체 없이 제거"에는 **내장 기능으로 옮겨간 경우**가 섞인다. 이건 특정 패키지의 패배가 아니라 분야 자체의 축소다.

## 8. 착수 순서

| | 할 일 | 이유 | 비용 |
|---|---|---|---|
| 1 | 연속 버전 쌍의 시간 역전 비율 측정 | 1단계 설계가 여기 걸린다 | 쿼리 1회 |
| 2 | 신호 밀도 실측 (변경 있는 전이 / 교체 이벤트) | 2-5가 미확정 | 쿼리 1회 |
| 3 | peer·optional 재분류 비율 측정 | 5-1의 규모 확인 | 쿼리 1회 |
| 4 | 정답지 5쌍 재현 | 파이프라인 검증 | 쿼리 1회 |
| 5 | 주체 묶기 전후 비교 | 부풀림 규모 확인 | 쿼리 1회 |

**1번을 하기 전에 2단계 이후를 구현하지 않는다.** 순서가 틀린 상태로 만들면 가짜 마이그레이션이 대량 생성된다.

## 부록 — 이 문서의 검증 근거

- 260개 패키지 표본 실행 결과는 본문 2절 수치 그대로다. npm 공개 레지스트리 사용, 인증 없음.
- 릴리즈 4,690만 / 패키지 405만 / moment 채택자 58,287 등은 2026-08-24 스냅샷 기준 검증 보고서 실측치다.
- 배포 주체 600건 → 297곳은 2026-08-31 변경 피드 실측이다.
- 4단계 예시의 `dayjs 78배`, `zod 1.1배`는 **설명용 가상 수치**다. 실측 아님.
