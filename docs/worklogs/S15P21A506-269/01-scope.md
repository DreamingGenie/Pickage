# 01. 작업 정의와 변경 범위

상태: 병행 범위 및 승인된 대상 DB 날짜 반영·검증 완료, 공통 이력 연동을 포함한 269 전체 범위는 미완료. [계획](02-plan.md) · [결과](05-results.md)

## 목표와 경계

267의 package/version 전체 적재와 병행하여, 다운로드 구간 집계·저장소 지표 생성·requirements 대상 버전 해석·버전별 dependents 집계가 참조할 스냅샷 시간 계약과
독립 검증 모듈을 구현한다. 기존 PostgreSQL loader·V1·V2·공유 README는 수정하지 않는다.
현재 PostgreSQL의 `snapshot_at DATE` 명칭은 유지하고 정확한 원천 시각은 `snapshot_timestamp`로
구분한다. 한 UTC 날짜에 서로 다른 snapshot 시각이 있으면 임의 병합하지 않고 거부한다.

2026-09-08 후속 승인으로 267의 전체 데이터 DB `pickage_267_full_defaulted`에 snapshot 날짜를
추가하는 범위를 진행한다. 기존 SQL의 명시적 DATE INSERT만 짧은 트랜잭션으로 실행하며,
version/package·마이그레이션·공통 게시 이력은 변경하지 않는다. 이번 실행 증거는 로컬 기록에
보존하고 공통 실행 이력 연결은 별도 후속 작업으로 둔다.

| 작업 | 포함 내용 | 제외 / 합류 조건 |
| --- | --- | --- |
| T-01 | 사용자 지정 Projects의 실제 SnapshotAt 목록을 추출·검증 | 선택 Projects 범위를 deps.dev 전체 역사라고 표현하지 않음. DB 적재 성공 날짜로 P를 바꾸지 않음 |
| T-02 | UTC 날짜 변환, 원천 시각 보존, 정렬·중복·같은 날짜 시각 충돌 검사 | DATE에서 원천 자정 시각을 복원하지 않음 |
| T-03 | 동일 목록의 직전 P, `[P,S)` 경계·불규칙 간격·최초/누락/범위 밖 사유 | 실제 다운로드 합계 계산은 후속 다운로드 구간 집계에서 수행 |
| T-04 | Projects 정확한 관측 시각 선택, 미래/과거 대체 제한, 대상 집합 정책 | 저장소 지표 생성·requirements 대상 버전 해석·버전별 dependents 집계는 별도 후속 작업 |
| T-05 | 정책 버전·해시·입력 계보를 가진 후보와 명시적 날짜 INSERT SQL, 격리 DB 검증 및 후속 승인된 267 대상 DB 날짜 반영 | 공통 실행 이력·snapshot-reference PUBLISHED·서비스 준비 상태는 후속 통합 |

## 완료 기준

| ID | 병행 범위의 기대 결과 |
| --- | --- |
| AC-01 | 원천 시각·출처·입력 SHA와 UTC 날짜가 재현되며, 확인하지 않은 입력을 승인 데이터로 표시하지 않는다 |
| AC-02 | 정렬·동일 시각 중복 제거·같은 UTC 날짜의 다른 시각 거부, 직전 P의 결정이 DB 상태와 독립이다 |
| AC-03 | 24→31은 24~30일, 14일 간격은 실제 14일, 최초·누락·범위 밖을 실제 0과 구분한다 |
| AC-04 | 미래 Projects 관측과 다른 스냅샷의 package/version을 과거의 확정 데이터로 사용하지 않는다 |
| AC-05 | 정책 버전·해시, 입력 해시·범위, 미지원 범위가 산출물과 문서에서 일치한다 |
| AC-06 | 독립 테스트·소형 실제 원천 검증을 수행하고 미실행 DB 연동은 별도 인계한다 |

269 범위의 **DB 중복 없는 적재, 공통 실행 이력 연결, 서비스 완료 snapshot 노출 제어**까지
끝나야 269 전체 완료다. 이번 독립 범위의 완료와 티켓 전체 완료를 구분한다.

## 범위 변경

사용자 후속 지시: "스냅샷은 proejcts에 있는 스냅샷들만 뽑아서 넣으면 돼".
이에 따라 별도 BigQuery Snapshots 전체 목록 조회를 제외하고, 선택한 Projects 디렉터리의
실제 SnapshotAt을 검증한 날짜 목록을 기준으로 삼는다. 첫 날짜는 선택 목록에서 이전 항목이
없다는 의미이며, deps.dev 역사상 첫 스냅샷이라고 단정하지 않는다.
