# 서비스 데이터 서버 이관 계획

상태: **실행 전 계획**. 계획과 현재 관측, 추정, 실제 실행 결과를 구분한다.

## 1. 목표와 완료 조건

로컬에서 검증한 다섯 테이블을 서버로 옮겨 동일한 키와 조회값으로 서비스에서 사용한다.
`package_version_snapshot`의 날짜별 파티션 구조를 유지하고 Flyway로 생성되는 구조와 맞춘다.

- 사용자 데이터 대상: `public.package`, `public.version`, `public.snapshot`, `public.package_snapshot`, `public.package_version_snapshot`.
- 파티션 대상: 부모의 전체 자식 229개. 기존 위치인 `vd193_reload_20260912_ready01.dYYYYMMDD`를 이번 복원에서 보존한다.
- 로컬 백업 스키마, 작업용 reload 테이블, 로컬 ETL 이력 데이터, MinIO 데이터는 이번 전송 대상에 포함하지 않는다.
- 기존 서버 Flyway 이력은 실제 적용 기록으로 보존한다. 로컬 이력으로 덮어쓰거나 baseline/repair로 적용 사실을 만들지 않는다.
- 완료는 파일 업로드가 아니라 **복원·구조/데이터 검증·합의한 Flyway 버전 적용·API 연결 확인**까지다.
- ETL 이력의 내용까지 옮기지 않으므로 과거 배치의 서버 재개·자동 게시 가능 상태를 완료로 주장하지 않는다.

## 3. 선택한 이관 방식

**압축 디렉터리 덤프 → 같은 서버 PostgreSQL의 후보 DB 복원 → 검증 → API 연결 전환**을 기본안으로 한다.

- 원래 서버 DB는 약 7.6MiB여서 후보 DB를 만들어도 144GiB 데이터가 두 벌 필요한 상황은 아니다.
- 원래 DB와 API 연결을 유지한 채 후보 DB에서 복원·실패 복구를 진행한다. 자원은 공유하므로 성능 격리는 아니다.
- 후보 DB 이름은 `pickage_import_341_<runid>` 같은 실행별 고유 이름으로 구현 시 확정한다.
- 로컬 `pg_dump -Fd -j 4 --compress=zstd:1`을 우선 시험한다. zstd 지원/효율이 부족하면 `gzip:1`을 비교한다.
- 덤프 선택은 네 일반 테이블의 `--table`과 부모의 `--table-and-children`을 사용한다. 실제 현재 클라이언트에서 이 옵션과 234개 테이블 선택을 확인했다.
- 서로 다른 시점의 덤프를 다섯 개 만드는 대신 한 번의 병렬 pg_dump로 일관된 스냅샷을 만든다.
- 서버 복원은 `pg_restore`의 data/post-data 단계 병렬 처리를 사용한다. 컨테이너가 2GiB인 현재 조건에서는 jobs=2로 파일럿을 시작하고, jobs=4 및 자원 확대는 결과에 따라 결정한다.
- `--no-owner --no-acl --exit-on-error`를 복원에 적용하고 서버 역할의 소유권·권한을 별도로 확인한다.
- 동일 파티션 배치를 복원하므로 `--load-via-partition-root`로 모든 행을 다시 라우팅하지 않는다.
- 전송은 SSH 기반 이어받기와 파일별 SHA-256 검증을 사용한다. Windows 쪽 rsync/WSL 사용 가능 여부를 먼저 확인하고, 없으면 이어받기 가능한 SFTP 경로를 정한다. 압축 디렉터리를 다시 압축하거나 중복 복사하는 단계를 기본값으로 넣지 않는다.

공식 근거: [pg_dump](https://www.postgresql.org/docs/16/app-pgdump.html), [pg_restore](https://www.postgresql.org/docs/16/app-pgrestore.html), [대량 적재](https://www.postgresql.org/docs/16/populate.html).

### 비교한 대안

| 대안 | 판단 |
| --- | --- |
| 서버의 기존 다섯 테이블에 직접 덮어쓰기 | 비어 있어 가능하지만, 복원 중 API가 불완전한 구조/데이터를 볼 수 있고 실패 복구 경계가 불명확해 기본안에서 제외 |
| 기존 일반 테이블에 data-only 복원 | 파티션 구조가 옮겨지지 않고 기존 PK/FK 유지 비용이 있으므로 현재 목표와 맞지 않음 |
| CSV/Parquet로 전부 다시 적재 | 기존 검증 데이터·DDL을 활용하는 덤프보다 이관용 변환·적재 코드를 더 요구하므로 보조안으로 보존 |
| 전체 PostgreSQL 볼륨 복사 | 다섯 테이블만 선택하는 목적에 맞지 않고 원치 않는 백업/작업 DB까지 포함하므로 제외 |

## 4. Flyway와 덤프의 역할 분리 — 전체 실행 전 필수 설계

현재 V1~V5는 수정하지 않는다. 추가 마이그레이션 번호는 구현 직전 최신 이력을 확인한다. 지금 확인한 다음 후보는 V6이다.
새 마이그레이션은 날짜별 파티션 부모와 음수 금지 CHECK를 계약에 반영하며 두 시작 상태를 명시적으로 지원한다.

1. 기존 일반 테이블이 **비어 있는 상태**: 외부 의존성을 확인하고 트랜잭션 안에서 파티션 부모로 교체한다. 필요한 PK/FK/인덱스를 보존 또는 재구성한다.
2. 검증된 파티션 부모가 **이미 복원된 상태**: 컬럼·PK·FK·CHECK·부모/자식 경계·인덱스가 요구 계약과 일치하는지 검사한다. 단순히 같은 이름이 있다는 이유로 성공 처리하지 않는다.
3. 데이터가 있는 일반 테이블이나 예상 밖 스키마는 자동 삭제/변환하지 않고 실패시킨다. 별도의 데이터 보존 전환 경로가 필요하다.

**후보 DB의 준비·복원 순서**:

1. 기존 서버 DB의 작은 백업을 만들어 Flyway 이력을 포함해 보존하고, 후보 DB에 복원한다. 진짜 적용된 V1 이력을 그대로 복제하며 이력을 새로 지어내지 않는다.
2. 후보가 원래 서버와 같은 V1 상태인지, 교체할 다섯 테이블이 여전히 0행인지 확인한다. 적용할 코드의 V1 체크섬과 실제 이력도 먼저 대조한다.
3. 후보 안에서만 다섯 빈 테이블을 FK 역순으로 제거한다. 허용 목록·DB 이름·소유권·0행·외부 의존성 검사와 트랜잭션을 사용하고 CASCADE는 사용하지 않는다. Flyway 이력은 유지한다.
4. 필요한 자식 스키마를 생성하고, 로컬 선택 덤프의 pre-data → data → post-data를 후보에 복원한다. 이 후보 준비 단계의 DDL 변화는 실행 기록에 남긴다.
5. 합의한 배포 revision의 Flyway 마이그레이션을 **서비스 API 기동과 분리해** 적용한다. 현재 서버는 V1이므로 V2~V5의 영향과 새 마이그레이션을 함께 검토해야 한다. API 기동의 60초 healthcheck 안에서 대용량 인덱스 생성이 끝날 것으로 가정하지 않는다.
6. Flyway validate와 최종 실제 구조 검사를 모두 통과시킨다. 복원된 구조를 새 마이그레이션이 검증·정식 수용한 뒤에만 서비스 연결을 허용한다.

V4는 `package`, `version`, `package_version_snapshot`에 조회 인덱스를 추가한다. 복원 후 V4를 적용하면 **현재 로컬 144.6GiB보다 인덱스 공간과 생성 시간이 늘 수 있다**. 반드시 덤프의 인덱스와 V4의 추가 인덱스를 대조하고 별도 예산에 넣는다. 기능상 필요한 인덱스를 용량 절약만을 이유로 임의 생략하지 않는다.

구조 미리보기에서는 V4의 `idx_package_name_prefix`, `idx_version_pkg_ordinal`, `idx_pvs_pkg_snapshot`이 없었다. 전체 실행 시에는 archive TOC와 SQL 정의를 다시 검사한다. 이 인덱스가 소스에 추가됐다면 복원 뒤 V4가 같은 이름으로 다시 생성해 실패할 수 있다. **중복 생성은 실행 전 차단**하고, 정의가 일치하는 V4 소유 인덱스만 복원 목록에서 제외해 V4가 생성하게 한다. 파티션 인덱스의 자식 및 ATTACH 의존성도 함께 처리하고 파일럿으로 확인한다. 정의가 다르거나 소유 단계가 불명확하면 자동 제외하지 않고 계획을 수정한다. V4 원문이나 Flyway 이력을 바꿔 충돌을 숨기지 않는다.

새 마이그레이션은 빈 DB에 V1부터 순서대로 적용하는 경로도 시험한다. 서버 후보에만 통하는 수동 구조를 다시 만들지 않는 것이 목표다.
새 날짜 파티션 자동 생성과 배치 자동화는 후속 범위이며, 빈 부모에는 날짜에 맞는 자식이 필요하다는 계약을 문서화한다.

## 5. 단계별 실행 계획

| 단계 | 수행 내용 | 통과 기준/산출물 |
| --- | --- | --- |
| M0 대상 고정 | 서버/로컬 실체, 새 데이터 여부, 배포 revision, 스키마 차이, 덤프 포함/제외 목록 확인 | 실체/스키마/자원 보고서와 대상 목록. 예상 밖 변경 시 중단 |
| M1 로컬 구현·구조 검증 | 새 Flyway와 후보 DB 준비·덤프/복원 스크립트 구현. 일반 빈 테이블/이미 파티션/잘못된 구조 검증 | 두 정상 경로의 동일 계약, 비정상 경로의 롤백·실패 증거 |
| M2 작은 실제 데이터 예행연습 | 다섯 테이블의 FK가 닫힌 표본 DB를 로컬에서 구성. 문자열/JSON 큰 version 행, package_snapshot, 날짜 파티션을 포함. 덤프·전송·서버 격리 복원·검증을 동일 도구로 측정 | 명시한 표본 범위·건수, 단계별 시간/압축률/메모리/디스크/WAL. 서버 쓰기 시작은 실행 단계의 명시적 권한 확보 후 |
| M3 전체 덤프 | 고정한 로컬 입력에 한 번의 -Fd 병렬 덤프. 경고/종료 코드·TOC·파일 해시 기록 | 완성된 archive, 5논리/234테이블 정의 및 데이터 항목 포함, 제외 대상 없음 |
| M4 전송 | 완성 archive를 서버 전용 경로로 이어받기. 전체 파일 목록·바이트·SHA 대조 | source/target 파일 100% 일치. 불완전 전송 상태에서는 복원 금지 |
| M5 후보 DB 복원 | §4 순서대로 준비·pre-data·data·post-data·합의한 Flyway 적용. DB 전용 연결 사용 | 모든 단계 종료 0, 예상 객체만 생성, FK/인덱스 정상, 기존 DB는 그대로 |
| M6 데이터·API 검증 | 아래 검증 수행, 통계 갱신, 후보 연결의 최소 조회 확인 | 행 수/합계/표본값/구조/Flyway/권한/API 검사 PASS |
| M7 서비스 연결 전환 | 후보 연결로 DB_URL의 DB명만 명시적으로 변경. API 재시작/health/조회 확인, 되돌림 검증 | 실제 서비스가 후보 DB를 조회, 실패 시 원래 DB_URL로 복귀. 원래 DB·덤프 보존 |

M2가 통과하면 전체 소요 시간을 다시 보고한다. 이전 로컬 집계/적재 시간은 이번 덤프·인터넷 전송·서버 복원 예상치로 재사용하지 않는다.

## 6. 용량·메모리·시간 예산

- 저장 공간 통과식: **실측 archive + 복원 최종 테이블/인덱스 + V4 등 추가 인덱스 + 실측 기반 WAL/임시 공간 + 다른 서비스 여유분**이 서버 여유 디스크보다 작아야 한다.
- 현재 144.6GiB는 출발점이다. 압축률과 서버 인덱스 추가량을 모른 채 297GiB면 충분하다고 확정하지 않는다.
- 자원이 부족하면 jobs 축소·archive 별도 디스크/승인된 보관 경로·임시 용량 확보 순서로 재설계한다. 기존 서버 파일이나 Docker 볼륨은 임의 삭제하지 않는다.
- DB 메모리를 올릴 때 Spark 6.5GiB, API 1.6GiB, 웹 256MiB 상한과 호스트 여유를 함께 계산한다. 현재 사용량이 작다는 이유만으로 DB에 8~12GiB를 배정하지 않는다.
- 필요한 경우에만 검토한 DB 전용 설정을 적용하고 원래 설정과 복귀 방법을 기록한다. fsync/synchronous_commit 비활성화, 트리거 무시로 속도를 얻지 않는다.
- 단계별 경과 시간을 따로 잰다: dump / checksum / transfer / pre-data / COPY / indexes-FK / 추가 migration / validation / cutover.
- `version`, `package_snapshot`처럼 큰 단일 테이블의 데이터는 pg_dump/restore jobs를 늘려도 자동으로 테이블 내부가 분할되지 않는다. 최대 작업 단위와 병렬 총시간을 함께 고려하고 단순 4배 속도나 패키지당 시간 환산을 하지 않는다.

## 7. 검증 범위

1. **Archive**: TOC의 대상 5개와 229개 자식, 포함된 constraint/index/attach 항목, 역할·스키마 의존성, 압축 지원을 확인한다.
2. **행 수**: 소스의 동결 시점과 같은 검증 기준을 만든다. 이미 검증된 receipt의 재사용은 입력/쓰기 불변 근거가 있을 때만 허용한다. 없으면 소스 exact count를 별도 비용으로 측정한다. 서버는 다섯 테이블과 파티션별 exact count를 확인한다. 통계 추정치로 대체하지 않는다.
3. **핵심 값**: 날짜별 count 합계·0 포함 건수, package/version 키, NULL 분포, version JSON/문자열 표본, react/pino/vue 등 고정 표본의 전체 날짜 반환값을 비교한다. 행 수와 합계만으로 모든 행의 완전 동일성을 증명했다고 주장하지 않는다.
4. **구조**: PK/FK/CHECK, `convalidated`, 인덱스 `indisvalid`, 파티션 수/경계/연결과 비대상 객체 보존을 확인한다.
5. **실행 이력**: Flyway 이력과 체크섬, 실제 DDL 정합성을 함께 검사한다. ETL 이력 테이블이 새로 생겨도 로컬 배치 실행 이력을 이관했다고 표시하지 않는다.
6. **서비스**: ANALYZE 후 서버의 패키지/버전/날짜 조회, 실제 배포 revision의 API 조회, 권한과 health를 확인한다. 새 API 기능의 배포나 조회 의미 변경은 자동으로 범위에 추가하지 않는다.

## 8. 중단·재시작·복구

- 긴 실행은 채팅/SSH 세션 수명에 묶이지 않는 작업으로 실행하고 상태·PID·시각·로그를 남긴다. 정상 실행에 임의의 1시간 전체 제한을 두지 않는다. 준비/잠금/연결에는 제한을 둔다.
- pg_dump 자체의 중간 재개는 지원한다고 가정하지 않는다. 실패한 실행은 별도 실패 디렉터리에 남기고 새 일관 스냅샷으로 재덤프한다. 다른 시점의 archive 조각을 합치지 않는다.
- 전송은 파일별 이어받기가 가능하지만 해시 일치 확인 후만 완료 처리한다.
- 병렬 pg_restore도 전체가 하나의 트랜잭션이거나 단순 재실행이 안전하다고 가정하지 않는다. 구현에서 TOC 작업 단위로 상태와 대상 행/객체를 대조한다. 단계 중간 실패 시 실패/미완료 객체만 후보 DB에서 재준비하거나 후보 전체를 새로 만드는 경로를 제공한다. 이것이 구현되지 않으면 재개 지원이라고 표시하지 않는다.
- data 재시도 시 성공한 테이블에 COPY를 다시 실행해 중복을 만들지 않는다. index/FK 단계 실패는 확인된 미완료 항목만 재실행한다.
- 전환 전에는 원래 DB에 손대지 않는다. 전환 후 문제가 발생하면 API DB_URL을 원래 값으로 되돌린다. 전환 후 새 쓰기가 발생한 경우에는 그 데이터를 보존하는 추가 절차 없이 단순 되돌림하지 않는다.
- 복원 후보 삭제·기존 DB 교체·자원 설정/서비스 연결 변경은 각각 정확한 대상과 복구 방법을 기록한 실행 단계에서 처리한다.

## 9. 구현 예정 위치와 이번 턴의 종료 조건

- `backend/src/main/resources/db/migration/V<next>__partition_package_version_snapshot.sql`: 새 스키마 계약. 번호는 최신 develop 확인 후 확정.
- `scripts/service-data-migration/`: 계획 검사, dump/TOC/전송 해시, 후보 준비, 복원 상태, 검증·전환 안내. 아직 생성하지 않았다.
- `deploy/prod/app/compose.yaml`: 필요하면 API의 DB_URL을 별도로 덮어쓸 수 있는 최소 변경과 검증된 자원 설정. DB 초기화용 POSTGRES_DB를 바꿔 API 연결만 변경한 것으로 착각하지 않는다.
- `data/service-data-migration/<runid>/`: 원본 archive, 로그, 해시, 검증 결과. Git에 넣지 않는다.
- 이 작업 폴더: 계획·측정 요약·문제·해결·운영 절차. 시크릿과 대용량 반복 로그를 넣지 않는다.

이번 턴은 **계획 작성·검토·보고에서 종료**한다. 코드 구현, 전체 dump, 서버 파일 생성/전송, 자원 변경, DB 준비/복원/전환, 커밋/푸시는 아직 실행하지 않는다.
