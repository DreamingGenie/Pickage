# 서비스 데이터 이관 최종 결과

## 완료한 일

로컬 PostgreSQL의 `package`, `version`, `snapshot`, `package_snapshot`, `package_version_snapshot`을 서버로 옮겼다. 마지막 테이블은 날짜별 229개 파티션을 포함한다. 전체 덤프를 후보 DB에 복원한 뒤 인덱스·외래키·Flyway V6까지 완료하고, 2026-09-15 07:46:33 KST에 기존 서비스 이름 `pickage`로 전환했다.

현재 서비스 DB의 OID는 22046이다. 이전의 빈 서비스 DB는 `pickage_before_341_20260915`(OID 16384)로 보존했고 접속을 차단해 두었다. API 이미지와 DB 연결 URL은 유지했다. DB 이름 변경으로 전환했으므로 대량 데이터를 다시 복사하지 않았다.

## 시행착오와 개선 이유

1. **Windows 상태 파일 교체 실패**: 공유 잠금 때문에 검증 상태 저장이 실패했다. 고유 임시 파일과 원자적 교체 재시도를 추가하고, 완료한 덤프와 원래 검증 이력을 보존했다. 이후 사용자가 반복 원본 검증을 유예하고 서버 복원을 진행하기로 결정했다.
2. **외래키와 인덱스의 잠금 충돌**: 부모 테이블의 version FK 검사가 실행되는 동안 날짜별 PK 생성이 잠금을 기다렸다. 사전 통계가 없는 상태에서 재구성한 계획은 양쪽 테이블을 읽고 정렬하는 경로였다. 실행 중 내부 계획을 직접 추출한 결과와는 구분한다.
3. **완료 데이터를 버리지 않는 재개**: 동일 덤프에서 만든 빈 참조 DB와 실제 객체 정의를 비교해 완료 객체를 건너뛰었다. 기존 작업을 종료한 뒤 PK/인덱스 연결 → VACUUM/ANALYZE → 실제 검사 계획 → FK 순서로 실행했다. 데이터 COPY는 반복하지 않았다.
4. **실제 실행 계획으로 진행 여부 결정**: 첫·중간·마지막 날짜에서 양쪽 Index Only Scan, Heap Fetches=0, 정렬 없음이 확인된 경우에만 전체 FK로 진행했다. 대표 검사 실측은 약 21.0/22.2/23.4초였다.
5. **자동 유지보수를 이전 작업으로 오인**: 첫 재개 사전 검사가 자동 VACUUM까지 남아 있는 클라이언트로 취급해 중단했다. 일반 클라이언트만 검사하도록 고친 후 새 실행으로 진행했다. 이 실패는 인덱스 복원 전이며 실패 기록도 보존했다.
6. **DB 연결과 기능 배포 분리**: 기존 운영 이미지가 이관 DB로 정상 기동하는 것을 먼저 확인했다. 하지만 그 이미지에는 패키지 조회 라우트가 없었고 전환 전후 모두 404였다. DB 전환 성공과 최신 API 기능 배포 성공을 분리해 기록했다.

## 확인한 결과와 남은 경계

- 관련 단위 테스트 38개와 별도 작은 DB의 부분 복원, 완료 재실행, 기존 PK/데이터 보존, 완료 후 객체 변조 감지 시험을 통과했다. 작은 데이터 성공 경로 시험에만 해당 테스트 DB의 순차 읽기를 비활성화했으며 서버에 그 설정을 적용하지 않았다.
- 서버의 외래키 검증, 229개 파티션 구조 검사, Flyway V1~V6 검사가 완료됐다.
- 전환 후 API의 JDBC 연결 10개가 새 DB OID를 사용했다. API/PostgreSQL/web은 healthy, 외부 HTTPS health는 HTTP 200/UP이었다.
- React/Pino의 두 날짜 dependents 합계가 전환 전후 같았다. 사용자가 제공된 SQL을 직접 실행한 후 정상 동작을 확인했다. 사용자의 확인을 전수 데이터 비교나 모든 쿼리의 성능 측정으로 확대 해석하지 않는다.
- **원본과 서버의 전체 행 값 대조는 유예**했다. 복원 결과 `RESTORED_UNVERIFIED`는 유지하고, 별도 전환 기록은 `SERVICE_DB_SWITCHED`로 남겼다. 전환이 유예된 검증을 대신하지 않는다.
- **최신 백엔드 배포 및 그래프 API 검증**, 원본 전수 대조, 임시 산출물 정리는 후속 작업이다. 복구용 기존 DB는 삭제하지 않았다.
