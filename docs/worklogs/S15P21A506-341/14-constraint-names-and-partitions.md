# 제약 이름 통일과 날짜 파티션 생성 책임

## 요청과 변경 범위

2026-09-15. 리뷰 ③의 환경별 제약 이름 차이는 후속 Flyway 마이그레이션으로 통일한다. 리뷰 ④는 데이터 업데이트 작업이 날짜 파티션을 먼저 준비한 뒤 적재하는 것으로 책임을 정하고 메모를 남긴다.

- 작업 브랜치: `data/feat/S15P21A506-341-service-data-server-migration`
- 작업 위치: 별도 `S15P21A506-341-constraint-review` worktree. 기존 `develop` 작업 폴더와 미추적 파일은 유지한다.
- 이미 적용된 V1~V6는 수정하지 않는다. V7과 전용 로컬 통합시험을 추가한다.
- 최초 구현 범위는 코드·문서·격리된 로컬 PostgreSQL 검증이다. 이후 사용자 요청으로 원격 추적 브랜치를 확인하고 관련 파일 커밋·푸시를 진행한다. 운영 DB 적용과 Jira 변경은 포함하지 않는다.

## 작업 계획

1. 부모 테이블의 제약 종류·컬럼·참조 대상·검증 상태를 확인하고 이름만 변경하는 V7을 추가한다.
2. 새 DB, 과거 대문자 이름, 운영과 같은 복원 이름에서 같은 결과가 나오는지 검사한다.
3. 데이터·인덱스·제약 객체 보존, 재실행, 잘못된 정의·이름 충돌의 원자적 실패를 검사한다.
4. 파티션 생성 책임과 검증 결과, 미실행 범위를 기록한다.

## ③ 제약 이름 계약

V1은 대문자 이름, V6의 새 DB 경로는 소문자 이름, 과거 적재 파이프라인은 `version_fk` 같은 별도 이름을 사용한다. V6는 의미상 구조를 확인하지만 이름은 통일하지 않는다. V7은 기존 이름을 가정하지 않고 제약 정의로 대상을 찾는다.

| 부모 제약 | V7 이후 기준 이름 |
| --- | --- |
| PK `(package_id, version, snapshot_at)` | `pk_package_version_snapshot` |
| FK `(package_id, version)` → `version` | `fk_version_package_version_snapshot` |
| FK `snapshot_at` → `snapshot` | `fk_snapshot_package_version_snapshot` |
| CHECK `dependents_count >= 0` | `ck_package_version_snapshot_dependents_nonnegative` |

정의가 없거나 다르면 중단한다. 이미 기준 이름이면 변경하지 않는다. 이름 충돌을 피하려고 다른 객체를 삭제하지 않는다. `RENAME CONSTRAINT`만 사용하므로 데이터 UPDATE·재적재, 인덱스 재생성, FK 전수 재검증은 수행하지 않는다. PK에 연결된 인덱스 이름도 함께 변경된다.

환경 간 통일 대상은 `public.package_version_snapshot` 부모이다. 상속된 CHECK는 PostgreSQL 규칙에 따라 자식도 함께 이름을 변경한다. 자식 PK·FK의 개별 이름까지 부모와 같게 만들지는 않으며, 후속 파티션 작업은 자식 제약을 구조·연결 관계로 찾아야 한다.

기존 `historical_db_fast_publish.py`는 별도 reload 부모를 과거 이름으로 만든다. 향후 그 부모로 서비스 테이블 전체를 다시 교체하는 경우에는 게시 전에 위 이름 계약도 맞춰야 한다. 이미 성공한 V7은 Flyway가 자동 재실행하지 않으므로, 전체 재게시 구현에서 생성·전환 후 이름을 검증해야 한다. 이는 기존 부모에 새 날짜 자식만 추가하는 업데이트와 다른 작업이다.

이름 변경도 DDL 잠금이 필요하다. V7은 잠금을 5초 내 얻지 못하면 실패하며, 무한히 서비스 작업을 기다리게 하지 않는다. 실패 시 Flyway 트랜잭션이 변경을 되돌린다. 운영 적용 완료 여부는 Flyway 이력과 실제 이름으로 확인해야 한다.

## ④ 날짜 파티션은 데이터 업데이트 작업이 먼저 준비한다

**V6/V7 적용만으로 새 DB에 날짜별 자식이 생기지는 않는다. 데이터 업데이트 작업이 해당 날짜의 자식 파티션을 준비한 뒤 INSERT/COPY를 수행해야 한다.**

현재 운영에 복원된 229개 날짜는 이미 자식이 있다. 그 범위의 조회에는 문제가 없다. 신규 로컬 DB 또는 기존에 없는 새 날짜의 적재는 아래 순서를 따라야 한다.

1. 대상 부모는 `public.package_version_snapshot`으로 명시한다.
2. 날짜 D를 담당하는 자식이 있는지 실제 부모 연결과 범위를 확인한다. 테이블 이름이 존재한다는 이유만으로 적재를 진행하지 않는다.
3. 없으면 적재용 스키마를 준비하고 `[D, D+1)` 범위의 자식을 생성·연결한다. 스키마 선택과 소유권은 업데이트 작업의 설정으로 명시한다.
4. 기존 자식은 범위·컬럼·제약·인덱스가 맞는지 확인한 뒤 재사용한다. 다르면 중단한다.
5. 파티션 준비가 완료된 뒤 데이터를 적재하고, 재실행의 중복 처리 및 동시 실행 충돌을 검증한다.

DEFAULT 파티션은 두지 않는다. V6가 하루 범위의 자식만 허용하는 계약을 유지한다. 운영의 `vd193_reload_20260912_ready01`은 과거 적재 실행에서 정한 물리 스키마이며 모든 신규 환경이 반드시 그 이름을 사용해야 한다는 뜻이 아니다. 파티션은 `pg_inherits` 등 실제 연결로 찾는다.

기존 `pipeline/version_dependents/historical_db_fast_publish.py`에는 별도 reload 스키마의 부모·자식을 만들고 적재·검증·연결하는 코드가 있다. 하지만 이것을 신규 서비스 DB와 정기 업데이트에 자동 연결하는 일반 작업은 아직 없다. **정기 업데이트 구현, 실행 주기와 담당 프로세스 확정은 후속 범위**이다. 이번에는 그 기능을 구현하거나 후속 Jira 티켓을 생성하지 않는다.

## 검증 결과

- 기존 실제 표본 통합시험: **22개 검사 PASS**, Flyway 이력 `1,2,3,4,5,6,7` 확인. React/Pino/Winston의 5개 테이블 **2,179행 전체 값**이 복원 전후 같았다. 실행은 60.097초이며 대량 운영 적용 시간으로 환산하지 않는다.
- 관련 단위 테스트: **40개 PASS**. 과거 문서의 38개는 당시 기록이며 이번에는 실제 출력의 40개를 기록했다.
- Python 구문 검사 및 `git diff --check` PASS. V1~V6 파일은 변경하지 않았다.
- 독립 SQL 리뷰에서 차단 결함은 발견되지 않았다. 과거 reload 부모를 다시 서비스로 게시할 때 이름 계약이 되돌아가지 않도록 해야 한다는 후속 주의사항을 위에 기록했다.
- 전용 이름 통일 통합시험: **6개 검사 묶음 PASS**. 새 DB·과거 대문자·운영과 같은 이름에서 기준 이름 일치, 데이터와 테이블/인덱스/제약 OID·물리 파일·정의·검증 상태·상속 연결 보존, V7 SQL 재실행 시 변경 없음과 Flyway validate를 확인했다.
- 잘못된 이름 점유, 무관한 인덱스 이름 충돌, 누락·잘못된 FK를 V7이 거부했다. 자식 CHECK의 이름 충돌로 마지막 단계가 실패한 경우 앞서 변경한 부모 PK/FK 이름까지 트랜잭션으로 원복되는 것을 확인했다.
- 신규 DB에서 날짜 자식 없이 INSERT하면 실패하고, 해당 날짜 자식을 만든 뒤 같은 INSERT가 성공함을 실제 확인했다. 정기 업데이트 작업 자체를 구현한 시험은 아니다.
- 운영 DB 적용은 **미실행**이다. 이번 로컬 시험은 운영 데이터에 접근하거나 변경하지 않았다. 임시 시험 컨테이너만 생성·사용하며, 기존 로컬 원본은 표본 추출을 위한 읽기만 수행했다.

실제 표본 시험 결과: `data/service-data-migration/341/v7-existing-pilot/result.json` (이 worktree의 Git 제외 경로).

전용 시험 결과: `data/service-data-migration/341/constraint-test-20260915-05/result.json`, run `516e868d8a29`, `status=PASS`, `server_executed=false`. 사용한 전용 PostgreSQL 16 컨테이너는 시험 종료 후 제거했다.

운영 적용 전 읽기 전용 확인에서는 서비스 DB `pickage`의 V1~V6 성공 이력, 부모 제약 검증 완료, 대상 이름 충돌 없음, 자식 229개를 확인했다. 조회 시점에 부모 테이블의 타 세션 잠금은 없었다. 이는 V7 적용 완료나 이후 시점의 잠금 확보를 보장하는 결과가 아니다.
