# 서비스 DB 전환

## 범위와 계획

2026-09-15 사용자 승인으로 복원한 DB의 실제 조회, 서비스 전환 및 기동/조회 확인을 수행한다. 기존 서비스 DB는 복구용으로 보존한다. 원본 전수 값 대조는 계속 유예한다. API 기능 추가나 새 버전 배포는 범위에 포함하지 않는다.

1. 현재 운영 API 이미지/DB 연결과 실제 제공 라우트를 확인한다.
2. 이관 DB의 React/Pino 조회를 측정하고 동일 운영 이미지를 임시 루프백 포트에서 이관 DB에 연결해 기동 호환성을 확인한다.
3. 실제 배포 설정에 맞는 지속 가능한 전환 방법과 복구 절차를 준비한 뒤 API를 짧게 중지하고 전환한다.
4. API 기동, 실제 DB 연결과 제공되는 GET 응답을 확인한다. 실패하면 기존 DB로 복구한다.

## 사전 확인

- 복원 상태 RESTORED_UNVERIFIED, V1~V6 성공, 229개 날짜 파티션 구조 검사 통과. 원본 전체 값 대조는 유예됐다.
- 운영 API는 `pickage-api:manual-01`, DB_URL은 `jdbc:postgresql://postgres:5432/pickage`이다. 운영 `/v3/api-docs`의 paths는 비어 있어 로컬 저장소의 최신 패키지 API가 실제 운영 이미지에 포함됐다고 가정하지 않는다.
- 서버 compose는 POSTGRES_DB 한 변수를 PostgreSQL 초기 DB와 API 연결에 함께 사용하며, 현재 작업 디렉터리에 .env가 없다. 재배포 때 임시 API 설정이 덮어써지는 문제를 피하도록 전환 방식을 결정한다.

## 결과

- 이관 DB에서 React/Pino의 최신 버전과 2026-08-24/31 dependents 합계 조회 성공(약 0.142초). Pino는 179,551 → 181,502, React는 2,323,889 → 2,332,077이다. 버전별 count를 합한 값이며 고유 사용 패키지 수로 재해석하지 않는다.
- 동일 운영 이미지의 임시 API가 이관 DB에 연결되어 약 8초 만에 기동하고 health=UP을 반환했다. 이미지에는 V1까지만 있으나 V6 DB에 대해 이전에 적용한 migration을 변경하지 않고 기동했다.
- 기존 운영 API의 패키지 검색/개요/dependents 라우트는 모두 404, OpenAPI paths도 비어 있다. 최신 API 배포 전에는 HTTP 패키지 조회 성공을 검증할 수 없다. 이는 전환 전부터 있는 기능 미배포 상태다.
- 전환 방식: 기존 `pickage`를 `pickage_before_341_20260915`로 보존하고 복원 DB를 `pickage`로 이름 변경한다. 테이블이나 데이터를 복사/삭제하지 않고 DB OID를 보존한다. API의 기존 DB_URL/배포 설정은 유지하므로 다음 재배포에도 같은 서비스 DB를 사용한다. 변경 전 API를 중지하고 두 DB의 연결이 없는 것을 확인한다. 실패 시 이름을 복구하고 API를 재시작한다.

## 전환 완료

- 2026-09-15 **07:46:33 KST** 완료, 전환 절차 전체 **12.649초**. API 중지부터 health 회복까지 약 11초 수준이며 외부 요청을 연속 측정한 정확한 다운타임 값은 아니다.
- 서비스 DB `pickage`의 OID는 기존 후보 OID **22046**이다. 이전 서비스 DB OID **16384**는 `pickage_before_341_20260915`로 보존했다. 백업 DB는 우발적인 사용을 막기 위해 ALLOW_CONNECTIONS=false로 남겼다.
- API의 JDBC 연결 10개가 새 서비스 DB OID 22046에 연결된 것을 확인했다. API 이미지와 DB_URL은 변경하지 않았다.
- API/PostgreSQL/web 컨테이너 모두 healthy. 외부 HTTPS `/actuator/health`는 HTTP 200 / UP이다.
- 서비스 이름 `pickage`에서 229개 파티션과 React/Pino 집계값이 전환 전과 같은 것을 확인했다. 패키지 HTTP API는 전환 전후 모두 404이며, 최신 백엔드 배포가 남아 있다. 전체 서비스 기능 검증 완료로 표현하지 않는다.
- 서버 기록: `/home/ubuntu/service-data-migration/341/service-cutover-20260915-01/cutover-result.json`. 비밀값이 들어 있는 원래 API 설정 사본은 서버의 권한 0600 파일로만 보관하며 저장소/로컬 결과에 포함하지 않았다.
- 원래 복원 결과의 후보 이름은 역사 기록으로 유지한다. 현재 서비스 이름은 복원 실행 폴더의 `service-publication.json`에 기록했다. 예전 후보 이름으로 재개 도구를 다시 실행하지 않는다.

## 복구 절차

전환 실행기는 health/실제 연결/외부 health 확인 실패 시 자동으로 원래 이름을 복구하도록 작성했다. 실제 전환은 성공했으므로 복구는 실행하지 않았다. 독립 PostgreSQL 16에서 두 DB 이름의 트랜잭션 변경과 역방향 변경을 시험했다.

나중에 복구해야 한다면 API를 중지하고 두 DB의 연결이 없는지 확인한 뒤, 현재 `pickage`를 원래 후보 이름으로, `pickage_before_341_20260915`를 `pickage`로 한 트랜잭션에서 변경한다. 복구할 DB의 ALLOW_CONNECTIONS를 true로 바꾸고 API를 기동한다. 전환 이후 쓰기가 발생했다면 이를 먼저 확인해야 하며, 백업은 전환 전의 빈 서비스 DB라는 점에 유의한다. 어느 DB도 삭제하지 않는다.
