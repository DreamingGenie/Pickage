# 서비스 데이터 이관 — 큰 실제 표본 측정

이 문서는 해당 단계 당시의 계획·검증 기록이다. 이후 서버 복원과 서비스 DB 전환을 완료했으며, 현재 상태와 검증 범위는 [최종 결과](12-final-result.md)를 따른다. 당시 실패·미실행 기록은 이력으로 보존한다.

## 목적과 범위

작은 표본 2,179행은 복원 절차의 정확성을 확인했지만 전체 처리 시간을 예측하기에는 작았다.
이번에는 다섯 테이블의 실제 행과 FK 참조 행을 추출해 덤프·전송·데이터 복원·인덱스/제약 생성·검증을 나눠 측정한다.
기존 서버 `pickage`와 API 연결은 유지하고 새 후보 DB만 사용한다. 전체 이관은 아직 실행하지 않는다.

따라서 원본 DB 크기만큼의 여유 공간만 있으면 된다고 계산하지 않는다.

## 측정 해석

- 표본을 만들기 위한 참조 키 보완/별도 DB 구성은 전체 배포에서 반복하지 않는다. 해당 시간은 배포 예상에서 분리한다.
- directory dump는 데이터를 압축해 옮기며 인덱스는 목적지에서 다시 만든다. 물리 인덱스 파일을 전송하지 않는다.
- 복원 도구의 `pre-data`, `data`, `post-data`를 따로 기록한다. `post-data`에는 기본 인덱스뿐 아니라 FK 검증도 포함된다.
- Flyway V2~V6 시간에는 V4 조회 인덱스 생성이 포함된다.
- 큰 표본의 모든 행은 건수와 두 개의 순서 독립 MD5 부분합으로 비교한다. 모든 열/NULL을 포함한 확률적 무결성 검사이며 충돌 가능성이 없는 전수 비교라고 표현하지 않는다.
- 메모리는 기존 PostgreSQL cgroup의 페이지 캐시를 포함하고, WAL·호스트 디스크는 다른 부하가 섞이는 공유 지표다.
- 작은 표본의 참조 인덱스는 메모리에 들어갈 수 있지만 전체 인덱스는 그렇지 않다. 단순 배수 환산은 조건부 기준값이며 완료 시간 보장이 아니다.
- 로컬 전체 데이터에서 대표 FK 확인용 anti-join을 `EXPLAIN`만 실행하면 최근 날짜의 PK와 5,420만 버전의 PK를 읽는 Merge Anti Join이 계획된다. 이는 실제 서버의 `ALTER TABLE` 수행 시간을 측정한 결과가 아니다. 참조 테이블 크기에 따라 검증 비용이 달라질 수 있다는 근거로만 사용한다.

## 전체 실행 시간의 조건부 환산

**덤프 → 전송 → 서버 복원·검증의 단순 환산은 약 4~6시간이다. 확정 소요 시간이나 상한이 아니다.**
원본 전수 검증값을 별도로 생성하는 시간, 입력 기준 시점 고정, API 전환/검사는 아직 이 숫자에 포함하지 않았다.
따라서 모든 준비부터 서비스 전환까지 4~6시간 안에 끝난다는 의미가 아니다.

표본 50.293초에 전체 행 수의 배수를 한 번 곱하지 않았다. 각 단계가 다루는 크기를 구분했다.

| 단계 | 환산 기준 | 조건부 시간 |
| --- | --- | ---: |
| 원본 덤프 | 테이블별 CSV 바이트/행 × 전체 추정 행, 총 약 64.6GiB | 약 13분 |
| 전송 | 테이블별 압축 바이트/행 × 전체 추정 행, archive 약 6.3GiB | 약 3분 |
| 데이터 복원 | 바이트 기준 약 106.6배 ~ 행 수 기준 약 547.7배의 민감도 비교 | 약 19~97분 |
| 기본 인덱스·FK | 기존 물리 인덱스 크기 기준 약 477배 ~ 행 수 기준 약 548배 | 약 107~123분 |
| V4 추가 인덱스 | 표본의 해당 인덱스 크기를 테이블별 전체 행 수로 환산 | 약 10분 |
| 서버 값 서명 검증 | 테이블별 검증 시간 × 해당 테이블의 행 수 비율 | 약 84분 |

이 합계는 약 3.95~5.52시간이다. 범위 양 끝은 두 단순 모델의 비교이며 신뢰구간이 아니다.
통계/메타데이터 고정 비용과 반올림을 고려해 대략 4~6시간의 기준값으로만 보고한다.
특히 62MB를 1.8초에 보낸 측정이 수 GiB의 지속 전송 속도를 보장하지는 않는다.

전체 참조 인덱스의 캐시 부족, FK 검사 방식, 더 큰 외부 정렬, WAL/checkpoint 부하 때문에
실제 시간이 이 범위를 넘을 수 있다. 기존 인덱스에는 여유 공간/팽창이 있어 새 인덱스 크기와도 다를 수 있다.
서버 검증만 약 84분으로 환산되므로 검증 시간을 제외하고 “업로드 몇 분이면 끝난다”고 설명하면 안 된다.

## 해결한 문제

- 초기 표본에서 `version`의 TEMP 테이블 열 순서를 `package_id,version`으로 바꿔 MD5 서명이 달라졌다.
  원본 물리 순서인 `version,package_id`를 유지하도록 바꾸고 새 표본에서 검증했다. 실패한 `benchmark-01` 자료는 별도로 남겼다.
- 첫 SFTP 시도는 없는 목적지 파일에 `put -a`를 적용해 실패했다. 새 파일은 `put`으로 전송하고 SHA를 대조했다.
  앞선 작은 파일럿에서 확인한 부분 파일 이어받기와 구분한다.
- 측정 뒤 표본 생성기의 입력 일관성/쓰기 제한을 강화했다. PostgreSQL에서는 읽기 전용 트랜잭션 안의 CTAS도 거부되므로
  빈 TEMP 구조를 먼저 만든 뒤 `REPEATABLE READ READ ONLY`로 데이터를 채운다. 별도 작은 실제 DB에서 이 실행 경로를 확인했다.
  이미 측정한 큰 표본 파일의 생성 이력을 새 코드로 소급해서 표시하지 않는다.
