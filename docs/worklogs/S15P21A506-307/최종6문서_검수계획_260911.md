# 6문서 최종 정밀 검수 계획 및 계획 평가

작성: 2026-09-11. Jira: S15P21A506-307. 기존 MR: !106.
시작 HEAD: `41e5e9f`, 최신 확인 develop: `6f4fe68`. 변경은 기존 MR 브랜치에서 수행한다.

## 1. 완료 기준

docs 루트의 서비스 기획서·요구사항·IA·개발 구상안·변경 상세분석 5개와 커뮤니티 구현계획을
전체 읽고, 새 팀원이 사용자 흐름부터 구현·운영·검수까지 따라갈 수 있는지 판단한다.
검색 일치, 표·링크 검사만으로 의미 검수를 통과시키지 않는다. 각 발견 사항에는 문제가 생기는
구체적 상황, 근거, 수정, 수용한 잔여 한계를 기록한다.

## 2. 판단 순서

1. 사용자가 확정한 후보 최대 3개·기준만 초기 선택·최대 비교 3개와 이전 기획 유지 결정.
2. 사용자가 승인한 AI팀 랭커 원문. community에는 관련 제품 결정을 적용한다.
3. 현행 기획의 제품 요구. 현재 코드 사실과 목표 요구를 구분한다.
4. 코드·migration·설정은 구현 현황의 증거, 공식 외부 문서는 외부 API 사실의 증거다.

제품 결정으로 외부 API 사실을 바꾸거나, 코드 미구현을 이유로 사용자가 유지한 요구를 삭제하지
않는다. 과거 검수의 통과 판정도 이번 검수에서 다시 증명해야 한다.

## 3. 실행 계획

| 단계 | 읽기·판단 작업 | 산출물·합격 기준 |
|---|---|---|
| A | 6개 전 문서와 사용자 결정 기록을 처음부터 끝까지 읽는다. 원문 구현계획과 비교해 이전 축약 중 잃은 계약도 찾는다. | 문서별 전체 범위와 제품 의도를 기록 |
| B | 입력→검증→후보 선택→보고서→차트/상태→community의 정상·실패 시나리오를 6개 문서에 대입한다. | 동일 사용자 행동의 대상·한도·상태·후속 행동이 일치 |
| C | backend controller→service→repository/DTO, frontend route→query→adapter→component, migration·seed·compose를 읽어 현행 단정을 검증한다. | 허용 gap 목록과 새로운 사실 오류를 구별 |
| D | community를 PM/BE/FE/AI/data/infra/QA 담당자가 차례로 인계받는 상황을 검토한다. | 작업 파일·선행 입력·산출물·의존성·완료 기준·불필요 작업이 명시 |
| E | 저장소 판정표·검색/댓글 절차·LLM schema·DB payload·API wire·UI 표시를 하나의 샘플로 연결한다. | 필드 타입/nullable/집계 분모/역할/ID/오류가 끝까지 정의 |

| G | 외부 API의 pagination·rate limit·Contents·버전을 공식 근거와 대조한다. GMS 실제 계약 근거를 저장소에서 확인한다. | 모르는 계약을 확정 사실처럼 만들지 않음 |

| J | 문서 구조·내부 링크·표·예시 데이터와 Git 변경 범위를 확인하고 기존 MR 브랜치에 push한다. | 원격 SHA 일치, 실제 MR 본문 갱신 여부도 구별해 보고 |

## 4. 중점 반례

- 기준만 선택·후보 3개 노출·최대 3개 비교가 혼동되지 않는가.
- series 일부만 빈 값이거나 요청 실패할 때 정상 카드까지 사라지는가.
- npm URL이 같아도 monorepo package.json이 없거나 이름이 다를 때 서로 다른 판정을 내리는가.
- 댓글 101개/199개에서 마지막 페이지 하나를 최신 100개라고 잘못 부르는가.
- 모든 요약 실패와 GitHub 수집 실패가 같은 상태가 되어 쓸 수 있는 결과를 버리는가.
- 새 작업이 거절됐을 때 기존 진행 task를 실패로 덮어쓰는가.
- 20초 deadline이 queue 대기·DB 게시·하위 HTTP timeout까지 실제로 제한하는가.
- raw 원문 미보존으로 검증할 수 없는 의미 정확성을 자동 보장한다고 쓰는가.
- 신규 JDBC table을 Hibernate validate만으로 검증했다고 오인하는가.
- GMS endpoint/auth처럼 근거 없는 외부 계약이 있어도 개발 가능하다고 단정하는가.

## 5. 계획 자체 평가와 보완

| 위험 | 평가 후 수정 |
|---|---|
| 문서 수가 많아 키워드 검색만으로 끝남 | 전체 순차 읽기 A와 수정 후 전체 읽기 I를 필수로 고정 |
| 파트 이름만 나열하고 실제 인계가 없음 | D에서 파일·입출력·완료 증거를 함께 요구 |
| 동일 상태명을 붙여 부분 실패를 숨김 | E/F에서 수집·요약·갱신·화면 상태를 각각 판단하고 하나의 예제로 연결 |
| 원문 축약으로 구현 상세가 유실됨 | 원문 편입 `1b60139`와 직접 비교 |
| 미확정 외부 정보를 임의로 채움 | G에서 확인 가능한 값과 구현 전 외부 입력을 분리; 확인되지 않은 값은 차단 조건과 담당 역할 명시 |
| 기존 수용 gap을 불필요하게 구현 | 이번 범위는 문서 변경. 수용 gap은 보존하고 새 코드 결함은 근거와 후속 조치로 기록 |
| 과거 이력이 현재 지침을 덮어씀 | H에서 본문/부록을 분리하고 현행 계약의 참조 지점을 하나로 지정 |
| 기술 문서의 무결성을 기계 검사로 과장 | J는 보조 검증이며 의미 검수 결과와 별도로 기록 |

평가 결과: 위 보완을 반영한 계획으로 진행한다. 실환경 GMS 계약을 확보하지 못하면 해당 연결
구현의 선행 조건을 남긴다. 문서의 완성도와 외부 연결 실행 가능성을 같은 판정으로 취급하지 않는다.
