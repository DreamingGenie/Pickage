## 1. 결론

검토 당시 docs 루트 기획 문서는 2026-09-10 확정한 제품 의도를 비교적 잘 담고 있었지만, 같은 날 뒤이어 병합된 후보 API·AI 배치·Dependents 표시·요구사항 해석 파이프라인의 **현재 구현 상태**를 반영하지 못했다. 또한 코드가 문서의 확정 제품 계약과 다르게 구현된 항목도 있어, 모든 차이를 문서에 흡수하면 합의된 요구사항을 역으로 훼손할 수 있었다.

따라서 수정은 다음 세 묶음으로 분리해 처리했다.

1. **사실관계 정정**: 오래된 문서 인덱스, 후보 API/파이프라인 구현 상태, PDF의 MVP 분류 모순 등을 바로잡았다.
2. **사용자 결정 반영**: 검색 입력, 후보 UX, Dependents major 선택, 104주 상한처럼 현재 구현을 존중하기로 한 항목을 제품 계약에 반영했다.
3. **기획 계약 유지 + 구현 gap 기록**: log1p, 8일 초과 결측 단절, 계열별 축적 상태, 카드별 실패 격리, 선택 기간 delta는 요구사항을 유지하고 현재 미구현임을 명시했다.

가장 급한 코드 차단 사항인 프런트 타입 검사 실패는 기획 문구로 덮지 않고 별도 버그 `S15P21A506-308`로 기록했다. `analyze-page.tsx`가 존재하지 않는 `setError`를 호출하므로 후속 코드 수정이 필요하다.

## 4. 추가 관찰

### 4.1 적은 관측점 처리 기준은 구현과 문서가 다르다

- `frontend/src/routes/report/ecosystem/model.ts:76`은 `MIN_POINTS_FOR_LINE = 3`이다.
- `metric-chart.tsx:55-58`은 개별 series가 아니라 전체 중 최대 point 수로 축적 중 여부를 판단한다.
- 한 패키지만 1~2개 point이고 다른 패키지가 3개 이상이면 짧은 series도 선으로 그릴 수 있다.
- 문서의 “유효 point 2개 이하인 해당 계열은 축적 중”과 정확히 맞추려면 series별 판정이 필요하다.

### 4.2 현재 후보 API 데이터 상태는 공통 상태 모델의 부분집합이다

`COMPLETE|NO_DATA`는 유용한 구현 진전이지만, 문서의 `loading|partial|success|empty|error|stale`과 명칭·계층이 다르다. 배치 데이터 상태와 UI 요청 상태를 같은 필드 하나로 합칠지, 서로 다른 상태 축으로 유지할지도 개발 구상안에서 구분할 필요가 있다.

### 4.3 저장소 내 AI 안내 문서도 기준일이 오래됐다

`ai/README.md`는 제목의 기준일이 2026-09-09이고 배치 본체를 일부 미래 작업으로 기술한다. 이 파일은 docs 루트 기획 문서 수정 범위 밖이므로 이번 변경 대상에는 넣지 않되, 후속 기술 문서 정리 대상으로 남긴다.
