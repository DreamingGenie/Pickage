## 작성 규칙

1. 시작 전에 [작업 정의](01-scope.md)의 범위와 [작업 계획](02-plan.md)을 구체화한다. 사용자 요구사항과 확정한 계약을 작업 정의에 기록한다.
2. 각 단계에 `P-01`, 완료 기준에 `AC-01`, 이슈에 `ISS-001`, 작업 기록에 `W-001`, 검증에 `V-001`처럼 식별자를 붙여 서로 연결한다. 번호는 삭제된 항목에도 재사용하지 않는다.
3. **계획**, **실제 수행**, **검증 결과**를 구분한다. 계획된 명령을 실행 기록으로 쓰거나, 원문 문서의 기대값을 측정값으로 옮기지 않는다.
4. 사실에는 파일·커밋·로그·쿼리 결과 등 근거를 붙인다. 설계 제안은 `제안`, 확인하지 못한 내용은 `미확인`, 실행하지 않은 검증은 `미실행`으로 적는다.
5. 범위·계획을 바꾸면 현재 표를 갱신하고 변경 이력을 남긴다. 실패한 시도와 원래 계획도 이유를 추적할 수 있게 보존한다.
6. 실행 시각은 `YYYY-MM-DD HH:mm:ss +09:00`처럼 시간대를 포함한다. 데이터 snapshot, 공급자 관측 시각, 적재 실행 시각은 별도 필드로 기록한다.
7. `[작성 필요]`는 미작성, `없음`은 확인 결과 없음, `해당 없음 — 사유`는 적용 대상이 아님을 뜻한다. 빈칸을 성공이나 문제 없음으로 해석하지 않는다.
8. 명령·로그에서 비밀번호, 토큰, 인증정보가 포함된 연결 문자열은 제거한다. 큰 로그·데이터는 저장 위치와 실행 ID·해시를 남긴다.

다른 브랜치에서는 이 폴더를 `docs/worklogs/<티켓 키>/`로 복사하고 기본 정보·요구사항·완료 기준을 해당 작업에 맞게 바꾼다. 기존 실행 기록과 검증 결과는 가져오지 않는다.
