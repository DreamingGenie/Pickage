상태: **P-01~07 구현·전체 적재·읽기 전용 검증·동일 입력 재실행 검증 완료** · [작업 정의](01-scope.md) · [문서 안내](README.md)

단계 목록은 계획이며 실제 수행 기록은 04에 남긴다. 입력 검증과 PostgreSQL 실행 모듈을 독립적으로 구현한 뒤 CLI에서 통합한다.

| --- | --- | --- |

## 구현 결정과 검증 순서

1. **입력 고정:** snapshot과 Curated run ID를 필수로 받는다. 해당 manifest와 `_SUCCESS`를 검증하고 그 manifest의 단일 attempt 서비스 파일만 읽는다. 가변 `_current.json`은 선택 기준으로 사용하지 않는다.
2. **값 보존:** Parquet 물리 스키마를 파일별로 확인하고 값·키·참조를 DuckDB에서 검증한다. `TIMESTAMP`는 원천의 timezone 없는 마이크로초 값을 그대로 보존한다. `version.dependency`는 V1의 `NOT NULL DEFAULT` 계약을 유지하며, invalid dependency 25개는 loader COPY에서 기본 JSON으로 대체하고 품질 JSONL 및 실행 이력에 기록한다.
3. **전송:** 기존 DuckDB·boto3·stdlib와 PostgreSQL 이미지의 psql을 사용한다. 새 Python 패키지는 추가하지 않는다. PostgreSQL COPY text 형식에서 역슬래시·탭·줄바꿈을 이스케이프해 다중행 문자열과 `\\.` 종료 표식 충돌을 방지한다.
4. **실행 이력:** 승인 manifest 확인 후 PREPARING 실행·attempt를 먼저 기록한다. 입력 검증 실패와 DB 실패는 서비스 반영과 별도 트랜잭션으로 남긴다. DB 연결 전 실패는 로컬 실행 보고서에 남긴다.
5. **반영:** dataset 단위 세션 잠금, 세션별 임시 staging, 대상 테이블의 쓰기 충돌 방지, 키 대응 검사 후 package→version 순으로 반영한다. 데이터·PUBLISHED·DB 현재 입력 선택 정보를 한 트랜잭션에서 확정한다.
6. **재실행:** 실행 ID는 입력·계약 해시에 묶는다. 실패 후 재시도는 새 attempt로 남긴다. 과거에 게시한 입력 재검증은 현재 속성을 다시 쓰지 않는다. 더 오래된 snapshot은 신규 게시를 거부하고, 같은 snapshot의 새 입력은 현재 입력을 parent로 가진 경우만 허용한다.
7. **검증:** 입력 단위 테스트 → 새 격리 DB에 V1+V2 적용 → 작은 정상/NULL/문자열 경계·ID 충돌·오류 주입·재시도·동시성·과거 입력 테스트 → 승인된 전체 run 적재 → 입력과 DB 건수·표본 대조 순으로 진행한다.

독립 구현 담당: 입력 검증 executor / PostgreSQL 실행·V2 executor. 통합·실제 환경·최종 기록은 주 담당이 수행하고, 통합 뒤 독립 검토를 받는다. 기존 데이터용 compose 볼륨과 seed는 사용하지 않는다.

## 작업 순서

상태는 `미착수 / 진행 중 / 차단 / 완료 / 제외`로 기록한다. 완료에는 실제 작업 기록과 검증 근거가 필요하며, 제외에는 사유와 범위 변경 기록이 필요하다.
