## 3. 현재 사실 기준선

### 3.1 Git·DB·배포

- MR !90·!91의 결과는 이미 develop에 병합됐다. 마지막 migration은
  `V4__index_similar_package.sql`이고 `similar_package`가 존재한다.
- `community_snapshot`과 community backend/frontend 코드는 아직 없다.
- 패키지를 비우는 파일은 세 데이터 시드뿐 아니라 `seed_reset.sql`까지 총 네 개다.
  `seed_clear_snapshots.sql`은 package를 유지하므로 community 행을 지울 대상이 아니다.
- 로컬·운영 API 컨테이너의 메모리 상한은 모두 1.6 GiB이고 운영은 Swap 0이다.
- root `.env.example`, local/prod compose, `application*.yaml`에 community/GMS 설정은 없다.
- GitLab CI 파일은 없다. 검증 명령과 결과는 MR에 사람이 남겨야 한다.

### 3.2 백엔드

- Java 21, Spring Boot 4.0.8, Spring MVC, JdbcTemplate 기반이다.
- 기존 데이터 경로는 JPA Entity가 아니라 명시적 SQL·record mapper를 사용한다.
- 전역 wire JSON은 snake_case이고 성공 응답은 `success/data` wrapper다.
- `PackageController`는 `/api` 아래 여섯 조회 endpoint를 제공한다. community endpoint는 없다.
- scheduling/configuration-properties/bounded executor/external REST client는 아직 없다.

### 3.3 프론트엔드

- React 19, React Router 7, TanStack Query 5를 사용한다.
- 보고서는 `/report/:reportId`이며 ecosystem/features 두 lazy tab만 있다.
- 분석 화면은 `state.packages`만 전달한다. 기준 패키지는 배열 첫 항목이라는 암묵 계약이다.
- API client는 GET query를 지원하지만 POST query와 호출자 `AbortSignal`을 지원하지 않는다.
- 화면 후보는 현재 2개로 제한되고 `setError` 미정의 typecheck 결함이 있다. 이는 community
  구현 범위에서 몰래 고치지 않고 선행 결함으로 추적한다.

### 3.4 Jira·외부 계약

- `S15P21A506-137`은 완료 상태지만 community 코드가 없으므로 완료 상태를 구현 증거로 쓰지 않는다.
- `S15P21A506-212`, `S15P21A506-213`은 해야 할 일 상태다. 실제 구현 착수 시 담당·범위를
  확인하고 필요한 DB/API/UI 작업은 팀 규칙대로 별도 이슈에 연결한다.
- GitHub REST `2026-03-10`은 현재 지원 버전이다. issue comment endpoint는 issue별
  `per_page` 최대 100이고 ID 오름차순이다. Search와 일반 REST 한도는 별도이며 403/429에서는
  `retry-after`, `x-ratelimit-remaining`, `x-ratelimit-reset`을 구분해야 한다.

## 4. 검토·개정 작업

### A. 문서 성격과 최신성

1. 문서 머리말을 2026-09-11 검증 기준으로 바꾸고 기준 commit을 기록한다.
2. 과거 MR 병합 예정 문구를 완료 사실로 교체한다.
3. 2026-09-20 일정은 현행 정본이 아닌 보관 일정임을 명시하고 새 확정일로 오인시키지 않는다.
4. 본문에는 현재 유효 계약만 두고 부록의 과거 상충 설계는 구현 지침이 아님을 강화한다.

### B. 제품·범위 계약

1. 기준 패키지 하나만 community 분석 대상으로 삼는다.
2. 다른 후보·비교 패키지 snapshot으로 fallback하지 않는다.
3. 같은 `/report/:reportId` shell의 세 번째 확장 tab이며 별도 최상위 route/header를 만들지 않는다.
4. Issue 장기 시계열은 ecosystem Activity 확장 소유로 유지한다.
5. 저장소 식별자는 읽기 전용으로 표시한다.

### C. 저장소·Issue 수집

1. DB `repo_url`과 npm latest repository를 독립 정규화하고 최종 host를 재검사한다.
2. npm `repository.directory`와 root/directory package.json 이름으로 연결 증거와 Issue scope를
   분리한다. monorepo는 근거 없이 `PACKAGE_SCOPED`로 올리지 않는다.
3. archived는 실패가 아니라 limitation, ambiguous/unverified/unsupported는 수집 중단으로 둔다.
4. `github-active-v1`의 180일 → 결과 0건 시 365일 확장, comments/updated/number 순서,
   상위 30개 후보, 최대 Issue 2개를 고정한다.
5. PR 제외, locked/Bot issue 제외, Bot comment의 집계 포함·대표 후보 제외를 분리한다.
6. issue별 최신 댓글 최대 100개를 Link pagination으로 확인하고 시각 순으로 복원한다.

### D. 요약·정확성·보안

1. 원문별 4,000자, issue별 48,000자, 결과 2,048 token 상한과 절단 limitation을 연결한다.
2. GMS에는 원문과 source ID만 주고 역할·개수·시각·순서는 서버가 GitHub 원본에서 계산한다.
3. JSON schema, 길이, enum, source 소속, support source 실재를 게시 전 검증한다.
4. 원문·prompt·token·외부 응답 원형을 DB/API/log에 남기지 않는다.
5. prompt injection, 조건 제거, 주장 반전, 가짜 합의, 인용 혼동, 코드/로그 오독 fixture를 둔다.

### E. DB 계약과 초기화

1. 현재 기준 migration은 V5이나 착수 직전에 빈 번호를 재확인한다. 기존 V1~V4는 수정하지 않는다.
2. `community_snapshot`은 package당 한 행, 6개 컬럼으로 유지한다.
3. `result` JSON schema를 별도 typed record로 정의하고 임의 Map 수정을 금지한다.
4. 외부 작업은 transaction 밖, 게시만 짧은 transaction에서 timeout → advisory lock → upsert
   순으로 수행한다.
5. fresh 경계는 24시간 미만, stale 제공은 24시간 이상 7일 미만, 7일 이상은 만료로 고정한다.
6. `seed_sample`, `seed_mock_parity`, `seed_service_full`, `seed_reset`의 TRUNCATE 목록에
   community_snapshot을 추가하고 local README도 갱신한다. community 가짜 DB 행은 넣지 않는다.

### F. 상태와 API wire

1. 저장 상태, refresh 실행 상태, 화면 상태, 일시 실패 코드를 서로 다른 enum namespace로 둔다.
2. persistent `data_status`에는 외부 일시 장애를 저장하지 않는다. 실패는 refresh 상태에 둔다.
3. `GET /api/packages/community?name=`은 조회만, `POST .../refresh?name=&trigger=`는 명령만 한다.
4. POST 새 작업은 202, fresh/single-flight/capacity 결과는 200으로 반환할 수 있도록
   `ResponseEntity<ApiResponseBody<...>>` 계약을 명시한다.
5. 진행/최초 실패는 `result=null`, 저장 결과가 있으면 FRESH/STALE와 함께 반환한다.
6. package 미존재는 실제 전역 code `C006`으로 연결하고, 업무 실패 code와 HTTP 실패 code를 섞지 않는다.
7. DTO는 기존 전역 snake_case를 따르며 community에 중복 naming 설정을 추가하지 않는다.

### G. 백엔드 구조와 동시성

1. 기존 JdbcTemplate 관례에 맞춰 query/publish repository를 구현하고 JPA Entity 도입 지시를 제거한다.
2. community controller/service/coordinator/clients/policy/validator/payload/API DTO를 분리한다.
3. refresh worker(최대 2)와 GMS 병렬 호출 executor를 분리해 같은 pool을 기다리는 교착을 막는다.
4. 전체 refresh start 10건/분·burst 4, 실행 2, interactive queue 4를 원자적으로 관리한다.
5. 20초 단일 deadline을 모든 외부 호출에 전파하고 종료 시 5초 유예 뒤 취소한다.
6. 현재 단일 API 인스턴스에서 in-memory single-flight를 v1 한계로 허용하되, 두 번째 인스턴스
   배포 전 DB lease/분산 조정이 필요함을 gate로 둔다.

### H. 프론트엔드 연결

1. 분석 → 보고서 route state를 `{basePackage, packages}`로 명시한다. 정렬된 query key나
   임의 기본 fixture에서 기준 패키지를 역추론하지 않는다.
2. API client가 POST query와 호출자 signal을 지원하도록 하되 기존 호출을 깨지 않는다.
3. 분석 확정 POST는 화면 이동을 막지 않고 rejection을 소비하며, tab open POST는 작업 존재를 보장한다.
4. GET query는 `refresh.status`가 QUEUED/RUNNING이고 tab이 보일 때만 서버 지정 간격으로 poll한다.
5. community tab은 lazy import하고 hover prefetch는 code chunk만 가져온다.
6. 진행률을 timer로 만들지 않고 서버 stage/message·경과 시간·aria-live를 표시한다.
7. stale 결과 갱신, 부분 결과, 빈 결과, 저장소 미검증, 최초 실패를 각각 fixture로 렌더링한다.

### I. 설정·운영·관측

1. root local env, local compose, prod env example, prod compose, Spring properties의 변수명을
   양쪽 실행 환경별로 빠짐없이 연결한다.
2. 실제 secret은 어떤 tracked 파일에도 넣지 않고 backend 컨테이너에만 주입한다.
3. 운영 key 누락 시 community만 비활성화하고 core API 기동 여부를 명시적으로 시험한다.
4. refresh/package/stage/duration/cache/failure/retry/model/prompt version을 구조화 로그로 남긴다.
5. 1.6 GiB·Swap 0에서 peak heap/thread/raw input 상한과 graceful shutdown을 시험한다.

### J. 시험과 인계

1. migration 정적 검증, 빈 DB migration, 기존 V1~V4 upgrade, Hibernate validate를 분리한다.
2. pure unit test와 PostgreSQL integration test를 현재 sourceSet 규칙에 맞춘다.
3. GitHub/npm/GMS는 동결 fixture와 fake server로 정상·부분·rate limit·timeout·malformed JSON을 검증한다.
4. frontend typecheck/lint/format/build, adapter unit, 상태별 component test, mock external-call 0건을 확인한다.
5. 실제 secret을 쓰는 smoke test는 명시적 수동 job으로 격리하고 기본 MR 검증에서 호출하지 않는다.
6. Swagger·Jira·docs root와 실제 endpoint/schema/status를 같은 MR에서 대조한다.
