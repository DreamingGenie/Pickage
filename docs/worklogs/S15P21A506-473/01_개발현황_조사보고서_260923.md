# Pickage 개발 현황 조사 보고서

> Jira: `S15P21A506-473`  
> 조사일: 2026-09-23  
> 제품 코드 기준점: `origin/develop` `c88e20a`  
> 목적: 2026-09-23 완성 기준 기획 문서를 작성하기 전에 실제 병합 코드·데이터·운영 구성을 확인한다.

## 1. 조사 원칙

이번 조사는 기존 기획서의 문장을 코드에 맞추는 작업이다. 서로 충돌할 때는 다음 순서로 판단했다.

1. `origin/develop`에 병합된 실행 코드와 스키마
2. 같은 기능을 검증하는 테스트
3. 최신 운영·데이터 실행 기록과 완료된 Jira 이슈
4. README와 과거 기획 문서

브랜치에만 있는 코드는 제품 현황에서 제외했다. 운영 서버에는 접속하지 않았으므로, 저장소에 실행 기록이
있더라도 당일 서버 상태가 필요한 항목은 **운영 확인 필요**로 남겼다. Jira 상태와 코드가 다르면 둘을 함께
기록했으며, 어느 한쪽을 임의로 완료 처리하지 않았다.

### 1.1 상태 표현

| 상태 | 의미 |
| --- | --- |
| 완료 | 기준점 코드에 구현이 있고 테스트 또는 실행 근거가 있다 |
| 부분 완료 | 핵심 흐름은 있으나 범위·지속성·운영 데이터가 제한된다 |
| 미구현 | 기준점 코드에 사용자 기능이 없다 |
| 의도적 제외 | 제품 계약상 하지 않기로 정한 기능이다 |
| 운영 확인 필요 | 배포 코드·절차는 있으나 현재 서버 상태를 이 조사에서 확인하지 않았다 |
| 문서 불일치 | README·과거 기획서가 현재 코드보다 오래됐다 |

## 2. 결론

Pickage는 **npm 패키지 최대 3개를 생태계 변화, 기능 차이, GitHub 커뮤니티 근거로 비교하고 PDF와
에이전트용 Markdown으로 내보내는 서비스**로 구현돼 있다. 제품은 우승 패키지나 교체 결론을 대신
내리지 않고 관측값과 출처의 한계를 함께 제시한다.

사용자 핵심 흐름인 `패키지 입력 → 후보 선택·직접 추가 → 3개 분석 탭 → 결과 내보내기`는
`develop`에 완성돼 있다. 9월 17일 기획서 이후 교체 흐름·제거 이유·버전 후보·비교 하이라이트·PDF
확장·HAND-OFF Markdown 등이 추가됐다. 반대로 과거 문서의 Evidence Drawer, verdict 표, Redis,
pgvector, 영구 보고서 저장은 현재 제품에 없다.

완성 기준 문서에는 다음 제약을 숨기지 않아야 한다.

- 분석 대상은 npm이며 비교는 최대 3개다.
- `reportId`는 현재 `draft`이고 분석 세션 자체는 서버에 영구 저장되지 않는다.
- 기능 비교와 보고서 작업 상태는 프로세스 메모리에 있어 서버 재시작 시 사라질 수 있다.
- GitHub 커뮤니티 분석은 기준 패키지 하나에 대해 표시한다.
- dependents 절대값은 버전별 값을 합친 지표라 중복 과대 계상될 수 있다.
- 교체 흐름은 동시 변경을 관측한 값이지 인과관계나 대체 추천이 아니다.
- 확장 데이터 기반은 468,519개 대상까지 마련됐지만 일부 최신 파생 지표와 유사도 배치는 아직 같은
  범위로 맞춰지지 않았다.

## 4. 백엔드·데이터 계약

### 4.1 외부 API

`PackageController`는 패키지 개요, 다운로드, 의존 패키지, 버전, 유사 패키지, 교체 흐름, 제거 이유,
관측된 이동 경로, 검색을 제공한다. 여기에 생태계 요약, 커뮤니티 조회·갱신, 기능 비교 실행·조회,
PDF·Markdown 생성·조회·파일 API가 구현돼 있다. 응답 필드명은 snake_case이고 비교 이름은 최대
3개로 제한된다.

운영 주간 실행 조회·수동 요청 API(`/api/v1/ops/weekly/**`)도 있지만 nginx가 외부 접근을 차단하고
OpenAPI에서 숨긴 내부 운영 계약이다.

### 4.2 지표 해석

- 다운로드와 의존 패키지 추이는 주 단위 시계열이다.
- dependents는 버전별 의존 패키지 수를 합하므로 동일 소비자가 여러 버전을 쓰면 중복될 수 있다.
- 버전 점유율은 패키지 내부 백분율이다.
- 교체 흐름은 1년·3년·5년과 regular·peer·optional 범위를 제공한다. `미관측`은 `유지`가 아니다.
- 제거 이유의 단위는 패키지 수가 아니라 관측된 전환 이벤트다.
- 이동 경로의 점유율 분모는 publisher-month이며 동시 변경을 인과나 추천으로 표현하면 안 된다.
- 양방향 표시는 같은 두 패키지 사이에 반대 방향 관측도 있다는 뜻이지 같은 제품의 변종이라는 뜻이
  아니다.

### 4.3 스키마

Flyway `V1`부터 `V13`까지 적용 대상이다. 핵심 테이블은 패키지·버전·스냅샷,
`similar_package`, `community_snapshot`, `dependent_transition`, `dependent_removal_reason`,
`package_env`, `available_package`, `migration_pair`이며 ETL 회차·현재 데이터셋 메타데이터도 관리한다.
JPA는 스키마를 생성하지 않고 `validate`만 수행한다.

## 5. AI 현황

### 5.1 유사 후보

운영 모델 계약은 MLflow의 `pickage-similarity@production`이다. 현재 기록상 모델 버전 2,
`BAAI/bge-small-en-v1.5` 기반 384차원 ONNX 임베딩을 사용한다. 설명·키워드 문장을 임베딩한 뒤
의미 유사 상위 후보에 플러그인/어댑터, 같은 패밀리, 보완 관계, 보관 여부, 다운로드 하한을 적용하고
코사인 유사도로 정렬한다.

최신 기록의 29,376개 코퍼스·315개 평가쌍에서 recall@3 0.238, recall@10 0.511,
recall@30 0.740이다. 첫 운영 배치는 약 29,164개를 처리했고 최고 메모리 약 5.236 GiB를 기록해
2·4 GiB에서 실패하고 8 GiB에서 성공했다. 메모리 제한 정리는 `S15P21A506-384`가 미완료다.

확장 대상은 468,519개지만 현재 배치 기본 `max-rank`는 100,000이다. 468k 확장은
`S15P21A506-460`이 미완료이므로 “전체 468k 유사 후보 제공”으로 문서화하면 안 된다.

### 5.2 기능 비교 RAG

RAG API는 `POST /compare` 하나를 제공한다. 패키지·버전별 HAND-OFF Markdown을 읽어 메타데이터와
README 청크를 구성하고, 패키지당 문자 예산 내에서 검색한 근거를 한 번의 생성 호출로 비교한다.
출력은 `COMPLETE` 또는 `COMPARISON_LIMITED`, 공통점, 패키지별 차이 문단, 강조 구간, 소스 상태다.

비교는 증거 우선이며 불충분한 경우 제한을 표시한다. 널리 알려진 일반 사실은 “일반적으로”로
구분할 수 있지만 추천·순위는 만들지 않는다. 결과는 DB에 저장되지 않고 자동 재시도도 없다.

주간 수집기는 데이터 노드의 systemd timer가 10분마다 실행 조건을 확인하고 화요일 10:00 KST

책임지는 것은 아니다.

### 6.2 남은 범위와 확인 항목

- 468k 최근 dependents 재계산은 `S15P21A506-455` 브랜치에만 있어 기준점에서 제외한다.
- 유사도 배치 468k 확대(`S15P21A506-460`)와 일부 배치 모니터 바인드(`-456`)는 미완료다.
- registry 추가분 기반 `package_env` 확장 도구는 병합됐지만 최신 실행 문서는 로컬
  `--verify-only` 롤백까지 확인한다. 운영 468k 게시 완료는 별도 확인이 필요하다.
- 다운로드 실패 태스크 재수집(`S15P21A506-367`)은 미완료다.
- Python 파이프라인 전체를 한 번에 `pytest pipeline`으로 실행하면 중복 모듈명, 상대 import,
  로컬 PySpark 부재 때문에 collection 단계에서 실패한다. 개별 모듈 테스트는 다수 존재하지만 CI의
  `pipeline-ok`는 환경 smoke 검사만 수행한다.

## 7. 인프라·운영 현황

로컬은 PostgreSQL, API, MinIO, 단일 Spark, similarity 서비스로 구성하고 프런트는 Vite로 실행한다.
운영은 앱 노드와 데이터 노드로 나뉜다.

- 앱 노드: PostgreSQL, API, RAG API, nginx web, Spark worker 2, similarity·package-env loader
- 데이터 노드: MinIO, MLflow, Spark master·worker 1, AI 수집·배치, 주간 ingest
- 모니터링: Netdata와 pipeline monitor용 별도 compose

운영 MinIO는 콘솔 호환성을 위해 로컬보다 오래된 릴리스에 고정돼 있고 데이터는 `/srv/minio/data`
바인드에 있다. 운영 Spark는 두 호스트의 host network를 쓰며 로컬 단일 컨테이너와 다르다. nginx는
TLS 종단, SPA fallback, 내부 ops API 차단을 맡는다.

CI에는 frontend, backend 단위·통합, AI, RAG, pipeline smoke, 앱 배포, AI 이미지 빌드 job이 있다.
앱 노드 모니터링 배포 기록은 있으나 데이터 노드 모니터링은 최신 README 기준 미배포다. 현재 서버의
실제 컨테이너·타이머·데이터 적재 상태는 이번 조사에서 확인하지 않았다.

## 10. 현재 문서의 주요 불일치

- 9월 17일 기획 문서: Evidence Drawer, verdict, 확장 예정 표현이 현재 UI와 맞지 않는다.
- `ai/README.md`: 후보 2개 기본 선택, 초기 구축 단계 표현이 현재 프런트와 다르다.
- AI 모델 계약 문서: MLflow 미배포 표현이 현재 운영 모델 참조와 다르다.
- `pipeline/README.md`: 현재 존재하는 여러 파이프라인 디렉터리와 최신 확장 흐름을 모두 열거하지 않는다.
- `.gitlab-ci.yml` 머리말: 아직 없다고 적은 loader·batch 코드가 현재 존재한다.
- `deploy/prod/README.md`: CI 자동 배포, 주간 수집, 모니터링을 “아직 없음”으로 적은 구간이 최신
  구성과 충돌한다.
- 일부 데이터 README는 작성 당시 “PostgreSQL 적재 전” 상태와 후속 완료 기록이 한 문서에 공존한다.

이 불일치는 새 기획 문서에서 바로잡되 기존 운영 README 전체를 이번 기획 이슈에서 무리하게
재작성하지 않는다. README 정리는 사용자가 정한 다음 작업 단계에서 별도 근거로 처리한다.

## 11. 새 기획 문서 작성 기준

1. 현재 제공하는 사용자 행동과 화면을 먼저 적는다.
2. 수치와 상태는 기준일·단위·해석 제한을 함께 적는다.
3. 미구현 UI(Evidence Drawer 등)를 목표 기능처럼 남기지 않는다.
4. 운영 코드의 존재와 실제 운영 완료를 구분한다.
5. 468k 데이터 기반과 100k 유사도 배치 범위를 구분한다.
6. 추천·인과·품질 보증을 하지 않는 제품 원칙을 유지한다.
7. 사용자에게 중요한 제한은 별도 부록이 아니라 각 기능의 수용 기준 가까이에 둔다.
