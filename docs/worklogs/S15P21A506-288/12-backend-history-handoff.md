# 백엔드 인계: 재구성 이력 표시와 지표 비교 조건

## 상태와 문제

백엔드 구현은 후속 작업이다. 이번 적재 계약 보완에서 Java 코드나 API 응답을 변경하지 않는다.

과거 228개 기준일은 현재 승인 버전의 배포일로 패키지 대상과 저장소 연결을 재구성했다.
다운로드는 해당 기간의 실제 유효 일별 합계이며, stars·open_issues는 해당 시각의 실제 Projects 관측값이다.
지표 숫자를 추정했다는 뜻으로 `재구성값`을 표시하면 안 된다.

예를 들어 한 패키지가 이전 기준일에는 저장소 A(100 stars), 다음 기준일에는 저장소 B(500 stars)를
선택했다면 단순 차이 400을 A 또는 B의 증가량으로 표시할 수 없다.
전체 패키지 수 차이 역시 신규 패키지 증가량을 뜻하지 않는다. 최신 관측 목록에는 과거 배포일을
확인하지 못한 패키지도 포함되므로 과거 재구성 목록과 포함 기준이 다르다.

## 수정 위치와 사용할 근거

- `backend/src/main/java/com/ssafy/pickage/domain/packages/PackageQueryRepository.java`의 `last2`·`recent`:
  현재 최근 두 행의 stars·open_issues 차이를 계산하지만 선택 저장소의 동일성을 확인하지 않는다.
- 같은 파일의 `DOWNLOADS_TREND_SQL`: 현재 날짜·다운로드 값만 반환한다. 재구성 여부, COMPLETE/PARTIAL,
  실제 `[P,S)` 구간 길이를 소비자가 구분할 수 있는 응답 계약을 결정해야 한다.
- `etl_load_execution.input_metadata.history_policy.history_kind`:
  과거 경로는 `RECONSTRUCTED_FROM_CURRENT_APPROVED_VERSIONS`다.
  필드가 없다는 이유만으로 아무 실행이나 관측 경로로 간주하지 말고 승인된 생산자·manifest 형식을 확인한다.
- `etl_load_execution.input_metadata`의 승인 quality 파일 참조: 저장소 선택 URL·버전·관측 시각과
  다운로드 품질을 추적할 수 있다. 공통 형식은 [quality 계약](13-quality-schema.md)을 따른다.
  실행 메타데이터는 날짜 전체의 재구성 여부이며, 개별 패키지의 저장소 동일성을 단독으로 증명하지 못한다.

## 후속 구현에서 지켜야 할 조건

1. API에서 패키지 대상·연결이 관측 기반인지 재구성 기반인지 알 수 있게 한다.
   컬럼·뷰·응답 DTO 중 구체적인 구현 방식은 백엔드 담당자가 선택한다.
2. stars·open_issues 증감은 같은 저장소를 비교한다는 근거가 있을 때만 게시한다.
   확인할 수 없거나 저장소가 바뀌었다면 증가량을 만들지 않고 비교 불가 사유를 전달한다.
3. 다운로드 PARTIAL은 유효한 날짜의 부분합임을 표시한다. 실제 0과 미관측 NULL을 구분하고,
   기간 길이가 다른 합계를 일평균 또는 동일 기간 지표처럼 표현하지 않는다.
4. 날짜 메타데이터나 저장소 연결 정보를 서비스 조회에 공급할 경로를 설계한다.
   요청마다 거대한 quality Parquet 전체를 읽는 방식은 피하고 필요한 정보의 조회·적재 방식을 정한다.

## 확인 예시와 완료 조건

- 같은 저장소의 100 → 130 stars: 근거가 확인되면 +30.
- 다른 저장소의 100 → 500 stars: +400을 노출하지 않고 저장소 변경 또는 비교 불가를 표시.
- 연결 근거가 없는 두 행: 확인 불가 상태를 전달하고 임의로 동일 저장소라고 가정하지 않음.
- COMPLETE·PARTIAL·UNAVAILABLE 다운로드: 합계·부분합·NULL과 사유가 API에서 구분됨.
- 최신 관측일과 과거 재구성일이 섞인 응답: 각 날짜의 목록·연결 기준을 소비자가 확인 가능.

데이터는 로컬 `pickage-267-validation` 컨테이너의 `pickage_267_full_defaulted` 검증 DB에 있다.
앱 DB·운영 서버 적용 및 실제 API 동작 검증은 아직 수행하지 않았다.
