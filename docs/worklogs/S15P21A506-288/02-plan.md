## 실행 순서와 대상

통합 코드의 입력 변환과 DB 전송 구현은 P-03에서 인터페이스를 고정한 뒤 분담할 수 있다.
실제 Curated 게시와 DB 적재는 검증된 입력·구현에 대해 순서대로 수행한다.

초도 로컬 DB 대상 후보는 선행 작업에서 사용한 `pickage-267-validation` 컨테이너의
`pickage_267_full_defaulted`다. 이번에는 DB에 접속하지 않았다. P-02에서 대상·접속 방식·적용
migration·package/snapshot 실행 이력·기존 지표·활성 쓰기를 확인하고 실제 대상을 기록한다.
테스트는 먼저 별도 격리 DB에서 수행하며 기존 전체 적재 DB를 시험 데이터로 초기화하지 않는다.

## 필수 검증 사례

- COMPLETE·PARTIAL·UNAVAILABLE 다운로드, 실제 0, 지표별 NULL의 독립 보존.
- 저장소 미매핑·정확한 시각의 관측 없음·유효 관측, 선택된 지표가 원본 NULL인 경우의 근거 보존.
- 패키지/기준일 불일치, 중복 ID, 누락 행, 알 수 없는 ID, 음수·정수 범위 초과, 파일 손상·해시 불일치 거부.
- 한 입력의 `_SUCCESS` 누락 또는 manifest 변경 시 적재 거부, 전체 시도 경로를 glob하여 중복 소비하지 않음.
- staging 완료 전·서비스 반영 중·게시 상태 확정 전 실패 시 롤백, 기존 성공한 Curated는 보존.
- 동일 실행·같은 입력의 DB 값 재검증, 같은 실행 ID의 다른 입력 거부, 같은 기준일의 상충 입력 보호.
- 병행 writer 차단과 기존 package/version·snapshot·다른 기준일 지표 및 실행 기록 보존.

실제 전체 적재에서는 값·NULL 건수·복합키 집합·품질 요약을 독립 SQL로 대조한다.
대표 패키지 조회만으로 전수 검증을 대신하지 않는다. 테스트 skip은 통과와 따로 보고한다.
백엔드 애플리케이션 기동·운영 서버 검증은 별도 범위로 남긴다.
