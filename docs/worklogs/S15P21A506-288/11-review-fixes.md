# 적재 재검증·품질 파일 계약 보완

## 변경 범위와 작업 계획

2026-09-10 사용자 승인 범위는 다음 두 코드 수정과 백엔드 인계 메모다.
리뷰 원문 번호와 사용자에게 설명한 번호를 혼동하지 않도록 수정 대상을 이름으로 기록한다.

| 대상 | 진행할 작업 | 완료 기준 |
| --- | --- | --- |
| 적재 계약 해시와 재검증 (리뷰 8) | 무관한 마이그레이션을 계약 해시에서 제외하고 기존 게시 실행의 재검증을 지원한다 | 기존 게시 해시·실패 이력 보존, 변경된 입력 차단, 호환 가능한 재검증 회귀 테스트 통과 |
| quality 공통 형식 (리뷰 2) | 관측·과거 산출물의 공통 컬럼·자료형을 맞추고 로더가 공통 계약으로 검증하게 한다 | 두 생산자의 공통 스키마 일치, 잘못된 상태·컬럼 차단, 기존 승인 파일 재검증 호환 확인 |

기존 산출물은 승인 SHA로 고정된 파일이다. 과거 파일이나 이미 게시한 DB 행을 덮어쓰지 않는다.
새 형식과 기존 형식을 명시적으로 구분하고, 기존 파일을 읽어야 할 때는 검증 후 DuckDB의 읽기 형식만 맞춘다.

작업 순서는 기존 동작 회귀 확인 → 두 수정 구현 → 격리된 샘플·DB 테스트 → 변경 검토·결과 기록이다.
백엔드 Java/API, 서비스 DDL·인덱스, Spark 환경, 전체 기간 완료 검사와 저장소 매칭 규칙은 이번 코드 수정 범위에 포함하지 않는다.
실제 229개 기준일 재적재, 기존 검증 DB 갱신, 운영 배포와 커밋은 실행하지 않는다.

Jira 연결 기준은 기존 S15P21A506-288이다. 현재 세션에서 Jira 도구가 제공되지 않아 원격 검색·댓글·상태 변경은 미실행이다.

## 확인된 이슈와 해결 방법

- 관측 로더는 모든 `V*.sql`을 해시해 무관한 V4 추가만으로 기존 실행과 계약이 달라진다.
  게시 당시 계약은 보존하고, 현재 검증 계약은 개별 attempt에 남기는 기존 스냅샷 로더 방식을 확인한다.
- 관측·과거 quality 파일은 동일 역할 아래 다른 컬럼을 사용한다. 서비스 값과 품질 의미를 유지하면서
  공통 계약을 도입하고, 기존 파일의 출처·형식을 검증하는 호환 경로를 둔다.

## 실제 수행 작업과 검증 결과

2026-09-10 구현·격리 검증 완료. 후속 사용자 요청에 따라 관련 코드·테스트·문서를 하나의 커밋으로 정리한다.

1. 적재 코드 해시에서 전체 migration glob을 제거하고 직접 의존하는 V1~V3만 명시했다.
   PUBLISHED인 동일 입력은 새 검증 코드로 재검증하되 최초 게시 해시·건수는 보존한다.
   새 해시는 attempt에 기록한다. 다른 입력·정책, 게시 전 실행의 계약 변경은 계속 거부한다.
2. 현재 DB의 핵심 서비스 컬럼 자료형·NULL 허용 여부를 잠금 안에서 확인한다.
   새 코드 해시를 허용하더라도 호환되지 않는 서비스 스키마나 실제 값의 변경은 통과하지 못한다.
3. 관측·과거 생산자를 동일한 `package-snapshot-quality-v2` 30개 컬럼으로 맞췄다.
   기존 파일은 정확한 이전 스키마를 검사한 뒤 공통 컬럼으로 읽는다. 다운로드 부분합·0·NULL,
   독립적인 star·issue NULL 및 저장소 매핑 상태를 공통 검사 함수에서 확인한다.
   관측 경로에 재구성 배포일이 채워진 파일도 거부한다.
4. 정상 history 재실행 진입점에서도 기존 승인 파일의 읽기 호환 처리를 사용할 수 있게 연결했다.
   기존 파일 재검증에는 버전 상태 재생성이 필요 없고, 새 날짜 생성에만 코드별 캐시를 준비한다.
5. 백엔드 수정 위치·데이터 의미·같은 저장소 비교 조건과 테스트 예시를
   [인계 메모](12-backend-history-handoff.md)에 남겼다. Java/API 코드는 변경하지 않았다.
