# 생성 코드 확인과 검증 증거 해시 보완

## 변경 범위

- 연결 이슈: S15P21A506-288. 이번 범위는 후속 리뷰 A·B다.
- A: 저장된 과거 산출물을 재사용할 때 생성 코드가 같은지 확인한다. 생성 계약과
  검증 계약을 분리해, 검증 코드만 바뀌면 현재 검사로 재검증할 수 있게 한다.
- B: 이전 검증 기록의 소스 해시를 Git에 저장되는 LF 줄바꿈 기준으로 바로잡고,
  대상 소스 버전과 계산 방식을 명시한다.
- 이번에는 집계 SQL·서비스 DDL·백엔드·기존 PostgreSQL/MinIO 데이터는 변경하지 않는다.
  리뷰 C의 항목들은 이번 승인 범위에 포함하지 않는다.

## 작업 계획

1. 생성 결과에 영향을 주는 정책·입력·생성 SQL·품질 컬럼 투영과 검사 코드를 분리한다.
2. 새 manifest에 생성 계약 해시를 기록하고 저장된 산출물과 현재 생성 계약을 비교한다.
   다르거나 생성 계약을 확인할 수 없는 기존 manifest는 자동 재사용을 중단한다.
   기존 파일에 현재 해시를 임의로 붙여 넣지 않는다.
3. 상태 캐시도 생성 계약으로 구분한다. DB 재검증에는 현재 검증 계약을 전달하고
   원래 manifest와 최초 게시 계약은 보존한다.
4. 생성 코드 변경 차단·검증 코드 변경 허용·기존 형식 거부·입력/정책 보존을 테스트한다.
5. 이전 77개 테스트 기록은 당시 소스 커밋에 연결해 보존한다. 이번 변경의 테스트와
   최종 소스 해시는 별도 증거로 남긴다.

## 검증 계획과 실행 경계

- 작은 Parquet fixture로 정상 재개와 잘못된 재사용 차단을 검증한다.
- DB 검증은 별도 임시 데이터베이스에서 수행한다. 646,219,939행이 있는 적재 DB는
  재적재·전수 재검증하지 않는다.
- 줄바꿈이 LF·CRLF·혼합인 경우의 동일 해시와 실제 내용 변경 시 다른 해시를 검증한다.
- 원격 Jira 변경 도구가 없어 Jira 상태/코멘트 변경은 수행하지 않는다.

## 실제 진행 내용과 결과

### A. 생성 계약과 검증 계약

`history_contract.py`에서 두 해시를 따로 계산한다.

| 저장 위치 | 의미 | 재개 시 처리 |
| --- | --- | --- |
| manifest `build_contract_sha256` | 입력 선택·정책·집계 SQL·품질 컬럼 투영·호출 흐름 및 DuckDB 버전 | 현재 생성 계약과 일치해야 함 |
| 새 manifest `contract_sha256` | 파일을 처음 만들 때 사용한 검증 계약 | 원래 값을 보존함 |
| DB 최초 실행 `contract_sha256` | 처음 게시할 때 사용한 적재 검증 계약 | 기존 보존 규칙 유지 |
| `etl_load_attempt.validation_contract_sha256` | 이번 DB 검사에 사용한 검증 계약 | 각 시도에 현재 해시 기록 |
| 상태 캐시 `build_contract_sha256` | 버전·대표 저장소 상태를 생성한 계약 | 입력과 생성 계약이 모두 같을 때만 재사용 |

이전 manifest의 `contract_sha256`는 생성·검증 코드가 합쳐진 해시였으므로 위 새 형식의
생성 해시로 바꿔 해석하지 않는다. 새 결과 보고서에는 생성·검증 해시를 각각 명시한다.

품질 컬럼과 생성 투영을 `quality_schema.py`로 옮기고 기존 SQL·컬럼·자료형은 보존했다.
`quality.py`에는 읽기 어댑터와 값 검사를 남겼다. 따라서 검사 함수만 바뀌면 파일을 다시
만들 필요가 없지만, 집계 SQL이나 품질 투영이 바뀌면 저장된 파일을 재사용할 수 없다.
생성 인자를 바꿀 수 있는 `history.py`와 원천 선택 코드는 보수적으로 생성 계약에 포함한다.
검증 전용 모듈 변경 허용을 위해 계약 계산 모듈 자체를 통째로 해시하지는 않는다.
대신 각 계약의 버전 식별자와 순서가 고정된 파일 경로·내용을 해시에 포함한다.
해시 조합 방식이나 줄바꿈 정규화 규칙을 바꿀 때는 해당 계약의 `format` 버전을 올린다.

선택된 날짜의 저장된 manifest를 모두 먼저 확인하므로 생성 계약 오류가 있으면
큰 DB의 날짜별 조회나 MinIO 객체 게시 전에 중단한다. 파일 SHA·입력·정책·날짜·경로 검사와
실제 Parquet/COPY 검증은 유지한다.

### 기존 산출물과 재개 시 주의점

- 기존 manifest에 생성 해시가 없으면 새 `history` 진입점은 재개를 거부한다.
  17컬럼 이전 형식뿐 아니라 이번 필드 도입 전 만들어진 30컬럼 형식도 해당한다.
- 임의의 64자리 해시를 신뢰하거나, 현재 해시를 기존 manifest에 덧붙이는 예외는 두지 않았다.
  과거 통합 해시만으로는 현재 생성 코드와의 일치를 입증할 수 없다.
- 기존 데이터 조회와 이전 quality 읽기 어댑터는 유지한다. 이번에는 과거 생성 코드의
  증명 자료를 등록하는 별도 호환 기능을 만들거나, 기존 데이터를 재생성·재적재하지 않았다.
- 생성 코드가 달라 다시 생성할 때는 기존 run을 보존하고 새 run ID를 사용한다.
  새 run이라고 기존 DB의 다른 값 덮어쓰기를 허용하지는 않는다.

### B. 검증 증거의 소스 해시

이전 기록은 워킹 트리의 원시 바이트를 해시했다. 당시 확인에서 16개 모두 워킹 트리 해시와
일치했지만, Git blob과는 12개가 달랐다. CRLF를 LF로 정규화하면 16개 모두 Git blob과 일치했다.
따라서 코드가 검증 후 변경됐다는 근거가 아니라 줄바꿈 기준 차이였다.

기존 [77개 테스트 기록](evidence/review-fixes-validation.json)은 당시 커밋
`a8c25ec744ec9039a60a7c63e9735530acc232c1`에 연결했다. 테스트 수·시간·실행 범위는 그대로
보존하고, 소스 해시만 해당 커밋의 UTF-8 텍스트를 LF로 정규화한 SHA-256으로 보정했다.
이번 수정의 증거는 별도 파일에 남긴다. Parquet·manifest 등 데이터 파일의 SHA 계산은
기존처럼 원시 바이트 기준이며 이번 소스 해시 도구의 정규화를 적용하지 않는다.

재확인 명령(저장소 루트):

```powershell
.venv-bq/Scripts/python.exe -B scripts/source_evidence.py --verify docs/worklogs/S15P21A506-288/evidence/review-fixes-validation.json
.venv-bq/Scripts/python.exe -B scripts/source_evidence.py --verify docs/worklogs/S15P21A506-288/evidence/build-contract-validation.json --worktree
```

첫 명령은 당시 커밋을, 둘째 명령은 이번 검증 기록과 현재 파일을 비교한다.
커밋 준비 시 둘째 명령의 `--worktree`를 `--index`로 바꾸면 스테이징된 코드와도 비교할 수 있다.
해시 기준이 없거나 다르거나, 파일이 누락되거나, 내용 해시가 다르면 실패로 종료한다.
