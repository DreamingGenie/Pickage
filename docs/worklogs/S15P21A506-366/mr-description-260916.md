## 개요

npm registry 수집기가 버전마다 남기는 열에 **패키지 형태 6열**을 추가한다 — `unpacked_size`·`file_count`(설치 크기), `module_type`·`main`·`types`·`exports`(모듈 형태·진입점·타입 제공).

`collect.py`는 원본 문서를 보존하지 않아 이미 받은 2,143만 행에 열을 덧붙일 수 없으므로 상위 10만 패키지를 다시 받아야 한다. 직렬 재수집은 17.9시간(09-09 실측)이라 **대상을 4등분해 프로세스 4개로 돌리는 경로**를 같이 넣었다.

**재수집은 이미 돌고 있다**(2026-09-16 회차). 아래 숫자 상당수는 추정이 아니라 그 회차의 실제 행에서 잰 것이다.

커밋 5개다. 첫 커밋이 기능이고, 나머지는 자체 리뷰 3회에서 나온 결함 10건을 고친 것이다.

## 작업 상세 내용

### 1. 형태 6열 (`collect.py`, `to_parquet.py`)

존재율을 두 가지로 적는다. **표본**은 착수 전 패키지 20개(2,787 버전)를 받아 잰 것이고 오래된 대형 패키지에 치우쳐 있다. **수집**은 2026-09-16 회차의 실제 행(진행 35% 시점, 98,715 행)이며 순위 높은 쪽부터 받아 최신·활발한 패키지에 치우쳐 있다. **최종값은 두 값 사이로 내려온다.**

| 열 | 원문 위치 | 표본 | 수집(35%) | 결정·주의 |
| --- | --- | --- | --- | --- |
| `unpacked_size` | `versions[v].dist.unpackedSize` | 78.8% | 96.5% | top level이 아니라 **`dist` 안**이다 |
| `file_count` | `versions[v].dist.fileCount` | 78.8% | 96.5% | 위와 붙어 다닌다 |
| `module_type` | `versions[v].type` | 7.0% | 30.4% | `type`은 열 이름으로 너무 일반적이라 `module_type` |
| `main` | `versions[v].main` | 51.8% | 79.8% | 원문 문자열. 없다고 진입점이 없는 게 아니다 |
| `types` | `versions[v].types`, 없으면 `typings` | 56.2% | 69.5% | `types`만 보면 과소 계상(`ajv`는 `typings`만 127버전) |
| `exports` | `versions[v].exports` | 29.2% | 42.0% | 중첩 객체라 **JSON 문자열**로 저장 |

**2018년 절벽이 실측으로 확인됐다.** 98,715 행 기준 `unpacked_size` 존재율을 발행 연도로 끊으면 — 2013~2017년 **0.0%**(한 건도 없다) → 2018년 **92.9%** → 2019년 이후 **100%**. npm이 2018년부터 계산하기 시작해서다. **결측은 "작다"가 아니라 "모른다"이고, 무작위가 아니라 연도로 갈린다.** 크기를 시계열로 보려는 쪽(S15P21A506-128)이 놓치면 안 되는 사실이라 README 열 계약에 연도별 수치를 넣었다.

**`exports`는 아주 클 수 있다.** 표본에서는 중앙값 184 B·p95 535 B였는데 실제 수집에서 한 버전이 **2.6 MB**였다. 이 열을 그대로 프런트로 내보내면 안 된다는 경고를 README에 달았다.

그 밖의 결정:

- **`license`는 받지 않는다.** deps.dev `PackageVersions.Licenses`로 이미 보유 중이다. registry 행 2,143만 중 2,039만(95.1%)이 매칭되고 1,893만(88.3%)에 값이 있으며, 거기 값은 SPDX 배열로 **정규화까지 끝나 있다**. registry 원문은 문자열 95.5%·객체 2.0%·구형 `licenses` 배열 0.5%가 섞여 있어 `deprecated`처럼 손으로 맞춰야 한다. 조인이 싸고 정확하다.
- **`has_main`·`has_types` 불리언 대신 원문 문자열을 남겼다.** 불리언은 되돌릴 수 없고 쿼리에서 만들 수 있다.
- unpublish된 버전은 선언을 모르므로 의존 네 열과 같이 6열도 전부 NULL이다.
- 정수가 아니거나 BIGINT를 넘는 크기 값은 그 행만 NULL로 둔다. 4.5시간 수집 뒤의 30분짜리 변환이 이상치 한 줄에 통째로 실패하는 것보다 낫다.

### 2. 4분할 수집 (`shard_targets.py`, `start_registry_sharded.cmd`, `status.py`)

- 17.9시간을 쓰는 것은 전송이 아니라 우리가 건 0.5초 간격이다(패키지당 0.643초, 문서 왕복은 0.14초). 간격만 낮춰도 왕복 지연(중앙값 0.32초)에 묶여 10시간 밑으로 안 내려간다.
- **사전 실측**(순위를 섞은 1,000건, 동시 4, 100초 지속): 초당 9.99건 · 429 **0건** · 10만 건 환산 2.78시간.
- **실물 확인**: 지금 도는 회차가 35% 시점까지 **실패 0 · 429 0 · 5xx 0 · 연결오류 0**, 완료 예상 약 4시간. 샤드 넷이 거의 같은 속도로 간다.
- **수집기에 동시성을 넣지 않았다.** `Writer`의 gzip 핸들, `flush()→commit()` 순서로 막고 있는 고아 행, 공유 상태인 `consec429`와 적응형 `interval`이 전부 직렬 전제라, 자체 리뷰에서 잡았던 함정(잘린 gzip·체크포인트와 행 불일치)을 다시 여는 수정이 된다. 샤드마다 자기 run 폴더·체크포인트·Writer를 갖게 하면 충돌 지점이 없고 수집기 코드는 그대로다.
- `shard_targets.py`는 **순위로 돌아가며** 나눈다. 앞에서부터 25,000개씩 끊으면 상위권 샤드는 문서가 크고(react 6.8MB) 하위권 샤드는 CDN이 차가워(지연 중앙값 0.18초 대 0.60초) 같이 끝나지 않는다.
- 이름 중복은 상위 순위만 남긴다. 상위 10만 CSV에 중복이 4건 있고(`@capgo/capacitor-mqtt` 61000·61001 등), 직렬 수집은 체크포인트의 `INSERT OR IGNORE`가 합쳐 왔지만(작업 99,996건) 나눠 돌리면 두 샤드가 같은 패키지를 따로 받는다.
- 런처의 실행 중 검사는 **샤드별**이다. 하나만 죽었을 때 다시 더블클릭하면 죽은 것만 이어서 띄운다. 이 RUN의 샤드가 아닌 수집기(직렬 `start_registry.cmd` 등)가 돌고 있으면 아무것도 띄우지 않는다.
- `status.py --shards N`으로 샤드를 합산해 전체 진행률과 완료 예상 시각을 낸다. **남은 시간은 샤드들의 합이 아니라 가장 늦는 샤드의 시간이다.**

## 데이터·파이프라인 영향 (해당 시)

- 스키마/테이블 변경 : `registry_versions` Parquet에 6열 추가(`unpacked_size`·`file_count` BIGINT, 나머지 넷 VARCHAR). DB 마이그레이션은 없다. 6열이 없던 09-09 raw도 그대로 읽힌다(없는 키는 NULL).
- 기존 적재 데이터 재처리(backfill) 필요 여부 : **있다. 상위 10만 패키지 전량 재수집**(약 4시간, 전송 약 73GB). 원본 문서를 보존하지 않아 다른 방법이 없다. **현재 진행 중**이다.
- 용량(실측) : 실제 행 60,000개에서 6열만 떼어 재면 한 줄당 **평균 +315 B**(중앙값 135 B, p95 1,265 B) → 2,143만 행 환산 비압축 **+6.74 GB**. 압축 뒤에는 행당 35.7 B → **45.4 B**(+27%)라 `jsonl.gz`가 765 MB → **약 960 MB**가 된다. 착수 전 추정(+241 B·5.2 GB)보다 크다.
- 외부 API 호출량·키 사용 변화 : registry 요청 10만 건(직렬 재수집과 같은 수). 인증 없음. 동시 요청 수가 1→4로 늘어 초당 약 8건이 된다. 사전 실측과 실물 모두 429 0건이고, 429가 보이면 `INTERVAL`을 늘리면 된다.
- 배치 주기·실행 시간 변화 : 1회성. 주간 갱신(S15P21A506-273)은 이 MR에 포함되지 않는다.

- **본 수집 35% 시점 중간 결과**: 실패 0 · 429 0 · 5xx 0 · 연결오류 0 · `odd_time_keys` 1. 6열 채움률은 위 표와 같다.

## 알려진 한계

고치지 않고 두는 것들이다. 리뷰에서 "그래도 고치자"가 나오면 반영하겠다.

- **런처를 8초 안에 두 번 더블클릭하면** 두 인스턴스가 모두 검사를 통과해 샤드가 겹쳐 뜰 수 있다. 검사와 `start` 사이의 경쟁 구간이다. 기존 직렬 런처도 같았다.
- `status_watch_sharded.cmd`의 `RUN`·`SHARDS`가 런처와 **이중 관리**다. 주석으로만 묶여 있어, 한쪽만 고치면 현황 창이 엉뚱한 샤드 집합을 본다.
- `SHARDS`를 바꾸려면 `RUN`도 새 이름으로 잡아야 한다(받아 둔 것을 버린다는 뜻). 코드로 막지 않고 주석·README로만 막았다.
- 4개 동시 실행의 메모리: 문서가 100MB를 넘는 패키지가 10만 중 5개, 50MB 초과가 41개다. 이 PC는 RAM 63.5GB라 문제 없지만, 더 작은 기계에서 `SHARDS`를 늘리면 근거가 달라진다.
- README의 존재율은 **수집 35% 시점** 값이다. 완료 후 최종값으로 갱신해야 한다.

## 리뷰 요청 사항

1. **`module_type` 이름.** 원문 필드명은 `type`인데 열 이름으로 너무 일반적이라 바꿨다. 원문 이름을 지키는 게 나으면 말씀해 주세요 — 이미 받은 raw를 버리지 않고 `to_parquet`에서 열 이름만 바꾸면 되므로 **재수집은 필요 없습니다.**
2. **`to_parquet.py`의 다중 `--raw` 지원**이 기존 단일 run 경로의 거동을 바꾸지 않는지. 09-09 raw로 변환해 확인했지만 한 번 더 봐 주시면 좋겠습니다.
3. **`status.py --parquet-force`가 가드를 약하게 만드는지.** 이제 이 플래그는 "이전 run의 결과 폴더를 이번 run 것으로 갈아탈 때"만 필요합니다. 명시적 플래그로 두는 게 맞는지, 아니면 `--parquet-out`을 새 폴더로 두게 강제하는 쪽이 나은지.
4. `unpacked_size`의 2018년 절벽을 README 열 계약에 연도별 수치까지 적어 뒀는데, 쓰는 쪽(S15P21A506-128 공통 환경·설치조건 추출)에서 놓치지 않을 만큼 눈에 띄는지.
