## 실행 순서와 병렬 범위

1. P-01에서 본 실행과 파일 역할을 고정하고, 768개 선택 파일과 742개 제외 파일을 기록한다.
2. 고정된 목록을 기준으로 P-02의 전체 행 검증과 P-03의 생성 코드·표본 조사를 병렬로 수행한다.
   P-03의 실제 생성 버전은 확인되지 않았으므로 manifest에 미확인 상태를 남긴다.
3. P-04에서 다운로드 입력 전용 manifest와 불변 Bronze 경계를 구현한다.
4. 작은 fixture와 test prefix로 P-05의 실패·재실행·동시성·물리 스키마·READY coverage 검사를 끝낸 후 P-06의 실제 입고를 수행한다.
   테스트용 객체는 별도 prefix로 한정하고 기존 완료 run과 공유하지 않는다.
5. 모든 선택 파일의 업로드·재조회 검증이 끝난 뒤 완료 표시를 게시한다.
   파일 일부가 올라간 상태와 후속 처리에 사용할 수 있는 완료 run을 구분한다.
6. 후속 단계는 명시한 run의 manifest에 적힌 파일만 소비한다. 실패·진행 중 실행을 함께 읽지 않는다.

## 구현 전에 정할 세부 계약

- **파일 종류별 검증**: CSV·압축 JSONL·Parquet·JSON 메타데이터에 적용할 행 수·기간의 의미를 각각 정한다.
  적용할 수 없는 통계는 사유를 남기며 0으로 위장하지 않는다.
- **입력 변경 감지**: 파일 목록·크기·해시가 고정 입력과 달라지면 같은 실행의 입력으로 처리하지 않는다.
- **실행 식별자**: 원천 수집 run과 새 Bronze 입고 run을 별도 필드로 기록한다. prefix와 manifest 형식은 기존 deps.dev 입력과 충돌하지 않게 정한다.
- **재실행**: 기존 완료 run은 내용과 검증 기록의 동일성을 확인한 뒤 재사용한다.
  다른 입력에는 새 실행 ID를 사용하며 이미 완료된 객체를 덮어쓰지 않는다.
- **미확인 계보**: 원본 보존·파일 동일성 검증과 변환 규칙 재현의 확인 수준을 나누어 기록한다.
  생성 코드가 없다는 사실을 추정 코드나 원본 API 재호출로 감추지 않는다.
- **회귀 범위**: 기존 MinIO 공통 코드를 수정할 경우 deps.dev 입고 테스트를 포함한다.
  이 작업만을 위해 새 의존성을 추가하거나 기존 완료 데이터의 형식을 바꾸지 않는다.

기존 [MinIO 입고기](../../../pipeline/minio/ingest_raw.py)는 다운로드 데이터를 직접 선택하지 않는다.
접속·해시·불변 업로드 동작만 재사용하고, 다운로드 입력 선택·manifest·계보 처리는
`pipeline/downloads`에 별도 구현했다. 실행 예시는 [다운로드 모듈 README](../../../pipeline/downloads/README.md)에
기록된 실제 진입점을 따른다. 전체 입력의 입고 run은 `downloads-278-20260909-v1`로 시작했으며,
완료 표시와 전체 원격 재조회 결과는 [05 결과](05-results.md)와
[Bronze receipt](evidence/bronze-load.json)에 기록한다.
