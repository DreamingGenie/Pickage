# 28. CPU 준비·GPU 계산·CPU 집계 중첩 계획과 작업 기록

## 승인 범위와 완료 기준

2026-09-11 사용자가 다음 작업의 계획과 실행을 승인했다. 기준 커밋은 `9825696`이다.
P4의 새 실행 경로와 작은 데이터 장애 검증, 실제 32개 target×229일의 정확성·성능 비교까지 수행한다.
전체 선정 99,996개 계산, EC2, DB 적재, Jira, commit·push는 이번 범위에 포함하지 않는다.

- 전체 source·선정 target·dependencies·NULL 배포일 제외·PARTIAL·ready_for_load=false를 유지한다.
- 기존 입력·CPU/GPU resolver·CPU 병렬 writer의 생성 코드와 과거 산출물은 변경하지 않는다.
- 모든 lookup 구간·count·품질을 기존 CPU 결과와 비교한다. 누락·중복·다른 attempt 응답은 거부한다.
- GPU 실패를 CPU 성공으로 전환하지 않는다. 승인된 partition만 재개 시 재사용한다.
- 같은 32개 표본과 CPU/메모리 예산에서 전체 시간을 비교하고, 전체 패키지 ETA로 환산하지 않는다.

## 구체적 계획

1. **패키지 자료 재사용:** 새로운 begin/batch/end 정규화 adapter로 후보 정렬·rank/birth를 패키지마다
   한 번 준비한다. 기존 npm 정책과 batch framing 검사는 동등성 테스트로 유지한다.
2. **GPU 전담 프로세스:** CUDA 초기화와 후보 tensor는 한 프로세스가 소유한다. 작업자마다 별도 local IPC
   연결을 사용하고 run/epoch/attempt/package/batch를 구분한다. CPU는 정규화·결과 변환·집계를 담당한다.
3. **제한된 대기량:** 작업자당 한 요청만 대기하도록 해 요청 수를 worker 수 이하로 제한한다.
   송수신 frame 크기와 후보 cache, 계산 workspace를 제한한다. 느린 소비자가 있으면 요청자가 기다린다.
4. **종료·재개:** 전담 GPU와 CPU/Node 모두 coordinator의 Windows Job에 포함한다. GPU 장애·통신 만료는
   현재 실행을 실패시키고 미완료 묶음은 새 실행에서 재개한다. 완료 pointer가 승인하지 않은 응답은 사용하지 않는다.
5. **정확성/속도:** 합성 CPU/GPU parity·범위/응답 식별·queue 한도·종료/재개를 먼저 검증한다.
   실제 32개를 GPU owner 1+CPU worker 1/2/4로 비교하고, 유리한 구성을 현재 CPU 4 worker와 교대 반복한다.
   시작 비용·대기/전송·계산·집계·저장·검증 시간을 분리한다. 10% 개선 기준에 못 미치면 기본 방식으로 채택하지 않는다.

## 범위상 구분

공통 입력 준비는 기존 `data/vd-q-input`의 검증된 파일을 재사용한다. P4는 준비가 끝난 이후의 작업을 겹친다.
기존 P3의 준비 72.205초를 P4가 줄였다고 주장하지 않는다. 실제 실행 비교에는 동일 입력 재사용 조건을 적용한다.
한 GPU 프로세스가 여러 CPU 작업자의 요청을 순서대로 계산하므로 GPU를 여러 개 사용하는 방식은 아니다.

## 실제 진행

- 기준 커밋과 작업 트리를 확인했다. 관련 tracked 변경은 없고 기존 개인 파일은 작업 범위 밖이다.
- 기존 알고리즘/저장 계약을 보존하기 위해 새 GPU 전용 adapter와 조정 모듈을 추가하는 방향으로 설계한다.
- 기존 CPU/GPU 수치 함수, 입력·receipt·재개·Windows 프로세스 종료 경계를 확인했다.
- 병렬 실행 재사용 경계 검토와 GPU 후보 cache 구현을 독립적으로 분담했다. 측정 결과와 장애 검증은 완료 후 추가한다.

## 구현 경계와 초기 검증

- 새 `historical_gpu_parallel` 실행기와 CPU worker, GPU owner, 후보 cache, stateful Node adapter를 추가했다.
- IPC는 인증된 Windows named pipe를 사용한다. 구현 근거는 [Python multiprocessing Listener/Client 문서](https://docs.python.org/3/library/multiprocessing.html#listeners-and-clients)다.
  인증키는 새 실행마다 메모리에서 전달하고 실행 계획·로그에 저장하지 않는다.
- 코드 검토 중 owner 오류 이벤트가 한 번 소비된 뒤 정상으로 오판할 가능성을 발견해 실패 상태를 유지하도록 보완했다.
  GPU 오류는 현재 실행 전체를 실패시키고 완료 pointer가 있는 묶음만 재사용한다.
- CUDA cache/owner 검사 6개가 7.039초에 통과했다. 두 CPU 연결 교차 사용, 숫자 결과 대조, 메모리/요청 한도,
  잘못된 순서 거부와 owner 종료 감지를 포함한다.
- 집계 연결 검사 4개가 48.899초에 통과했다. CPU 기준과 13개 그룹 비교, CPU 작업자 수 변경 재개,
  완료 승인 직전 중단, GPU 강제 종료와 새 owner 재개, 출력 변조 거부를 포함한다.
- 실제 Node adapter 검사 5개가 1.668초에 통과했다. 2,051개 조건을 빠짐없이 처리하고 기존 CPU interval 전체 행과 일치했다.
- 중첩 시간 검사는 CPU 작업 두 개가 동시에 겹쳐도 중복 합산하지 않는 예제로 확인했다.
- 기존 CPU 생성 계약 및 입력/이전 결과 5,006개 파일 SHA가 일치함을 확인했다.

## 성능 측정 방법

같은 `data/vd-q-input`과 P3 기준 `data/vd-p3-repeat/new-1`을 사용한다.
GPU 전담 1개에 CPU 작업자 1/2/4개를 붙여 각각 측정하고, 계산·저장·검증 합계가 가장 짧은 구성을 고른다.
그 구성과 CPU 4개를 교대 3회 실행해 중간값을 비교한다. 시험 실행도 최종 파일 검증 및 기준값 13그룹 대조를 수행한다.

- `run_seconds`: 입력 파일 재검증, 프로세스 시작, 해석, 집계, 병합, 저장, 프로세스 정리까지의 벽시계 시간.
- `verify_seconds`: 독립 실행 검증 시간. 실제 출력 및 입력·중간 결과의 연결을 검사한다.
- `comparison_seconds`: 이전 기준값과의 실험용 비교 비용. 전처리 시간과 별도로 기록한다.
- CPU 여러 작업자의 단계 시간 합계는 중첩될 수 있으므로 전체 벽시계 시간과 더하지 않는다.
- GPU 중첩 시간은 GPU 요청 계산 구간과 CPU의 Node 정규화/집계 구간이 겹친 실제 시간을 뜻한다.
  순수 CUDA 커널 점유율은 아니다. 대기 시간에는 요청 직렬화·전송과 앞선 요청 대기가 포함된다.
- 측정기는 별도 실행마다 프로세스 트리 RSS/임시 디스크를 1초 간격으로 기록한다. 순간 peak의 완전한 상한은 아니다.

## 최종 보강 검사

- 독립 검토에서 실제 229일 표본 실행을 막는 결함은 발견되지 않았다.
- 최대 4,096일 입력에서 GPU 응답이 16MiB를 넘지 않도록 날짜 수에 따라 lookup batch를 자동으로 줄였다.
  511개 조건이 510개와 1개 요청으로 나뉘고 누락 없이 처리되는 테스트를 추가했다.
- 이미 실행 중인 결과 폴더의 재개는 GPU를 띄우기 전에 실행 잠금을 확인하도록 보완했다.
  두 번째 재개가 GPU owner를 생성하지 않는 테스트를 추가했다.
- 첫 전체 검사 명령에는 존재하지 않는 `test_historical_parallel_verify` 모듈명이 포함돼 로더 오류가 났다.
  검증기 테스트는 실제 `test_historical_parallel_writer` 안에 있다. 명령을 바로잡은 회귀 41개는 108.298초에 통과했다.
- 위 두 항목을 보강한 뒤 GPU 관련 18개를 다시 실행해 56.716초에 모두 통과했다.
  최종 범위는 기존 CPU 25개와 신규 GPU 18개, 총 43개 고유 검사다.
- 원본 바이트 SHA를 보존하도록 신규 Python/CJS를 UTF-8 LF로 고정했다. 기존 코드 파일은 바꾸지 않았다.
- 결과 로그: [회귀 41개](evidence/gpu-overlap-tests-final.log), [보강 후 GPU 18개](evidence/gpu-overlap-tests-hardened.log).

## 실제 32개·229일 결과

**P4 구현과 검증은 완료했지만, 이번 표본에서는 GPU 중첩이 CPU 기본 방식보다 느렸다. 기본 실행 방식은 바꾸지 않는다.**

RTX 4070 Laptop, 동일한 4개 DuckDB thread·4GB 예산에서 측정했다. worker 수별 예산을 나눠 쓰며
CPU 코어 자체를 강제로 고정한 실험은 아니다. 입력 준비는 이미 완료한 파일을 공통으로 사용했다.

| GPU 전담 1개에 연결한 CPU 작업자 | 계산·저장 | 독립 검증 | 합계 |
| --- | ---: | ---: | ---: |
| 1개 | 59.879초 | 15.512초 | 75.390초 |
| 2개 | 44.730초 | 14.984초 | 59.714초 |
| 4개 | 35.474초 | 15.250초 | 50.724초 |

4개가 가장 빨라 이 구성을 선택하고, CPU 4개 방식과 교대 3회 반복했다.

| 실행 | CPU 계산·저장·검증 | GPU 계산·저장·검증 |
| --- | ---: | ---: |
| 1회 | 44.437초 | 50.205초 |
| 2회 | 43.630초 | 50.291초 |
| 3회 | 43.995초 | 50.728초 |

| 3회 중간값 | CPU 4개 | GPU 1개 + CPU 4개 |
| --- | ---: | ---: |
| 계산·저장 | 30.725초 | 35.334초 |
| 독립 검증 | 13.270초 | 15.062초 |
| 합계 | 43.995초 | 50.291초 |

GPU 합계가 **14.31% 더 길었다.** 합계의 중간값은 각 회차 합계에서 구하므로 단계별 중간값을 더한 값과 약간 다를 수 있다.

이 표에 공통 입력 준비는 포함되지 않는다. 이전에 한 번 측정한 준비 72.205초를 단순 합산하면
CPU 116.200초, GPU 122.496초다. 이는 이번에 입력 준비까지 다시 재측정한 값이 아니다.

### 왜 빨라지지 않았는가

- 숫자 계산 및 요청의 작업자별 누적 시간은 CPU **6.890초 → GPU 1.007초**로 줄었다.
  GPU 순수 숫자 연산은 약 **0.347초**였다. 이 수치는 여러 작업자의 누적값이라 전체 벽시계 시간과 다르다.
- 그러나 실제 전체 묶음 계산 구간은 **18.553초 → 19.169초**로 줄지 않았다.
  남아 있는 정규화·결과 변환·집계 및 작업 분배의 영향을 함께 받는다.
- GPU owner 시작 비용이 중간값 **3.928초** 추가된다. 작은 표본 전체 시간에서 이 비용이 크다.
- 독립 검증은 CPU 13.270초, GPU 15.062초였다. GPU 수치 연산만 빠르게 해서는 이 비용을 줄일 수 없다.
  현재 GPU accepted wrapper에는 공통 파일 검사를 거듭 호출하는 부분도 남아 있어 후속 최적화 후보로 기록한다.
- GPU와 CPU의 동시 실행은 실제로 발생했다. 4-worker 반복에서 GPU 요청 계산 구간 약 0.61~0.63초 중
  CPU 정규화/집계와 겹친 시간은 **0.516~0.563초**였다. 겹칠 GPU 구간 자체가 짧다.

따라서 이번 결과는 “중첩이 구현되지 않았다”는 뜻이 아니다. 같은 표본에서 CPU 기본 경로보다
전체 시간이 짧아지지 않았다는 관측이다. 더 큰 묶음에서는 시작 비용의 비중이 달라질 수 있지만 아직 측정하지 않았다.

### 정확성·자원·산출물

- 9회 모두 입력·lookup interval·중간 count·품질·최종 날짜 결과 **13개 그룹이 기존 CPU와 완전히 일치**했다.
- 각 실행의 양수 count **1,875,271행**, 날짜별 품질 **229행**, lookup interval **502,119행**이 동일하다.
- 최종 날짜 출력은 양수 count Parquet 25개와 품질 Parquet 1개다. 0 조회는 기존 grouped reader가 복원한다.
- 반복 구간에서 관측한 프로세스 트리 RSS 최고치는 CPU 약 **3.08GiB**, GPU 약 **4.74GiB**였다.
  GPU PyTorch allocated 최고 약 **70.78MiB**는 CUDA context나 다른 앱의 GPU 메모리를 포함한 총 VRAM 값이 아니다.
- 관측한 scratch 최고는 **353.22MiB**다. 이는 spill용 임시 파일 값이며 전체 실행 폴더 용량과 다르다.
- GPU 실행 `gpu-r3`는 새 Python 프로세스에서 PyTorch import를 금지한 상태로 독립 검증에 통과했다.
- 기존 CPU 생성 계약과 보호한 입력·과거 산출물 **5,006개 SHA가 그대로 유지**됐다.
- 실행 폴더: `data/vd-gp4`. 9회 측정 완료 상태는 `progress.json`, 원본 결과는 `results.json`에 있다.
- 요약 근거: [측정·정확성·자원·보존 증거](evidence/gpu-overlap-results.json).

측정기 보고서가 JSON 구성 시간을 `encode_seconds`라는 잘못된 이름으로 찾는 문제를 결과 정리 중 수정했다.
실제 값은 각 실행 receipt의 `ipc_encode_seconds`에 이미 저장돼 있다. 원본 `results.json`은 보존하고,
그 receipt에서 정확한 필드를 다시 합산한 `results-corrected.json`과 위 요약 증거를 만들었다.
시간 측정·count·run manifest는 변경하지 않았다. 측정 당시 benchmark 소스는 `data/vd-gp4-base/benchmark-measured.py`에 보존했고,
요약 증거에 수정 전후 benchmark SHA를 함께 기록했다. 계산을 생성한 GPU 코드 6개와 공통 CPU 생성 계약은 측정 당시와 일치한다.

## 완료 범위와 후속 순서

P4의 선택형 GPU owner·후보 재사용·CPU 작업 중첩, 장애/재개, 실제 32개 회귀 측정까지 완료했다.
10% 개선 채택 기준에는 도달하지 못해 CPU 4-worker grouped 방식을 기본 비교 기준으로 유지한다.

다음은 P5의 대표성 검증이다. 기존 32개에 빠진 극단적인 3개 패키지와 작은 패키지 다수를 포함해
작업량 구간별 성능을 확인해야 한다. 전체 입력 준비·집계·출력 비용까지 측정하기 전에는
이번 시간을 99,996개로 단순히 곱해 전체 완료 시간을 확정하지 않는다.
전체 선정 실행, 서버·Spark 확장, DB 적재, commit·push는 이번에 수행하지 않았다.

최종 확인에서 기록된 coordinator·CPU·Node·GPU 프로세스 ID 77개가 모두 종료된 것을 확인했다. 신규 Python 11개 구문 검사와 변경 파일 공백 검사도 통과했다.
