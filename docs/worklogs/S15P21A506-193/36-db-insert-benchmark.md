# 36. DB 삽입·외래키 병목 분리 실험

## 범위와 순서

2026-09-12 사용자 지시에 따라 날짜 인덱스보다 삽입·외래키 비용 분리 측정을 먼저 수행한다.
현재 43일/106,346,692행은 중단 상태로 보존한다. 원래 적재 코드·계획·DB 제약조건을 변경하거나 전체 적재를 재개하지 않는다.

실험용 테이블은 기존 DB 안의 새 `vd193_bench_<UUID>` schema에만 만든다. 별도 DB에서 FK 성능을 재현하려면
약 18GB의 실제 version 본문과 인덱스를 먼저 복제해야 하므로, 이번에는 테스트 대상 테이블만 격리하고
실제 `public.version`과 `public.snapshot`을 참조한다. 서비스 값은 읽기만 하며 기존 테이블 DDL은 변경하지 않는다.

1. 검증된 원본에서 중단 날짜 2023-03-06의 COPY 입력을 새 폴더로 재생성한다.
2. 골고루 선택한 실제 10만 행으로 정확성과 측정 장치를 검사한다.
3. INSERT + PK/FK, INSERT + PK만(원인 분리용), COPY + PK/FK, COPY 후 PK/FK 일괄 생성(구조 변경 후보)을 비교한다.
4. 실제 하루치로 기준 방식과 유망 후보를 비교한다. 작은 표본으로 전체 시간을 추정하지 않는다.
5. 모든 결과는 원본과 전체 key/value 비교, 품질/행 수 검사 후 기록한다. FK 없는 진단 테이블은 적재 결과로 사용하지 않는다.

COPY 후 키 생성은 검증 전 테이블이 서비스에 연결되지 않는 별도 준비 경로 실험이다. 이 방식이 빨라도
현재 테이블로 바로 적용 가능한 것으로 보고하지 않는다. 파티션 연결과 이행은 별도 검증 범위다.

## 측정

파일 준비, staging COPY, 실제 삽입 또는 COPY, PK 생성, FK 생성·검증, 값 비교, COMMIT을 분리한다.
EXPLAIN ANALYZE의 constraint trigger 시간은 진단 표본에서만 수집하고 일반 wall-clock 측정과 구별한다.
같은 입력·설정, 새 대상 테이블, 순차 실행으로 비교하며 참조 테이블 cache 상태에 따른 편차를 기록한다.

## 실제 결과

### 완료한 부분

- 기존 FullSource로 2023-03-06의 2,827,680행을 17.766초에 재생성했다. `data/vd-db-bench-input-20260912-01`의 입력과 metadata는 재사용 가능하다.
- 격리 실험기 `pipeline/version_dependents/historical_db_benchmark.py`를 추가했다. 실제 참조 테이블 FK, 정/역순 반복, 값 전수 비교, 제약 검증, UUID schema 정리, 기존 두 loader의 advisory lock을 사용한다. 기존 적재기 코드는 수정하지 않았다.
- 새 안전성/입력 테스트 및 기존 COPY 입력 테스트 7개 통과. 최초 표본 실행의 DuckDB 별칭 구문 오류를 수정한 뒤 실제 표본 실행 성공.
- 10만 행 진단 네 방식 모두 원본과 전수 비교 일치. [원본 진단 결과](evidence/db-insert-diagnostic-results.json).

| 방식 | 총시간(초) | 해석 |
| --- | ---: | --- |
| INSERT + PK/FK | 22.391 | EXPLAIN 진단 포함 |
| INSERT + PK만 | 0.172 | 외래키 비용 분리용, 적재에 사용 불가 |
| COPY + PK/FK | 3.093 | 앞 실험이 캐시를 채운 뒤 실행 |
| COPY 후 PK/FK 생성·검증 | 0.579 | PK 생성 0.031초, FK 생성+검증 0.313초 포함 |

첫 INSERT의 PostgreSQL 실행 22.331초 중 version FK 20.931초, snapshot FK 1.258초였다. 이 표본에서 FK 검사가 주요 비용임은 관측했다. 단, EXPLAIN 여부·캐시 차이와 1회 측정 때문에 위 시간을 방식별 개선 배수로 해석하지 않는다. 새 빈 대상 테이블의 PK를 사용했으므로 기존 1억 행 이상 누적 테이블의 인덱스 비용도 반영하지 않는다. COPY 후 제약 생성은 구조 변경 후보이며 기존 서비스로 바로 적용하는 검증은 아니다.

### 사용자 이동 요청에 따른 중단

하루 전체 4방식×정/역순 2회 실험은 첫 INSERT 도중 사용자 요청으로 취소했다. 완료한 하루 전체 trial은 0개이며 시간 추정 근거로 사용하지 않는다.

- backend 30164를 DB·application_name·실험 schema가 일치하는 조건으로 취소했다.
- 해당 transaction rollback 및 실험 schema 정리 완료. 실험 세션 0개, 실험 schema 0개 확인.
- 기존 43일/106,346,692행의 게시 이력과 원래 적재 코드·입력 계약 재검사 통과. 실제 적재 재개 없음.
- 체크포인트: `data/vd-db-bench-full-20260912-01/pause-checkpoint.json`.
- 재개 도구: 같은 폴더 `resume-benchmark.ps1`. `-CheckOnly`는 검사만 수행한다. 옵션 없이 실행하면 코드 지문·기존 중단 계약 확인 후 저장된 입력으로 새 실험 폴더에서 시작한다. **기존 서비스 전체 적재는 시작하지 않는다.**
- SQL 삽입 도중 위치부터 이어 붙이는 것은 지원하지 않는다. 취소된 첫 trial만 처음부터 다시 시작하며, 완료한 10만 행 진단과 입력 준비는 다시 수행할 필요가 없다.

다음 순서: 하루 전체 일반 실행 비교 완료 → 반복별 결과·캐시 한계 보고 → 필요 시 일괄 제약 검증/파티션 연결의 실제 적용 경로 검증. 현재 성능 개선율과 전체 적재 ETA는 미확정이다.

### 하루 전체 비교 완료

2026-09-12 16:00:50 KST 완료. 15:32:58 재개부터 약 27분 52초 걸렸다. 사용자 요청으로 완료까지 직접 확인했다. 앱 자동 확인 도구는 연결 오류로 설정하지 못했으며 별도 예약 감시는 만들지 않았다.

입력은 2023-03-06의 2,827,680행이며 네 방식 각각 정/역순 2회, 총 8회다. EXPLAIN 없이 측정했다.
아래 총시간은 해당 trial의 테이블 생성·삽입·키 생성/검증·값 전수 비교·COMMIT을 포함한다. 공통 입력 준비와 staging 준비, trial 종료 후 DROP은 제외한다. 공통 staging COPY는 2.859초였으며 이것이 전체 입력 준비 시간은 아니다.

| 방식 | 1회차 총시간 | 2회차 총시간 | 의미 |

관측된 결론: 이 날짜·격리 테이블에서는 PK를 유지하고 FK만 제외해도 수분에서 약 5초로 줄었다. 따라서 이 측정의 주요 비용은 PK 유지보다 행별 FK 검사다. COPY 명령으로만 변경하는 효과는 반복별 차이가 커서 확정하지 않는다. COPY 후 일괄 PK/FK 생성은 두 번 모두 빠르지만 참조 데이터 cache·실행 순서 영향이 있으므로 전체 남은 900,737,916행의 ETA로 단순 환산하지 않는다.

- 최종 `result.json`: COMPLETE, exact_match 전부 true, cleanup_complete true, service_history_unchanged true.
- 사후 실험 세션 0개/schema 0개, 백그라운드 wrapper 종료 확인.
- 기존 43일/106,346,692행 게시 이력과 원래 코드·입력 계약 재검사 통과. 실제 서비스 적재는 재개하지 않았다.

한계와 다음 작업: 대상은 새 빈 테이블이므로 실제 누적 1억 행 이상 테이블의 인덱스 크기와 동시 서비스 부하를 반영하지 않는다. 기존 테이블의 제약을 제거하는 변경은 하지 않았다. 다음에는 기존 43일을 보존하면서 별도 날짜 테이블의 일괄 검증 결과를 안전하게 연결하는 경로와 중단/재개를 검증해야 한다. 날짜 인덱스와 전체 게시 검증 비용 비교도 아직 수행하지 않았다.
