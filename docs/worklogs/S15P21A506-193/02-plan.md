## H5-B 실행 범위와 이후 순서

2026-09-11 후속 요청으로 [18 성능 개선 계획](18-performance-improvement-plan.md)을 작성했다.
요청 구성·전역 검사·구간/변화 기록·날짜별 검증의 반복을 순서대로 줄이고, 작은 실제 표본의
정확성과 처리량을 비교하는 계획이다. 현재는 계획 보고까지이며 최적화 구현과 전체 선정 실행은 시작하지 않았다.

2026-09-11 사용자 요청으로 이번 범위는 **코드 완성 → 작은 실제 표본의 정확성·속도 확인 → 보고**다.
아래 1~4번의 실행 코드는 구현했으며 6개 target의 229개 날짜에만 적용했다. 전체 선정
99,996개 이름에 대한 입력 준비·계산 실행과 DB 적재는 이번 범위에 포함하지 않는다.

1. 검증된 H5-A와 D-22 다운로드 CSV 지문을 고정해 selected target과 고유 요구조건을 추린다.
   source는 선정 목록으로 거르지 않고 선정 target의 전체 후보 이력도 유지한다. 기존 전체
   H1/H5-A 파일을 다시 생성하거나 덮어쓰지 않는다.
   H5-A workload는 규모/요구조건 색인이며 source 식별자를 없앤 자료이므로 그 합계를 count로
   쓰지 않는다. 전체 H1 source와 원본 requirements를 연결해 source ID/version을 보존한다.
   target 필터 후의 source별 선언 수·계산용 순서를 만들고 원본 선언 순서도 이력으로 남긴다.
   품질 수치는 전체 npm이 아닌 선정 target에 대한 선언 범위를 명시한다.
2. 선정 목록 밖 source의 참조, 동일 source의 중복 선언, 서로 다른 source 버전의 참조를

   시간·메모리를 측정한다. 최신 진단도 선정 target만 추린 값과 대조한다.
3. 구간을 그대로 처리하는 대용량 실행 경로와 파티션별 저장·재개를 연결한다. 현재 H3의

   준비가 끝나면 선정 target의 229개 날짜 count를 계산하고 H4 Parquet에 저장한다.
   파티션은 target 이름을 기준으로 나눠 같은 target에 대한 source 중복 제거가 유지되도록
   한다. 선정 이름 중 후보가 없는 경우에도 알려진 package와 미매핑 package를 구분한다.
4. 완료 날짜/파티션, PARTIAL 품질, 입력/선정 목록 지문을 보존한다. 시간 경과로 자동 종료하지
   않고 메모리·디스크 보호를 유지한다. 독립 계산이 시작되면 모델 폴링을 중단한다.

## 먼저 확인할 입력 조건

1. 작업 위치는 기존 워크스페이스로 고정한다. 현재 이 위치에 `data/requirements-resolution`이 없다는 확인과, 입력을 실제로 잃었다는 판단은 구분한다.
2. 7번 run과 실제 파일을 이전 계산 위치에서 확인했다. 현재는 읽기 전용 참조이며 이동·복사를 하지 않는다. 위치와 확인 범위는 [입력 조사](07-input-contract.md)에 남긴다.
3. 기록된 `PARTIAL`, `ready_for_dependents=false`와 최종 완료 기록·추가 검증의 한계를 확인한다. 코드 병합을 데이터 입력 승인으로 대체하지 않는다.
4. 전체 target 버전 집합과 정확한 스냅샷 시각을 확정한다. edge에 나타난 target만 집계 모집단으로 삼지 않는다.
5. 현재 계약에서 PARTIAL 결과는 정상 count로 게시하지 않는다. D-07에서 승인한 별도 진단 집계는 성공 관계에 등장한 target만 센다. 전체 target 모집단에 0을 채우는 정상 집계와 완료 상태를 구분한다.

실제 입력의 사용 조건이 미충족이어도 합성 데이터로 P-02~04를 개발·검증할 수 있다. 실제 데이터의 정상 게시 가능 여부와 구현 진행 가능 여부를 구분한다.

## 작은 정답 데이터에서 검증할 사례

- 같은 source 버전·target 버전의 중복 관계는 한 번만 센다.
- 같은 패키지의 서로 다른 source 버전은 각각 센다.
- target의 버전이나 snapshot이 다르면 count가 섞이지 않는다.
- 관계가 없는 정상 target의 0과 입력 누락·미해석·실패를 구분한다.
- target 집합 밖의 관계, 미래 배포, 파일 누락·변조, 잘못된 manifest를 거부한다.
- count의 INT 범위와 DB 복합키·외래키를 검증한다.
- 계산 실패와 DB 적재 실패를 구분하며, 적재 실패가 완료된 count 파일을 훼손하지 않도록 검증한다.
- 동일 입력 재실행, 다른 입력 충돌, 동시 실행과 중간 실패의 결과 보존을 확인한다.

## 2026-09-10 Parquet 저장 단계의 실행 계획

1. 기존 집계 함수가 입력을 검사하고 계산한 결과를 스냅샷·run별 새 폴더에 저장한다. count, 입력 이력, 품질 요약을 각각 Parquet로 만들고 파일별 스키마·행 수·크기·SHA를 manifest에 기록한다.
2. 입력 이력은 호출자가 제공한 run·manifest SHA·정책 SHA를 보존한다. 이 저장 계층은 실제 upstream manifest나 전체 모집단을 승인하는 기능이 아니므로, 이력의 검증 상태를 미검증으로 기록하고 DB 적재 가능 상태나 정상 게시용 `_SUCCESS`를 만들지 않는다.
3. 저장 파일만 읽는 별도 검증 기능에서 manifest SHA·정확한 snapshot 시각·스키마·복합키·count·품질/이력 일치를 검사한다. 이는 원본 관계를 다시 해석하거나 원본 모집단의 완전성을 증명하는 검증과 다르다.
4. 합성 데이터로 서로 다른 날짜의 count 분리, 변조·누락·혼합 날짜·PARTIAL 차단, 중간 실패와 기존 결과 보존을 검증한다. 작은 예제 파일과 조회 방법을 남긴다.
5. 변경 범위는 `pipeline/version_dependents/`와 이 작업 기록 폴더다. 실제 7번 전수 계산·DB 적재·7번 resolver 수정·commit·push는 수행하지 않는다.

위 구분은 현재 요청인 저장 기능의 완료와 생산용 입력 승인 대기를 따로 추적하기 위한 것이다. P-03 전체를 완료로 표시하지 않는다.

## 전체 실행 자원 확인

입력 검증과 집계 과정에서 중복되는 전수 스캔을 줄일 수 있는지 검토하되 검증 항목을 생략하지 않는다. 7번의 추가 검증은 메모리 부족으로 중단된 이력이 있으므로 사용할 메모리·임시 디스크·복구 방법을 실행 전에 기록한다. D-07 승인에 따른 진단 집계의 자원 설정과 실행 기록은 [09 진단 집계](09-diagnostic-run.md)를 따른다.

## 2026-09-11 가중치 이벤트 집계 단계

승인된 알고리즘 계획 A0~A3을 구현하고 실제 표본과 대조했다. [19 결과](19-weighted-event-aggregation.md)에 변경 범위·실측·검증을 기록했다. lodash 집계/품질은 3회 중간값 58.54% 감소했지만 작은 6개 target에서는 회귀했으므로 기본 알고리즘은 기존 방식이다. 새 방식은 명시적 옵션과 새 v2 run에서 사용한다. 전체 229개 테스트·6개 target 229일 독립 재계산을 통과했다.

다음 미실행 범위는 A4(반복 조회/직렬화), A5(버전 범위 검색), A6(cache/날짜별 저장 검증)와 대표 표본별 적용 기준이다. 전체 선정 입력 준비·계산 및 H6/H7/DB는 아직 완료되지 않았다. 이번 승인의 종료점은 작은 실제 데이터 검증 결과 보고다.

사용자가 명확히 한 O-4/O-5의 구현과 대표 표본 측정을 완료했다. O-4는 [20 결과](20-daily-verification-throughput.md)의

A5의 SemVer 후보 검색은 이번 변경에 포함하지 않는다. O-5는 대표 8·16·32개에 대해 선택한
target을 참조하는 전체 source 입력부터 229개 기준일의 양수 파일 전수 검증까지 측정했다.
8/16/32개 전체 시간은 각각 147.56/327.30/315.83초이며 단일 순차 측정의 환경 차이를 보존한다.
전체 선정 실행과 H6의 0 보완/DB key 연결·H7 적재는 별도 미실행 범위로 유지한다.

## 2026-09-11 병렬 구조 후속 계획

CPU/GPU 실제 집계 연결은 `1ec693c`로 커밋했다. 사용자가 요청한 다음 구조 계획은
[25 병렬 계산 구조 계획](25-parallel-execution-plan.md)에 정리한다. P0 기준 고정 → P1 입력 분할 →
P2 CPU 작업자·재개 → P3 날짜×묶음 출력 → P4 CPU/GPU 중첩 → P5 실측 → P6 EC2 확장 경계 순서다.
첫 구현 체크포인트 P0~P2와 32개×229일 실제 데이터 비교는 [26 결과](26-parallel-input-cpu-execution.md)에 기록했다.
worker 1/2/4의 결과는 동일하며 4-worker 계산·저장 시간은 1-worker보다 35.8% 줄었다.
입력 분할·검증을 합친 표본 전체 시간은 이전 CPU 측정보다 길어 병렬 경로는 선택형으로 유지한다.
이후 P3 출력 저장 개선과 32개 표본 반복 평가는 [27 최신 결과](27-input-verification-storage-optimization.md)로 진행했다.
P4 GPU 중첩·P5 전체 모집단 대표성 평가·P6 서버 확장은 미실행이다.
