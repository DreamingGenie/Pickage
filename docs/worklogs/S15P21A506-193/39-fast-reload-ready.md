# 39. 전체 재적재 실행 준비

## 요청·변경 범위

사용자 요청: 전체 적재는 나중에 시작하되 바로 실행할 수 있도록 준비한다.
기존 Parquet와 중단된 43일 적재·재개 코드·서비스 테이블을 보존한다.
새 실행기는 같은 DB의 별도 schema에 날짜별 partition과 실행/시도/현재 이력을 만든다.
전체 시작 시 기존 날짜까지 229일을 새 대상에 적재한다. 서비스 테이블 전환은 자동 실행하지 않는다.
이번에는 코드·설정·점검·제한된 격리 검증까지 수행한다. 전체 적재/원격 작업/커밋은 실행하지 않는다.

## 작업 계획

1. 검증된 COPY→PK/FK 일괄 생성→날짜 연결을 실제 날짜별 실행기에 통합한다.
2. 원본/코드 지문, 실제 package-version·달력 원천, 완료 이력과 값 재검증을 연결한다.
3. 새 대상과 서비스 이력을 분리하고, 하루 데이터와 완료 이력을 같은 트랜잭션으로 확정한다.
4. 공통 입력 1회 준비, 날짜 경계 중단, 중복 실행 방지, 재개·로그·백그라운드 실행을 제공한다.
5. 읽기 전용 사전 점검과 실제 시작 명령을 분리하고 로컬 실행 설정을 고정한다.
6. 격리 DB에서 중단·실패·변조·재개를 검사하고 최대 하루를 통합 경로로 측정한다.
7. 기존 43일 재개 계약 보존과 전체 적재 미시작을 확인하고 사용법/증거를 기록한다.

## 완료 기준

- 점검 명령은 서비스/새 대상에 데이터를 쓰지 않는다.
- 명시적 시작 명령만 새 대상을 생성하고 전체 적재를 수행한다.
- 재부팅/오류 후 확정된 날짜는 재검증하고 미완료 날짜를 다시 적재한다.
- 원본·입력·코드·대상 변경과 저장된 값 변조를 감지한다.
- 전체 고정 시간 제한은 없고 잠금 대기는 제한한다.
- 기존 서비스 데이터/이력은 그대로 유지되며 새 대상의 완료와 서비스 전환을 구분한다.

## 실제 결과

### 실제 구현

- `historical_db_fast_publish.py`: 새 schema 안에 실제 공통 ETL 실행/시도/current 열·제약을 복제하고 내부 FK를 재구성했다. 원본 public 참조/원천을 읽고 같은 DB 세션의 advisory lock을 유지한다.
- 하루를 한 트랜잭션으로 적재한다. staging 품질·ID/이름 검증, COPY, PK/FK 생성, 값 전수 대조, ATTACH, 원본/코드/입력 재검사, receipt와 ETL 완료 기록을 함께 COMMIT한다.
- 원래 작업의 loader/source/key/prepare/publish/postgres 코드와 재개 계획은 수정하지 않았다.
- `historical_db_reload.py`: 공통 FullSource와 전체 키 검사 1회, 날짜별 실행, OS 잠금, 날짜 경계 stop, 명시적 resume, 자원 부족 시 중단, 코드/DB/입력/날짜별 행 수 고정.
- 실행 중 Status는 로컬 상태/heartbeat만 읽는다. Check/재개/마지막 검사에서 DB의 행 수·PK/FK·날짜 경계·입력 manifest·현재 포인터를 검사한다. 완료 날짜 값 전수 대조는 실제 날짜 재개 단계에서 수행한다.
- 전체 완료는 `READY_FOR_CUTOVER`, 일부 날짜 시험은 `PILOT_VERIFIED`로 표시한다. public 서비스 전환은 자동으로 수행하지 않는다.
- `scripts/version-dependents-reload.ps1`: 기본 Check, Start/Resume 숨김 백그라운드 실행, Stop/Status, 별도 시간별 로그, 프로세스 PID+시작 시각 확인, 의존성 경로, Windows 자동 절전 억제.
- 전체 코드에 고정된 실행 종료 시간 제한이 없다. DB 잠금 대기는 10초이며 디스크 점검 명령에는 30초 제한이 있다.

### 최대 날짜 통합 검증

실제 시작 명령을 **1일짜리 별도 시험 설정**에 적용했다. 전체 설정은 실행하지 않았다.

- 시험 schema: `vd193_reload_pilot20260912_01`.
- 날짜 2026-08-31, 7,822,819행, 97,745개 ID. 원본 PARTIAL 품질을 보존.
- 결과: `PILOT_VERIFIED`, 전체 값/행 수 일치, 실제 execution/attempt/current 기록 및 PK/FK 연결 확인.
- 공통 준비부터 최종 검사까지 **111.173초**.
- 날짜별 입력 생성+DB 처리 **53.047초**, 그중 DB publish **45.682초**.
- DB 세부: staging 12.309초, COPY 10.520초, PK 1.686초, FK 12.558초, 값 검사 2.670초, ATTACH 0.005초, 완료 직전 원본/코드/입력 재검사 3.917초.
- 최종 구조/행 수/current 검사도 이 통합 실행에 포함했다. 전체 229일의 최종 count 재검사 시간은 아직 직접 측정하지 않았다.
- [최대 날짜 통합 결과](evidence/db-fast-reload-pilot.json).

### 수정·검증 중 발견한 문제

- PostgreSQL JSON의 OID 문자열을 정수로 정규화하여 다른 target으로 오인하지 않도록 수정했다.
- parent/child CHECK 제약 이름을 명시적으로 동일하게 해 ATTACH가 같은 검증을 재사용하도록 했다.
- 임시 PID 파일만으로 재개를 막는 구조를 OS 커널 잠금으로 바꿨고, 키 검사와 적재 사이에도 같은 DB 세션 잠금을 유지했다.
- DB identity·실제 날짜별 행 수·immutable plan 검사, parent/history/child 제약 변조, current 포인터 누락 검사를 연결했다.
- heartbeat가 현재 날짜 상태를 덮어쓰지 않도록 별도 파일로 기록한다.

### 실제 전체 설정 및 실행 안내

전체 229일/1,007,084,608행은 `data/vd-db-reload-ready-20260912-01/config.json`에 고정했다.
상세 명령과 결과 의미는 [실행 안내](40-fast-reload-runbook.md)를 따른다.

실제 기본 Check가 전체 ID 97,745개/버전 7,822,819개/229일과 원본·DB 원천 일치를 확인했다.
새 전체 대상 schema는 존재하지 않았고 완료 날짜/행 수는 0이었다. Check는 이를 생성하지 않았다.
점검 시 호스트 여유 1,225,740,615,680바이트, DB 데이터 파일시스템 여유 839,652,511,744바이트로 양쪽 200GiB 기준을 통과했다.
관련 실제 PostgreSQL·coordinator 테스트 **22개 전부 통과, 45.282초, skip 없음**.
독립 검토에서 최종 코드의 추가 차단 결함은 확인되지 않았다. 최종 전체 행 수 재검사 비용은 별도 관찰 항목이다.

최대 날짜 시험을 새 백그라운드 프로세스의 Resume 명령으로 재개했다. 공백이 포함된 config 경로도 실제 실행했다.
**7,822,819행 전수 재검증, REVERIFIED, 삽입 0행**. 날짜별 재준비+검증 28.687초, DB 단계 21.471초였다.
시험 DB schema는 소유자·1일 시험 계획·세션 종료를 확인한 후 명시한 테이블만 제거했다. 원본 파일과 결과 증거는 남겼다.
마지막 확인: 실행 세션 0, 전체용 schema 0, public 기존 PUBLISHED 43일/106,346,692행 유지, 이전 `check_resume.py` 통과.

### 미실행 범위

전체 10억 행 적재, public 테이블 교체·삭제·이력 전환, 서버 작업, 커밋/푸시는 하지 않았다.
기존 3~4시간 예상은 최대 날짜 통합 처리 시간과 부합하지만 229일 지속 적재와 마지막 전체 재검사 시간을 보장하는 실측은 아니다.
