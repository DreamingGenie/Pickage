# 44. 로컬 서비스 테이블 전환

## 변경 범위와 계획

사용자가 완료된 테이블의 서비스 전환만 요청했다. 대상은 로컬 PostgreSQL
`pickage-267-validation`의 `pickage_267_full_defaulted`이며 서버 배포는 포함하지 않는다.

1. 완료 보고서·코드 지문·DB 실체·229개 파티션 이력·권한·외부 의존성을 확인한다.
2. 기존 `public.package_version_snapshot`과 그 데이터셋의 실행/시도/현재 이력을
   `vd193_backup_20260913`에 보존한다. 다른 데이터셋의 이력은 변경하지 않는다.
3. 완성된 부모 테이블을 public으로 이동하고 새 실행/시도/현재 이력을 같은 트랜잭션에서 반영한다.
   229개 자식 파티션은 기존 스키마에 남으며 부모를 통한 서비스 조회는 동일하다.
4. 전환·복구 SQL을 미커밋 트랜잭션에서 실행하여 왕복 검증한 후 실제 전환한다.
5. public 이름으로 실제 반환값·파티션 연결·제약·게시 이력을 확인한다.

현재 테이블의 소유자는 모두 postgres이고 별도 서비스 역할의 GRANT는 없다.
기존 테이블을 가리키는 외부 FK·뷰·사용자 트리거는 확인되지 않았다.
이전 43일/106,346,692행은 삭제하지 않는다. 원본 Parquet·백엔드 코드는 변경하지 않는다.

## 전환 후 운영 경계

이전 적재기의 저장된 계획은 전환 전 테이블 OID/스키마 계약을 고정하고 있다.
전환 후 기존 Check/Start/Resume 및 private 테이블용 조회 실험을 재실행하지 않는다.
계획이나 생성 코드 지문을 덮어쓰지 않으며 새 날짜 적재는 별도 후속 작업이다.
복구 SQL은 추가 적재 전에만 사용한다. 새 서비스 데이터나 이력이 바뀌었다면 먼저 재검토한다.

## 결과

2026-09-13 **09:46:46 KST** 실제 전환과 새 연결의 조회 확인을 완료했다.

- 서비스 이름: `public.package_version_snapshot`, 새 부모 OID 280767.
- 연결된 날짜 파티션: 229개, 기존 전체 적재 검증/receipt 기준 1,007,084,608행.
  이번 전환은 데이터를 복사하거나 10억 행을 다시 COUNT하지 않았다.
  모든 파티션의 OID·열·제약·경계와 날짜별 receipt를 대조했고,
  적재 후 통계의 insert 합계 1,007,084,608, update/delete 0을 확인했다.
  통계는 독립적인 전수 데이터 검증을 대체하지 않으며 앞선 적재 완료 검증을 함께 사용한다.
- 이전 43일/106,346,692행 테이블은 `vd193_backup_20260913.package_version_snapshot`에
  OID 87774 그대로 보존했다. 이동은 메타데이터 변경이므로 대용량 복사본을 만들지 않았다.
- 이전 version-dependents 실행/시도/현재 이력을 백업한 뒤 새 229일 이력과 현재 날짜 2026-08-31을 반영했다.
  다른 데이터셋의 실행·시도·현재 이력은 전후 전체 행 직렬화 해시가 일치했다.
- 복합 PK·version/snapshot FK·음수 금지 제약 및 기존 날짜 파티션 인덱스를 유지했다.
  기존과 새 부모의 유효 권한은 모두 postgres 소유자 권한이며 별도 GRANT 추가는 없었다.
- 전환 전 예행연습에서 전환→복구→전체 ROLLBACK 후 원래 OID와 이력 해시 복원을 확인했다.
- 실제 전환은 서비스 테이블과 적재 이력을 같은 트랜잭션에서 COMMIT했다.
  전환 전후 및 COMMIT 후 새 연결로 48개 버전/7,560행이 기존 실제 조회 결과와 모두 일치했다.
- 실제 실행기의 검증·전환·새 연결 확인을 포함한 시간은 3.334초였다. 순수 DDL 시간과 구분한다.
- 별도 전체 ANALYZE나 인덱스 재생성은 하지 않았다. 기존 파티션 통계/인덱스를 보존했다.

첫 예행연습에서는 복구의 외부 의존성 검사가 부모 자신의 `dependents_nonnegative` CHECK를
외부 객체로 오인해 실패했다. 트랜잭션 전체가 취소된 뒤 서비스 OID 87774와 백업 스키마 부재를 확인했다.
자신의 제약을 제외하도록 조건을 수정한 뒤 전환·복구 왕복 검증에 성공했고, 그 SQL 그대로 실제 전환했다.

SQL은 이 로컬 DB의 system identifier와 OID를 고정한 일회성 기록이며 서버에 그대로 실행하면 안 된다.
복구는 ON_ERROR_STOP을 켠 동일 psql 세션에서 `BEGIN`, `SET LOCAL lock_timeout='10s'`,
`SET LOCAL statement_timeout='180s'`, 복구 SQL, `COMMIT` 순서로 실행한다.
추가 데이터/이력/외부 의존성 또는 통계 초기화가 발견되면 자동 복구를 거부한다.
이번 작업에서는 복구를 예행연습에서만 실행했으며 실제 최종 상태는 새 테이블이다.

서버 이관·백엔드 버전별 쿼리 수정·API/동시 요청 성능 검증·추가 날짜 적재는 이번 전환 범위에 포함하지 않았다.
전환 후 사용자 요청에 따라 문서의 최신 상태를 정리하고 관련 전환·복구·검증 기록을 커밋한다. 푸시는 별도다.
