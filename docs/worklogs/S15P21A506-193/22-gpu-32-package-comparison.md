# 22. 32개 패키지 전체 요구조건 CPU/GPU 비교

## 요청과 범위

2026-09-11 사용자 요청: 기존 32개 패키지에 대해 CPU와 RTX 4070 Laptop GPU의 차이를 실험한다.
이번 실험은 두 패키지의 제한된 조건을 사용한 [21번 실험](21-gpu-resolver-experiment.md)을 확장한다.
기존 `data/vd-pilot-a/32/input`의 **32개 이름·40,701개 요구조건·141,607개 후보·229개 날짜**를 모두 사용한다.
요구조건 없는 이름 2개와 unmapped 이름 2개도 보존한다. 선언 모집단은 10,118,750행인 동일 입력이다.

비교 대상은 개선 CPU 범위 인덱스와 GPU 묶음 계산의 **버전 해석 구간**이다.
생산 `_resolve_partition`의 DuckDB 반복 조회·응답 삽입, 가중치 집계, 날짜별 Parquet 저장,
DB 적재의 속도를 측정했다고 표시하지 않는다. 기존 315.835초 또는 해석 관련 174.184초와
직접 배속을 계산하지 않는다. 전체 10만 패키지 실행·생산 통합·commit/push는 수행하지 않는다.

## 작업 계획

1. prepared input plan/manifest와 완료 production run plan/partition receipt·파일 SHA·코드 지문을 검사한다.
   기존 lookup interval을 같은 입력의 저장된 기준 정답으로 사용한다. 날짜별 파일 전체를 새로 계산하지 않는다.
2. 32개 패키지의 후보·요구조건·기존 해석 결과를 공통으로 한 번 읽고, lookup_id 누락·중복과
   229일 coverage를 검사한다. 패키지별 후보 수·조건 수를 target_names의 예상 수와 대조한다.
3. 패키지 경계를 지켜 요구조건을 최대 1024개씩 나누되 전체를 순회한다.
   기존 normalizer/GPU/production 파일은 변경하지 않고 별도 묶음 측정기를 추가한다.
4. 사전 검증에서 모든 조건×후보의 rank 포함 여부를 npm Range.test와 대조하고 CPU/GPU의
   전체 interval을 저장된 정답의 lookup_id·기간·상태·정규화 조건·target key와 비교한다.
5. 전체 패키지를 5회 순회하고 CPU/GPU 순서를 교대한다. 같은 회차의 공통 정규화 시간을
   양쪽에 동일하게 포함한다. 정답 대조·해시·기록 시간은 해석 시간과 분리한다.
6. 회차별 32개 합계의 중간값, 패키지별 시간, CPU/GPU 준비·전송·계산·interval 변환,
   최고 allocated/reserved VRAM과 느려지는 패키지도 기록한다.

준비된 파일 읽기·지문 검사는 한 번의 공통 비용이며 원본 Bronze에서 prepared 파일을 새로
만드는 시간과 다르다. Python import·CUDA/Node 시작과 warmup은 가능한 범위를 별도 계측한다.
출력은 새 로컬 폴더에 두고 COMPLETE/FAILED 상태를 남긴다. 독립 계산에 들어간 뒤에는
불필요한 모델 폴링을 하지 않는다.

## 완료 기준

- 32개 이름, 40,701 lookup, 141,607 후보가 보존되고 모든 lookup의 229일 결과가 일치한다.
- 사전 검증 및 5회 CPU/GPU 결과 불일치가 0이고 반복 정답 해시가 같다.
- 기존 완료 파일과 생성 코드 지문은 보존한다. CPU fallback을 GPU 성공으로 기록하지 않는다.
- 해석·준비·검증 비용과 측정하지 않은 생산 전체 작업의 경계를 구분해 보고한다.

## 실제 진행과 결과

입력 구조와 완료 run의 파티션 정답 경로를 확인하고 별도의 읽기 전용 loader와 묶음 측정기를
추가했다. production plan의 생성 계약·입력 지문·완료 partition pointer를 대조하며,
최종 결과에서도 입력·기준 정답·실험 코드 지문이 변하지 않았는지 확인한다.

실행 전 합성 데이터 통합 검사에서 진행 상태 파일의 반복 갱신이 write-once 규칙에 막히는
문제와 run manifest의 잘못된 receipt pointer를 놓치는 문제를 찾았다. 진행 상태만 원자적
교체로 갱신하고 완료 보고서는 write-once를 유지했다. 완료 partition reference와 manifest
pointer 전체 일치 검사를 추가했다. 보완 후 **14개 검사 11.693초 통과**. 실제 CUDA의 작은
전체 흐름, 조건 누락·정답 모든 필드·0개 조건·미매핑·generation 변경·입력 변조를 포함한다.

실제 측정은 `data/vd-gpu32-a`에서 **COMPLETE**로 끝났다. 입력·기준 정답 170개 파일과 측정
코드 지문이 실행 전후 및 최종 확인에서 일치했다. 기존 GPU prototype 4개 파일과 production
생성 계약도 보존했다. Python 58개 파일의 구문 검사를 통과했다.

## 측정 결과

CPU는 Intel Core Ultra 9 185H(16코어·22논리 프로세서), GPU는 RTX 4070 Laptop(8GB)이다.
CPU 비교 대상은 앞선 실험에서 개선한 범위 인덱스 구현이며 CPU 여러 코어나 EC2 두 대의
분산 실행을 비교한 것은 아니다. 기존 PyTorch 2.7.1+cu128·CUDA 12.8을 사용했다.

모든 행은 **32개 합계를 먼저 구한 뒤 5회 중간값**을 취했다. 정규화는 조건 해석·후보 순위
정리·Node 요청/응답을 포함하며 양쪽에 같은 실측 시간을 더했다. 숫자 계산은 GPU 측 준비와
메모리 전송도 포함한다. 결과 정리는 선택한 숫자를 버전·상태·기간으로 되돌리는 단계다.

## 정확성·자원·적용 범위

- 입력 32개 이름·141,607 후보·40,701 조건과 502,119개 기준 정답 구간을 모두 보존했다.
- 요구조건×후보 **137,010,465회** rank 포함 여부가 npm Range.test와 일치했다.
- 한 번의 전체 처리당 **9,320,529개 조건·날짜 조합**을 포괄한다. 사전 CPU/GPU 및 5회
  반복 결과의 버전·대상 package_id·상태·정규화 조건·시작/끝 날짜 불일치가 0건이고 해시가 같다.
- GPU 최고 allocated **70.69 MiB**, reserved **114 MiB**. PyTorch allocator 관측값이며
  CUDA context나 다른 앱을 포함한 시스템 전체 VRAM 수치는 아니다. 128 MiB 옵션은 묶음
  임시 계산 예산이고 전체 GPU 메모리의 강제 상한은 아니다.
- loader는 작은 합성 입력도 지원하는 최대 32개 bounded 도구다. 이번 실행은 지정한 기존
  run manifest SHA와 최종 32·40,701·141,607·229 수치 검사를 통해 기대 모집단을 확인했다.
- 기존 표본은 특성이 다른 패키지를 포함하지만 전체 10만 개의 무작위 대표 표본은 아니다.
  이 값에서 전체 선정 패키지 시간이나 생산 파이프라인의 배속을 바로 환산하지 않는다.
- 생산 집계·저장·재개 통합, EC2/Spark 비교, 전체 선정 실행과 DB 적재는 미실행이다.
