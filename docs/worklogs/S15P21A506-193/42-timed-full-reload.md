# 42. 날짜별 전체 재적재 시간 측정

## 요청과 작업 계획

사용자는 날짜별 구조의 전체 적재를 완료한 후 패키지·버전별 모든 날짜 조회를 측정하려 한다.
이번에는 이전에 적재한 부분을 비우고 처음부터 다시 실행하여 전체 적재 시간을 측정하도록 요청했다.

- 초기화 대상은 `pickage_267_full_defaulted.vd193_reload_20260912_ready01`의 이전 빠른 적재 결과 19일/43,616,976행 및 해당 private 실행 이력이다.
- 원본 Parquet와 참조 package/version/snapshot, 별도 public 테이블의 기존 43일은 초기화 대상이 아니다. 새 대상에는 이 43일도 포함하여 모든 229일/1,007,084,608행을 처음부터 저장한다.
- 기존 소스·코드 지문과 날짜별 저장 구조는 그대로 사용한다. 기존 job 로그/체크포인트는 삭제하지 않는다.
- 새 실행 기록은 `data/vd-db-reload-timed-20260912-2354/job/`, 설정은 상위 폴더 `config.json`이다.
- 사전 점검 → 대상 소유자/DB 실체/계획/receipt/프로세스/잠금 확인 → 명시한 테이블만 RESTRICT 삭제 → 빈 대상 확인 → 새 백그라운드 실행 순서다.
- DELETE/초기화 시간과 사전 점검은 적재 총시간과 분리한다. 적재 총시간에는 새 CLI의 입력 초기화·키 검사·날짜별 준비/저장/검증·최종 전수 행 수 검사·세션 정리를 포함한다.
- 총시간은 `time.perf_counter()`로 측정하며 `timing.json`에 시작/종료 UTC, 상태, 완료 날짜/행 수, 경과 초를 기록한다. 완료하지 못하면 성공 시간으로 표시하지 않는다.
- 정상 시작을 한 번 확인한 후 반복 모니터링하지 않는다. 전체 실행 제한 시간은 없고 기존 디스크 여유 검사·날짜별 중단/재개·절전 억제를 유지한다.
- 실제 그래프 조회 성능 측정은 전체 적재 완료 후의 별도 단계다. 이번 전체 적재 시간에는 포함하지 않는다.

## 초기화 안전 경계

전역 적재 잠금과 이전 job의 파일 잠금을 잡고, 저장된 계획 및 실제 private 테이블 구조/소유자를 대조한다.
외부 의존성을 지우는 CASCADE는 사용하지 않는다. private 실행/시도 이력의 순환 FK는 관련 테이블을 한 DROP 명령에 명시해 처리한다.
PostgreSQL 공식 문서는 같은 DROP에 포함된 객체끼리의 의존성에는 CASCADE가 필요하지 않다고 설명한다.
[의존성 처리 공식 문서](https://www.postgresql.org/docs/16/ddl-depend.html).

기존 기본 실행 스크립트의 config 위치는 유지하되 새 job/config를 가리키도록 갱신한다.
기존 config 원문은 새 실행 폴더의 `previous-config.json`에 보관한다.
이전 job은 초기화 전 기록이며 이후 기본 Status/Stop/Resume은 새 실행을 대상으로 한다.

## 결과

- 사전 점검 CHECKED: 97,745개 패키지 ID/이름, 7,822,819개 버전, 229개 날짜 전수 키 일치. 원본·생성 코드 지문 일치, 호스트 여유 약 1.224TB/DB 데이터 파일시스템 약 840GB.
- 2026-09-12 **23:57:31 KST** private 19일/43,616,976행 초기화 완료. 대상 schema 없음/0행 확인, public 이력과 서비스 DDL 보존. 잠금·구조 대조를 포함한 초기화 3.002초이며 적재 총시간과 별도다.
- **2026-09-12 23:58:09 KST** 전체 측정 시작, PID **310612**. `resume=false`, `SOURCE_OPEN`, stderr 0바이트와 프로세스 생존을 한 번 확인했다.
- 실행 코드 변경 없음. `timed-run.py`가 기존 CLI를 감싸 시간을 기록하며 성공/중단/예외/이미 적재된 날짜 검출/기록 덮어쓰기 거부를 작은 대체 실행으로 검증했다.
- 완료 시 `job/timing.json`의 `full_load_complete=true`, `all_dates_newly_loaded=true`, `completed_dates=229`, `completed_rows=1007084608`, `elapsed_seconds`를 함께 확인해야 처음부터 전체를 적재한 시간으로 사용할 수 있다.
- CLI의 최종 값/행 수/제약/이력 검증이 통과해도 public 서비스 전환이나 그래프 성능 측정이 끝났다는 뜻은 아니다.
- 중간 재부팅 등으로 기록이 RUNNING에 남으면 완료 시간으로 해석하지 않는다. 기존 Stop/Resume은 새 job을 대상으로 작동하지만, 중단 후 재개의 시간은 이번 무중단 전체 측정과 구분해야 한다.
- 시작 확인 당시에는 완료와 총시간이 미확인이었다. 이후 완료 결과는 아래에 기록했다. 기존 최대 날짜 실험의 일정 예산 3~4시간과 실제 측정 시간을 구분한다.
