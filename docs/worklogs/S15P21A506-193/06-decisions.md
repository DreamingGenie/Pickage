## 2026-09-10 적용한 구현 선택

- 사용자가 앞서 설명한 1·2번 진행을 요청하여 입력 기준 조사와 작은 정답 데이터 집계 핵심·테스트를 현재 범위로 삼았다. 7번 resolver 수정·실제 전체 계산·DB 적재는 포함하지 않는다.
- 입력 원본은 이전 계산 위치에서 읽기 전용으로 참조한다. 파일 복사·이동 없이 조사 증거를 현재 워크스페이스에 남긴다. 이 선택은 PARTIAL 입력의 정상 계산·게시 승인이 아니다.
- 기존 Python 환경의 DuckDB 1.5.5를 재사용한다. SQL에서 복합 edge를 DISTINCT한 뒤 target별로 집계하여 모든 관계를 Python 리스트로 모으지 않는다.
- 집계 핵심과 생산용 manifest·파일·모집단 검증 어댑터를 구분한다. 합성 데이터 테스트의 `COMPLETE`·준비 상태를 실제 입력 승인 증거로 사용하지 않는다.
- 배포 시각은 날짜로 축소하지 않고 정확한 snapshot 시각까지 비교한다. 정규화된 입력에서 timezone이 있는 timestamp를 요구하며 원천의 timezone 없는 값 변환은 후속 어댑터에서 명시적으로 처리한다.

## 진단용 전체 실행 전 성능 검토

2026-09-10 표본 비교에서 기존 `SELECT DISTINCT` 후 target별 `GROUP BY`를 유지하고
DuckDB를 8스레드·8GB로 실행했을 때 평균 1.2130초를 측정했다. 같은 SQL의 4스레드·2GB는
2.4691초였다. 2,400만 관계·target 680,282개의 값은 모두 일치했다. 이는 각 2회의 warm-cache
표본 결과이며 CPU와 메모리 각각의 기여를 분리하거나 전수 spill 성능을 측정한 것은 아니다.

다음 진단 실행에는 기존 DISTINCT 의미를 보존하고 8스레드·8GB 설정을 우선 적용할 것을 권장한다.
COUNT(DISTINCT 복합 source 키) 표현으로 바꾸는 것 자체의 이득은 이번 표본에서 확인되지 않았다.
추가 코드 후보는 검증 조건의 동일 조회 통합과 정상 집계에서 target 초기화/UPDATE를 LEFT JOIN
한 번으로 만드는 것이다. 이번에는 적용하지 않았다. 진단 집계는 해석된 관계에 등장한 target만
대상으로 하며, 전체 모집단의 0을 생성하지 않는다. 실제 edge 유일성을 전수 확인하지 않고
DISTINCT를 제거하는 최적화는 사용하지 않는다.

## D-22 — 다운로드 선정 패키지만 저장하고 전체 source 버전을 집계

2026-09-11 사용자 결정: “10만개에 대해서만 저장하되 dependents_count수는 너가 말한대로
전체 패키지가 참조하는 수로 가자.” 직전 안내의 0 포함·전체 유효 버전 기준을 적용한다.

- 저장 target은 다운로드 작업의 `targets_top100k_20260902.csv`의 고유 이름 99,996개로
  제한한다. 원본 100,000행의 중복은 이름 기준으로 제거한다. CSV SHA는
  `c21416d44bf8abaed63ddd35c44daae9c5d8ac915b388098eb8b1f7817f9525a`다.
- source는 선정 목록으로 제한하지 않는다. 기존 정책에 맞는 전체 source package/version 중
  해당 스냅샷까지 배포된 버전의 일반 dependencies를 사용한다. 직접 해석된 관계에 대해
  `DISTINCT(source_package_id, source_version)`를 세며 한 패키지의 여러 버전도 각각 센다.
- target도 대표 버전 하나로 줄이지 않는다. 선정 패키지의 전체 유효 후보 이력에서 각 시각의
  요구조건을 해석한다. 미해석 PARTIAL·배포일 NULL 제외 등 기존 해석 정책은 유지한다.
- 현재 H1에서 선정 이름 97,743개에 유효 target 버전 7,822,819개가 있다. 229개 날짜에
  0을 포함하면 1,007,084,608개 키다. 2,253개 이름은 현 입력의 유효 후보가 없으며 가상의
  버전/ID를 만들지 않는다. [규모 실측](evidence/download-target-version-snapshot-size.json)
- Parquet는 양수 count와 선정 target 모집단·날짜별 완료/품질 기록을 저장한다. 성공 관계
  기준 0은 날짜의 계산 완료와 유효 후보 존재를 확인한 경우에만 적용하며, 미계산 날짜나
  선정 모집단 밖 이름을 0으로 간주하지 않는다.
- D-18/D-20의 전체 패키지 69.7억 행 저장 제안은 새 실행에 적용하지 않는다. 최종 저장 대상은
  D-22를 따른다. 원본과 기존 H1/H5-A 전체 모집단 결과는 보존하고 새 scope로 연결한다.

이번 턴은 결정·계획 기록이며 필터 구현, 실제 count 계산, DB 적재를 실행하지 않았다.
