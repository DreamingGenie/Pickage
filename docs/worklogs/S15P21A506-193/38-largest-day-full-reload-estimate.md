# 38. 최대 하루치 전체 흐름 측정과 전체 재적재 예상

## 요청과 범위

2026-09-12 사용자 요청: 행 수가 가장 큰 날짜를 입력 생성부터 측정하고, 기존 43일도 모두 다시 넣는다고 가정한 전체 소요 시간을 계산한다.

- 기존 Parquet 집계 결과는 재사용한다. 의존 관계 집계 자체를 다시 계산하는 시간은 포함하지 않는다.
- 전체 재적재는 예상만 계산하며 실제 서비스 행 삭제·재적재·DDL 전환은 수행하지 않는다.
- 229개 날짜의 0 포함 실제 행 수 분포를 확인하고, 최대 날짜의 입력 생성·COPY·제약 검증·연결·결과 검증 시간을 측정한다.
- 공통 입력 초기화는 1회 비용, 날짜별 파일 생성/검증 및 DB 작업은 반복 비용으로 구분한다. 기존 실험의 비교용 source/legacy 테이블과 재개 테스트 비용도 표시한다.
- 최대 날짜는 반복 측정하고, 날짜별 고정 비용과 행 수 의존 비용을 구분하기 위해 앞서 사용한 작은 날짜도 같은 실행기에서 측정한다. 전체 예상은 단순 패키지 수 곱셈이 아닌 실제 총행 수와 날짜 수로 계산한다.
- 결과 범위와 캐시·메모리·공유 디스크·운영 ETL 연동의 미측정 부분을 함께 기록한다.

## 진행 결과

### 측정 범위와 실제 행 수

`data/vd-db-largest-scale-20260912-01`에서 최대/작은/작은/최대 순서로 실행했다. 최대 날짜는 `2026-08-31` 7,822,819행, 비교 날짜는 `2023-03-06` 2,827,680행이다.

전체 targets의 birth_index별 버전 수를 누적하고 각 날짜의 published quality와 일치함을 확인했다. 전체 229일의 합계는 **1,007,084,608행**이며, 가장 작은 날짜는 2,169,881행이다. 이미 적재된 43일/106,346,692행도 이 합계에 포함하며 차감하지 않는다.

여기서 전체 재적재는 **비어 있는 새 날짜별 partition 대상에 229일을 모두 다시 쓰는 가정**이다. 기존 같은 테이블에 중복 INSERT하거나 실제 43일을 삭제하지 않았다. source/참조 테이블은 기존 것을 유지하고, 원본 Parquet 집계 자체는 다시 계산하지 않는다.

### 실제 시간

공통 초기화 14.280초, 전체 97,745개 패키지/7,822,819개 버전/229일 키 검증과 초기 원본 재검사 57.004초. 합계 **71.285초는 한 번만** 반영한다.

| 순서 | 날짜/행 수 | Parquet에서 입력 생성·검사 | DB 실험 흐름 | 합계 |
| --- | --- | ---: | ---: | ---: |
| 1 | 2026-08-31 / 7,822,819 | 9.901초 | 39.038초 | 48.940초 |
| 2 | 2023-03-06 / 2,827,680 | 7.113초 | 21.351초 | 28.463초 |
| 3 | 2023-03-06 / 2,827,680 | 6.216초 | 21.470초 | 27.686초 |
| 4 | 2026-08-31 / 7,822,819 | 7.274초 | 45.550초 | 52.824초 |

입력 생성 시간은 FullSource.prepare_date의 0 복원, 전체 값/품질 검사, 정렬된 TSV 생성, 원본 recheck를 포함한다. 원래 loader 코드를 수정하지 않았다.

DB 실험 흐름은 입력 hash/행 수 검사, 비교용 source COPY 및 PK/통계, legacy 1,000행 fixture 준비, 실제 날짜 COPY/PK/FK/전수 검증, 연결·journal 게시, 새 세션 재개 검사·최종 대조·cleanup을 모두 포함한다. 비교 source/legacy/reverification/drop은 실제 적재기에서 일부 제거될 수 있는 실험 비용이지만, 예상에서는 보수적으로 매 날짜 비용에 그대로 포함했다. 입력 보관용 파일 복사(약 0.05~0.16초)는 실험 아카이브 비용이라 날짜 적재 시간에는 포함하지 않는다.

최대 날짜의 세부 관측은 COPY 7.501/10.848초, PK 생성 1.851/1.654초, FK 검증 9.809/10.204초, 연결 5.155/3.973ms였다. 이 항목들은 DB 실험 흐름에 포함돼 있으며 합계에 다시 더하지 않는다.

### 완료 직전 원본 재검사 비용 보완

원래 `historical_db_load.publish_date.before_commit`은 prepare_date 내부 검사와 별개로 source.recheck를 한 번 더 수행한다. partition probe에는 이 callback이 아직 연결되지 않았으므로 이 비용을 빼먹지 않도록 따로 3회 측정했다.

- 3.941 / 3.843 / 3.712초, 평균 **3.832초/일**.
- 전체에는 229회, 평균 **877.565초(약 14분 38초)**를 추가한다.
- 이 별도 실험의 source 초기화 시간은 이미 공통 초기화에 반영돼 있으므로 또 더하지 않는다.
- 실제 commit 직전에 통합해서 실행한 측정은 아니며, 같은 원본 검사 함수를 별도로 실행해 비용을 가산했다.

### 전체 재적재 예상

회계식은 다음과 같다.

```text
전체 예상 = 공통 source 초기화/키 검사 1회
          + 모든 날짜의 입력 생성·검사
          + 모든 날짜의 DB 실험 흐름
          + 모든 날짜의 완료 직전 원본 재검사
```

두 행 수 구간에서 각각 2회 얻은 시간으로 단계별 `날짜 고정 비용 + 행 수 × 비례 비용`의 비음수 모델을 맞추고, 실제 229개 날짜/1,007,084,608행에 적용했다. 음수 시간이나 음수 증가율은 허용하지 않는다. 초기 43일은 작은 표본보다 작으므로 해당 구간은 외삽이며, 이것은 검증된 성능 법칙이나 신뢰구간이 아니다.

| 항목 | 전체 환산 |
| --- | ---: |
| 공통 초기화·키 검사 | 71.285초 |
| 날짜별 입력 생성·검사 | 1,664.562초 |
| 날짜별 DB 실험 흐름 | 6,406.143초 |
| 추가 완료 직전 원본 검사 | 877.565초 |
| **측정 모델 중심값** | **9,019.555초 = 약 2시간 30분** |

작은/큰 측정값 조합에 따른 민감도는 약 2시간 27분~2시간 34분이나, 표본 4회의 좁은 범위일 뿐 실제 전체 실행의 불확실성 범위로 사용하지 않는다.

더 보수적으로 **모든 229일이 가장 큰 날짜의 느린 측정 52.824초만큼 걸린다**고 가정하고, 추가 원본 검사도 최댓값 3.941초씩 더하면 **13,070.398초 = 약 3시간 38분**이다. 최대 날짜보다 더 느려질 가능성을 배제한 보장 상한은 아니다.

현재 노트북/로컬 DB에서 개선 경로를 적용한 전체 재적재의 **일정상 예산은 3~4시간**으로 제시한다. 중심 모델 약 2시간 30분과 위 보수적 가정을 함께 근거로 삼는다.

### 자원·검증·한계

- 최대 날짜 counts TSV 221,203,502바이트(약 221MB). 4회 입력을 보관한 실험 파일은 측정 시 약 1.06GB였다. 실험 DB 테이블 크기는 실행 중 한 관찰 시점에 약 665MB였으며 피크로 주장하지 않는다. 임시 디스크 피크를 연속 측정하지는 않았다.
- PostgreSQL 컨테이너 메모리는 5초 간격 44개 표본 중 최대 약 **9.76GiB/16GiB**. 파일 캐시를 포함한 cgroup 메모리이며 DB 프로세스 RSS나 엄밀한 순간 최대값과 다르다.
- 4회 모두 정확한 행/값 일치, FK/PK 재사용, ATTACH 중 추가 읽기 0, 새 세션 재개 시 재삽입 0, cleanup 완료.
- 데이터 증가 효과는 관측했으나 실제 229개 partition을 유지하며 10억 행을 끝까지 쌓는 지속 실행은 하지 않았다. 누적 partition·WAL/checkpoint·캐시·다른 작업 I/O의 장시간 영향은 미검증이다.
- 실제 서비스 ETL execution/attempt/current 연결과 잠금, API 부하, 통계 갱신, 배포/기존 데이터 제거·테이블 전환 비용은 아직 측정하지 않았다. 이번 숫자는 **새 빈 대상의 전처리+partition 적재 경로 예상**이며 운영 완료 시각의 보장이 아니다.
- 기존 43일은 실제로 삭제하거나 다시 적재하지 않았다. 기존 게시 이력·source/loader 계약 검사 통과, 실험 세션/schema 정리 확인.
- 입력/namespace/COPY/예상 모델 관련 unittest 11개 통과(0.521초), diff 공백 검사 통과. 독립 검토에서 전체 합계·229일 가산·추가 원본 검사의 중복 계상 없음을 확인했다.
- 추가 877.565초는 `source.recheck()` 자체의 비용이다. before_commit의 코드 지문·manifest 파일 hash 등 callback 전체를 재현한 비용으로 표현하지 않는다. 실제 통합 경로의 비용은 적용 후 최종 확인한다.
