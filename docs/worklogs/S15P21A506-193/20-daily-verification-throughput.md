# 20. 날짜별 검증 누적 계산과 8·16·32개 처리량 평가

상태: O-4 구현·기존 실제 출력 대조·전체 249개 회귀 통과. O-5 8·16·32개 전체 source 표본의 준비·계산·저장·검증 완료.

## 변경 범위와 순서

2026-09-11 사용자가 명시한 4번·5번은 [18 계획](18-performance-improvement-plan.md)의
O-4 날짜별 검증과 O-5 처리량 평가다. 조회/직렬화 또는 버전 검색 알고리즘 개선은 이번 범위가 아니다.

1. 현재 코드·작은 실제 입력·완료 결과의 지문을 고정한다.
2. production 전용 cache helper에서 target birth 누적합과 count 구간 시작/종료 변화량으로
   전체 기준일의 target 수·양수 버전 수·count 합계를 한 번 계산한다. 날짜별 최대 count는
   구간별 최댓값의 범위 갱신으로 계산한다.
3. production 날짜 writer와 검증기에 이 합계를 연결한다. 실제 Parquet의 모든 값 대조,
   schema·key·SHA·변조·재개 검증을 유지한다. 같은 실행의 끝에는 cache bytes를 다시 검사한다.
4. 기존 6개 target/lodash의 고정 cache로 변경 전후 값을 대조하고 저장·검증 시간을 분리 측정한다.
5. workload로 정한 중첩 8→16→32개 target의 모든 source·후보·229일을 순차 처리한다.
   입력 준비→계산→파일 저장→최종 검증 단계별 시간, 메모리·임시 디스크를 기록한다.
6. 대표성·비선형 비용·제외한 극단값을 명시하고 전체 예상 시간의 근거 또는 부족한 측정을 보고한다.

기준 지문: `data/vd-date-baseline-20260911T043619Z/baseline.json`.
기존 H1/H5-A/H4, prepared adapter, SemVer worker, 집계 모듈은 보존한다.
production helper·writer·runner의 변경 지문은 새 실행에 포함한다. 이전 manifest를 고치지 않는다.
전체 선정 입력/계산, EC2/Spark, H6의 0 보완·DB key 연결, DB 적재, commit/push는 미실행 범위다.

## 검증 기준

- 날짜별 합계 및 출력 count·품질은 기존 구현과 차이 0건.
- 최대 count는 덧셈으로 누적하지 않는다. 겹친 구간·끝점·최대값 하락도 기존 직접 계산과 대조한다.
- legacy cache의 schema, population, interval, quality, manifest 검증 항목을 대응표로 보존한다.
- 입력 중도 변조, 검사 직후 출력 변조, 누락/추가 파일, 재개 변조와 다른 생성 코드를 거부한다.
- 전체 데이터를 다시 합산하는 횟수가 날짜 수에 비례하지 않는지 확인한다.
- 각 pilot은 독립 프로세스·동일 4 threads/4GB 설정으로 순차 실행한다. 1시간 경과 종료를 넣지 않는다.
- 표본 수에 비례해서 전체 시간을 단순 곱하지 않는다. 최종 sparse 파일 검증과 H6/DB 전처리 시간을 구분한다.

## 실제 작업·이슈·결과

### O-4 구현

`historical_production_cache.py`는 기존 cache 검증의 schema·키·구간·품질 상태·보존식·manifest
검사를 유지하고 날짜별 대형 테이블 조회를 누적 합계 참조로 바꾼다. target birth를 묶고,
count 구간을 `(start_index,end_index)`별 양수 버전 수·count 합·최댓값으로 축약한다.
축약 행은 최대 4,096개씩 읽는다. 합계는 시작/끝 delta, 최댓값은 작은 범위 max 트리로 계산한다.
원본 count 구간 전체를 Python 리스트에 올리거나 구간×229일 행을 만들지 않는다.

`historical_production_daily.py`는 계산한 합계를 기대 품질에 사용한다. 실제 count·품질·이력
Parquet는 기존과 같이 양방향 `EXCEPT ALL`로 모든 값을 비교한다. writer는 새 파일 검사 직후
SHA·크기를 재확인하고, 실행 종료 시 cache bytes를 다시 검사한다. 재개·별도 검증도 새로 검사한다.
합계는 각 cache 검증/날짜 writer 단계에서 한 번에 계산하며 날짜 수만큼 대형 테이블을 재조회하지 않는다.

새 cache에는 `production_cache_sha256`를 기록한다. 이전 cache는 원래 manifest 그대로
읽을 수 있지만, 새 helper로 생성된 manifest의 helper SHA가 다르면 거부한다. runner와
daily plan에도 cache·daily helper SHA를 추가해 새로운 코드로 이전 run을 혼합 재개하지 않는다.

### 동일 6개 target·229일의 O-4 실측

변경 전 production writer의 원본 파일을 기준 디렉터리에서 읽어 비교했다. 비교 대상은
이미 앞 단계에서 fresh 날짜 중복 검증을 제거한 writer다. 그 앞 단계 개선을 다시 합산하지 않는다.
알고리즘마다 새 프로세스·새 출력 폴더를 사용했고 실행 순서를 교대했다. 각 3회 중간값이다.

| 측정 구간 | 변경 전 | 변경 후 | 감소 |
| --- | ---: | ---: | ---: |
| 공통 cache 검증 | 1.015초 | 0.141초 | 86.11% |
| 229일 파일 저장·검증 전체 | 37.094초 | 34.906초 | 5.90% |
| 저장 결과 별도 전수 검증 | 17.625초 | 14.015초 | 20.48% |

각 반복의 229×3개 실제 파일 값을 비교했고 총 2,061개 파일 대조가 모두 일치했다.
quality에서는 실행 plan SHA만, lineage에서는 실행 plan SHA와 생성 코드 SHA만 제외했다.
count는 모든 컬럼을 비교했고 cache SHA·입력·정책 값은 제외하지 않았다.
위 시간은 입력 준비·버전 해석·count 집계·DB 적재를 포함하지 않는다.
관측 시점/시스템 상태가 다른 과거 25.781초 실행과 직접 개선율을 계산하지 않는다.

6개 표본의 build 3회는 기존 `39.016/37.094/33.516초`, 개선 후
`34.906/36.843/33.922초`였다. 마지막 반복에서는 약 0.4초 느렸으므로 5.9%는 이 표본의
중간값 차이다. 최초 cache 검증과 별도 전수 검증은 세 반복 모두 개선됐다.

lodash cache(후보 113행·count 구간 2,309행)도 동일한 229일·687개 파일 대조를 통과했다.
기존 6개 cache는 후보 49,936행·count 구간 402행이다.

| lodash 측정 구간 | 변경 전 | 변경 후 | 감소 |
| --- | ---: | ---: | ---: |
| 공통 cache 검증 | 1.156초 | 0.172초 | 85.1% |
| 229일 파일 저장·검증 전체 | 42.735초 | 31.171초 | 27.1% |
| 저장 결과 별도 전수 검증 | 22.265초 | 12.969초 | 41.8% |

lodash는 기존→개선 순서 한 번만 측정한 관측값이다. 순서와 파일 cache 영향을 분리한
반복 중간값으로 해석하지 않는다. [6개 비교 증거](evidence/daily-verification-six-comparison.json),
[lodash 비교 증거](evidence/daily-verification-lodash-comparison.json).
이 검증은 `NORMALIZED_CACHE_AND_DAILY_ARTIFACTS`이며 원본 SemVer 재해석 정답 대조가 아니다.

### O-5 표본·측정 설계

선정 파일과 SHA는 [표본 목록](evidence/daily-throughput-selection.json)에 보존했다.
8개는 기존 6개에 lodash·semver를 더한 목록이며, 16개·32개는 앞 목록을 모두 포함한다.
조건 수나 source를 자르지 않고 선택한 패키지의 모든 후보·모든 source 선언을 처리한다.

| 표본 | 후보 버전 V | 고유 요구조건 Q | 원본 선언 D | V×Q 검사량 지표 |
| --- | ---: | ---: | ---: | ---: |
| 8개 | 50,166 | 1,508 | 4,000,238 | 195,162 |
| 16개 | 99,976 | 23,340 | 9,916,089 | 86,349,824 |
| 32개 | 141,607 | 40,701 | 10,118,750 | 137,156,499 |
| 전체 선정 목록 | 7,822,819 | 4,220,751 | 239,556,025 | 4,190,303,911 |

32개는 선정 이름의 약 0.032%, 후보 1.81%, 선언 4.22%, V×Q 지표 3.27%다.
극단적인 세 패키지 `@octopusdeploy/type-utils`, `@octopusdeploy/design-system-tokens`,
`@octopusdeploy/design-system-icons`는 이번 표본에서 제외했다. 이 세 패키지만 V×Q 지표의
51.52%를 차지한다. 그 지표는 버전 해석 비용의 대용값이며 229일을 곱하거나 실제 시간으로 취급하지 않는다.
기존 요청 한도 2,000,000은 패키지 전체가 아니라 batch당 제한이다.

각 크기는 입력 준비·run·별도 verify를 별도 프로세스로 순차 실행한다. Python과 Node 자식의
합산 RSS·CPU 및 작업 디렉터리 scratch/작업 DB 크기를 1초 간격으로 기록한다. 짧게 존재하는
프로세스나 순간 peak는 놓칠 수 있는 표본 관측값이다. DuckDB는 4 threads/4GB/40GB scratch,
자원 감시는 합산 RSS 12GiB/scratch 64GiB/여유 디스크 20GiB의 soft guard를 사용한다.
시간 경과만으로 종료하는 제한은 없다. 229일 합계 검증용 최대값 트리는 SemVer 검색 알고리즘 변경이 아니다.

디스크 peak는 같은 표본의 이전 단계 산출물을 포함한 누적 크기다. 시작/끝 크기와 시작 대비
최고 증가량을 함께 저장한다. 측정기 코드 SHA도 고정하고 단계 사이·종료 시 검사한다.
prepare 결과의 target 이름/후보/요구조건/원본 선언 행 수를 표본의 V/Q/D와 대조한다.
자원값은 1초 관측으로 포착한 값이며 실제 순간 최고 사용량을 보장하지 않는다.

### 발견한 문제와 처리

- helper 초안에서 원본 구간 전체를 Python에 가져오고 일부 legacy 품질 검사를 누락한 문제가
  발견됐다. 구간 경계별 축약·나누어 읽기로 교체하고 기존 검사 전 항목을 대응시켰다.
- 검증 테스트가 중복 target을 삭제하면서 정상 원본까지 삭제하거나, 변조용 Parquet 읽기에서
  디렉터리명을 추가 컬럼으로 읽는 문제가 있었다. fixture 복원과 `hive_partitioning=false`로 보완했다.
- 측정 도구의 CLI 인자 이름·대조 SQL 괄호 오류를 수정했다. 실패 로그는 남겼고,
  완료된 첫 반복은 입력·생성 코드·run SHA를 확인한 후 실제 값 대조를 다시 수행했다.
- 독립 코드 검토는 correctness blocker 없이 WATCH였다. 종료 시 bytes 재검사의 I/O 비용과
  관측 자원값의 한계는 성능 결과에 포함해 해석한다.
- O-5 실행 전 검토에서 profile SHA 전사 오타, 측정기 SHA 미고정, 누적 디스크의 모호한
  표기를 고쳤다. 기존 profile manifest는 변경하지 않고 실제 파일 SHA를 표본 목록에 반영했다.
- 첫 전체 회귀 검사 249개 중 기존 H4 자식 프로세스 종료 테스트가 실패했다. Windows venv
  redirector만 종료되어 실제 Python이 잠금을 보유한 것이 원인이었다. 실패 로그를 보존하고
  실제 기본 Python과 같은 venv 라이브러리 경로로 재실행했다. H4 코드는 바꾸지 않았다.

### O-5 실제 결과

`data/vd-pilot-a`에서 8→16→32 순서로 각 한 번 실행했다. 모두 `SAMPLE/COMPLETE`,
229개 기준일 검증 통과, `PARTIAL/ready_for_load=false`다. 실제 prepared 행 수는 위 표의
V/Q/D 및 이름 수와 정확히 일치한다. source 선언을 잘라 실행하지 않았다.
세 run 모두 현재 생성 코드 지문과 일치하고, 완료 manifest/cache/partition 영수증 SHA를 확인했다.
[단계·자원·코드·출력 이력 증거](evidence/daily-throughput-results.json).

| 표본 | 입력 준비 | 계산·저장 | 별도 전수 검증 | 합계 |
| --- | ---: | ---: | ---: | ---: |
| 8개 | 85.30초 | 43.93초 | 18.33초 | 147.56초 (2분 28초) |
| 16개 | 116.12초 | 194.76초 | 16.42초 | 327.30초 (5분 27초) |
| 32개 | 68.40초 | 230.67초 | 16.76초 | 315.83초 (5분 16초) |

위 시간은 worker 내부에서 측정한 각 단계 전체 시간이다. 프로세스 시작·종료 관측 간격까지
포함한 부모 측정 합계는 각각 151.05/331.02/318.96초다. 입력 준비는 크기별 비교를 위해
세 번 실행했으며 실제 전체 배치에서 패키지마다 준비를 반복하는 구조가 아니다.

16→32에서 전체 시간이 줄었다고 크기 증가가 속도 개선이라고 해석하지 않는다.
캐시 상태·CPU/실행환경 영향을 분리하지 않은 단일 순차 측정이며 준비 단계의 변화가 특히 크다.
추출/정합성 검사 시간은 각각 46.88/63.41/35.23초, 최초+종료 입력 검증은
34.58/43.36/27.53초, 정렬·저장은 3.28/8.78/5.14초였다. O-5는 변경 전후 개선율 실험이 아니며,
O-4 변경 전후 비교는 앞의 동일 cache 실험으로만 판단한다.

| 계산·저장 내부 구간 | 8개 | 16개 | 32개 |
| --- | ---: | ---: | ---: |
| 후보 조회·요청 구성·npm 처리·응답 정리 | 1.36초 | 132.73초 | 174.18초 |
| 가중치 집계 핵심 | 6.06초 | 20.38초 | 18.34초 |

표에 없는 실행 시작·입력 검사·partition 파일 저장/해시 등도 계산·저장 전체 시간에 포함된다.

실제 candidate_checks는 137,010,465회다. 관계 행을 날짜마다 만드는 비용이 이번 병목은 아니다.

32개 중 `@lightdash/common` 하나의 해석 구간이 65.53초, 가중치 집계는 약 0.52초였다.

### 단계 시간의 의미와 전체 시간 추정 경계

입력 progress의 `VERIFY_PINNED_INPUTS→EXTRACT_SELECTED_DECLARATIONS`는 검증·view 준비,
`EXTRACT→WRITE_PREPARED_INPUTS`는 추출·정합성 검사, `WRITE→REVERIFY_PINNED_INPUTS`는
정렬·Parquet 저장, `REVERIFY→PREPARATION_COMPLETE`는 재검증·해시·manifest다.

run progress의 각 `RESOLVE_PARTITION→AGGREGATE_PARTITION`은 후보/요구조건 조회,
요청 JSON 구성, npm worker 왕복, 응답 삽입을 포함한다. `worker_metrics.request_seconds`는
그 안의 요청 왕복 부분이므로 위 해석 구간과 더하지 않는다. 실제 집계 핵심은 각 receipt의
`metrics.aggregation.seconds`다. partition 전체 시간에서 두 구간을 뺀 값은 저장·해시 등의
근사 잔차이며 이벤트 경계의 작은 오차가 있다.

`FINALIZE_INTERVAL_CACHE→WRITE_SNAPSHOT_PARQUETS`는 전역 병합·cache 생성,
`WRITE_SNAPSHOT_PARQUETS→RUN_COMPLETE`는 날짜 파일 저장과 종료 시 입력 재검증·manifest다.
별도 verify는 입력 해시·partition→cache 파생값·실제 날짜 파일을 확인하는 전체 시간이다.
매 날짜 원본 npm 해석기를 다시 실행하는 독립 정답 계산과는 구분한다.

전체 비용은 준비 + 패키지별 조회/해석 + 선언/이벤트 집계 + 전역 병합 + 날짜 출력 + 검증으로
분해해야 한다. 후보 수 V, 요구조건 수 Q, 원본 선언 수 D, 실제 candidate_checks, 요청 횟수,
출력 version-days/bytes가 서로 다른 비용을 설명한다. Q×V는 실제 검사량과 동일하지 않다.
미해석 선언이나 파싱 실패가 있고, Q가 0이어도 패키지별 조회는 실행한다.

이번 32개 측정만으로 전체 99,996개 시간을 좁은 범위로 확정하지 않는다. 전체 검사량 지표의
51.52%인 극단 3개를 측정하지 않았고, 거의 10만 이름에 반복되는 조회, 전체 크기의 전역
병합·spill·날짜 출력량을 측정하지 않았다. 입력 준비를 패키지 수만큼 곱하거나 전체 시간을
`99,996÷32`로 곱하지 않는다. 실측은 로컬 4 threads/4GB 설정이며 EC2 두 대의 시간은 아니다.
H6의 0 보완·DB key 연결 및 DB 적재는 이 측정에 포함하지 않는다.
