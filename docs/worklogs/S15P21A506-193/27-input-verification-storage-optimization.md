# 27. 입력 준비·검증·날짜 저장 비용 개선

## 승인 범위와 계획

2026-09-11 사용자가 승인한 후속 작업이다. 이전 P0~P2 결과에서 늘어난 입력 준비·검증 비용을 분석하고
반복 입력 스캔과 검증을 줄인 뒤 P3 저장 구조를 구현한다. 전체 선정 계산·GPU 큐·EC2·DB 적재·Jira·commit·push는 포함하지 않는다.

1. 이전 생성 코드와 결과 지문을 동결하고 이전 입력 준비 104.246초의 세부 비용을 새 측정에서 분리한다.
2. 한 번의 분류로 입력을 물리 분할하고 빈 partition 파일과 반복 연결/검사 비용을 줄인다.
3. 실제 내용·소유권·변조·재개 검사를 유지하면서 동일 파일 검사를 합친다.
4. 여러 날짜의 count를 partition 단위 파일에 저장하고 날짜 조회·0 복원·독립 행 검증을 제공한다.
   기존 계획의 날짜×partition 다수 파일보다 최신 사용자 승인 설명인 여러 날짜 묶음 저장을 따른다.
5. 작은 실제 입력/합성 회귀를 통과한 뒤 32개×229일을 기존/개선 교대 순서로 반복 측정한다.
   원본 준비 비용, 계산/저장, 별도 검증, 개발용 의미 대조를 분리하고 전체 약 10만 개 시간으로 환산하지 않는다.

## 결과 수락 기준

- 기존 13개 의미 그룹을 양방향 실제 행으로 비교하여 차이 0건; lineage는 각 산출물의 계약으로 별도 검증.
- 명시한 target 범위·전체 source·dependencies·NULL 배포일 제외·PARTIAL 정책 유지.
- 입력/출력 변조 및 누락, 중단 후 재개, 중복 target/날짜, 0 복원 오류 검출.
- 이전 생성 코드와 저장된 결과 지문 불변. 새 생성 계약으로 이전 manifest를 바꿔 재사용하지 않음.
- 동일 CPU/메모리 예산 및 각 구성 반복 관측을 사용하고 측정 변동·미측정 비용을 표시.

## 실제 진행

### 구현

- `historical_parallel_input` v2: 각 입력 테이블을 한 번의 partitioned COPY로 분류한다. 여러 조각이 생긴
  묶음만 합치며, 빈 묶음은 manifest에 `EMPTY`와 0행을 기록하고 파일을 만들지 않는다.
- 같은 연결에서 파일 schema·행 수를 검사한다. coordinator가 전체 내용·소유권을 검증한 뒤 worker는
  자신에게 배정된 네 파일의 경로·바이트 SHA를 실행 전후에 확인한다. 전역 내용 검증은 유지한다.
- 선택형 `history_layout=grouped`: 묶음마다 모든 날짜의 양수 count를 한 파일로 저장하고,
  날짜별 품질 229행은 한 파일로 저장한다. 이력은 고정 cache SHA·lineage·calendar·생성 계약을 담은 run plan에 보존한다.
- 저장기와 독립 검증기는 서로 다른 날짜 확장 SQL을 사용한다. 실제 저장 행을 양방향 `EXCEPT ALL`로 확인하며
  날짜별 합계는 기존 누적 합계 계산을 재사용한다.
- 완료 pointer가 승인한 UUID attempt만 읽는다. 수락 전 중단된 attempt는 보존하고 새 attempt로 재시도한다.
  완료 후 재개는 manifest·파일을 덮어쓰지 않으며, 커널 run lock으로 동시 writer를 차단한다.

### 입력 준비 측정 — 각 방식 1회

이전 방식을 `data/vd-p3-base/pipeline`에 바이트 그대로 동결해 실행했다. 이전 manifest의 생성 SHA를
새 코드 SHA로 바꾸지 않았다. 직접 원본을 준비한 같은 32개 표본이며, 아래 단일 관측에 반복 안정성을 주장하지 않는다.

| 단계 | 이전 P0~P2 | 개선 입력 v2 |
| --- | ---: | ---: |
| 입력 준비 전체 | 92.899초 | 72.205초 |
| 공통 테이블 준비 | 34.621초 | 34.777초 |
| 분할 파일 저장·해당 metadata 검사 포함 | 17.011초 | 3.934초 |
| 생성 후 입력 검증 | 12.536초 | 4.412초 |
| 파일 metadata 함수 호출 | 1,024회 | 216회 |
| 네 종류 입력 Parquet 수 | 512개 | 108개 |

전체 준비 시간은 22.3% 감소했다. 단계 값은 호출 포함 시간이므로 중첩되는 metadata 시간을 다시 합산하지 않는다.
원본 SHA 확인·H1 검증·전체 source 테이블 준비 비용은 남아 있다. 이 준비는 실행 입력을 만들 때 한 번 수행한다.
worker를 늘리거나 개별 패키지를 처리할 때 원본 준비를 다시 실행하는 구조는 아니다.

### 조회 계약

`historical_parallel_writer.open_counts(con, run_dir, manifest_sha256, snapshot_at='YYYY-MM-DD')`는
해당 날짜의 양수 count를 `counts` view로 연다. `include_zero=True`를 명시하면 그 날짜에 존재했던
cache target 버전 목록과 결합해 0을 복원한다. 날짜를 생략하면 모든 날짜를 조회하므로, 전체 선정 범위에서는
결과 행 수가 커질 수 있다. 저장되지 않은 count를 임의로 0으로 간주하지 않고 완료 manifest와 고정 cache를 확인한다.

`open_quality`는 날짜별 계산·해석 상태와 품질을 `quality` view로 연다. `PARTIAL`, 전체 source 유지,
선정 target 제한, NULL 배포일 제외, `ready_for_load=false` 정책은 같다. 기존 일별 writer는 기본값으로 유지한다.

### 검증과 측정 중 발견한 문제

- partitioned COPY의 staging 부모가 없어 첫 입력 테스트가 실패했다. 새 출력 내부에 staging 부모를 만든 뒤 재검증했다.
- grouped cache 바이트 검증 호출의 manifest 인자가 누락돼 첫 통합 테스트가 실패했다. 인자를 고쳤다.
  실행 중 생성 코드가 바뀐 테스트는 해당 실행을 폐기하고 코드 변경이 없는 상태에서 다시 실행했다.
- 최종 통합/입력/프로세스 검사 15개가 50.849초에 통과했다. grouped 13개 의미 그룹 대조도 포함한다.
- writer 검사 10개가 11.253초에 통과했다. 세 날짜의 0 복원 SQL oracle, 실제 0행 존재, 빈 묶음,
  count·quality·receipt 변조, 소유권 누락/중복, 완료 재개, PART/QUALITY receipt 직후 중단·재개,
  이전 attempt 불변, 동시 run lock 충돌을 검사했다.
- 이전 병렬 결과 JSON/Parquet 4,557개와 동결 소스 193개 SHA가 동일함을 확인했다.

### 실제 32개 × 229일 — 교대 3회 결과

기존/개선, 개선/기존, 기존/개선 순서로 각각 새 프로세스와 새 출력 폴더를 사용했다.
양쪽 모두 CPU worker 4개, 전체 DuckDB 기본 예산 4 threads·4GB이며 GPU는 사용하지 않았다.
입력 준비는 위 각 1회 실측이고, 아래 계산·저장과 별도 검증은 각각 3회 중간값이다.
합산은 준비 1회 + 해당 반복의 계산·저장 + 검증이다. 정확성 대조용 쿼리 시간은 합산에 넣지 않았다.

| 단계 | 이전 P0~P2 | 개선 입력 + P3 | 시간 감소 |
| --- | ---: | ---: | ---: |
| 입력 준비 1회 | 92.899초 | 72.205초 | 22.3% |
| 계산·저장 | 60.078초 | 30.631초 | 49.0% |
| 별도 최종 검증 | 30.867초 | 13.313초 | 56.9% |
| 준비 포함 합산 중간값 | **183.844초** | **116.149초** | **36.8%** |
| 위 계산·저장 중 날짜 출력·마지막 확인 | 25.803초 | 4.511초 | 82.5% |

| 반복 | 이전 계산·저장 | 이전 검증 | 개선 계산·저장 | 개선 검증 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 98.598초 | 30.333초 | 30.631초 | 13.313초 |
| 2 | 60.078초 | 30.867초 | 31.165초 | 13.770초 |
| 3 | 58.776초 | 31.300초 | 30.450초 | 13.166초 |

이전 방식의 첫 실행이 후속 실행보다 길었다. 원인을 단정하거나 해당 관측을 삭제하지 않고 범위를 남긴다.
준비 포함 합산 범위는 이전 182.975~221.831초, 개선 115.821~117.140초였다.
이 실험은 이전 CPU/GPU 단일 프로세스 경로를 다시 비교한 것이 아니라 **직전 P0~P2 병렬 구조**를 대조군으로 삼았다.

저장 결과는 양수 count **1,875,271행**, 날짜별 품질 229행으로 동일하다. 세 번 모두 입력 네 테이블,
partition 네 테이블, cache 세 테이블, 날짜 count·품질의 **13개 의미 그룹에서 실제 행 차이 0건**이다.
날짜 품질의 실행 plan SHA만 의미 대조에서 제외하고, 각 실행의 이력·생성 계약은 해당 verifier로 검증했다.

- 입력 Parquet: 512개 → 108개. READY 27묶음만 파일을 만든다.
- 날짜 결과 Parquet: 기존 count 229 + quality 229 + lineage 229 = 687개 → count 25 + quality 1 = **26개**.
  양수 count가 없는 두 READY 묶음은 완료 receipt와 `file=null`로 기록한다. 이력은 run plan에 보존한다.
- 1초 간격 프로세스 트리 최대 RSS: 이전 **2.36GiB**, 개선 **2.32GiB**. hard memory 상한의 증명은 아니다.
- 관측한 run 폴더 내부 scratch 최대 0바이트. 시스템 임시 폴더와 장치 I/O 바이트는 측정하지 않았다.
- 기존 CPU/GPU 산출물 **2,640개**, 이전 병렬 산출물 **4,557개**, 동결 소스 **193개**의 SHA 불변을 다시 확인했다.
- 독립 읽기 검토에서 현재 범위의 차단 결함을 찾지 못했다. Python 12개 AST·공백 검사도 통과했다.

### 결과 위치·증거·남은 범위

입력 준비의 공통 테이블 구성·원본/입력 검증이 이제 표본 전체 시간의 큰 비중이다. 준비된 입력을 재사용할 수 있으면
개선된 계산·저장·검증은 표본 중간값 43.945초다. 이 입력 재사용도 기존 생성 계약과 파일 지문이 같을 때만 허용한다.

**이번 수치는 전체 99,996개 패키지의 예상 시간이 아니다.** 극단 패키지·전체 분포·메모리 spill은 별도 측정이 필요하다.
P4 CPU/GPU 중첩, 전체 선정 실행, EC2, DB 적재, commit·push는 수행하지 않았다. 병렬/묶음 저장은 선택형이며
기존 production 기본 경로와 과거 산출물을 변경하지 않았다.
