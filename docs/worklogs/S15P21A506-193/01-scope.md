# 01. 작업 범위

상태: **입력 기준 조사·집계 핵심·로컬 Parquet 저장 및 재검증을 구현했다. 실제 입력 승인·전체 데이터 처리·DB 적재는 후속이다.** [계획](02-plan.md) · [기준과 결정](06-decisions.md)

## 목표와 집계 의미

입력 관계의 방향은 `source → target`이다. 각 `(target package_id, target version, snapshot_at)`별로 서로 다른 `(source package_id, source version)` 쌍을 센다.

예를 들어 `A@1 → B@3`, `A@2 → B@3`, `A@2 → B@3`이 있으면 중복 관계 하나를 제거한 뒤 `B@3`의 count는 **2**다. A의 대표 버전만 남기거나 A라는 패키지 하나로 합치지 않는다.

이 값은 스냅샷 시점의 requirements 해석으로 추론한 **직접 의존 관계 수**다. 실제 설치 횟수나 여러 단계를 거치는 all-depth 도달 수를 의미하지 않는다.

2026-09-11 사용자가 저장 target을 다운로드 선정 목록으로 제한하고, count는 전체 source
패키지/버전의 참조 수로 유지하기로 결정했다. 이후 실행의 “전체 승인 target”은 선정
패키지의 전체 유효 버전을 뜻한다. [D-22 결정](06-decisions.md)

## 8번에서 다룰 범위

| 영역 | 예정 작업 |
| --- | --- |
| 입력 검증 | 명시적으로 선택한 edge run의 manifest·완료 상태·파일 집합·해시·스냅샷·정책·coverage 확인 |
| 집계 | 전체 source 버전의 식별자를 유지하고 관계 중복을 제거한 뒤 target 버전별 count 계산 |
| 대상 집합 | D-22에 따라 다운로드 선정 패키지의 전체 유효 target 버전 집합에 한정. source는 전체 모집단 유지. 누락·추가 target은 품질 결과로 기록 |
| 결과 파일 | count Parquet, 품질 정보, 입력 이력과 검증 결과를 담은 manifest 생성 |
| PostgreSQL | 전용 staging 검증 후 서비스 행과 적재 성공 이력을 트랜잭션으로 반영 |
| 재실행 | 동일 입력 재검증, 충돌·실패·동시 실행 시 기존 완료 결과 보존 |
| 인계 | 실제 실행 명령, 결과 수치, 조회 방법, 제한 사항 기록 |

문서 준비와 1·2번 구현 이후, 사용자가 Parquet 저장 진행을 요청했다. 현재 변경 범위는
**`pipeline/version_dependents/`의 집계·로컬 저장·재검증·합성 예제·테스트와 이 기록 폴더**다.
로컬 출력은 `snapshot=<날짜>/run_id=<ID>`로 분리한다. 이후 D-07의 사용자 승인으로 성공 관계만
세는 PARTIAL 진단 입력 경로를 추가하고 최신 스냅샷 전체 집계를 완료했다. 정상 입력 승인·
전체 target 모집단 검증·운영 게시·DB 적재는 후속이다. 실제 결과는 [09 진단 집계](09-diagnostic-run.md)를 따른다.

## 변경·보존 경계

- 일반 `dependencies`만 계산하고 배포일 NULL을 source·target에서 제외한다는 기존 결정은 유지한다.
- 스냅샷은 `snapshot-time-v1`의 날짜·정확한 원천 시각·정책 해시를 따른다. 실제 초도 입력 검토는 `2026-08-31`이다. 여러 날짜의 기능 검증은 합성 입력으로 수행하며 실제 과거 데이터 전체로 확장하지 않는다.
- `package`, `version`, `snapshot`과 `package_version_snapshot`의 기존 서비스 DDL·제약을 유지한다.
- Bronze, 기존 Curated 결과, 7번 edge와 완료·실패 증거, 다른 작업의 데이터와 포인터를 덮어쓰지 않는다.
- prerelease·alias·프로토콜에 대한 7번 코드 수정은 이번 문서 요청에 포함하지 않는다. 확인한 한계와 후속 판단 사항만 기록한다.
- all-depth 계산, 신규 API, 자동 스케줄러, 운영 서버 배포는 별도 범위다.

## 완료 기준

아래는 향후 구현의 완료 기준이다. 현재 통과한 항목으로 해석하지 않는다.

| ID | 완료 기준 |
| --- | --- |
| AC-01 | 승인된 입력 run·파일·시간·정책·대상 집합이 일치하며 실패·불완전 입력의 정상 게시를 차단한다 |
| AC-02 | 작은 정답 그래프에서 source 버전별 count와 중복 제거 결과가 기대값에 일치한다 |
| AC-03 | 전체 승인 target마다 `(package_id, version, snapshot_at)`이 유일하며, 정상 계산 완료 후 관계가 없는 경우만 0을 부여한다 |
| AC-04 | count의 NULL·음수·PostgreSQL INT 초과, 알 수 없는 target, 미래 버전 유입을 검출한다 |
| AC-05 | Parquet와 manifest의 행 수·파일 해시·입력 계보·품질 정보가 일치한다 |
| AC-06 | PK·FK·값 검증 실패 시 DB에 부분 결과나 성공 이력이 남지 않는다 |
| AC-07 | 같은 입력 재실행과 동시 실행·장애 복구가 기존 완료 결과를 훼손하지 않는다 |
| AC-08 | 전체 계산·격리 DB 검증·실제 대상 적재 여부와 한계를 각각 증거로 남긴다 |
