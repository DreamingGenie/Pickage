# 32. 전체 DB 키 검증과 날짜별 원자적 적재기

## 승인 범위와 완료 기준

2026-09-12 사용자가 전체 DB 키 검증·실행 이력·중단 후 재개가 가능한 적재기 구현을 승인했다.
기존 `pickage_267_full_defaulted`의 서비스 테이블은 읽기만 하고, 실제 쓰기는 새 격리 DB에서 검증한다.
완료 기준은 전체 선정 키 전수 검증 결과, 날짜별 COPY/게시/재개 코드 및 실패·변조 통합 테스트다.
기존 DB의 전체 적재, 서버 작업, 서비스 DDL 변경, commit·push는 이번 범위에 포함하지 않는다.

## 설계와 순서

1. 완료된 전체 계산과 H1 입력·달력·package-version 게시 원천 지문을 확인한다.
2. 선택한 모든 package ID/이름과 중복 없는 적격 version 키를 PostgreSQL TEMP 테이블로 전달한다.
   서비스 데이터를 조회하는 트랜잭션은 읽기 전용이다. 약 10억 날짜별 행을 먼저 만들지 않는다.
3. DB의 게시된 package-version 원천, snapshot-reference 원천 및 모든 버전 키·날짜·관측 시각을 대조한다.
4. 날짜 하나씩 0 포함 COPY 파일을 생성한다. 날짜별 target/positive/zero 및 count 합계를 원본 품질과 비교한다.
5. 날짜 전체를 하나의 트랜잭션으로 게시한다. 서비스 값과 공통 execution/attempt/current 이력이 함께 COMMIT된다.
6. 같은 입력·코드로 재개하면 완료한 날짜는 값을 재검증하고, 미완료 날짜부터 적재한다.
   날짜 내부에서 실패하면 그 날짜의 쓰기를 모두 rollback한다.
7. 다른 입력으로 이미 게시한 날짜나 출처 없이 남은 서비스 행은 자동으로 덮어쓰지 않는다.

적재 단위가 하루인 이유: 패키지 묶음을 서비스 테이블에 따로 확정하면 일부만 들어간 날짜가
노출될 수 있다. 날짜 단위면 한 번에 최대 약 782만 버전 행을 처리하며 229개 완료 지점이 생긴다.
약 10억 행 전체를 한 트랜잭션이나 하나의 중간 파일로 만들지 않는다.

## 구현 경계

신규 `historical_db_source.py`, `historical_db_keys.py`, `historical_db_publish.py`,
`historical_db_load.py` 및 관련 테스트를 사용한다. H1/H5 생성 코드와 결과는 변경하지 않는다.
`version-dependents` dataset으로 기존 V2/V3 실행 이력을 사용하며 서비스 스키마를 바꾸지 않는다.
계산상의 PARTIAL은 품질 이력에 보존하고, 적재 트랜잭션의 PUBLISHED와 의미를 구분한다.
검증된 동일 입력을 적재하는 승인과 연결 정보는 CLI에서 명시하게 한다.

## 실제 진행

- 로컬 package-version 게시 manifest와 H1 원천 SHA 일치 확인.
- snapshot-reference 게시 manifest와 H1 달력 SHA 일치 확인.
- 전체 키 파일 준비: 12.031초, 매핑된 패키지 97,745개 / 적격 버전 7,822,819개.
- 99,996개 선정 이름 중 2,251개는 입력에서 ID가 매핑되지 않는다. DB 키를 만들어 내거나 0으로 처리하지 않고 제외 수를 기록한다.
- 기존 DB의 모든 버전 복합키, 패키지 ID/이름, 229개 날짜/UTC 관측 시각과 게시 원천을 읽기 전용으로 확인했다. 42.984초, 전수 일치.
- 최신 2026-08-31 날짜 COPY 파일: 7,822,819행, 221,203,502 bytes, 준비 7.328초.
  양수 2,345,847행 / 0 5,476,972행 / 참조 수 합계 236,651,273이며 원본 품질 집계와 일치한다.
- 이 시간은 파일 준비와 키 검증의 실측이며, PostgreSQL 10억 행 적재 시간 추정으로 사용하지 않는다.
- 실제 기존 DB `package_version_snapshot`은 검증 후에도 0행이다.
- 실제 CLI 기본 모드도 전체 입력 준비→키 검사→원천 재확인→결과 기록까지 통과했다(53.250초).
- H6/H7 관련 테스트 50회 실행, 53.900초, 실패·skip 없음. 공유 키 테스트의 반복 실행 8회가 포함되어 있으며 서로 다른 테스트 동작은 42개다.
- 격리 PostgreSQL에서 성공 적재/0, 동일 입력 REVERIFIED, COPY 직후·INSERT 직후·COMMIT 직전 실패와 재시도,
  DB 값 변조·zero 행 삭제 감지, 이전 날짜 적재 시 최신 current 유지, PARTIAL 이력과 외부 패키지/다른 지표 보존을 확인했다.
- coordinator는 source-open 실패 기록, 중간 날짜 실패 후 같은 execution ID 재개, 연결 대상·코드 변경 거부, 기본 모드 무적재를 확인했다.
- 실제 계산 producer/input generator 계약과 저장된 job 계약이 동일하고 run manifest SHA도 그대로다.
- 신규 Python 구문 검사와 git diff 공백 검사를 통과했다. 별도 lint/typecheck 설정은 이 모듈에 없어 해당 도구는 실행하지 않았다.

## 발견한 문제와 수정

- 게시 실행 ID와 Curated run ID는 서로 다르므로 원천 확인을 `curated_run_id`와 current의 실행 연결로 분리했다.
- Windows 텍스트 변환이 COPY 값에 CR을 섞지 않도록 파일과 psql 입력을 바이너리 LF로 전달한다.
- immutable 메타데이터 작성 함수를 상태 갱신에 쓰면 재실행이 실패한다. attempt 결과는 불변으로 보존하고 root 상태/최신 결과만 원자적으로 갱신한다.
- source를 여는 단계의 실패도 FAILED를 기록하도록 예외 처리 범위를 확장했다.

## 남은 작업과 실제 미실행 범위

- 기존 서비스 DB의 전체 1,007,084,608행 적재는 실행하지 않았다. 이 규모의 PostgreSQL 적재 시간·WAL·인덱스/디스크 사용량은 아직 실측하지 않았다.
- 실제 쓰기 전에 날짜 하나의 제한된 적재를 별도 DB에서 측정하면 전체 적재에 필요한 시간·공간 판단 근거를 얻을 수 있다.
- 재실행은 완료 날짜를 무조건 건너뛰지 않고 원본과 DB 값을 재검증한다. 완료 날짜 내부의 파일 준비/COPY 검증 비용은 다시 발생한다.
- H7의 실행 이력만 PUBLISHED이며 원본 PARTIAL과 ready_for_load=false는 보존한다.
- 서버·원격 작업, 기존 DB 전체 쓰기, commit·push는 하지 않았다.
