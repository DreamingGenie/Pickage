# 버전별 참조 수 파이프라인: 문제 해결 사례와 증거 안내

패키지·버전·날짜별 참조 수를 계산하고 로컬 서비스 DB에 연결하기까지의 기록이다.
2026-09-10~13의 작업을 문제별로 다시 묶었다. 성공 결과뿐 아니라 느려진 시도, 잘못된 가정,
오류 수정, 측정하지 못한 범위도 남겨 팀 리뷰와 포트폴리오 설명에 함께 사용할 수 있도록 했다.

## 최종 결과와 해석 범위

| 항목 | 확인된 결과 | 범위 |
| --- | --- | --- |
| 전체 집계 | 99,996개 선정 이름·229일, 1시간 26분 55초 | 로컬 CPU 작업자 4개. 입력 준비·계산·저장·최종 검증 포함 |
| 파일 출력 | 양수 count 296,325,102행 | 모든 날짜의 target count 합계. 관계 행 수와 다름 |
| 전체 DB 적재 | 0 포함 1,007,084,608행, 2시간 30분 28초 | DB 키가 연결된 97,745개 패키지의 유효 버전·날짜. 사전 점검·초기화는 시간에서 제외 |
| 버전별 전체 날짜 조회 | 반복 DB 중앙값 13.274ms | 로컬 단일 연결, 229행을 반환한 19개 버전. HTTP/API 시간 아님 |
| 서비스 전환 | public 테이블과 229일 이력 전환, 기존 데이터 백업 | 로컬 DB. EC2 배포나 백엔드 쿼리 변경 완료 아님 |

근거: [전체 집계](../evidence/full-selected-results.json), [전체 적재](../evidence/db-timed-reload-complete.json),
[조회](../evidence/db-history-query-results.json), [전환](../evidence/db-service-cutover-complete.json).

저장 target은 선정 패키지로 제한했지만, 참조 source는 전체 적격 패키지·버전이다.
같은 source 버전의 중복 선언은 한 번만 세고 서로 다른 source 버전은 각각 센다.
미해석 관계는 PARTIAL로 남아 있으며, 성공적으로 해석된 직접 관계의 수를 계산한 결과다.
서비스 데이터가 준비됐다는 사실을 미해석 해소나 운영 환경 검증 완료로 표현하지 않는다.

## 원본 기록을 보존하는 구조

| 자료 | 현재 위치와 사용법 | 이번 정리에서 한 일 |
| --- | --- | --- |
| 사례 문서 | 현재 `case-studies/` | 문제별 설명과 증거 연결 추가 |
| 날짜순 기록·상세 실험 | [작업 폴더](../README.md)의 01~44번 문서 | 기존 내용 보존. 당시 상태는 현재 상태와 구분 |
| 핵심 JSON·시험 로그·실행/복구 SQL | [evidence/](../evidence/) | 모두 보존. 계산 입력·재현 코드가 섞여 있어 통째로 제외하지 않음 |
| 대용량 Parquet·전체 실행 폴더 | 각 상세 기록이 가리키는 로컬 `data/` | 이번 정리에서 이동하거나 Git에 추가하지 않음 |
| 팀 공용 대용량 원본 보관소 | 아직 확정되지 않음 | MinIO 등 공용 보관소에 업로드했다고 표시하지 않음 |

팀원이 이 브랜치를 받으면 사례와 커밋된 증거 파일을 읽을 수 있다. 로컬 `data/` 원본은 자동으로 공유되지 않는다.
이번에는 파일을 삭제·축약하거나 Git 이력을 다시 쓰지 않았다. MR의 줄 수를 줄이는 작업은 별개다.

추후 상세 원본을 Git 밖으로 분리한다면 **공용 위치·접근 권한·원래 경로·파일 SHA-256·실행 조건**을
먼저 기록하고 다른 팀원이 접근 가능한지 확인한 후 이동할 대상을 정한다.
요약 수치·실패 원인·최종 결정·대표 증거는 저장소에 남긴다. 반복 로그를 단순 삭제하거나 JSON을 한 줄로 눌러
증거의 읽기 편의와 줄 수를 맞바꾸지 않는다.

## 포트폴리오에 옮길 때

문제 한 가지를 고르고 **문제 → 가정 → 측정 → 시도와 실패 → 선택 → 검증 → 한계** 순서로 줄이면 된다.
사례의 숫자 옆에 있는 표본과 측정 범위는 짧은 소개에서도 유지한다.

- 합성 예제 8.49배를 10만 패키지 전체 개선 배수로 표현하지 않는다.
- 32개 표본의 병렬 저장 개선 36.8%를 전체 10만 패키지의 개선율로 표현하지 않는다. 한 PC의 다중 프로세스와 두 EC2 분산 실행을 구분한다.
- 부분 GPU 실험의 이득을 전체 GPU 집계 완료로 표현하지 않는다. 최종 전체 실행은 CPU였다.
- 중단한 기존 DB 적재와 새 전체 적재를 동일 조건의 완주 비교처럼 표현하지 않는다.
- 최초 조회는 캐시를 비운 실험이 아니며, 로컬 반복 조회 시간을 서비스 응답 성능으로 표현하지 않는다.
- 예측 시간과 실제 측정 시간을 구분하고, 실제 서버 운영 경험으로 바꾸어 쓰지 않는다.
- 문서는 프로젝트 작업 결과를 설명한다. 외부 공개 시 개인이 맡은 역할·기여 범위는 실제 수행 내용에 맞춰 별도로 기재한다.

## MR에서 안내할 리뷰 순서

MR 본문에는 최종 동작, 데이터 의미, 검증 결과, 남은 범위를 요약하고 이 페이지를 연결한다.
계산 경로는 사례 1·2·3, DB 적재와 전환은 사례 4·5를 먼저 읽은 뒤 상세 코드와 테스트로 이동하면 된다.
사례 6은 전체 과정의 검증 방법과 그 한계를 연결하므로 정확성 리뷰의 공통 안내로 사용한다.
과거 실험의 모든 로그를 처음부터 읽어야 최종 설계를 이해하는 구조를 피하고,
필요한 주장의 원문은 사례에서 바로 찾아갈 수 있게 한다. 이번 정리에서는 MR을 생성하거나 게시하지 않았다.
