# 최적화한 참조 수가 맞는지 확인하기: 기준 계산부터 저장·복구까지

## 문제: 빨라진 결과가 같은 의미인지 확인해야 했다

날짜마다 계산하던 코드를 구간·변화량으로 바꾸고, 같은 조건을 가중치로 묶고,
CPU 작업자와 GPU까지 연결했다. 출력 파일 구조와 DB 적재 방식도 바뀌었다.
이 과정에서는 중복을 더 세거나 일부 날짜를 빠뜨리고도 계산을 성공으로 표시할 수 있다.
총합과 파일 개수만 같아서는 버전별 숫자가 올바른지 알 수 없었다.

예를 들어 기대값이 `B@1=1, B@2=2`인데 결과가 `B@1=2, B@2=1`이면 합계는 둘 다 3이다.
이 설명용 예제처럼 합계는 일치해도 그래프의 각 버전 값은 틀릴 수 있다.
따라서 계산 의미, 실제 행, 품질, 파일 이력, 완료 상태를 서로 다른 경계에서 확인했다.

## 첫 기준: 무엇을 한 번으로 셀 것인가

키는 `(target package_id, target version, snapshot_at)`이며, 값은 그 target을 직접 참조하는
서로 다른 `(source package_id, source version)` 쌍의 수다.
같은 source 버전의 중복 선언은 한 번만 세고, 같은 패키지의 서로 다른 source 버전은 각각 센다.
간접 경로는 더하지 않고, 배포일 NULL 제외·미해석 PARTIAL·선정 target/전체 적격 source 정책을 유지했다.

작은 H2 기준 구현은 각 날짜마다 후보를 직접 선택하고 DISTINCT로 중복을 제거했다.
빠른 구간 집계와 별도 계산 경로로 남겨 H3의 날짜별 결과와 대조했다.
두 구현이 따르는 npm 해석 정책은 같으므로, 이 대조가 원본 데이터의 완전성이나 npm 실제 설치와의 모든 차이를 증명하는 것은 아니다.
[작은 정답 예제와 경계](../12-historical-reference-results.md)

## 비교한 것은 count 하나가 아니었다

실제 행은 양방향 차집합으로 누락과 추가를 확인했다. `EXCEPT ALL`은 중복 행 수 차이도 남긴다.
실행마다 달라지는 ID나 계획 지문까지 바이트로 같다고 요구하지 않고,
계산 의미가 같은 값은 행으로, 각 실행의 생성 이력은 해당 실행의 검증기로 따로 확인했다.

## 검증 과정에서 실제로 발견한 오류

### 1. count 120이 121이 된 중복 구간 오류

H3 반복 예제에서는 source 버전 120개가 같은 target을 중복 선언했다.
동일한 시작·종료 시각을 가진 구간에서 두 SQL window의 정렬이 달라 count가 121이 됐다.
두 연산에 원본 `declaration_index`를 일관되게 포함하고, 날짜별 count 120과 관계 구간 480을 확인하는 회귀 검사를 추가했다.
성능 개선 전에 값 비교가 필요했던 실제 사례다.
[발견·수정 기록](../13-historical-optimization-results.md)

### 2. 변조 테스트가 엉뚱한 오류로 통과한 문제

H4 초기 변조 테스트 일부는 필수 SHA를 생략하거나 keyword 전용 인자를 위치 인자로 넘겼다.
예외가 발생하기만 하면 통과하는 검사로는 파일 변조를 제대로 감지하는지 알 수 없었다.
호출을 고치고 의도한 오류 메시지를 확인했다. 값과 manifest의 해시를 함께 바꾼 경우에도
기준 cache와 값이 다르면 실패하는 검사를 추가했다.
파일 해시는 받은 파일의 일관성을 확인하는 수단이며, 잘못 계산된 숫자를 자동으로 정답으로 만드는 수단은 아니다.
[H4 검증 보강](../14-historical-artifact-results.md)

### 3. 기대값의 ID가 잘못된 손계산 검사

초기 H4 대조 스크립트는 fixture의 package ID 2/3을 20/30으로 잘못 적어 실패했다.
실제 입력을 다시 확인하고 기대값을 수정한 뒤 기존 저장 파일 그대로 통과했다.
테스트가 실패했다고 계산 결과부터 바꾸지 않고, 입력·기대값·구현 중 어느 쪽의 오류인지 구분했다.
[합성 예제 대조 기록](../14-historical-artifact-results.md)

### 4. 복구 검사가 정상 CHECK를 외부 의존성으로 오인

서비스 전환 첫 예행연습에서 부모 자신의 음수 금지 CHECK를 외부 객체로 판단해 복구 검사가 중단됐다.
트랜잭션이 취소돼 기존 서비스 상태가 남았는지 먼저 확인했다. 조건을 수정한 뒤
전환→복구→전체 ROLLBACK을 다시 검증하고, 동일한 전환 SQL을 실제 적용했다.
예행연습 실패와 수정 결과는 [서비스 전환 기록](../44-service-table-cutover.md)에 함께 남겼다.

## 입력·코드가 다른 결과를 재사용하지 않기

입력 파일, 선정 목록, 날짜 목록, 정책, 생성 코드와 필요한 runtime 정보를 실행 계획에 고정했다.
완료된 결과를 다시 쓸 때 원래 manifest와 파일 지문을 확인하고, 새 코드의 해시를 과거 manifest에 덮어쓰지 않았다.
다른 생성 계약의 산출물은 새 계약의 결과로 간주하지 않고 원래 검증 경로에서 확인했다.

이 구분은 성능 실험에도 필요했다. 이전 코드와 결과를 보존한 상태에서 새 실행을 만들고,
결과 값은 비교하되 각 실행의 provenance는 별도로 유지했다.
[생성 계약 보존·이전 결과 대조](../27-input-verification-storage-optimization.md)

## 파일이 존재하는 것과 작업이 완료된 것을 구분하기

작업자는 새 attempt 폴더에 결과를 쓴다. 검사 후 coordinator가 완료 포인터로 승인한 결과만 재사용한다.
파일이 생겼지만 승인 직전에 프로세스가 끝난 경우, 승인된 결과를 읽는 도중 파일이 변조된 경우,
같은 묶음의 candidate가 여러 개지만 값이 다른 경우를 따로 검사했다.

- 계산 묶음의 완료 전후 중단, 작업자 강제 종료, 2개→4개 작업자로 재개를 확인했다.
- 날짜/grouped 출력에서 미승인 attempt와 완료 결과의 재사용 경계를 확인했다.
- 동시 실행은 run lock으로 막고, 프로세스 종료 뒤 잠금이 해제되는지 실제 자식 프로세스로 검사했다.
- GPU 장애를 CPU 성공으로 조용히 바꾸지 않고 실행 실패와 완료 묶음 재사용을 구분했다.
- DB에서는 COPY 직후·INSERT 직후·COMMIT 직전 실패, 값 변조·0행 삭제, 재실행과 최신 포인터 보존을 확인했다.

근거: [CPU 프로세스·재개](../26-parallel-input-cpu-execution.md), [grouped 저장 검증](../27-input-verification-storage-optimization.md),
[GPU 실패·재개](../28-cpu-gpu-overlap.md), [DB 실패 주입](../32-full-db-loader.md).
프로세스 강제 종료 검사를 컴퓨터 재부팅·전원 차단의 모든 경우를 시험한 결과로 표현하지 않았다.

## 전체 실행에서 확인한 결과

최종 CPU 전체 집계는 99,996개 선정 이름·229일을 완료하고 양수 count 296,325,102행을 저장했다.
최종 파일 검증에는 **1,848.813초**가 걸렸다. 전체 5,215.125초에 포함된 실제 단계이며 비용을 숨기거나 0으로 계산하지 않았다.
다만 이 검증은 입력·중간 결과·산출물의 연결과 내용 확인이며, 전체 원본을 H2로 재계산한 독립 oracle은 아니다.
[전체 집계 증거](../evidence/full-selected-results.json)

DB에서는 229일·0 포함 1,007,084,608행의 날짜별 적재와 최종 행 수·구조·이력 검증을 마쳤다.
그 뒤 서비스 전환은 이미 검증된 결과의 연결을 검사하고, 새 연결로 48개 버전·7,560행이 기존 조회와 같은지 확인했다.
전환 때 10억 행을 다시 COUNT하거나 원본 관계부터 재집계한 것은 아니다.
[전체 적재 기록](../42-timed-full-reload.md) · [전환 후 조회 증거](../evidence/db-service-cutover-complete.json)

## 품질 상태와 남은 한계

`calculation_status=COMPLETE`는 정한 입력과 정책으로 계산이 끝났다는 뜻이다.
`resolution_status=PARTIAL`은 해석하지 못한 관계가 남았다는 뜻이므로 두 상태는 함께 존재할 수 있다.
H7의 날짜별 `PUBLISHED`는 DB 데이터와 이력이 성공적으로 반영됐다는 뜻이다.
이후 DB 적재가 승인·완료돼도 초기 Parquet의 `ready_for_load=false`와 원본 품질 기록을 소급 변경하지 않았다.
[DB 게시와 원본 품질 경계](../32-full-db-loader.md)

검증은 각 단계에서 어떤 오류를 찾을 수 있는지 설명해야 한다.
공유하는 npm 정책의 한계, 원본의 미해석, 과거 관측의 완전성, EC2/API 성능은 별도 문제다.
이 사례에서는 검사 횟수를 모두 더해 하나의 성공 수치로 내세우기보다, 실제로 대조한 대상과 아직 확인하지 않은 범위를 남겼다.
