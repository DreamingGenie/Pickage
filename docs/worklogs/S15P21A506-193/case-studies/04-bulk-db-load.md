# 사례 04. 대량 DB 적재가 느려진 이유와 날짜별 게시 구조

## 문제

계산 결과를 서비스 테이블에 넣는 단계에서 예상보다 긴 시간이 걸렸다.
목표는 선정 목록에 연결된 97,745개 패키지의 적격 버전과 229개 스냅샷 날짜를
`package_version_snapshot`에 저장하는 것이었다.
최종 입력은 날짜별 0값을 포함한 1,007,084,608행이었다.

처음에는 계산이 끝난 Parquet를 PostgreSQL에 넣는 작업이 단순한 대량 쓰기라고 생각했다.
하지만 테이블에는 `(package_id, version, snapshot_at)` 기본 키와
`version`, `snapshot`을 확인하는 외래 키가 있었다.
행을 넣을 때마다 이미 쌓인 인덱스와 외래 키 검사가 함께 작동하므로,
Parquet 파일의 크기만으로 적재 시간을 판단할 수 없었다.

## 처음의 가정

처음 적재기는 날짜별 staging 테이블에 COPY한 뒤 서비스 테이블로
`INSERT ... SELECT`를 수행했다.
기본 키와 외래 키를 유지한 채 한 날짜씩 처리하면 실패한 날짜만 되돌릴 수 있고,
완료 날짜를 기록해 중단 후 재개할 수 있다는 장점이 있었다.

다만 누적 서비스 테이블에 날짜를 순서대로 INSERT하면 각 날짜의 쓰기가
이미 커진 기본 키와 외래 키에 계속 영향을 준다.
시작부터 중단까지 약 3시간 36분이 경과한 시점에 완료된 데이터는 43일, 106,346,692행이었고,
전체의 약 10.6%였다. 경과 시간에는 중단된 다음 날짜 작업도 포함된다.
실행 중 `DataFileRead`와 `DataFileWrite` 대기가 보였고,
취소 시점 SQL의 CONTEXT는 `version` 외래 키 검사였다.
이 관찰만으로 FK, PK, 디스크가 각각 전체 시간에서 차지한 비율을 확정하지는 않았다.

## 병목을 나눈 실험

원래 서비스 테이블은 건드리지 않고, 같은 PostgreSQL과 실제 참조 테이블을 사용하는
격리 schema에서 네 가지 방식을 비교했다.
먼저 2023-03-06 입력에서 10만 행을 추출해 네 방식 모두 원본과 전수 대조했다.

| 방식 | 총시간 | 실험 목적 |
| --- | ---: | --- |
| INSERT + PK/FK | 22.391초 | 기존 경로의 진단 기준 |
| INSERT + PK만 | 0.172초 | FK 비용을 분리하는 진단용 |
| COPY + PK/FK | 3.093초 | COPY 경로의 가능성 확인 |
| COPY 후 PK/FK 생성·검증 | 0.579초 | 일괄 제약 생성 후보 |

10만 행 진단에서 `INSERT + PK/FK`의 EXPLAIN 실행 시간 중
version FK trigger가 20.931초, snapshot FK trigger가 1.258초였다.
첫 INSERT에는 EXPLAIN 진단이 포함됐고 후속 방식은 앞선 실행이 채운 캐시의 영향을 받았다.
이는 해당 표본에서 행별 FK 검사가 큰 비용임을 보여 주지만,
빈 실험 테이블과 한 번의 측정이라는 조건 때문에 전체 적재 배수로 환산하지 않았다.

이후 중단됐던 날짜인 2023-03-06의 2,827,680행으로 네 방식을 각각 두 번 실행했다.
첫 번째 전체 날짜 비교 중 이동 요청으로 한 번 취소했지만,
실험을 정리하고 저장된 입력을 재사용해 8회 비교를 완료했다.
완료한 8회는 모두 원본과 정확히 일치했고, FK를 유지한 여섯 실행은 검증 상태도 확인했다.
아래 총시간은 테이블 생성·삽입·키 검증·값 전수 비교·COMMIT을 포함하며,
공통 입력/staging 준비와 실험 후 DROP은 제외한다. 네 방식은 정순·역순으로 실행했다.

| 방식 | 1회차 | 2회차 |
| --- | ---: | ---: |
| INSERT + PK/FK | 440.484초 | 406.609초 |
| INSERT + PK만 | 4.375초 | 5.344초 |
| COPY + PK/FK | 326.078초 | 410.187초 |
| COPY 후 PK/FK 생성·검증 | 55.609초 | 15.719초 |

일괄 방식의 두 번째 실행은 COPY 2.968초, PK 생성 0.735초,
두 FK 생성·전체 검증 11.062초였다.
따라서 COPY 명령으로 바꾸는 것만으로는 충분하지 않고,
행별 FK 검사를 적재 시점에서 분리하는 구조가 핵심 후보가 됐다.

## 선택한 구조

일괄 방식의 장점을 날짜 단위 원자성에 결합했다.

1. 준비한 날짜 입력을 별도 일반 테이블에 COPY한다.
2. 날짜 범위 CHECK, 기본 키, 외래 키를 만들고 전체 데이터를 검증한다.
3. 검증된 테이블을 날짜 partition으로 부모에 ATTACH한다.
4. 실행·시도·현재 포인터와 적재용 부모 테이블 연결을 같은 트랜잭션에서 확정한다.
5. 실패하면 해당 날짜와 게시 이력을 함께 rollback하고, 다음 실행에서 그 날짜를 처음부터 재처리한다.

2023-03-06 전체 날짜 연결 실험은 COPY 3.707초, PK 생성 0.555초,
FK 생성·검증 8.597초, 준비 단계 전체 13.452초였다.
ATTACH 자체는 0.003327초로 측정됐다.
연결 전후 읽기 카운터가 증가하지 않았고, 부모 조회와 원본 값도 일치했다.
이 수치는 미리 만들어 둔 TSV에서 시작한 격리 실험의 측정값이며,
전체 소스 준비나 실제 서비스 테이블 전환 비용을 포함하지 않는다.

이 구조로 private schema에 229일을 처음부터 적재했다. 기존 public 서비스 테이블은
이 과정에서 바꾸지 않았고, 완료 후의 실제 전환은 [사례 5](05-query-and-cutover.md)에서 다룬다.
실제 전체 적재는 2026-09-12 23:58:09에 시작해
2026-09-13 02:28:37에 종료했고(KST), 총 9,028.416초(2시간 30분 28초)였다.
229일과 1,007,084,608행이 모두 검증되었고, 각 날짜의 receipt와 최종 행 수가 일치했다.
이 시간에는 입력·키 확인, 날짜별 준비·저장·검증, 최종 검사와 정리가 포함된다.
초기화와 사전 점검은 제외했다.

## 검증과 남은 한계

중단 후 재개, 날짜 중간 실패 rollback, 입력 변조 거부, FK/PK 검증,
다른 데이터셋 이력 보존을 격리 테스트에서 확인했다.
기존 43일 서비스 데이터는 실험과 전체 private 적재 중 변경하지 않았다.

다만 이 결과가 운영 서버의 처리 시간을 보장하지는 않는다.
EC2의 디스크·WAL·메모리, 동시 서비스 요청, 실제 기존 테이블에서의 전환 잠금은
별도로 측정해야 한다.
또한 `COPY 후 제약 생성` 실험의 빠른 시간을 남은 날짜에 단순 곱하지 않았다.
캐시와 실행 순서가 달랐고, 누적 인덱스 크기도 private 새 테이블과 다르기 때문이다.
