# 사례 05. 날짜별 저장 구조를 조회에 연결하고 서비스 테이블로 전환하기

## 문제

적재 구조를 정한 뒤 서비스가 실제로 필요한 조회를 다시 확인했다.
목표 서비스 화면은 패키지와 버전을 지정해 특정 기간의 날짜별
`dependents_count`를 그래프로 보여주는 것이다. 이번에는 화면 구현보다 먼저 목표 SQL을 검증했다.
따라서 패키지 이름만으로 여러 버전을 합산하는 조회와
`package + version` 하나의 날짜 이력을 반환하는 조회는 서로 다른 계약이다.

날짜별 partition을 사용하면 특정 날짜 적재와 재개가 쉬워진다.
반대로 하나의 버전에서 229개 날짜를 읽을 때 모든 날짜 partition을 확인해야 하므로,
패키지·버전·날짜 순서로 조회해야 한다는 요구와 충돌할 수 있다고 보았다.
이를 확인하지 않고 저장 구조를 바꾸거나 추가 인덱스를 만들지 않았다.

## 조회 실험을 설계한 방법

전체 적재가 완료된 private 테이블에서 16개 패키지, 48개 버전을 표본으로 골랐다.
8개 유명 패키지와 이름 SHA 순서로 고른 8개 패키지를 섞었고,
각 패키지의 최신 날짜 버전 문자열에서 사전순 처음·중간·마지막을 선택했다.
이 선택은 semver 순서나 배포 시각 순서를 뜻하지 않는다.

실제 목표에 맞춰 `package_id`와 `version`을 고정하고,
`snapshot_at` 범위를 지정한 뒤 날짜순으로 `snapshot_at`과 `dependents_count`를
반환하는 조회를 측정했다. 이 조건은 버전 간 SUM을 수행하지 않는다.

각 사례에서 EXPLAIN ANALYZE와 일반 SELECT를 실행했다.
최초 실행과 반복 실행을 따로 기록했지만 PostgreSQL이나 OS cache를 비우지는 않았다.
따라서 최초 실행은 엄밀한 cold-cache 측정이 아니다.
일반 SELECT 시간은 지속 psql 연결을 통한 결과 수신까지이며,
HTTP, 인증, 연결 생성, 패키지 이름을 ID로 바꾸는 시간은 포함하지 않는다.

## 측정 결과

48개 버전 모두 229개 날짜 relation을 Index Scan으로 접근했다.
229일이 모두 반환된 19개 버전의 결과는 다음과 같다.

| 측정 | 횟수 | 중앙값 | 표본 p95 | 최댓값 |
| --- | ---: | ---: | ---: | ---: |
| 최초 DB 계획+실행 | 19 | 105.605ms | 316.327ms | 316.327ms |
| 반복 DB 계획+실행 | 57 | 13.274ms | 15.577ms | 16.458ms |
| 반복 일반 SELECT 결과 수신 | 57 | 15.482ms | 18.987ms | 26.626ms |

가장 느린 최초 조회는 `express@0.14.0`으로 316.327ms였다.
반복 실행에서는 root buffer read가 0이었고, 최초 실행에는 캐시 상태와
partition 계획 준비 비용이 섞였다.
이 결과는 날짜별 구조가 이 로컬 단건 조회에서 즉시 교체되어야 한다는 증거가 아니었다.

실험에서 추가 인덱스는 만들지 않았다.
기존 복합 PK `(package_id, version, snapshot_at)`가 각 partition에 있었고,
조건에 맞는 index scan이 사용됐다.
다만 모든 조회가 빠르다고 일반화할 수는 없다.
표본은 16개 패키지뿐이고, 동시 요청·연결 풀·EC2 네트워크·실제 API 경로는 측정하지 않았다.
기존 백엔드의 버전 간 SUM 쿼리는 수정하지 않았다. 실제 API의 버전별 조회 연결은 후속 작업이다.

## 전환 전 안전장치

전체 229일 private 적재가 완료된 뒤 private 부모를 서비스 이름으로 노출해야 했다.
테이블을 바로 삭제하거나 복사하면 실패 시 복구가 어렵고,
실행 이력과 현재 날짜 포인터가 실제 서비스 테이블과 어긋날 수 있다.

전환 절차를 다음처럼 제한했다.

1. 기존 `public.package_version_snapshot`과 기존 이력을 별도 backup schema에 보존한다.
2. 외부 FK, view, trigger, 권한과 소유자를 확인한다.
3. private 부모와 229개 날짜 partition의 열·제약·범위를 확인한다.
4. 서비스 테이블 이름과 version-dependents 실행·시도·현재 이력을 한 트랜잭션에서 바꾼다.
5. 새 연결에서 실제 패키지·버전·날짜 조회 결과를 재확인한다.

첫 번째 예행연습은 복구 검사에서 부모 자신의 `dependents_nonnegative` CHECK를
외부 의존성으로 잘못 판단해 실패했다.
트랜잭션 전체가 취소되는지와 기존 상태가 남는지 확인한 뒤,
자기 제약조건을 외부 객체 검사에서 제외하도록 조건을 고쳤다.
수정 후 전환→복구 왕복과 이력 복원을 다시 검증했다.

## 실제 전환 결과

2026-09-13 09:46:46 KST에 로컬 PostgreSQL에서 실제 전환을 완료했다.
이전 서비스 테이블은 backup schema에서 OID 87774로 보존했고,
새 서비스 부모의 OID는 280767이었다.
기존 부모의 OID가 새 부모로 유지된 것은 아니며,
기존 데이터를 삭제하지 않고 backup으로 보존한 것이다.

새 서비스 이름에는 229개 날짜 partition이 연결되어 있고,
앞선 적재 receipt 기준 행 수는 1,007,084,608행이다.
전환 과정에서 대용량 행 복사나 다시 10억 행 COUNT를 수행하지 않았다.
검증된 receipt, partition 구조, 열·제약, 통계의 insert 합계와 대표 조회를 조합해 확인했다.

전환 전후 48개 버전, 7,560개 반환 행은 모두 이전 조회 결과와 일치했다.
다른 데이터셋의 실행·시도·현재 이력은 전후 직렬화 해시가 같았고,
이전 version-dependents 이력은 backup 후 새 229일 이력과 현재 날짜를 기록했다.
전환 실행기 전체 시간은 3.334초였지만, 이 값은 검증과 이력 처리까지 포함한다.
순수 DDL 시간이나 운영 중 잠금 시간으로 해석하지 않았다.

## 현재의 의미와 한계

로컬 서비스 테이블 전환과 복구 가능성 검증은 끝났다.
이 과정은 데이터 구조와 전환 절차를 확인한 것이며 EC2 서버 배포 완료를 뜻하지 않는다.
운영 적용 전에는 서버 DB의 기존 객체·권한·데이터 상태를 다시 확인해야 한다.
또한 API가 요구하는 버전별 조회 계약에 맞춰 백엔드 쿼리를 별도 수정하고,
실제 연결 풀과 동시 요청 조건에서 성능을 검증해야 한다.
