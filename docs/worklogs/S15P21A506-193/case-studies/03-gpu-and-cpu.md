# GPU를 붙이면 전체 집계가 빨라질까?

입력 분할과 CPU 작업자·저장 구조의 개선은 [CPU 병렬처리 사례](02-cpu-parallelism.md)에서 먼저 설명한다.

이 문서는 229개 스냅샷의 npm 의존성 버전 해석과 `dependents_count` 집계를
빠르게 만들기 위해 CPU와 RTX 4070 Laptop GPU를 비교한 과정을 정리한다.
수치 계산 구간은 GPU로 빨라졌지만, 최종 병렬 집계 비교에서는 CPU가 더 빨랐다.
어느 구간을 측정했는지에 따라 달라진 결과와 CPU를 선택한 근거를 설명한다.

## 문제

각 요구조건은 기준일마다 후보 버전 중 하나를 선택한다. 이를 위해 후보 버전의
배포일과 semver 순위를 준비하고, `^`, `~`, 비교식, OR/AND 등의 조건을 해석한 뒤
선택 결과를 날짜 구간으로 바꾼다. 이후 구간 이벤트를 집계해 날짜별 count를 저장한다.

처음에는 후보와 요구조건의 비교를 수치 배열로 바꾸면 GPU가 대량 비교를 빠르게
처리할 수 있다고 보았다. 하지만 버전 해석은 숫자 계산만으로 끝나지 않는다.
Node/npm 정규화, JSON 요청과 응답, 결과 객체 복원, DuckDB 집계, Parquet 저장,
독립 검증이 함께 실행된다.

## 처음 가정과 측정 범위

첫 실험은 **버전 해석 부분만 따로 실행하는 standalone resolver** 비교였다. 준비된 입력을 읽고
조건을 정규화해 버전 구간을 만드는 부분만 측정했다. 기존 생산 writer의 count 집계,
날짜별 저장, DB 적재는 포함하지 않았다.

범위별 기록은 다음 순서로 남아 있다.

- [21번 resolver 실험](../21-gpu-resolver-experiment.md): 2개 패키지의 조건 59/256/1024개 표본을 229일에 적용했다. GPU가 개선 CPU보다 약 1.22~1.67배 빠른 사례를 확인했다.
- [22번 32개 비교](../22-gpu-32-package-comparison.md): 32개 이름, 40,701개 조건, 141,607개 후보를 229일에 적용했다. 해석 구간은 GPU 9.863초, CPU 15.053초였다.
- [24번 생산 연결](../24-cpu-gpu-production-integration.md): 같은 32개 전체 요구조건을 집계·저장·검증까지 연결했다. 개선 CPU 156.135초, GPU 153.091초였다.
- [28번 중첩 구조](../28-cpu-gpu-overlap.md): 같은 32개를 CPU/GPU 중첩과 grouped 저장으로 3회 교대 측정했다. CPU 43.995초, GPU 50.291초였다.

각 행은 서로 다른 실행 경로와 포함 범위를 가리킨다. 따라서 21·22번의 배속을
전체 production 시간에 곱하지 않았고, 24번과 28번의 합계도 동일한 벤치마크로
취급하지 않았다.

## 시도 1: 수치 계산만 GPU로 옮기기

후보를 버전 순서 번호(rank)로 정렬하고 각 조건을 만족하는 번호 구간으로 바꿨다.
CPU는 후보의 최초 포함 날짜(birth)를 저장한 segment tree로 해당 구간을 검색하고,
GPU는 PyTorch CUDA tensor로 구간 포함 여부와 birth별
`amax`, 날짜별 `cummax`를 계산했다. 전체 조건×후보×날짜 배열은 만들지 않고
묶음 단위로 처리했다.

2개 패키지의 sampled 조건×후보 55,350,243회와 32개 표본의 137,010,465회
rank 포함 여부가 npm `Range.test`와 모두 일치했다. 이 결과는 GPU 계산의
정확성을 확인했지만, GPU가 전체 pipeline을 빠르게 만든다는 증거는 아니었다.

| 32개 standalone 비교 | 개선 CPU | GPU | CPU/GPU |
| --- | ---: | ---: | ---: |
| 숫자 계산만 | 5.852초 | 0.627초 | 9.34배 |
| 정규화 + 선택 | 11.738초 | 6.611초 | 1.78배 |
| 정규화 + 선택 + 결과 정리 | 15.053초 | 9.863초 | 1.53배 |

숫자 계산은 크게 줄었지만, 정규화와 결과 정리는 CPU에 남았다. 작은 조건 수에서는
GPU 요청·전송의 고정 비용 때문에 CPU가 더 빠른 패키지도 있었다. 32개 기준으로
GPU가 빠른 패키지는 19개, CPU가 빠른 패키지는 11개, 계산 조건이 없는 패키지는
2개였다.

## 시도 2: 실제 집계 pipeline에 연결하기

다음 단계에서는 `npm`, 개선 `cpu`, `gpu`를 선택하는 backend 경계를 생산 집계기에
연결했다. GPU가 CUDA를 사용할 수 없을 때 CPU로 조용히 대체하지 않도록 했고,
입력·설정·코드 지문이 바뀐 결과를 재개하지 못하게 했다.

이때 CPU와 GPU는 같은 32개 입력과 229개 날짜를 사용했다. 입력 준비는 한 번만
수행하고 양쪽에 공통 비용으로 반영했다.

| 구간 | 이전 CPU | 개선 CPU | GPU |
| --- | ---: | ---: | ---: |
| 공통 입력 준비 | 68.401초 | 64.301초 | 64.301초 |
| 해석·집계·Parquet 저장 | 230.669초 | 74.687초 | 71.502초 |
| 별도 파일 검증 | 16.764초 | 17.148초 | 17.288초 |
| 전체 | 315.835초 | 156.135초 | 153.091초 |

개선 CPU와 GPU가 이전 CPU보다 짧아진 이유를 GPU 하나의 효과로 볼 수 없다.
범위 인덱스, batch 구성 재사용, weighted-event 집계, 저장 구조 개선이 함께
적용됐기 때문이다. 개선 CPU에서 GPU로 바꾼 추가 감소는 3.044초, 1.95%였다.

## 시도 3: GPU 계산과 CPU 작업을 겹치기

GPU 전담 owner 하나가 후보 계산을 맡고, CPU worker가 정규화·결과 변환·집계를
동시에 수행하도록 named pipe 기반 중첩 구조를 만들었다. worker 수를 1·2·4개로
비교했고, 오류·중단·재개·출력 변조 검사를 추가했다.

4개 CPU worker 구성이 가장 짧았지만, 같은 조건에서 CPU 기본 경로와 3회 교대
측정하자 결과가 뒤집혔다.

| 3회 중간값, 입력 재사용 | CPU 4 worker | GPU owner 1 + CPU 4 worker |
| --- | ---: | ---: |
| 계산·저장 | 30.725초 | 35.334초 |
| 독립 검증 | 13.270초 | 15.062초 |
| 전체 | **43.995초** | **50.291초** |

이 측정에서 GPU 경로는 전체가 **14.31% 더 길었다**. 숫자 계산 누적 시간은
CPU 6.890초에서 GPU 1.007초로 감소했고, GPU 순수 숫자 연산은 약 0.347초였다.
그러나 owner 시작 비용이 중간값 3.928초였고, 정규화·결과 복원·집계·검증은
CPU에 남았다. 이 작은 표본에서는 줄어든 계산 시간이 고정 비용을 상쇄하지 못했다.

GPU 요청 구간과 CPU 정규화·집계는 실제로 겹쳤다. 4 worker 반복에서 GPU 요청
구간 약 0.61~0.63초 중 0.516~0.563초가 CPU 구간과 겹쳤다. 따라서 느린 결과는
중첩이 작동하지 않았기 때문이 아니라, 중첩해도 전체 병목이 남았기 때문이다.

## 최종 선택

현재 기본 경로는 개선 CPU 4 worker와 grouped 저장 구조로 둔다. GPU 코드는 선택형
실험 경로로 보존했다. 28번의 10% 개선 채택 기준을 충족하지 못했고, GPU를 쓴다고
기록하기 위해 CPU 성공으로 대체하지도 않았다.

전체 선정 실행에서도 GPU를 별도로 비교하지 않았다. 실제 전체 CPU 실행은
[30번 기록](../30-full-selected-run.md)에 99,996개 target, 229일, 총 5,215.125초로
남아 있다. 이 값은 GPU와 동일 조건으로 맞춰 측정한 비교값이 아니므로 GPU의 전체
예상시간을 산출하는 근거로 사용할 수 없다.

## 시간 추정에서 바로잡은 가정

이전 대화에서 GPU 약 9시간의 표본 단순 환산과 1~3시간 추정이 나왔지만,
두 값을 같은 범위의 검증된 전체 예상시간으로 사용할 수 없었다.
[병렬 계획](../25-parallel-execution-plan.md)은 9시간 환산과 철회한 1~3시간을 목표나 근거로 쓰지 않는다고 명시했다.

32개 표본은 고유 요구조건 40,701개, 전체 선정 목록은 4,220,751개였다.
패키지당 평균은 약 1,272개와 약 42개로 달랐다. 반면 표본에 없던 극단 패키지 세 개는
전체 후보 수×요구조건 수 지표의 **51.52%**를 차지했다. 이 비율은 실제 시간 점유율이 아니다.
표본 패키지당 시간을 단순 곱하면 평범한 패키지의 비용을 과대평가하면서도 큰 패키지의 비용은 놓칠 수 있었다.
[모집단과 표본 구성](../20-daily-verification-throughput.md)

이후 입력 준비·해석·집계·병합·저장·검증의 포함 범위를 나누고,
같은 입력을 사용한 부분 비교와 실제 전체 실행을 구분했다. 최종 5,215.125초는 CPU 전체 실행의 관측값이며
GPU 9시간 추정이 그만큼 개선됐다는 비교값이 아니다. GPU 전체 완료 시간은 별도로 측정하지 않았다.

## 검증 결과

9회 실제 32개 실행의 입력, lookup interval, 중간 count, 품질, 최종 날짜 결과는
13개 의미 그룹에서 차이가 0건이었다. 양수 count는 1,875,271행, 날짜별 품질은
229행으로 같았다. GPU 실행 완료 후 재개해도 새 계산 파티션은 0개였고 완료 파일과
manifest가 보존됐다.

GPU 실험에는 RTX 4070 Laptop 8GB, PyTorch 2.7.1+cu128, CUDA 12.8을 사용했다.
22번 standalone 비교의 GPU tensor allocated 최고값은 약 70.69MiB였으며 시스템 전체 VRAM 사용량이 아니다.
28번 중첩 실행의 process-tree RSS 최고값은 CPU 약 3.08GiB, GPU 약 4.74GiB였다.

검증 코드는 [historical_gpu.py](../../../../pipeline/version_dependents/historical_gpu.py),
[historical_gpu_parallel.py](../../../../pipeline/version_dependents/historical_gpu_parallel.py)
및 해당 테스트에 있다. 상세 원본은 [22번 측정 증거](../evidence/gpu-32-package-results.json),
[24번 생산 연결 증거](../evidence/production-backends-results.json),
[28번 중첩 증거](../evidence/gpu-overlap-results.json)에서 확인한다.

## 한계와 다음 판단 기준

- 32개 표본은 전체 99,996개 target의 무작위 대표 표본이 아니다. 후보가 매우 많거나
  요구조건이 많은 극단 패키지와 작은 패키지의 분포가 다르다.
- 24번 수치는 공통 입력 준비를 포함하지만 28번 수치는 준비된 입력을 재사용했다.
  두 수치를 이어 붙여 개선율을 만들 수 없다.
- GPU 실험은 서버 EC2 두 대나 Apache Spark 분산 실행을 비교하지 않았다.
- 28번의 scratch와 RSS는 1초 간격 관측값이어서 순간 최고치를 놓칠 수 있다.
- GPU가 전체 흐름에서 유리한 workload 크기와 시작 비용 손익분기점은 아직 측정하지
  않았다. 이를 주장하려면 극단 패키지·작은 패키지·동일 입력 준비·전체 저장 비용을
  포함한 별도 benchmark가 필요하다.

GPU는 병렬 수치 계산을 실제로 빠르게 했고 결과도 CPU와 일치했다.
현재 작업의 전체 시간은 CPU 정규화,
객체 변환, 집계, 저장, 검증과 시작 비용이 함께 결정하므로, 측정된 전체 결과에
따라 CPU 경로를 기본값으로 유지한다.
