# 229개 날짜의 참조 수: 관계를 반복 저장하는 대신 변화를 계산하기

## 문제: 필요한 결과는 관계 목록이 아니라 버전별 숫자였다

목표는 `(패키지, 버전, 스냅샷 날짜)`별로 직접 참조하는 source 패키지·버전 쌍의 수를 구하는 것이었다.
같은 source 버전의 중복 선언은 한 번만 세고, 같은 source 패키지의 서로 다른 버전은 각각 센다.
이 값은 설치 횟수나 여러 단계를 거친 간접 의존자 수가 아니다.

최신 한 날짜의 초기 진단에서는 성공 관계 **280,232,217개**를 집계해 양수 target 버전
**6,156,555개**를 얻었다. 이 관계를 날짜마다 반복해 만드는 방식은 최종 숫자보다 중간 데이터가 커지는 문제를 낳는다.
이 두 수치는 전체 target을 대상으로 한 초기 진단이며, 이후 선정 패키지 결과와 같은 모집단이 아니다.
[초기 진단 기록](../09-diagnostic-run.md)

또한 7번 작업의 단일 관측일 해석 결과를 229개 날짜의 관계 파일로 간주할 수 없었다.
각 기준일까지 포함되는 source·후보 버전을 정하고, 그때 선택되는 target을 다시 계산하는 경로가 필요했다.
최신에 관측한 버전·요구조건을 이용한 과거 재구성이며, 당시 설치나 모든 원본 변경을 실제 관측한 기록은 아니다.
[재구성 입력 계약](../10-historical-count-plan.md)

## 처음 가정과 계산 단위를 정한 과정

처음에는 모든 target 버전에 모든 날짜의 0까지 저장하는 규모를 계산했다. 그 키 수는 **6,971,338,953개**였다.
이는 저장이 반드시 필요한 행 수가 아니라, 전체 모집단을 그런 방식으로 펼쳤을 때의 규모였다.

사용자와 범위를 정한 뒤 **저장할 target은 다운로드 선정 목록의 99,996개 이름**으로 제한했다.
반면 이들을 참조하는 source는 선정 목록으로 제한하지 않았다. 인기 패키지끼리의 참조 수로 의미가 바뀌지 않도록 한 결정이다.
DB 키가 연결된 97,745개 패키지의 유효 버전·날짜를 0까지 저장하는 최종 대상은 **1,007,084,608행**이었다.
미매핑 이름을 조용히 성공한 것으로 처리하지 않았으며, 선정 이름 수와 실제 DB 패키지 수를 구분했다.
[저장 대상 결정 D-22](../06-decisions.md) · [DB 키 확인](../32-full-db-loader.md)

예를 들어 선정 목록 밖의 `A@1`이 선정된 `B@2`를 참조하면 B@2의 count에는 포함된다.
목록은 저장할 target을 고르는 기준이지 참조 source를 제거하는 기준이 아니다.

| 상태 | 해석 |
| --- | --- |
| target이 해당 날짜에 유효하고 count=0 | 계산이 완료된 범위에서 성공적으로 해석된 직접 참조가 0개 |
| target 버전이 그 날짜에는 미배포 | 그 날짜의 저장 대상이 아님. 미래 버전의 0행을 미리 만들지 않음 |
| PARTIAL | 해석하지 못한 관계가 남아 있음. 계산 완료와 함께 존재할 수 있음 |
| 파일 누락·계산 미완료 | 결과가 없는 상태. 정상적인 0으로 대체하지 않음 |

따라서 0을 “어떤 방식으로도 참조되지 않는다”는 뜻으로 확대하지 않는다.
계산·품질·저장 상태를 각각 확인하는 방식은 [정확성 검증 사례](06-correctness-and-recovery.md)에 정리했다.

## 구조 변경: 선택 결과가 유지되는 기간과 바뀌는 순간

작은 기준 구현 H2는 날짜마다 후보를 직접 선택하고 중복을 제거한다. 빠른 운영 경로보다는 결과를 대조할 기준으로 남겼다.
H3는 같은 요구조건을 공유하는 선언의 해석을 묶고, 선택 버전이 유지되는 기간을 계산한다.
source가 등장한 기간과 겹치는 부분만 남긴 뒤, 같은 source-target 쌍의 중복 기간을 합친다.
마지막으로 기간 시작에는 +1, 끝에는 -1을 기록하고 날짜순으로 누적한다.

예를 들어 아래는 실제 패키지 측정값이 아닌 설명용 예제다. 모든 source가 같은 범위를 요구하고,
세 번째 날짜에 새 후보가 가장 높은 만족 버전으로 선택된다고 가정한다.

| 사건 | B@1에 적용할 변화 | B@2에 적용할 변화 | 그날의 count |
| --- | ---: | ---: | --- |
| 첫 날짜에 A@1 등장 | +1 | 0 | B@1=1, B@2는 아직 대상 아님 |
| 둘째 날짜에 A@2 등장 | +1 | 0 | B@1=2, B@2는 아직 대상 아님 |
| 셋째 날짜에 B@2 등장, 두 source의 선택 변경 | -2 | +2 | B@1=0, B@2=2 |

기간 동안 달라지지 않은 같은 관계를 매 날짜 영구 저장하지 않아도 이 숫자를 얻을 수 있다.
다만 기간 생성 자체와 중복 제거도 비용이 있으므로, 구조 변경만으로 빨라졌다고 판단하지 않았다.
[구현·비교 원리](../13-historical-optimization-results.md)

## 실제 전체 실행으로 연결

후속 단계에서는 입력을 한 번 준비하고 target 이름별 묶음에 배치했다. 같은 target의 source 중복 제거가
묶음 간에 갈라지지 않도록 한 뒤 CPU 작업자들이 독립적인 묶음을 계산하도록 했다.
출력 파일도 날짜마다 작은 파일을 반복 생성하는 비용을 줄이는 방향으로 묶었다.
완료 기록과 입력·코드 지문이 일치하는 결과만 재개에서 재사용했다.
[병렬 입력·계산](../26-parallel-input-cpu-execution.md) · [검증·묶음 저장 개선](../27-input-verification-storage-optimization.md)

작업 분할 기준, 작업자 1·2·4개 비교, 병렬화 후 남은 비용과 중단·재개는 [CPU 병렬처리 사례](02-cpu-parallelism.md)에서 다룬다.

실제 최종 실행은 로컬 CPU 작업자 4개, DuckDB 메모리 한도 16GB, 임시 디스크 한도 256GB,
개별 resolver 요청 한도 180초로 수행했다. 아래는 **하나의 전체 실행**에서 측정한 서로 겹치지 않는 단계다.

| 전체 선정 이름 99,996개·229일 | 실측 시간 |
| --- | ---: |
| 입력 준비 | 956.532초 |
| 계산·병합·저장 | 2,409.730초 |
| 최종 검증 | 1,848.813초 |
| 합계 | **5,215.125초 — 1시간 26분 55초** |

128개 계산 묶음을 완료하고 양수 count **296,325,102행**을 Parquet에 저장했다.
이 행 수는 날짜별 숫자의 개수이며 source-target 관계 수가 아니다. 0 포함 행은 이후 DB 적재 때 준비했다.
[전체 실행 기록](../30-full-selected-run.md) · [단계별 시간·파일 검증 증거](../evidence/full-selected-results.json)

## 무엇을 확인했고 무엇이 남았는가

- H2의 작은 기준 계산과 H3의 날짜별 count·선언/source 상태·품질을 비교했다.
- 가중치와 병렬 처리의 실제 표본에서도 기존 결과와 의미상 같은 행이 나오는지 대조했다.
- 최종 전체 실행에서는 산출물과 입력·이력의 연결을 검증했다. 작은 oracle 대조를 전체 10만 이름의 독립 재계산으로 표현하지 않는다.
- 입력 준비·검증을 포함한 전체 시간과 패키지별 부분 연산 시간을 분리했다. 단일 패키지 시간을 10만 배 해 전체 ETA로 쓰지 않는다.
- regular dependencies만 계산하고 배포일 NULL은 제외했다. 미해석은 PARTIAL이며 0은 성공적으로 해석된 관계 범위 안에서의 0이다.
- 서버 성능과 새 날짜 자동화는 이번 로컬 전체 실행의 완료 범위 밖이다.

이 사례의 성과는 숫자가 같아야 하는 기준을 고정한 채, 반복 계산과 중간 데이터의 발생 지점을 바꿔
실제 전체 날짜 계산을 끝낸 것이다. 각 개선의 부분 실험 결과를 이어 곱한 가상의 전체 배수는 제시하지 않는다.
