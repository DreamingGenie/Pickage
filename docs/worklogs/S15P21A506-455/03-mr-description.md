## 개요

의존 수 추이(`package_version_snapshot`)를 재정렬 10만 회차로 229일 전부 다시 계산하고,
운영 표를 **날짜 단위로 교체하는 절차**를 만들어 로컬에서 끝까지 리허설했다.
그 과정에서 V7 이후 모든 DB 에서 적재가 시작되지 않던 결함을 찾아 고쳤다.
운영 반영은 이 MR 범위가 아니다.

## 작업 상세 내용

### 1. 적재기 결함 수정 (`fix` 커밋)

`historical_db_fast_publish.service_contract()` 은 `public.package_version_snapshot` 의
제약이 기본키와 외래키 둘, **정확히 셋**이기를 요구한다. 이 검사는 2026-09-12 에 쓰였고,
V7(2026-09-15, S15P21A506-341)이 `ck_package_version_snapshot_dependents_nonnegative` 를
추가해 넷이 됐다. 검사가 갱신되지 않아 실제 서비스 표를 만나면 이렇게 거부한다.

```
Service DDL differs from the verified four-column contract; review before reload
```

즉 **V7 이후의 모든 DB(운영 포함)에서 참조 수 적재가 한 날짜도 시작되지 않았다.**
09-12 적재가 성공한 것은 그때 표에 아직 그 CHECK 가 없었기 때문이다.

기대 집합에 `CHECK ((dependents_count >= 0))` 를 더했다.

- 부르는 곳은 같은 파일 안 세 곳(`inspect_target`, 계획 비교, 계획 저장)뿐이다.
- 계산 회차의 지문(`historical_parallel.contract()`)에는 이 파일이 들어가지 않아
  **기존 계산 결과를 다시 만들 필요가 없다.** 적재 계획의 지문만 바뀐다.

### 2. 날짜 단위 교체 절차 (`docs` 커밋)

적재 모듈은 원래 새 부모와 229개 자식을 **전부 만든 뒤** 서비스 전환을 따로 한다.
그 방식은 전환 직전 옛 86 GiB 와 새 86 GiB 가 공존하는데, 앱 노드 여유는 50 GB 라
약 36 GB 모자란다. 그래서 날짜 하나씩 붙이고 떼는 방식으로 바꿨다.

- 순간 최대가 하루치(약 1.27 GB)로 줄고, 서비스 부모는 항상 229개를 온전히 갖는다.
- 교체는 `DETACH`/`ATTACH`/`SET SCHEMA` 뿐이라 **데이터를 복사하지 않는다.**
- 옛 파티션은 지우지 않고 백업 스키마로 옮긴다. 제거는 대조를 마친 뒤 별도 단계다.

교체 SQL 이 한 트랜잭션 안에서 검사하는 것.

1. 새 파티션의 기본키·검증된 외래키 2개·`date_bound` CHECK
   (이게 있어야 ATTACH 가 전수 스캔을 건너뛴다 — 실측 9 밀리초)
2. 행 수와 적재 영수증 대조, 영수증의 `child_oid` 와 실제 OID 일치
3. 옛 파티션을 **이름이 아니라 경계값으로** 탐색
4. 두 회차에 공통인 대상의 `dependents_count` **전수 대조**
   (선정 목록은 target 만 고르고 source 는 생태계 전체이므로 값이 같아야 한다)
5. 교체 후 경계·파티션 개수·기본키·상속된 외래키 재확인

## 데이터·파이프라인 영향

- 스키마/테이블 변경 : **없음.** 열·제약·파티션 키 계약은 그대로다. 파티션 내용만 바뀐다.
- 기존 적재 데이터 재처리(backfill) 필요 여부 : **있음.** 운영 229일 파티션을 이 회차로
  교체한다. 이 MR 에는 절차·스크립트만 들어 있고 실행은 별도다.
- 외부 API 호출량·키 사용 변화 : 없음. 기존 Curated/Bronze 산출물만 읽는다.
- 배치 주기·실행 시간 변화 : 없음.

운영 적재 전에 두 가지가 더 필요하다. 명령서 1.3·1.4 절에 절차를 적었다.

1. **달력 계보 등록** — 적재기는 이번 달력 SHA 로 등록된 PUBLISHED 실행을 요구한다.
   달력 파일에 생성 시각이 들어 있어 재생성마다 SHA 가 달라지고, 원본은 로컬에도
   서버 MinIO 에도 없다. `pipeline.snapshot.load` 로 등록하면 날짜는 건드리지 않고
   실행만 연결한다(`LINKED_EXISTING`).
2. **다른 적재기와 동시 실행 금지** — 날짜마다 `package`·`version`·`snapshot`·`etl_*` 에
   SHARE 락을 건다. 다른 로더가 트랜잭션 중이면 `etl_load_execution` 의 RowExclusive 와
   충돌해 10초 만에 실패한다. 리허설에서 실제로 걸렸다.

| **값이 다르면 중단** | 한 행을 777 만큼 틀리게 만들어 확인. `기존 대상의 값이 1 건 다릅니다` 로 중단, 부모·백업·영수증 모두 손대기 전 그대로 |

## 리뷰 요청 사항

1. **적재기 수정의 범위** — `required` 에 CHECK 를 더하는 것이 맞는지. 대안은 제약 비교를
   느슨하게 하는 것인데, 그러면 서비스 표가 조용히 달라져도 지나간다고 판단했다.
2. **교체 SQL 의 `parent` 인자** — 리허설을 격리하려고 부모 테이블을 인자로 받는다.
   오타를 막으려 `public.package_version_snapshot` 또는 `vd193_reload_`/`vd455_` 스키마의
   같은 이름만 허용했다. 운영에서 실수로 스테이징을 가리킬 여지가 남는지 봐 주면 좋겠다.
3. **값 대조 범위** — 운영에서는 `cmp=full` 만 쓴다. `sample`·`none` 은 코드에 있으나
   검증하지 않았고 파일 머리말에 그렇게 적었다. 지우는 편이 나은지 의견을 듣고 싶다.

## 알려진 한계 (이 MR 밖)

- **통합 테스트가 깨져 있다.** `test_historical_db_keys`·`test_historical_db_fast_publish`·
  `test_historical_db_reload` 가 마이그레이션을 이름순 정렬해 앞 3개를 적용하는데,
  V10 이 생긴 뒤로 그게 `V10, V11, V12` 가 되어 `relation "version" does not exist` 로
  실패한다. 이 MR 의 변경과 무관한 기존 결함이라 손대지 않았다.
- **대상 CSV 의 줄끝.** `datasets/targets/*.csv` 에 `.gitattributes` 항목이 없어
  Windows 체크아웃본이 CRLF 가 된다. 고정 SHA 로 쓰려면 LF 로 되돌려 대조해야 한다.
  타워가 별도 MR 로 처리한다.
- 앱 노드로 계산 폴더를 옮길 필요는 없다는 것을 확인했다(`COPY FROM STDIN` 으로
  표준입력에 흘린다). 명령서 5절 참고.
