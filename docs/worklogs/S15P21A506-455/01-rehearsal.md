# 01. 로컬 파티션 교체 리허설

2026-09-23 03:09~03:52 KST, 공유 로컬 PostgreSQL(`pickage-local-postgres-1` / `pickage`)에서
날짜 하나의 교체 절차를 끝까지 연습했다. 운영에는 접촉하지 않았다.

서비스 `public.package_version_snapshot` 을 쓰지 않고 스테이징 부모 두 개로 격리했다.
같은 날짜(2026-08-31)를 두 번 적재해 하나를 "옛 회차", 하나를 "새 회차"로 두고
운영에서 칠 것과 **같은 문장**으로 교체했다.

| --- | --- |

### 229일 전체 추정

| | 기존 10만 회차 | 재정렬 10만 회차 |
| --- | ---: | ---: |
| 총 행 수 | 1,007,079,260 | **1,094,936,926** (+8.7%) |
| 바이트/행 | 91.7 (기존 실측) | **84.69** (이번 실측) |
| 총 크기 | 86 GiB | 약 86.4 GiB |

행은 8.7% 늘지만 바이트/행이 7.6% 작아 **총량은 거의 그대로**다(약 +0.4 GiB).
최신 기준일 하나의 버전 수는 +0.07%(7,823,980 → 7,829,660)인데 229일 누적이 +8.7%인 이유는
재정렬 목록에 과거 날짜부터 존재하던 패키지가 더 많이 들어왔기 때문이다.
**장부에는 누적 수치를 쓴다.**

날짜당 순간 최대는 옛 파티션 + 새 파티션이고, 옛 것을 지워야 비로소 줄어든다.
가장 큰 날짜 기준 순간 최대 약 1.27 GB, 정착 후 약 0.63 GB다.

## 확인한 것

1. **정상 교체** — 공통 7,829,660건 전부 일치, `delta_bytes=0`, 경계·기본키·상속된 외래키 2개 확인.
2. **값이 어긋나면 멈춘다** — 옛 파티션의 한 행을 일부러 777 만큼 틀리게 만들고 교체를 실행했다.
   ```
   ERROR: 기존 대상의 값이 1 건 다릅니다 (공통 7829660 건). 교체를 중단합니다.
   ```
   중단 후 부모의 파티션·백업 스키마·영수증이 **손대기 전 그대로**임을 확인했다.
   전수 대조는 3.5초였다.
3. **복구** — 옛 파티션이 서비스로 돌아오고 영수증이 지워진다. 데이터 복사 없음.
4. **제거 안전장치** — 교체 기록이 없으면 거부한다. 되돌린 상태에서 옛 것을 지우는 사고를 막는다.
5. **제거** — 서비스가 새 회차인지 다시 확인한 뒤에만 지운다. 지운 뒤 633 MB.

## 리허설이 잡은 결함

### 코드 결함 (고쳤다)

`historical_db_fast_publish.service_contract()` 가 서비스 표의 제약을 3개로 기대하는데
실제로는 4개다. 음수 금지 CHECK 가 빠져 있었다.

| 무엇 | 날짜 |
| --- | --- |
| 이 검사 작성 | 2026-09-12 (S15P21A506-193) |
| V6 파티셔닝 | 2026-09-14 (S15P21A506-341) |
| **V7 이 CHECK 추가** | **2026-09-15** (S15P21A506-341) |

검사가 쓰인 사흘 뒤 마이그레이션이 제약을 추가했고 검사는 갱신되지 않았다.
그래서 **V7 이후의 모든 DB(운영 포함)에서 적재가 시작되지 않는다.**
09-12 적재가 성공한 것은 그때 표에 그 CHECK 가 없었기 때문이다.

기대 집합에 `CHECK ((dependents_count >= 0))` 를 추가했다.
영향 반경은 같은 파일 안 세 곳뿐이고, 계산 회차의 지문(`historical_parallel.contract()`)에는
이 파일이 들어가지 않아 **어제 계산한 결과는 그대로 유효하다.**
단위 테스트 22개 중 실행 가능한 7개 통과, 실제 적재로 회귀를 확인했다.

### 교체 스크립트의 빈틈 (고쳤다)

복구는 새 파티션을 떼어 둔 채 끝난다. 그 상태에서 다시 교체하려 하면
"스테이징 부모에 붙어 있지 않다"며 거부됐다. 되돌린 뒤 재시도가 막히는 것은 곤란하다.

붙어 있는 곳이 스테이징 부모이거나 아무 데도 아니면 통과하도록 바꾸고,
대신 **영수증의 `child_oid` 와 실제 OID 가 같은지**를 새로 확인한다.
이름이 같아도 지우고 다시 만든 표라면 여기서 걸린다. 검사는 느슨해지지 않고 옮겨 갔다.

### 운영 절차에 반영할 것

1. **달력 계보** — 적재기는 DB 에 `manifest_sha256` 이 이번 달력과 같은 PUBLISHED 실행이
   있어야 진행한다. 이번 달력은 재생성본이고 파일 안에 생성 시각(`created_at`)이 들어 있어
   **재생성할 때마다 SHA 가 달라진다.** 원본은 로컬에도 서버 MinIO 에도 없다.
   운영에는 다른 SHA 가 등록돼 있을 가능성이 높다. `pipeline.snapshot.load` 로 등록하면
   날짜는 건드리지 않고 실행만 연결한다(`LINKED_EXISTING`). `--verify-only` 로 먼저 본다.
2. **동시 실행 금지** — 적재기는 날짜마다 `package`·`version`·`snapshot`·`etl_*` 에 SHARE 락을
   건다. 다른 데이터셋 적재기가 트랜잭션 중이면 `etl_load_execution` 의 RowExclusive 와
   충돌해 **10초 만에 실패**한다. 리허설에서 실제로 걸렸다(U1 `package_env` 적재).
   타워가 정한 적재 순번은 편의가 아니라 필수 조건이다.
3. **SQL 은 파일로 넣는다** — PowerShell 파이프로 흘리면 인코딩이 깨져
   `syntax error at or near "WHERE"` 같은 엉뚱한 오류가 난다. `docker cp` 후 `-f` 를 쓴다.
4. **실행 위치** — `python -m` 은 cwd 가 PYTHONPATH 보다 앞선다. 고친 코드를 쓰려면
   그 트리에서 실행해야 한다. 아니면 "코드 계약이 바뀌었다"며 거부된다.
5. **pytz** — DuckDB 1.5.5 가 TIMESTAMPTZ 를 파이썬 값으로 바꿀 때 필요하다.
   공유 venv 에는 없다. 적재기를 돌릴 환경에 있어야 한다.

## 정리

리허설 스키마 세 개는 확인을 마친 뒤 제거했다. 공유 DB 에 남긴 것은 229개 기준일
(`snapshot` 표, `ON CONFLICT DO NOTHING`)과 달력 실행 이력 하나다. 둘 다 운영과 같은 값이다.
