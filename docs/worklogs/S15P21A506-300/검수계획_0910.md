## 2. 판정 원칙

1. 제품 의도는 사용자 지시와 명시적 결정사항을 우선한다. 변경분석도 검증 대상이므로 “이미 Figma에서 제거했다”, “실측했다”, “구현되지 않았다” 같은 사실 주장은 원자료로 재확인한다.
2. API 의도는 Notion 명세, 구현 사실은 기준 커밋의 코드와 버전이 확인되는 Swagger로 구분한다. Notion의 서버 반영 여부와 조회 시점을 기록한다.
3. ERD는 설계 모델, Flyway와 SQL은 저장소의 구현 근거로 비교한다. 불일치만으로 어느 한쪽의 오류를 단정하거나 실제 운영 DB에 적용됐다고 가정하지 않는다.
4. 배포 설정과 서버 PDF가 다르면 측정일·환경·실측 여부를 확인한다. 운영 접속이나 부하 실행 없이 확인 가능한 범위를 먼저 검증한다.
5. 코드에 없는 기능은 구현 격차일 수 있다. 코드를 따라 확정된 제품 결정을 자동으로 바꾸지 않는다.
6. 의도적 OPEN은 누락으로 판정하지 않는다. 다만 그 OPEN에 의존하는 완료 조건과 후속 결정 필요성은 기록한다. 다른 문단에서 확정 구현처럼 서술하면 모순 후보로 본다.
7. 사실과 다른 것으로 확인된 항목, 근거를 찾지 못한 항목, 접근하지 못한 항목을 구분한다. 근거 부재만으로 거짓이라고 판정하지 않는다.
8. 예시 JSON·UI 모델·mock·POC·확장 구상을 운영 API 계약 또는 구현 완료 증거로 사용하지 않는다.

- Figma 대상 `485:241`의 실제 이름과 구조를 읽을 수 있다. 아직 모든 화면·상태·프로토타입을 검수한 것은 아니다.
- 다운로드에 `api 결정사항.pdf`, `api 명세.zip`, `api 현황.zip`, `서버 정보.pdf`가 있다. ZIP 목록상 API 상세 endpoint 전체가 확보됐다고 볼 수 없어 Notion 원문과 연결 자료를 추가 확인해야 한다.
- ERD 주소는 일반 HTTP 요청에서 200과 페이지 제목 `v 0.6`을 반환한다. 웹 도구는 본문 접근에 실패했다. 아직 테이블·관계 데이터 자체는 읽지 못했다.
- 정밀 검수에서 ERD의 읽기 가능한 데이터·공개 이미지·브라우저 렌더링 경로를 확인한다. 끝내 세부 구조를 확보하지 못하면 ERD export/DDL/이미지를 요청하고 해당 대조는 미검증으로 남긴다. 그동안 문서·코드 검수는 진행한다.
- 현재 기록된 기준 커밋 이후 변경이나 실제 운영 배포 상태는 별도 증거 없이 최신 상태로 가정하지 않는다.
