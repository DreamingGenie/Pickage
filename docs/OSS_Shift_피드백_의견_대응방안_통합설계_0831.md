# OSS Shift 피드백 대응 및 서비스 개선안

> 개정판 v4 · 2026-09-01  
> 기준 자원: EC2 2대, 서버당 4 vCPU·메모리 15GiB·사용 가능 디스크 약 307GB  
> 중요 제약: 지급된 S3와 별도 공유 저장소 없음

![S3 없는 OSS Shift 시스템 구조](./OSS_Shift_시스템_아키텍처_S3없음_v4.png)

## 한눈에 보는 요약

OSS Shift는 사용자가 npm 패키지를 입력하면 비교할 후보를 자동으로 찾고 다음 보고서를 제공하는 서비스다.

1. **생태계 변화**: 다운로드 수와 의존성 선언 변화를 분석한다.
2. **기능 비교**: 정확한 버전의 npm 배포 파일과 공식 문서에서 근거를 찾고 AI가 차이를 설명한다.
3. **커뮤니티 현황**: 확장 범위에서 검증된 GitHub 저장소의 최근 활동을 요약한다.

이번 개정의 핵심은 다음과 같다.

- S3를 기본 구성에서 완전히 제거한다.
- BigQuery 데이터를 파일로 장기 보관하지 않고 두 서버의 Spark가 직접 나누어 읽는다.
- 원본 전체가 아니라 최종 집계 결과와 기능 근거만 로컬에 저장한다.
- MVP 10만 패키지는 확정 약속이 아니라 성능 시험을 통과해야 하는 도전 목표로 바꾼다.
- 모든 공개 npm 패키지는 입력할 수 있지만 실제 데이터에 따라 페이지별 보고서 품질이 달라진다고 명확히 한다.
- 기능 정보는 전체 패키지에 미리 생성하지 않고 요청된 `패키지@버전`만 수집·캐시한다.
- AI는 수집된 근거만 설명하며 근거가 없으면 `확인 불가`라고 답한다.
- 돈뿐 아니라 조회 횟수, 전송량, 처리 시간, 디스크, 실패 복구까지 비용으로 관리한다.

## 0. 판단 표시

| 표시 | 뜻 |
|---|---|
| 확인됨 | 공식 문서 또는 실제 응답으로 존재를 확인함 |
| 조건부 | 데이터는 있지만 모든 패키지에서 제공되지는 않음 |
| 추정 | 계산식으로 예상했으나 실제 서버에서 측정하지 않음 |
| 실험 필요 | 시험 통과 전에는 기능이나 규모로 약속하지 않음 |
| 제외 | 현재 자원과 일정에서는 제공하지 않음 |

처리 시간이나 비용을 새로 제시하려면 측정 날짜, 입력 규모, 조회량을 함께 남긴다.

## 1. 최종 의사결정

### 유지할 방향

- 사람이 비교 묶음을 미리 만들지 않는다.
- AI가 단독으로 패키지 이름을 지어내지 않도록 실제 검색 결과에서만 후보를 고른다.
- deps.dev BigQuery와 Spark 분산 처리를 생태계 분석의 핵심으로 사용한다.
- npm 웹 화면과 npmtrends를 크롤링하지 않는다.
- 기능 비교는 정확한 버전의 npm 배포 파일을 가장 중요한 근거로 사용한다.
- 패키지 설명과 GitHub 문서는 보조 근거로 사용한다.
- 기능 차이와 함께 어떤 상황에서 어느 패키지가 적합한지 설명한다.

### 바로잡을 방향

- S3 기반 원본·정제본·결과본 저장 구조를 폐기한다.
- 모든 버전과 기능 문서를 미리 저장하지 않는다.
- 10만 패키지를 MVP 확정 수량으로 표현하지 않는다.
- 다운로드 추이는 서비스 시작 시점에 최대 18개월까지만 제공한다.
- 직접 의존과 간접 의존을 분리한다.
- npm 패키지와 GitHub 저장소 연결을 항상 확정 정보로 취급하지 않는다.
- 서로 다른 출처의 조회 시점을 하나의 기준 시점처럼 꾸미지 않는다.
- 실측하지 않은 처리 시간과 월 비용을 확정값으로 쓰지 않는다.

## 2. 피드백별 대응

| 피드백 | 적용 방법 | 개발 영향 |
|---|---|---|
| 인쇄보다 PDF가 필요함 | 서버에서 보고서를 PDF로 생성 | 기준일·패키지 버전·근거 번호를 포함 |
| 회원 기능이 불필요함 | 회원가입과 로그인 제거 | 예측하기 어려운 임시 보고서 주소 사용 |
| package.json 업로드가 불필요함 | 패키지 이름 또는 `패키지@버전`만 입력 | 버전이 없으면 당시 최신 버전을 확정해 저장 |
| GitHub 정보를 보고서에 포함 | 확장 3페이지로 제공 | 저장소 연결 신뢰도가 낮으면 제공하지 않음 |
| 후보별 기능 차이가 중요함 | 실제 배포 파일과 공식 문서를 근거로 비교표 생성 | 근거 없는 칸은 `확인 불가` |
| 다운로드 출처가 불명확함 | npm Downloads API와 조회일 표시 | 초기에는 최대 18개월만 제공 |
| npmtrends 크롤링은 위험함 | npmtrends와 npm 웹 화면 크롤링 제거 | Registry·Downloads API·deps.dev·GitHub API 사용 |
| 분산 처리가 대회 필수임 | BigQuery 데이터를 두 EC2의 Spark가 나누어 계산 | 서버별 작업 기록과 처리량을 시연 |
| S3가 없음 | Storage Read API로 직접 읽고 작은 결과만 로컬 저장 | 원본 장기 보관과 S3 비용 항목 삭제 |

## 3. “모든 npm 패키지 지원”의 정확한 뜻

| 지원 항목 | 지원 조건 | 부족할 때 처리 |
|---|---|---|
| 입력 | 공개 npm Registry에 이름이 존재 | 존재하지 않음을 즉시 안내 |
| 후보 추천 | 검색 결과와 설명·관계 정보가 충분 | 후보 수를 줄이고 낮은 신뢰도를 표시 |
| 다운로드 분석 | npm Downloads API에 기록이 존재 | 가능한 기간만 표시 |
| 의존성 분석 | deps.dev가 해당 버전을 처리 | 누락 기간과 누락 비율 표시 |
| 기능 비교 | 배포 파일에 문서·타입·공개 API 근거가 존재 | 근거 없는 기능은 확인 불가 |
| 커뮤니티 분석 | 정확한 GitHub 저장소를 검증 | 페이지를 숨기거나 연결 불가 표시 |

페이지마다 데이터 품질을 별도로 표시한다.

- **A**: 핵심 항목 대부분에 직접 근거가 있음
- **B**: 일부 근거만 있어 제한적인 비교가 가능함
- **C**: 자료가 부족해 확인 가능한 사실만 제공함

입력이 가능하더라도 모든 페이지가 A등급이라는 뜻은 아니다.

## 4. 사용자 흐름

1. 사용자가 `axios` 또는 `axios@1.20.0`처럼 패키지를 입력한다.
2. Registry에서 패키지 존재 여부와 분석할 정확한 버전을 확인한다.
3. npm 검색과 저장된 최소 정보에서 실제 후보를 찾는다.
4. AI가 검색된 후보를 목적과 사용 환경에 따라 다시 정렬한다.
5. Registry에 실제 존재하는 후보만 사용자에게 보여 준다.
6. 사용자가 비교할 패키지를 고른다.
7. 보고서 기준일과 각 패키지의 정확한 버전을 고정한다.
8. 1페이지는 Spark 집계 결과와 npm 다운로드 기록으로 만든다.
9. 2페이지는 선택된 정확한 버전의 배포 파일로 만든다.
10. 확장 범위에서는 검증된 GitHub 저장소만 3페이지에 추가한다.
11. 완성된 화면과 같은 내용으로 PDF를 생성한다.

## 5. S3 없는 시스템 구조

### 미리 계산하는 과정

1. BigQuery에서 사용할 스냅샷 날짜를 정한다.
2. 필요한 열과 패키지 범위만 쿼리한다.
3. Spark 연결 도구가 BigQuery Storage Read API를 통해 데이터를 여러 흐름으로 나눈다.
4. 두 EC2가 의존 관계와 시계열 집계를 나누어 계산한다.
5. 패키지별·기간별 최종 집계만 PostgreSQL과 압축 파일로 저장한다.
6. Spark 임시 파일은 작업 성공 확인 후 삭제한다.

BigQuery Storage Read API는 열 선택, 조건 밀어넣기와 여러 읽기 흐름을 지원한다. 논리 뷰는 바로 읽을 수 없으므로 필요하면 BigQuery 쿼리 결과를 임시 테이블로 만든 뒤 읽는다. 이 과정에는 BigQuery를 사용할 Google Cloud 프로젝트, 조회 권한, 비용 청구 설정과 AWS에서 Google API로 나가는 네트워크가 필요하다.

### 사용자가 요청할 때 처리하는 과정

1. Registry에서 정확한 버전 정보와 tarball 주소를 받는다.
2. tarball을 임시 공간에 내려받는다.
3. 크기와 파일 수를 검사하고 안전하게 압축을 푼다.
4. `package.json`, README, 타입 선언과 공개 진입점을 분석한다.
5. 기능 주장과 연결되는 짧은 근거만 저장한다.
6. AI가 근거를 검색해 비교표와 설명을 만든다.
7. 임시 tarball과 압축 해제 파일은 삭제한다.

### 두 서버의 역할

| 서버 | 역할 | 주의점 |
|---|---|---|
| EC2 1 | API, PostgreSQL, 작업 관리, Spark Driver와 Worker | 사용자 요청과 배치 작업이 경쟁하지 않도록 상한 설정 |
| EC2 2 | Spark Worker, 기능 자료 추출 작업 | Spark 임시 파일이 디스크를 채우지 않도록 작업별 정리 |

초기 Spark 설정은 서버당 실행 코어 2개, 실행 메모리 6~8GB 수준에서 시작하고 시험 결과에 따라 조정한다. 확정 설정은 아니다.

### 디스크 원칙

약 614GB는 하나의 공유 공간이 아니다. 노드별 디스크가 70%를 넘으면 다음 규모로 확대하지 않는다.

| 구분 | EC2 1 제안 | EC2 2 제안 | 상태 |
|---|---:|---:|---|
| 운영체제·로그 | 40~60GB | 30~50GB | 추정 |
| DB·최종 결과·백업 | 60~100GB | 20~40GB 복제본 | 추정 |
| Spark 임시 공간 | 80~120GB | 140~180GB | 추정 |
| 비상 여유 | 최소 70GB | 최소 70GB | 초기 안전 기준 |

전체 npm 원본, BigQuery 원본과 모든 tarball은 보관하지 않는다. HDFS 복제 수 2는 실질 용량을 한 서버 수준으로 줄이고 두 노드만으로 고가용성을 만들 수 없으므로 기본 구조에서 제외한다. Spark 분산 처리 자체는 HDFS 없이도 증명할 수 있다.

### 장애 복구의 한계

- 실패하면 같은 BigQuery 스냅샷과 쿼리 조건으로 다시 읽는다.
- 작업 번호, 스냅샷, 쿼리 해시, 코드 버전과 처리 범위를 저장한다.
- 최종 집계와 DB 백업은 다른 EC2에도 복사한다.
- 두 서버가 동시에 손실되면 복구할 외부 저장소가 없다.
- 따라서 현재 구조는 대회·MVP용이며 상용화에는 외부 백업이 필요하다.

## 6. 패키지 수와 선별 방식

| 단계 | 패키지 수 | 의미 |
|---|---:|---|
| 1차 시험 | 1천 | 데이터 형태와 오류 확인 |
| 2차 시험 | 1만 | 기본 분산 처리 검증 |
| MVP 기준 후보 | 3만 | 지급 자원에서 반복 실행 검증 |
| 확장 시험 | 5만 | 디스크·네트워크·처리 시간 확인 |
| 도전 목표 | 10만 | 앞 단계 통과 시에만 MVP 포함 검토 |
| 장기 확장 | 20만 이상 | 서버 또는 외부 저장소 추가 후 검토 |

10만 개의 이름과 간단한 통계를 저장하는 것과 10만 개의 모든 버전·관계·문서를 저장하는 것은 다르다. 패키지 수는 반드시 처리 범위와 함께 표현한다.

### 기본 선별 조건

- npm 이름이 유효함
- deps.dev에서 하나 이상의 정상 릴리스를 확인할 수 있음
- 최근 배포 시점 또는 다운로드 기록이 있음
- 삭제·보안 보류·명백한 자동 생성 복제본이 아님
- 버전이 많아도 대표 버전으로 줄일 수 있음

선별 점수에는 최근 직접 의존 패키지 수, 다운로드, 최근 릴리스, 저장소 활동, 문서 존재와 데이터 완성도를 사용한다. 가중치는 검증된 사실이 아니라 1만 개 표본에서 분야별 편향을 확인하며 바꾸는 실험값이다.

### 모든 버전을 처리하지 않는 방법

- 최신 안정 버전은 포함한다.
- 분기 상태는 그 분기 마지막 시점에 유효했던 버전을 이어서 사용한다.
- 의존 선언이 바뀐 버전은 포함한다.
- 변화가 없는 중간 버전은 생략한다.
- 패키지당 대표 버전 상한은 실제 분포를 본 뒤 정한다.

## 7. 사람이 Cohort를 만들지 않는 후보 추천

AI가 기억만으로 후보를 만들면 존재하지 않거나 목적이 다른 패키지가 섞일 수 있다. 검색과 검증을 먼저 하고 AI는 정렬과 설명을 맡는다.

1. 입력 패키지의 이름, 설명, 키워드와 README 첫 부분을 읽는다.
2. npm Registry 검색에서 최대 30~50개 후보를 받는다.
3. 저장한 최소 패키지 정보에서 설명과 사용 관계가 비슷한 후보를 보충한다.
4. Registry에서 실제 존재 여부를 다시 확인한다.
5. 실행 환경, 모듈 방식, 타입, 최근 활동과 직접 의존 신호로 10~20개로 줄인다.
6. AI가 같은 문제를 해결하는지 근거와 함께 평가한다.
7. 최종 3~5개와 추천 이유를 보여 준다.

AI가 추가 이름을 제안해도 Registry 존재 확인과 용도 검증을 통과하지 못하면 노출하지 않는다.

후보 추천용으로 미리 저장하는 정보는 이름, 최신 버전, 설명, 키워드, 최근 배포 시점, 타입·모듈 신호, 직접 의존 집계, 다운로드 집계와 검증된 저장소 주소 정도다. 10만 패키지의 상세 기능 설명과 AI 요약은 만들지 않는다.

## 8. 보고서 1페이지: 생태계 변화

### 다운로드 변화

npm Downloads API를 사용하고 출처와 조회일을 화면·PDF에 표시한다.

- 묶음 조회: 한 번에 최대 128개 패키지, 최대 365일
- 개별 기간 조회: 한 번에 최대 18개월
- 버전별 다운로드: 최근 7일
- 서비스 시작 시 과거 3년을 소급해 만들 수 없음

MVP는 최대 18개월을 제공한다. 운영 후 일별 결과를 계속 저장하면 그 시점부터 더 긴 기간을 제공할 수 있다.

### 의존성 선언 변화

| 목적 | deps.dev BigQuery 데이터 | 주의점 |
|---|---|---|
| 패키지와 버전 | `PackageVersionsLatest` | 처리 실패와 릴리스 여부 확인 |
| npm 의존 선언 | `NPMRequirementsLatest` | 일반·개발·선택·동료 의존 구분 |
| 해석된 의존 관계 | `DependenciesLatest` | 범위가 실제 어떤 버전으로 해석됐는지 확인 |
| 역의존 참고 | `DependentsLatest` | 직접·간접 관계가 섞일 수 있음 |
| 프로젝트 연결 | `PackageVersionToProjectLatest` | 확정 연결이 아니므로 신뢰도 필요 |

직접 의존 패키지 수는 `NPMRequirementsLatest`의 선언을 역으로 집계한다. `DependentsLatest`를 곧바로 직접 사용자 수라고 부르지 않는다.

분기 $t-1$과 $t$에서 패키지 $P$를 직접 선언한 관측 프로젝트 집합을 $D_{t-1}(P)$와 $D_t(P)$라고 할 때 다음처럼 계산한다.

- 유지: $|D_{t-1}(P) \cap D_t(P)|$
- 유입: $|D_t(P) - D_{t-1}(P)|$
- 이탈: $|D_{t-1}(P) - D_t(P)|$

이는 deps.dev가 관측한 공개 생태계 안의 값이지 전체 npm 사용자를 뜻하지 않는다. 버전 고착과 교체 흐름은 확장 범위이며, 교체 흐름은 인과 관계가 아니라 관측 신호로 표시한다.

## 9. 보고서 2페이지: 기능 비교

### 9.1 데이터가 실제로 존재하는가

npm이나 deps.dev에 `인터셉터 지원=true`, `브라우저 지원=true` 같은 표준 기능 표는 없다. 실제로 가져올 수 있는 것은 패키지 메타데이터, 정확한 버전의 배포 파일, 문서, 타입 선언과 공개 API다. 서비스가 이 원재료에서 근거를 찾는다. RAG와 AI는 없는 정보를 만들어 주지 않는다.

### 9.2 출처 우선순위

| 순위 | 출처 | 가져오는 정보 | 사용 조건 |
|---:|---|---|---|
| 1 | Registry 정확한 버전 | 버전, tarball, 무결성, 크기, 진입점, 타입, 의존성 | `패키지@버전` 일치 |
| 2 | 해당 버전 tarball | 실제 `package.json`, README, 타입, 공개 파일 | 무결성 확인과 안전한 압축 해제 |
| 3 | provenance·`gitHead` | 배포본과 소스 커밋 연결 | 필드가 있을 때만 |
| 4 | 검증된 GitHub 태그·커밋 | 릴리스 문서 보충 | 저장소와 버전 연결이 확인될 때만 |
| 5 | GitHub 기본 브랜치 | 누락 문서 탐색 | 과거 버전의 확정 근거로 사용하지 않음 |

### 9.3 실제로 추출하는 값

프로그램이 `package.json`에서 AI보다 먼저 직접 읽는 값은 다음과 같다.

- `name`, `version`, `engines.node`
- `type`, `main`, `module`, `exports`
- `types` 또는 `typings`
- `browser`, `react-native`, `sideEffects`
- `dependencies`, `peerDependencies`, `optionalDependencies`
- `repository`, `homepage`, `license`
- `dist.tarball`, `dist.integrity`, `dist.fileCount`, `dist.unpackedSize`

tarball에서는 README 제목과 기능 구간, 공개 타입·함수 이름, 공개 진입점, 예제 코드, 오류 클래스, 설정 항목과 지원 환경의 명시적 문장을 읽는다. 내부 코드와 테스트 전체를 AI에 넣지 않는다.

### 9.4 안전·용량 상한

| 항목 | 초기 상한 | 초과 시 처리 |
|---|---:|---|
| 압축 파일 | 25MB | tarball 분석 중단 |
| 압축 해제 결과 | 100MB | 즉시 중단·삭제 |
| 파일 수 | 2,000개 | 허용 파일만 부분 분석 |
| 보관 텍스트 | 패키지당 3MB | 중요 구간 우선 |
| 근거 조각 | 패키지당 100~200개 | 중복 제거 |
| 수집 시간 | 패키지당 60초 | 제한 분석으로 전환 |

이 수치는 100개 표본의 실제 분포를 본 뒤 조정한다.

### 9.5 근거 데이터 형식

```json
{
  "package": "axios",
  "version": "1.20.0",
  "feature_id": "request_response_interceptors",
  "value": "SUPPORTED",
  "claim": "요청과 응답 인터셉터용 공개 API를 제공한다.",
  "source_type": "TARBALL_README",
  "file_path": "package/README.md",
  "section": "Interceptors",
  "evidence": "instance.interceptors.request.use(...) / response.use(...)",
  "evidence_hash": "sha256:...",
  "confidence": "HIGH",
  "collected_at": "2026-09-01T00:00:00Z",
  "extractor_version": "feature-extractor-1"
}
```

긴 원문 전체 대신 출처 위치, 짧은 근거, 해시, 수집 시각과 추출기 버전을 저장한다.

### 9.6 기능 리포트 생성 순서

1. 선택한 패키지의 정확한 버전을 고정한다.
2. `package@version` 캐시가 있으면 같은 무결성의 기존 결과를 사용한다.
3. 캐시가 없으면 Registry 메타데이터와 tarball을 받는다.
4. 프로그램이 JSON 값과 공개 API를 먼저 추출한다.
5. README와 타입 파일을 제목·기능 단위로 나눈다.
6. 고정 비교 항목과 분야별 추가 항목을 만든다.
7. 단어 검색과 문서 유사도 검색으로 항목별 근거를 찾는다.
8. AI가 근거만 사용해 `지원`, `제한적 지원`, `확인 불가`로 분류한다.
9. 서버가 근거 번호, 패키지와 버전을 다시 검사한다.
10. 근거 없는 문장을 제거하고 비교표와 선택 기준을 만든다.

공통 비교 항목은 실행 환경, ESM·CommonJS, 타입, 브라우저, 공개 API, 인스턴스 설정, 인터셉터, 취소·시간 제한, 오류, 스트림, 리다이렉트, 프록시, 직렬화, 쿠키와 외부 의존성이다. 이후 분야별로 3~8개를 추가한다.

### 9.7 부정 판단 규칙

- 문서에서 못 찾았다는 이유만으로 `지원하지 않음`이라고 쓰지 않는다.
- 공개 타입과 export 전체, 명시적 제한 문장을 확인했을 때만 부정 판단한다.
- 그 외에는 `확인 불가`라고 표시한다.
- 확인 불가는 실패가 아니라 환각을 막는 정상 결과다.

### 9.8 실제 예시: axios와 node-fetch

다음 값은 2026-09-01에 실제 npm 응답과 공식 문서에서 확인했다. 구현에서는 같은 값을 해당 버전 tarball에서 다시 확인한다.

| 값 | `axios@1.20.0` | `node-fetch@3.3.2` | 원자료 |
|---|---|---|---|
| 버전 | `1.20.0` | `3.3.2` | Registry·npm 정보 |
| `type` | `module` | `module` | `package.json` |
| 기본 진입점 | `./dist/node/axios.cjs` | `./src/index.js` | `main` |
| 타입 | `index.d.ts` | `./@types/index.d.ts` | `types` |
| CommonJS | `exports.require`가 CJS 파일을 가리킴 | 공식 README가 v3는 ESM 전용이라고 명시 | `exports`, README |
| 실행 환경 | browser와 Node 진입점 존재 | Node.js용이라고 명시 | `browser`, `exports`, README |
| Node 조건 | 명시적 `engines.node` 없음 | `^12.20.0 || ^14.13.1 || >=16.0.0` | `engines.node` |
| 파일 수 | 89 | 17 | `dist.fileCount` |
| 압축 해제 크기 | 1,983,343바이트 | 107,319바이트 | `dist.unpackedSize` |
| 직접 의존성 | 4개 | 3개 | `dependencies` |
| tarball | `axios-1.20.0.tgz` | `node-fetch-3.3.2.tgz` | `dist.tarball` |

Axios의 공식 README는 브라우저와 Node 사용, 사용자 정의 인스턴스, 요청·응답 인터셉터와 AbortController 취소를 명시한다. node-fetch의 공식 README는 Node.js용 Fetch API, ESM 전용, Node 스트림, gzip·deflate·brotli 해제, 리다이렉트·응답 크기 제한을 명시한다.

| 비교 항목 | axios | node-fetch | 판단 근거 |
|---|---|---|---|
| 주 사용 환경 | 브라우저와 Node.js | Node.js | 메타데이터와 공식 설명 |
| 모듈 | ESM과 CommonJS 진입점 | v3 ESM 전용 | `exports.require`, README |
| API 성격 | 자체 HTTP 클라이언트 | Fetch 표준에 가까운 API | 목적과 공개 API |
| 인스턴스 설정 | `axios.create()` 제공 | 같은 형태의 전용 API 근거 없음 | 공개 사용법 |
| 인터셉터 | 요청·응답 API 명시 | 전용 API를 확인하지 못함 | Interceptors 구간과 공개 API |
| 취소 | AbortController | AbortSignal | 각 README 예제 |
| TypeScript | 타입 포함 | 타입 포함 | `types` |
| 배포 크기 | 약 1.98MB | 약 0.11MB | `dist.unpackedSize`; 성능을 뜻하지 않음 |

사용자에게는 다음처럼 설명한다.

> 브라우저와 Node.js에서 같은 클라이언트 설정을 쓰고 공통 헤더, 인터셉터, 인스턴스 기본값이 필요하다면 axios가 더 직접적인 선택이다. CommonJS에서도 별도 우회 없이 사용할 수 있다.  
> Node.js에서 Fetch 방식 API를 유지하고 패키지 구성이 작은 쪽을 원한다면 node-fetch가 단순하다. 다만 v3는 ESM 전용이므로 CommonJS 프로젝트에는 전환 또는 비동기 import가 필요하다.  
> node-fetch에서 인터셉터가 불가능하다고 단정하지 않는다. 이번 근거에서는 axios와 같은 전용 인터셉터 API를 확인하지 못했다고만 표시한다.

### 9.9 조회·시간 비용

| 작업 | 패키지당 횟수 | 비고 |
|---|---:|---|
| Registry 버전 조회 | 1회 | 메타데이터 확인 |
| tarball 다운로드 | 1회 | 크기는 패키지마다 다름 |
| provenance | 0~1회 | URL이 있을 때만 |
| GitHub 보충 | 0~5회 | 정확한 저장소·커밋이 있을 때만 |
| AI 기능 추출 | 0~1회 | 규칙으로 충분하면 미사용 |
| AI 최종 비교 | 묶음당 1회 | 근거만 전달 |
| 답변 수정 | 묶음당 0~1회 | 근거 검사 실패 시 |

패키지 3개 비교의 최소 네트워크 작업은 Registry 3회와 tarball 3회로 6회다. GitHub와 AI는 선택적으로 추가된다.

캐시 적중, 처음 분석하는 작은 패키지, 큰 패키지를 나누어 처리 시간을 측정한다. 기존 문서의 10~60초는 성능 사실로 사용하지 않는다.

### 9.10 캐시

- 키는 `패키지@버전 + tarball 무결성`으로 만든다.
- 추출기와 모델 버전을 기록한다.
- `latest`가 가리키는 버전만 6~24시간 뒤 재확인한다.
- 원본 tarball은 추출 후 삭제한다.
- 상세 기능 캐시는 사용 빈도에 따라 정리한다.

## 10. 보고서 3페이지: GitHub 현황

저장소 연결은 npm `repository` → provenance·`gitHead` → deps.dev 연결 → 실제 저장소의 패키지 파일·릴리스 태그 확인 순서로 검증한다. 모노레포는 `저장소 기준`이라고 표시한다.

우선 제공할 항목은 최근 릴리스, 최근 커밋, 열린 이슈·PR 수, 보관 여부와 최근 주요 릴리스 요약이다. 이슈 최초 응답 시간, 기여자 변화와 Discussion 분석은 많은 페이지와 댓글을 읽어야 하므로 호출량 시험 후에만 제공한다.

GitHub REST API의 일반적인 한도는 미인증 시간당 60회, 일반 인증 시간당 5,000회다. 이외에도 분당 요청 점수, 동시 요청과 처리 시간 제한이 있다.

## 11. 비용 계산

비용은 돈, 조회 횟수, 대기 시간, 서버 점유와 실패 복구를 모두 뜻한다.

### BigQuery와 Spark

| 비용 | 계산 | 확인 방법 |
|---|---|---|
| BigQuery 조회 | 실제 읽은 바이트 × 적용 단가 | Dry Run·실행 기록 |
| Storage Read | 실제 스캔·반환 바이트 | 감사 로그 |
| Google Cloud→AWS 전송 | 반환 바이트 × 지역별 단가 | 청구·네트워크 사용량 |
| Spark CPU | 서버별 실행 시간 × 코어 | Spark 기록 |
| Spark 디스크 | 노드별 최대 셔플·임시 파일 | 시스템 측정 |
| 재시도 | 실패 작업의 재조회·재계산 | 작업 이력 |

Google Cloud 프로젝트의 지역과 결제 방식이 확정되지 않았으므로 월 정액을 제시하지 않는다.

### 기능 비교

- npm 조회 = 패키지 수 × 메타데이터 1회
- tarball 전송 = 선택한 tarball 실제 바이트 합계
- GitHub 조회 = 저장소별 실제 REST·GraphQL 호출 수
- AI 입력 = 실제 근거 토큰 × 모델 입력 단가
- AI 출력 = 실제 보고서 토큰 × 모델 출력 단가
- 처리 시간 = 다운로드 + 해제 + 추출 + 검색 + 생성

모델명은 `GPT-5.5`로 고정하지 않는다. 개발 시점에 실제 제공 모델과 공식 가격을 확인하고 품질·시간·비용을 비교한다.

월 비용은 월 보고서 수, 보고서당 패키지 수, 캐시 적중률, tarball 평균·상위 95% 크기, AI 토큰, BigQuery 조회·반환량, GitHub 호출과 Spark 시간을 측정한 뒤 계산한다.

## 12. 저장 용량

장기 저장하는 것은 검색용 최소 정보, Spark 최종 집계, 다운로드 집계, 기능 주장과 근거 위치·해시, 보고서·PDF, 작업 기준일과 버전이다.

장기 저장하지 않는 것은 BigQuery 원본, 모든 npm 버전의 복제본, 모든 tarball, GitHub 원문 전체, 중복 AI 입력과 Spark 셔플이다.

```text
최종 저장량 = 검색용 최소 정보
            + 시계열 집계
            + 기능 캐시
            + 보고서와 PDF
            + DB 색인과 백업
```

100개 표본에서 평균과 상위 95% 크기를 측정한 뒤 1만·3만·5만·10만 규모로 계산한다. 고정 GB 수치를 먼저 약속하지 않는다.

## 13. 보안과 남용 방지

- npm 이름 규칙으로 입력을 검사한다.
- Registry가 돌려준 tarball 주소만 허용한다.
- 내부 IP, 로컬 파일과 임의 URL을 읽지 못하게 한다.
- 절대 경로, 상위 경로 이동과 심볼릭 링크를 거부한다.
- 압축 크기와 해제 크기를 제한한다.
- `npm install`과 `postinstall`을 실행하지 않는다.
- JavaScript를 실행하지 않고 정적으로 읽는다.
- README의 지시문은 데이터로만 취급한다.
- AI 출력은 정해진 JSON 구조와 값으로 검사한다.
- 익명 요청은 IP·열람 주소·시간 단위로 제한한다.
- GitHub와 AI 비밀키를 브라우저에 전달하지 않는다.

- 사용할 AI API와 예산

### 데이터 시험

서로 다른 분야의 npm 패키지 100개에서 메타데이터, tarball, README·타입·exports, 저장소 연결, deps.dev 처리, 다운로드 기간, 파일 크기와 수를 측정한다.

### 기능 비교 시험

최소 10개 분야의 비교 묶음 100개를 사람이 검토한다. 근거 연결 비율, 잘못된 주장, 부정 판단 오류, 확인 불가 비율, 캐시 전후 시간, 호출 수, 전송량과 AI 토큰을 기록한다. 근거 없는 확정 문장이 나오면 수정 후 재시험한다.

### Spark 규모 시험

1천 → 1만 → 3만 → 5만 → 10만 순서로 늘린다. 조회 바이트, 반환 바이트, 서버별 행 수, 시간, 메모리, 디스크, 셔플, 실패, 재시도, 최종 저장량과 재현성을 기록한다.

다음 조건을 만족하지 못하면 확대하지 않는다.

- 메모리 부족 0건
- 노드별 디스크 70% 미만
- 서비스 API와 DB 정상 응답
- 같은 스냅샷으로 실패 작업 재실행 가능
- 대회 운영 시간 안에 반복 실행 가능
- BigQuery·네트워크 비용이 승인 예산 안에 있음

### GitHub 시험

저장소 100개에서 호출 수, 페이지 수, 제한·재시도, 평균·상위 95% 시간, 연결 실패와 모노레포 비율을 측정한다. 안정화 전에는 댓글 전체 분석을 추가하지 않는다.

## 16. MVP 완료 기준

- 실제 존재하는 패키지만 후보로 표시한다.
- 추천 이유에 사용 환경과 목적 차이가 포함된다.
- 보고서의 패키지 버전이 끝까지 바뀌지 않는다.
- 다운로드 출처와 기간이 표시된다.
- 직접·간접 의존을 혼용하지 않는다.

- 서버별 처리량·작업 기록·최대 메모리·디스크를 시연할 수 있다.

- 5만·10만은 검증된 경우에만 지원 수량으로 표기한다.
- PDF가 화면의 기준일·버전·근거를 유지한다.

## 18. 최종 결론

핵심 아이디어는 구현 가능하지만 범위는 다음처럼 정직하게 정의해야 한다.

- 모든 공개 npm 패키지를 입력받을 수 있다.
- 모든 패키지의 모든 버전과 기능을 미리 저장하지 않는다.
- 대규모 의존 관계 계산은 BigQuery와 두 서버의 Spark가 맡는다.
- 기능 비교는 사용자가 고른 정확한 버전을 요청 시 분석한다.
- AI는 근거를 설명하고 근거가 없으면 확인 불가라고 답한다.
- S3가 없으므로 실패 시 같은 BigQuery 스냅샷을 다시 읽는다.
- 지급 자원으로 3만 패키지를 먼저 증명하고 5만·10만은 시험 후 도전한다.
- 시간, 저장량과 비용은 표본·Dry Run 전에는 확정 숫자로 약속하지 않는다.

이 구조라면 고정 Cohort 없이 후보를 만들면서 기능 비교의 환각을 줄이고 Spark 분산 처리의 실제 역할도 분명하게 보여 줄 수 있다.
