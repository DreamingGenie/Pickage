## 1. 한눈에 보는 결론

### 서비스 한 문장

Pickage는 사용자가 검토 중인 npm 패키지를 입력하면 순수 의미 검색 뒤 보완재·노후·실체 미달 구조적 자격 관문을 통과한 비교 후보를 발견하도록 돕고, 사용자가 선택한 최대 3개 패키지의 직접 의존 선언 수 추이와 Snapshot 간 증감·다운로드 추이·최신 DB Snapshot 기반 Version Share를 하나의 보고서로 제공한다. 현재 구현된 plugin/adapter·same-family 관문은 이 목표 관문의 부분 구현이며 AI팀 검증 전에는 확정 관문 전체와 동일시하지 않는다.

### 서비스가 답하는 질문

- 이 패키지와 목적이 가깝고 실제 공개 생태계에서도 비교할 의미가 있는 npm 패키지는 무엇인가?
- 비교할 패키지를 내가 직접 선택하거나 바꿀 수 있는가?
- 공개 생태계에서 직접 Dependency와 Downloads는 어떻게 변하고 있는가?
- 선택한 major 계열의 직접 Dependency 변화는 전체 추이와 어떻게 다른가?
- 선택한 조회 구간의 처음과 끝 사이에 직접 의존 선언 수가 얼마나 증가하거나 감소했는가?
- 최신 DB Snapshot에서 버전별 의존 수를 major로 합산하면 어떤 계열이 어느 비중인가?
- 일부 자료가 없거나 처리에 실패한 경우 결과와 어떻게 구분되는가?
- 팀에 공유할 수 있도록 생태계 분석과 현재 선택 버전 기능 비교를 함께 담은 PDF를 받을 수 있는가?

확장 기능이 제공되는 경우에는 정확한 버전의 기능 차이와 근거, GitHub 커뮤니티의 현재 논의까지 추가로 확인할 수 있다.

### 서비스가 결정하지 않는 것

- 가장 좋은 패키지
- 사용자가 최종 선택해야 할 패키지
- 기술 품질 순위
- 후보 순위만으로 본 기술 우열
- 실제 설치·실행·호출량
- Snapshot 간 직접 의존 선언 수 증감만으로 본 개별 dependent의 유지·유입·이탈
- 특정 패키지가 교체된 이유
- 앞으로 성공하거나 사라질 패키지

## 2. 문제와 기회

패키지를 선택하려는 개발자는 관련 후보, 다운로드, 의존 관계, 버전 분포를 서로 다른 위치에서 확인해야 한다. 검색 결과의 이름이나 설명만 비슷하다고 해서 실제로 비교할 가치가 있는 후보라는 보장도 없다. 반대로 다운로드 같은 인기 지표 하나만으로 후보를 고르면 목적이 다른 패키지가 섞일 수 있다.

기존 탐색 과정에는 다음 문제가 있다.

| 문제 | 사용자에게 생기는 어려움 |
|---|---|
| 후보 탐색이 분산됨 | 익숙한 패키지만 비교하거나 검색 결과의 인기에 의존함 |
| 구조적 자격 확인 없이 의미 유사도만으로 후보를 고름 | 설명은 비슷하지만 보완재·방치·실체 미달 패키지가 상위 후보가 될 수 있음 |
| 인기 지표만으로 후보를 고름 | 목적이 다른 대형 패키지가 후보를 잠식할 수 있음 |
| 의존 관계 범위가 넓음 | MVP부터 모든 의존 관계를 보여주면 분석 비용과 해석 부담이 커짐 |
| 시계열과 스냅샷이 섞임 | Version Share를 변화 추이로 오해하거나 기준일이 불명확해질 수 있음 |
| 공개 수치의 의미가 혼동됨 | 의존 선언·다운로드를 실제 설치량이나 기술 품질로 오해할 수 있음 |
| Snapshot 총수 변화의 의미가 혼동됨 | 이전·현재 총수 차이를 개별 dependent의 유지·유입·이탈로 오해할 수 있음 |
| 공유 문서를 다시 작성함 | 화면 결과를 복사해 별도 보고서를 만드는 시간이 듦 |

Pickage MVP는 `후보 발견 → 비교 대상 확정 → 직접 의존 관계·Downloads 확인 → 최신 Version Share 스냅샷 확인`을 하나의 사용자 여정으로 연결한다. PDF 공유는 기능 비교가 제공되는 확장 단계에 추가한다.

정확한 버전의 기능 비교와 근거 검토는 가치가 크지만 수집·정적 분석·RAG·판정 검증 비용이 크므로 MVP에서 분리하고 확장 기능으로 설계한다.

## 5. 서비스 구조

## 6. 전체 사용자 경험

### 6.1 서비스 이해

사용자는 첫 화면에서 다음을 먼저 이해한다.

- 이 서비스는 순수 의미 검색으로 후보 풀을 넓게 찾고, 보완재·생존·실체의 구조적 자격 관문을 거쳐 비교 후보를 발견하도록 돕는다.
- MVP는 공개 npm 생태계에서 관측된 직접 의존 선언 수 추이와 조회 구간 첫·마지막 유효 관측 간 증감, Downloads의 변화, 최신 DB Snapshot 기반 Version Share를 보여준다.
- MVP의 Snapshot 증감은 두 시점의 총수 차이일 뿐 개별 dependent의 유지·유입·이탈을 의미하지 않는다.
- 기술적으로 가장 좋은 패키지를 추천하거나 최종 선택을 대신하지 않는다.
- 기능 비교와 GitHub 커뮤니티 분석은 확장 기능이다.

사용자는 `패키지 분석 시작`을 선택해 분석 흐름에 진입한다.

### 6.2 패키지 입력

사용자는 npm 패키지명 하나만 입력한다. 후보를 정하기 전에는 버전을 요구하지 않는다.

입력 중에는 `/packages/search?q=...` 접두사 자동완성으로 DB 패키지명을 제시한다. 사용자는 목록을 선택하거나 입력 문자열을 그대로 Enter/`패키지 확인`으로 제출할 수 있다. 제출된 이름은 `/packages/similar`의 `not_found` 응답을 통해 서버에서 존재 여부를 검증하며, 존재하지 않으면 입력 단계에 오류를 표시하고 후보 선택으로 진행하지 않는다.

자동완성은 사용자가 입력한 접두사에 맞는 실제 패키지명을 나열하는 탐색 보조다. 시스템이 다른 패키지명을 추측해 자동 교체하지는 않지만, 목록에 없는 자유 입력 자체를 차단하지도 않는다.

### 6.3 관련 후보 선택

후보 화면에서는 기준 패키지와 관련 후보를 함께 보여준다.

#### 후보 결정 원칙

후보 선정은 순수 의미 검색, 구조적 관문, 최종 정렬을 분리한다(`DEC-RANK-20260910-01`). 검색 후보 수와 화면에 보여주는 후보 수는 같은 값이 아니다.

**1단계 — 의미 후보 풀**

- description·keywords 기반 cos 의미 유사도로 `search_k=N`개를 넓게 찾는다.
- popularity·Downloads·채택도는 검색이나 임베딩 학습 신호에 넣지 않는다.
- `N`은 화면 노출 최대 3개와 별도다. 현재 배치 기본값은 30이며 최종 운영값은 30·50·100 평가 후 확정한다.

**2단계 — 구조적 관문과 최종 정렬(v1 계약)**

- 보완재·노후·실체 미달 후보는 점수를 조금 깎는 대신 관문에서 제외한다.
- 관문 통과 후보는 cos 유사도만으로 정렬한다. dependents 수는 cos 동점 tie-break에만 사용한다.
- deprecated 패키지는 기준과 후보에서 모두 제외하며 별도 추천 경로를 만들지 않는다.
- npm Downloads는 후보/생태계 맥락 보조 정보로만 제공하고 ranking 입력으로 사용하지 않는다.
- 관측된 대체 이동 신호(`move_lift`)와 대체 이동 쌍은 순위 가산에 사용하지 않는다. deprecated→대체·migration pair는 모델 학습 positive pair로만 사용한다.

후보 화면에는 정렬 결과인 `유사도 순위`를 표시하되 수치형 `score`나 관문 판정은 노출하지 않는다. v1 내부 구조와 OPEN 파라미터는 개발 구상안의 시스템 아키텍처 확정안을 따른다. 계수 튜닝으로 후보 품질을 맞추지 않는다.

후보 랭킹은 기술 품질 순위가 아니라 `비교 후보로서의 현실적인 관련성`을 정리하는 내부 기준이다.

> **현재 후보 API**
> `GET /packages/similar?name={name}&limit={limit}`가 구현되어 있다. 기본 `limit`은 20, 최대 50이며 응답에는 `base`, `model_ver`, `data_status`, `candidates(rank, score, name, latest_version, description)`, `not_found`가 포함된다. 화면은 순서·rank·이름·최신 버전·설명을 사용하고 수치 score는 표시하지 않는다. Notion 정본 반영 여부와 배치→PostgreSQL 게시 자동화는 별도 정합 과제로 남는다.

#### 최초 상태

- 기준 패키지는 항상 선택 상태다.
- 정렬 상위 후보를 최대 3개 카드로 표시하지만 기본 선택하지 않는다.
- 하단에는 최초 `1 / 3 선택됨`과 기준 패키지만 나타난다.

기준 패키지는 후보 카드 최대 3개에 포함하지 않으며 사용자가 해제할 수 없다.

- 후보 카드: 기준 패키지를 제외한 최대 3개
- 최종 비교 대상: 기준 패키지를 포함한 최대 3개

후보를 미리 선택하지 않아 사용자가 비교 조합을 직접 확정하게 한다. 사용자는 후보를 선택·해제하거나 다른 npm 패키지를 자유 입력할 수 있다. 직접 추가는 `/packages/search` 결과에 입력과 정확히 같은 이름이 포함됐는지 확인한 뒤 적용한다.

#### 최대 3개 제한

한 보고서에서 비교 가능한 패키지는 기준 패키지를 포함해 최대 3개다. 이미 3개가 선택된 상태에서 다른 후보나 직접 추가 패키지를 넣으려면 기존 후보 하나를 먼저 해제해야 한다.

서비스는 사용자의 기존 선택을 자동으로 버리지 않는다.

#### 후보 카드에서 보여주는 정보

- 패키지명
- 짧은 설명
- 유사도 순위
- 최신 버전

후보 카드에는 수치 score를 표시하지 않는다. `유사도 순위`는 후보 정렬 순서이며 기술 품질 순위나 채택 권고가 아니라는 안내를 유지한다.

### 6.4 보고서 진입

사용자가 `분석 시작`을 선택하면 MVP 생태계 변화 보고서로 이동한다. 보고서 상단에는 최종 비교 패키지를 표시한다. 생태계 보고서는 기능 비교의 진행 여부와 무관하게 읽을 수 있으며, PDF 내보내기는 기능 비교와 PDF가 제공되는 단계에 추가한다.

기능 비교와 GitHub 커뮤니티는 실제 제공되는 확장 단계에서 같은 보고서 안에 별도 탭으로 추가할 수 있다. 다만 PDF는 각 비교 패키지의 현재 선택 버전 기능 비교가 완료된 경우에만 생성한다.

Dependency의 `Total` 또는 major 계열 다중 선택은 직접 의존 시계열을 탐색하는 표시 필터이며, 전체 분석 대상을 바꾸는 기능이 아니다.

### 6.5 API 정본과 기획 경계

API endpoint·HTTP 응답 필드명과 오류 코드는 개발팀의 **Notion API 명세를 정본**으로 따른다. 다만 현재 저장소에 병합된 구현 사실은 별도로 기록하고, Notion과 다르면 `pending API alignment`로 표시한다.

2026-09-10 전달받은 Notion export에서는 기존 5개 MVP endpoint가 모두 `서버 반영 = No`였지만, 이후 저장소 코드에는 검색·개요·Downloads·Dependents·Version Share와 후보 `/packages/similar`가 구현됐다. 아래는 현재 코드 기준이며 Notion/Swagger 동기화는 후속 확인이 필요하다.

현재 MVP 연동 방향은 다음과 같다.

- 패키지 입력: `/packages/search?q=...` 자동완성 또는 자유 입력 후 `/packages/similar`의 `not_found`로 서버 검증
- 후보: `/packages/similar?name=...&limit=...` — 기본 20·최대 50, 화면에는 상위 최대 3개 사용
- 패키지 개요: `/packages?names=a,b,c`
- Downloads: `/packages/downloads?names=a,b,c&from=&to=`
- Dependency: `/packages/dependents?names=a,b,c&from=&to=`가 package-major별 series를 반환하며 화면이 `Total` 또는 선택 major들을 합산
- Version Share: `/packages/version?names=a,b,c`가 최신 DB Snapshot의 version별 dependents를 major로 합산
- Dependency signed 증감: 서버 별도 summary가 아니라 프론트 adapter가 조회 구간 첫·마지막 유효 point로 계산
- 게시 데이터 상태와 UI 요청 상태를 분리한다. 현재 후보 API 데이터 상태는 `COMPLETE|NO_DATA`이며 생태계 API는 `not_found`를 사용한다. UI는 `loading|success|empty|error`를 기본으로 하고 출처가 지원할 때 `partial|stale`을 추가한다. PDF의 `READY` 등 lifecycle과는 구분한다.
- HTTP wire는 snake_case를 따르며 화면용 camelCase 변환은 프론트 adapter 경계에서 처리
- 서버 배치·사양은 제품 화면 요구와 분리하고, 실제 인프라 기준은 `Pickage_기능별_개발_구상안_0917.md` §3의 `DEC-SERVER-ALIGN-20260910-01`을 따른다. 제품 기획서에서는 서버 인스턴스 타입·자원량을 별도 재정의하지 않는다.

## 7. 보고서 1페이지: 생태계 변화

### 7.1 사용자가 얻는 답

- 공개된 직접 Dependency 추이는 어떻게 변했는가?
- 선택한 major 계열만 보면 직접 Dependency 변화가 다른가?
- Downloads는 어떤 흐름인가?
- 최신 DB Snapshot에서 version별 의존 수를 major로 합산하면 어떤 계열이 어느 비중인가?
- 선택한 조회 구간의 처음과 끝 사이에 직접 의존 선언 수가 얼마나 증가하거나 감소했는가?

### 7.2 Dependency

MVP의 Dependency는 **직접 의존 관계만** 분석한다.

Dependency 카드의 그래프 아래에 패키지별 major 선택 UI를 둔다. 처음에는 모든 major를 합친 `Total`이다. `Total`은 각 버전의 `dependents_count`를 합산한 **의존 수(버전별 합계)**이며 고유 프로젝트 수가 아니다. 따라서 `N개 프로젝트가 사용`처럼 중복 제거된 실제 사용처 수로 표현하지 않는다.

사용자가 한 패키지에서 major 하나 이상을 선택하면 이미 받은 major별 series를 프런트가 합산해 해당 패키지의 직접 의존 선만 바꾼다. 다른 패키지의 선택은 유지되며 필터 변경 때문에 API를 다시 호출하지 않는다.

이 major 선택 UI는 분석 대상을 새로 정하는 기능이 아니라 사용자가 직접 의존 시계열을 탐색하는 표시 필터다. 여러 패키지의 규모 차이가 큰 비교 화면에서는 작은 패키지의 기울기가 사라지지 않도록 Dependency 추이를 **로그축**으로 표현한다. 유효 Snapshot point가 2개 이하라 추세를 판단하기 어려운 경우에는 계열별로 선을 과장해 연결하지 않고 `데이터 축적 중 (N주차)`를 표시한다. 로그축 표현과 계열별 축적 판정은 구현 완료됐다(S15P21A506-311).

카드 하단에는 각 패키지별로 현재 표시 필터(`Total` 또는 선택 major 합계)와 동일한 조회 구간에서 **마지막 유효 관측값과 첫 유효 관측값**의 직접 의존 선언 수 차이를 signed 값으로 보여준다. `+`는 총수 증가, `-`는 총수 감소를 뜻하며 개별 dependent의 유입·이탈을 뜻하지 않는다. 증감값은 API의 별도 summary 필드를 전제로 하지 않고 프론트 `adapter.ts`가 dependents trend의 첫·마지막 유효 point로 계산한다. 사용자가 그래프 조회 기간을 바꾸면 증감의 비교 기준도 그 구간의 양 끝으로 바뀌며, 화면에는 두 기준일을 표시한다(S15P21A506-311로 구현 완료). 유효 point가 2개 미만이면 0으로 대체하지 않고 자료 상태를 표시한다.

Dependents·Downloads 카드에 지수(=100 기준) 비교·증감 그래프 토글, 절대값 로그축의 압축 표시(0~데이터 사이를 눌러 그리되 지그재그로 압축했다는 사실을 드러냄)가 추가로 구현됐다(S15P21A506-379). Downloads는 절대값 축 하나로 고정하고, Dependents는 접속 시 총합·지수가 기본값이다 — 증감으로 전환하면 스냅샷 간 순증감을 부호 있는 값으로 보여준다.

### 7.3 Activity

MVP에서는 **주간 Downloads 시계열**을 제공한다. 한 point는 직전 7일 다운로드 합계이며, 조회 요청 상한은 현재 API와 같은 **104주**로 고정한다. 실제 보유 기간이 짧으면 확보된 구간만 표시한다. 여러 패키지를 비교할 때 규모 차이로 작은 패키지의 변화가 바닥에 눌리지 않도록 추이는 **로그축**으로 표현한다. 현재 화면은 선형축이므로 로그축은 미구현 제품 계약이다. 확장 단계에서 같은 영역 또는 별도 전환 UI에 Issues를 추가할 수 있다.

두 비교 시계열의 로그축은 0을 보존하는 `log1p(x)`를 사용하고 눈금·툴팁은 원래 수치를 표시한다.
자료가 없는 구간은 0으로 연결하지 않는다. 주간 관측 간격이 8일을 넘으면 선을 끊어 연속 관측으로 오해하지 않게 한다. 유효 point가 2개 이하라 추세선의 의미가 충분하지 않으면 계열별로 `데이터 축적 중 (N주차)` 또는 동등한 상태를 표시한다. 현재 코드는 명시적 null만 끊고 축적 여부를 전체 series의 최대 point 수로 판단하므로 후속 수정이 필요하다.

### 7.4 Version Share

Version Share는 **시계열 그래프가 아니라 최신 DB Snapshot 분석**으로 확정한다.

MVP는 최신 DB Snapshot의 구체 버전별 `dependents_count`를 major로 합산한 관측 비중을 보여준다.

- 패키지 탭(생태계 1페이지 카드 전체가 공유하는 선택 탭 — 전환하면 Dependents·Downloads 강조도 같이 바뀐다. Version Share만의 독립 탭이 아니다, S15P21A506-379)
- Snapshot 기준일
- 전체 비중 도넛
- 버전 계열별 막대
- 상위 major와 나머지 major를 묶은 `기타`

Version Share에는 시간축을 두지 않고 과거 비중의 연결선을 만들지 않는다. 실제 설치 버전이나 고유 프로젝트 비중을 뜻하지 않는다. requirement 문자열을 해석한 `RESOLVED|UNKNOWN|AMBIGUOUS` 비중과 최신 완료 실행 선택은 확장 목표다.

### 7.5 1페이지 해석 원칙

- 직접 Dependency와 Downloads의 변화가 기술 품질을 의미하지 않는다.
- 공개 의존 관계가 실제 실행량을 의미하지 않는다.
- Snapshot 간 직접 의존 선언 수 증감이나 자료 누락을 개별 dependent의 유지·유입·이탈로 해석하지 않는다.
- Version Share Snapshot을 업데이트 의지나 위험으로 단정하지 않는다.
- 후보 ranking과 보고서 지표를 기술 우열 점수로 재해석하지 않는다.

### 7.6 확장 경계: 유지·유입·이탈 분석

`DEC-DEPENDENCY-DELTA-20260910-01`에 따라 개별 dependent의 유지·유입·이탈 분류는 MVP에서 제공하지 않는다. 동일 dependent를 Snapshot 사이에서 안정적으로 식별하고 상태 전이를 분류하는 데이터·계산 기준이 개발팀 검토를 통해 검증된 이후 기능-08 확장으로 제공한다.

확장 구현 전에는 단순 Snapshot 총수 차이로 유지·유입·이탈을 역산하거나 추정하지 않는다.

### 7.7 1페이지 인페이지 확장 모듈 UX

`DEC-ECOSYSTEM-INPAGE-EXT-20260910-01`에 따라 확장-01·02는 새로운 보고서 탭이나 별도 페이지를 만들지 않고 **생태계 변화 1페이지 안에서 확장되는 기능**으로 정의한다.

- **확장-01 버전 고착**: Version Share 아래에 인페이지 모듈로 추가한다. §7.4의 카드 공유 탭(S15P21A506-379)을 그대로 재사용하며 새 탭을 만들지 않는다. 기본 선택은 기준 패키지다. 탭을 전환하면 선택 패키지 카드 전체(고착 분포 포함)가 갱신되고, 비교 대상 자체는 바뀌지 않는다.
- **확장-02 관측된 교체 흐름**: 확장-01 아래에 인페이지 모듈로 추가한다. 비교 패키지가 3개라면 자기 자신을 제외한 최대 6개 방향(`A→B`, `A→C`, `B→A`, `B→C`, `C→A`, `C→B`)을 한 flow map에서 비교한다. 선 두께는 관측 건수, 좌→우 방향은 같은 공개 변화에서 제거된 패키지→추가된 패키지를 뜻한다. 기본은 전체 흐름이며 패키지 focus를 선택하면 해당 패키지의 들어온/나간 흐름만 강조한다.

확장-02의 flow는 실제 사용자의 마이그레이션, 교체 원인, 완전한 전환을 의미하지 않는다. 정확한 관측 건수는 선 두께만으로 의존하지 않고 hover/focus 또는 동등한 상세 표시에서 확인할 수 있어야 한다.

시계열의 8일 공백·유효 point 수는 표시 기간 안의 원시 주간 관측을 기준으로 판정한다.
화면 간격을 2주 이상으로 다운샘플링한 뒤 공백을 판단하거나, 표시점이 줄었다는 이유로 축적 중으로 바꾸지 않는다.

## 8. 확장: 보고서 2페이지 기능 비교

### 8.1 확장 구현 원칙과 결과 우선 경험

이 장은 MVP 완료 조건이 아니라 확장 기능의 목표 UX다. 구현은 **구조화 데이터 + AI + RAG**를 우선 검토하고, 구조화 데이터 계층의 비용·정확도·수집 가능성이 충분하지 않으면 **AI + RAG**로 축소한다. 어느 방식이든 검색된 근거와 생성된 설명의 연결을 보존하며, 근거 없는 기능 생성이나 추천은 허용하지 않는다.

사용자는 기능 비교 페이지에 들어왔을 때 버전을 먼저 설정해야만 결과를 볼 수 있기를 원하지 않는다. 따라서 각 패키지의 최신 안정 버전을 자동 선택하고, 완료된 결과가 있으면 별도 확인 없이 바로 보여준다.

Figma 기준 페이지 순서는 다음과 같다.

1. 기능 비교 버전 선택
2. 분석 진행·완료 상태
3. 핵심 환경·설치 조건
4. 핵심 기능 비교
5. 중립적인 기능 비교 해설

버전 선택 영역이 먼저 보여도 최신 안정 버전이 이미 선택되어 있으므로 사용자가 별도 조작을 해야 결과가 나타나는 구조는 아니다. 정식 버전이 없는 패키지는 사전 배포 버전을 자동 선택하지 않고 그 이유를 표시한다.

### 8.2 핵심 표

결과 표는 사용자가 패키지의 큰 차이를 빠르게 파악하는 역할을 한다. 환경 요약표 다음에 핵심 기능표를 배치한다.

표에는 다음만 넣는다.

- 기능 또는 확인 기준
- 패키지별 판정
- evidence ID

조건 설명, 긴 발췌, 기술 감사 정보는 표 안에 넣지 않는다. 사용자가 셀을 선택했을 때 Drawer에서 확인한다.

핵심 기능은 근거가 충분할 때 5~7개를 보여준다. 직접 비교할 근거가 5개보다 적다면 확인 가능한 항목만 표시하고 비교가 제한적인 이유를 설명한다. 숫자를 맞추기 위해 기능 항목을 만들지 않는다.

### 8.3 기능 비교 버전

최신 안정 버전은 자동 선택되지만 사용자가 다른 버전을 선택할 수 있다.

버전 변경 직후에는 기존 결과를 없애지 않는다. 사용자는 기존 결과를 보면서 선택한 버전과 현재 완료 결과 버전이 다르다는 사실을 확인한다.

`선택한 버전으로 재분석`을 실행하면 새 분석이 시작된다.

- 성공: 새 결과로 교체하고 직전 결과와 달라진 이유를 한 번 보여준다.
- 실패: 이전 정상 결과를 유지한다.
- 부분 완료: 확인 가능한 결과부터 보여주고 영향을 받는 셀만 미확인으로 남긴다.

### 8.4 GPT형 진행 경험

최초 분석에서 결과가 아직 준비되지 않은 영역은 skeleton으로 표시한다. 그 아래에는 실제 완료된 단계만 순서대로 나타낸다.

예:

- 정확한 버전과 배포 자료를 확인했습니다.
- 실행 환경과 공개 진입 정보를 확인하고 있습니다.
- 기능 근거를 정리하고 있습니다.
- 근거를 기능 판정과 연결하고 있습니다.
- 비교 해설을 작성하고 있습니다.

완성되면 진행 문구가 핵심 표와 완성된 해설로 대체된다. 작업하지 않은 내용을 완료된 것처럼 보여주지 않는다.

### 8.5 중립 해설

하단 글은 표의 판정을 반복하지 않는다. 다음을 설명한다.

- 여러 패키지에 공통으로 확인된 기반
- 같은 목적을 서로 다른 방식으로 제공하는 차이
- 특정 환경·설정·추가 패키지와 같은 조건
- 사용 상황에 따라 추가로 확인해야 할 기준

문장마다 evidence ID를 연결한다. “이 패키지를 선택하세요”와 같은 추천 문장은 만들지 않는다.

### 8.6 판정의 의미

| 판정 | 사용자 해석 |
|---|---|
| 지원 | 직접 근거로 기능이 확인됨 |
| 조건부 지원 | 명시된 환경·설정·추가 조건에서 지원됨 |
| 제한적 지원 | 기능은 있으나 범위나 제공 수준에 제한이 있음 |
| 미확인 | 자료로 확정할 수 없거나 같은 버전 근거가 충돌함 |
| 미지원 | 공식적인 부정 근거가 확인됨 |

미확인은 미지원보다 낮은 점수가 아니다. 판단을 유보해야 하는 상태다.

## 9. 확장: Evidence Drawer 경험

### 9.1 목적

Drawer는 사용자가 표의 한 판정을 신뢰할 수 있는지 검토하는 공간이다. 외부 문서 사이트를 다시 탐색하게 하기보다 판정에 실제 사용한 최소 근거를 화면 안에서 제공한다.

### 9.2 열림 방식

- 기능표의 한 셀 선택
- 데스크톱 웹 화면 우측 560px 오버레이
- 배경 표와 선택 셀 유지
- 같은 기능의 패키지 탭 전환
- 다른 셀을 선택하면 Drawer 위치는 유지하고 내용만 교체
- 열릴 때 Drawer 제목으로 포커스 이동, 닫힐 때 원래 비교 셀로 복귀

### 9.3 상단 신뢰 요약

- 패키지와 정확한 버전
- 기능과 판정
- 한 문장 판정 이유
- 공식 근거와 정적 확인 수
- 분석일
- 자료 상태

기술 정보는 처음부터 펼치지 않는다. 사용자가 판정 재현이나 자료 신선도를 확인하려 할 때만 펼친다.

### 9.4 근거 구성

근거는 역할별로 묶는다.

1. 지원이 확인된 근거
2. 조건과 제한을 확인한 근거
3. 추가 확인 자료
4. 충돌하는 근거

각 그룹의 가장 중요한 근거 하나만 기본으로 펼친다. 발췌는 기본 3줄이며 최대 10줄까지 Drawer 안에서 확장할 수 있다.

### 9.5 외부 이동을 제공하지 않는 이유

Drawer에서 공식 원문 보기, npm 보기, GitHub 보기, deps.dev 보기로 연결하지 않는다. 서비스가 판정에 사용한 출처 유형·경로·섹션·발췌는 표시하지만 외부 원문으로 이동시키지 않는다.

복사는 근거 ID와 분석 정보만 제공한다.

복사 완료는 버튼 주변의 짧은 완료 문구로 알려준다. 저장소 주소와 출처 위치를 포함한 사용자 화면의 식별 정보는 클릭 가능한 외부 링크로 만들지 않는다.

### 9.6 근거 충돌

같은 버전의 타입 선언과 공개 진입 정보가 서로 다른 결과를 가리키면 AI가 한쪽을 선택하지 않는다.

- 판정: 미확인
- 자료 상태: 근거 충돌
- 본문: 양쪽 근거 보존
- 다음 행동: 단순 반복 재분석 미제공

## 10. 확장: GitHub 커뮤니티 현황

### 10.1 페이지 역할

이 페이지는 선택한 패키지의 검증된 GitHub 저장소에서 **지금 이어지는 핵심 이슈와 실제 논의 흐름**을 함께 이해하는 공간이다. 단순한 Issue 목록이나 저장소 통계 페이지가 아니라 `요약과 수치 → 핵심 이슈·쟁점 → 실제 논의 흐름`의 3단 구조로 제공한다.

Issue 수의 장기 시계열은 이 페이지에서 중복 제공하지 않고 보고서 1페이지 Activity 확장 영역에서 다룬다.

### 10.2 1단: 커뮤니티 보고서 요약과 수치

최상단은 현재 보고서의 범위와 분석 대상을 짧게 이해하는 영역이다.

- 패키지명 + `커뮤니티 현황` 제목
- 검증된 GitHub 저장소 식별 정보
- 이번 분석에서 다룬 공개 Issue 범위
- 해당 패키지의 Issue 논의와 수집 범위를 설명하는 한 문장 안내(고정 문구이며 별도 종합 LLM 요약 아님)
- 분석 이슈 수
- 분석 대상 이슈의 누적 댓글 수
- 분석 대상 이슈에서 확인한 사용자 반응 수
- 분석 대상 이슈의 열린 상태 수

수치는 저장소 전체의 임의 통계가 아니라 **이번 커뮤니티 분석에 포함된 실제 공개 Issue 집합**을 기준으로 계산한다. Figma의 `2건·40개·17개·2건`과 같은 값은 화면 예시일 뿐 고정 제품 값이 아니다.

커뮤니티 현황은 사용자가 최초 입력한 기준 패키지 하나만을 분석 대상으로 한다(`DEC-COMMUNITY-20260909-01`). 비교 대상으로 추가한 다른 패키지의 커뮤니티 정보는 제공하지 않는다. 기준 패키지의 저장소 연결이 검증되지 않으면 다른 패키지 정보로 대신하지 않고 제공 불가 상태와 이유만 표시한다. 저장소 주소는 식별 정보이며 외부 이동 기능이 아니다.

### 10.3 2단: 핵심 이슈와 논의 쟁점

요약 아래에는 현재 논의가 이어지는 핵심 Issue를 카드 또는 동등한 구역으로 보여준다. 각 항목은 최소한 다음을 포함한다.

- Issue 번호와 OPEN/CLOSED 등 확인된 상태
- 댓글 수와 사용자 반응 수
- 실제 Issue 제목 또는 사용자가 이해하기 쉬운 제목
- 현재 쟁점을 요약한 짧은 설명
- 논의가 어떤 순서로 전개되고 있는지 보여주는 `논의 흐름`

`논의 흐름`은 예를 들어 `문제 제기 → 유지보수자 설명 → 사용자 대안 공유 → 해결 방향 논의`처럼 실제 댓글 전개를 압축한다. 존재하지 않는 단계나 합의를 만들어내지 않는다.

### 10.4 3단: 실제 논의 흐름

핵심 이슈 아래에는 선택한 주제의 실제 공개 댓글을 바탕으로 대화형 기록을 제공한다.

각 대화 항목은 가능한 범위에서 다음을 유지한다.

- 작성자 식별명
- 확인 가능한 역할: `ISSUE_AUTHOR`, `REPOSITORY_OWNER`, `ORGANIZATION_MEMBER`, `COLLABORATOR`, `CONTRIBUTOR`. `USER_SOLUTION`은 역할이 아니라 해결 방법을 제시한 메시지 유형이다.
- 실제 댓글 순서
- 원문 댓글의 핵심 논지를 한국어로 요약한 메시지

이 영역은 AI가 가상의 토론을 생성하는 기능이 아니다. 수집 대상은 GitHub Issue만이며 PR은 제외한다. Issue 본문은 쟁점 요약의 근거로 사용하고, 대표 발화는 실제 공개 댓글에서만 가져온다. 화면에서 읽기 쉽게 요약하더라도 원래 주장·반박·조건·해결안의 방향을 바꾸지 않는다. 역할을 확인할 수 없으면 임의 역할을 부여하지 않는다.

### 10.5 해석·표시 원칙

- 상단 수치와 하단 대화 기록은 같은 분석 대상 Issue 집합을 사용한다.
- 생성 시 모든 요약의 원본 Issue/댓글 근거를 검증하고, 게시 결과에는 Issue와 대표 댓글 식별자를 내부적으로 연결한다. raw 원문·문장별 support 목록은 보존하지 않으므로 삭제·편집된 원문의 장기 재감사를 보장하지 않는다.
- 합의되지 않은 의견을 프로젝트의 결론처럼 표현하지 않는다.
- 댓글의 일부만 수집됐거나 API 제한이 있으면 완전한 논의라고 단정하지 않는다.
- 저장소 연결 범위가 모호하면 패키지 단위 논의라고 단정하지 않는다.

### 10.6 수집·실패·재시도 계약

기본 최근 180일, 완전 검색의 원시 결과가 0건일 때만 365일로 한 번 확장한다.
Issue 최대 2개, Issue별 최신 댓글 최대 100개, 대표 댓글 최대 3개를 사용한다.
상단 댓글·반응 수는 선택 Issue record의 수치 합계이지 수집한 댓글 수나 저장소 전체 수가 아니다.
정상 결과는 24시간 재사용하고 수집 후 7일 미만의 이전 결과만 stale로 제공한다.
요약이 모두 실패한 경우에도 검증된 제목·수치는 보존하며, 실패 완료 후 5분부터 사용자 재시도를 허용한다.
원문 ID 검증만으로 의미 왜곡 방지를 보장하지 않으며 사람의 원문 대조 평가를 병행한다.
저장소 미검증·범위 모호·미지원·논의 없음과 일시 수집 실패, 일부 요약 실패를 구분한다.

화면 상태·API·저장·파트별 구현 및 시험의 상세 정본은
[커뮤니티 구현계획](for_community/Pickage_GitHub커뮤니티_구현계획_260908.md)이다.
이 기능은 아직 코드에 구현되지 않았고 시안은 완료 증거가 아니다.

## 11. PDF 경험 [확장: 기능 비교 제공 이후]

### 11.1 목적

PDF는 현재 화면을 인쇄하는 기능이 아니라, 완료된 보고서를 팀에서 공유하고 재검토하기 좋은 문서로 재구성하는 기능이다.

PDF는 완료된 생태계 분석 결과와 각 비교 패키지의 현재 선택 버전 기능 비교 결과를 함께 재구성한다. GitHub 커뮤니티는 완료 Snapshot이 있을 때만 추가로 포함한다.

### 11.2 내보내기 확인

사용자는 기능 비교가 제공되는 단계에서 보고서 상단의 `PDF 내보내기`를 선택한다. 확인 화면에서는 다음을 보여준다.

- 비교 대상 패키지
- 생태계 조회 기간
- 패키지별 직접 Dependency 표시 필터
- 현재 선택 버전과 일치하는 완료 기능 비교 결과
- Version Share Snapshot 기준일
- 포함되는 보고서 구역
- 전체·부분·자료 없음·오류 상태

사용자는 구성을 편집하지 않고 현재 완료된 생태계 보고서와 현재 선택 버전 기능 비교 결과가 맞는지만 확인한다.

기능 비교 버전·근거는 PDF에 항상 포함하며, GitHub 커뮤니티 구역은 실제 완료되어 포함 가능한 경우에만 추가로 표시한다.

### 11.3 생성 차단

통합 PDF는 다음 상태에서 만들지 않는다.

- 비교 대상이 확정되지 않음
- 최초 생태계 핵심 결과가 아직 없음
- 필수 보고서 스냅샷을 만들 수 없는 처리 오류
- 기능 비교가 미실행·분석 중이거나 결과 버전이 현재 선택과 다름

일부 기간 자료 없음, 일부 패키지 자료 부족, Version Share의 `기타` major는 차단 사유가 아니다. 해당 상태를 PDF에 명시한다.

기능 비교는 생태계 영역과 별개로 표시하지만, PDF 적격성에서는 각 비교 패키지의 현재 선택 버전 결과가 완료되었는지 반드시 검사한다. 버전 변경 뒤 기존 결과는 비교 화면에서 유지하되 PDF는 재분석 완료 전까지 `BLOCKED`다.

### 11.4 부분 결과 허용

다음은 경고와 함께 PDF로 만들 수 있다.

- 일부 기간 자료 없음
- 일부 패키지 Dependency 자료 부족
- Version Share의 `기타` major와 현재 집계 의미
- 후보 API `NO_DATA`
- 확장 GitHub 보조 자료 일부 실패

사용자에게 불완전한 부분을 숨기지 않는다.

### 11.5 PDF 구성

필수 구성:

1. 표지·분석 요약
2. 후보·비교 대상과 분석 범위
3. 생태계 변화: Downloads, 직접 Dependency와 현재 표시 필터, Snapshot 간 직접 의존 선언 수 증감
4. 최신 Version Share Snapshot과 기준일
5. 현재 선택 버전의 기능 비교와 근거 요약
6. 자료 상태·해석 한계

완료된 경우 선택 없이 자동 포함할 수 있는 선택 구역:

- Issues·GitHub 커뮤니티 현황

실제 용지 수는 내용에 따라 달라진다.

### 11.6 다운로드 경험

- 생성 완료 시 자동 다운로드
- 파일명·생성 시각·페이지 수·크기 표시
- **생성 작업 실패**와 **생성 완료 후 다운로드 실패**를 구분한다. 생성 실패에는 준비된 파일이 있다고 표시하지 않는다.
- 다운로드 실패 시 같은 파일 다시 받기
- 다시 받기를 선택해도 보고서를 재분석하거나 PDF를 다시 만들지 않음

## 12. 자료 상태와 실패 경험

게시 데이터 상태와 화면 요청 상태는 별도 축으로 관리한다. 현재 후보 API의 `COMPLETE|NO_DATA`는 사전 계산 데이터 상태이고, 화면의 `loading|success|empty|error`는 요청 상태다. 데이터 원천이 지원하는 경우에만 `partial|stale`을 추가한다. PDF 생성의 `READY/GENERATING/COMPLETE/BLOCKED/FAILED`는 별도 lifecycle이며 두 상태 축과 혼용하지 않는다.

| 상황 | 사용자에게 보여줄 것 | 유지할 것 |
|---|---|---|
| 후보 부족 | 있는 후보와 직접 추가 | 기준 패키지 |
| 후보 검색 실패 | 오류·후보 다시 검색·직접 추가 | 기준 패키지 |
| 후보 API `NO_DATA` | 빈 후보 상태와 직접 추가 | 기준 패키지 |
| 네 번째 패키지 추가 | 기존 선택 해제 안내 | 현재 3개 선택 |
| 직접 Dependency 일부 기간 없음 | 가능한 구간·기간 경고 | 다른 패키지 그래프 |
| 시계열 Snapshot 축적 부족 | `데이터 축적 중 (N주차)` 등 추세 판단 보류 상태 | 확보된 point와 다른 지표 |
| 실제 0 | 숫자 0과 범위 | 정상 상태 |
| Version Share에 표시 상한 초과 major 존재 | `기타` 비중과 Snapshot 기준일 | 상위 major 비중 |
| PDF 다운로드 실패 | 동일 파일 다시 받기 | 생성 완료 파일 |
| 확장 기능 분석 중·실패 | 확장 영역 상태와 가능한 다음 행동 | MVP 생태계 보고서 |
| 확장 기능 근거 충돌 | 미확인·양쪽 근거 | MVP 생태계 보고서 |
| GitHub 조회 제한 | 조회 시점·부분 상태 | 확인된 논의 |

현재 생태계 화면은 Overview·Downloads·Dependents 중 하나의 요청이 실패하면 탭 전체 오류를 표시하고 Version Share만 별도 격리한다. 위 카드별 유지 계약을 만족하려면 요청·오류 경계를 카드 단위로 분리해야 한다.

## 13. AI의 역할

### 후보 단계

후보 단계의 최종 순위는 생성형 AI가 결정하지 않는다.

- 의미 후보 풀 탐색에는 description·keywords 등의 벡터/텍스트 관련성을 사용할 수 있다.
- v1 랭커는 의미 검색 후보 풀을 구조적 관문으로 거른 뒤 통과 후보를 cos 유사도로만 정렬한다(`DEC-RANK-20260910-01`). popularity·Downloads·dependents를 연속 score에 더하거나 빼지 않으며 `move_lift`도 사용하지 않는다.
- 생성형 AI는 후보 이름 생성, 후보 점수 임의 보정, 후보 순서 변경을 수행하지 않는다.
- 후보 API는 내부 활용을 위해 수치 score를 전달하지만 화면에는 표시하지 않는다. 화면의 `유사도 순위`는 기술 품질 순위가 아니라 정렬 결과임을 안내한다.

### 확장 기능 비교 단계

기능 비교가 구현되는 경우 AI는 RAG로 검색된 근거와, 가능하면 구조화된 데이터에 기반해 다음 역할만 수행한다.

- 확보된 근거를 비슷한 사용자 목적의 기능으로 정리
- 제공된 근거 안에서 차이 설명
- evidence ID 또는 동등한 근거 식별자가 연결된 문장 작성

우선 구조는 `구조화 데이터 + AI + RAG`이며, 구조화 데이터 계층의 현실성이 충분하지 않으면 `AI + RAG`로 축소한다.

다음은 수행하지 않는다.

- 원자료에 없는 기능 생성
- 근거 없는 지원·미지원 판정
- 충돌하는 근거 중 하나를 임의 선택
- 최종 추천·순위·승자·미래 예측

## 17. 용어

| 용어 | 정의 |
|---|---|
| 기준 패키지 | 사용자가 처음 입력한 패키지 |
| 관련 후보 | 순수 의미 검색으로 찾은 뒤 보완재·생존·실체 관문을 통과한 실제 npm 패키지 |
