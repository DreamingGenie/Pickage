## 0. 결론 먼저

**우리가 가진 원천의 정체는 "다운로드 원장"이 아니라 "결정 원장"이다.**

npm·npm Trends·Snyk·Socket이 보여주는 다운로드 수와 별표는 **트래픽**이다. CI·미러·봇이 섞인다. 우리가 가진 것은 npm 패키지 작성자 **406만 명이 16년(2010-11-09 ~ 2026-09-01)에 걸쳐 4,718만 번 내린 "무엇을 의존으로 쓸지" 결정**의 전수 기록이다. 이건 트래픽이 아니라 **동료 개발자의 선택**이다.

여기서 나오는, 지금 어느 서비스도 한 화면에 놓지 않는 4개 숫자:

| # | 사용자 질문 | 오늘 실측한 답의 예 | 비용 |
|---|---|---|---|
| 1 | 지금 몇 개가 쓰는가 (누적) | `moment` 51,443개 · `dayjs` 20,916 · `date-fns` 19,423 | 15.3 GiB/쿼리 |
| 2 | **올해 시작한 프로젝트는 뭘 골랐나 (신규)** | 2026년 첫 배포: `date-fns` 2,789 > `dayjs` 1,822 > **`moment` 1,162** | 같은 쿼리 |
| 3 | **남들은 새 메이저로 넘어갔나 (고착)** | `chalk` v5 55,181 vs 아직 v4 43,476 · v2 26,603 | 같은 쿼리 |
| 4 | 그 선택의 대가는 (발자국·권고) | `winston@3.9.0` 직접 11개 → 실제 설치 28개 / npm GHSA 6,894건 | 0.44 GiB, 0.02 GiB |

**②가 이 서비스의 존재 이유다.** 누적 순위에서 `moment`는 2위인데, 신규 채택에서는 3위이고 2024년 4,831 → 2026년 1,162로 무너지는 중이다. 누적만 보는 사람은 이 역전을 못 본다. 기획서 문제-01이 실물로 확인됐다.

**결정 제안 3줄**
- 메인 가치 = **"누적 인기와 지금의 선택을 분리해서 보여준다."** 증거는 나왔다.
- **버전 고착(확장-03)을 MVP로 올린다.** 추가 비용이 거의 0인데 유일성은 ②에 버금간다.
- **설치 발자국·보안 권고를 비교표에 한 칸씩 넣는다.** 지금 기획서에 아예 없다. 합쳐서 1 GiB 미만.

## 1. BigQuery와 deps.dev가 각각 무엇인가

### 1-1. BigQuery — 우리가 서버를 안 사도 되는 이유

Google Cloud의 **서버리스 데이터 웨어하우스**다. 우리 입장에서 중요한 성질은 4개뿐이다.

| 성질 | 뜻 | 우리에게 미치는 영향 |
|---|---|---|
| **서버리스** | 클러스터를 띄우지 않는다. SQL만 던진다 | 514 TiB짜리 데이터를 노트북에서 3초에 질의했다 |
| **컬럼 저장** | 열 단위로 저장·과금 | `SELECT *` 대신 열 5개만 고르면 10배 싸진다 |
| **스캔량 과금** | 읽은 바이트로 과금. 월 **1 TiB 무료** | 오늘 쿼리 12개 전부 합쳐 **79.86 GiB = 무료 한도의 7.8%** |
| **파티션·클러스터** | 날짜로 잘라두고(파티션) 특정 열로 정렬해둠(클러스터) | 필터를 걸면 안 읽는다. **안 걸면 한 방에 무료 한도를 넘긴다** |

> **과금은 "데이터 크기"가 아니라 "내가 읽은 열 × 내가 읽은 파티션"이다.** 전체 514 TiB 중 우리가 실제로 만지는 건 한 스냅샷의 필요한 열뿐이라 20 GiB 수준이다.

**공개 데이터셋(`bigquery-public-data`)은 저장 비용이 우리에게 안 붙는다.** 우리는 쿼리 스캔량만 낸다. 그래서 이 주제는 데이터 조달 비용이 사실상 0인 몇 안 되는 주제다.

### 1-2. deps.dev — Google Open Source Insights

Google이 운영하는 **오픈소스 의존 관계 관측 서비스**다. npm·PyPI·Maven·Go·Cargo·NuGet·RubyGems 7개 생태계의 패키지를 매주 긁어서 ①메타데이터 ②선언된 의존성 ③실제로 해석된 의존성 그래프 ④GitHub 저장소 연결 ⑤보안 권고를 정리한다.

우리가 접근할 수 있는 경로는 3개이고, **각각 할 수 있는 일이 다르다.**

| 경로 | 인증 | 강점 | 한계 |
|---|---|---|---|
| **BigQuery 공개 데이터셋** `bigquery-public-data.deps_dev_v1` | GCP 계정 | **전수 계산.** 400만 패키지를 한 번에 집계 | 주 1회 스냅샷. 최신성 없음 |
| **REST API** `api.deps.dev/v3` | 불필요·무과금 | 단건 조회. **OSSF Scorecard가 여기만 있다** | 전수 불가 |
| **npm 레지스트리** (deps.dev 아님) | 불필요 | 설명·키워드·폐기 표시·다운로드 수 | 요청 제한 빡빡함(§5) |

**우리가 BigQuery를 써야 하는 진짜 이유는 딱 하나다: 역방향 전수 집계.** "winston을 쓰는 패키지가 몇 개인가"는 REST API로는 영원히 답이 안 나온다. 21,007개를 하나씩 물어볼 수 없기 때문이다.

**갱신 주기**: `Snapshots` 테이블 224개 실측, **매주 월요일**. 최신 2026-08-31, 최초 2022-05-08.

### 2-1. 여기서 나온 제약 3개 — 설계에 직결된다

**① `NPMRequirements`는 35주치만 보관한다 (2026-01-05 ~ 2026-08-31).**
스냅샷을 서로 비교하는 방식으로 시계열을 만들면 **8개월밖에 못 본다.** 다행히 기획서의 '기간별 한 패키지 한 표'는 그 방식이 아니다 — 한 스냅샷 안에 모든 버전의 선언이 다 들어 있고, `UpstreamPublishedAt`으로 기간을 자르므로 **한 스냅샷으로 16년치가 나온다.** 실제로 §4의 연도별 결과가 그렇게 나왔다.
→ **기획서의 '관측 상태'라는 말이 스냅샷을 연상시켜 오해를 부른다.** '버전 발행 시각 기준 대표 상태'로 용어를 못 박아야 한다.

**② `Dependents` 테이블은 클러스터 키가 없다.** 패키지 하나의 역방향 의존을 물어보는 데 **dry-run 298.52 GiB**가 나온다. 한 번 돌리면 월 무료 한도의 29%가 날아간다. 역방향은 `NPMRequirements`에서 우리가 직접 계산한다(15.3 GiB에 **전 생태계분**이 나온다 — §4-1).

**③ 문서에 있는데 비어 있는 열이 있다.** `PackageVersions.ProjectStatus` / `ProjectStatusReason`은 npm 7,855만 행 **전부 NULL**이다. "저장소가 아카이브됨" 신호로 쓰려던 계획이 있다면 여기서 접어야 한다. `Projects` 테이블에 OSSF Scorecard 열도 없다(REST API에만 있음).

## 3. 테이블별 "얻는 정보 → 만들 수 있는 사용자 가치"

### `PackageVersions` — 배포 이력의 시간축
얻는 것: 패키지명 · 버전 · **발행 시각** · 정식배포 여부 · semver 순서 · 라이선스 · 폐기 표시 · 저장소 링크 · 설명
→ **모든 시계열의 X축이 여기서 나온다.** "패키지가 처음 세상에 나온 날", "이 메이저가 공개된 날", "마지막 배포가 언제인지(유지보수 신호)".
→ 화면 가치: *"이 후보는 2018년에 시작해 지금까지 213번 배포됐고, 마지막 배포는 3주 전이다."*

### `NPMRequirements` — 선언 원장 (핵심 자산)
얻는 것: 각 버전의 `dependencies` / `devDependencies` / `peerDependencies` / `optionalDependencies` 목록과 **버전 조건 원문**(`^5.0.0` 같은)
→ 여기서 **누가 무엇을 언제 채택·유지·제거했는지** 전부가 복원된다. 버전 조건 원문이 살아 있어서 **버전 고착**까지 계산된다.
→ 화면 가치: 현재 규모 · 신규 선택 · 유지 · 이탈 · 버전 고착 · 마이그레이션 쌍 — **기획서 핵심 지표 전부**.

### `Dependencies` — 해석된 전이 의존 (기획서에 없는 자산)
얻는 것: 버전 하나를 실제로 설치했을 때 **딸려오는 전체 패키지 목록**과 깊이(`MinimumDepth`)
→ 선언은 11개인데 실제로는 28개가 깔린다는 걸 보여준다. 클러스터 키가 있어 **패키지 1개 조회에 0.44 GiB**로 싸다.
→ 화면 가치: *"winston 11개 선언 → 실제 28개 설치 / pino는 몇 개?"* 비교표에 **한 칸 추가로 끝나는 강한 차별점**.

### `Advisories` — 보안 권고
얻는 것: 권고 ID · 제목 · 심각도(GitHub 기준) · CVSS3 점수 · 공개일 · 영향 버전 범위 · 참조 URL
→ **주의: npm 권고 227,780건 중 220,886건이 `MAL-`(악성 패키지 신고)이다.** 진짜 취약점 권고는 `GHSA-` 6,894건 / 3,527개 패키지뿐이다. 섞으면 화면이 오염된다.
→ 화면 가치: *"이 후보에는 미해결 GHSA 권고가 N건 있다"* 한 칸. 비용 0.02 GiB.

### `PackageVersionToProject` — 패키지 → GitHub 저장소
얻는 것: 소스 저장소 / 이슈 트래커 링크와 그 **출처 등급**
→ npm 이름 **8,184,976개(71.9%)**가 GitHub 소스 저장소로 연결된다. 저장소 **1,691,238곳**.
→ 용도 ①마이그레이션의 '배포 주체 묶기'(같은 조직이 20개 패키지를 한꺼번에 바꾼 걸 1표로 축약) ②커뮤니티 논의 수집 대상 확정.
→ **경고**: 대부분(5,275만 행)이 `UNVERIFIED_METADATA`, 즉 package.json이 자기 신고한 값이다. 검증된 `SLSA_ATTESTATION`은 208,307개 이름뿐. 주체 묶기의 신뢰도 한계를 화면에 밝혀야 한다.

### `Projects` — 저장소 지표
얻는 것: 별 · 포크 · 미해결 이슈 수 · 라이선스 · 설명 · 홈페이지 · OSS-Fuzz 커버리지
→ GitHub 저장소 **5,170,961개**(별이 있는 건 2,175,936개, p50=0 · p99=1,257)
→ 화면 가치: 비교표의 맥락 열. **단독 가치는 없다** — GitHub에서 그냥 보이는 값이다. 우리 지표 옆에 놓일 때만 의미가 생긴다.

### 안 쓰는 것
`DependencyGraphEdges`(300 TiB, 전이 그래프의 간선 — 우리 질문에 과잉) · `PackageVersionHashes`(공급망 무결성) · npm 외 6개 생태계 requirements(범위 밖).

**읽는 법**: `moment`는 누적 2위(51,443)로 여전히 압도적이지만, 신규 채택은 2024년 4,831 → 2026년 1,162로 무너졌고 순위도 3위로 내려갔다. **2025년에 dayjs가, 2026년에 date-fns가 앞질렀다.** 오늘 npm 다운로드 수만 보면 `moment`가 여전히 1위처럼 보인다.

> 이게 기획서 문제-01("누적 인기와 최근 변화가 섞여 있다")의 실물 증거다. **가설이 아니라 측정된 사실이 됐다.**
> ⚠️ 2024년 신규 패키지 수가 66.7만으로 튀는 등 신규 패키지 수 자체에 스팸 유입 변동이 있다. 그래서 **원값과 비중을 반드시 같이** 보여줘야 한다(기획서 규칙과 일치).

### 증거 2 — 버전 고착이 진짜로 보인다 ★ 저평가된 자산

각 패키지의 **최신 대표 버전이 허용하는 메이저 버전** 분포:

| 대상 | 허용 메이저별 선언 패키지 수 |
|---|---|
| **chalk** | v5 **55,181** / v4 **43,476** / v2 26,603 / v1 14,577 / v3 4,607 / 해석불가 1,369 |
| **express** | v4 **79,269** / v5 11,128 / v3 2,056 / 해석불가 1,167 |
| **uuid** | v8 14,284 / v9 12,927 / v3 12,880 / v11 6,691 / v10 3,213 / v13 2,447 / v14 1,775 |
| **axios** | v1 79,837 / **v0 71,746** / 해석불가 728 |

**읽는 법**: chalk v5(ESM 전환)로 넘어간 건 55,181개인데, **아직 v4에 머무는 게 43,476개**다. express는 v5가 나왔는데 92%가 v4다. axios는 47%가 아직 0.x다. uuid는 8개 메이저에 흩어져 있다.

> **"내가 이 메이저로 올려도 되나"**는 팀 리드가 실제로 하는 질문인데, 지금 이걸 숫자로 답하는 서비스가 없다. 계산 비용은 §4-1 쿼리에 **정규식 열 하나 추가**가 전부다. 해석불가 비율도 1% 미만으로 낮게 나왔다(기획서가 걱정한 지점).

### 증거 3 — 설치 발자국을 잴 수 있다 ★ 기획서에 없는 지표

`winston` 버전별 (`Dependencies` 테이블, 0.44 GiB):

|---|---:|---:|
| 3.9.0 | 11 | **28** |
| 3.8.1 | 10 | 27 |
| 3.7.2 | 10 | 27 |

**읽는 법**: 선언 11개를 골랐는데 실제로는 28개가 들어온다. 후보 4개를 이 기준으로 나란히 놓으면 *"pino는 8개, winston은 28개"* 같은 결정적 비교가 된다. Bundlephobia가 용량으로 하는 걸 우리는 **패키지 수 × 시간축**으로 한다.

## 6. 가치 명제 결정안

### 6-1. 가치 축 5개 평가

### 6-2. 추천 가치 명제

> **"OSS Shift는 다운로드 수가 아니라 다른 개발자들의 선택을 보여준다.
> 누적으로 몇 개가 쓰는지, 지금 새로 시작하는 프로젝트는 무엇을 고르는지, 남들은 새 메이저로 넘어갔는지,
> 그 선택이 실제로 몇 개를 끌고 오는지 — 같은 기준일·같은 규칙으로 한 화면에 놓는다."**

**비교표 한 줄 = 6칸.** 후보 4개면 이 표 하나가 결과 화면의 전부다.

| 후보 | 누적 선언 | 2026 신규 채택 (비중) | 신규 흐름 | 새 메이저 전환률 | 설치 발자국 | 미해결 GHSA |
|---|---|---|---|---|---|---|
| date-fns | 19,423 | 2,789 (0.45%) | ↑ 1위 | — | (계산) | (계산) |
| dayjs | 20,916 | 1,822 (0.30%) | ↓ 2위 | — | (계산) | (계산) |
| moment | 51,443 | 1,162 (0.19%) | ↓↓ 3위 | — | (계산) | (계산) |

**"누적 1위와 신규 1위가 다르다"는 발견 자체가 사용자가 돈 주고 살 정보다.** 나머지는 그 발견을 팀에 설명하기 위한 근거다.

### 6-3. 기획서에 반영할 변경 5건

1. **확장-03(버전 고착)을 MVP로 승격.** 근거: §4-2. 추가 비용 사실상 0, 유일성 최상, 문제-05의 절반을 MVP에서 해결. 대신 확장-04(마이그레이션)는 확장에 그대로 둔다.
2. **'설치 발자국'을 신규 지표로 추가** (`Dependencies` 테이블). 지금 기획서 지표 표에 없다. 비교표 한 칸.
3. **'미해결 보안 권고' 한 칸 추가 — `GHSA-`만.** `MAL-` 22만 건 제외를 계산 규칙에 명문화.
4. **`Dependents` 테이블 사용 금지를 데이터 계약에 명시.** 1쿼리 298 GiB.
5. **'관측 상태' 용어를 '발행 시각 기준 대표 상태'로 정정.** `NPMRequirements`가 35주만 보관하므로, 스냅샷 간 비교로 오해되면 설계가 8개월로 잘린다.

**빼지 않는 것**: 마이그레이션 쌍(E)은 화려하지만 밀도가 미확정이다. 기대치를 메인에 걸면 안 되고, 확장에 두되 §7-1을 먼저 돌린다.
