## 1. 제품 정의

Pickage는 개발자가 npm 패키지를 선택하거나 교체할 때 **최대 3개의 생태계 변화, 기능 차이,
GitHub 커뮤니티 상태를 한곳에서 비교**하게 하는 의사결정 보조 서비스다. 결과를 PDF와 에이전트용
HAND-OFF Markdown으로 내보낼 수 있다.

Pickage가 하는 일은 근거를 모아 비교 가능한 형태로 보여 주는 것이다. 특정 패키지를 승자로 정하거나,
관측된 동시 변경을 인과관계로 단정하거나, 사용자의 기술 결정을 대신하지 않는다.

## 2. 해결하려는 문제

패키지 선택에는 서로 다른 종류의 정보가 필요하다.

- 다운로드와 의존 패키지 수는 인기도를 보여 주지만 실제 이동 방향은 알려 주지 않는다.
- README는 기능을 설명하지만 여러 패키지의 공통점과 차이를 같은 기준으로 읽기 어렵다.
- GitHub 지표는 활동성을 보여 주지만 하나의 숫자로 건강도를 단정하기 어렵다.
- 개발자가 이 근거를 직접 모으면 출처·기준일·단위가 달라 비교와 공유가 어렵다.

Pickage는 데이터의 기준과 한계를 노출한 채 세 관점을 같은 분석 세션에 결합한다.

## 3. 대상 사용자와 이용 상황

주 사용자는 새 프로젝트의 의존성을 고르거나 기존 패키지의 대안을 검토하는 개발자다. 특히 익숙하지
않은 생태계에서 후보를 좁혀야 하거나, 선택 근거를 팀원 또는 AI 코딩 에이전트에게 전달해야 할 때를
대상으로 한다.

대표 이용 상황은 다음과 같다.

1. 기준 패키지의 최근 생태계 변화를 확인한다.
2. 유사 후보 중 비교할 패키지를 고르거나 이름을 직접 추가한다.
3. 버전별 기능·런타임 조건과 기준 패키지의 GitHub 커뮤니티 상태를 함께 본다.
4. 결론을 직접 내린 뒤 PDF로 공유하거나 Markdown을 에이전트에게 넘긴다.

## 4. 핵심 가치

### 4.1 같은 화면에서 보는 세 종류의 근거

- **생태계 변화**: 다운로드, 의존 패키지, 버전 점유율, 유입·유출·유지·미관측, 제거 이유,
  관측된 이동 경로
- **기능 비교**: 선택 버전의 모듈·타입·엔진·의존 조건과 README 기반 RAG 비교
- **GitHub 커뮤니티**: 활동, 반응, 기여, 유지보수 지표와 데이터 상태

### 4.2 해석 한계를 숨기지 않는 결과

각 지표는 관측 기간과 기준일을 표시한다. `미관측`을 유지로 바꾸지 않으며, 버전별 dependents 합계의
중복 가능성, 이동 경로의 동시 변경 잡음, RAG 근거 부족을 사용자에게 알린다.

### 4.3 다음 작업으로 이어지는 산출물

PDF는 사람이 검토·공유하는 문서이고 HAND-OFF Markdown은 AI 에이전트가 분석 맥락을 이어받는
텍스트다. 두 형식 모두 현재 화면의 근거와 제한을 보존하는 것을 우선한다.

## 5. 사용자 여정

### 5.1 소개와 기준 패키지 선택

사용자는 `/`에서 서비스의 세 분석 관점과 주의사항을 읽고 npm 패키지를 검색한다. 유효한 패키지를
선택하면 `/analyze?base=<name>`으로 이동한다.

### 5.2 비교 대상 구성

분석 화면은 기준 패키지에 대한 유사 후보를 최대 3개 보여 준다. 후보는 자동으로 선택되지 않는다.
사용자는 후보를 선택하거나 검색으로 다른 패키지를 직접 추가해 기준 패키지를 포함한 총 3개까지
구성한다. 유사 후보를 사용하지 않는 흐름은 `nosimilar=1`로 유지된다.

### 5.3 보고서 탐색

보고서는 세 탭으로 구성된다.

1. **생태계 변화**에서 정량 시계열과 관측된 이동 신호를 비교한다.
2. **기능 비교**에서 각 패키지 버전을 정하고 공통점·차이를 생성한다.
3. **GitHub 커뮤니티**에서 기준 패키지의 저장소 활동과 데이터 갱신 상태를 본다.

탭은 처음 방문할 때 불러오며 방문한 탭은 다시 이동해도 상태를 유지한다.

### 5.4 저장과 전달

사용자는 생태계 내용을 포함한 PDF를 만들고, 커뮤니티와 완료된 기능 비교 결과를 선택적으로 포함한다.
또는 HAND-OFF Markdown을 내려받아 다른 에이전트 작업의 입력으로 사용한다.

## 6. 기능 범위

### 6.1 제공하는 기능

- npm 패키지 검색과 사용 가능 여부 확인
- 기준 패키지 기반 유사 후보 조회 및 직접 비교 대상 추가
- 최대 3개 패키지 비교와 URL 상태 복원
- 다운로드·dependents·버전 점유율 비교
- 1년·3년·5년, regular·peer·optional 의존 관계별 전환 분석
- 제거 이유와 관측된 이동 경로 표시
- 버전 후보 조회, 실행 환경 비교, README 기반 기능 비교
- 기준 패키지 GitHub 커뮤니티 조회와 비동기 갱신
- PDF 미리보기·다운로드와 HAND-OFF Markdown 다운로드

### 6.2 의도적으로 제공하지 않는 기능

- 패키지 순위·승자·자동 추천 결론
- 교체의 인과관계 보증
- npm 이외 생태계 지원
- 사용자 계정, 분석 프로젝트 저장, 협업 편집
- 원문 Evidence Drawer와 문장별 인용 탐색
- 분석 세션과 RAG 결과의 영구 보관

## 7. 데이터와 표현 원칙

### 7.1 기준일과 관측 기간

서로 다른 수집원은 최신일이 다를 수 있다. 화면과 출력물은 가능한 범위에서 각 지표의 기준일과
관측 범위를 따로 표시하며, 최신성 차이를 하나의 날짜로 덮지 않는다.

### 7.2 추천이 아닌 관측

교체 흐름과 이동 경로는 의존성 선언의 변화를 집계한다. 함께 빠지고 들어온 패키지가 실제 대체 관계가
아닐 수 있으므로 “대체됐다”가 아니라 “함께 관측됐다”로 표현한다. 양방향 배지는 반대 방향 관측도
있다는 의미다.

### 7.3 결측과 제한

자료가 없거나 비교 근거가 부족할 때 0으로 치환하지 않는다. `미관측`, `자료 없음`,
`COMPARISON_LIMITED`처럼 상태를 드러낸다. 데이터가 일부인 경우 가능한 부분은 보여 주되 완전한
비교처럼 표현하지 않는다.

## 9. 운영·품질 원칙

- 외부 API 장애가 다른 분석 영역까지 전부 막지 않도록 부분 실패를 분리한다.
- 시크릿은 저장소에 기록하지 않고 실행 환경으로 주입한다.
- 로컬과 운영의 MinIO·Spark·nginx 차이를 테스트와 장애 판단에 반영한다.
- 스키마는 Flyway로 관리하고 애플리케이션은 `validate`만 수행한다.
- 사용자에게 보이는 계약은 테스트로 보호하고, 운영 내부 API는 외부에 노출하지 않는다.

## 10. 알려진 제약과 후속 추적

- 분석 보고서 경로의 `reportId`는 현재 `draft`이며 공유 가능한 서버 보고서 ID가 아니다.
- 기능 비교·PDF·Markdown 실행 상태는 서버 프로세스 재시작 시 사라질 수 있다.
- 확장 468k 대상의 최근 dependents, similarity 전체 배치, 일부 데이터 포인터·모니터링은 후속 이슈다.
- 파이프라인 테스트는 모듈별로 존재하지만 저장소 전체 `pytest pipeline`과 CI 계약이 정리되지 않았다.
- 오래된 README의 현재 상태 표현은 별도 README 정리 작업에서 갱신한다.
