## 1. 왜 JdbcClient 인가

명세가 사실상 결정해 두었다.

- **0.7 "집계는 DB 에서 끝낸다"** — 애플리케이션이 하는 일은 JSON 모양으로 바꾸고 요청
  순서로 재배열하는 것뿐이다. 도메인 객체가 필요 없고 `ResultSet → record` 매핑 하나면 된다.
- **§3·§6 의 SQL** 이 `WITH … DISTINCT ON … ROW_NUMBER() OVER (PARTITION BY …)` 다.
  JPQL 로 표현할 수 없다. JPA 를 써도 전부 `nativeQuery = true` 가 되고, 그러면 엔티티 5개는
  `ddl-auto: validate` 의 대상으로만 존재하는 껍데기가 된다.
- **§10-1 이 `= ANY(:names)` 에 JDBC `createArrayOf` 를 명시**한다. JdbcClient 에서 배열
  파라미터를 그대로 넘길 수 있다.
- **v1 에 쓰기가 없다.** 영속성 컨텍스트·더티체킹·1차 캐시가 전부 비용만 된다.

> `spring-boot-starter-data-jpa` 를 남길지는 별개 문제다. 지금 엔티티가 0개라 `validate` 가
> 검증할 대상이 없다. 빼면 `spring-boot-starter-jdbc` 만 남기면 되지만, 팀이 나중에 쓸
> 계획이 있으면 두어도 손해는 없다.

## 2. 패키지 구조

```
com.ssafy.pickage
├─ global/                       (기존)
│  ├─ response/  ApiResponseBody · SuccessResponseBody · FailedResponseBody
│  ├─ exception/ ExceptionType · BusinessException · GlobalExceptionHandler
│  └─ config/    OpenApiConfig · LocalFlywayConfig
└─ domain/packages/              ← 이번에 만든 것
   ├─ PackageNames.java          names 배열 규칙 (0.1) · 검증 완료
   ├─ SnapshotWindow.java        from·to 구간 규칙 (§4) · 검증 완료
   ├─ dto/
   │  ├─ PackagesOverviewResponse.java   §3
   │  ├─ TrendResponse.java              §4·§5 (두 엔드포인트 공용)
   │  ├─ VersionShareResponse.java       §6
   │  ├─ PackageSearchResponse.java      §2.4
   │  └─ DictManifestResponse.java       §2.2
   ├─ PackageController.java     ← 미작성
   ├─ PackageService.java        ← 미작성
   └─ PackageQueryRepository.java ← 미작성
```

`package` 는 자바 예약어라 패키지명으로 못 쓴다. 그래서 `packages` (복수) 다.

**`PackageNames` · `SnapshotWindow` 는 값 객체로 따로 두었다.** 네 엔드포인트가 같은 규칙을
쓰는데, 규칙을 각 컨트롤러에 흩어 놓으면 언젠가 한 곳만 상한이 다르거나 중복 제거를
빠뜨린다. 그 차이는 "어떤 화면에서는 되는데 어떤 화면에서는 안 된다" 로 나타나 원인을
찾기 어렵다.

### 검증 순서가 규칙이다

`PackageNames.of()` 는 **누락(V001) → 상한(V002) → 형식(V004)** 순으로 본다. 순서를 바꾸면
안 된다 — 형식을 먼저 보면 이름 4개 중 하나가 오타일 때 V004 가 나가고, 사용자는 오타를
고친 뒤에야 "3개까지만 됩니다" 를 만난다. 고쳐야 할 것을 한 번에 알려주지 못한다.

날짜 **형식** 검증은 `SnapshotWindow` 가 하지 않는다. 스프링이 `String → LocalDate` 변환에
실패하면 `MethodArgumentTypeMismatchException` 이 나고 전역 핸들러가 그것을 V003 으로
옮긴다. 즉 `SnapshotWindow.of()` 에 도달한 값은 이미 파싱된 날짜다. 여기서 또 검사하면
같은 규칙이 두 곳에 생기고 나중에 한쪽만 고쳐진다.

## 4. 착수 전 확인할 함정

명세 §10 이 네 가지를 짚었다. 여기에 옮기면서 발견한 것 셋을 더한다.

### 4-1. `licenses` 가 JSON 컬럼이다

`List<String>` 으로 바로 안 나온다. `ResultSet.getString("licenses")` 로 문자열을 받아
Jackson 으로 파싱하거나, SQL 에서 `json_array_elements_text` 로 펼친다.
**전자가 낫다** — 후자는 한 패키지가 여러 행이 되어 §3 의 CTE 구조를 흔든다.

### 4-2. `TIMESTAMP` 에 시간대가 없다

DDL 이 `TIMESTAMP` (= `TIMESTAMP WITHOUT TIME ZONE`) 인데 명세 0.5 는 **ISO 8601 UTC** 를
요구한다. 적재된 값이 이미 UTC 라는 전제가 필요하고, 그 전제가 맞는지 파이프라인 쪽에서
확인해야 한다. `LocalDateTime` 으로 읽어 무심코 `atZone(systemDefault())` 을 붙이면 KST 로
해석되어 **9시간이 밀린다**. 에러 없이 조용히 틀리는 쪽이다.

### 4-3. `pct` 를 `double` 로 받지 말 것

명세 §6 SQL 이 `ROUND(..., 1)` 로 소수 한 자리를 만든다. `double` 로 받으면 `91.4` 가
`91.40000000000001` 로 직렬화된다. `BigDecimal` 로 받는다.

### 4-4. `PARTITION BY` 누락 (명세 §10-2)

§3·§6 의 윈도 함수에서 빠지면 **에러 없이 틀린 숫자**가 나온다. §3 은 express 의 증감이
fastify 값과의 차이로 계산되고, §6 은 각 원의 조각 합이 100% 가 아니게 된다.

> 확인법: 패키지 2개로 호출해 각 `pct` 합이 100 인지, 단건 조회의 `stars_delta` 와
> 배치 조회의 값이 같은지 본다. **이 두 가지는 테스트로 박아 둘 것.**

### 4-5. 윈도 함수는 `LIMIT` 보다 먼저 평가된다 (명세 §3)

한 CTE 안에서 `LAG` 와 `LIMIT 2` 를 같이 쓰면 결과는 맞지만 전체 이력에 `LAG` 를 계산한 뒤
2행을 잘라낸다. 명세의 `last2` → `recent` 2단 구조를 그대로 옮길 것.

### 4-6. 배열 바인딩 (명세 §10-1)

문자열을 이어붙여 `IN (...)` 을 만들지 않는다. SQL 인젝션 경로가 열릴 뿐 아니라, 조합마다
SQL 문자열이 달라져 실행 계획 캐시도 못 쓴다. `PackageNames.toArray()` 를 그대로 넘긴다.

### 4-7. 응답 순서는 애플리케이션이 만든다 (명세 0.5)

DB 는 순서를 보장하지 않는다. `PackageNames.values()` 의 순서로 재배열한다.
`not_found` 도 마찬가지로 `PackageNames.notFoundAmong()` 이 요청 순서로 만든다.

## 5. dev 연결

`frontend/vite.config.ts` 에 proxy 를 넣었다. `/api` 와 `/static` 만 8080 으로 넘어간다.

**서버에 CORS 설정을 넣지 않는다.** 브라우저가 보기에 요청은 여전히 같은 오리진(5173)에서
나가므로 프리플라이트 자체가 생기지 않는다. 서버에 `@CrossOrigin` 을 두면 개발 편의를 위한
설정이 운영 코드에 남고, 나중에 허용 오리진을 좁히는 일을 누군가 해야 한다. 운영에서는
nginx 가 같은 오리진으로 묶으므로 이 블록이 필요 없다.

```
# 프론트
cd frontend && npm run dev          # 5173

# 서버
cd backend && ./gradlew bootRun     # 8080

# mock 끄기
frontend/.env.local 의 VITE_USE_MOCK 을 false 로 두거나 줄을 지운다
```

## 6. 구현 순서

**1. `GET /api/packages` 를 끝까지 (수직 절단)**
Controller → Service → Repository → SQL → 테스트. 여기서 패턴이 확정되면 나머지 넷은
같은 모양의 복제다. 이걸 건너뛰고 다섯 개를 동시에 쓰면 나중에 다섯 곳을 같이 고치게 된다.

**2. 추이 둘 (`downloads` · `dependents`)**
평평한 행 집합으로 받아 애플리케이션에서 `name` 별로 묶는다. 형태가 같아 매핑 코드를 공유한다.

**3. `GET /api/packages/version`**
`OVER (PARTITION BY name)` 이 있는 쪽. 4-4 의 테스트를 여기서 박는다.

**4. `GET /api/packages/search`**
인덱스가 선행 조건이다 (§8). 붙인 뒤 `EXPLAIN` 으로 Index Scan 이 뜨는지 확인.

**5. 사전 배포 (§2.2)**
주간 배치의 마지막 단계 + `/api/dict-manifest` + 정적 파일 서빙. 프론트는 이미
manifest → 사전 파일 순으로 받게 되어 있고, **실패하면 전량 서버 폴백으로 동작한다** —
사전은 최적화이지 의존성이 아니므로 마지막에 붙여도 된다.

## 7. 스키마 (2026-09-09 갱신)

새 ERD 의 **핵심 다섯 테이블은 `V1__init.sql` 과 완전히 같다** — 컬럼·PK·UK·FK 전부.
그래서 V1 은 손대지 않는다(고치면 체크섬이 어긋나 기동이 막힌다). 추가분만 V2 로 넣었다.

`V2__index_similar_etl.sql`
1. 명세 §8 조회 인덱스 3개
2. `similar_package` (UC4 · 빈 테이블)
3. `etl_load_execution` · `etl_load_attempt` · `etl_dataset_current`

ETL 테이블은 API 가 읽지 않고 파이프라인이 쓴다. 그래도 Flyway 가 소유한다 —
스키마 정의가 한 곳에 있어야 로컬과 운영이 구조적으로 갈라질 수 없다.

### 7-1. 자동완성 인덱스는 실제로 필요하다 (실측)

`idx_package_name_prefix` 가 정말 일하는지 20,000행으로 확인했다. **collation 에 따라
결과가 갈린다.**

| collation | 인덱스 | 실행 계획 | cost |
|---|---|---|---|
| `en_US.utf8` (운영·compose 기본) | UNIQUE 만 | **Seq Scan** | 358 |
| `en_US.utf8` | + `text_pattern_ops` | **Bitmap Index Scan** | 147 |
| `C` | UNIQUE 만 | Bitmap Index Scan | — |

> **`C` 로케일에서는 이 인덱스가 없어도 접두사 검색이 인덱스를 탄다.** 그래서 로컬을
> `--locale=C` 로 만들어 두고 시험하면 "인덱스 없어도 잘 되는데?" 라는 잘못된 결론이 난다.
> `compose.yaml` 의 `postgres:16` 이미지는 `en_US.utf8` 로 뜨므로 위 표의 첫 줄이 실제 환경이다.

### 7-2. ⚠ §3 SQL 에 구멍이 하나 있다

명세 §3 의 SQL 은 `latest_ver` 를 **INNER JOIN** 한다. 그래서 **`version` 행이 하나도 없는
패키지는 결과에서 통째로 사라진다.**

`not_found` 는 "요청한 이름 − 조회된 이름" 으로 만들므로, 그 패키지는 *존재하는데도*
`not_found` 로 분류된다. 화면은 "이름을 확인하세요" 를 띄우고, 사용자는 멀쩡한 이름을
계속 다시 친다.

실측으로 두 경우를 갈라 확인했다.

| 상황 | 결과 | 명세 0.5 |
|---|---|---|
| `version` 있음 + `package_snapshot` 없음 | items 에 남고 지표만 `null` | ✅ 맞음 |
| `version` 자체가 없음 | items 에서 **사라짐** → `not_found` | ❌ 어긋남 |

**확인이 필요하다:** 파이프라인에서 `package` 행이 `version` 없이 만들어질 수 있나?
(`transform.py` 는 versions 에서 package 를 파생시키는 것으로 보여 실제로는 안 생길 수도 있다.)

- 생길 수 **없다면** → 지금 SQL 그대로 두고, 이 전제를 주석으로 박아 둔다.
- 생길 수 **있다면** → `JOIN latest_ver` 를 `LEFT JOIN` 으로 바꾸고 `latest_version` 을
  nullable 로 연다. 프론트 타입은 지금 `latest_version: string` 이라 이때 같이 고쳐야 한다.

### 7-3. `PARTITION BY` 누락은 정말 조용히 틀린다 (실측)

명세 §6 SQL 을 패키지 2개로 돌려 확인했다.

```
PARTITION BY name 있음 →  express 92.0 + 8.0 = 100.0     fastify 61.9 + 38.1 = 100.0
PARTITION BY name 없음 →  express 88.1 + 7.7 =  95.8     fastify  2.6 +  1.6 =   4.2
```

에러가 나지 않는다. 조각이 그려지고 숫자도 그럴듯하다. **화면에서 원의 합이 100% 가
아닌 것으로만 드러난다.** 이 두 줄은 테스트로 박아 둘 것.

### 7-4. 순환 FK 는 트랜잭션을 강제한다 (실측)

`fk_etl_active_attempt` 가 `DEFERRABLE INITIALLY DEFERRED` 다.

```
자동커밋으로 execution 먼저 INSERT  →  ERROR: violates foreign key constraint
BEGIN … execution + attempt … COMMIT →  성공
```

파이프라인 쪽에서 두 INSERT 를 나눠 커밋하면 **첫 INSERT 부터 실패한다.**
제약을 지우지 말고 트랜잭션을 묶을 것.

### 7-5. 시드 두 벌 — 목적이 다르다

| 파일 | 규모 | 무엇을 보려고 |
|---|---|---|
| `seed_sample.sql` | 패키지 3 × 스냅샷 2 | 자료가 모자란 상태 ("데이터 축적 중") |
| `seed_mock_parity.sql` | 패키지 14 × 스냅샷 130 | 차트가 그려지는 상태 + **대조 검증** |

둘 다 `TRUNCATE` 로 시작하므로 같이 쓸 수 없다. 나중에 돌린 쪽만 남는다.

**`seed_mock_parity.sql` 은 프론트 mock(`dataset.ts`)을 실제로 실행해 뽑은 자동 생성 파일이다.**
그래서 이 시드로 띄운 서버와 `VITE_USE_MOCK=true` 인 화면은 같은 숫자를 그린다.

이게 구현 검증 수단이 된다 — 엔드포인트를 붙인 뒤 mock 을 켰다 껐다 하며 **화면이 달라지는
곳을 찾으면 그게 곧 구현 차이**다. 응답 스키마를 눈으로 대조하는 것보다 촘촘하다.
`not_found` 를 잘못 계산하거나 `PARTITION BY` 를 빠뜨리면 화면에서 바로 드러난다.

실제로 이 시드로 §3·§4·§5·§6 SQL 을 돌려 mock 출력과 대조했고 전부 일치했다
(downloads 1573행, dependents 1573행, `null` 케이스 포함).

> `dataset.ts` 를 고치면 이 파일을 다시 생성해야 한다. 한쪽만 고치면 둘이 갈라지고,
> 그때부터 "화면이 다른데 어느 쪽이 맞는지" 를 알 수 없게 된다.

### 7-6. Parquet → Postgres 적재 경로가 없다

`pipeline/curated` 는 DuckDB 로 Parquet 까지만 만든다. Postgres 로 넣는 단계가 아직 없어서,
실데이터로 화면을 보려면 이 다리를 놓아야 한다. v1 범위에 넣을지는 별도 판단.

## 8. 검증 현황

**자바 로직** — `PackageNames` · `SnapshotWindow` 를 명세의 에러 표에 맞춰 23개 항목으로
확인했다 (검증 순서, 중복 제거 후 상한 판정, 스코프 패키지, 104주 경계, 양 끝 포함 계산 등).

**마이그레이션** — 실제 Postgres 에 V1 → V2 순서로 적용해 확인했다.
테이블 9개·인덱스 생성, 순환 FK 의 트랜잭션 강제, CHECK 3종(hex 형식·`completed_at` 정합성),
명세 §3·§6 SQL 실행, 인덱스 사용 여부(§7-1).

**컴파일** — `./gradlew compileJava` 통과 (2026-09-09). DTO·예외·핸들러 포함 전체.

> 그 과정에서 `settings.gradle` 에 툴체인 자동 내려받기를 넣었다. build.gradle 이 Java 21 을
> 요구하는데 Gradle 은 PC 에 설치된 JDK 중에서만 찾아서, 21 이 없으면
> `Cannot find a Java installation … matching {languageVersion=21}` 로 멈춘다.
> 이제 Gradle 이 필요한 JDK 를 직접 받으므로 팀원이 JDK 를 설치하고 `JAVA_HOME` 을 맞출
> 필요가 없다. Docker 빌드(`eclipse-temurin:21-jdk`)에는 영향이 없다.

**런타임** — `GET /api/packages` 를 실제 서버·실제 DB 로 확인했다 (2026-09-09).

| 항목 | 결과 |
|---|---|
| Flyway V1 → V2 적용 | `now at version v2` · Postgres 16.15 |
| `is_deprecated` snake_case | 나온다 — Jackson 3 에서도 `@JsonProperty` 가 먹는다 |
| `published_at` | `2026-07-14T09:02:11Z` — KST 로 밀리지 않는다 |
| `licenses` | `["MIT"]` — SQL 의 `text[]` 경로가 동작한다 |
| **mock 과 값 일치** | downloads·stars·delta 전부 동일 |

마지막 줄이 이 시드의 목적이다. `VITE_USE_MOCK` 을 켜고 끄며 **화면이 같은지**로 나머지
엔드포인트를 검증할 수 있다.

**§7-2 의 경계가 확정됐다.** 두 경우를 실제 DB 로 갈라 확인한 결과:

```
version 있음 + package_snapshot 없음 (consola)  → items 에 남고 지표만 null   ✅ 명세대로
version 자체가 없음         (인위적 ghost-pkg)  → 빠져서 not_found 로        ❌ 어긋남
```

**즉 구멍은 "스냅샷이 없는 경우" 가 아니다.** 그쪽은 잘 돈다. `version` 행이 하나도 없는
패키지만 해당되고, 파이프라인이 `package` 를 versions 에서 파생시키면 애초에 안 생긴다.
`PackageService#warnIfSilentlyDropped` 가 그 경우를 감지해 경고를 남기고,
`PackageServiceTest` 가 현재 동작을 못 박아 두었다 — LEFT JOIN 으로 바꾸면 그 시험이 깨지고,
그때 프론트의 `latest_version` 타입도 함께 열어야 한다는 것을 알려 준다.

**아직 안 본 것** — 실패 봉투(`{success, code, message}`)가 실제로 나가는지.
`?names=` (V001), 4개 (V002), `?names=Express` (V004) 로 확인할 것.
