## 1. 서비스 범위와 요구사항 원칙

### 서비스 한 문장

OSS Shift는 사용자가 검토 중인 실제 npm 패키지를 입력하면 설명·키워드가 가까운 실제 후보를 최대 3개까지 보여 주고, 사용자가 비교 대상을 정한 뒤 생태계 변화와 정확한 버전의 기능 차이를 근거와 함께 제공하는 서비스다.

### MVP와 확장

| 구분 | MVP | 확장 |
|---|---|---|
| 입력 | 패키지명 또는 `패키지@버전` | 동일 |
| 후보 추천 | 설명·키워드 기반 최대 3개 | 동일 |
| 비교 대상 | 사용자가 선택·직접 추가 | 동일 |
| 보고서 1페이지 | 생태계 변화 분석 | 버전 고착·관측된 교체 흐름 추가 |
| 보고서 2페이지 | 기능 비교 분석 | 동일 |
| 보고서 3페이지 | 없음 | GitHub 커뮤니티 현황 |
| 후보 검색 색인 | 10만 목표 | 20만 이상 확대 가능 |
| 1페이지 사전 집계 | 3만 | 10만 이상 |
| 기능 자료 | 요청한 정확한 버전만 | 반복 요청 버전 캐시 확대 |

### 요구사항 적용 원칙

1. 후보 추천은 MVP에 포함한다.
2. 사람이 비교 묶음을 미리 등록하지 않는다.
3. 추천 후보는 실제로 확인된 npm 패키지만 허용한다.
4. 후보 이름 생성과 후보 순서 결정에 생성형 AI 또는 LLM을 사용하지 않는다.
5. 추천 기준을 넘는 후보가 3개보다 적으면 결과 수를 줄인다.
6. 사용자는 추천 후보를 선택하거나 다른 패키지를 직접 추가한다.
7. 후보 추천은 관련 패키지 발견 기능이며 완전한 대체 관계를 보장하지 않는다.
8. 1페이지와 2페이지는 같은 비교 대상과 정확한 분석 버전을 사용한다.
9. 자료 없음, 확인 불가, 처리 오류와 실제 값 0을 서로 다른 상태로 표시한다.
10. 기술 우열, 최종 추천, 교체 원인과 미래 전망을 단정하지 않는다.

## 3. 전체 사용자 흐름

### MVP

1. 사용자는 서비스 소개에서 관측 범위와 한계를 확인한다.
2. 패키지명 또는 `패키지@버전`을 입력한다.
3. 서비스는 실제 npm 존재 여부와 분석 버전을 확인한다.
4. 서비스는 후보 검색 색인에서 관련 후보를 최대 3개 보여 준다.
5. 사용자는 후보를 선택하거나 다른 npm 패키지를 직접 추가한다.
6. 서비스는 최종 비교 대상의 정확한 버전을 고정한다.
7. 사용자는 1페이지에서 다운로드 변화와 직접·간접 의존, 유지·유입·이탈을 확인한다.
8. 사용자는 2페이지에서 공통 환경·설치 조건과 공식 자료에서 실제로 발견한 기능을 비교한다.
9. 모든 확정 기능 주장에 연결된 근거를 확인한다.
10. 사용자는 같은 내용과 근거가 유지된 PDF를 받을 수 있다.

### 확장

1. MVP 흐름과 1·2페이지는 그대로 유지한다.
2. 1페이지에 버전 고착과 관측된 교체 흐름을 추가한다.
3. GitHub 저장소 연결을 검증할 수 있는 경우 3페이지를 제공한다.
4. 3페이지에는 정보 범위와 조회 시점을 함께 표시한다.

| 공통-R03 | 자료 없음·확인 불가·처리 오류·값 0을 구분해야 한다. | 상태별 문구 제공 | 알 수 없는 값을 0으로 변경 금지 | 네 상태가 구분됨 |
| 공통-R04 | 사용자가 최종 비교 대상을 확정해야 한다. | 후보 선택·직접 추가 가능 | 추천 후보 자동 확정 금지 | 보고서 대상과 선택 목록 일치 |
| 공통-R05 | 같은 분석에서 패키지 버전은 끝까지 고정되어야 한다. | 1·2페이지와 PDF 버전 일치 | 중간에 최신 버전으로 변경 금지 | 모든 페이지 버전 일치 |
| 공통-R06 | 후보 추천은 관련 후보 발견으로 표현해야 한다. | 사용자가 선택 필요성을 이해 | 완전 대체·최고 대안 표현 금지 | 화면·PDF에 오해 표현 없음 |
| 공통-R07 | 후보 추천 단계에서 생성형 AI 또는 LLM을 호출하지 않아야 한다. | 로컬 검색 결과만 표시 | 후보 이름 생성·재정렬 금지 | 후보 처리 기록에 생성형 호출 없음 |
| 공통-R08 | 1페이지는 직접 의존과 간접 의존을 구분해야 한다. | 두 결과 범위 확인 | 하나의 사용량으로 합치지 않음 | 제목·정의가 구분됨 |
| 공통-R09 | 2페이지는 특정 패키지 분야의 기능표를 공통 기준으로 강제하지 않아야 한다. | 자료에서 발견한 기능만 비교 | HTTP 기능을 모든 분야에 적용 금지 | 여러 분야 검수 가능 |
| 공통-R10 | 기능 비교의 확정 문장에는 원자료 근거가 연결되어야 한다. | 근거 번호를 열어 확인 | 근거 없는 확정 문장 금지 | 확정 주장 모두 근거 연결 |
| 공통-R11 | `지원하지 않음`은 공식적인 미지원 근거가 있을 때만 사용해야 한다. | 부정 근거가 있을 때 제한 표시 | 검색 실패만으로 미지원 판정 금지 | 부정 판정 검수 통과 |
| 공통-R12 | 화면과 PDF는 같은 분석 결과와 근거를 사용해야 한다. | 값·버전·기준일 일치 | PDF에서 다른 계산 금지 | 화면·PDF 대조 일치 |

| 상황 | 서비스 동작 | 사용자 안내 | 다음 행동 |

### 허용 표현

- 관련 후보
- 설명이 의미상 가까운 후보
- 공개 npm 자료에서 관측된 변화
- 직접 의존 선언
- 간접 의존 관계
- 현재 확보한 근거에서 지원을 확인
- 특정 조건에서 제한적으로 지원
- 현재 근거로는 확인 불가
- 추가 검토가 필요한 차이

### 사용하지 않는 표현

- 가장 좋은 패키지
- 자동 추천 1위
- 완전한 대체재
- 실제 사용자 수·실제 설치량
- 기술 품질 보증
- 특정 패키지 때문에 교체했다는 원인 단정
- 검색되지 않았으므로 지원하지 않음
- 곧 사라질 패키지
- 앞으로 성공할 패키지
