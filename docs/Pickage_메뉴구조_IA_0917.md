## 1. IA 적용 원칙

0. 모든 화면은 데스크톱 컴퓨터의 웹 브라우저를 기준 화면으로 설계한다.

1. 사용자는 접두사 자동완성 결과를 선택하거나 패키지명을 자유 입력한 뒤 서버 검증을 거쳐 다음 단계에 진입한다. 시스템은 입력을 임의의 다른 이름으로 교체하지 않는다.
2. 기준 패키지는 고정 선택하고 후보 ranking 상위 최대 3개는 미선택 카드로 제공한다.
3. 비교 대상은 기준 패키지를 포함해 총 3개로 제한한다.
4. 후보 카드는 패키지명·설명·유사도 순위·최신 버전을 보여준다. API 수치 score와 관문 판정은 표시하지 않으며 유사도 순위는 기술 품질 순위가 아니다.
5. MVP 보고서는 생태계 변화 1페이지로 완결된다.
6. MVP Dependency는 직접 의존만 제공한다. 간접·전이 의존 기능은 프로젝트 범위에서 제외한다.
7. Dependency는 카드 안에서 `Total` 또는 하나 이상의 major를 선택하며, 프런트가 이미 받은 major별 series를 합산한다.
8. Version Share는 최신 DB Snapshot의 version별 dependents를 major로 합산한 비중이며 시간축을 제공하지 않고 기준일을 카드 안에 표시한다.
8A. MVP Direct Dependency 하단에는 패키지별 **조회 구간 첫 유효 관측값 → 마지막 유효 관측값** signed 총수 증감을 표시하되 이를 유지·유입·이탈로 표현하지 않는다. 증감값은 프론트 adapter가 dependents trend의 첫·마지막 유효 point로 계산한다.
8B. Dependency `Total`은 **의존 수(버전별 합계)**이며 고유 프로젝트 수로 표현하지 않는다. 비교 시계열은 규모 차이를 고려해 로그축을 사용하고, 유효 point가 2개 이하이면 `데이터 축적 중 (N주차)` 상태를 우선한다.
8C. Downloads는 직전 7일 합계의 주간 point이며 조회 요청 상한은 최대 104주다. 비교 시계열은 로그축이고 유효 point가 2개 이하이면 계열별로 같은 축적 중 상태를 사용한다. 로그축과 계열별 판정은 현재 코드의 후속 구현 항목이다. 기준일 달력이 월요일 주간이 아니어도 서버가 구간 합계를 일평균으로 펼쳐 **월요일 주간 합계**로 환산해 내려준다(S15P21A506-403).
9. 기능 비교와 Evidence Drawer는 확장 화면으로 분리한다.
10. PDF는 보고서 상단의 공통 행동으로 제공하며 생태계 결과와 현재 선택 버전의 기능 비교 결과가 모두 완료되어야 생성 가능하다.
11. 자료 부족·부분 완료·오류는 결과가 나타나는 바로 그 영역에서 표시한다. 게시 데이터 상태와 UI 요청 상태를 별도 축으로 표현하며 PDF lifecycle의 `READY`와 구분한다. 카드별 실패 격리는 현재 코드의 후속 구현 항목이다.
12. 보고서 화면에서는 추천·순위·승자 표현을 사용하지 않는다.
13. 키보드 포커스와 상태 문구를 제공하고 색상만으로 의미를 전달하지 않는다.
14. 확장 화면의 저장소·출처 식별 정보는 외부 링크로 동작하지 않는다.

```text

         ├─ 1. 생태계 변화 [MVP + 인페이지 확장]

         │  │  └─ 직접 Dependency [MVP]

         │  ├─ Activity / Downloads
         │  ├─ 최신 Version Share Snapshot
         │  ├─ 버전 고착 [확장-01 제공 시 · 인페이지]
         │  └─ 관측된 교체 흐름 [확장-02 제공 시 · 인페이지]
         ├─ 2. 기능 비교 [확장]
         │  ├─ 기능 비교 버전 선택
         │  ├─ 분석 진행·완료 상태
         │  ├─ 핵심 환경·설치 조건
         │  ├─ 핵심 기능 비교
         │  ├─ 기능 비교 해설
         │  └─ Evidence Drawer
         ├─ 3. GitHub 커뮤니티 현황 [확장]
         ├─ 유지·유입·이탈 분석 [확장 검토 · 진입 UI 미정]

            ├─ 생성 중
            ├─ 다운로드 완료
            └─ 생성 불가
```

### 4.2 UI 계약

`DEC-HERO-INPUT-20260919-01`: 히어로의 패키지 입력은 화면-01(§5.2)과 같은 `PackageSearch`
컴포넌트를 재사용한다 — 접두사 자동완성 목록·자유 입력·Enter 확정 규칙이 동일하다. 여기서는
서버 검증(`/packages/similar`)을 하지 않고 형식만 확인한 뒤 화면-01·02(패키지 입력·후보 선택)로
바로 진입시킨다. 존재 여부·후보 조회는 진입한 화면에서 확인한다.

| 분석 결과 예시 | Hero 아래 | 읽기 전용 | 없음 | MVP 생태계 분석과 확장 기능의 범위 이해 |
| 범위 안내 | 화면 하단 | 항상 표시 | 없음 | 우열·실제 사용량 오해 방지 |

Hero 의 배경은 **뷰포트 전폭**이다. 화면이 컨테이너 최대 폭(1440px)보다 넓어져도 좌우가 비어 보이지 않는다(S15P21A506-404).
Hero 는 **자동완성 목록이 아래로 내려와도 잘리지 않는다.** 배경 도형만 자르고 내용은 자르지 않는다.
Hero 설명은 제품 책임자가 정한 문구다 — `유사한 기능을 가진 패키지를 제안하고, 믿을 수 있는 근거와 함께 분석을 제공합니다.` /
`PDF로 다운로드 받아 팀원들과 공유하세요.` "추천" 이 아니라 **"제안"** 이다 — 서비스는 유사 후보를 내놓을 뿐 우열·최종 선택을
권하지 않는다(§1-12, 아래 "관측 범위와 판단 한계"). 후보 자격 관문처럼 아직 로직이 없는 것은 약속하지 않는다.
예시로 둘러보기 패키지는 `express`·`yaml`·`axios` 이다(실데이터가 있고 유사 후보 계산이 `COMPLETE` 인 이름).
소개 화면의 문구는 줄을 **마침표·쉼표 뒤에서만** 바꾼다 — 글자 수대로 끊으면 뜻이 잘린다.

### 8.1.1 조회 기간·열 높이·설명 안내 (S15P21A506-405)

**조회 기간.** 조작줄 왼쪽에 프리셋 `전체 기간·반년·1년·2년·3년`이 있고, 그 오른쪽에 세부 기간(시작일 ~ 종료일)이 있다.
기본은 **전체 기간**이다. 프리셋은 최신 집계일에서 N개월을 거슬러 올라가 **그 이후의 첫 집계일**을 시작으로 삼아 세부 기간에
채운다 — 시작·끝은 언제나 서버가 준 실제 집계 날짜다. 세부 기간을 직접 고르면 프리셋 선택이 풀린다. 자료가 프리셋보다 짧으면
전체 기간과 같은 구간이 되고 누른 프리셋은 눌린 채로 둔다. 표시 간격(`매주·2주·4주·분기`)은 오른쪽 끝에서 따로 고른다.

**좌우 열의 높이는 언제나 같다.** 왼쪽(그래프 카드 둘)과 오른쪽(패키지 카드)의 위·아래가 맞아 사이에 이유 없는 빈 공간이 없다.
- 오른쪽이 길면 왼쪽 그래프 카드 둘이 늘어난 높이를 **똑같이 나눠** 갖고, 그래프도 함께 커진다.
- 왼쪽이 길면 오른쪽 패키지 카드가 늘어나고 안의 요소는 **세로 중앙**에 놓인다.
- 한 열로 무너지는 좁은 화면에는 적용하지 않는다. 예전의 왼쪽 열 `sticky` 는 폐지했다.

**설명 안내는 ⓘ 모달로 둔다.** 매번 읽을 필요는 없지만 궁금할 때 찾아볼 설명은 화면에 상시 노출하지 않고 ⓘ 버튼 뒤에 둔다.
| 자리 | 모달 제목 | 내용 |
|---|---|---|
| 의존 수 그래프 제목 옆 | `의존 수란?` | 개념·직접 의존만 세는 것·버전별 합계라 실제 프로젝트 수보다 클 수 있음 |
| Downloads 그래프 제목 옆(구간이 관측 시작보다 앞서 잘렸을 때만) | `Downloads` | 이 지표의 관측 시작일 |
| 표시 버전 줄 끝 | `표시 버전` | 전체와 버전 선택의 뜻, 선택은 패키지마다 독립 |
| Version Share 라벨 옆 | `Version Share` | major 단위 비율, 실제 설치 버전이 아님 |
| 유지·유입·이탈 제목 옆 | `계산 기준` | 의존 수 증감과 다른 기준, devDependencies 제외 |
| 의존 종류 토글 옆 | `의존 종류` | 일반·동반·선택 의존의 뜻 |

**용어.** 화면에서 영어 `Dependents` 를 쓰지 않는다. 그래프는 **의존 수**, 카드 증감은 **의존 수 증감**이다(기획서가 정한 "의존 수(버전별
합계)"). 영어 표기는 `의존 수란?` 모달 본문에만 밝힌다. **PDF 보고서의 제목도 같은 말이다**(`ReportHtmlRenderer`) — 화면과 문서의 용어가 갈리지 않는다. **쓰지 않는 말:** "사용처", "N개 프로젝트가 사용", "가져다 쓰는 수" — 이 값은 의존을
**선언**한 횟수를 버전별로 더한 합계라 고유 프로젝트 수나 실제 설치·사용량으로 읽히면 안 된다.

| major 선택 | 선택한 major들을 표시하고 해당 series 합계 선만 갱신 |
| 일부 기간 | 관측 범위 안의 빈 주는 서버가 월요일 격자로 선형 보간해 이어 주므로 선이 끊기지 않음. 관측 시작 이전은 표시하지 않음(S15P21A506-403) |
| 유효 관측값 2개 미만 | 패키지별 증감 영역에 0 대신 자료 상태 표시 |
| 유효 point 2개 이하 | 선 추세 대신 `데이터 축적 중 (N주차)` 또는 동등한 상태 표시 |
| 자료 없음 | 그래프 영역 안에 자료 없음과 범위 표시 |
| 오류 | 이전 정상 결과가 있으면 유지, 오류 표시 |

### 8.4 Activity 카드

| 요소 | 위치 | 기본 상태 | 동작 |
|---|---|---|---|
| 주간 Downloads [MVP] / Issues [확장] | 우측 상단 | MVP에서는 주간 Downloads만 표시 | Downloads point는 직전 7일 합계, 최대 104주; Issues 확장이 실제 제공될 때 같은 카드에서 Issues 전환 UI 추가 |
| 그래프 | 중앙 | Downloads 시계열 · 로그축 | 규모 차이가 큰 패키지도 변화 방향이 보이도록 표시하며, 그 패키지의 행이 없어 7일이 덮이지 않은 주는 점이 없어 선을 끊음(주간 관측 간격 8일 초과) |
| 축적 부족 상태 | 그래프 영역 | 유효 point 2개 이하 | 선 대신 `데이터 축적 중 (N주차)` 또는 동등한 상태 |
| 기간·출처 | 하단 | 항상 표시 | 자료 구간과 최대 104주 조회 요청 상한 확인 |

현재 MVP V2 기본 화면에는 Issues 전환 UI를 노출하지 않는다.
Issues 시계열은 확장 제공 시 Activity 카드 안에서 활성화하며, GitHub 커뮤니티 화면에 중복 배치하지 않는다.

### 8.5 Version Share 카드

Version Share는 최신 DB Snapshot으로 고정하며 시계열 조작을 제공하지 않는다.

이 절의 패키지 탭은 Version Share 전용 독립 탭이 아니라 **패키지 상세 카드 전체(뱃지·Dependents 증감·Version Share)가 공유하는 선택 탭**이다(S15P21A506-379) — 탭을 바꾸면 Dependents·Downloads 카드의 강조도 함께 바뀐다. §7 공통 상단이 아니라 이 카드 하나의 상단에 있다.

| 요소 | 위치 | 기본 상태 | 동작 |
|---|---|---|---|
| 패키지 탭 | 카드 상단 | 기준 패키지 | 다른 패키지 전환(카드 전체 갱신) |
| Snapshot 기준일 | 카드 상단 또는 하단 메타 | 항상 표시 | API가 사용한 최신 DB 집계 시점 확인 |
| 도넛 | 좌측 | 최신 관측 비중 | version별 dependents의 major 합산 분포 확인 |
| 계열 막대 | 우측 | major별 최신 비중 | 비중 확인 |
| 기타 | 막대 하단 | 표시 상한을 넘는 major가 있을 때 | 나머지 major 합계 확인 |
| 해석 안내 | 카드 하단 | 항상 표시 | 실제 설치 버전·고유 프로젝트 비중·요구조건 해석 결과가 아님을 안내 |

시간축, 과거 Snapshot 선택, Version Share 추이 선은 MVP에 배치하지 않는다. requirement 해석 기반 `UNKNOWN|AMBIGUOUS` 표시는 확장 단계에 추가한다.

## 11. 확장 화면: GitHub 커뮤니티 현황

### 11.1 페이지 순서

1. 커뮤니티 보고서 서브헤더 (탭 콘텐츠 내부. 공통 상단의 브랜드·메뉴는 다시 그리지 않는다)

   - 검증된 저장소 식별 정보

2. 커뮤니티 요약 지표
   - 분석 이슈
   - 누적 댓글
   - 사용자 반응
   - 열린 상태
3. `핵심 논의` — 열린 Issue 가 하나도 없을 수 있어 `지금 이어지는` 이라는 말은 쓰지 않는다(S15P21A506-407)
4. 핵심 Issue별 쟁점 카드
5. `실제 논의 흐름`
6. Issue별 대화형 댓글 기록

Issue의 장기 시계열은 이 화면에 중복 배치하지 않고 생태계 변화의 Activity 확장 영역에서 제공한다.

### 11.2 상단 보고서 요약

| 요소 | 표시 규칙 |
|---|---|
| 보고서 제목 | 선택 패키지명 + `커뮤니티 현황` |
| 한 문장 설명 | 해당 저장소의 공개 Issue에서 핵심 논의와 실제 댓글 흐름을 본다는 목적 표시. 열린 Issue 가 없어도 성립하는 문장이어야 한다 |
| 저장소 | 검증된 GitHub 저장소 식별 정보. 링크가 아닌 글자로만 쓰고(`github.com/{owner}/{repo}`) 같은 카드에 ⓘ `수집 기준과 한계`·최신 여부 배지·기준 시각을 둔다 |
| 분석 기준 | 이번 분석에 포함한 공개 Issue 범위. 별도 줄로 쓰지 않고 `분석 이슈` 칸의 부제(`최근 N일 공개 Issue`)와 ⓘ 모달이 말한다 — 저장소 카드와 요약 칸에 같은 수를 두 번 적지 않는다 |
| 분석 이슈 | 실제 분석 대상 Issue 개수 |
| 누적 댓글 | 분석 대상 Issue의 댓글 합계 |
| 사용자 반응 | 분석 대상 Issue에서 확인한 reaction 합계. 부제는 `GitHub 반응 합계` — `추천`·`관심` 같은 말로 풀지 않는다 |
| 열린 상태 | 분석 대상 Issue 중 OPEN 상태 개수. 화면 라벨은 `열린 Issue`, 0건이면 부제로 `분석한 Issue 모두 종료`를 쓴다 |

Figma에 표시된 예시 수치 자체를 고정하지 않고 현재 분석 snapshot에 따라 갱신한다.

### 11.3 핵심 이슈와 쟁점

각 핵심 Issue는 독립 카드로 보여준다.

| 정보 | 표시 규칙 |
|---|---|
| Issue meta | 번호, 열림/종료 상태(색이 아니라 글자), 댓글 수, 반응 수. 카드 왼쪽 굵은 선과 번호 색은 같은 Issue 의 `실제 논의 흐름` 카드와 잇는 장식이다 |
| 제목 | 실제 논의 주제를 이해할 수 있는 제목 |
| 쟁점 요약 | 현재 문제와 충돌 지점을 짧게 설명 |
| ~~논의 흐름~~ | **표시하지 않는다**(2026-09-20, S15P21A506-406). 쟁점 요약이 같은 사건을 이미 말하고 있어 번호 목록이 되풀이일 뿐이라 뺐다. API 는 `flow` 를 계속 내려주지만 화면은 쓰지 않는다 |

Figma의 예시처럼 서로 다른 Issue를 병렬로 비교해서 볼 수 있지만, 카드 수와 배치는 실제 분석 대상에 따라 달라질 수 있다.

### 11.4 실제 논의 흐름

핵심 이슈 다음에는 실제 공개 댓글을 대화 카드 형태로 보여준다.

| 정보 | 표시 규칙 |
|---|---|
| Issue 식별 | 어떤 Issue의 대화인지 명확히 표시 |
| 작성자 | 공개 GitHub 작성자 식별명 |
| 역할 | ISSUE_AUTHOR·REPOSITORY_OWNER·ORGANIZATION_MEMBER·COLLABORATOR·CONTRIBUTOR 중 원본으로 확인된 것만 표시. USER_SOLUTION은 별도 메시지 유형 |
| 메시지 | 원문 댓글의 핵심 논지를 한국어로 요약 |
| 순서 | 실제 댓글 순서와 논지 전개를 유지 |
| 정렬 | 저장소를 운영하는 쪽(REPOSITORY_OWNER·ORGANIZATION_MEMBER·COLLABORATOR)의 발화는 오른쪽에 두고 아이콘도 오른쪽에 붙여 답변하는 느낌을 준다. 작성자·기여자·역할 없음은 왼쪽. 정렬은 장식이며 역할은 배지 글자로 함께 말한다(S15P21A506-407) |
| 표시 | 발화 날짜는 한국 시간 기준. `해결 방법 제시`(USER_SOLUTION)만 라벨을 달고 일반 논의에는 달지 않는다. 카드 제목은 `핵심 논의` 카드와 같은 말이라 다시 쓰지 않고 `ISSUE #번호`로 잇는다. `댓글 N개 중 대표 발화 N개` 같은 부가 문구는 두지 않는다 |

서비스가 새로운 대화를 생성하거나 여러 사용자의 발화를 하나의 가상 발화로 합치지 않는다. 생성 시 원문 근거를 검증하고 게시된 대표 메시지는 원본 댓글 식별자와 내부 연결한다. raw 원문과 문장별 support 목록의 장기 보존을 의미하지 않는다.

### 11.5 저장소 미검증 예외

커뮤니티 현황은 기준 패키지 하나만 대상으로 하며 패키지 전환을 제공하지 않는다. 저장소 연결이 검증되지 않으면 비활성 상태와 이유를 표시하고 다른 패키지 정보로 대체하지 않는다. 저장소 주소는 읽기 전용이며 외부로 이동하지 않는다.

### 11.6 수집 상태와 탭 유지

최초 기준 패키지 하나의 Issue 최대 2개·Issue별 최신 댓글 최대 100개·대표 댓글 최대 3개를 표시한다.
PR은 포함하지 않는다. 수치는 같은 Issue 집합 기준이며 저장소 전체 합계처럼 보이지 않게 한다.
24시간 이후 결과에는 stale를 표시하고 7일 경계 이후 결과는 숨긴다.
요약 실패는 검증된 제목·수치까지 숨기는 사유가 아니다. 전체 요약 실패는 실패 완료 후 5분부터 사용자 재시도를 제공한다.
저장소 미검증/모호/미지원/논의 없음, 최초 수집 중, 이전 결과 갱신 중, 일부 요약 실패를 구분한다.
진행 상태는 실제 서버 단계로 표시하며 가짜 퍼센트를 사용하지 않는다.
탭을 나가면 GET polling을 멈추되 서버 작업은 취소하지 않는다. 탭 왕복 시 생태계 기간·major 필터를 보존한다.

**한계·수집 기준의 노출 위치 (S15P21A506-406).** 같은 사실을 두 번 말하지 않는다.
- 저장소 수준 한계(패키지 범위 추정, 제외된 이슈 등)와 수집 기준(조회 기간·Issue·댓글 상한)은 저장소 이름 옆 ⓘ 모달 `수집 기준과 한계`에 모은다. 저장소를 확인하지 못한 상태에서도 둔다.
- Issue 수준 한계(요약 입력 한도 등)는 그 Issue 요약 옆 ⓘ 모달 `요약 안내`에 둔다. 남는 한계가 없으면 ⓘ 도 없다.
- Issue 카드의 수집 상태 배지(`댓글 전체 수집·댓글 일부만 수집·댓글 수집 실패`)가 이미 말하는 문장(`댓글 일부만 수집했습니다.`, `댓글을 확인하지 못했습니다.`)은 되풀이하지 않는다.
- 불완전 수집을 완전한 논의로 오해하게 하면 안 되므로, 모달로 옮겨도 한계 내용 자체는 남긴다.

API enum·상태별 행동·파트별 인수 조건은
[커뮤니티 구현계획](for_community/Pickage_GitHub커뮤니티_구현계획_260908.md)을 따른다.
이 계약은 목표이며 현재 코드는 두 탭·fixture 기반 문맥으로 community가 아직 구현되지 않았다.

## 12. PDF 내보내기 [확장: 기능 비교 제공 이후]

Figma 상태: `485:1090`, 문서 레이아웃: `485:1441`

PDF는 기능 비교가 제공되는 단계에 영역별 선택 없이 `Pickage 통합 보고서 PDF 1종`으로 제공한다. 현재 선택 버전의 기능 비교 결과가 완료되어야 하며, 버전을 바꾼 뒤 재분석이 필요하면 PDF를 생성할 수 없다.

### 12.1 진입

보고서 공통 상단의 `PDF 내보내기`를 선택하면 서비스가 생태계 결과와 각 비교 패키지의 현재 선택 버전 기능 비교 결과를 함께 확인한다.

### 12.2 READY 확인 화면

| 구역 | 표시 정보 |
|---|---|
| 상단 | PDF 내보내기 제목과 닫기 |
| 비교 대상 | 최종 패키지명 |
| 조회 기간 | 생태계 기간 |
| Dependency 표시 | 패키지별 직접 의존 Total 또는 선택 major 합계 |
| Version Share | 최신 DB Snapshot 기준일 |
| 기능 비교 | 패키지별 선택 버전과 완료 결과 일치 여부 |
| 포함 내용 | 직접 Dependency·Snapshot 간 signed 증감·Downloads·Version Share Snapshot·현재 선택 버전 기능 비교·자료 상태 |
| 자료 상태 | 전체·부분·자료 없음·오류 |
| 하단 | 취소, PDF 생성 |

사용자는 이 화면에서 문서 구성을 편집하지 않는다.

기능 비교는 필수 포함 항목이며, 커뮤니티는 완료된 경우에만 포함 여부를 읽기 전용 정보로 추가 표시할 수 있다.

### 12.3 생성 상태

| 상태 | 표시 | 행동 |
|---|---|---|
| GENERATING | `PDF를 만들고 있습니다`, 단계별 진행 | 창 닫기 가능 |
| COMPLETE | 파일명, 생성 시각, 페이지 수, 크기 | 자동 다운로드, PDF 다시 받기 |
| FAILED | PDF 생성 작업 실패, 완료 파일 없음 | 다운로드 실패와 구분해 오류 표시 |
| 다운로드 실패 | 동일 파일 준비 상태 유지 | PDF 다시 받기 |
| BLOCKED | 비교 대상 미확정·생태계 핵심 결과 미완료·스냅샷 생성 오류·기능 비교 미실행·선택 버전 불일치 | 보고서 또는 기능 비교로 돌아가기 |

### 12.4 PDF 물리 구조

필수 구성:

- 표지·요약
- 후보·비교 대상과 분석 범위
- Downloads
- 직접 Dependency와 표시 필터
- Snapshot 간 직접 의존 선언 수 signed 증감
- 최신 DB Snapshot 기반 Version Share와 기준일
- 현재 선택 버전의 기능 비교와 근거 요약
- 자료 상태·해석 한계

확장 기능이 완료된 경우 추가 가능:

- Issues·GitHub 커뮤니티

실제 용지 수는 콘텐츠 길이에 따라 증가한다.
