## 1. 한눈에 보는 결론

> **서비스 한 문장** OSS Shift는 사용자가 검토 중인 npm 패키지를 입력하면 실제 수집된 패키지 중 의미가 가까운 후보를 보여 주고, 사용자가 비교 대상을 고른 뒤 생태계 변화와 정확한 버전의 기능 차이를 근거가 연결된 보고서로 제공한다.

### 왜 만드는가

패키지를 선택할 때 개발자는 다운로드 변화, 의존 관계, 버전, README, 타입 선언, GitHub 저장소 등 여러 자료를 따로 확인해야 한다. 또한 이름이나 인기가 비슷하더라도 실제 목적이 다른 패키지가 섞일 수 있어 후보 탐색과 기능 비교에 시간이 든다.

OSS Shift는 이 과정을 다음 두 단계로 줄인다.

1. **후보 발견**: 입력 패키지의 설명과 키워드와 의미가 가까운 실제 npm 패키지를 빠르게 찾는다.
2. **근거 비교**: 사용자가 선택한 정확한 버전을 기준으로 생태계 변화와 공식 자료에서 확인된 기능 차이를 나란히 보여 준다.

### 무엇이 4주 뒤 완성되어야 하는가

- 사용자가 패키지명 또는 `패키지@버전`을 입력할 수 있다.
- 버전을 입력하지 않으면 분석할 정확한 버전을 확정해 이후 보고서에서 바꾸지 않는다.
- 후보 추천은 MVP에 포함한다.
- 후보는 실제 수집된 npm 패키지 안에서 설명·키워드의 벡터 유사도로 찾는다.
- 기본적으로 최대 3개를 보여 주되 기준을 넘는 후보가 부족하면 억지로 채우지 않는다.
- 사용자는 추천 후보를 선택하거나 다른 패키지를 직접 추가한다.
- MVP 보고서는 `생태계 변화 분석`과 `기능 비교 분석` 두 하위 페이지로 제공한다.
- 화면과 같은 기준일·버전·근거를 유지한 PDF를 제공한다.
- 1페이지 사전 집계는 3만 패키지를 MVP 범위로 둔다.
- 후보 검색 색인은 10만 패키지를 MVP 목표로 둔다.

## 2. 문제와 기회

### 개발자가 실제로 겪는 상황

예를 들어 `winston`을 검토하는 개발자는 npm과 문서 사이트를 오가며 다음을 확인한다.

- 비슷한 목적의 다른 패키지가 무엇인지
- 최근 다운로드 변화가 어떤지
- 공개 npm 생태계에서 의존 선언이 유지·유입·이탈하고 있는지
- 현재 프로젝트 환경에서 설치·실행 조건이 맞는지
- 선택한 버전에서 실제로 제공되는 주요 기능이 무엇인지
- 그 판단의 근거가 어느 문서와 파일에 있는지

### 해결해야 할 핵심 문제

| 번호 | 문제 정의 |
|---|---|
| 문제-01 | 관련 패키지 후보를 직접 찾고 비교 대상을 정하는 데 시간이 든다. |
| 문제-02 | 다운로드 변화와 공개 의존 관계 변화를 서로 다른 출처에서 확인해야 한다. |
| 문제-03 | 직접 의존과 간접 의존, 자료 없음과 실제 0이 섞이면 잘못 해석하기 쉽다. |
| 문제-04 | 패키지 분야마다 기능이 다른데 고정된 기능표로는 비교하기 어렵다. |
| 문제-05 | 정확한 버전이 아닌 최신 문서만 보면 과거 버전의 기능을 잘못 판단할 수 있다. |
| 문제-06 | 비교 결과와 원자료 근거를 다시 정리해 팀 공유용 문서를 만들어야 한다. |
| 문제-07 | 버전 전환과 실제 교체 흐름, GitHub 커뮤니티 상황은 추가 검토가 필요하다. |

> **해결하지 않는 문제** 기술적으로 가장 좋은 패키지를 자동 선정하거나, 특정 패키지로 교체해야 한다고 결정하지 않는다. 실제 설치·실행량, 보안 보증, 유지보수 품질, 교체 원인, 미래 생존 가능성도 자동으로 단정하지 않는다.

## 3. 목표 사용자와 사용 상황

> **주 사용자** 새 서비스를 만들거나 기존 패키지를 교체하면서 npm 패키지 선택을 실제로 책임지는 기술 책임자와 경력 개발자

| 구분 | 내용 |
|---|---|
| 결정 상황 | 새 프로젝트 도입, 오래된 패키지 교체, 기능·환경 차이 검토 |
| 현재 행동 | 후보 검색 → 다운로드·의존성 확인 → README·타입·버전 문서 확인 → 팀 논의 |
| 필요한 정보 | 관련 후보, 최근 변화, 정확한 버전의 기능 근거, 비교 한계 |
| 최종 산출물 | 팀에서 검토할 수 있는 화면 보고서와 PDF |

### 사용자가 답을 얻어야 하는 질문

- 이 패키지와 의미가 가까운 실제 npm 패키지는 무엇인가?
- 추천 후보 중 내가 비교할 대상을 직접 고를 수 있는가?
- 다운로드와 공개 의존 선언은 최근 어떻게 변했는가?
- 직접 의존과 간접 의존은 각각 어떻게 보이는가?
- 기존 선언은 얼마나 유지되고 새로 유입되거나 이탈하는가?
- 선택한 정확한 버전의 실행 환경과 설치 조건은 무엇인가?
- 선택한 패키지들의 공식 자료에서 실제로 확인되는 핵심 기능 차이는 무엇인가?
- 근거가 부족한 항목은 명확히 `확인 불가`로 표시되는가?

## 4. 서비스 정의와 제공 가치

### 서비스가 하는 일

- 패키지명 또는 `패키지@버전`을 입력받는다.
- npm Registry에서 존재 여부와 분석할 정확한 버전을 확인한다.
- 입력 패키지의 설명·키워드 정보를 바탕으로 로컬 후보 검색 색인에서 가까운 실제 npm 패키지를 찾는다.
- 후보 카드에 설명 유사도, 공통 키워드, 버전, 배포일 등 계산 가능한 근거를 보여 준다.
- 사용자가 후보를 선택하거나 다른 패키지를 직접 추가하게 한다.
- 1페이지에서 다운로드 변화와 공개 의존 관계의 유지·유입·이탈을 보여 준다.
- 2페이지에서 정확한 버전의 실행 환경·설치 조건과 실제 공식 자료에서 발견된 기능을 비교한다.
- 기능 비교의 모든 확정 주장에 원자료 근거를 연결한다.
- 근거가 부족한 항목은 `확인 불가`로 표시한다.
- 같은 결과를 화면과 PDF로 제공한다.
- 확장 단계에서 버전 고착, 관측된 교체 흐름, 검증된 GitHub 커뮤니티 현황을 추가한다.

### 사용자에게 주는 가치

| 기존 불편 | 서비스 경험 | 얻는 결과 |
|---|---|---|
| 후보를 직접 찾아야 함 | 최대 3개의 관련 후보 확인 | 탐색 시작 시간 단축 |
| 인기 지표만 보게 됨 | 다운로드와 의존 선언 변화를 분리 | 변화의 성격을 구분 |
| 기능표가 분야에 맞지 않음 | 선택한 패키지 문서에서 기능 항목 생성 | 로깅·검증·테스트·빌드·ORM·CLI 등에도 같은 절차 적용 |
| 최신 문서가 과거 버전과 섞임 | 정확한 `패키지@버전`에 근거 고정 | 버전별 판단 오류 감소 |
| 근거를 다시 정리해야 함 | 주장마다 원자료 근거 연결 | 팀 공유와 재검토 용이 |

### 서비스의 판단 경계

**제공하는 것**
- 관련 후보를 발견하기 위한 유사도 기반 검색 결과
- 다운로드와 공개 의존 관계의 관측 변화
- 선택한 버전의 실행 환경·설치 조건
- 공식 자료에서 확인된 기능과 근거
- 자료 부족과 확인 불가 상태

**제공하지 않는 것**
- 완전한 대체 관계 보장
- 기술 우열 점수
- 자동 최종 추천
- 실제 사용·설치·실행량
- 교체 이유와 인과관계
- 미래 성공·실패 예측

## 5. MVP와 확장 서비스 구조

### MVP 보고서

1. **생태계 변화 분석**
   - 다운로드 변화
   - 직접·간접 의존 구분
   - 유지·유입·이탈
   - 출처, 조회 기간, 자료 기준일과 한계

2. **기능 비교 분석**
   - 정확한 분석 버전
   - 공통 실행 환경·설치 조건
   - 선택한 버전의 공식 자료에서 실제로 발견한 기능
   - `지원`, `제한적 지원`, `확인 불가`
   - 주장별 근거

### 확장 보고서

3. **GitHub 커뮤니티 현황**
   - npm 패키지와 GitHub 저장소의 연결을 검증한 경우에만 제공
   - 저장소 전체 정보인지 패키지 단위 정보인지 구분
   - 최근 릴리스·커밋·이슈·PR 등 확인 가능한 공개 정보
   - 기본 브랜치의 최신 문서를 과거 패키지 버전의 확정 근거로 사용하지 않음

### MVP와 확장의 기능 경계

| 항목 | MVP | 확장 |
|---|---|---|
| 후보 검색 색인 | 10만 목표 | 20만 이상 확대 가능 |
| 1페이지 사전 집계 | 3만 | 10만 이상 |
| 2페이지 기능 자료 | 요청한 정확한 버전만 분석·캐시 | 반복 요청 버전 캐시 확대 |
| 보고서 페이지 | 1·2페이지 | 1·2페이지 + 3페이지 |
| 버전 고착 | 제외 | 포함 |
| 관측된 교체 흐름 | 제외 | 포함 |
| GitHub 커뮤니티 | 제외 | 포함 |

## 6. 전체 사용자 경험

### MVP 기본 흐름

1. **서비스 이해**  
   사용자는 서비스 소개에서 무엇을 관찰하고 무엇을 단정하지 않는지 확인한다.

2. **패키지 입력**  
   `winston`, `axios`, `zod@4.0.0`처럼 패키지를 입력한다.

3. **존재·버전 확인**  
   Registry에서 실제 존재 여부를 확인한다. 버전이 없으면 분석할 정확한 버전을 확정한다.

4. **후보 추천**  
   저장된 설명·키워드 벡터를 바탕으로 기준을 통과한 가까운 후보를 최대 3개 보여 준다.

5. **비교 대상 확정**  
   사용자가 후보를 선택하고 필요하면 다른 실제 npm 패키지를 직접 추가한다.

6. **분석 조건 확인**  
   비교 대상의 정확한 버전과 1페이지 조회 기간을 확인한다.

7. **1페이지 확인**  
   다운로드 변화와 직접·간접 의존, 유지·유입·이탈을 확인한다.

8. **2페이지 확인**  
   공통 환경 정보와 실제 공식 자료에서 발견된 기능 차이, 근거를 확인한다.

9. **PDF 받기**  
   화면과 같은 기준일·버전·근거가 포함된 PDF를 받는다.

### 예외 상황

| 상황 | 서비스 처리 | 사용자 안내 |
|---|---|---|
| 존재하지 않는 패키지 | 분석 중단 | 입력 이름을 다시 확인 |
| 버전을 찾을 수 없음 | 분석 중단 또는 다른 버전 선택 | 분석 가능한 버전 안내 |
| 후보가 3개 미만 | 있는 후보만 표시 | 억지로 3개를 채우지 않음 |
| 추천 근거 부족 | 후보 추천 축소 또는 없음 | 직접 패키지 추가 가능 |
| 후보의 1페이지 자료 부족 | 가능한 항목만 제공 | 페이지별 자료 품질 표시 |
| 기능 근거 부족 | 기능 판정 유보 | `확인 불가` 표시 |
| 목적이 다른 패키지 선택 | 공통 환경 정보 우선 제공 | 기능 비교 가능한 항목이 부족함을 안내 |
| GitHub 연결 불가 | 3페이지 미제공 | 저장소 연결을 확인할 수 없음 |

## 8. 후보 추천 기준

### 확정 원칙

- 사람이 비교 묶음을 미리 만들지 않는다.
- 실제로 수집된 npm 패키지 안에서 후보를 찾는다.
- 기본 입력은 패키지의 `description`과 확보 가능한 `keywords`다.
- 짧은 텍스트를 숫자 벡터로 바꾸는 임베딩을 사용해 가까운 후보를 찾는다.
- 후보 이름을 생성하거나 후보 순서를 생성형 AI 또는 LLM으로 다시 정하지 않는다.
- 후보 추천 단계에서는 외부 AI API 호출 비용이 발생하지 않도록 한다.
- 후보는 기본 최대 3개이며, 기준 미달이면 더 적게 표시한다.
- 사용자가 최종 비교 대상을 결정한다.

### 후보 카드

후보 카드에는 다음처럼 계산 가능한 근거를 표시한다.

- 패키지명
- 설명 유사도
- 공통 키워드
- 분석 기준 버전
- 최근 배포일
- 자료 상태

설명 유사도는 기술 품질이나 완전한 대체 가능성을 뜻하지 않는다.

### 후보 데이터

- deps.dev BigQuery의 패키지 설명을 대량 후보 데이터의 기본 출처로 활용할 수 있다.
- deps.dev BigQuery의 패키지 설명 스키마에는 `Description`이 확인되지만 후보 키워드 전용 `Keywords` 열은 확인되지 않는다.
- 키워드는 npm Registry 또는 Libraries.io 등 허용된 출처에서 보완할 수 있다.
- 대량 색인 구축은 사용자 요청마다 패키지를 하나씩 외부 API로 조회하는 구조로 만들지 않는다.
- npm 웹 화면과 npmtrends를 크롤링하지 않는다.

> **개발팀 확인 사항** 유사도 기준, 임베딩 모델, 세부 호출 제한과 저장 상한은 개발 시험에서 확정한다. 서비스 기획서는 특정 수치를 제품 약속으로 두지 않는다.

## 9. 보고서 구성

### 1페이지: 생태계 변화 분석

#### 다운로드 변화

- npm의 공식 다운로드 데이터를 사용한다.
- 화면과 PDF에 출처와 조회 기간을 표시한다.
- MVP는 최대 18개월 범위에서 제공한다.
- 자료가 없는 기간을 0으로 채우지 않는다.

#### 의존 관계 변화

- 직접 의존과 간접 의존을 구분한다.
- 유지·유입·이탈을 제공한다.
- deps.dev가 관측한 공개 생태계 결과로 표현한다.
- 전체 npm 사용자 수나 전체 프로젝트 사용량으로 표현하지 않는다.
- 버전 고착과 관측된 교체 흐름은 확장 범위다.

### 2페이지: 기능 비교 분석

비교 항목을 두 층으로 나눈다.

#### 1) 공통 환경·설치 조건

- 정확한 버전과 기준일
- Node.js 등 명시된 실행 조건
- ESM·CommonJS 진입 방식
- TypeScript 타입 제공 위치
- 직접·동료·선택 의존 조건
- 브라우저 등 명시된 실행 환경
- 배포 파일 크기·파일 수와 라이선스 등 확인 가능한 배포 정보

#### 2) 공식 자료에서 실제로 발견한 기능

- 선택한 패키지의 정확한 버전 tarball, README, 타입 선언, 공개 진입점과 검증된 버전 문서를 본다.
- 각 패키지의 공식 자료에서 기능 근거를 먼저 찾는다.
- 서로 다른 표현이 같은 사용자 목적을 뜻할 때만 비교 질문으로 묶는다.
- HTTP 패키지에서 쓰는 기능을 로깅·검증·테스트·빌드·ORM·CLI 패키지에 그대로 적용하지 않는다.
- 비교 가능한 기능 항목이 부족하면 억지로 표를 채우지 않는다.

#### 기능 판정

| 판정 | 의미 |
|---|---|
| 지원 | 명시적인 문서·타입·공개 API 근거가 있음 |
| 제한적 지원 | 특정 환경·설정·추가 패키지 등 조건이 필요함 |
| 확인 불가 | 확보한 공식 자료만으로 지원 여부를 확정할 수 없음 |
| 지원하지 않음 | 공식적인 미지원 근거가 있을 때만 제한적으로 사용 |

검색에서 단어를 찾지 못했다는 이유만으로 `지원하지 않음`으로 판정하지 않는다.

### 3페이지: GitHub 커뮤니티 현황

확장 범위다.

- npm 패키지와 GitHub 저장소 연결을 검증한 경우에만 제공한다.
- 모노레포는 저장소 전체 정보인지 패키지 단위 정보인지 구분한다.
- 최근 공개 활동을 참고 정보로 제공한다.
- GitHub API의 호출 제한과 조회 비용은 개발 시 공식 문서와 실제 사용량을 기준으로 관리한다.
- 기본 브랜치의 최신 문서를 과거 패키지 버전의 확정 근거로 사용하지 않는다.

## 10. 자료와 계산 기준

### 1페이지 자료

| 목적 | 기본 출처 | 사용 원칙 |
|---|---|---|
| 다운로드 변화 | npm Downloads API | 출처·조회 기간 표시 |
| 직접 의존 선언 | deps.dev의 npm 요구 관계 자료 | 공개 선언 기반으로 해석 |
| 직접·간접 의존 관계 | deps.dev 의존 관계 자료 | 두 범위를 화면에서 구분 |
| 시계열 집계 | BigQuery + Spark | 두 EC2가 실제 작업을 나누어 처리 |

### 2페이지 자료

| 순위 | 출처 | 역할 |
|---|---|---|
| 1 | npm Registry 정확한 버전 응답 | 버전·배포 정보·tarball 주소 확인 |
| 2 | 정확한 버전 tarball | 실제 `package.json`, README, 타입 선언, 공개 배포 파일 확인 |
| 3 | 검증된 버전 문서·태그·커밋 | 배포본에서 부족한 버전별 근거 보완 |
| 4 | GitHub 기본 브랜치 | 최신 사용법 참고. 과거 버전 확정 근거로 사용하지 않음 |

`package.json`은 분석 버전, 실행 조건, 진입점, 타입 위치와 의존 조건을 확인하는 데 사용한다.

`dist.tarball`, `dist.integrity`, `dist.fileCount`, `dist.unpackedSize`는 tarball 안 `package.json`이 아니라 npm Registry 응답의 배포 정보로 취급한다.

`exports`는 공개 진입 경로를 찾는 단서이며, 함수·클래스·옵션과 기능 전체를 알려 주는 목록으로 사용하지 않는다.

### 규모 기준

| 처리 범위 | MVP | 확장 |
|---|---:|---:|
| 후보 검색 색인 | 10만 목표 | 20만 이상 확대 가능 |
| 1페이지 사전 집계 | 3만 | 10만 이상 |
| 2페이지 기능 자료 | 요청한 정확한 버전만 | 반복 요청 버전 캐시 확대 |

서로 다른 처리 범위를 하나의 “지원 패키지 수”로 합쳐 표현하지 않는다.

## 11. AI와 근거의 역할

### 후보 추천 단계

생성형 AI 또는 LLM을 사용하지 않는다. 후보는 미리 만든 임베딩과 로컬 벡터 검색, 명시적인 제외 규칙으로 결정한다.

### 기능 비교 단계

사용자가 비교 대상을 확정한 뒤에만 생성형 AI를 사용할 수 있다.

AI의 역할은 다음으로 제한한다.

- 수집된 기능 근거를 비슷한 사용자 목적의 질문으로 정리
- 제공된 근거 안에서 기능 차이를 설명
- 근거 ID가 붙은 비교 문장 생성

AI가 할 수 없는 일은 다음과 같다.

- 새 후보 패키지 이름 생성
- 후보 순위 변경
- 원자료에 없는 기능 생성
- 근거 없는 지원·미지원 판정
- 최종 추천이나 미래 예측

| 직접·간접 의존 혼용 | 의미가 다른 관계가 섞임 | 구분해 표시·집계 |
| 누락을 이탈로 계산 | 잘못된 이탈 발생 | 자료 없음·처리 오류 제외 |
| 최신 문서를 과거 버전 근거로 사용 | 버전별 기능 오판 | 정확한 버전 자료 우선 |
| 검색 실패를 미지원으로 해석 | 부정 판정 오류 | 기본 판정은 확인 불가 |
| 분야에 맞지 않는 기능표 | 잘못된 비교 | 공식 자료에서 실제 발견된 기능만 사용 |
| 원본 자료 장기 보관 확대 | 저장 공간·운영 복잡도 증가 | 최소 메타데이터·집계·근거·캐시만 장기 저장 |
| 분산 처리가 한 서버에 치우침 | 대회 요구와 처리 목적 미달 | 두 EC2 작업 분담과 처리량 기록 |
| 범위 확대 | 4주 MVP 미완성 | 1·2페이지 MVP를 먼저 완료 |

### 용어

| 용어 | 뜻 |
|---|---|
| 후보 추천 | 입력 패키지와 설명·키워드 의미가 가까운 실제 npm 패키지를 찾는 단계 |
| 추천 후보 | 서비스가 최대 3개까지 보여 주는 관련 패키지. 완전한 대체 관계를 보장하지 않음 |
| 비교 대상 | 사용자가 최종 선택하거나 직접 추가한 패키지 집합 |
| 설명 유사도 | 임베딩 벡터 사이의 가까움을 나타내는 검색 근거. 품질 점수가 아님 |
| 분석 버전 | 보고서 전체에서 고정되는 정확한 `패키지@버전` |
| 직접 의존 | 패키지가 직접 선언한 의존 관계 |
| 간접 의존 | 직접 의존을 통해 이어진 의존 관계 |
| 유지 | 이전과 다음 관측 모두에 관계가 있는 상태 |
| 유입 | 이전에는 없고 다음 관측에 새로 나타난 관계 |
| 이탈 | 이전에는 있고 다음 관측에서 사라진 관계 |
| 기능 근거 | README·타입 선언·공개 진입점·검증된 버전 문서 등 기능 주장을 뒷받침하는 원자료 |
| 확인 불가 | 확보한 공식 자료만으로 지원 여부를 확정할 수 없는 상태 |
| 생태계 변화 분석 | MVP 보고서 1페이지 |
| 기능 비교 분석 | MVP 보고서 2페이지 |
| GitHub 커뮤니티 현황 | 확장 보고서 3페이지 |

> **최종 한 문장** OSS Shift는 패키지를 자동으로 골라 주는 서비스가 아니라, 관련 후보를 발견하고 사용자가 선택한 정확한 버전의 생태계 변화와 기능 근거를 함께 비교하도록 돕는 서비스다.
