       2. 해결하려는 문제
           "3분 후 도착"이 실제로는 1분일 때도, 6분일 때도 있으며 사용자는 그 편차 폭을 알 수
           없다.

           오차의 원인이 데이터 전달 지연인지 실제 운행 편차인지 구분되지 않는다.

           모든 앱이 동일한 원천(TOPIS) 예측값을 그대로 전달할 뿐, 그 값의 과거 적중률을 추적
           하지 않는다.

           역과 시간대에 따라 오차 특성이 크게 다른데도 단일한 형태로 표시된다.

           사용자는 결과적으로 "대충 더 여유 두고 나가기"라는 개인적 보정에 의존한다.

       7. 예측 로직
       7.1 1단계: 예측 스냅샷 누적
       동일 열차에 대해 리드타임이 다른 예측 스냅샷이 반복 수신된다. Flink는 열차번호를 키로
       이 스냅샷들을 상태에 보관한다.

       7.2 2단계: 실제 도착 매칭
       도착 상태 코드가 도착으로 전이되는 시점을 실제 도착으로 확정하고, 보관 중이던 모든 스
       냅샷과 짝지어 잔차를 계산한다. 한 번의 도착이 여러 개의 학습 샘플을 생성하며, 리드타임
       자체가 중요한 피처가 된다. 10분 전 예측의 오차와 1분 전 예측의 오차는 다른 문제다.

       매칭 완료 후 열차 상태는 즉시 정리하고, 누락에 대비해 TTL을 설정한다.

       7.3 3단계: 조건부 분포 추정
       역·방향·시간대를 키로 잔차 분포를 유지한다. 원본 잔차를 모두 보관하면 상태가 무한히 증
       가하므로 t-digest로 압축하고 관측 건수를 함께 저장한다.

       7.4 4단계: 계층적 사전분포
       관측이 부족한 조합은 상위 레벨 분포를 사전분포로 사용하고, 관측이 쌓이면 개별 분포로
       이행한다.


         추정 분포 = w(n) × 개별 분포 + (1 − w(n)) × 상위 분포
         w(n) = n / (n + k)




       상위 레벨은 노선×시간대, 그다음 노선 전체 순으로 폴백한다. 가짜 데이터로 빈 칸을 채우
       지 않으며, 모든 값은 실제 관측의 집계다. 사용자에게는 "관측 23건, 노선 평균 기반 추
       정"과 같이 근거를 그대로 노출한다.

       처리 순서
        1. 수집기가 일괄 API를 폴링해 원본과 수신 시각을 Kafka에 발행한다.
        2. Flink가 열차번호 키로 예측 스냅샷을 상태에 보관한다.
        3. 도착 상태 전이를 감지하면 보관 스냅샷 전체와 매칭해 잔차를 산출한다.

        4. 잔차를 파이프라인 지연분과 운행 편차분으로 분해해 분포에 반영한다.
        5. 스코어링 시점의 피처 벡터를 그대로 Parquet에 적재한다.
        6. Spark가 원본 API 응답이 아닌 이 잔차 로그로 학습한다.
        7. 모델 버전이 Kafka로 발행되고 Flink가 broadcast state로 무중단 교체한다.

       분담 원칙
           Flink 담당은 반드시 2명 이상 관여한다. 스트림 상태 디버깅은 배치 대비 3배 이상 느리
           고, 단일 담당자가 막히면 전체 일정이 정지한다. 6인 구성에서 Flink에 2명을 배치하는
           이유다.

           3주차 말까지 세로 흐름을 먼저 완성한다. 수집 → 매칭 → 학습 → 스코어링 → 화면의
           한 줄이 얇게라도 관통해야 한다. 각 영역을 병렬로 깊게 파면 통합 시점에 무너진다.

           4주차는 신규 기능을 넣지 않는다. 장애 실험과 측정, 문서화에만 사용한다. 이 주차가
           평가 대상 산출물을 만든다.

           인프라 담당이 1주차 병목이다. 1주차에는 다른 인원이 스키마 설계, 화면 와이어프레임,
           학습 코드 골격 등 인프라 비의존 작업을 선행한다.

           담당자별로 작은 리플레이 파일(1천 행) 을 공유해 빠른 반복이 가능하게 한다. 전체 데
           이터로 매번 검증하면 개발 속도가 급락한다.

       20. 최종 데모 시나리오
        1. 수집기가 며칠간 무중단으로 축적한 데이터 규모를 제시한다.
        2. 특정 역의 예측 스냅샷이 실제 도착으로 수렴하는 과정을 시각화한다.
        3. 같은 역·다른 시간대의 잔차 분포가 뚜렷이 다름을 보여준다.
        4. 관측 건수가 적은 역과 많은 역의 신뢰도 표시 차이를 비교한다.
        5. 오차를 파이프라인 지연분과 운행 편차분으로 분해한 리포트를 제시한다.
        6. AOE 랭킹으로 예측이 가장 안 맞는 역을 공개한다.
        7. 캘리브레이션 다이어그램으로 확률의 정직성을 입증한다.
        8. 20배속 리플레이 중 TaskManager를 강제 종료하고, 복구 후 중복·유실이 0임을 보여
           준다.

        9. 모델을 무중단 교체하고 확률 출력이 바뀌는 것을 실시간으로 확인한다.

          마나 믿어야 하는지를 실측 누적으로 알려주는 서비스다.
