    이 프로젝트는 무엇을 하는가?
    버스 앱의 “5 분 후 도착”이라는 숫자를 다시 예측하는 프로젝트가 아니다. 그 5 분이라는 예측이 실제로 얼마나 자주 맞았고, 얼
    마나 흔들리는지를 과거 실측으로 누적해 “지금 이 ETA 를 어느 정도 믿어도 되는가”를 확률과 오차 범위로 보여주는 프로젝트다.


1.    API 가 제공하는 버스 도착예정시간(ETA)을 15 초 간격으로 반복 저장한다.
2.    같은 차량이 실제 정류장에 도착하는 순간을 위치 API 에서 잡는다.
3.    예측시각과 실제 도착을 연결해 오차(Residual = Actual - Predicted)를 만든다.
4.    오차를 ETA 거리, 정류장, 시간대, 첫 번째/두 번째 도착예정버스 등의 조건으로 누적한다.
5.    사용자에게 “10 분 후”뿐 아니라 “이 예측은 ±1 분 안에 들어올 확률이 약 몇 %”처럼 신뢰도를 제공한다.

    가장 중요한 결론
    이번 1 시간 데이터에서는 ETA 의 중앙 오차가 모든 구간에서 대체로 0 초 부근이었지만, ETA 가 멀어질수록 오차 분포의 폭이

1. 프로젝트 배경과 검증 목표
Handoff 문서가 정의한 원안의 핵심은 “더 정확한 ETA 를 새로 만드는 것”이 아니라 기존 ETA 의 오차를 누적해 신뢰도와 불확실성
을 계량하는 것이다. 버스 파트에서는 API 목록을 많이 모으는 것이 아니라 다음 세 가지를 실제 response 로 증명하는 것을 성공조
건으로 두었다.
     특정 노선·정류장에 대한 예측 ETA 를 반복적으로 얻을 수 있는가?
     동일 버스를 시간에 따라 식별하고 추적할 수 있는가?
     특정 버스가 정류장에 실제 도착한 시각 또는 도착 구간을 잡을 수 있는가?
    성공조건
    한 차량에 대해 여러 prediction snapshot 과 하나의 actual arrival 을 연결하고, 각 lead time 별 residual 을 생성할 수 있어야
    한다.


공통 엔진은 교통수단이 달라져도 다음 구조를 유지한다: Prediction → Actual → Residual → Reliability. 버스·지하철·고속열차의
시간 스케일이나 UI 임계값은 달라질 수 있지만 데이터 엔진의 핵심 상태 전이와 오차 누적 원리는 같다.

서울 도착 API 의 핵심 장점은 한 번의 노선 조회가 그 노선의 전체 경유 정류소 도착예정정보를 반환한다는 점이다. 또한
Prediction 응답에 차량 ID(vehId1/vehId2)와 원천 생성시각(mkTm)이 함께 들어온다. 서울 위치 API 는 같은 vehId 를 반환하므
로 차량 단위 direct JOIN 이 가능하다.
TAGO 도착 API 는 정류소(nodeId) 기준으로 현재 도착예정정보를 반환하며 ETA(arrtime)는 충분히 얻을 수 있지만, 도착 응답에
차량 ID 와 source timestamp 가 없다. 따라서 TAGO 위치 API 의 vehicleno/nodeord 와 결합할 때는 직접 JOIN 이 아니라
heuristic 매칭이 필요하다.

 Residual 의 부호
 Residual = Actual - Predicted. 음수이면 실제 버스가 예측시각보다 일찍 도착했고, 양수이면 예측보다 늦게 도착했다는 뜻이
 다. Actual 은 21 초 interval 이므로 midpoint 는 대표값일 뿐이며, 분석에서는 interval 의 lower/upper 도 함께 보존했다.

15 초마다 요청했지만 원천 timestamp 가 그대로인 응답이 다시 제공되는 경우가 있었다. 서울 Arrival 의 unique source

횟수”를 독립 Prediction 수로 세면 표본 수가 부풀려진다. 원본은 보존하되 분석용 Silver layer 에서는 source-generated
timestamp 와 핵심 필드를 기준으로 dedupe 했다.

1. 서울을 Main bus source 로 확정한다. vehId direct JOIN, mkTm/dataTm, stopFlag 때문에 Prediction→Actual 의 증거 품
  질이 가장 높다.
2. 현재 753 번 collector 를 3~7 일 이상, 출근·낮·퇴근·주말 window 로 확장해 lead-time Reliability 를 안정화한다.
3. 2~5 개의 성격이 다른 노선으로 확장해 51~60 구간 anomaly 와 rank2 효과가 재현되는지 검증한다.
4. 운영계정 traffic 증액을 즉시 신청한다. 전체 노선 실시간 PoC 의 feasibility 는 API quota 에 직접 좌우된다.
5. Collector 출력 형식을 Bronze/Silver event schema 로 고정하고 Kafka replay 가 가능한 JSON/Avro/Protobuf schema 를
  정의한다.
6. Flink 에서는 Location 을 keyBy(route_id, vehicle_id), Prediction state 를 논리적으로 (route_id, vehicle_id,
  target_stop_id) 단위로 관리하고 TTL 을 둔다.
7. TAGO 는 전국 확장 가능성 비교 소스로 유지하되, residual 에는 join_method / join_quality / actual_method 를 반드시 기
  록한다.
 보고서 전체 결론
 “예측 ETA 자체를 새로 만드는 것”보다 “제공된 ETA 가 현재 얼마나 믿을 만한지 계량한다”는 서비스 방향은 실제 버스 데이터에
 서 end-to-end 로 구현 가능했다. 서울 753 번 1 시간 PoC 에서는 ETA 가 멀어질수록 오차가 뚜렷하게 커졌고, 차량 ID 기반
 Prediction↔Location JOIN 과 stopFlag 기반 Actual interval 을 통해 Reliability 계산의 기반을 확보했다. 다음 병목은 알고리
 즘보다 데이터 기간·노선 다양성·API traffic 이다.
