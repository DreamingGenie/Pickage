## 한눈에 보는 결론

> **서비스 한 문장 OSS Shift는 회원이 검토 중인 npm 패키지를 같은 역할의 후보와 비교하도록 돕고, 공개 의존 관계 이력에서 현재 규모·신규 선택·유지·이탈을 계산해 보고서로 제공하며, 확장 단계에서는 npm 생태계의 주요 선택 변화를 공개 트렌드 소식으로 보여 준다.**

### 왜 만드는가

기존 서비스는 검색, 내려받기 수, 별표, 보안, 유지 상태를 잘 보여 준다. 그러나 최근 프로젝트가 유사 패키지 가운데 무엇을 새로 선택하고, 계속 유지하고, 제거하는지를 같은 기준으로 비교하기는 어렵다. OSS Shift는 이 빈칸을 의존 관계의 버전 이력으로 보완한다.

### 누가 쓰는가

새 서비스를 만들거나 기존 패키지를 교체하면서 자바스크립트 개발 도구 선택을 책임지는 기술 책임자와 경력 개발자를 주 사용자로 본다. 이들은 단순 인기보다 팀에 설명할 수 있는 변화 흐름과 근거가 필요하다. 확장 단계의 공개 트렌드 페이지는 npm 생태계의 변화를 빠르게 살펴보고 분석 서비스로 들어오는 일반 개발자를 두 번째 사용자로 본다.

### 무엇이 4주 뒤 완성되어야 하는가

- 패키지명 입력부터 비교 묶음 확인, 기간 선택, 그래프, 해설, 보고서, 근거 확인까지 한 흐름으로 동작한다.

- 비회원은 서비스 설명과 회원가입 진입만 볼 수 있고, 실제 패키지 분석은 로그인한 회원에게만 제공한다.

- 신규 선택·유지·이탈은 정해진 규칙으로 계산하며 인공지능이 숫자를 만들거나 바꾸지 않는다.

- 대용량 계산은 일을 나누고 배분하며 실패 작업을 다시 실행하고, 같은 입력에서 같은 결과를 만든다.

- 4주 MVP에서는 운영자가 미리 정의한 3개 비교 묶음을 사용하며, 그 밖의 패키지는 사용자가 후보를 직접 정하면 같은 분석이 동작한다.

- 인공지능은 MVP 분석 엔진과 사용자 흐름이 안정된 뒤 비교 묶음 생성까지 확대하며, 그전에는 계산 결과 해설과 보고서 문장 작성만 맡는다.

## 문제와 기회

### 개발자가 실제로 겪는 상황

winston 도입을 검토하는 개발자는 npm, npm Trends, Snyk, Socket 등을 오가며 검색 결과, 내려받기 수, 별표, 보안과 유지 상태를 확인한다. **하지만 최근 다른 프로젝트들이 winston과 유사한 패키지 중 무엇을 새로 선택하고, 계속 쓰고, 빼는지는 한곳에서 같은 기준으로 보기 어렵다.**

### 기존 서비스가 잘하는 것과 남아 있는 빈칸

| **서비스**      | **현재 주로 보여 주는 것**                          | **OSS Shift가 보완하는 판단 근거**             |
|-----------------|-----------------------------------------------------|------------------------------------------------|
| **npm**         | 검색어 일치, 내려받기 수, 의존 수, 최근 공개일 정렬 | 유사 패키지의 신규 선택·유지·이탈 흐름         |
| **npm Trends**  | 내려받기 변화, 묶음 크기, GitHub 별표 비교          | 의존을 선언한 패키지의 선택 상태 변화          |
| **Snyk·Socket** | 보안, 유지 상태, 인기도, 의존성, 관리자, 버전, 경고 | 같은 역할의 패키지끼리 선택 변화를 보는 시계열 |

확인 위치: npm 공식 ‘Searching for and choosing packages to download’, npm Trends 소개 화면, Snyk의 winston 정보 화면, Socket ‘Package Search’ 안내(2026-08-30 확인). ‘기능이 없다’고 단정하기보다 공식 소개에서 해당 비교 기능이 명시적으로 확인되지 않았다는 뜻이다.

### 현직자 조사에서 확인된 어려움

> **조사 결과 11개 기업 개발자 16명 인터뷰와 115명 설문에서는 외부 개발 도구 선택이 어렵고, 잘못 고르면 비용·시간·개발 노력이 커지며, 실제 선택이 임시방편적으로 이뤄지는 경우가 확인됐다. 다른 연구는 세계 실무자 24명 인터뷰에서 선택 과정을 가로막는 7가지 장벽을 찾았다.**

조사 출처 1: Enrique Larios-Vargas 외 4명, ‘Selecting third-party libraries: The practitioners' perspective’, ACM ESEC/FSE 2020, 245-256쪽, DOI 10.1145/3368089.3409711.

조사 출처 2: Minaoar H. Tanzil·Gias Uddin·Ann Barcomb, ‘How do people decide?: A Model for Software Library Selection’, IEEE/ACM CHASE 2024, 리스본, 1-12쪽, DOI 10.1145/3641822.3641865.

### 사용자가 답을 얻어야 하는 질문

- 같은 역할의 후보 가운데 최근 새로 선택되는 비중은 어떻게 변하고 있는가?

- 기존에 선언한 패키지들이 다음 관측 상태에서도 관계를 유지하는가?

- 이탈이 늘고 있다면 그 판단을 뒷받침하는 관측 대상은 몇 개인가?

- 누적 규모와 최근 흐름이 다를 때 팀은 무엇을 추가로 검토해야 하는가?

- 새 주버전이 공개된 뒤 기존 주버전에 남은 선언은 얼마나 되는가?

- 특정 패키지를 제거한 공개 패키지 작성자들은 무엇을 함께 추가했는가?

- 자료에서 가장 이른 정식 배포가 해당 기간에 있는 패키지들은 같은 역할의 무엇을 처음 선택했으며, 전체 생태계에서 최근 선택이 빠르게 변한 대상은 무엇인가?

### 대표 사용 사례

기술 책임자는 신규 서비스의 기록용 패키지로 winston을 검토한다. 서비스에 **winston**을 입력하면 MVP에서 운영자가 미리 정의한 기록 묶음에 따라 pino, bunyan, log4js가 제시된다. 사용자는 후보를 고친 뒤 기간을 정하고, 각 패키지의 현재 규모와 신규 선택·유지·이탈 흐름, 근거 수, 해설을 함께 확인한다. 결과는 팀 검토용 보고서 형태로 정리된다.

> **중요한 입력 원칙 사용자는 ‘기록 남기기’ 같은 기능명을 입력하지 않는다. 실제 도입을 검토 중인 패키지명을 입력한다. MVP에서는 운영자 정의 묶음에서 후보를 제안하고, 후속 단계에서는 AI가 실제 패키지 정보에 근거해 새로운 후보를 제안한다. 두 방식 모두 사용자가 최종 묶음을 확정한다.**

## 서비스 정의와 제공 가치

### 서비스가 하는 일

- 공개 랜딩에서 서비스의 관측 범위와 결과 형태를 설명하고 회원 분석으로 연결한다.

- 입력한 패키지가 분석 자료에 존재하는지 확인한다.

- MVP에서는 운영자가 미리 정의한 비교 묶음에서 후보를 제안하고 사용자가 수정할 수 있게 한다.

- MVP가 안정된 뒤에는 AI가 패키지 설명과 문서를 읽고 실제 검색된 후보 가운데 같은 역할의 패키지를 제안한다.

- 정해진 기간 동안 현재 규모, 신규 선택, 유지, 이탈을 같은 기준으로 계산한다.

- 패키지별 흐름을 시계열 그래프와 비교표로 보여 준다.

- 계산 결과 안에서 핵심 변화와 주의사항을 쉬운 문장으로 설명한다.

- 선택한 조건, 그래프, 해설, 근거를 인쇄 가능한 보고서로 정리한다.

- 확장 단계에서는 package.json에서 분석 대상을 고르게 하고, 보고서에 버전 고착과 마이그레이션 현황을 추가한다.

- 확장 단계에서는 첫 배포 선택·최근 선택 증가·감소·커뮤니티 논의를 근거가 붙은 공개 패키지 트렌드로 제공한다.

| **누적 인기와 최근 변화가 섞임** | 현재 규모와 신규 선택 흐름을 분리           | 도입 시점의 변화를 별도 검토 |
| **비교 기준이 제각각**           | 같은 자료·기간·계산 규칙 적용               | 후보 간 비교 가능성 확보     |
| **그래프 해석을 다시 써야 함**   | 계산 결과 기반 해설과 보고서 생성           | 팀 공유에 필요한 설명 준비   |
| **근거가 보이지 않음**           | 기준일·대상 수·자료 부족 표시               | 과도한 확신 방지             |
| **주버전 전환과 교체 방향이 안 보임** | 확장 보고서에서 버전 조건 분포와 마이그레이션 쌍 확인 | 추가 검토가 필요한 전환 지점 발견 |
| **생태계 변화를 여러 곳에서 찾음** | 공개 트렌드에서 계산 변화와 공식 저장소 논의를 근거와 함께 확인 | 탐색 시작점과 분석 대상 발견 |

### 서비스의 판단 경계

> **제공하는 것 후보 패키지의 의존 관계 선언 규모와 시간 변화, 비교 묶음 안에서의 상대 흐름, 계산에 사용된 근거 수와 해석 주의사항**
>
> **제공하지 않는 것 최종 추천, 기술 성능 점수, 실제 실행량, 보안 보증, 유지보수 품질 보증, 마이그레이션 이유, 미래 생존 예측**

## MVP와 확장 서비스 구조

서비스는 회원이 사용하는 패키지 분석 영역과, 확장 단계에서 비회원에게도 공개할 패키지 트렌드 영역으로 나눈다. 공개 범위가 넓어져도 회원 분석의 계산 규칙과 보고서 근거는 동일하게 유지한다.

### 회원과 비회원의 접근 범위

| **서비스 영역** | **MVP 비회원** | **MVP 회원** | **확장 비회원** | **확장 회원** |
|---|---|---|---|---|
| **첫 랜딩 화면** | 조회·회원가입 진입 | 조회 | 조회·회원가입 진입 | 조회 |
| **패키지 분석 시작** | 로그인 안내 | 사용 | 로그인 안내 | 패키지명·package.json 입력 사용 |
| **비교 묶음 확인** | 접근 불가 | 운영자 정의 묶음·직접 입력 | 접근 불가 | AI 제안 묶음·직접 수정 |
| **분석 보고서** | 접근 불가 | 핵심 시계열·해설·근거 | 접근 불가 | MVP 내용과 버전 고착·마이그레이션 현황 |
| **패키지 트렌드** | 제공하지 않음 | 제공하지 않음 | 공개 조회 | 공개 조회와 분석 화면 이동 |

> **접근 원칙 랜딩과 확장 트렌드는 공개한다. 사용자가 입력한 패키지, 비교 묶음, 분석 조건과 개인 보고서는 회원 영역에서만 처리하고 다른 사용자에게 공개하지 않는다.**

### MVP와 확장의 기능 경계

| **단계** | **분석 입력** | **비교 묶음** | **분석 보고서** | **공개 콘텐츠** |
|---|---|---|---|---|
| **MVP** | 실제 npm 패키지명 1개 | 운영자가 미리 정의한 3개 묶음, 또는 사용자 직접 입력 | 현재 규모·신규 선택·유지·이탈·근거 수·간단 해설 | 서비스 설명 랜딩 |
| **확장** | 패키지명 또는 package.json에서 선택한 패키지 | AI가 실제 후보에서 제안하고 사용자가 확정 | MVP 내용 + 버전 고착 + 마이그레이션 현황 | 패키지 트렌드와 근거가 붙은 이슈 리포트 |

package.json 입력은 파일 안의 모든 패키지를 한꺼번에 자동 분석한다는 뜻이 아니다. 먼저 일반 의존 패키지 목록을 읽어 보여 주고, 사용자가 분석할 대상을 선택하면 기존의 비교 묶음·기간·보고서 흐름으로 연결한다. 대량 일괄 분석은 별도 범위로 둔다.

## 전체 사용자 경험

서비스의 핵심은 ‘검색 결과 목록’이 아니라, 실제 패키지 입력에서 비교 근거와 보고서까지 이어지는 하나의 완결된 흐름이다.

### MVP 회원 분석 흐름

1.  **공개 랜딩 확인** 서비스가 제공하는 비교 방식과 관측 범위를 이해하고 회원가입 또는 로그인을 선택한다.

2.  **패키지 입력** 로그인한 사용자가 도입을 검토 중인 실제 패키지명을 입력한다. 예: winston.

3.  **존재 확인** 자료에 존재하는 패키지인지, 분석 가능한 이력이 있는지 확인한다.

4.  **비교 묶음 확인** 운영자가 미리 정의한 묶음에 따라 pino·bunyan·log4js 등이 제안된다.

5.  **후보·기간 확정** 사용자가 후보를 추가·제외하고 모든 후보의 자료가 겹치는 범위에서 기간을 정한다. 기본은 최근 8개 완결 분기이며, 최근 1년·2년·3년과 직접 선택을 제공한다.

6.  **시계열 비교** 현재 규모와 기간별 신규 선택·유지·이탈을 그래프에서 비교한다.

7.  **결과 해설** 계산값과 근거 안에서 작성된 짧은 해설과 자료 부족 경고를 본다.

8.  **보고서 확인** 그래프·해설·근거·주의사항을 한 화면과 인쇄용 결과로 확인한다.

### 확장 회원 분석 흐름

1.  패키지명을 직접 입력하거나 package.json 파일·붙여넣기를 브라우저에서 읽어 일반 의존 패키지 목록을 확인한다. 서버에는 사용자가 선택한 공개 npm 패키지명만 전달한다.

2.  package.json을 사용한 경우 목록에서 분석할 패키지를 선택한다.

3.  AI가 실제 검색 후보를 같은 역할의 직접 대안과 제외 대상으로 나눠 제안한다.

4.  사용자가 비교 묶음과 기간을 확정한다.

5.  MVP 시계열과 함께 버전 고착·마이그레이션 현황을 보고서에서 확인한다.

### 확장 공개 트렌드 흐름

1.  비회원도 패키지 트렌드 목록을 연다.

2.  ‘지금 시작하는 패키지가 처음 고른 것’, 최근 선택 증가·감소, 커뮤니티 논의 중 원하는 소식을 선택한다.

3.  기준 기간·대상 수·계산 방법·원문 출처가 붙은 이슈 리포트를 읽는다.

4.  더 깊은 비교가 필요하면 회원가입 후 해당 패키지 분석으로 이동한다.

## 자료와 계산 기준

> **관측 계약 핵심 시계열은 npm 정식 배포 버전 중 공개 시각이 있고, package.json의 dependencies에 선언된 일반 의존 관계만 분석한다. 개발·동료·선택·묶음 의존 관계는 핵심 지표에 포함하지 않는다. 다만 확장 마이그레이션에서는 일반 의존에서 peer·optional로 옮겨간 관계를 잘못된 제거로 세지 않기 위해 두 종류를 판정용으로만 읽는다.**

### AI 확장에 사용할 패키지 정보

deps.dev 의존 관계 자료만으로는 패키지가 어떤 기능을 제공하는지 충분히 판단할 수 없다. 후속 AI 비교 묶음 생성에는 별도 패키지 정보 원천에서 다음 자료를 가져와야 한다.

- npm 공개 레지스트리에서 확인한 실제 패키지명·공식 설명·폐기 표시

- 등록된 주요 검색어와 저장소 설명

- npm이 연결한 공식 저장소의 소개·주제·README 요약

- 서버가 실제 존재를 확인한 후보 목록

이 자료는 비교 후보의 의미를 판단하는 데만 사용한다. 신규 선택·유지·이탈 계산에는 섞지 않는다. 원문이 지나치게 길거나 악의적인 지시를 포함할 수 있으므로 필요한 설명만 추출하고, AI가 문서 안의 명령을 실행하지 못하도록 단순 자료로 전달한다.

전체 npm 패키지를 한번에 자동 군집화하지 않는다. 입력 패키지의 역할 단어로 npm 검색에서 실제 후보를 넓게 찾고, 기존에 정리한 설명 카드와 숫자 벡터 검색으로 후보를 보완한 뒤, AI가 입력 패키지와 후보를 한 쌍씩 비교해 직접 대안인지 재판정한다. 전체 생태계 군집화는 운영자의 역할 탐색에만 보조적으로 사용한다.

### 추가 기능에 필요한 자료

| **기능** | **필요 자료** | **현재 판단** |
|---|---|---|
| **package.json 입력** | 사용자가 선택하거나 붙여 넣은 JSON의 dependencies | 브라우저에서 해석하고 초기 파일 제한은 1MB로 둔다. 서버에는 사용자가 선택한 공개 npm 이름만 보내며 원문은 저장하지 않는다. |
| **버전 고착** | 의존 패키지명과 버전 조건 원문, 대상 패키지의 주버전 공개 시점 | 기존 요구 정보에 버전 조건이 있어 계산 가능성이 높음. 전체 조건 해석률 측정 필요 |
| **마이그레이션 현황** | 배포 순서·시각·일반 의존 추가·제거, peer·optional 이동 여부, 배포 주체 | 260개 패키지 표본에서 전체 절차 실행과 실제 이름 변경 쌍 탐지 확인. 전체 규모 신호 밀도 미확인 |

| **최근 선택 증가·감소** | 신규 선택·이탈의 최근 기간과 기준 기간, 근거 수 | 기존 지표에서 파생 가능. 순위 기준과 최소 근거 수 검증 필요 |
| **커뮤니티 논의** | npm이 연결한 공식 GitHub 저장소의 Issues·Discussions, 생성·갱신 시각, 글·댓글·반응·참여자 수, 원문 주소 | 수집 출처는 공식 저장소로 고정. API 이용 조건·호출 제한·수집 비용과 저장소 연결 정확도는 공개 전 검증 필요 |

package.json은 분석할 패키지를 고르는 입력 수단으로만 사용한다. 사용자의 프로젝트 이름·스크립트·사설 패키지 주소·기타 설정은 분석에 필요하지 않으며, 필요한 일반 의존 항목만 추출한 뒤 원문은 저장하지 않는 것을 기본으로 한다. 사설 주소·공개 npm에서 확인되지 않는 이름은 분석 후보에서 분리하고 AI나 공개 화면으로 보내지 않는다. 보관이 필요해지는 경우에는 보관 목적·항목·기간을 별도 요구사항으로 확정하고 사용자에게 먼저 알린다.

커뮤니티 수집은 전체 npm 저장소를 처음부터 모두 다루지 않는다. 1차는 운영자 승인 비교 묶음에 속한 패키지의 공식 저장소, 2차는 선택 변화 규칙에서 후보로 올라온 패키지의 공식 저장소다. 100~500개 저장소로 호출량·실패·비용을 측정한 뒤 수집 범위를 늘린다. 하나의 저장소가 여러 npm 패키지에 연결되면 특정 패키지가 아닌 ‘저장소 전체 논의’로 표시한다.

### ‘지금 시작하는 패키지가 고르는 것’ 계산

- 공개 npm 패키지마다 자료에서 확인되는 가장 이른 정식 배포 한 건을 고르고, 그 배포 시각이 대상 기간에 든 패키지를 모은다.

- 각 패키지의 가장 이른 관측 가능한 정식 배포에서 일반 의존 패키지를 읽는다.

- 비교 묶음 하나마다 공개 npm 패키지 하나가 최대 한 표를 갖는다. 같은 첫 배포에 비교 후보가 여러 개 있으면 한 표를 후보 수로 똑같이 나눠 비중의 합이 100%를 넘지 않게 한다.

- 첫 배포에 해당 비교 묶음의 후보가 하나도 없는 패키지는 묶음별 비중의 분모에서 제외한다. 전체 첫 배포 수와 후보를 하나 이상 선언한 수를 나란히 보여 주어 관측 범위를 숨기지 않는다.

- 최근 기간과 과거 같은 길이의 기준 기간을 비교하고, 후보별 선택 수·비중·근거 패키지 수를 함께 표시한다.

> **표현 경계 화면 이름은 이해하기 쉽게 ‘지금 시작하는 패키지가 고르는 것’으로 쓸 수 있지만, 실제 관측 대상은 자료에서 확인되는 가장 이른 정식 배포다. 회사 내부 프로젝트나 비공개 서비스의 선택을 대표한다고 말하지 않는다.**

### 버전 고착 계산

- 대상 패키지를 일반 의존으로 선언한 서로 다른 패키지의 최신 관측 가능한 버전 조건을 사용한다.

- `^5.0.0`, `~5.1.0`, 정확한 버전처럼 해석 가능한 조건은 허용하는 주버전으로 분류한다.

- 여러 주버전을 동시에 허용하거나 별칭·주소·해석 불가 표현을 사용한 조건은 억지로 한 주버전에 넣지 않고 별도 상태로 표시한다.

- 새 주버전 공개 후 경과 기간, 이전 주버전 비중, 새 주버전 비중, 해석 불가 비중과 근거 패키지 수를 함께 보여 준다.

- ‘버전 고착’은 느린 전환을 관찰하는 표현이며, 업데이트하지 않은 이유·위험·기술 수준을 뜻하지 않는다.

### 마이그레이션 현황 계산

마이그레이션은 패키지 X를 제거한 같은 배포에서 무엇이 추가됐는지를 찾는 확장 분석이다. 계산 방법은 260개 패키지 표본에서 실행해 실제 이름 변경 쌍을 찾았지만, 전체 npm 규모의 신호 밀도는 아직 확인하지 못했다.

1.  패키지별 배포를 주버전 계열로 나누고 공개 시각 순으로 연결한다. 0.x는 부버전까지 같은 계열의 기준으로 사용한다.

2.  연속 배포 사이의 일반 의존 추가·제거를 구한다.

3.  일반 의존에서 peer·optional 의존으로 옮겨간 경우는 제거가 아니라 종류 이동으로 분리한다.

4.  제거 하나와 같은 배포의 추가 후보를 연결한다. 추가가 여러 개면 제거의 한 표를 추가 개수로 나눠 우연한 대규모 정리의 영향을 줄인다.

5.  ‘X를 제거할 때 Y를 추가한 비율’을 ‘전체 변경에서 Y를 추가한 비율’과 비교한 배수로 우연한 동시 변경을 줄인다.

6.  같은 조직·저장소가 짧은 기간에 여러 패키지를 함께 바꾼 경우 한 배포 주체의 한 표로 축약한다.

7.  최소 제거 사건·표·배수 기준을 통과한 쌍만 보여 주고, 대체 후보가 없는 제거는 별도로 표시한다.

> **마이그레이션 표현 경계 같은 배포에서 제거와 추가가 함께 일어난 관계이지, 코드가 실제로 완전히 옮겨갔거나 Y 때문에 X를 제거했다는 인과 증거가 아니다. 제거와 추가가 다른 배포에 나뉜 경우는 기본 결과에서 놓칠 수 있으며, 넓은 시간 창 결과는 별도 등급으로 분리한다.**

### 공개 트렌드와 이슈 리포트 기준

공개 트렌드는 다음 네 사건을 서로 다른 규칙으로 탐지한다.

| **사건** | **기본 비교 기간** | **보여 주는 변화** |
|---|---|---|
| **첫 배포 선택** | 최근 180일 대 이전 180일 | 처음 공개된 npm 패키지의 같은 역할 후보 선택 비중 |
| **새 선택 증가** | 최근 90일 대 이전 90일 | 비교 묶음 안의 신규 선택 비중 증가 |
| **새 선택 감소·이탈 증가** | 최근 90일 대 이전 90일 | 새로 선택되는 비중 감소와 기존 관계의 이탈률 증가를 분리 |
| **커뮤니티 논의 증가** | 최근 30일 대 이전 90일의 30일 환산값 | 공식 저장소의 새 이슈·토론·참여자 증가 |

30·90·180일은 분기 집계를 나눠 대신하지 않고 자료 기준일에서 날짜 경계를 직접 정해 계산한다. 새 선택 감소는 묶음 안 신규 선택 비중을, 이탈 증가는 직전 기간에 해당 패키지를 선택한 관측 가능 주체를 분모로 사용하므로 하나의 그래프나 점수로 합치지 않는다.

- 공개 순위의 계산 대상은 자료 기준일, 정식 배포, 최소 관측 기간, 최소 근거 수를 통과한 공개 npm 패키지로 제한한다. 역할이 다른 패키지의 비중을 직접 비교하지 않으며, 역할별 비교에는 운영자 승인 묶음 또는 검증을 통과한 AI 묶음만 사용한다.

- 최근 선택 증가·감소는 단순 증감률만으로 순위를 만들지 않는다. 최근 기간과 기준 기간의 원값, 근거 수, 비교 묶음 내 비중을 함께 보고 최소 근거가 부족한 패키지를 제외한다.

- 빠르게 감소한다는 표현은 최근 신규 선택이 줄거나 이탈이 늘어난 관측을 뜻한다. 프로젝트 실패·패키지 품질 저하·미래 소멸을 뜻하지 않는다.

- 커뮤니티 논의는 npm이 연결한 공식 GitHub 저장소의 Issues·Discussions만 사용한다. Pull Request와 봇 활동은 공개 판정에서 빼고, 글·댓글·고유 참여자 수를 표시하며 긍정·부정 또는 품질 점수로 바꾸지 않는다.

- 이슈 리포트 사건은 계산 규칙이 먼저 만든다. AI는 통과 사건의 수치·기준일·비교 기간·대상 수·제외 조건·승인된 원문 ID로 제목과 설명 초안만 작성하며, 운영자가 승인한 사건만 공개한다. 원인·전망·추천은 만들지 않는다.

- 계산과 출처가 갱신되지 않거나 자료 수집이 실패한 글은 새 소식으로 공개하지 않는다.

### 기간별 한 패키지 한 표 원칙

- 정식 배포 버전을 공개 시각으로 기간에 배치하고, 각 기간 끝까지 공개된 버전 중 npm 의미 순서가 가장 높은 정식 배포를 그 기간의 대표 상태로 사용한다.

- 각 의존을 선언한 패키지는 대상 패키지·기간마다 최대 한 번의 상태로 축약한다.

- 기간 중 새 배포가 없어도 기간 끝 이전의 대표 상태를 이어간다. 직전 기간의 대표 상태와 비교해 선택·유지·이탈을 계산한다.

- 직전 없음→현재 있음은 신규 선택, 있음→있음은 유지, 있음→없음은 이탈로 분류한다.

- 기간 끝까지 한 번도 관측된 정식 배포가 없거나 의존 정보가 알 수 없음·처리 오류 상태인 기간은 없음으로 채우지 않고 계산 대상에서 제외한다.

- 같은 패키지가 버전을 자주 공개해도 다른 패키지보다 더 많은 표를 갖지 않게 한다.

### 버전 조건 변경

같은 의존 패키지 이름을 유지하면서 허용 버전 조건만 바꾼 경우는 신규 선택이나 이탈로 세지 않는다. 별도의 ‘버전 조건 변경’ 상태로 기록할 수 있지만, 4주 완성 화면의 핵심 지표에는 포함하지 않는다.

> **자료 부족과 해석 안전 장치 근거 수가 0이면 결과와 방향 설명을 만들지 않는다. 일부 기간만 관측되면 가능한 구간만 표시하고, 후보별 기간이 다르면 공통 구간으로 맞춘다. 처리 오류는 제외 수를 밝히며 원인을 단정하지 않는다. 차이가 작으면 원값과 근거 수를 그대로 보여 주고 과도한 증가·감소 표현을 쓰지 않는다. 신규 선택·유지·이탈·현재 규모는 정해진 규칙이 계산하며, 인공지능은 원값을 수정하거나 빈 값을 추정하지 않는다.**

## 개발 방식과 시스템 역할

이 장은 특정 제품이나 세부 구현법을 확정하지 않는다. 각 부분이 무엇을 받고, 어떤 책임을 지며, 무엇을 다음 부분에 전달하는지만 정의한다.

### 전체 동작 흐름

대용량 계산과 사용자 요청을 한 흐름으로 보지 않는다. 정기 작업이 패키지·기간별 지표를 미리 만들고 품질 검사를 통과한 기준일만 승격시킨다. 회원이 분석을 요청할 때는 승격된 결과를 조회·합산하며 대용량 계산을 새로 실행하지 않는다.

|---|---:|---|---|---|

| **온라인 요청** | 2 | 분석 입력·비교 묶음 | 패키지를 확인하고 MVP 운영자 묶음 또는 확장 AI 후보를 제안 | 사용자가 확정한 후보·기간 |
| **온라인 요청** | 3 | 서비스 운영 서버 | 승격된 지표를 조회하고 후보 묶음에 맞게 조합 | 그래프·근거용 숫자 |

| **공개 트렌드** | 1 | 사건 탐지·인공지능·공개 콘텐츠 관리 | 규칙 통과 사건에서 초안을 만들고 운영자가 승인 | 근거·원문이 붙은 공개 소식 |

| **작업 배분**   | 사용 가능한 여러 처리 장치에 일을 배분하고 진행 상태를 기록한다.             |
| **재실행**      | 실패한 부분만 다시 실행해 전체 작업을 처음부터 반복하지 않는다.              |
| **결과 병합**   | 나뉜 결과를 중복 없이 하나의 지표 결과로 합친다.                             |
| **중복 방지** | 기준일·계산 규칙 버전·작업·분할 키로 중복 실행과 중복 적재를 막는다. |
| **결과 일치**   | 1·2·4개 처리 장치에서 행 수·핵심 합계·체크값이 같은지 확인한다.   |
| **쏠림 확인**   | 인기 패키지에 일이 몰리는 현상과 메모리·전송 지연을 기록한다.                |
| **부분 결과 미게시** | 모든 분할과 품질 검사가 끝나기 전에는 새 기준일을 공개하지 않고, 실패 중에도 지난 승격 결과를 계속 제공한다. |
| **확장 계산 격리** | 핵심 시계열과 버전 고착·마이그레이션·공개 트렌드를 별도 작업으로 실행해 하나의 실패가 전체 서비스에 번지지 않게 한다. |

> **분리 원칙 deps.dev 의존 관계 이력은 신규 선택·유지·이탈을 계산하는 자료다. 패키지의 기능과 역할을 판단하는 설명·문서는 별도 패키지 정보 원천에서 가져온다. AI가 의존 관계 숫자만 보고 같은 역할을 추측하지 않는다.**

버전 고착·마이그레이션·트렌드 해설에서도 같은 원칙을 적용한다. AI는 계산된 비중·배수·근거 수와 승인된 원문만 문장으로 바꾸며, 업데이트하지 않은 이유, 마이그레이션의 원인, 커뮤니티 반응의 긍정·부정, 앞으로의 성공·실패를 추정하지 않는다.

## AI 비교 묶음 확장 전략

비교 묶음은 처음부터 AI에 맡기지 않는다. 먼저 사람이 정의한 묶음으로 분석 엔진과 사용자 경험을 안정시키고, 그 결과를 기준 답안으로 삼아 AI 제안 품질을 확인한 뒤 적용 범위를 넓힌다.

| **구분** | **MVP: 운영자 정의 묶음** | **후속: AI 생성 묶음** |
|---|---|---|
| **묶음 생성 주체** | 서비스 운영자와 기획자 | AI 모델이 후보를 제안하고 서버·사용자가 검증 |
| **사용 자료** | 사전에 검토한 역할·패키지 목록·선정 이유 | 패키지 설명·문서 요약·실제 검색 후보·기존 승인 묶음 |
| **지원 범위** | 날짜·시간, 기록, 통신의 3개 묶음 우선 | 승인된 범위부터 새로운 역할로 점진 확대 |
| **화면 표시** | ‘운영자 정의 묶음’으로 표시 | ‘AI 제안 묶음’과 제안 이유를 표시 |
| **최종 확정** | 사용자가 추가·제외 후 확정 | 사용자가 추가·제외 후 확정 |
| **실패 대응** | 사용자가 후보를 직접 입력 | 운영자 정의 묶음 또는 직접 입력으로 복귀 |

### MVP: 운영자 정의 비교 묶음

운영자는 비교 묶음 저장소에 다음 정보를 직접 등록한다.

- 묶음 식별값과 사람이 읽을 수 있는 역할 이름

- 포함할 실제 npm 패키지명과 선정 이유

- 직접 대안이 아닌 부가 기능·연결 도구·다른 역할의 제외 기준

- 자료 확인일, 작성자, 변경 이력과 묶음 버전

사용자가 묶음 안의 패키지를 입력하면 저장된 후보를 즉시 제안한다. 묶음에 없는 패키지는 사용자가 후보를 직접 입력한다. 이 단계에서는 AI가 비교 묶음을 새로 만들거나 확정하지 않는다.

### 후속: AI 비교 묶음 생성

1.  사용자가 입력한 패키지가 실제로 존재하는지 확인한다.

2.  별도 패키지 정보 원천에서 공식 설명·주요 검색어·문서 요약을 가져온다.

3.  AI가 입력 패키지의 핵심 역할을 한 문장으로 정리한다.

4.  서버가 패키지 검색 목록이나 별도 검색 색인에서 실제 후보를 넓게 찾는다. AI가 기억에 의존해 임의의 패키지명을 만들게 하지 않는다.

5.  AI가 후보를 직접 대안, 부가 기능, 연결 도구, 다른 역할로 나누고 포함·제외 이유를 작성한다.

6.  서버가 후보의 실제 존재, 이름, 분석 자료 보유 여부를 다시 확인한다.

7.  사용자에게 AI 제안임을 표시하고 후보와 이유를 수정할 수 있게 한다.

8.  사용자가 확정한 묶음과 기간을 서비스 운영 서버에 전달한다. 서버는 정기 분산 작업이 미리 만든 패키지·기간별 지표를 조회·합산하며 사용자 요청으로 분산 작업을 실행하지 않는다.

> **AI의 위치 AI는 패키지의 의미를 읽고 후보를 선별한다. 현재 규모·신규 선택·유지·이탈·비교 묶음 내 비중은 기존의 정해진 계산 규칙이 만들며, AI가 숫자를 만들거나 바꾸지 않는다.**

### AI 적용 전 확인할 기준

- 운영자 정의 3개 묶음에서 입력부터 보고서까지 동일한 분석 엔진이 안정적으로 동작한다.

- 같은 자료와 같은 비교 묶음으로 반복 실행했을 때 계산 결과가 일치한다.

- AI가 만든 후보를 대조할 평가 자료를 30개 이상 역할, 역할당 4~10개 패키지로 준비한다. 두 명이 독립적으로 직접 대안·일부 대안·플러그인·관련 없음을 분류하고 불일치만 합의한다.

- 직접 대안과 부가 기능·연결 도구·다른 역할을 구분하고, 포함·제외 이유를 확인할 수 있다.

- 서버 검증 이후 존재하지 않는 패키지가 사용자 후보로 노출되지 않는다.

- AI가 실패하거나 제안을 보류해도 운영자 정의 묶음과 사용자 직접 입력으로 전체 분석이 동작한다.

위 기준을 확인하기 전에는 AI 생성 묶음을 사용자에게 자동 확정하지 않는다. 초기에는 내부 검토용으로만 결과를 저장하고, 승인된 역할부터 사용자 제안 기능으로 연다.

초기 공개 목표는 정답 대체재의 95% 이상이 검색 상위 20개 안에 들고, 최종 상위 5개의 직접 대안 정확도가 90% 이상이며, 플러그인·관련 없음의 위험한 잘못 포함이 5% 이하인 것이다. 존재하지 않는 이름은 0건이어야 한다. 같은 자료·모델·지시문으로 반복했을 때 최종 묶음 겹침은 80% 이상, 사용자가 후보를 대규모로 고치는 비율은 20% 미만을 목표로 한다. 이 수치는 검증 전 목표이며 실제 성능이 아니다. 하나라도 충족하지 못하면 AI 묶음을 기본 방식으로 전환하지 않는다.

### 운영자 정의 방식에서 AI 방식으로 전환

1.  **MVP 운영** 운영자 정의 묶음을 기본값으로 사용한다.

2.  **내부 비교** 같은 입력에 대해 운영자 정의 결과와 AI 생성 결과를 함께 저장하고 차이를 검토한다. 사용자에게는 아직 AI 결과를 노출하지 않는다.

3.  **선택적 공개** 검토를 통과한 역할부터 AI 제안을 표시하되, 운영자 정의 묶음과 사용자 직접 입력을 함께 제공한다.

4.  **기본 방식 전환** AI 제안이 여러 역할에서 안정적으로 직접 대안을 찾고 서버 검증·사용자 수정 흐름이 동작하면 AI 생성 묶음을 기본 제안 방식으로 바꾼다.

5.  **안전한 복귀** 기본 방식이 바뀐 뒤에도 운영자 정의 묶음은 삭제하지 않는다. AI 실패·자료 부족·품질 저하 시 즉시 사용할 기준 답안과 대체 경로로 유지한다.

## 4주 개발 완성 범위

> **완성의 의미 일부 화면이나 표본 결과를 보여 주는 데모가 아니라, 비회원이 공개 랜딩에서 서비스를 이해하고 가입·로그인한 뒤 패키지를 입력해 비교 묶음을 확정하고 실제 계산 결과·그래프·해설·보고서·근거를 확인할 수 있는 하나의 서비스 흐름을 완성한다.**

### 완성 범위에 포함

- 비회원이 보는 서비스 설명·관측 범위·회원가입 유도 랜딩 화면

- 회원가입·로그인과 분석 화면·개인 보고서의 회원 접근 제한

- 웹 화면에서 실제 npm 패키지명 입력과 존재 확인

- 운영자가 미리 정의한 비교 묶음 자동 제안과 사용자 직접 수정

- 날짜·시간, 기록, 통신의 3개 비교 묶음과 12개 패키지에서 자동 제안 보장

- 그 밖의 유효 패키지는 사용자가 직접 비교 후보를 정하면 같은 분석 엔진 적용

- 기본 8개 완결 분기·1·2·3년·직접 선택 중 후보의 공통 관측 기간 안에서 기간 확정

- 현재 규모·신규 선택·유지·이탈 시계열 계산

- 후보 패키지별 그래프와 근거 수 표시

- 계산 결과 안에서만 작성되는 쉬운 해설

- 선택 조건·그래프·해설·주의사항을 묶은 인쇄용 보고서

- 자료 기준일·부분 기간·자료 없음·처리 오류 안내

- 대용량 작업 분배·진행 상태·실패 분할 재실행·중복 방지·결과 병합

- 1·2·4개 처리 장치에서 같은 입력의 행 수·핵심 합계·체크값이 일치하는지 확인하는 검증

- 부분 실패 결과는 게시하지 않고, 새 기준일 승격 전까지 지난 완전한 결과를 제공

### 완성 범위에서 제외

- 패키지 설명과 문서를 읽어 새로운 비교 묶음을 자동 생성하는 AI 기능

- package.json 입력과 여러 의존 패키지 목록 처리

- 버전 고착·마이그레이션 현황 계산과 보고서 추가

- 자료상 가장 이른 정식 배포의 선택·최근 증가·감소·커뮤니티 논의를 제공하는 공개 트렌드

- 개발·동료·선택·묶음 의존 관계 분석

- npm 이외 패키지 저장소 지원

- 회원 프로필 관리, 조직 권한, 결제, 공동 편집

- 모바일 전용 앱

- 코드 자동 수정이나 패키지 자동 교체

- 저장소의 변경 이유를 읽어 마이그레이션 의도를 단정하는 기능

- 기술 우열 점수·미래 생존 예측·최종 추천

| **마이그레이션을 인과로 오해**      | 같은 배포의 동시 변경일 뿐    | 배수·주체 축약·최소 근거 적용, 원인·완전 전환 표현 금지 |
| **커뮤니티 논의량을 품질로 오해**   | 문제·홍보·질문이 모두 섞임    | 원문·기간·출처 수 표시, 긍정·부정·우열 점수화 금지 |
| **비용·반출 크기 불확실**          | 전체 운영 비용 예측 어려움   | 실행 전 크기·비용 확인, 최대 처리량 제한       |
| **4주 범위 확장**                  | 핵심 흐름 미완성             | 기능-01~16만 MVP로 구현하고 확장-01~09는 분리  |

> **4주 안에 반드시 측정하고 기록할 것 전체 분석 입력의 실제 크기·파일 수·처리 시간·비용, 처리 장치별 작업 분포와 실패·재실행 기록, 반복 실행 결과 체크값, 운영자 정의 3개 비교 묶음의 실제 신규 선택·유지·이탈 결과와 근거 수, 묶음에 없는 패키지의 직접 입력 동작, 비회원 차단과 회원 보고서 접근, 해설 숫자의 원값 일치와 자료 부족 문장 준수 여부를 남긴다. 원천 자료를 분석 파일로 만드는 길은 확인됐으며, 최종 현실성은 이 측정과 4주 개발 범위의 완료 기준 충족 여부로 판단한다. AI 비교 묶음과 확장 지표·공개 트렌드 품질은 MVP 이후 별도 평가한다.**

## 문제-기능 연결

**새로운 기능이나 요구사항을 추가할 때는 반드시 해결하려는 문제에 연결한다. 연결되지 않는 항목은 개발 범위에 넣지 않는다.**

|---|---|---|

### 요구사항 명세서로 넘길 형식

다음 문서에서는 각 기능·확장 번호에 접근 대상, 입력값, 처리 규칙, 출력값, 정상 상태, 오류 상태, 자료 조건, 보관 범위, 완료 판단 기준을 붙인다. 이 기획서의 번호를 바꾸지 않고 그대로 추적한다.

> **변경 관리 지표·기간·비교 묶음을 실제 결과에 맞춰 임의로 바꾸지 않는다. 변경이 필요하면 문제, 근거, 변경 전후, 영향받는 기능·화면을 함께 기록한다.**

| **이탈**           | 이전에는 있었으나 다음 관측 상태에서 사라진 관계                         |
| **비교 묶음**      | 같은 역할로 비교할 패키지 후보 집합. 코호트(cohort)라고도 함             |
| **운영자 정의 묶음** | 서비스 운영자가 역할·후보·선정 이유를 검토해 미리 등록한 비교 묶음      |
| **AI 생성 묶음**   | AI가 실제 패키지 정보와 검색 후보를 바탕으로 제안하고 서버·사용자가 검증하는 비교 묶음 |
| **비교 묶음 저장소** | 승인된 묶음의 역할·후보·선정 이유·확인일·변경 이력을 보관하는 곳       |
| **첫 배포 선택 비중** | 공개 npm 패키지의 자료상 가장 이른 정식 배포에서 특정 의존 패키지가 선언된 비중 |
| **버전 고착**     | 새 주버전이 공개된 뒤에도 이전 주버전을 허용하는 의존 조건이 남아 있는 정도 |
| **마이그레이션 현황** | 특정 패키지 제거와 다른 패키지 추가가 같은 배포 변경에서 함께 나타난 방향과 비중 |
| **배수**           | X를 제거할 때 Y가 추가되는 비율이 전체 변경에서 Y가 추가되는 비율보다 몇 배 큰지 나타낸 값 |
| **패키지 트렌드**  | 첫 배포 선택·최근 증가·감소·커뮤니티 논의처럼 npm 생태계의 변화를 공개 소식으로 정리한 영역 |
| **이슈 리포트**    | 계산 지표와 외부 원문을 기준일·기간·근거 수와 함께 짧은 소식 형태로 정리한 글 |
| **근거 수**        | 각 지표 계산에 실제로 포함된 서로 다른 패키지 수                         |
| **분산 처리**      | 큰 계산을 여러 작은 작업으로 나눠 여러 처리 장치에서 수행하는 방식       |
| **체크값**         | 나뉜 계산 결과가 같은지 빠르게 확인하기 위한 고정된 비교 값              |

> **최종 한 문장 OSS Shift는 npm 패키지의 인기 순위를 만드는 서비스가 아니라, 공개된 의존 관계 이력에서 현재 규모와 선택 변화를 계산해 회원의 패키지 비교를 돕고, 확장 단계에서는 검증된 생태계 변화를 근거가 붙은 공개 트렌드 소식으로 제공하는 서비스다.**
