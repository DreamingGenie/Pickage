## 3. 아키텍처 / 데이터 흐름

### 3.1 HTTP 클라이언트 — 새 의존성을 추가하지 않는다

`build.gradle`에 `WebClient`·`RestTemplate`·`OkHttp` 등 외부 HTTP 클라이언트 의존성이 전혀
없고(`grep` 확인, §6), 기존 코드에 클라이언트 클래스도 없다 — 이 프로젝트가 지금까지 외부
HTTP 호출을 한 번도 한 적이 없다는 뜻이다(백엔드는 지금까지 DB 조회 전용, 외부 호출은 전부
Python pipeline이 담당). "존중할 기존 방식"이 없으므로 새로 고른다: **JDK 내장
`java.net.http.HttpClient`**를 쓴다. 새 `build.gradle` 의존성이 필요 없고(범위 밖 파일을
건드리지 않는다), `.followRedirects(HttpClient.Redirect.NEVER)`로 리다이렉트를 자동으로
따라가지 않게 만들어 §3.3의 cross-host redirect 차단을 직접 구현할 수 있다.

### 3.2 npm/GitHub 클라이언트는 "이 Phase가 필요한 만큼만"

- `NpmRepositoryLookup.fetchRepositoryField(String packageName)`: `GET
  https://registry.npmjs.org/{name}/latest`만 호출하고 `repository` 필드(문자열 또는
  `{url, directory}` 객체)만 파싱해 돌려준다. 그 외 npm metadata(버전 목록, dist 등)는
  다루지 않는다 — 그건 221의 몫이다.
- `GitHubRepositoryClient`: 세 호출만 한다.
  1. `GET /repos/{owner}/{repo}` — 존재 확인, `archived` 여부, 404/403 구분
  2. `GET /repos/{owner}/{repo}/contents/{directory}/package.json`(directory 있을 때) 또는
     `.../contents/package.json`(루트) — base64 디코드 후 `name` 필드만 읽어 일치 여부 확인
  3. 위 두 응답의 헤더에서 `X-RateLimit-Remaining`·`X-RateLimit-Reset`·`Retry-After`를 읽어
     일시 실패를 구분
  - API 버전은 구현계획 §설정과 보안이 고정한 `2026-03-10`을 `X-GitHub-Api-Version` 헤더로
    보낸다.
  - 이슈·댓글 조회(`/repos/{owner}/{repo}/issues`, `.../comments`)는 이 클라이언트에
    없다 — Phase 3(212)가 이 Phase의 검증 결과(owner/repo)를 받아 직접 만든다(Jira 212
    "213의 저장소 검증 결과를 받은 고정 GitHub API 경로만 호출한다").

### 3.3 SSRF 방지 — 임의 host에 실제로 연결하지 않는 것이 핵심 방어다

DB의 `repo_url`이나 npm의 `repository.url`은 신뢰할 수 없는 문자열이다. 이 코드는 **그
문자열이 가리키는 host에 직접 연결하지 않는다** — 문자열에서 `owner/repo`(그리고 있으면
`directory`)만 정규식으로 추출하고, 실제 HTTP 요청은 항상 고정된 `api.github.com`·
`registry.npmjs.org`로만 나간다. 즉 "받은 URL을 그대로 fetch"하는 코드 경로 자체가 없다 —
런타임에 IP를 검사하는 방식보다 강한 방어다.

그래도 판정표(§3.1)의 host 검사는 필요하다 — **문자열 파싱 단계**에서 스킴(https만)·
host(`github.com` 정확히 일치, `www.github.com`이나 IP 리터럴 불가)·port(기본 443 외 거부)·
경로(owner/repo 세그먼트에 `..`, `/`, 제어문자 없음)를 확인해 `UNSUPPORTED_HOST`로 조기
분류한다. `followRedirects(NEVER)`로 받은 3xx 응답의 `Location` 헤더가 있으면(정상 API
호출에서는 거의 없어야 함) host를 다시 검사하고, `api.github.com`/`registry.npmjs.org`가
아니면 즉시 실패시킨다 — 자동으로 따라가지 않는다.

### 3.4 정책 함수는 순수 함수로 분리한다

`RepositoryVerificationPolicy`는 §3.1·§3.2의 두 판정표를 그대로 옮긴 순수 함수
(HTTP 응답을 이미 받은 상태의 값만 입력으로 받는다)로 만든다 — Phase 1이 `CommunitySnapshotTtl`을
순수 함수로 분리한 것과 같은 이유다(외부 I/O 없이 표 하나로 통째로 단위 시험 가능).
`NpmRepositoryLookup`·`GitHubRepositoryClient`는 이 정책 함수에 넣을 원시 값만 만든다.

## 7. 2026-09-11 사용자 결정 — 미결 사항 해소

- **응답 byte 상한**: `2 MiB`(2,097,152 bytes)를 npm·GitHub 양쪽 기본값으로 정한다 — GitHub
  repo metadata(수 KB)·package.json(대개 수십 KB, 큰 monorepo도 수백 KB)보다 넉넉하되
  악의적/손상 응답이 무한정 메모리를 먹지 않을 정도로 좁다. **하드코딩 상수가 아니라 클라이언트
  생성자 인자**로 받는다 — 사용자가 실제 토큰으로 검증할 때 일부러 아주 작은 값(예: 100
  bytes)을 넣어 실제 GitHub 응답으로 이 상한이 진짜로 끊는지 확인할 수 있게 하기 위해서다.
  응답 본문은 `HttpResponse.BodyHandlers.ofInputStream()`으로 받아 **읽는 도중** 누적
  바이트를 세고, 상한을 넘는 순간 연결을 끊는다 — `ofString()`처럼 전체를 먼저 버퍼링한
  뒤에 길이를 재면 상한을 두는 의미가 없다(공격 응답을 이미 다 메모리에 올린 뒤다).
- **GitHub 토큰**: 사용자가 실제 발급받은 토큰으로 직접 검증한다. 이를 위해 JUnit 5
  `@EnabledIfEnvironmentVariable(named = "GITHUB_COMMUNITY_TOKEN", matches = ".+")`로 감싼
  선택적 실네트워크 시험을 `integrationTest`에 추가한다 — 269
  (`pipeline/snapshot/test_integration.py`)가 `PICKAGE_SNAPSHOT_TEST_CONTAINER` 환경변수로
  없으면 건너뛰는 것과 같은 패턴이다. 토큰이 없는 환경(CI·다른 팀원)에서는 자동으로
  skip되어 실패하지 않는다. 이 시험이 (1) 실제 pino/pinojs 저장소로 정상 검증 경로를,
  (2) 일부러 낮춘 byte 상한으로 실제 응답을 끊는 경로를 함께 확인한다.
