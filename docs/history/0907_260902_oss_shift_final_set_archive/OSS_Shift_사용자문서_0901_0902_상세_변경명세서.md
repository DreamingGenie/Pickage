# OSS Shift 사용자 문서 0901 → 0902 상세 변경 명세서

작성 기준일: 2026-09-02  
문서 상태: 최종본  
비교 대상:

- `OSS_Shift_요구사항_명세서_0901.md` → `OSS_Shift_요구사항_명세서_0902.md`
- `OSS_Shift_메뉴구조_IA_0901.md` → `OSS_Shift_메뉴구조_IA_0902.md`

이 문서는 0901과 0902 최종본의 차이를 사용자 여정, 화면 배치, 표시 정보, 조작 결과, 예외 상태와 서비스 범위 관점에서 추적한다. 단순 문장 차이가 아니라 사용자가 경험하는 방식과 개발팀이 구현해야 하는 화면 계약이 어떻게 달라졌는지를 설명한다.

## 1. 변경 규모

줄 수는 내용의 품질이나 중요도를 뜻하지 않는다. 0902에서는 0901의 반복적인 기술 설명을 줄이는 대신, 화면에서 실제로 필요한 상태와 사용자 행동의 결과를 세분화했다.

| 번호 | 0901 | 0902 최종본 | 사용자·화면 영향 |
|---:|---|---|---|
| 1 | 패키지명 또는 `패키지@버전` 입력 | 패키지명만 입력 | 후보를 정하기 전에 버전을 판단해야 하는 부담 제거 |
| 2 | 입력 단계에서 분석 버전 확정 | 기능 버전은 보고서 2페이지에서 선택 | 패키지 선택과 버전 판단을 순서대로 분리 |

| 4 | 후보 자동 선택 금지 | 기준 패키지와 상위 후보 2개 기본 선택 | 사용자는 즉시 분석할 수 있고 필요할 때만 조정 |

## 3. 전체 사용자 여정 변화

### 3.1 0901 사용자 여정

1. 서비스 소개
2. 패키지 또는 `패키지@버전` 입력
3. 존재와 분석 버전 확인
4. 후보 최대 3개 확인
5. 후보 선택·직접 추가
6. 전체 보고서에서 사용할 정확한 버전 고정
7. 생태계 변화 확인
8. 기능 비교와 근거 확인
9. PDF 받기

### 3.2 0902 최종 사용자 여정

1. 서비스 소개에서 제공 범위와 판단 한계 확인
2. 패키지명만 입력하고 npm 존재 여부 확인
3. 기준 패키지와 기본 선택된 상위 후보 2개 확인
4. 필요하면 후보를 해제하거나 다른 패키지를 직접 추가
5. 기준 패키지를 포함해 총 3개 이내로 비교 대상 확정
6. 생태계 변화에서 패키지별 Dependency `Total` 추이 확인
7. 필요하면 각 패키지의 Dependency 표시 버전만 독립적으로 변경
8. Activity와 Version Share 확인
9. 기능 비교에서 자동 선택된 최신 안정 버전과 완료 결과 확인
10. 필요하면 기능 비교 버전을 변경하고 명시적으로 재분석
11. 기능표 셀을 선택해 Evidence Drawer에서 판정 근거 확인
12. 확장 자료가 있으면 비교 패키지별 GitHub 커뮤니티 확인
13. 현재 완료 결과가 일치하면 전체 보고서 PDF 생성·다운로드

### 3.3 여정 변화의 핵심 의미

0901은 `입력할 때 버전 확정 → 보고서 전체에서 고정` 구조였다. 0902는 `패키지 선택 → 생태계 탐색 → 정확한 기능 버전 판단`의 순서로 바뀌었다. 사용자는 어떤 패키지를 비교할지도 정하지 않은 상태에서 버전을 먼저 알아야 할 필요가 없으며, 그래프를 보기 위한 버전과 기능을 판정하기 위한 버전을 서로 혼동하지 않게 된다.

### 5.3 기능-01·02: 패키지 입력과 존재 확인

| 항목 | 0901 | 0902 최종본 |
|---|---|---|
| 입력값 | 패키지명 또는 `패키지@버전` | 패키지명만 허용 |
| 입력 예시 | `winston`, `zod@4.0.0` | `winston`, `axios`, `zod` |
| 성공 결과 | 존재 여부와 확정 분석 버전 | `npm에서 확인됨`과 후보 선택 이동 안내 |
| 버전 안내 | 입력 화면에서 구체 버전 확인 | 버전은 보고서에서 확인·선택한다고 안내 |
| 다음 화면 전달 | 패키지와 분석 버전 | 패키지명만 전달 |

삭제된 경험은 `입력 단계의 버전 존재 확인`, `버전 미입력 시 자동 확정 버전 표시`, `입력 버전을 보고서 끝까지 고정`이다. 이 역할은 기능 비교 페이지로 이동했다.

### 5.4 기능-03·04: 관련 후보와 비교 대상

| 항목 | 0901 | 0902 최종본 |
|---|---|---|
| 후보 카드 수 | 최대 3개 | 기준 패키지를 제외한 최대 3개 |
| 기준 패키지 | 입력 패키지와 버전 표시 | 별도 고정 영역, 항상 선택, 해제 불가 |
| 기본 선택 | 자동 선택 금지 | 관련성 상위 2개 기본 선택 |
| 초기 선택 수 | 사용자 선택 전 미확정 | 기준 + 상위 2개로 `3 / 3 선택됨` |
| 최종 비교 제한 | 명시적인 총수 제한 부족 | 기준 포함 최대 3개 |
| 네 번째 추가 | 구체 동작 없음 | 적용하지 않고 기존 후보 해제 안내 |
| 직접 추가 | 존재 확인 후 추가 | 존재·중복 확인 후 사용자 추가 항목으로 선택, 후보 순위 유지 |
| 후보 검색 실패 | 후보 없음과 구분 부족 | 처리 실패와 유효 후보 0개를 별도 상태로 표시 |

기본 선택은 최종 추천이 아니다. 사용자는 상위 후보를 해제할 수 있지만 기준 패키지는 비교의 출발점이므로 유지한다.

### 5.5 기능-05~09·17: 생태계 변화

| 영역 | 0901 | 0902 최종본 |
|---|---|---|
| 페이지 구성 | 다운로드, 직접·간접 의존, 유지·유입·이탈 | Dependency → Activity → Version Share |

| 버전 변경 영향 | 보고서 전체 버전과 연결 | 해당 패키지 그래프 선만 변경 |
| 관계 전환 | 직접·간접 구분 | 같은 카드 우측 전환 컨트롤로 위치 확정 |
| 유지·유입·이탈 | 별도 지표 | Dependency 카드 하단 요약으로 위치 확정 |

Version Share는 실제 설치 버전 분포가 아니다. 공개 의존 조건에서 관측된 주버전 계열 비중이며, 해석하지 못한 조건은 별도로 남긴다.

## 7. 서비스 기획서 상세 변경

### 7.1 문서 성격 변화

0901 서비스 기획서는 후보 색인 규모, BigQuery·Spark, 자료 출처, 저장 원칙 같은 구현 설명을 함께 포함했다. 0902 최종본은 해당 내용을 개발 구상안으로 분리하고 다음에 집중한다.

- 사용자가 겪는 문제
- 서비스가 답하는 질문
- 서비스가 결정하지 않는 것
- 화면별 사용자 경험
- 판정과 근거를 이해하는 방식
- 실패해도 유지되는 결과
- PDF 공유 경험

### 7.2 서비스 정의 변화

| 0901 | 0902 최종본 |
|---|---|
| 패키지 또는 버전을 입력해 정확한 분석 버전 고정 | 패키지만 입력하고 버전은 보고서에서 판단 |

### 7.3 문제 정의 추가·변경

0902에서 새로 강조된 문제는 다음과 같다.

- 후보를 정하기 전에 버전을 요구하는 문제
- 최신 문서와 과거 버전 자료가 섞이는 문제
- 근거를 별도로 다시 찾아야 하는 문제
- 커뮤니티를 숫자만으로 파악하는 문제
- 화면 결과를 팀 공유 문서로 다시 작성하는 문제

기존의 후보 탐색 분산, 수치와 기능 분리, 분야에 맞지 않는 고정 기능표 문제는 유지됐다.

### 7.4 제공 가치 변화

후보 탐색 시간 단축과 근거 비교라는 기존 가치는 유지됐다. 여기에 다음 가치가 추가됐다.

- 후보 단계에서 버전을 결정하지 않아도 되는 자연스러운 판단 순서
- Dependency 탐색과 기능 판정이 서로 영향을 주지 않는 안정성
- Drawer를 통한 셀 단위 재검토
- 추천이 아닌 상황별 확인 기준
- 커뮤니티의 현재 작업 맥락 이해
- 완료 결과를 그대로 재사용하는 팀 공유 PDF

### 7.5 후보 경험 변화

0901은 후보 최대 3개와 사용자 선택을 정의했다. 0902는 기본 선택과 최대 제한을 사용자 행동 수준으로 설명한다.

- 기준 패키지는 고정 선택
- 상위 후보 2개 기본 선택
- 세 번째 후보는 미선택 추가 선택지
- 총 3개 상태에서 다른 후보를 넣으려면 기존 후보 먼저 해제
- 서비스가 기존 선택을 자동으로 버리지 않음
- 직접 추가 패키지는 후보 순위와 분리

### 7.6 생태계 변화 설명의 변화

0901의 다운로드·의존·관계 지표는 유지됐다. 0902는 사용자가 페이지에서 답을 얻는 질문과 해석 금지 기준을 강화했다.

- Dependency 드롭다운은 분석 대상 변경이 아니라 표시 필터
- 각 패키지 필터는 독립 동작
- Issues 시계열은 Activity에 배치
- Version Share를 MVP에 포함
- Version Share를 실제 설치 버전·업데이트 의지·위험으로 해석하지 않음

### 7.7 기능 비교 설명의 변화

0901은 정확한 버전 자료에서 기능을 발견하고 동적 기능표를 만든다는 원칙을 정의했다. 0902는 사용자가 보는 결과 순서와 재분석 경험을 추가했다.

- 최신 안정 버전 자동 선택
- 완료 결과가 있으면 별도 설정 없이 즉시 노출
- 정식 버전이 없으면 사전 배포 자동 선택 금지
- 버전 선택과 분석 상태를 화면 상단에 배치
- 환경 요약과 기능표를 짧게 제공
- 긴 조건과 발췌는 Drawer로 분리
- GPT와 같은 실제 진행 상태 표시
- 버전 변경 후 이전 결과 유지
- 성공할 때만 새 결과로 교체
- 직전 결과와 변경 이유를 한 번 표시

### 7.8 추천 없는 중립 해설

0901도 최종 추천을 금지했지만, 0902는 해설에 들어갈 수 있는 내용을 구체적으로 제한했다.

- 공통으로 확인된 기반
- 같은 목적을 제공하는 구성 방식의 차이
- 환경·설정·추가 패키지 조건
- 사용 상황에 따라 추가로 확인할 기준

`이 패키지를 선택하세요`, 추천 순위, 승자, 최종 선택 문장은 제공하지 않는다.

### 7.9 Evidence Drawer 가치 추가

서비스 기획서에 Drawer 목적, 열림 방식, 신뢰 요약, 근거 그룹, 외부 이동 제한, 충돌 처리까지 독립 장으로 추가됐다. 이는 사용자가 결과를 믿기만 하는 것이 아니라 판정의 최소 근거를 같은 화면에서 다시 검토할 수 있게 하기 위한 변화다.

### 7.10 GitHub 커뮤니티 가치 변화

0901은 최근 릴리스·커밋·Issue·PR 같은 공개 활동 확인이 중심이었다. 0902는 다음 질문에 답하는 글 중심 페이지로 변경됐다.

- 무엇을 논의하고 있는가?
- 사용자·기여자는 무엇을 주장하는가?
- 유지관리자는 어떤 조건과 우려를 말하는가?
- 어떤 재현·검토·구현 작업이 진행 중인가?
- 합의된 내용과 아직 합의되지 않은 내용은 무엇인가?

수치는 상단에 짧게 남기고 Issue 수의 시계열은 1페이지로 이동했다.

### 7.11 PDF 경험 변화

0901의 PDF는 화면과 같은 기준일·버전·근거를 유지하는 결과물이었다. 0902는 이를 독립적인 사용자 경험으로 확장했다.

- 현재 완료 보고서 확인
- 생성 가능 여부 판단
- 생성 단계 진행
- 자동 다운로드
- 같은 파일 다시 받기
- 재분석 필요 시 차단
- 부분 결과 경고와 포함
- 현재 탭과 무관한 전체 보고서 구성

### 7.12 AI 역할 변화

후보 단계에서 생성형 AI를 사용하지 않는 원칙은 유지됐다. 기능 비교에서의 AI 역할은 다음으로 더 좁아졌다.

- 구조화된 근거를 같은 사용자 목적의 기능으로 정리
- 제공된 근거 안에서 차이 설명
- evidence ID가 연결된 문장 작성

근거 없는 기능 생성, 충돌 근거 중 임의 선택, 추천·순위·미래 예측은 금지된다.

- 후보 카드 수와 최종 비교 수 혼동
