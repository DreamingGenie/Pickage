## 1. 한눈에 보는 결론

### 서비스 한 문장

OSS Shift는 사용자가 검토 중인 npm 패키지를 입력하면 관련 후보를 발견하도록 돕고, 사용자가 선택한 최대 3개 패키지의 생태계 변화와 정확한 버전 기능 차이를 근거가 연결된 보고서로 제공한다.

### 서비스가 답하는 질문

- 이 패키지와 목적이 가까운 실제 npm 패키지는 무엇인가?
- 비교할 패키지를 내가 직접 선택하거나 바꿀 수 있는가?
- 공개 생태계에서 다운로드와 의존 관계는 어떻게 변하고 있는가?
- 특정 버전의 Dependency 변화는 전체 추이와 어떻게 다른가?
- 최신 안정 버전의 환경·기능 차이는 무엇인가?
- 기능 판정은 어떤 자료에 근거하는가?
- 근거가 없거나 충돌하는 부분은 명확히 구분되는가?
- 현재 진행 중인 GitHub 논의와 작업은 무엇인가?
- 팀에 공유할 수 있는 동일한 PDF를 받을 수 있는가?

### 서비스가 결정하지 않는 것

- 가장 좋은 패키지
- 사용자가 최종 선택해야 할 패키지
- 기술 품질 순위
- 실제 설치·실행·호출량
- 특정 패키지가 교체된 이유
- 앞으로 성공하거나 사라질 패키지

## 2. 문제와 기회

패키지를 선택하려는 개발자는 관련 후보, 다운로드, 의존성, 버전, README, 타입 선언, GitHub 논의를 서로 다른 위치에서 확인해야 한다. 수치가 많아도 정확한 버전의 기능 조건이나 현재 커뮤니티가 무엇을 해결하려는지는 한눈에 알기 어렵다.

기존 탐색 과정에는 다음 문제가 있다.

| 문제 | 사용자에게 생기는 어려움 |
|---|---|
| 후보 탐색이 분산됨 | 익숙한 패키지만 비교하거나 검색 결과의 인기에 의존함 |
| 버전을 너무 일찍 요구함 | 후보도 정하지 않은 상태에서 어떤 버전을 봐야 할지 알기 어려움 |
| 수치와 기능이 분리됨 | 사용 흐름 변화와 실제 기능 조건을 함께 판단하기 어려움 |
| 최신 문서와 과거 버전이 섞임 | 선택한 버전에서 제공되지 않는 기능을 있다고 오해할 수 있음 |
| 기능표가 고정됨 | 로깅·검증·테스트·빌드처럼 분야가 다른 패키지에 맞지 않음 |
| 근거를 별도로 찾아야 함 | 표의 판정을 믿기 어렵고 팀에서 다시 검토하기 어려움 |
| 커뮤니티 화면이 숫자 중심 | 현재 무엇을 논의하고 작업하는지 이해하기 어려움 |
| 공유 문서를 다시 작성함 | 화면 결과를 복사해 별도 보고서를 만드는 시간이 듦 |

OSS Shift는 `후보 발견 → 생태계 변화 확인 → 정확한 버전 기능 비교 → 근거 검토 → 공유`를 하나의 사용자 여정으로 연결한다.

## 3. 목표 사용자

### 주 사용자

새 프로젝트에 패키지를 도입하거나 기존 패키지 교체를 검토하는 기술 책임자와 경력 개발자다.

| 구분 | 내용 |
|---|---|
| 결정 상황 | 신규 서비스 설계, 기존 패키지 교체, 환경·기능 차이 검토 |
| 현재 행동 | 후보 검색 → 다운로드·의존성 확인 → 문서·타입 확인 → 팀 논의 |
| 필요한 정보 | 관련 후보, 공개 변화, 정확한 버전 기능, 확인 조건, 근거 |
| 최종 결과 | 화면 보고서와 팀 공유 PDF |

### 확장 사용자

기능과 수치뿐 아니라 저장소에서 현재 진행 중인 논의·리뷰·구현 작업까지 확인하려는 개발자다.

## 6. 전체 사용자 경험

### 6.1 서비스 이해

사용자는 첫 화면에서 다음을 먼저 이해한다.

- 이 서비스는 관련 후보를 발견하도록 돕는다.
- 공개 npm 생태계에서 관측된 변화만 보여준다.
- 정확한 버전의 공식 자료를 근거로 기능을 비교한다.
- 기술적으로 가장 좋은 패키지를 추천하지 않는다.

사용자는 `패키지 분석 시작`을 선택해 분석 흐름에 진입한다.

### 6.2 패키지 입력

사용자는 npm 패키지명 하나만 입력한다. 이 시점에는 아직 비교할 후보가 정해지지 않았으므로 버전을 요구하지 않는다.

서비스는 패키지가 실제로 존재하는지 확인하고 성공·실패를 입력 카드 안에서 알려준다. 정상 확인 후에는 “버전별 정보와 기능 비교 버전은 보고서에서 확인하고 선택합니다”라는 안내와 함께 후보 선택으로 이동한다.

이 설계의 목적은 사용자가 `무엇을 비교할지` 정하기 전에 `어떤 버전을 비교할지` 결정하도록 강요하지 않는 것이다.

### 6.3 관련 후보 선택

후보 화면에서는 기준 패키지와 관련 후보를 함께 보여준다.

#### 최초 상태

- 기준 패키지는 항상 선택 상태다.
- 관련성 상위 후보 2개가 기본 선택된다.
- 세 번째 후보는 비교 가능한 추가 선택지로 제공된다.
- 하단에는 `3 / 3 선택됨`과 최종 비교 목록이 나타난다.

기준 패키지는 후보 카드 3개에 포함하지 않으며 사용자가 해제할 수 없다. 후보 카드 수와 최종 비교 패키지 수는 다음처럼 구분한다.

- 후보 카드: 기준 패키지를 제외한 최대 3개
- 최종 비교 대상: 기준 패키지를 포함한 최대 3개

기본 선택은 사용자의 시작 부담을 줄이기 위한 것이며 자동 최종 추천이 아니다. 사용자는 후보를 해제하거나 다른 npm 패키지를 직접 추가할 수 있다.

#### 최대 3개 제한

한 보고서에서 비교 가능한 패키지는 기준 패키지를 포함해 최대 3개다. 이미 3개가 선택된 상태에서 다른 후보나 직접 추가 패키지를 넣으려면 기존 후보 하나를 먼저 해제해야 한다.

서비스는 사용자의 기존 선택을 자동으로 버리지 않는다. 어떤 패키지를 포기할지는 사용자가 결정한다.

#### 후보 카드에서 보여주는 정보

- 패키지명
- 짧은 설명
- 설명 유사도
- 공통 키워드
- 최근 배포일
- 자료 상태

버전은 보여주지 않는다. 유사도는 품질 점수나 대체 가능성 점수가 아니라 후보를 발견한 근거다.

### 6.4 보고서 진입

사용자가 `분석 시작`을 선택하면 생태계 변화 페이지로 이동한다. 보고서 상단에는 최종 비교 패키지, 보고서 탭, PDF 내보내기를 배치한다. MVP 탭은 생태계 변화와 기능 비교이며, 검증된 저장소 자료가 하나라도 있을 때만 GitHub 커뮤니티 탭을 추가한다.

보고서 전체를 지배하는 하나의 버전은 두지 않는다. 생태계 추이를 탐색하는 버전과 기능을 판정하는 정확한 버전의 목적이 다르기 때문이다.

## 7. 보고서 1페이지: 생태계 변화

### 7.1 사용자가 얻는 답

- 전체 Dependency 추이는 어떻게 변했는가?
- 특정 버전만 보면 변화가 다른가?
- Downloads와 Issues는 어떤 흐름인가?
- 공개 의존 조건에서 어떤 버전 계열이 관측되는가?
- 유지·유입·이탈은 각각 어느 정도인가?

### 7.2 Dependency

Dependency 카드의 그래프 아래에 패키지별 드롭다운을 둔다. 처음에는 세 패키지 모두 `Total`이다.

사용자가 한 패키지의 특정 버전을 선택하면 그 패키지의 그래프만 바뀐다. 다른 패키지 드롭다운과 기능 비교 버전은 유지된다.

이 드롭다운은 분석 대상을 새로 정하는 기능이 아니라 사용자가 시계열을 탐색하는 표시 필터다.

카드 하단에는 유지·유입·이탈을 나눠 보여주며, 자료 없음이나 처리 오류를 이탈로 계산하지 않는다.

### 7.3 Activity

MVP에서는 Downloads가 기본이다. 확장 단계에서 같은 카드에 Issues를 추가한다.

Issues는 시각적인 수치 변화이므로 GitHub 커뮤니티 페이지가 아니라 생태계 변화 첫 페이지에서 그래프로 보여준다. 자료가 없는 구간은 0으로 연결하지 않는다.

### 7.4 Version Share

Version Share는 선택한 패키지의 공개 의존 조건에서 관측된 버전 계열 비중을 보여준다.

- 패키지 탭
- 전체 비중 도넛
- 버전 계열별 막대
- 해석 불가 조건

실제 설치 버전을 뜻하지 않으며, 해석할 수 없는 조건을 임의의 버전 계열에 포함하지 않는다.

### 7.5 1페이지 해석 원칙

- 그래프 변화가 기술 품질을 의미하지 않는다.
- 공개 의존 관계가 실제 실행량을 의미하지 않는다.
- 자료 누락을 감소나 이탈로 해석하지 않는다.
- Version Share를 업데이트 의지나 위험으로 단정하지 않는다.

## 8. 보고서 2페이지: 기능 비교

### 8.1 결과를 먼저 보여주는 이유

사용자는 기능 비교 페이지에 들어왔을 때 버전을 먼저 설정해야만 결과를 볼 수 있기를 원하지 않는다. 따라서 각 패키지의 최신 안정 버전을 자동 선택하고, 완료된 결과가 있으면 별도 확인 없이 바로 보여준다.

Figma 기준 페이지 순서는 다음과 같다.

1. 기능 비교 버전 선택
2. 분석 진행·완료 상태
3. 핵심 환경·설치 조건
4. 핵심 기능 비교
5. 중립적인 기능 비교 해설

버전 선택 영역이 먼저 보여도 최신 안정 버전이 이미 선택되어 있으므로 사용자가 별도 조작을 해야 결과가 나타나는 구조는 아니다. 정식 버전이 없는 패키지는 사전 배포 버전을 자동 선택하지 않고 그 이유를 표시한다.

### 8.2 핵심 표

결과 표는 사용자가 패키지의 큰 차이를 빠르게 파악하는 역할을 한다. 환경 요약표 다음에 핵심 기능표를 배치한다.

표에는 다음만 넣는다.

- 기능 또는 확인 기준
- 패키지별 판정
- evidence ID

조건 설명, 긴 발췌, 기술 감사 정보는 표 안에 넣지 않는다. 사용자가 셀을 선택했을 때 Drawer에서 확인한다.

핵심 기능은 근거가 충분할 때 5~7개를 보여준다. 직접 비교할 근거가 5개보다 적다면 확인 가능한 항목만 표시하고 비교가 제한적인 이유를 설명한다. 숫자를 맞추기 위해 기능 항목을 만들지 않는다.

### 8.3 기능 비교 버전

최신 안정 버전은 자동 선택되지만 사용자가 다른 버전을 선택할 수 있다.

버전 변경 직후에는 기존 결과를 없애지 않는다. 사용자는 기존 결과를 보면서 선택한 버전과 현재 완료 결과 버전이 다르다는 사실을 확인한다.

`선택한 버전으로 재분석`을 실행하면 새 분석이 시작된다.

- 성공: 새 결과로 교체하고 직전 결과와 달라진 이유를 한 번 보여준다.
- 실패: 이전 정상 결과를 유지한다.
- 부분 완료: 확인 가능한 결과부터 보여주고 영향을 받는 셀만 미확인으로 남긴다.

### 8.4 GPT형 진행 경험

최초 분석에서 결과가 아직 준비되지 않은 영역은 skeleton으로 표시한다. 그 아래에는 실제 완료된 단계만 순서대로 나타낸다.

예:

- 정확한 버전과 배포 자료를 확인했습니다.
- 실행 환경과 공개 진입 정보를 확인하고 있습니다.
- 기능 근거를 정리하고 있습니다.
- 근거를 기능 판정과 연결하고 있습니다.
- 비교 해설을 작성하고 있습니다.

완성되면 진행 문구가 핵심 표와 완성된 해설로 대체된다. 작업하지 않은 내용을 완료된 것처럼 보여주지 않는다.

### 8.5 중립 해설

하단 글은 표의 판정을 반복하지 않는다. 다음을 설명한다.

- 여러 패키지에 공통으로 확인된 기반
- 같은 목적을 서로 다른 방식으로 제공하는 차이
- 특정 환경·설정·추가 패키지와 같은 조건
- 사용 상황에 따라 추가로 확인해야 할 기준

문장마다 evidence ID를 연결한다. “이 패키지를 선택하세요”와 같은 추천 문장은 만들지 않는다.

### 8.6 판정의 의미

| 판정 | 사용자 해석 |
|---|---|
| 지원 | 직접 근거로 기능이 확인됨 |
| 조건부 지원 | 명시된 환경·설정·추가 조건에서 지원됨 |
| 제한적 지원 | 기능은 있으나 범위나 제공 수준에 제한이 있음 |
| 미확인 | 자료로 확정할 수 없거나 같은 버전 근거가 충돌함 |
| 미지원 | 공식적인 부정 근거가 확인됨 |

미확인은 미지원보다 낮은 점수가 아니다. 판단을 유보해야 하는 상태다.

## 9. Evidence Drawer 경험

### 9.1 목적

Drawer는 사용자가 표의 한 판정을 신뢰할 수 있는지 검토하는 공간이다. 외부 문서 사이트를 다시 탐색하게 하기보다 판정에 실제 사용한 최소 근거를 화면 안에서 제공한다.

### 9.2 열림 방식

- 기능표의 한 셀 선택
- 데스크톱에서는 우측 560px
- 모바일에서는 전체 높이 하단 시트
- 배경 표와 선택 셀 유지
- 같은 기능의 패키지 탭 전환
- 다른 셀을 선택하면 Drawer 위치는 유지하고 내용만 교체
- 열릴 때 Drawer 제목으로 포커스 이동, 닫힐 때 원래 비교 셀로 복귀

### 9.3 상단 신뢰 요약

- 패키지와 정확한 버전
- 기능과 판정
- 한 문장 판정 이유
- 공식 근거와 정적 확인 수
- 분석일
- 자료 상태

기술 정보는 처음부터 펼치지 않는다. 사용자가 판정 재현이나 자료 신선도를 확인하려 할 때만 펼친다.

### 9.4 근거 구성

근거는 역할별로 묶는다.

1. 지원이 확인된 근거
2. 조건과 제한을 확인한 근거
3. 추가 확인 자료
4. 충돌하는 근거

각 그룹의 가장 중요한 근거 하나만 기본으로 펼친다. 발췌는 기본 3줄이며 최대 10줄까지 Drawer 안에서 확장할 수 있다.

### 9.5 외부 이동을 제공하지 않는 이유

Drawer에서 공식 원문 보기, npm 보기, GitHub 보기, deps.dev 보기로 연결하지 않는다. 서비스가 판정에 사용한 출처 유형·경로·섹션·발췌는 표시하지만 외부 원문으로 이동시키지 않는다.

복사는 근거 ID와 분석 정보만 제공한다.

복사 완료는 버튼 주변의 짧은 완료 문구로 알려준다. 저장소 주소와 출처 위치를 포함한 사용자 화면의 식별 정보는 클릭 가능한 외부 링크로 만들지 않는다.

### 9.6 근거 충돌

같은 버전의 타입 선언과 공개 진입 정보가 서로 다른 결과를 가리키면 AI가 한쪽을 선택하지 않는다.

- 판정: 미확인
- 자료 상태: 근거 충돌
- 본문: 양쪽 근거 보존
- 다음 행동: 단순 반복 재분석 미제공

## 10. 확장 3페이지: GitHub 커뮤니티 현황

### 10.1 페이지 역할

이 페이지는 패키지의 현재 커뮤니티가 무엇을 논의하고 어떤 작업을 진행하는지 이해하는 공간이다. Issue 수의 추이는 보고서 1페이지 Activity에서 보여준다.

### 10.2 상단 요약

상단에는 비교 패키지 탭과 다음 정보만 간략히 배치한다.

- 저장소 연결이 검증된 비교 패키지 선택
- 연결 저장소와 검증 범위
- 조회 시점
- 최근 릴리스
- 최근 커밋
- 열린 Issue
- 열린 PR

최종 비교 대상 중 저장소 연결이 검증된 첫 패키지를 기본으로 보여준다. 연결을 검증하지 못한 패키지는 다른 패키지의 정보를 대신 보여주지 않고 비활성 상태와 이유를 표시한다. 저장소 주소는 식별 정보이며 외부 이동 기능이 아니다.

### 10.3 글 중심 본문

각 논의 항목은 다음 질문에 답해야 한다.

- 지금 어떤 문제가 논의 중인가?
- 사용자나 기여자는 무엇을 주장하는가?
- 유지관리자는 어떤 조건이나 우려를 제시하는가?
- 현재 어떤 재현·검토·구현 작업이 진행 중인가?
- 합의된 내용과 아직 합의되지 않은 내용은 무엇인가?

합의되지 않은 의견을 프로젝트의 결론처럼 표현하지 않는다.

## 11. PDF 경험

### 11.1 목적

PDF는 현재 화면을 인쇄하는 기능이 아니라, 완료된 보고서를 팀에서 공유하고 재검토하기 좋은 문서로 재구성하는 기능이다.

### 11.2 내보내기 확인

사용자는 보고서 상단에서 `PDF 내보내기`를 선택한다. 서비스는 다음을 보여준다.

- 비교 대상 패키지
- 기능 비교 버전
- 생태계 조회 기간
- 패키지별 Dependency 표시 필터
- 포함되는 보고서 구역
- 전체·부분·미확인 자료 상태

사용자는 구성을 편집하지 않고 현재 완료 보고서가 맞는지만 확인한다.

### 11.3 생성 차단

다음 상태에서는 PDF를 만들지 않는다.

- 기능 비교 버전을 바꿨지만 재분석하지 않음
- 재분석 진행 중
- 최초 핵심 결과가 아직 없음
- 화면의 선택과 완료 결과 버전이 일치하지 않음

차단 화면은 이유, 선택 버전, 현재 완료 버전을 보여주고 기능 비교 화면으로 이동하도록 돕는다.

### 11.4 부분 결과 허용

다음은 경고와 함께 PDF로 만들 수 있다.

- 일부 기간 자료 없음
- 일부 기능 미확인
- 근거 충돌
- GitHub 보조 확인 일부 실패
- 비교 해설 생성 실패

사용자에게 불완전한 부분을 숨기지 않는 것이 완전해질 때까지 보고서 전체를 막는 것보다 중요하다.

### 11.5 PDF 구성

1. 표지·분석 요약
2. 생태계 변화: Downloads, Dependency와 현재 표시 필터, 유지·유입·이탈, Version Share, 제공 가능한 Issues
3. 기능 비교: 분석 버전, 핵심 환경, 핵심 기능표, 중립 해설
4. 근거 요약 부록
5. 제공 가능하면 비교 대상별 GitHub 커뮤니티 현황

실제 용지 수는 내용에 따라 달라진다. `보고서 1·2페이지`는 웹 보고서의 구역을 뜻하며 PDF가 두 장이라는 의미가 아니다.

### 11.6 다운로드 경험

- 생성 완료 시 자동 다운로드
- 파일명·생성 시각·페이지 수·크기 표시
- 다운로드 실패 시 같은 파일 다시 받기
- 다시 받기를 선택해도 보고서를 재분석하거나 PDF를 다시 만들지 않음

## 13. AI의 역할

### 후보 단계

생성형 AI는 후보 이름을 만들거나 후보 순서를 바꾸지 않는다. 후보는 실제 수집된 패키지와 계산 가능한 관련성 근거로 제공한다.

### 기능 비교 단계

AI는 사용자가 비교 대상을 확정한 뒤 다음 역할만 수행한다.

- 확보된 근거를 비슷한 사용자 목적의 기능으로 정리
- 제공된 근거 안에서 차이 설명
- evidence ID가 연결된 문장 작성

다음은 수행하지 않는다.

- 원자료에 없는 기능 생성
- 근거 없는 지원·미지원 판정
- 충돌하는 근거 중 하나를 임의 선택
- 최종 추천·순위·승자·미래 예측

## 17. 용어

| 용어 | 정의 |
|---|---|
| 기준 패키지 | 사용자가 처음 입력한 패키지 |
| 관련 후보 | 설명·키워드가 가까운 실제 npm 패키지 |
| 비교 대상 | 기준 패키지를 포함한 최대 3개 패키지 |
| Dependency 표시 버전 | 그래프 탐색용 Total 또는 특정 버전 |
| 기능 비교 버전 | 기능 근거 분석에 사용하는 정확한 버전 |
| Version Share | 공개 의존 조건에서 관측한 버전 계열 비중 |
| Evidence Drawer | 기능 셀의 판정 이유와 근거를 확인하는 패널 |
| 미확인 | 자료로 확정할 수 없거나 근거가 충돌하는 상태 |
| 부분 완료 | 일부 결과는 제공할 수 있는 상태 |

> **최종 한 문장** OSS Shift는 패키지를 대신 골라주는 서비스가 아니라, 관련 후보를 발견하고 사용자가 선택한 패키지의 변화·정확한 버전 기능·근거를 같은 흐름에서 검토하도록 돕는 서비스다.
