# 1. Bronze 저장 규약 정의

## 작업 내용

수집한 API 응답 원문과 수집 메타를 저장하는 디렉터리 구조, 파일명 규칙, 메타 JSON 스키마를 확정하고 문서화한다.

## 필요한 이유

수집기를 여러 개 만들기 전에 규약을 고정해야 나중에 전면 재적재를 피할 수 있다. 특히 파티션 키를 달력 날짜로 잡으면 심야 운행 데이터를 나중에 재배치해야 하는데, 이는 전량 재적재를 뜻한다.

## 세부 항목

- [ ] 디렉터리 구조 확정 — `bronze/<source_key>/service_date=YYYY-MM-DD/`
- [ ] 파일명 규칙 확정 — UTC timestamp 기반, 원문과 `.meta.json` 페어
- [ ] 수집 메타 JSON 스키마 확정 (아래 필수 필드 포함)
- [ ] `requested_at`(호출 직전)과 `received_at`(응답 직후)을 분리 기록하도록 규약에 명시
- [ ] `request_url`의 인증키 마스킹 규칙 정의
- [ ] `collector_version` 표기 규칙 정의
- [ ] 규약 문서를 저장소에 커밋

## 영향 범위

- [ ] 데이터 저장소 (스키마·마이그레이션)
- [ ] 분석/모델
- [ ] 백엔드 API

# 2. 공통 Bronze 수집기 골격 구현

## 작업 내용

## 필요한 이유

## 세부 항목

- [ ] HTTP 호출 래퍼 — 타임아웃, 재시도 정책(지수 백오프)
- [ ] `requested_at` / `received_at` 분리 기록
- [ ] 원문을 가공 없이 바이트 그대로 저장
- [ ] `payload_sha256`, `payload_bytes` 계산
- [ ] HTTP 상태와 업무코드(`INFO-000`, `resultCode` 등) 이중 판정
- [ ] 인증키 마스킹 후 `request_url` 기록
- [ ] 실패 응답도 Bronze에 저장 (성공만 남기면 장애 구간을 무데이터와 구분 불가)
- [ ] 단위 테스트 — 타임스탬프 분리, 마스킹, 해시

# 5. quota 원장과 일일 호출 상한 구현

## 작업 내용

## 필요한 이유

지하철 전용키는 1일 1,000회이며 **OA-15799·OA-12601·OA-12764가 이 한도를 공유**한다(인증키 단위). 초과 시 그날의 수집이 통째로 막힌다. 재시도 폭주로 오전에 quota를 소진하면 그날 하루가 손실된다. 과거에 파이프 결합 문법 오류로 90건을 낭비하고 재실행한 이력이 있다.

## 세부 항목

- [ ] 카운터를 메타의 `quota_seq_today`에 기록
- [ ] 프로세스 재시작 후에도 카운터가 유지되는지 확인

# 7. `openapi.seoul.go.kr:8088` 접근 차단 원인 확인

## 작업 내용

서울 열린데이터광장 Open API upstream 호스트에 대한 TCP 연결 실패가 교육망 방화벽 때문인지, 다른 네트워크에서는 정상인지 확인한다.

## 필요한 이유

이 차단 하나에 실시간 도로소통(OA-13291), 돌발(OA-13315), 지하철 알림(OA-22718) 세 API의 사용 가능 여부가 걸려 있다. 세 API 모두 파일 다운로드 대체 경로가 없다. 확인 비용은 낮은데 판정 가치는 크므로 가장 먼저 처리한다.

## 세부 항목

# 10. canonical 차원·크로스워크 스키마 설계

## 작업 내용

역·노선의 내부 표준 식별자를 정의하고, 각 원천의 ID를 여기에 연결하는 크로스워크 테이블 스키마를 설계한다.

## 필요한 이유

각 API가 같은 역을 서로 다른 ID로 부른다 — 실시간은 `statnId`, 이력 파일은 역명 문자열, 시각표는 별도 식별자, 혼잡도는 3자리 `역번호`. 이 연결 고리가 없으면 수집한 데이터가 서로 이어지지 않는 섬으로 남는다. 각 API 문서에 TODO로 흩어져 있을 뿐 통합 설계가 없다.

## 세부 항목

- [ ] `dim_station` 설계 — canonical id, 정규화 역명, 좌표, 유효기간
- [ ] `dim_route` 설계 — canonical id, 노선 구분(버스/지하철), 정규화 노선명, 유효기간
- [ ] `xref_station` / `xref_route` 설계 — source_system, source_id, mapping_method, confidence, 유효기간
- [ ] canonical ID가 raw identity를 대체하지 않고 추가하는 구조임을 명시
- [ ] 역명 단독 조인 금지 원칙을 제약조건으로 반영
- [ ] 사실 테이블이 차원 키를 참조하는 구조 정의
- [ ] DDL 작성 및 리뷰

# 17. Gold 분포 물질화 테이블 설계

## 작업 내용

집계된 구간별 소요시간 분포를 API가 요청 시점에 인덱스 조회할 수 있는 PostgreSQL 테이블로 설계한다.

## 필요한 이유

`출발 시간 추천` API는 요청 시점에 해당 경로·시간대의 분포를 읽어야 한다. 현재 기획서 아키텍처에는 Historical Reliability Artifact가 어느 저장소에 사는지 명시가 없고, 소거법상 Gold Parquet에 위치하게 된다. Parquet을 요청마다 스캔하면 응답 지연이 초 단위로 발생한다. Parquet은 분석 스캔용이지 서빙 저장소가 아니다.

**이 이슈는 기존 기획 문서에 명시되지 않은 부분을 메우는 제안이므로, 착수 전 팀 논의가 필요하다.**

## 세부 항목

- [ ] `gold_leg_distribution` 스키마 설계 — 경로·구간유형·요일유형·시간버킷 → P50/P90/support
- [ ] `artifact_version`, `data_start_at`, `data_end_at` 등 provenance 필드 포함
- [ ] 조회 패턴에 맞는 복합 인덱스 설계
- [ ] support 부족 구간을 임의 값으로 채우지 않고 미계산 상태로 남기는 규칙
- [ ] 배치 산출물을 이 테이블로 물질화하는 경로 정의
- [ ] 예상 응답 시간 측정
- [ ] 팀 논의 후 SERVICE_PLAN 반영 여부 결정
