## 2. 제공 범위

- 지역 범위:
  - 공식 설명은 “서울지하철” 운행 알림이라고만 밝힌다.
  - 행정구역 경계, 서울 밖 연장구간, 타 운영기관 구간의 포함 여부는 명시하지 않는다.
- 노선·운영기관 범위:
  - 제공기관은 서울교통공사이며 `lineNm` 검색과 `lineNmLst` 출력을 제공한다.
  - 지원 노선·운영기관의 완전한 목록은 공식 명세에 없다. 서울교통공사 공지에 포함된 노선만 보장 후보로 보고 발급 키로 범위를 프로파일링한다.
  - 2026-08-25 표본에서는 `1호선`, `4호선`이 확인됐다. 이는 전체 제공 범위를 뜻하지 않는다.
- 제공 기간:
  - `noftOcrnDt` 및 `xcseSitnBgngDt` 날짜 구간 검색을 지원한다.
  - 데이터 공개일·갱신일: 2025-10-17
  - 공개일은 API 공개일이며 이력 시작일이나 보존 하한이 아니다.
- 과거 이력 제공 여부: **부분적으로 제공**
  - 과거 알림발생일·이례상황 시작일 검색 파라미터가 있다.
  - 보존기간과 삭제 정책은 미공개다.
  - 2026-08-25 `sample` 응답은 전체 1,298건으로 표시됐고 반환 5건의 알림발생일 범위는 2026-08-18~2026-08-24였다. 이 표본만으로 1,298건 전체의 기간을 단정하지 않는다.
- 데이터 갱신 주기: **매 1분**
- 실제 데이터 지연시간: **측정 불가·공식 SLA 미공개**
  - 응답에는 공급자 레코드 생성·수정시각이 없다.
  - `noftOcrnDt`는 알림발생일시이고, 계획된 미래 사건이나 이미 종료된 공지도 반환되므로 `received_at - noftOcrnDt`를 전송 지연으로 해석하면 안 된다.
  - 운영 수집에서는 `first_seen_at`, `last_seen_at`, `received_at`을 자체 기록해 탐지 지연과 목록 반영 지연을 별도로 추정한다.

## 3. 인증 및 호출 제한

- 인증 방식: URL 경로에 `KEY`를 넣는 API Key 방식
- API 키 발급처:
  - [서울 열린데이터광장 인증키 신청](https://data.seoul.go.kr/together/mypage/actkeyMain.do)
  - OA-22718 API 화면은 **일반 인증키 신청** 경로를 사용한다. 프로젝트 환경변수는 `SEOUL_OPEN_API_KEY`로 분리한다.
- 기본 일일 호출 한도: **OA-22718/일반 인증키의 수치형 일일 상한은 공식 페이지에 별도 명시되지 않음**
  - 공식 인증키 안내는 일 1,000회를 “실시간 지하철 오픈API”에 한정해 설명하고, OA-22718 화면은 일반 인증키 발급 경로를 연결한다.
  - 프로젝트 Decision Sheet의 2026-08-23 콘솔 근거에는 일반 인증키의 호출 횟수 제한 없음이 기록돼 있으나, OA-22718 실키 호출 전 계정 콘솔에서 다시 확인한다.
- 초당 호출 한도: 공식 문서에서 확인하지 못함
- 1회 조회 한도: 최대 **1,000건**
  - `sample` 키는 최대 5건이다. `1/6` 테스트는 본문 코드 `ERROR-335`를 반환했다.
- 호출량 증액 가능 여부:
  - 서울 열린데이터광장은 이용 제약 없이 계속 사용하려면 인증키와 콘텐츠를 활용사례 갤러리에 등록하라고 안내한다.
  - 증액 후 수치, 심사 기준, 처리 SLA는 미공개다.
  - 동일 데이터의 공공데이터포털 배포는 개발계정 10,000건과 활용사례 등록 후 운영 트래픽 증가 신청을 안내하지만, **별도 서비스키·gateway 계약**이다.
- 이용요금:
  - OA-22718 서울 열린데이터광장 페이지에는 별도 과금표가 없다.
  - 동일 데이터의 공공데이터포털 배포는 “무료”로 표시한다. 운영 전 실제 사용하는 gateway의 조건을 다시 확인한다.
- 이용약관·라이선스:
  - OA-22718 표시 기준 **공공누리 제1유형**
  - 출처표시 조건으로 상업적 이용과 변경이 가능하다.
  - 결과·Evidence에 “서울교통공사/서울특별시 공공데이터 활용”과 원문 링크를 표시한다.
  - API 호출, cache, raw 장기보존, derived data 보존, Share/재배포 권한은 프로젝트 `ProviderPolicyRegistry`에서 각각 승인한다.

공식 endpoint는 HTTP이고 인증키가 URL 경로에 포함된다. 키를 브라우저에서 사용하지 않고 backend collector에서만 호출하며 access·proxy·error log에서 경로의 키를 마스킹한다. 가능하면 별도의 HTTPS 배포 경로를 검토하되, 두 gateway의 인증·quota·응답 계약을 섞지 않는다.

## 5. 응답 데이터

공식 출력표는 `list_total_count`와 `RESULT.CODE/MESSAGE` envelope를 명시한다. 그러나 2026-08-25 공식 포털 `sample` relay의 실제 JSON/XML은 `response.header/body` envelope를 반환했다. 파서는 두 구조를 모두 허용하고 business status·전체 건수·행 목록을 canonical 형태로 변환해야 한다.

아래 “저장”은 전체 HTTP body의 무조건 장기보존이 아니라, `ProviderPolicyRegistry` 승인 후 **sanitized record와 provenance**에 저장한다는 의미다.

| 필드 | 의미 | 타입 | 예시 | 저장 여부 |
| --- | --- | --- | --- | --- |
| `list_total_count` | 명세상 전체 건수 | Integer | `1298` | 구조 허용·저장 |
| `RESULT.CODE` | 명세상 업무 결과 코드 | String | `INFO-000` | 구조 허용·저장 |
| `RESULT.MESSAGE` | 명세상 업무 결과 메시지 | String | `정상 처리되었습니다.` | 구조 허용·저장 |
| `response.header.resultCode` | 실측 업무 결과 코드 | String | `00` | 저장 |
| `response.header.resultMsg` | 실측 업무 결과 메시지 | String | `NORMAL_CODE` | 저장 |
| `response.body.pageNo` | 실측 페이지 번호 | Integer | `1` | 저장 |
| `response.body.numOfRows` | 실측 반환 행 수 | Integer | `5` | 저장 |
| `response.body.totalCount` | 실측 전체 건수 | Integer | `1298` | 저장 |
| `noftTtl` | 알림제목 | String | `4호선 열차운행계획 일부 조정 알림` | 저장 |
| `noftCn` | 메시지내용 | String, multiline | `진접차량기지 이전에 따른 ...` | source string 저장 |
| `noftSeCd` | 알림구분코드 | String Enum | `7` | 저장 |
| `noftOcrnDt` | 알림발생일시 | Local datetime String | `2026-08-21T17:26:31` | source string+파싱값 저장 |
| `lineNmLst` | 호선명목록 | Comma-separated String | `1호선, 4호선` | source string+배열 저장 |
| `stnSctnCdLst` | 역구간코드목록 | Nullable comma-separated String | `0150, 0426` | source string+배열 저장 |
| `crtrYmd` | 기준일자 | `YYYYMMDD` String | `20260821` | source string+파싱값 저장 |
| `xcseSitnBgngDt` | 이례상황 시작일시 | Nullable local datetime String | `2026-08-22T04:00:00` | source string+파싱값 저장 |
| `xcseSitnEndDt` | 이례상황 종료일시 | Nullable local datetime String | `2026-08-18T10:22:20` | source string+파싱값 저장 |
| `nonstopYn` | 무정차 관련 여부 | String Boolean | `Y`, `N` | 저장 |
| `upbdnbSe` | 상·하행 구분 | Nullable String | `상행` | source string+정규화 저장 |


HTTP 상태와 본문 업무 상태를 분리 저장한다. `HTTP 200`이어도 `RESULT.CODE`, `response.header.resultCode`, 또는 XML 오류 본문이 실패일 수 있다.

## 6. 시간 데이터 해석

- 제공기관 데이터 생성시각 필드: **없음**
  - `noftOcrnDt`: 알림발생일시
  - `crtrYmd`: 기준일자
  - `xcseSitnBgngDt`: 이례상황 시작일시
  - `xcseSitnEndDt`: 이례상황 종료일시
  - 레코드 생성·수정·API snapshot 생성시각은 제공하지 않는다.
- 예측시각 또는 실제시각 여부:
  - `noftOcrnDt`: 알림이 발생한 시각이며 열차 도착 예측·실제 도착시각이 아님
  - `xcseSitnBgngDt`: 사전 공지의 미래 예정시각 또는 이미 발생한 사건의 시작시각일 수 있음
  - `xcseSitnEndDt`: 종료 공지에 기록된 종료시각일 수 있으나 null이 많고 실제 측정 완료시각 보장은 없음
  - 필드만으로 계획·예측·실제 관측을 일률적으로 구분할 수 없어 `event_time_semantics=ANNOUNCED_OR_OPERATIONAL`로 보존한다.
- 시간대:
  - 공식 문서는 시간대를 명시하지 않는다.
  - 실측 문자열은 offset 없는 `YYYY-MM-DDTHH:mm:ss`다.
  - 수집기는 `Asia/Seoul`로 파싱하되 `timezone_assumption=KST_UNDOCUMENTED`와 원문을 보존한다.
- 자정 이후 운행일 처리 방식:
  - 공식 문서에 없음
  - 사건의 달력 날짜와 내부 `service_date`를 분리하고, 심야 운행일 매핑은 운행시간표 규칙이 확정된 뒤 수행한다.
- 수집시각과 제공시각의 차이:
  - source-generated timestamp가 없어 실제 공급 지연을 계산할 수 없다.
  - 자체 `requested_at`, `received_at`, `first_seen_at`, `last_seen_at`을 저장한다.
  - `received_at - noftOcrnDt`는 **notice age**일 뿐 source latency가 아니다.
- 시간표 기준인지 실제 관측값인지:
  - 열차 시간표 행이 아니다. 코드 `7`·`8`도 “시간표 변경 공지”이지 기계 판독 가능한 열차별 시간표가 아니다.
  - 열차 도착의 실제 관측값도 아니다.
  - 계획·진행·종료 상태가 혼재할 수 있는 운영 공지 이벤트다.

> 이 API에는 열차 도착시간이 없다. `noftOcrnDt`는 알림발생시각이고 `xcseSitnBgngDt`·`xcseSitnEndDt`는 이례상황의 공지된 시작·종료시각이다. 계획 도착값, 도착 예측값, 실제 도착 관측값으로 사용하지 않는다.

과거 재현에서는 나중에 추가된 종료시각을 이전 예측 시점에 소급 사용하면 leakage다. 각 poll의 `first_seen_at`과 `record_fingerprint` 버전을 보존하고 `observed_at <= calculated_at`인 버전만 Leave-now feature로 사용한다.

## 7. 식별자

- 노선 식별자: **전용 ID 없음**
  - `lineNmLst`의 호선명 문자열 목록만 제공
  - 쉼표 분리·trim 후 내부 canonical line ID로 매핑한다.
- 차량·열차 식별자: **없음**
- 정류장·역 식별자:
  - 요청: `stnCd` 역코드
  - 응답: `stnSctnCdLst` 역구간코드목록
  - 실측값 `0150, 0426`처럼 선행 0이 있으므로 문자열로 보존한다.
- 방향 식별 방식:
  - `upbdnbSe`의 상·하행 문자열
  - 다중 호선·다중 방향 공지에 단일 값 또는 null이 반환될 수 있어 행 전체의 모든 노선에 그대로 복제하지 않는다.
- 다른 API와 ID가 동일한지:
  - 공식 동일성 보장 문서는 확인하지 못했다.
  - OA-12764의 `statnId`는 10자리 형식인 반면 이 API 표본은 4자리 역구간코드이므로 직접 조인하지 않는다.
  - 동일 코드의 일부 suffix가 겉보기로 일치하더라도 별도 crosswalk 검증 전에는 같은 역으로 확정하지 않는다.
- 내부 표준 ID 매핑 필요 여부: **필요**
  - `provider + lineName + stationSectionCode + direction + mappingVersion`을 후보 키로 둔다.
  - 역 목록이 null이면 제목·본문에서 임의로 역을 추출해 canonical ID로 자동 승격하지 않는다.
  - 자유 텍스트 파서는 별도 precision/recall 검증과 수동 검토 표본을 통과한 경우에만 보조 매핑으로 사용한다.

안정적인 공지 ID가 제공되지 않는다. 내부 중복 후보 키와 레코드 해시를 자체 생성해야 한다.

```text
notice_candidate_key = sha256(provider | noftOcrnDt | noftTtl | noftSeCd |
                              normalizedLineList | normalizedStationList |
                              upbdnbSe | nonstopYn)
record_fingerprint = sha256(all_11_provider_fields)
```

같은 `notice_candidate_key`에서 `record_fingerprint`가 달라지면 수정 후보로 보존한다. stable ID가 없으므로 자동 덮어쓰지 않고, 사건 연결 규칙이 모호하면 별도 레코드로 유지한다.

## 8. 수집 계획

- 수집 방식: **주기적 폴링**
  - 중앙 collector가 한 번 수집하고 모든 사용자 요청이 같은 freshness-bounded snapshot을 재사용한다.
  - `ProviderPolicyRegistry`의 cache 승인을 받기 전에는 in-process ephemeral snapshot만 사용하고 cross-session cache는 만들지 않는다.
  - 사용자별 직접 호출은 금지해 중복 호출과 키 노출을 막는다.
- 수집 주기:
  - 초기값: 60초
  - 공식 갱신주기와 같지만 실제 변경 탐지 지연을 24시간 이상 측정한 뒤 조정한다.
  - jitter를 두고 이전 poll 종료 전에 다음 poll을 겹치지 않는다.
  - 1페이지를 60초마다 호출하면 1,440회/일이다. 실제 일반 인증키에 일일 횟수 제한이 없음을 콘솔과 실키로 확인하기 전에는 운영 적용하지 않고, 제한이 확인되면 120초 이상 또는 별도 승인된 gateway 예산으로 축소한다.
- 수집 범위:
  - 모든 알림구분코드 `1`~`8` 수집
  - 정상 수집은 `srchStartNoftOcrnYmd`~`srchEndNoftOcrnYmd`에 KST 기준 최근 2일 overlap을 주고 최대 1,000행씩 paginate
  - 장애 복구·backfill은 날짜 window를 분리해 제한적으로 수행
  - 정렬 순서는 공식 보장이 없으므로 “첫 페이지가 항상 최신”이라고 가정하지 않는다.
- 원문 저장 여부: **정책 승인 전 영속 원문 저장 금지**
  - `ProviderPolicyRegistry`가 raw retention을 승인하기 전에는 response body를 memory/짧은 처리 구간에서만 사용한다.
  - 승인 후에도 인증키·전체 요청 URL을 제거한 sanitized record와 provenance만 저장한다.
  - 원형 응답이 계약 재현에 필요하면 운영 Bronze와 분리된 evidence artifact로 별도 승인·보관한다.
- 저장 위치:
  - 정책 승인 후 논리 Bronze: `bronze/seoul-subway-notice/received_date=YYYY-MM-DD/hour=HH/{fetch_id}.json.gz`
  - 정규화 Silver: `silver/subway_service_alert_event`
  - 현재 물리 저장소와 TTL: G5/배포 ADR 확정 전 `TBD`
- 재시도 정책:
  - connect/read timeout, HTTP 429/5xx, `ERROR-500/600/601`, gateway 일시 오류만 exponential backoff+jitter로 최대 2회
  - 인증·파라미터·서비스명·sample limit 오류는 자동 재시도하지 않음
  - timeout 뒤에는 응답이 공급자에 도달했을 수 있으므로 다음 성공 poll에서 overlap window로 멱등 보정
  - 연속 실패 시 circuit breaker를 열고 Leave-now를 `PARTIAL/NONE` 또는 historical-only로 축소
- 중복 판정 기준:
  - 전송 중복: `fetch_id + row_index`
  - 완전 동일 레코드: `record_fingerprint`
  - 공지 수정 후보: 같은 `notice_candidate_key`, 다른 `record_fingerprint`
  - 사건 연결: 시작·종료 공지가 서로 다른 행일 수 있으므로 별도 `incident_link_id`와 rule version을 사용하고, 제목 유사도만으로 자동 병합하지 않음

수집기는 HTTP status, business code, requested/received timestamp, page, total count, row count, schema version, body hash, retry count를 기록한다. 키가 포함된 원본 URL과 자유 텍스트 사용자 위치는 저장하지 않는다.

## 9. 전처리 및 활용

- 생성할 데이터:
  - [ ] 구간 운행시간
  - [ ] 정차시간
  - [ ] 실제 배차간격
  - [ ] 계획 대비 지연
  - [x] 사고·운행장애 이벤트

이 API는 “상당 시간 지연” 같은 공지 문구를 제공할 수 있지만 실제 지연 초·계획시각·열차별 Actual이 없으므로 앞의 네 데이터를 단독 생성하지 않는다.

- 전처리 규칙:
  1. 명세형 envelope와 실측 `response.header/body` envelope를 모두 canonical result로 변환
  2. HTTP success와 business success를 분리하고 `item`이 단일 object/array/null인 경우를 모두 처리
  3. 11개 공급자 필드를 source string으로 보존하고 명세 외 필드는 schema drift flag 후 검토
  4. `lineNmLst`, `stnSctnCdLst`를 comma split·trim하되 원문과 배열을 함께 보존
  5. 역코드와 알림코드는 문자열로 유지하고 선행 0을 보존
  6. offset 없는 시간은 KST 미문서화 가정으로 파싱하고 raw value·가정 flag를 저장
  7. `noftSeCd`와 `nonstopYn`만으로 현재 상태를 결정하지 않고 제목·이벤트 시작/종료·first-seen 버전을 함께 사용
  8. `xcseSitnEndDt=null`을 “현재 진행 중”으로 자동 변환하지 않음
  9. 종료 공지와 시작 공지는 rule-versioned matcher로 연결하고 ambiguous match는 별도 사건으로 유지
  10. 자유 텍스트는 CRLF 정규화·길이 제한·출력 escape를 적용하되 원문의 의미를 바꾸지 않음
  11. 모델에는 `observed_at <= calculated_at`인 feature만 넣고, 후속 종료 공지를 과거 snapshot에 소급하지 않음
  12. 정량 지연값을 본문에서 임의 추출하거나 `noftSeCd`에 임의 seconds/weight를 부여하지 않음
- 다른 데이터와 결합할 키:
  - 역 마스터: `lineName + stationSectionCode + mappingVersion`
  - 선택 경로: 내부 canonical line/station/direction ID
  - OA-12764 도착정보: 내부 crosswalk를 거친 `canonicalLineId + canonicalStationId + direction`
  - 운행시간표: `serviceDate + canonicalLineId + stationId + direction`; 코드 `7`·`8` 공지는 시간표 버전 재검증 trigger로만 사용
  - 이벤트 outcome 분석: incident window와 ETA/Actual observation의 event-time overlap
- 모델 입력 변수:
  - 알림구분코드, 무정차 관련 여부, event lifecycle state와 신뢰도
  - 영향 호선·역·방향, 영향 범위 cardinality, selected leg와의 match 여부
  - 알림 후 경과시간, 이례상황 시작까지 남은 시간, 종료 여부
  - `station_scope_missing`, `direction_missing`, `start_missing`, `end_missing`
  - source freshness 대신 `first_seen_age`, `last_seen_age`, poll health
  - 시간대·요일·service date, 다른 ETA/position source의 freshness와 residual

명확한 active 무정차가 selected route의 필수 역과 정확히 매칭되면 모델 weight보다 **service availability Gate**로 우선 처리한다. 단순지연·기타 알림은 temporal hold-out에서 유의한 개선이 확인되기 전까지 사용자 안내와 Evidence에만 노출하고 확률분포를 임의 보정하지 않는다.

## 10. 데이터 품질 및 제약

- 결측값 발생 조건:
  - 전체 노선 공지처럼 특정 역·방향이 없을 때 `stnSctnCdLst`, `upbdnbSe`가 null
  - 사전 공지·진행 공지·종료 공지의 lifecycle 단계에 따라 시작·종료시각이 null
  - 공급자 입력 누락 또는 여러 사건을 한 공지에 합친 경우
  - 검색 조건에 맞는 행이 없을 때 `INFO-200` 또는 빈 items
- 중복 데이터 가능성:
  - 목록형 API를 반복 poll하면 같은 공지가 계속 반환될 수 있다.
  - 시작·진행·종료가 별도 공지로 발행돼 하나의 사건이 여러 행으로 나타날 수 있다.
  - 동일 내용 수정 시 stable ID가 없어 같은 공지의 새 버전인지 별도 공지인지 모호할 수 있다.
- 잘못된 값 또는 특수값:
  - `stnSctnCdLst`는 `0150, 0426`처럼 선행 0과 쉼표를 포함한다.
  - `lineNmLst`도 다중값 문자열이고 `noftCn`은 CRLF를 포함한다.
  - 시간 문자열에 offset이 없다.
  - 코드 `6(기타)`에 시위·무정차·종료 공지가 함께 포함돼 분류력이 낮다.
  - 실측에서 “무정차 통과 종료” 공지도 `nonstopYn=Y`였다. 따라서 `Y`를 현재 무정차 상태로 해석하면 안 된다.
  - 다중 노선·다중 방향 내용에 단일 `upbdnbSe`만 나타날 수 있다.
- 데이터 제공 제외 구간: 정확한 제외 노선·운영기관·서울 밖 구간은 미공개
- 실시간 데이터 과거 보관 여부:
  - 날짜 검색과 다수 누적 행은 확인됐지만 보존기간·수정 이력·삭제 정책은 미공개
  - 공급자가 record version history를 제공하지 않으므로 프로젝트가 first-seen 기준 변경 이력을 자체 수집해야 한다.
- API 장애 시 대체 데이터:
  - 동일 데이터의 [공공데이터포털 배포](https://www.data.go.kr/data/15144070/openapi.do)를 별도 gateway 후보로 검증
  - OA-12764 도착정보와 실시간 위치정보로 현재 ETA·운행상태를 보강하되 사고 공지의 완전한 대체로 간주하지 않음
  - 대체 source도 없으면 stale 공지를 active로 재사용하지 않고 `realtimeContextCoverage=PARTIAL/NONE` 및 historical-only fallback 적용
- 확인된 문제:
  1. 공식 출력 명세의 `list_total_count/RESULT`와 실측 `response.header/body` envelope가 다름
  2. 공식 endpoint가 HTTP + 포트 8088 + URL path key 구조라 전송·로그 보안 검토 필요
  3. 이 실행환경에서 direct `openapi.seoul.go.kr:8088` 연결이 timeout되어 실제 서비스 endpoint latency를 검증하지 못함
  4. 공급자 생성·수정시각, 시간대, 자정 운행일, 실제 전달 지연 SLA가 미문서화
  5. stable notice ID, 열차 ID, 전용 노선 ID가 없음
  6. 역·방향·시작·종료의 null이 많고 lifecycle을 나타내는 명시적 상태코드가 없음
  7. `nonstopYn=Y`가 진행과 종료 공지에 모두 나타나 현재 상태 판별에 단독 사용 불가
  8. 지원 노선·운영기관·지역 경계와 과거 보존기간이 미공개
