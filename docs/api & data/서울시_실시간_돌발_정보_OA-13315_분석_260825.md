### 핵심 판정

이 API는 버스·지하철의 도착이나 운행 이력이 아니라 **호출 시점에 반환되는 도로 사고·공사·통제 이벤트의 실시간 스냅샷**이다. 공식 문서는 활성·예정·종료 이벤트의 포함·소멸 규칙을 명시하지 않는다. Journey Reliability에서는 노선의 도로 구간을 LINK_ID 또는 좌표와 결합할 수 있을 때 현재 출발 예측의 외생 위험 피처로 사용할 수 있다.

다만 다음 경계를 지킨다.

- API 한 건을 지연시간이나 도착확률로 직접 변환하지 않는다.
- 이벤트가 없다는 응답과 API 장애·매핑 실패를 구분한다.
- 목표 도착시각 기준 출발 추천은 현재 프로젝트 계약상 historical baseline을 사용하므로 이 실시간 스냅샷을 직접 투입하지 않는다.
- 실시간 데이터의 과거 이력은 포털에서 제공하지 않으므로 장기 활용에는 자체 스냅샷 적재가 필요하다.
- 경로와 도로 링크의 매핑이 불완전하면 realtimeContextCoverage를 NONE 또는 PARTIAL로 노출한다.

## 2. 제공 범위

- 지역 범위:
  - 서울시 TOPIS가 관리·제공하는 도로 돌발 이벤트
  - 정확한 도로망 경계, 이면도로·민자도로·서울 경계부 포함 여부는 공식 명세에 없음
- 노선·운영기관 범위:
  - 대중교통 노선·운영기관 단위 데이터가 아님
  - 도로 LINK_ID와 TM 좌표 기반이며 버스 노선 영향은 별도 공간 결합으로 계산
- 제공 기간:
  - 호출 시점에 API가 반환하는 도로 돌발 이벤트 스냅샷
  - 활성·예정·종료 이벤트의 정확한 포함·소멸 규칙은 미공개
  - 날짜 검색 인자가 없으므로 임의 과거 기간을 조회할 수 없음
  - 공개일자 2016-08-17은 API 공개일이며 2016년 이후 이력 제공을 뜻하지 않음
  - 샘플에는 발생일이 오래된 장기 공사·통제가 포함되어 있으나 일반적인 잔존 규칙으로 확정하지 않음
- 과거 이력 제공 여부: **미제공**
  - 서울 열린데이터광장 FAQ는 실시간 데이터의 과거 데이터를 별도 적재·제공하지 않는다고 안내
  - 이벤트 이력이 필요하면 소비자가 자체 폴링·스냅샷 적재해야 함
- 데이터 갱신 주기:
  - 데이터셋 페이지: 비정기(수시) - 실시간/매일
  - 서울 실시간 도시데이터 매뉴얼 V8.5 표 3-10: 서울시 실시간 돌발 정보 **5분**
  - 5분은 매뉴얼 표 3-10의 데이터 갱신주기 표기이며 가용성·전파지연 SLA는 아님
  - 표에는 데이터셋명은 직접 나오지만 OA-13315와 AccInfo 식별자는 없어 상세 페이지와 명세를 함께 대조함
- 실제 데이터 지연시간: **미확인**
  - 응답 생성시각·최종 수정시각 필드가 없음
  - OCCR_DATE/OCCR_TIME은 이벤트 발생·시작 시각이지 API 갱신시각이 아님
  - 반복 수집 시 ACC_ID별 최초 관측시각과 제공 발생시각의 차이를 참고할 수 있으나, 예정 공사와 사후 등록 이벤트가 섞일 수 있어 별도 분류가 필요

## 3. 인증 및 호출 제한

- 인증 방식:
  - 공식 명세에 문서화된 방식은 서울 열린데이터광장 발급 KEY를 URL path 첫 번째 세그먼트에 전달
  - query parameter·Authorization header 방식은 공식 계약에서 확인되지 않았으며, 미지원이라고 단정하지 않음
- API 키 발급처:
  - https://data.seoul.go.kr/together/mypage/actkeyMain.do
  - 서울시 통합회원 로그인 후 일반 인증키 신청
  - sample 키는 1~5번 행의 샘플 호출에만 사용
- 기본 일일 호출 한도: **OA-13315 전용 수치 공식 미공개**
  - 공통 안내의 일 1,000회 문구는 실시간 지하철 API에 한정되므로 이 API에 적용하지 않음
  - 한 번에 최대 1,000건이라는 행 수 제한과 일일 호출 횟수를 구분
- 초당 호출 한도: **공식 미공개**
- 호출량 증액 가능 여부:
  - 공통 안내는 이용 제약 없이 계속 사용하려면 활용사례(갤러리)에 인증키와 콘텐츠를 등록하라고 안내
  - FAQ의 심사·승인 상세 절차는 실시간 지하철 인증키 제한 문답에 명시된 내용이므로 OA-13315 적용 여부는 별도 확인 필요
  - OA-13315의 기본 한도·증액 단위·승인 기준은 공식 미공개
- 이용요금: **OA-13315별 요금 정책은 공식 명세에 표기되지 않음**
  - 데이터셋 페이지와 공통 Open API 안내에서 별도 과금표를 확인하지 못함
  - 공공누리 제1유형은 이용허락 조건이며 API 이용요금을 보장하는 문구는 아님
- 이용약관·라이선스:
  - 공공누리 제1유형: 출처표시
  - 상업적 이용과 변경 가능
  - 결과 노출 시 서울특별시 공공데이터 사용 및 출처를 표시
  - 이용약관상 인증키는 타인에게 제공·공개·공유할 수 없음

### 보안·운영 주의

- 공식 endpoint는 HTTP와 8088 포트를 사용하고 인증키가 URL path에 포함된다.
- production 도입 전 제공기관에 공식 HTTPS endpoint 존재 여부를 확인한다.
- 인증키를 프론트엔드, 저장소, 파일명, access log, proxy log, APM trace에 노출하지 않는다.
- collector backend에서만 호출하고 URL path의 KEY 구간을 마스킹한다.
- INFO-100 등 인증 오류에 키를 바꾸며 반복 호출하지 않는다.

## 4. 요청 방법

- HTTP Method: **GET**
  - 서울 열린데이터광장 공통 이용안내의 Java·JavaScript·cURL 샘플 코드가 GET을 사용
- Endpoint:

~~~text
http://openapi.seoul.go.kr:8088/{KEY}/xml/AccInfo/{START_INDEX}/{END_INDEX}/
~~~

- 응답 형식: **XML**
  - OA-13315 명세의 TYPE 허용값은 xml만 표시
  - 공식 샘플 프록시에서 json 요청은 ERROR-301 반환
- 필수 파라미터:

| 파라미터 | 설명 | 예시 | 필수 여부 |
| --- | --- | --- | --- |
| KEY | 서울 열린데이터광장 인증키 | {KEY} | 필수 |
| TYPE | 요청 파일 타입 | xml | 필수 |
| SERVICE | 서비스명, 대소문자 구분 | AccInfo | 필수 |
| START_INDEX | 요청 시작 행, inclusive | 1 | 필수 |
| END_INDEX | 요청 종료 행, inclusive | 1000 | 필수 |

### 페이지 제한

- sample 키는 START_INDEX와 END_INDEX 모두 1~5 범위만 허용
- 정식 호출은 한 번에 최대 1,000건
- 전체 건수는 list_total_count로 확인하고 1~1000, 1001~2000 형태로 나눠 호출
- 실시간 데이터가 페이지 수집 중 바뀔 수 있으므로 모든 페이지에 동일 snapshot consistency가 보장된다고 가정하지 않음

### 요청 예시

개인 인증키 호출:

~~~http
GET http://openapi.seoul.go.kr:8088/{KEY}/xml/AccInfo/1/1000/
~~~

공식 sample 키 호출:

~~~http
GET http://openapi.seoul.go.kr:8088/sample/xml/AccInfo/1/5/
~~~

2026-08-25 조사 환경에서는 openapi.seoul.go.kr:8088 직접 연결이 15초 안에 성립하지 않았다. 같은 URL을 호출하는 서울 열린데이터광장 공식 샘플 프록시는 정상 XML을 반환했으므로 API 장애가 아니라 현재 실행환경의 비표준 포트 egress 제한일 수 있다.

## 5. 응답 데이터

공식 출력표는 대문자 필드명을 사용하지만 실제 샘플 XML element는 소문자다. parser는 XML의 실제 이름을 기준으로 읽고 원문을 보존한다. 공식 명세는 데이터 필드의 엄밀한 자료형과 필수 여부를 제공하지 않으므로 아래 타입은 샘플 관측과 내부 저장 권고를 구분해 적었다.

### 공통 응답

| 필드 | 의미 | 관측 형식 | 예시 | 저장 여부 |
| --- | --- | --- | --- | --- |
| list_total_count | 정상 조회 시 전체 데이터 건수 | 정수형 텍스트 | 5 | 예, integer + raw |
| RESULT.CODE | 요청 결과 코드 | 문자열 | INFO-000 | 예 |

## 6. 시간 데이터 해석

- 제공기관 데이터 생성시각 필드:
  - 없음
  - 응답 생성시각, 최종 갱신시각, 이벤트 수정시각도 없음
- 예측시각 또는 실제시각 여부:
  - OCCR_DATE + OCCR_TIME: 공식 설명은 돌발 발생 일자·시각
  - 실제 발생시각인지 등록시각인지, 공사·행사의 계획 시작시각인지 구분하는 세부 계약은 미공개
  - EXP_CLR_DATE + EXP_CLR_TIME: **종료 예정시각**
  - 실제 해소시각이나 실제 종료 관측값이 아님
- 시간대:
  - 공식 명세에 timezone 없음
  - 서울 TOPIS 데이터이므로 Asia/Seoul 후보로 파싱하되 timezone_assumption을 provenance에 남김
  - 공식 확인 전 UTC 변환값을 원문보다 우선하지 않음
- 자정 이후 운행일 처리 방식:
  - 대중교통 운행일 개념이 아니라 calendar date 기반 이벤트
  - date와 time을 결합하며 별도 service-day 보정하지 않음
  - OCCR_TIME 샘플에 4자리 HHmm와 6자리 HHmmss가 함께 존재
  - 4자리는 초를 00으로 보완하되 raw 값을 보존
  - EXP_CLR_TIME=000000은 해당 EXP_CLR_DATE의 자정 후보이며 전일 24시로 임의 변경하지 않음
- 수집시각과 제공시각의 차이:
  - 생성·수정시각이 없어 직접 계산 불가
  - collected_at - occurrence_at은 이벤트 등록 지연과 이벤트 나이를 혼합하므로 data lag로 단정하지 않음
  - 자체 폴링의 first_seen_at을 별도 저장해 탐지 지연을 측정
- 시간표 기준인지 실제 관측값인지:
  - 시간표 데이터가 아님
  - OCCR는 사건 발생 또는 계획 통제 시작
  - EXP_CLR는 계획·예측 종료
  - 명시적 실제 종료값은 없음

> 도착시간을 제공하는 API가 아니다. OCCR는 이벤트 시작, EXP_CLR는 종료 예정이며 실제 해소시각과 구분해야 한다.

### 샘플에서 확인한 시간 품질 이슈

- OCCR_TIME 길이가 4자리와 6자리로 혼재
- 장기 통제 1건은 EXP_CLR_DATE가 20260930인데 ACC_INFO에는 2027년 9월 30일까지라고 적혀 있어 구조화 필드와 설명이 불일치
- 다른 장기 공사 2건은 설명의 23:59 종료 다음 날 00:00을 EXP_CLR_DATE/EXP_CLR_TIME으로 표현한 것으로 보임
- 구조화 필드와 자유문이 다르면 자동 수정하지 않고 conflict flag를 남긴다.

## 8. 수집 계획

- 수집 방식: **주기적 폴링**
- 수집 주기:
  - 설계안: 5분
  - 관련 공식 매뉴얼의 데이터 갱신주기 표기와 맞추되 OA-13315의 보장 SLA로 해석하지 않음
  - 실제 호출 한도 확인 전 개발환경에서는 10~15분으로 낮추고 quota 사용량 측정
- 수집 범위:
  - 매 주기 API가 반환하는 전체 목록
  - list_total_count가 1,000 초과이면 1,000건 단위 pagination
  - batch_id와 page_start/page_end를 저장
  - 페이지 수집 중 목록 변화가 감지되면 한 번 재수집해 snapshot drift 표시
- 원문 저장 여부: **예**
  - raw XML body
  - HTTP status, RESULT.CODE/MESSAGE
  - requested range, collected_at, elapsed_ms, body_sha256
  - URL은 KEY를 제거한 redacted 형태로 저장
- 저장 위치 설계안:

~~~text
raw/oa_13315/
  ingestion_date=YYYY-MM-DD/
    collected_hour=HH/
      batch_id={UUID}/
        page_start=000001.xml
~~~

- 정규화 저장:
  - incident_snapshot: 수집 batch별 관측
  - incident_revision: ACC_ID + content_hash별 변경 이력
  - incident_latest: ACC_ID별 최신 관측
  - incident_lifecycle: first_seen_at, last_seen_at, disappeared_at, reappeared_at
- 재시도 정책:
  - connection timeout·reset·HTTP 429·5xx·ERROR-500/600/601: exponential backoff + jitter, 최대 3회
  - INFO-100·ERROR-300~336: 자동 재시도 금지
  - INFO-200: 장애로 보지 않고 empty 후보로 기록하되 이전 snapshot과 급격한 차이면 1회 확인
  - timeout은 연결·응답 단계별로 분리
- 중복 판정 기준:
  - raw snapshot: batch_id + page range
  - 논리 이벤트: ACC_ID
  - revision: ACC_ID + normalized content hash
  - 같은 ACC_ID와 같은 hash의 반복 폴링은 관측 이력만 추가
  - 같은 ACC_ID의 값이 바뀌면 중복 제거가 아니라 revision 생성
  - 목록에서 사라진 사실은 실제 종료 확정이 아니므로 연속 2~3회 미관측 후 disappeared 상태로 전환

### 최초 개인키 발급 후 계약 테스트

1. 1~5 직접 호출로 HTTP status, content type, RESULT와 row 구조 저장
2. 1~1000과 다음 페이지를 호출해 list_total_count·pagination 검증
3. INFO-200 empty와 마지막 페이지의 row 부재 표현 확인
4. 같은 ACC_ID를 24시간 추적해 수정·소멸·재등장 동작 확인
5. 5분 폴링으로 first_seen delay와 응답 안정성 측정
6. 포털 인증키 관리 화면에서 일일·초당 quota와 제한 해제 절차 확인
7. HTTPS endpoint와 certificate·redirect 동작을 제공기관에 확인

### 활용 조건

- calculatedAt 이전에 수집된 최신 snapshot만 사용

- 실시간 feature의 효과는 historical-only baseline과 분리해 검증

## 10. 데이터 품질 및 제약

- 결측값 발생 조건:
  - 공식 명세가 개별 필드의 필수 여부와 null 계약을 제공하지 않음
  - LINK_ID·좌표·예정종료·설명 중 일부가 빈값 또는 누락될 가능성을 전제로 parser 구현
  - INFO-200에서는 row 자체가 없을 수 있음
- 중복 데이터 가능성:
  - 같은 이벤트가 여러 polling 응답에 반복
  - ACC_ID는 유지하면서 내용·예정종료가 변경될 수 있음
  - 페이지 수집 도중 원천 목록이 바뀌면 페이지 간 중복·누락 가능
- 잘못된 값 또는 특수값:
  - HTTP 200 안에 INFO/ERROR 코드가 포함됨
  - OCCR_TIME 4자리·6자리 혼재
  - EXP_CLR_TIME=000000
  - 매우 먼 미래의 종료 예정일
  - 구조화 종료예정과 ACC_INFO 본문 날짜 불일치
  - ACC_ROAD_CODE가 샘플에는 있지만 출력 명세에는 없음
  - XML의 CR entity, 개행, 앞뒤 공백
  - GRS80TM 좌표의 EPSG 코드·axis·unit 미공개
- 데이터 제공 제외 구간:
  - 정확한 제공 도로망·제외 도로·사건 등록 기준은 공식 명세에 없음
  - TOPIS 관리·등록 범위 밖의 누락 가능성은 운영상 가정으로만 취급
  - LINK_ID·좌표가 없는 이벤트는 경로 영향 매핑에서 제외 또는 PARTIAL 처리
- 실시간 데이터 과거 보관 여부: **포털 과거 제공 없음**
  - 자체 원문 snapshot과 revision 이력 필수
- API 장애 시 대체 데이터:
  - 마지막 성공 snapshot을 source age와 함께 제한적으로 유지
  - 오래된 snapshot을 현재 무사고로 해석하지 않음
  - 서울 실시간 도시데이터의 사고통제 현황이나 타 공식 도로 돌발 source는 coverage·스키마가 다르므로 drop-in 대체로 취급하지 않음
  - 장기 장애 시 realtimeContextCoverage=NONE과 사유 노출
- 확인된 문제:
  - 공식 endpoint가 HTTP이며 KEY가 URL path에 포함됨
  - 현재 조사환경에서 openapi.seoul.go.kr:8088 직접 연결 timeout
  - 개인키의 정상 직접 호출과 quota 미검증
  - 데이터셋 페이지 주기 표기와 별도 매뉴얼의 5분 표기를 함께 해석해야 함
  - 응답에 데이터 생성·수정시각과 명시적 상태·실제 종료시각이 없음
  - 명세 필드 대문자와 실제 XML 소문자 차이
  - ACC_ROAD_CODE 명세 누락
  - 시간 길이 혼재 및 자유문 날짜 충돌
  - 과거 조회·날짜 필터 없음

  - 모두 서울 열린데이터광장 샘플 프록시 왕복시간이며 API 서버 단독 성능이 아님
- 확인한 특이사항:
  - 공식 샘플 프록시 관측에서 응답 Content-Type은 XML
  - 공식 샘플 프록시 관측에서 application error도 HTTP 200으로 반환
  - json 요청은 ERROR-301
  - invalid key는 INFO-100
  - sample 1~6은 sample 키 전용 범위 제한 ERROR-335이며 정식 키의 1회 1,000건 제한과 별개
  - 0~0은 INFO-200
  - OCCR_TIME 4자리·6자리 혼재
  - 공식 출력표에 없는 acc_road_code 관측
  - 장기 통제 1건의 구조화 종료예정일과 ACC_INFO 날짜 불일치
  - 테스트 raw response fixture는 별도 파일로 저장하지 않았으며 본 문서에는 핵심 관측값만 기록
