## 1. 실측 — API가 실제로 허용하는 것

### 1-1. 속도 한도 (공식 문서엔 없음, Cloudflare 429)

| 호출 간격 | 시도 | 성공 | 429 | 판정 |
|---|---:|---:|---:|---|
| 1.0 s (초당 1건) | 35 | **35** | 0 | 안전 |
| 0.5 s (초당 2건) | 35 | 20 | 15 | 불가 |
| (08-31) 무대기 순차 | 40 | 23 | 17 | — |

- ~~지속 가능 속도는 초당 1건~~ **백필 실운영에서 수정(09-02 13:14~13:21 KST): 지속 한도는 분당 약 40건(0.67건/s)이다.** 35건 표본에선 버스트 허용량(약 40건) 때문에 초당 1건이 통과했지만, 25분 이상 돌리면 분당 50건 중 10건이 429로 돌아왔다. 수집기는 429가 나오면 간격을 15% 늘리고 200이 이어지면 되돌리는 적응형 간격으로 바꿨다(하한 1.0 s, 상한 3.0 s). 08-31의 "1.5~2건"은 낙관치였다.
- `Retry-After: 0`이라 헤더로 대기 시간을 알 수 없다. 429 시 **지수 백오프(2·4·8·…·60 s) + 성공 후 속도 복구**를 자체 구현해야 한다.
- 단일·벌크·range 구분 없이 **엔드포인트 공용 한도**다(08-31 확인). 벌크 1건 = 단일 1건 비용이므로 **벌크가 128배 이득**.
- **IP 단위로 확인됐다**(§9). 버스트 약 40건 + 초당 1건 보충의 토큰 버킷. IP를 더하면 그 수만큼 배가 된다.

### 1-2. 벌크·구간 규칙 (공식 문서 + 실측)

| 항목 | 규칙 | 실측 |
|---|---|---|
| 벌크 크기 | 최대 128개 | 128 OK / 129 → 400 (08-31) |
| 벌크 + 스코프 | 불가 | `@a/b` 섞으면 400 (08-31) |
| 벌크 기간 | 최대 365일 | `2024-09-01:2025-08-31` 365일 OK · `2016-01-01:2016-12-31` OK · 457일 → **400** `exceeded max days of 365 for bulk query` |
| 개별 기간 | 최대 18개월 | `2025-03-01:2026-08-31`(549일) OK · **32개월 요청 시 400이 아니라 시작일이 조용히 잘려 200**(`2024-01-01` 요청 → `start: 2025-02-28` 반환) |
| 최초 데이터 | 2015-01-10 | `2014-01-01:2015-06-30` 요청 → `start: 2015-01-10`부터 172일 반환 |
| 응답 크기 | — | 벌크 128 × 365일 = **1.90 MB**(gzip 해제 후), 1.2 s · 벌크 128 point = 14.6 KB, 0.5 s |
| 캐시 | — | `Cache-Control: public, max-age=300`(CF). 같은 URL 5분 내 재호출은 캐시 응답 |
| 데이터 갱신 | UTC 자정 직후 배치 1회 | 전일 데이터는 대략 **UTC 01:00 (KST 10:00) 이후** 안전 |
| 버전별 | 최근 7일만, 개별 호출 | 확장-01(버전 고착)용. 매주 찍으면 그때부터 이력이 쌓인다 |

**조용한 절단이 가장 위험하다.** 응답의 `start`·`end`를 요청값과 대조해 어긋나면 실패로 처리해야 한다. 안 그러면 "18개월 받았다"고 믿고 있는 채로 구간이 빈다.

## 2. 판정 — 무엇을 어떤 등급으로 받나

### 2-1. 등급

| 등급 | 대상 | 규모(상한) | 호출/바퀴 | 1 IP 소요 | 이력 | 주기 |
|---|---|---:|---:|---:|---|---|
| **A 화면 대상** | **ecosyste.ms 다운로드 순위(last-month) 상위 100,000. 스코프 포함.** 비교 묶음 후보(MVP 12개)는 전부 이 안에 든다 | 100,000 (스코프 54,606 = 54.6%, §1-5) | 스코프 54,606 개별 + 비스코프 45,394/128 = 355 벌크 = **54,961** | **15.3 h** | 백필 18개월(개별 1회·벌크 2구간), 이후 주간 | 주 1회 |
| **A′ 심층** | A 중 ecosyste.ms 상위 5,000 | 5,000 | 스코프 ~1,000 × 8구간 + 벌크 32 × 12구간 ≈ **8,400** | 2.3 h | **2015-01-10~** 전 기간 | 1회 |
| **B 비스코프 전수** | PackageVersions의 `@`로 시작하지 않는 이름 전부 | 2,685,225 | 20,979 벌크 | **5.8 h** | 백필 365일(벌크 1구간), 이후 주간 | 주 1회 (선택) |
| **C 나머지 스코프** | 스코프 − A | ~1,620,000 | — | — | 수집 안 함 | — |

- **A의 기준은 다운로드 순위 하나다.** 후보 색인(구상안 4.2)과 A는 다른 기준으로 뽑힌 집합이라 겹치지 않는 부분이 생긴다. 색인에는 있으나 A 밖인 패키지는 화면에서 `NOT_COLLECTED`로 정직하게 표시하고, 그 수를 §7-3에서 실측해 필요하면 다음 주 A에 편입한다(순위 큐 뒤에 붙이면 코드 변경 없음).
- **A가 필수, B는 선택, A′는 발표용.** MVP 화면(기능-06·09)은 A만으로 전부 채워진다. B는 코드가 A와 같고 대상 목록만 바뀌므로 A가 안정된 뒤(§5 일정) 스위치 하나로 켠다. B를 켜면 "사용자가 아무 비스코프 패키지를 입력해도 다운로드가 있다"가 된다.
- A의 처리 순서는 **ecosyste.ms 다운로드 순위 내림차순**. 창(window)이 끊겨도 큰 것부터 남는다.
- C는 요구사항 기능-16의 자료 상태로 흡수한다: `NO_DATA`가 아니라 **`NOT_COLLECTED`(수집 대상 아님)**. 0과 없음을 구분(08-31 §4-3).

### 2-2. 주간 갱신 시간표

| 요일(KST) | 무엇 | 왜 |
|---|---|---|
| 화 06:00 | deps.dev 새 스냅샷(월 21:01 UTC) → BigQuery T2 증분 → 후보 색인·순위표 재생성 → **A 대상 목록 확정** | 대상이 먼저 정해져야 큐를 만든다 |
| 화 10:00 ~ 수 09:00 | **A등급 수집** 54,961건 ≈ **23 h**(분당 40건 실측, 구간 = 직전 14일, 명시 날짜). 벌크 355건 먼저(9분), 스코프 순위 순 | 전일 데이터 UTC 01:00 이후 안정 → KST 10:00. 순위 순이라 끊겨도 상위가 남음 |
| 목 02:00~11:00 | **B등급 수집**(켠 경우, 20,979 벌크 ≈ 8.7 h) | A 다음 날. 같은 IP라 동시 실행 금지 |
| 수 오전 | Spark 적재 → `downloads/date=…` 7개 파티션 overwrite → 상태표 갱신 | 목요일 화면 반영 |

`last-week` 별칭을 쓰지 않고 **`YYYY-MM-DD:YYYY-MM-DD` 명시 구간**으로 호출한다. 별칭은 호출 시각에 따라 구간이 밀려 파티션 멱등성이 깨진다.

**재수집 겹침**: A등급은 매주 **직전 14일**을 다시 받는다(호출 수 동일 — 구간이 길어질 뿐 벌크·개별 모두 1건). npm이 과거 일자를 뒤늦게 보정하는지 공식 문서가 말하지 않으므로, 2주 겹침으로 흡수한다. 겹치는 7일의 값 변화율을 manifest에 남겨 실제로 보정이 있는지 3주 안에 알 수 있다.

```
  큐: tier A → rank 오름차순  ·  비스코프는 128개씩 묶어 벌크, 스코프는 개별
  속도: 토큰버킷 1건/s  ·  429 → 지수 백오프 2·4·8…60 s, 연속 5회면 5분 휴식
  검증: 200이어도 응답 start/end ≠ 요청이면 실패  ·  벌크 null 항목 = 미존재 패키지(NOT_FOUND)
  체크포인트: SQLite (name|chunk_id, window, status, attempts, http, fetched_at) → 중단 후 재시작 시 이어감
  출력: 원본 응답 그대로 gs://<bucket>/raw/downloads/run=YYYY-MM-DD/part-NNNN.jsonl.gz
        + manifest.json (대상 수, 호출 수, 429 수, 실패 목록, 구간, 소요, 겹침 변화율)

[Spark]
  raw jsonl → explode(downloads[]) → (date, name, downloads, tier, fetched_at)
  → downloads/date=YYYY-MM-DD/   (수집한 날짜 파티션만 overwrite — dynamic partition overwrite)
  → downloads_status/ (name, tier, first_date, last_date, last_fetched_at, status)   ← 기능-16 상태 원천
  → serving: downloads_weekly(name, week_start, downloads) 만 PostgreSQL에 적재
```

### 3-1. 원본을 저장하는 이유

BigQuery raw와 같은 원칙이다. 응답 JSON을 그대로 두면 **Spark 스키마를 바꿔도 npm을 다시 부르지 않는다.** A등급 백필 원본은 벌크 355 × 1.9 MB + 개별 54,606 × ~20 KB(549일) ≈ **1.8 GB(gzip 전)**, 압축 후 400 MB 안팎. 주간 갱신(14일)은 개별 응답이 1 KB 미만이라 100 MB 이하.

### 3-2. 스키마

**`downloads`** — 키 `(date, name)` · 파티션 `date` · 해당 날짜 파티션 overwrite (v1 2.3 유지, 컬럼 2개 추가)

| 컬럼 | 타입 | 비고 |

### 3-3. 규모 — 09-03 실측 기반 견적

실측(백필 60%, 4,121만 행): 원본 jsonl.gz **4.9 B/행**, Parquet(현재: 일 파티션·snappy) **19.9 B/행**, JSON 비압축 ≈ gz의 9.1배.
Parquet 재인코딩 실험: zstd + name 정렬 12.1 B/행 → tier·fetched_at 제외 9.5 → **월 파티션 + zstd + name·date 정렬 3.2 B/행**(일 파티션 대비 6배 절감. 730개 작은 파일이 문제였다).

|---|---:|---:|---:|---:|
| A 백필 18개월 (비스코프 45,394×730 + 스코프 54,606×549) | 63.1M | 0.31 GB | 1.25 GB | 0.20 GB |

| B 주간 증분 | 268만 × 7 ≈ 19M/주 | — |

PostgreSQL엔 `downloads_weekly`만 넣는다. A 기준 10만 × 78주 = 7.8M 행이라 인덱스 조회에 문제없다. **B의 일별 9.8억 행은 RDB에 넣지 않는다** — Parquet에 두고 DuckDB/Spark로 읽는다. 수집계획 v2 §7 "팩트는 Parquet, 화면 집계만 RDB" 원칙과 같다.

## 4. 데이터 의미 주의 (v1 §8에 추가할 것)

### 4-1. 0과 결손을 API가 구분하지 않는다

`express`의 `2016-01-01`이 **0**으로 온다. 스모크 52개에서도 **2026-07-12와 2026-08-14는 52개 전부 0**이었다(npm 전체 결손일). 규칙 적용 결과 35,788행 중 276행(0.8%)이 NULL로 바뀌었다. 2016년 1월 1일에 express가 0번 받아졌을 리 없으므로 npm 쪽 로그 결손이다. 요구사항 기능-06 "자료가 없는 기간은 0으로 보정하지 않음"과 정면으로 부딪히는데, **원천이 이미 0으로 보정해서 준다.** 조치: Spark에서 `downloads = 0`이고 전후 7일 중앙값이 1,000 이상이면 `NULL`로 바꾸고 `imputed_gap` 플래그를 남긴다. 화면에는 빈 구간으로 표시한다.

### 4-2. 시간대와 최근 일자

카운트 기준일은 UTC다. 화면의 "지난주"와 KST 주가 하루 어긋난다. 전일 데이터는 UTC 01:00 이후에야 안정되므로 **수집 구간의 끝은 항상 실행일 − 2일(UTC)**로 잡는다.

### 4-3. 다운로드는 사람이 아니다

CI·미러·봇이 섞인다. 08-31 §5의 사분면 표(선언 유지 + 다운로드 급증 = 기계)가 이걸 활용하는 방식이다. **다운로드는 트래픽, 선언은 결정**이라는 가치 명제(09-01)를 화면 문구에서 유지한다.

### 4-4. 미존재·개명 패키지

벌크 응답에서 `null`인 항목은 API가 모르는 이름이다(unpublish·오타). 개별 호출은 404. `NOT_FOUND`로 기록하고 재시도하지 않는다. deps.dev에는 있고 npm downloads에는 없는 이름이 얼마나 되는지 첫 백필 manifest에 남긴다(생존 편향의 또 다른 실측치).

## 9. [보류] 다중 IP 분산 수집 — 팀원 참여 시 (2026-09-02 실측, 전진님 결정으로 보류)

### 9-1. "계정"은 해당 없음, 한도는 IP 단위

`api.npmjs.org`는 인증이 없다. 계정을 여러 개 써도 달라지는 게 없고, 한도는 Cloudflare가 **요청 IP별**로 건다.

실측(09-02 10:18~10:21, 로컬 IP 211.192.252.135):

| 시각 | 로컬 IP (0.35 s 간격 연속 호출) | 다른 IP (같은 순간 별도 호출) |
|---|---|---|
| 0~30 s | 41건 전부 200 (버스트 허용량 소진 중) | — |
| 30 s~ | 10초당 1~3건만 200, 나머지 **429** | — |
| 61~62 s (10:19:45) | **429 연속** | `is-number`·`kind-of`·`is-plain-object` **3건 모두 200** |

한도 모양은 **토큰 버킷: 버스트 약 40건 + 초당 약 1건 보충**이다. 수집기는 초당 1건을 넘기지 않으면 429를 보지 않는다.

남은 불확실성 하나: 대조 IP는 해외 콜로를 탔을 가능성이 있다. Cloudflare 카운터는 IP를 키로 잡지만 콜로별로 따로 셀 수 있어, "한국 안의 다른 IP"가 같은 결과인지 착수일에 2분 재확인한다 — PC에서 `sat.py`를 돌려 429 상태를 만든 뒤 **폰(LTE, 와이파이 끄고)** 브라우저로 `https://api.npmjs.org/downloads/point/last-week/express`를 연다. 200이면 확정.

### 9-2. 함정 — 같은 교실은 같은 IP

SSAFY 캠퍼스 안 PC는 NAT로 **공인 IP를 공유**한다. 팀원이 옆자리에서 돌리면 IP가 하나로 합쳐져 서로 한도를 나눠 먹는다. 참여자는 먼저 `curl https://api.ipify.org`로 자기 공인 IP를 확인하고, 211.192.252.135(캠퍼스)와 같으면 **집 네트워크·폰 핫스팟·EC2** 중 하나로 옮겨야 효과가 있다.

### 9-3. IP 수에 따른 처리량

초당 1건/IP · 하루 86,400건/IP 기준.

| ① 단일 IP (현 계획) | 1 | 86k | 15.3 h | 46 h | 19.2 d | 불가 |
| ② EC2 2대 + 팀원 2명 야간 10 h | 2 상시 + 2 부분 | 245k | **5.1 h**(3 IP 동시) | **16 h** | **6.8 d** | 불가 (여유 0) |
| ③ EC2 2대 + 팀원 2명 + 전진님 집 24 h | 5 상시 | 432k | 3.1 h | 9.2 h | **3.9 d** | 이론상 가능, 권고 안 함 |

"전체를 매주"는 5 IP가 **한 주의 55%를 쉬지 않고** 돌아야 한다. PC 한 대가 꺼지면 다음 주까지 못 끝나고, npm 쪽 정책이 바뀌면 전부 무너진다. 주간 갱신을 전수에 걸지 않는다.

### 9-4. 다중 IP로 할 것 — 권고

| 우선 | 무엇 | 얻는 것 | 비용 |
|---|---|---|---|
| 1 | **A 상한 10만 → 30만** (ecosyste.ms 순위 상위 30만 ∪ 후보 색인, 스코프 포함) | 월 다운로드 수천 건 수준까지 화면 대상에 들어옴. 사용자가 입력할 만한 패키지는 거의 전부 A | 주 11 h (구성 ②) |
| 2 | **스코프 전수 1회 백필**(18개월, 09-05~09-11 야간) | C등급이 사라진다. 모든 스코프 패키지가 최소 "백필 시점까지의 18개월"을 가짐. 상태는 `STALE`(갱신 안 됨, 기준일 표시) | 1회 6.8 d (구성 ②) |
| 3 | B 비스코프 전수 주간 갱신 | 비스코프는 매주 최신 | 주 5.8 h (EC2 1대에 고정) |

이렇게 하면 화면의 자료 상태는 `READY`(A·B, 매주 갱신) / `STALE`(C, 백필 시점 고정) / `NOT_FOUND` 셋이 되고 **`NOT_COLLECTED`는 없어진다.** 기능-05-R02 "출처별 기간 표시"에 `last_date`를 그대로 쓰면 된다.

### 9-5. 협업 수집 방식 — 파이프라인 변경 최소화

```
targets/run=YYYY-MM-DD/targets.parquet  (name, scoped, rank, tier)
  → 샤딩: worker_id = rank % N  (순위 라운드로빈 → 어느 워커가 멈춰도 상위가 고르게 남음)
  → 각 참여자: python collect.py --run 2026-09-09 --worker 2 --of 4
       · 자기 샤드만, 초당 1건 토큰버킷, SQLite 체크포인트(재시작 시 이어감)
       · 출력 gs://<bucket>/raw/downloads/run=…/worker=2/part-*.jsonl.gz + manifest.json
  → Spark는 run=… 아래 worker 폴더를 전부 읽음. 스키마·파티션 변화 없음
```

참여자에게 필요한 것 세 가지: ① 저장소의 `collect.py` + 대상 파일(GCS에서 받기) ② 버킷 **objectCreator 권한만** 가진 서비스 계정 키(읽기·삭제 불가) ③ 자기 공인 IP가 캠퍼스와 다르다는 확인. 워커가 중간에 죽으면 다음 날 같은 명령으로 재시작하면 체크포인트부터 이어간다. 누락 샤드는 manifest로 바로 보이고 EC2가 대신 돌린다.

실행 예의: IP당 초당 1건은 npm이 사실상 허용하는 속도이고, 3~5 IP 합산 초당 5건은 벌크 미사용 클라이언트 하나가 내는 양과 비슷하다. 그 이상으로 IP를 늘리지 않는다. User-Agent에 프로젝트명과 연락처를 넣는다.
