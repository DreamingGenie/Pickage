## 1. 결론

- 공식 포털의 렌더링 상태와 샘플 응답을 함께 확인한 결과 OA-15799는 **활성 서비스**다. 다만 공개된 가용성·지연 SLA는 확인되지 않았으므로 운영 수집기는 실패·stale 대응을 갖춰야 한다.
- 실제 XML은 `/realtimeStationArrival/RESULT` 1개와 `/realtimeStationArrival/row` 2,920개로 구성된다.
- `RESULT.total`, 모든 행의 `selectedCount`, 모든 행의 `totalCount`, 실제 `row` 개수가 모두 `2920`으로 일치한다.
- 제공받은 XML에는 2,920개 행이 한 번에 들어 있다. 공식 일괄 URL에는 페이지 인덱스가 없지만, 파일 자체에는 실제 요청 URL이 없으므로 요청 경로는 원본 HTTP 캡처로 별도 확인해야 한다. 일반 이용안내의 “1회 최대 1,000건”과도 다르므로 **이 특수 일괄 응답에서 관측된 결과**로만 기록하고 장기 보장 계약으로 간주하지 않는다.
- `total=2920`은 역 수나 열차 수가 아니라 **도착정보 행 수**다. 실제로는 685개 노선별 역 ID, 559개 역명, 510개 열차번호가 포함됐다.
- 각 행은 `statnId` 역을 대상으로 한 도착예측이다. 동일 열차가 동일 시각에 여러 향후 역 행으로 확장되므로 `statnId`를 열차의 현재 위치로 해석하면 안 된다.
- 응답은 하나의 원자적 시각 스냅샷이 아니다. `recptnDt`가 209개 값으로 분산되고 전체 범위가 22분 26초에 달한다. 행 단위 신선도 검사가 필수다.
- `barvlDt=0`은 전체 2,920행 중 1,796행(61.5%)이며, 19개 노선 중 10개 노선에서는 모든 행이 `0`이다. 따라서 `barvlDt`를 전 노선 공통 ETA 변수로 사용할 수 없다.
- `btrainNo`에는 선행 0과 영문이 있고, `bstatnId`에는 1자리·3자리 ID가 있다. 모든 식별자는 문자열로 보존해야 한다.
- `subwayList`와 `statnList`의 항목 수가 93행에서 다르며, `statnList`에는 공백·중복·짧은 토큰이 있다. 두 목록을 위치별로 단순 결합하면 안 된다.
- 이 API로 직접 얻는 것은 확정 운행 이력이 아니라 현재 도착정보와 반복 관측이다. 실제 도착·출발시각은 품질 플래그가 붙은 **추정 이벤트**로만 생성한다.

## 3. 인증·요청·제한

### 공식 서비스 상태

- OA-15799 렌더링 화면: Open API 명세·인증키 신청·샘플 URL을 정상 표시
- 페이지 HTML 상태: `#openServ`는 `display: inline`, `#closeServ`는 `display: none`
- 상태 분기: `if('OA' == 'OC')`가 거짓이므로 종료 화면을 표시하지 않음
- 숨김 `#closeServ` 안의 `서비스 종료 안내` 문구는 공통 fallback 템플릿이며 OA-15799의 현재 상태가 아님
- 공식 샘플과 제공받은 2026-08-25 XML: 정상 본문 `INFO-000`
- 판정: `ACTIVE_NO_PUBLISHED_SLA`
- 운영 결정: 실제 키·호출 한도·신선도 계약 검증 후 수집 의존성 채택 가능

관련 OA-12764 “서울시 지하철 실시간 도착정보”는 역명별 조회 API이며, 서울시 외 구간 미제공 안내가 있어 OA-15799의 일괄·광역 범위와 계약이 다르다. 두 API를 서로의 drop-in 대체재로 간주하지 않는다.

### 요청

- HTTP Method: `GET`
- 공식 Endpoint:

```text
http://swopenAPI.seoul.go.kr/api/subway/{KEY}/{TYPE}/realtimeStationArrival/ALL
```

- `KEY`: 실시간 지하철 전용 인증키
- `TYPE`: `json`, `xml`, `xmlf`, `xls`
- `SERVICE`: `realtimeStationArrival/ALL`

공식 요청인자 표에는 `START_INDEX`, `END_INDEX`가 필수로 표시되지만, 같은 페이지의 일괄 서비스 URL과 공식 샘플 URL에는 인덱스가 없다. 제공받은 XML도 2,920행 전체 본문이다. 인덱스 경로와 전체 반환 동작은 실제 키 계약 테스트를 통과하기 전까지 운영 계약으로 확정하지 않는다.

### 호출 제한

- 기본 한도: 실시간 지하철 키 기준 1,000회/일
- 일반 이용안내: 1회 최대 1,000건
- 실제 일괄 XML 관측: 한 응답에 2,920행
- 30초 폴링: 2,880회/일 — 기본 한도 초과
- 60초 폴링: 1,440회/일 — 기본 한도 초과
- 120초 폴링: 720회/일 — 기본 한도 내

초기 수집 예산은 정규 호출 720회, 재시도·수동 검증 230회, 비상 여유 50회로 나눈다. 일일 950회에 도달하면 자동 재시도를 중단한다. 30~60초 폴링은 호출 한도 증액을 확인한 뒤에만 사용한다.

### 보안

- 인증키가 URL 경로에 있으므로 브라우저나 프론트엔드에서 직접 호출하지 않는다.
- 백엔드 수집기에서 호출하고 액세스·오류·프록시 로그의 키를 마스킹한다.
- 공식 URL은 HTTP다. HTTPS 실패를 API 자체의 영구 미지원으로 단정하지 말고 배포망에서 DNS, TLS, 프록시, 원본 응답을 분리 점검한다.
- 키를 소스코드, 분석 문서, 원시 응답 파일명에 포함하지 않는다.

구조 검증 결과:

- 루트: `realtimeStationArrival`
- 결과 메타데이터: `RESULT` 1개
- 반복 행: `row` 2,920개
- 행 필드: 모든 행에서 동일한 24개 필드
- `rowNum`: `1..2920`, 중복·누락 없음
- `selectedCount`: 모든 행에서 `2920`
- `totalCount`: 모든 행에서 `2920`
- 빈 행 필드: 이번 파일에서는 0건
- `RESULT.developerMessage`, `RESULT.link`: 빈 요소
- `list_total_count`: 실제 XML에 없음

빈 필드가 없었다는 것은 이번 파일의 관측 결과일 뿐이다. 파서는 빈 요소, 누락 요소, 공백 문자열을 모두 허용하고 원문 상태를 별도 보존해야 한다.

### JSON 호환성

공식 `sample` JSON은 `errorMessage`와 `realtimeArrivalList[]` 구조다. 샘플에는 `beginRow`, `endRow`, `curPage`, `pageRow`, `subwayNm`, `subwayHeading`, `trainCo` 같은 nullable 부가 필드가 나타날 수 있다. 이 필드들은 실제 XML의 24개 행 필드와 공식 OA-15799 출력 표에 없으므로 필수 계약으로 두지 않고, JSON 파서는 알 수 없는 부가 필드를 허용한다.

## 7. 응답 의미와 시간 해석

### 역 중심 도착예측

동일한 `subwayId+btrainNo+updnLine+recptnDt`가 여러 `statnId`에 반복된다. 최대 25개 목표 역이 같은 열차 관측에 연결됐다. 예를 들어 `1001|1605|하행|2026-08-25 10:47:49`는 현재 위치 메시지 `회룡`을 공유하면서 회룡부터 노량진까지 25개 목표 역의 행으로 반환됐다.

따라서:

- `statnId`: 도착예측 대상 역
- `arvlMsg3`: 현재 열차 위치를 나타내는 역명형 보조 메시지
- `statnFid`, `statnTid`: 대상 역 기준 인접 역
- `btrainNo`: 여러 대상 역 행을 연결하는 운행 열차번호

열차 현재 위치가 필요하면 `statnId`를 쓰지 말고, 동일 열차·방향·`recptnDt` 그룹의 `arvlMsg3`를 역 기준정보에 보수적으로 매핑하거나 실시간 열차 위치정보 API와 결합한다.

### 원자적 스냅샷이 아님

- 고유 `recptnDt`: 209개
- 최소: `2026-08-25 10:29:49`
- 최대: `2026-08-25 10:52:15`
- 범위: 22분 26초
- `subwayId+btrainNo+direction` 526개 그룹 중 113개는 내부 시각 범위가 60초 초과
- 27개 그룹은 300초 초과
- 최대 범위: 1,007초

이는 일괄 응답이 역·노선별로 갱신 시각이 다른 캐시성 데이터의 결합일 수 있음을 보여준다. 응답 전체에 하나의 `recptnDt`를 부여하지 않고 모든 품질·이벤트 판정을 행 단위로 수행한다.

### 수집시각과 공급자 시각

```text
source_lag_seconds = fetched_at_utc_or_kst - parsed_recptnDt
```

다만 다음 조건이 선행돼야 한다.

1. 수집기 호스트 NTP 동기화
2. `fetched_at`을 응답 완료 직후 단조·벽시계와 함께 기록
3. `recptnDt`를 우선 `Asia/Seoul`로 파싱하되 시간대 미명시 플래그 보존
4. 음수 lag를 0으로 덮지 않고 `future_source_time`으로 기록

파일 최종 기록시각을 임시 `fetched_at`으로 사용하면 52행의 `recptnDt`가 최대 약 162초 미래이며 모두 `subwayId=1077`에서 나타난다. 이 값은 파일 시각과 공급자 시계의 차이일 수 있으므로 실제 지연 SLA로 해석하지 않는다. 기존의 `max(0, barvlDt - source_lag_seconds)` 보정은 시계 동기화와 노선별 `barvlDt` 가용성을 확인한 뒤에만 적용한다.

## 8. 데이터 품질

### 식별자

- `statnId`, `statnFid`, `statnTid`: 이번 파일에서는 모두 10자리 숫자 문자열
- `btrainNo`: 510개 고유값
    - 선행 0 행: 383개
    - 영문 포함 행: 73개, 예: `A1011`, `A2059`
    - 길이: 1·2·4·5자리
- `bstatnId`:
    - 10자리: 2,886행
    - 3자리: 28행, GTX-A `346`, `351`, `353`, `356`
    - 1자리: 6행, 5호선 방화 `1`

숫자로 보이는 값도 정수 변환 후 다시 식별자로 사용하지 않는다. 내부 표준 ID와 제공자 원문 ID를 분리한다.

### 목록 필드

- `subwayList`·`statnList` 항목 수 불일치: 93행
- 대표 예: 김포공항 `subwayList=1005,1009,1065,1093`, `statnList=1005000512,1009000902,1065006505`
- `statnList` 토큰:
    - 쉼표 뒤 선행 공백이 포함된 토큰 33개 — split 후 trim 필요
    - 짧은 `106500` 토큰 3개
    - 서울역 목록에서 동일 `1001000133` 중복 3건

처리 규칙:

1. 원문 문자열 보존
2. 쉼표 분리 후 trim
3. 토큰 형식 검증
4. 중복 제거본을 별도 생성
5. 두 목록을 배열 위치로 zip하지 않음
6. 공식 역·노선 기준정보로 독립 매핑

### 중복과 정렬

- 완전히 동일한 XML 행: 0건
- `subwayId+btrainNo+statnId+updnLine+arvlCd+recptnDt` 중복: 0건
- `rowNum`: 중복·누락 없이 연속이나 의미 기반 정렬 계약은 아님
- 동일 열차가 여러 대상 역에 반복되는 것은 정상적인 fan-out이며 중복 제거 대상이 아님

### `barvlDt`

- 범위: `0..2640`
- 중앙값: `0`
- 0인 행: 1,796개(61.5%)
- 8호선·GTX-A·경의중앙선·공항철도·경춘선·수인분당선·신분당선·경강선·서해선·신림선의 10개 주 노선 ID에서 100% 0

`barvlDt` 품질 플래그를 다음처럼 둔다.

- `eta_available`: `barvlDt > 0`
- `eta_zero`: `barvlDt == 0`
- `eta_line_unsupported`: 최근 관측창에서 해당 노선의 양수 비율이 임계값 미만
- `eta_stale`: `recptnDt` 신선도 임계값 초과
- `eta_conflict`: 상태·메시지·ETA가 상충

### 막차

`lstcarAt`은 2,920행 모두 `0`이었다. 공식 값 `1`은 이번 오전 표본으로 검증되지 않았다. 막차 로직은 심야 표본을 확보하기 전까지 운영 판단에 사용하지 않는다.

## 9. 수집·저장 계약

### 수집 메타데이터

응답마다 다음을 저장한다.

```text
fetch_id
requested_at
headers_received_at
body_completed_at
http_status
content_type
content_length
body_sha256
api_result_code
api_result_status
api_result_total
parsed_row_count
parse_status
collector_clock_sync_status
```

`api_result_status`와 `http_status`를 섞지 않는다. `api_result_total`, 실제 행 수, 모든 `selectedCount`, 모든 `totalCount`가 일치하는지 검증한다.

### 원문 저장

```text
raw/subway-arrival-bulk/ingestion_date=YYYY-MM-DD/hour=HH/fetched_at={timestamp}.{json|xml}.gz
```

원시 파티션은 `service_date`가 아니라 `ingestion_date` 기준으로 만든다. `service_date`는 자정 이후 운행 규칙과 시각표를 적용한 후 생성한다.

### 키 설계

- 원시 행 PK: `fetch_id + rowNum`
- 역 도착예측 관측키 후보:

```text
subwayId + statnId + updnLine + btrainNo + bstatnId + recptnDt + ordkey
```

- 열차 위치 메시지 그룹 후보:

```text
subwayId + btrainNo + updnLine + recptnDt + arvlMsg3
```

`btrainNo`만으로는 PK를 만들지 않는다. 날짜·노선·방향뿐 아니라 동일 응답 안의 여러 목표 역 fan-out과 시각 차이를 구분해야 한다.

### 품질 플래그

```text
transport_ok
envelope_ok
row_count_match
row_field_missing
future_source_time
stale_source
eta_available
eta_zero
eta_line_unsupported
list_count_mismatch
invalid_station_list_token
non_atomic_snapshot
last_train_unverified
```

### 재시도

- 연결 실패·5xx·`ERROR-500/600/601`: 지수 백오프와 지터, 일일 예산 안에서 재시도
- 인증·파라미터 오류: 재시도 금지, 알림
- 동일 본문 해시: 원문 보존 정책에 따라 참조만 남기거나 압축 중복 제거
- 부분 본문: XML 파싱 실패, 바이트 수·해시와 함께 격리
