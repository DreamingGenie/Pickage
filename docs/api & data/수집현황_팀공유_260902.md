# OSS Shift 데이터 수집 현황 (팀 공유용)

작성 2026-09-02 · 작성자 전진 · 원천 Google deps.dev BigQuery 공개 데이터셋 `bigquery-public-data.deps_dev_v1`

이 문서는 "무엇을 받았고, 무엇은 안 받았고, 왜 그렇게 나눴는지"를 팀원이 처음 읽어도 따라올 수 있게 정리한 것이다. 세부 설계와 실측 근거는 리포의 `docs/api & data/수집계획_BigQuery_Parquet_v2_260902.md`에 있다.

## 1. 한 장 요약

- 원천 데이터셋은 **16개 테이블, 약 518 TiB**다. 우리는 그중 **4개 테이블**만 쓴다.
- **3개 테이블은 최신 스냅샷(2026-08-31) 하나만** 받았다. 한 스냅샷 안에 2010년부터의 전체 발행 이력이 들어 있어서 과거 스냅샷이 필요 없다.
- **1개 테이블(`Projects`, GitHub 별·이슈 수)은 229개 스냅샷 전부** 받았다. 이 값만 "그 주에 몇 개였나"라는 시점 측정값이라 과거를 복원할 수 없다.
- BigQuery 과금은 **누적 약 105 GiB**로, 월 무료 한도의 약 18%다. 유료 예산($100)은 쓰지 않았다.
- 받은 Parquet는 GCS `gs://oss-shift-a506-raw/raw/`에 있고 총 **약 31 GB**다.

### `Dependents`를 안 받은 이유

원래 계획의 핵심 테이블이었다. 그런데 이 테이블은 **클러스터 키가 없어서** npm 한 스냅샷을 읽는 데 650 GiB가 들고, 패키지 하나(`moment`)로 좁혀도 똑같이 650 GiB다. 스냅샷 177개를 다 받으면 112 TiB, 약 $700이다.

대신 `NPMRequirements` + `PackageVersions`로 **같은 표를 우리가 직접 계산**한다. `Dependents`는 deps.dev가 "어떤 버전이 있고(PackageVersions) 각 버전이 뭘 선언했나(NPMRequirements)"를 조합해 매주 만들어 두는 결과물이라, 원재료를 받으면 어느 시점에 대해서든 재계산할 수 있다. 원재료 두 개를 합쳐 42 GiB다.

## 3. 왜 어떤 건 스냅샷 하나면 되고 어떤 건 전부 받아야 하나

deps.dev는 매주 월요일 전체를 다시 긁어 스냅샷을 만든다. 2022-05-08부터 229개가 있다. 여기서 헷갈리기 쉬운 점이 있다.

**npm 버전은 발행 후 수정할 수 없다.** 2023년에 나온 `foo@1.2.0`의 package.json 선언은 2023년 스냅샷에서 보든 2026-08-31 스냅샷에서 보든 같은 행이다. 그래서 최신 스냅샷 하나에는 2010년부터 지금까지 발행된 모든 버전(7,856만 개)의 선언과 발행시각이 다 들어 있다. "2023년 4월 시점에 누가 moment를 쓰고 있었나"는 최신 스냅샷에서 "2023년 4월 이전에 발행된 버전 중 각 패키지의 최고 버전"을 고르면 복원된다.

반면 **GitHub 별 수는 시점 측정값**이다. 최신 스냅샷에는 지금 별 수만 있고 2년 전 별 수는 없다. 시계열을 원하면 그 주의 스냅샷을 받아야 한다. 다행히 `Projects`는 스냅샷당 0.1~0.3 GiB라 229개 전부 받아도 50 GiB다.

| 컬럼 | 최신 스냅샷 하나로 과거 복원 | 출처 |
|---|---|---|
| 누가 무엇을 언제부터 의존했나 | 가능 | T0 |
| 패키지의 마지막 릴리스 시각 | 가능 | T0 |
| 별 수, 미해결 이슈 수 | **불가** | T1 (전 스냅샷) |
| 폐기(deprecated) 여부 | 지금 값만 가능. "언제 폐기됐나"는 불가 | T0 (과거 시점 값은 T3 선택) |

## 4. 수집 계층 (Tier)

| Tier | 내용 | 주기 | 스캔 | 상태 |
|---|---|---|---|---:|
| **T0 핵심** | 최신 스냅샷 4테이블 (`PackageVersions` · `NPMRequirements` · `PackageVersionToProject` · `Projects`) | 1회 | 52.7 GiB | **완료 09-02** |
| **T1 백필** | `Projects` 옛 스냅샷 228개 (2022-05-08 ~ 2026-08-24) | 1회 | 50.5 GiB | **완료 09-02** |
| **T2 주간 증분** | 새 스냅샷마다 `NPMRequirements` + `PackageVersions`(최소 열) + `Projects` | 매주 화 | 약 23 GiB/주 | 첫 회 09-09 |
| **T2m 월간 갱신** | `PackageVersions` 전체 열(설명·라이선스·링크) + `PackageVersionToProject` | 월 1회 | 약 35 GiB | 10월 초 |
| **T3 선택** | `PackageVersions`의 폐기 표시를 스냅샷마다 받아 "언제 폐기됐나" 복원 | 1회 | 449 GiB | **보류** |

T2에서 설명·라이선스·링크 열을 빼는 이유: 이 세 열이 `PackageVersions` 스캔 24 GiB 중 19 GiB를 차지하는데 주 단위로 바뀔 일이 거의 없다.

T3를 보류한 이유: 449 GiB로 무료 한도를 넘기고, 얻는 건 "과거 시점의 폐기 여부" 하나다. 마감까지 화면에 쓸 계획이 없어 미뤘다. 필요해지면 4주 간격 스냅샷만 받는 절충안(114 GiB)이 있다.

### BigQuery 밖에서 따로 받는 것

**npm 다운로드 수**는 deps.dev에 없다. npm 공식 API로 별도 수집 중이며 문서는 `docs/api & data/수집계획_downloads_npmAPI_260902.md`다.

## 6. 과금 105 GiB인데 받은 파일은 31 GB인 이유

두 숫자가 재는 게 다르다.

**BigQuery 과금(스캔량)**은 "쿼리가 읽은 열의 논리적(압축 전) 크기"다. `Projects` 한 스냅샷의 별 수를 뽑으려면 `SnapshotAt`·`Type`·`Name`·별·포크·이슈 여섯 열을 520만 행만큼 읽어야 하고, 그 논리적 크기가 0.22 GiB다. 229번이면 50 GiB다.

**받은 Parquet 크기**는 그 결과를 압축해 저장한 것이다. Parquet는 열마다 사전 인코딩과 Snappy 압축을 걸기 때문에 `GITHUB`처럼 반복되는 값이나 저장소 이름 같은 문자열이 크게 줄어든다. 그래서 `Projects`는 스캔 50.5 GiB → 파일 17.5 GB(약 3배 압축)가 됐다.

T0는 차이가 더 크다(스캔 52.7 GiB → 파일 13.7 GB). 압축 외에 두 가지가 더 있다. 첫째, 읽은 열을 다 내보내지 않는다. `PackageVersions`의 `Links` 배열은 통째로 읽히지만 우리는 그 안의 소스 저장소 URL 하나만 뽑는다. 둘째, `System = 'NPM'` 필터로 npm 행만 내보내지만 스캔은 그 필터를 적용하기 위해 읽은 블록 단위로 계산된다.

정리하면 **과금은 "읽은 양", 파일 크기는 "남긴 양의 압축본"**이다. 과금은 항상 파일보다 크고, 이 비율(3~4배)이 앞으로 T2 증분에도 그대로 적용된다.

## 7. 받은 데이터의 형태와 위치

```
gs://oss-shift-a506-raw/raw/
  versions_full/snapshot=2026-08-31/   362 파일 · 4.5 GB · 78,559,731 행
  requirements/snapshot=2026-08-31/    790 파일 · 6.9 GB · 78,559,731 행
  pkg_project/snapshot=2026-08-31/     200 파일 · 2.5 GB · 106,450,418 행
  projects/snapshot=2022-05-08/ … snapshot=2026-08-31/   229 폴더 · 17.5 GB
```

- 폴더마다 `_MANIFEST.json`이 있다. BigQuery 잡 ID, 스캔·과금 바이트, 행 수, 검증 결과가 들어 있어 "이 폴더가 완전한가"를 확인하는 기준이다.
- `snapshot=YYYY-MM-DD` 폴더명은 Spark·DuckDB가 파티션 컬럼으로 자동 인식한다.
- `requirements`의 `Dependencies`·`PeerDependencies`·`OptionalDependencies`는 중첩 배열(`list<struct<Name, Requirement>>`) 그대로 들어 있다. 펼치는 건 Spark에서 한다.
- `pkg_project`는 한 패키지에 저장소가 여러 개 붙을 수 있다(예: express는 visionmedia·strongloop·expressjs 세 이름). `RelationType = 'SOURCE_REPO_TYPE'`만 쓰고 버전 단위로 조인해야 한다.

### 내려받기

Google Cloud SDK 설치 후 본인 Google 계정으로 `gcloud auth login`. 버킷 읽기 권한은 전진에게 요청(계정별로 부여).

```bash
gcloud storage rsync -r gs://oss-shift-a506-raw/raw ./data/raw
```

약 31 GB. `rsync`라 두 번째부터는 바뀐 파일만 받는다. `data/`는 `.gitignore`에 있어 커밋되지 않는다.

### 바로 열어보기 (DuckDB)

```sql
SELECT snapshot, COUNT(*) FROM read_parquet('data/raw/projects/snapshot=*/part-*.parquet', hive_partitioning=true) GROUP BY 1 ORDER BY 1;
```

## 8. 데이터를 읽을 때 알아둘 제약

- **npm에 공개된 패키지만** 있다. 사내 앱·비공개 코드는 없다. "라이브러리 생태계의 채택"으로 읽어야 하고, 총 사용량은 다운로드 수가 맡는다.
- **지금 스냅샷에 남아 있는 버전만** 있다. 과거에 있었다가 삭제(unpublish)된 버전은 안 보인다.
- 의존 선언은 **요구조건 원문**(`^5.0.0`)이다. 실제 설치되는 구체 버전이 아니다. major 단위 집계는 정확하고, 해석 불가 비율은 1% 미만이다.
- `Projects`의 별·이슈는 **2022-05-08 이후**만 있다. 그 이전 시점은 NULL이다.
- 폐기 표시는 "지금 폐기됐나"만 있다. "언제 폐기됐나"는 T3를 하기 전까지 모른다.
- 스냅샷은 주 1회(월요일)다. 화면에 항상 기준일을 표시한다.

## 9. 수집 도구

리포 `pipeline/collectors/bigquery/collect.py`. 실행 전 dry-run으로 스캔량을 재고, 테이블별 상한과 세션 예산을 넘기면 시작 전에 멈춘다. 잡마다 BigQuery 과금 상한을 걸어 예상보다 큰 잡은 거부되며(과금 없음), 끝난 폴더는 `_MANIFEST.json`으로 표시해 중단 후 재실행 시 이어서 받는다. 실행 기록은 `pipeline/collectors/bigquery/ledger/ledger.jsonl`.
