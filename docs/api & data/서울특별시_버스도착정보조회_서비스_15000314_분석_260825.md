  - `mkTm`과 수집시각을 함께 저장해 신선도를 판정한다.
  - 장기간 반복 수집한 경우에만 별도의 품질 플래그를 붙여 관측 기반 배차간격 추정 후보를 만든다.
  - 이 API만으로 목적지까지의 도착확률이나 출발 추천을 계산하지 않는다. 경로, 환승, 보행, 과거 WAIT/RIDE 분포가 별도로 필요하다.
- 적용 기능:
  - [x] 현재 출발 시 도착확률 — **조건부 실시간 보정 입력**

## 2. 제공 범위

- 지역 범위: 서울특별시 버스 도착정보 서비스. 공식 메타데이터의 공간범위는 `-`로 미기재되어 있다.
- 노선·운영기관 범위:
  - 활성 `busRouteId`로 조회되는 노선과 그 경유 정류소.
  - `routeType` 코드에는 공용·공항·마을·간선·지선·순환·광역·인천·경기·폐지·한강 유형이 열거되어 있다.
  - 인천·경기 코드가 존재한다는 사실만으로 해당 지역 모든 노선이 제공된다고 간주하지 않는다.
- 제공 기간: 조회시점의 현재 도착예정 정보만 제공. 날짜 범위 파라미터가 없다.
- 과거 이력 제공 여부: 제공하지 않음. 공식 4개 기능에 이력 조회 기능이 없다.
- 데이터 갱신 주기: 공식 활용가이드 기준 **매 10초**.
- 실제 데이터 지연시간: 공식 보장값 없음.
  - 가이드의 평균 응답시간 `100 ms`는 서버 처리 성능 명세이며 원천 관측의 신선도 보장이 아니다.
  - 운영 시 `received_at - mkTm`을 별도로 측정해야 한다.
- 서비스 상태:
  - 공공데이터포털은 2025-12-02 수정 명세와 활용신청 화면을 제공한다.
  - 서울 열린데이터광장 OA-1091 원본 HTML도 상태값 `OA`, `openServ=inline`, `closeServ=none`으로 활성 화면을 선택한다.
  - 판정은 `ACTIVE_SUCCESS_RESPONSE_UNVERIFIED`: 공식 페이지는 활성으로 확인했지만 유효키 정상 데이터 행은 아직 검증하지 못했다.

## 3. 인증 및 호출 제한

- 인증 방식: 공공데이터포털 발급 서비스키를 쿼리 파라미터 `serviceKey`로 전송.
- API 키 발급처: [공공데이터포털](https://www.data.go.kr)에서 활용신청 후 발급.
- 승인 방식: 개발단계 자동승인 / 운영단계 자동승인.
- 기본 일일 호출 한도:
  - 공개 상세 페이지 표기: 개발계정 `1,000`.
  - 프로젝트가 2026-08-23 콘솔에서 확인한 값: 4개 상세기능 각각 `1,000/day`.
  - 수집기는 일단 **상세기능별 일 1,000회**로 예산을 관리하되, 현재 계정의 실제 콘솔 한도를 배포 전에 다시 확인한다.
- 초당 호출 한도:
  - 첨부 활용가이드의 기능별 성능 명세: 최대 `30 TPS`.
  - 공개 포털 본문에는 계정별 숫자가 없고 초당 한도 초과 오류 `23`만 명시되어 있다.
  - 따라서 `30 TPS`를 보장된 개인키 한도로 간주하지 않고, 계정 콘솔·실호출 결과를 우선한다.
- 호출량 증액 가능 여부: 가능. 운영계정에서 활용사례 등록 후 트래픽 증가 신청.
- 이용요금: 무료.
- 이용약관·라이선스: 공공저작물 출처표시 제1유형.
  - 출처에 `서울특별시`, 데이터명과 공식 URL을 표시한다.
  - 호출권한, 화면 표시, 캐시, 원문 장기보존, 파생데이터 보존, 재배포 권한은 동일하지 않다.
  - 표준 메타데이터와 서울 열린데이터광장의 제3자 권리 표기가 완전히 일치하지 않으므로, 원문 장기보존·재배포는 `ProviderPolicyRegistry` 확인 전 기본 금지한다.
- 보안 제약:
  - 공식 가이드는 `http://` 서비스 URL과 SSL 미지원으로 명시한다.
  - 키를 프런트엔드에 넣지 않고 백엔드 수집기에서만 사용한다.
  - 요청 URL 전체와 `serviceKey`를 애플리케이션·프록시·CI 로그에 남기지 않는다.

## 4. 요청 방법

- HTTP Method: `GET`
- Base Endpoint: `http://ws.bus.go.kr/api/rest/arrive`
- 응답 형식:
  - XML: 공개 포털에 명시된 기준 형식.
  - JSON: 첨부 활용가이드의 선택 파라미터 `resultType=json`에 명시되어 있으나 유효키 실응답 미검증.
  - CSV: 미지원.

### 상세기능

| 기능 | Endpoint | 필수 파라미터 |
| --- | --- | --- |
| 경유노선 전체 정류소 도착예정정보 | `/getArrInfoByRouteAll` | `serviceKey`, `busRouteId` |
| 특정 정류소·노선 도착예정정보 | `/getArrInfoByRoute` | `serviceKey`, `stId`, `busRouteId`, `ord` |
| 특정 정류소·노선 저상버스 도착예정정보 | `/getLowArrInfoByRoute` | `serviceKey`, `stId`, `busRouteId`, `ord` |
| 정류소별 저상버스 도착예정정보 | `/getLowArrInfoByStId` | `serviceKey`, `stId` |

가이드의 기능명에는 `getArrInfoByRouteAllList`처럼 `List`가 붙지만 실제 요청 URL에는 붙지 않는다.

### 파라미터

| 파라미터 | 설명 | 예시 | 필수 여부 |
| --- | --- | --- | --- |
| `serviceKey` | 공공데이터포털 인증키. 전송 시 URL 인코딩을 한 번만 적용 | `{URL_ENCODED_SERVICE_KEY}` | 필수 |
| `busRouteId` | 노선 ID, 문서상 9자리 | `100100118` | 기능별 필수 |
| `stId` | 정류소 고유 ID, 문서상 9자리 | `111000299` | 기능별 필수 |
| `ord` | 해당 노선에서 요청 정류소의 순번 | `1` | 기능별 필수 |
| `resultType` | 응답 형식. 가이드 기준 `xml` 또는 `json` | `json` | 선택 |

`serviceKey`는 공개 포털 요청표의 소문자 표기를 기준으로 한다. 가이드 URI 예시의 `ServiceKey` 대문자 표기는 명세 불일치로 기록한다.

### 요청 예시

```http
GET http://ws.bus.go.kr/api/rest/arrive/getArrInfoByRouteAll?serviceKey={URL_ENCODED_SERVICE_KEY}&busRouteId=100100118&resultType=json
```

실제 서비스키가 포함된 완성 URL은 로그·문서·브라우저 히스토리에 저장하지 않는다.

| `goal1`, `goal2` | 종점 도착까지의 예정시간(초) | String → Integer | `0` | 예, 의미 재검증 |
| `nstnId*`, `nstnOrd*`, `nstnSec*` | 다음 정류소 ID·순번·예정여행시간 | String | `0` | 예, 단위 검증 후 사용 |
| `nmain*`, `nmain2*`, `nmain3*` | 최대 3개 주요 정류소의 ID·순번·예정여행시간 | String | `0` | 예, 원문 필드명 보존 |
| `traSpd1`, `traSpd2` | 명세상 여행속도(km/h) | String → Decimal | `0` | 예, 실측 검증 전 모델 제외 |
| `traTime1`, `traTime2` | 명세상 여행시간(분) | String → Decimal | `0` | 예, 단위 검증 전 모델 제외 |
| `isArrive1`, `isArrive2` | 최종 정류소 도착 상태(0 운행중, 1 도착) | String → Boolean | `0` | 예 |
| `isLast1`, `isLast2` | 막차 여부 | String → Boolean | `0` | 예 |
| `busType1`, `busType2` | 차량유형(0 일반, 1 저상, 2 굴절) | String → Enum | `0` | 예 |
| `full1`, `full2` | 만차 여부 | String → Boolean | `0` | 예 |
| `nextBus` | 명세상 막차운행 여부 | String → Enum | `Y` | 예, `isLast*`와 교차검증 |

### 제공기관 업무 결과 코드

정상 데이터 행은 HTTP 상태와 아래 `headerCd`를 함께 검사해 판정한다. 공개 포털의 게이트웨이 오류코드 `01`, `04`, `05`, `10`, `12`, `20`, `22`, `23` 등과 활용가이드의 제공기관 업무코드 `0`~`8`은 서로 다른 계층이다.

| `headerCd` | 의미 | 수집기 처리 |
| --- | --- | --- |
| `0` | 정상 | `itemCount`와 본문 파싱 |
| `1` | 시스템 오류 | 제한된 재시도 후 격리 |
| `2` | 잘못된 질의 | 재시도하지 않고 요청 검증 |
| `3` | 정류소 없음 | ID 매핑·유효기간 확인 |
| `4` | 노선 없음 | ID 매핑·폐지 여부 확인 |
| `5` | 잘못된 위치 좌표 | 해당 기능 입력 검증 |
| `6` | 실시간 정보 조회 불가 | 제한된 재시도 후 historical-only 전환 |
| `7` | 노선 검색 결과 없음 | 정상 무결과와 요청 오류를 구분해 기록 |
| `8` | 서비스 종료 | 해당 상세기능 호출 중지 및 공식 상태 재확인 |

재차정보의 구분값은 값의 의미를 바꾼다.

- 구분 `0`: 데이터 없음
- 구분 `2`: 재차인원. `routeType=6`이면 잔여좌석수로 설명됨
- 구분 `4`: 혼잡도. 값 `0` 데이터 없음, `3` 여유, `4` 보통, `5` 혼잡

`routeType`은 가이드 기준 `0 공용`, `1 공항`, `2 마을`, `3 간선`, `4 지선`, `5 순환`, `6 광역`, `7 인천`, `8 경기`, `9 폐지`, `14 한강`이다.

### 실제 관측한 인증 오류 응답

```json
{
  "error": "Unauthorized",
  "message": "serviceKey 파라미터가 필요합니다.",
  "status": 401
}
```

정상 응답의 `headerCd`와 HTTP 상태를 각각 판정해야 한다. HTTP 200만으로 업무 성공으로 처리하지 않으며, 반대로 현재 인증 오류는 XML 업무 오류가 아니라 HTTP 401 JSON으로 반환됐다.

## 6. 시간 데이터 해석

- 제공기관 데이터 생성시각 필드: `mkTm`(제공시각).
- 보조 시각 필드:
  - `repTm1`: 첫 번째 차량 최종 보고시각. 활용가이드에만 확인되어 실제 응답 존재 여부 재검증 필요.
  - `firstTm`, `lastTm`: 예시상 `yyyyMMddHHmmss` 형식의 첫차·막차 기준시각.
- 예측시각 또는 실제시각 여부:
  - `exps*`, `kals*`, `neus*`, `goal*`, `nstnSec*`, `nmain*Sec*`는 **미래 도착·여행시간 예측값**이다.
  - 절대 도착시각이 아니라 조회 기준 잔여 초 값으로 해석한다.
  - `arrmsg*`는 표시 문구이며 정규화된 실제 이벤트 시각이 아니다.
  - `isArrive*`는 최종 정류소의 상태값이지 도착시각이 아니다.
- 시간대: 공식 문서 미기재.
  - 프로젝트에서는 서울 서비스라는 맥락에 따라 `Asia/Seoul`로 파싱하되 `TIMEZONE_UNDOCUMENTED` 품질 플래그를 유지한다.
  - 제공기관 확인 전 UTC 변환값을 무조건 확정 사실로 취급하지 않는다.
- 자정 이후 운행일 처리 방식: 공식 명세 없음.
  - `provider_calendar_date`와 프로젝트의 `service_date`를 분리 저장한다.
  - 자정 이후 첫·막차를 임의로 전날 운행일에 붙이지 않는다.
- 수집시각과 제공시각의 차이:
  - `source_lag_ms = received_at - mkTm`으로 계산한다.
  - 요청 시작·응답 수신·파싱 완료 시각을 각각 `requested_at`, `received_at`, `parsed_at`으로 저장한다.
  - 음수 또는 비정상적으로 큰 차이는 시계 불일치·stale 응답으로 플래그한다.
- 시간표 기준인지 실제 관측값인지:
  - `firstTm`, `lastTm`, `term`: 운행 기준 또는 계획 성격의 값.
  - `mkTm`: 제공기관이 응답을 생성·제공한 시각.
  - `exps*`, `kals*`, `neus*`, `goal*`: 실시간 상태를 반영한 **예측값**.
  - 실제 정류소 도착·출발시각: 제공하지 않음.

> 이 API의 도착시간은 실제 관측 도착시각이 아니라 예측 잔여시간이다. 반복 관측으로 만든 도착·출발 이벤트도 정확한 시각이 아니라 관측 간격에 갇힌 interval-censored 추정값으로만 저장한다.

추가로 `traTime*`는 가이드에서 분 단위로 설명하지만 다른 초 단위 필드와 샘플값의 관계가 불명확하다. `nstnSpd*`도 필드명은 속도를 암시하지만 설명은 예정여행시간이다. 두 그룹은 유효키 실측 전 모델 입력에서 제외한다.

## 7. 식별자

- 노선 식별자: `busRouteId`.
  - 숫자처럼 보여도 문자열로 보존한다.
  - 노선 표시명은 `busRouteAbrv`, `rtNm`으로 별도 저장한다.
- 차량·열차 식별자: `vehId1`, `vehId2`.
  - `plainNo1`, `plainNo2`는 표시용 차량번호이며 내부 기본키로 쓰지 않는다.
  - 차량번호 보관·노출 범위는 접근·보존 정책을 별도 적용한다.
- 정류장·역 식별자:
  - 기본 제공자 키: `stId`.
  - 이용자 안내 번호: `arsId`.
  - 이름 `stNm`만으로 결합하지 않는다.
- 방향 식별 방식:
  - 명시적 방향 설명 `dir`, 노선 내 순번 `staOrd`, 노선의 정류소 순서 조합으로 식별한다.
  - `dir` 문자열 하나만 방향 코드로 사용하지 않는다.
- 다른 API와 ID가 동일한지:
  - 공식적으로 동일성이 보장되지 않는다.
  - 같은 서울시 TOPIS 계열 버스 위치·노선·정류소 API와도 샘플 교차검증 전에는 동일하다고 가정하지 않는다.
- 내부 표준 ID 매핑 필요 여부: 필요.
  - `canonical_route_crosswalk(provider, busRouteId, valid_from, valid_to, mapping_version)`
  - `canonical_stop_crosswalk(provider, stId, arsId, valid_from, valid_to, mapping_version)`
  - 차량은 장기 고정 식별자로 가정하지 않고 관측 범위의 제공자 ID로 보존한다.

## 8. 수집 계획

- 수집 방식: **백엔드 주기적 폴링 + 사용자 요청 병합**.
  - 브라우저가 공급자 API를 직접 호출하지 않는다.
  - 같은 노선·정류소 요청은 짧은 캐시 창 안에서 합쳐 호출량을 줄인다.
- 수집 주기:
  - 공식 생성 주기: 10초.
  - 개발계정 사전실험: 한 상세기능·한 노선을 120초 간격으로 24시간 수집하면 최대 720회/일이다. 남은 약 280회는 검증·오류·재시도 예산으로 둔다.
  - 출퇴근 8시간 집중 실험을 30초 간격으로 수행하면 노선당 960회/일이므로 한도를 거의 모두 사용한다.
  - 다노선 10~20초 수집은 호출량 증액과 서버 측 중앙 예산 관리가 완료된 후에만 수행한다.
  - 계산식: `예상 호출량 = ceil(수집창 초 / 폴링 간격 초) × 대상 노선 수`.
- 수집 범위:
  - 1단계: 검증용 대표 노선 1개, `getArrInfoByRouteAll`.
  - 2단계: 모델 평가 대상 노선·시간창만 allow-list로 확대.
  - 저상버스 전용 기능은 제품 요구가 생길 때 별도 quota와 품질을 평가한다.
- 원문 저장 여부: **정책 확인 전 영구 저장 금지**.
  - 허용 시 응답 body와 HTTP 상태·선별 헤더·요청 파라미터의 비밀 제거본·body SHA-256을 불변 스냅샷으로 저장한다.
  - 인증키와 완성 요청 URL은 저장하지 않는다.
- 저장 위치: 정책 승인 시 논리 경로
  - `bronze/seoul_bus_arrival/service_date=YYYY-MM-DD/hour=HH/endpoint={operation}/{fetch_id}.{xml|json}.gz`
  - 정규화 테이블과 모델용 파생 테이블은 원문 스냅샷과 분리한다.
- 저장 메타데이터:
  - `provider`, `endpoint`, `request_id`, `requested_at`, `received_at`, `parsed_at`, `mkTm`, `http_status`, `headerCd`, `body_sha256`, `collector_version`, `policy_status`.
- 재시도 정책:
  - 연결 실패, timeout, HTTP 5xx, 게이트웨이 오류 `01`, timeout 오류 `05`, 일시적 실시간정보 조회 실패는 지수 백오프와 jitter로 최대 2회 재시도.
  - HTTP 401, 키·권한·파라미터·노선·정류소 오류는 재시도하지 않고 설정 오류로 격리.
  - 일일 한도 오류 `22`는 해당 quota window 종료까지 중단.
  - 초당 한도 오류 `23`은 중앙 throttle을 낮추고 제한된 횟수만 재시도.
  - 모든 재시도도 호출량으로 계산한다.
- 중복 판정 기준:
  - 원문 중복: `SHA-256(response_body)`.
  - 행 저장키: `(fetch_id, row_index)`로 원문 재현성을 보장.
  - 의미상 동일 후보: `(endpoint, busRouteId, stId, staOrd, vehId1, vehId2, mkTm, exps1, exps2, isArrive1, isArrive2)`.
  - 같은 상태가 반복돼도 시계열 관측 증거이므로 물리 삭제하지 않고 `duplicate_of` 또는 품질 플래그로 표시한다.
- quota 보호:
  - 상세기능별 일일 ledger를 중앙화한다.
  - 검증 전 운영 상한은 950회로 두어 수동 점검·재시도 여유를 확보한다.
  - 키 회전으로 한도를 우회하지 않는다.

## 9. 전처리 및 활용

- 생성할 데이터:
  - [ ] 구간 운행시간 — 이 API의 ETA를 실제 구간 소요시간으로 저장하지 않음
  - [ ] 정차시간 — 정류소 도착·출발 실측 시각이 없어 직접 생성 불가
  - [ ] 실제 배차간격 — 직접 생성 불가. 장기 반복 관측과 차량 ID 품질을 통과한 경우 별도의 interval-censored 추정값만 후보로 생성
  - [ ] 계획 대비 지연 — 비교할 확정 운행시각표와 실제 이벤트가 이 API에 없음
  - [ ] 사고·운행장애 이벤트 — `deTourAt`은 우회 상태일 뿐 사고·장애 이벤트 피드가 아님
- 전처리 규칙:
  1. 원시 식별자와 숫자형 후보를 모두 문자열로 먼저 보존한다.
  2. `headerCd=0`과 HTTP 성공을 모두 만족한 응답만 데이터 행으로 승격한다.
  3. `mkTm`, `firstTm`, `lastTm`, `repTm1`은 서로 다른 의미의 컬럼으로 파싱한다.
  4. `exps*`, `kals*`, `neus*`, `goal*`은 초 단위 예측 후보로 분리하고 서로 대체하지 않는다.
  5. 값 `0`은 문맥에 따라 실제 0, 데이터 없음, 차량 없음, 출발대기 샘플일 수 있으므로 `vehId*`, `arrmsg*`, 상태 필드와 함께 판정한다.
  6. 혼잡·인원 값은 반드시 대응하는 `*_Div*` 구분값과 함께 해석한다.
  7. `namin2Sec1/2`처럼 공식 명세에 존재하는 오탈자 필드는 원문명을 보존하고 정규화 계층에서 `nmain2Sec*` 별칭을 둔다.
  8. `arrmsg*`의 한국어 문구 파싱은 보조 규칙으로만 사용하고 숫자 ETA의 대체 진실값으로 사용하지 않는다.
  9. 반복 관측에서 차량의 순번·ETA 변화로 만든 이벤트에는 `INFERRED`, 관측 시작·종료시각, interval width, rule version을 저장한다.
  10. `source_lag_ms`가 임계값을 넘거나 `mkTm`이 역행한 응답은 실시간 보정에서 제외한다. 임계값은 장기 실측 후 확정한다.
- 다른 데이터와 결합할 키:
  - 제공자 기준: `(busRouteId, stId, staOrd)`.
  - 차량 관측 기준: `(busRouteId, vehId, mkTm)`.
  - 내부 결합: `canonical_route_id`, `canonical_stop_id`, `service_date`, `direction_key`, `time_bucket`.
  - 서울시 버스 위치·노선·정류소 API, 경로 결과, 운행시각표와 결합할 때 버전이 있는 crosswalk를 사용한다.
- 모델 입력 변수 후보:
  - `eta_exps_1/2`, `eta_kals_1/2`, `eta_neus_1/2`, 예측값 간 spread.
  - `sect_ord_1/2`, `is_arrive_1/2`, `is_last_1/2`, `bus_type_1/2`, `full_1/2`.
  - 구분값을 적용한 혼잡도·재차인원·광역버스 잔여좌석.
  - `de_tour`, `route_type`, `nominal_term_min`, 시간대·요일·공휴일.
  - `source_lag_ms`, 응답 품질 플래그, 실시간 feature coverage.
  - `traTime*`, `nstnSpd*`, `repTm1`은 의미·단위·실재성 검증 전 제외.
- 제품 활용 경계:
  - Leave-now Forecast: 신선도·coverage·유효성 게이트를 통과한 실시간 feature만 historical baseline에 추가.
  - Departure Recommendation: 이 API의 현재 스냅샷은 사용하지 않음. 장기 수집으로 만든 검증된 historical artifact는 별도 provenance 아래 재평가 가능.
  - 실시간 데이터가 없거나 stale이면 historical-only 결과와 limitation을 표시한다.

## 10. 데이터 품질 및 제약

- 결측값 발생 조건:
  - 첫 번째 또는 두 번째 도착예정 차량이 없음.
  - 출발대기·운행종료·정보 미수신 상태.
  - 혼잡도·재차인원 수집 대상이 아니거나 장비 보고가 없음.
  - 저상버스 전용 조회 결과가 없음.
  - 정류소·노선 ID가 폐지·변경되었거나 요청 조합이 유효하지 않음.
- 중복 데이터 가능성:
  - 10초보다 짧게 폴링하면 같은 `mkTm`과 같은 상태가 반복될 수 있다.
  - 제공기관 갱신이 늦거나 캐시가 개입하면 서로 다른 요청도 동일 body를 반환할 수 있다.
  - 동일 차량이 노선의 여러 정류소 행에 나타날 수 있으므로 `vehId`만으로 행을 중복 처리하지 않는다.
- 잘못된 값 또는 특수값:
  - 다수 필드의 `0`은 유효한 0과 데이터 없음이 혼재할 수 있다.
  - `routeType=9`는 폐지노선 코드.
  - `deTourAt=00/11`, `nextBus=Y/N`, 혼잡 구분값은 일반 Boolean으로 무리하게 통합하지 않는다.
  - `traTime*`의 문서 단위와 샘플값 관계가 불명확하다.
  - `nstnSpd*`는 이름과 설명이 충돌한다.
  - `namin2Sec*`는 `nmain2...` 계열과 다른 공식 오탈자로 보인다.
- 데이터 제공 제외 구간:
  - 공식 명세에 완전한 제외 구간 목록이 없다.
  - 조회되지 않는 `busRouteId`와 종료·폐지 노선은 제공 범위 밖으로 처리한다.
  - 서울 경계를 넘는 노선의 어느 구간까지 제공되는지는 유효키 표본으로 확인해야 한다.
- 실시간 데이터 과거 보관 여부: 제공기관 과거 조회 기능 없음. 자체 적재하지 않은 과거 스냅샷은 복원할 수 없다.
- API 장애 시 대체 데이터:
  - Leave-now는 마지막으로 검증된 historical artifact를 사용한 `historical-only` 모드로 강등한다.
  - stale 실시간 값을 현재값처럼 사용하지 않는다.
  - 서울시 버스위치정보조회 API는 보조 관측원 후보이지만 동일 기관·원천 시스템 장애의 영향을 받을 수 있어 독립적인 장애 대체재로 간주하지 않는다.
- 확인된 문제:
  1. 서울 열린데이터광장 HTML의 숨김 종료 템플릿을 텍스트 추출기가 현재 상태로 오인할 수 있다. 실제 표시 상태를 함께 확인해야 한다.
  2. 포털은 XML로 표시하지만 활용가이드는 JSON 선택을 설명한다.
  3. `serviceKey`와 `ServiceKey` 대소문자 표기가 문서 간 다르다.
  4. 공식 엔드포인트가 HTTP이고 가이드는 SSL 미지원으로 기재한다.
  5. 시간대와 자정 이후 운행일 규칙이 문서화되지 않았다.
  6. `traTime*`, `nstnSpd*`, `namin2Sec*`의 단위·명칭에 명세 품질 문제가 있다.
  7. 실제 도착·출발시각과 과거 이력을 제공하지 않는다.
  8. 공개된 source freshness·가용성 SLA가 없다.
  9. 정상 JSON/XML 응답의 현재 필드 존재·타입·채움률을 유효키로 확인하지 못했다.

## 11. 테스트 결과
