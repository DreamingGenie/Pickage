# Pickage 0917 → 0923 기획 변경 상세분석

> 비교 대상: 2026-09-17 기획 세트와 2026-09-23 `origin/develop` `c88e20a`
> 목적: 문구 변경이 아니라 실제 개발 완료·범위 변경·보류를 추적한다.

## 1. 요약

0917 세트는 구현 중 제품의 목표와 확장 항목을 함께 담았다. 0923 세트는 개발 종료 시점의 병합 코드를
정본으로 다시 작성했다. 가장 큰 변화는 다음과 같다.

1. 교체 흐름, 제거 이유, 관측 이동 경로가 실제 생태계 보고서에 들어왔다.
2. 기능 비교가 버전 선택·환경 표·RAG 하이라이트까지 연결됐다.
3. PDF가 새 생태계 지표와 기능 비교를 포함하고 HAND-OFF Markdown이 추가됐다.
4. 비교 대상·보고서 URL 상태와 사용자 오류 처리가 강화됐다.
5. 데이터 기반은 468,519개 target으로 넓어졌으나 모든 파생 지표가 같은 범위로 완성된 것은 아니다.
6. 과거 목표였던 Evidence Drawer·verdict·Redis·pgvector·영구 보고서 저장은 현재 제품에서 제거했다.

## 3. 사용자 여정 변경

### 3.1 입력·후보

- `/analyze`에서 기준 패키지와 후보 선택을 통합했다.
- `/analyze/candidates`는 이전 링크 호환을 위해 리다이렉트한다.
- 후보는 최대 3개를 보여 주지만 자동 선택하지 않는다.
- 유사 후보를 쓰지 않고 직접 패키지를 추가할 수 있다.
- 분석 상태를 `base`, `with`, `nosimilar` 쿼리로 복원한다.
- 보고서 이동 전 선택 패키지의 overview를 검증한다.

직접 추가의 빠른 조작 중 URL 상태 유실은 `S15P21A506-472`로 남았다. 따라서 0923 문서는 URL
기능을 완료로 과장하지 않고 부분 완료로 분류한다.

### 3.2 보고서

보고서는 생태계 변화, 기능 비교, GitHub 커뮤니티의 세 탭으로 확정됐다. 방문 탭 상태 유지, 비교 대상
변경, 새 분석, PDF, HAND-OFF 행동이 헤더에 모였다. `reportId`는 현재 `draft`이므로 영구 공유
보고서처럼 설명하던 가능성을 제거했다.

## 4. 생태계 변화 확장

### 4.1 의존 전환

1년·3년·5년과 regular·peer·optional 조합에서 유지, 유입, 유출, 미관측을 제공한다. V11
freshness로 데이터가 아직 도달하지 않은 상태를 유지와 분리했다. 프런트 구현은 `S15P21A506-391`,
PDF 반영은 `-394`와 연결된다.

### 4.2 제거 이유

제거 이유 API와 화면이 추가됐다(`S15P21A506-378`, `-396`, PDF `-428`). 단위는 패키지 수가
아니라 전환 이벤트이며 문서도 이 단위를 사용한다.

### 4.3 관측 이동 경로

regular·dev 이동 경로를 상위 5개+기타로 제공한다(`S15P21A506-424`, 화면 보완 `-430`, `-431`).
실측 검수 결과 대표 사례의 1위는 타당했지만 다음 한계가 확인됐다.

- `rxjs → tslib` 같은 딸려 들어온 부품은 기본 필터를 통과한다.
- 무관한 동시 변경도 강한 근거 등급을 받을 수 있다.
- 양방향은 변종을 뜻하지 않으므로 배지 이름을 “양방향”으로 바꿨다.

0923 문서는 이 기능을 “대체 추천”이 아닌 “관측된 이동”으로 정의한다.

## 5. 기능 비교 변경

### 5.1 버전과 환경

기능 비교 전에 버전 후보를 조회하고 패키지별 버전을 고를 수 있다. module format, bundled types,
direct·peer dependency 수 등의 환경 표를 함께 제공한다. 버전 후보 코드는 병합됐지만 Jira
`S15P21A506-447`은 조사 시점에 진행 중이었다.

### 5.2 RAG 출력

현재 출력은 공통점, 패키지별 차이, 소스 상태, 핵심 용어·핵심 문장 강조다(`S15P21A506-419`,
`-420`, `-470`, `-471`). HAND-OFF Markdown 파일을 직접 근거로 사용하며 결과는 영구 저장하지 않는다.

0917 문서에 있던 Evidence Drawer, 문장별 인용 패널, verdict 표, 승자 결론은 실제 제품에 없으므로
0923 IA와 요구사항에서 제거했다. pgvector·Redis 기반 구조도 현재 아키텍처가 아니다.

## 6. GitHub 커뮤니티 변경

0917 시점에 별도 구현 기록으로 관리하던 DB, API, GitHub 수집, GMS 요약, 화면, 운영 계약은 현재
제품의 한 탭으로 통합됐다. GET 조회와 POST refresh를 분리하고 분석 확정 시 비동기 갱신한다.

범위는 기준 패키지 하나다. 세 비교 패키지의 커뮤니티를 모두 병렬 비교하는 기능으로 확대하지 않았다.
과거 상세 구현 근거는 보관 폴더에 남기고 0923 기획서는 사용자 계약만 현재형으로 정리했다.

## 7. 출력 변경

### 7.1 PDF

PDF는 생태계를 필수로 하고 커뮤니티와 완료된 기능 비교를 선택적으로 포함한다. 교체 흐름, 제거 이유,
기능 비교 등 0917 이후 데이터가 추가됐다(`S15P21A506-414`, `-416`, `-428`, `-463`). HTML
미리보기와 파일은 같은 생성 소스를 사용한다.

### 7.2 HAND-OFF Markdown

에이전트 인계용 Markdown 생성·다운로드가 새로 추가됐다(`S15P21A506-466`, `-467`). 별도 편집
모달이나 영구 저장함은 없고, 가능한 현재 세션 자료를 구조화해 즉시 내려받는다.

## 8. 데이터 범위 변경

### 8.1 확장된 것

- target 목록 468,519개
- registry 추가분 수집
- downloads 468k 범위 재적재
- 확장 transition 데이터 적재
- 여러 registry 회차를 합치는 package_env 빌드·loader
- regular 전수와 dev 상위 100k 이동 경로 데이터

관련 완료 이슈에는 `S15P21A506-451`, `-452`, `-453`, `-454`가 있다.

### 8.2 아직 같은 범위가 아닌 것

- similarity loader 기본 `max-rank`는 100k이며 468k 배치 `-460`은 미완료다.
- 최신 dependents 468k 재계산 `-455`는 미병합이다.
- package_env 추가분은 도구·로컬 verify-only 근거와 운영 게시 상태를 구분해야 한다.
- 다운로드 실패 태스크 재수집, 일부 pointer·monitor 후속이 남아 있다.

따라서 “Pickage의 모든 데이터가 468k로 확장 완료”라는 표현은 사용하지 않는다.

## 9. AI·운영 변경

유사도 모델은 MLflow `pickage-similarity@production`과 ONNX 실행 구조로 운영된다. 첫 배치의 자원
실측 결과 8 GiB가 필요했고, 메모리 한도 이슈 `-384`가 남았다. 0917 문서와 AI 계약의 “MLflow
미배포” 표현은 더 이상 현재 상태가 아니다.

운영 구성에는 앱·데이터 노드 compose, 주간 ingest timer, 앱 배포·AI 이미지 CI, Netdata·pipeline
monitor 구성이 있다. 다만 데이터 노드 모니터링과 당일 서비스 상태는 저장소만으로 완료 확인하지 않았다.

## 10. 품질·검증 변경

0923 조사에서 다음을 다시 실행했다.

- 프런트 typecheck, lint, 168개 테스트, production build 통과
- 백엔드 단위 테스트 560개 통과·1개 skip, main·integrationTest compile 통과
- AI/RAG 247개 테스트 통과
- pipeline 전체 pytest는 collection·상대 import·PySpark 환경 문제로 실패

파이프라인 모듈 테스트가 많다는 사실과 전체 CI가 통과한다는 사실을 구분한 것이 0917 문서보다
엄격해진 부분이다.

## 13. 결론

0923 문서는 제품 범위를 넓히기 위한 계획이 아니라, 구현이 끝난 기능과 남은 제약의 경계를 다시
그은 문서다. 현재 사용자는 최대 3개의 npm 패키지를 세 관점에서 비교하고 두 형식으로 전달할 수 있다.

완료된 것도 아니다. 이 두 문장을 함께 유지하는 것이 최종 기획 정본의 핵심이다.
