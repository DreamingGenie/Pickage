# Jira 분류 운영 규칙

최신 결정: 2026-09-11 사용자 후속 승인 / S15P21A506-327.
321의 에픽 배치는 유지하고, 에픽과 하위 업무의 접두사를 분리한다.

## 네 가지 구분

| 구분 | 기록 위치 | 의미 |
| --- | --- | --- |
| 제품 범위 | 에픽 제목·상위 에픽 | `[MVP]`, `[확장]`, `[인프라]`, `[기획]`, `[운영]` + 결과 단위 |
| 수행 내용 | 하위 업무 제목 | `[영역] [행동] 구체적 대상` |
| 담당 파트 | 라벨 | 프런트엔드·백엔드·데이터·AI·인프라·기획·문서·검수·운영 |
| 개인 책임 | 담당자 | 승인된 개인 업무 배분. 라벨 변경으로 재배정하지 않는다. |

Story/Task/Bug는 기존 이슈 유형으로 구분한다. 버그 제목 예시는 `[FE] [수정] 후보 입력 오류`다.
상태는 Jira 상태 필드에 두며, 범위 보류·미확정 조건은 본문에 명시한다.

### 영역과 행동 선택

| 영역 | 의미 |
| --- | --- |
| FE / BE / AI / 데이터 | 프런트엔드 / 백엔드 / AI 처리 / 데이터 파이프라인 |
| 공통 | 여러 파트의 공통 계약·통합 연동·교차 검수. 개인 담당은 별도이며 미배정을 뜻하지 않음 |
| 기획 / 운영 | 기획 판단·문서 정비 / 평가·발표·팀 운영 |

영역 뒤에 `[설계]`, `[구현]`, `[연동]`, `[보완]`, `[수정]`, `[검증]`, `[수집]`, `[전처리]`,
`[검토]`, `[평가]`, `[제작]`, `[정비]` 등 본문의 주요 행동을 하나 붙인다.
FE나 AI만 쓰면 행동이 드러나지 않으므로 `[FE] [보완]`, `[AI] [설계]`처럼 함께 표시한다.

- `[구현]`: 새 처리·저장·판정 로직을 개발한다. validator 구현도 여기에 속한다(179·180).
- `[검증]`: 기존 산출물을 시험·대조·인수한다(196·207·250·310·315).
- `[설계]`: 계약·스키마·인계 기준을 확정한다. 제목에 '검증'이 있어도 계약을 정하는 148은 설계다.
- `[연동]`: 준비된 API·컴포넌트·모듈을 연결한다. `[보완]`은 현 구현의 기획 차이를 보완하고 `[수정]`은 결함을 고친다.

범위는 상위 에픽과 기존 본문으로 확인한다. 예외적으로 공통 MVP 에픽 아래의 250은
`[공통] [검증] 확장 도메인 판정·자료·요청 상태 분리 검수`로 적어 확장 범위를 잃지 않게 한다.
공통 tarball 안전 모듈 자체는 인프라 보호 대상이고, 기능 비교 경로에서 이를 사용하는
199는 `[BE] [연동]`으로 정리한다. 새 행동 접두사는 기존 구현 범위를 넓히거나 다시 착수시키는 지시가 아니다.

## 안전한 변경과 예외

1. 대상 이슈와 실제 산출물을 읽고 에픽·접두사·파트를 결정한다.
2. 수정 직전 상태·제목·본문·현재 에픽을 확인한다. 진행 중·완료·보호 영역이거나 동시 변경을 발견하면 제외한다.
3. 기존 키·담당자·상태·스프린트·마감일·우선순위·이슈 유형·이슈 간 링크를 보존한다.
4. 이번 후속 정리는 일반 업무 제목과 비보호 에픽 분류 안내만 수정한다. 기존 에픽 배치·라벨은 유지한다.
5. 재조회하여 변경 필드와 보호 필드를 대조한다. 분류와 무관한 코드·기획 결함 수정은 별도 작업이다.

2026-09-11 후속 정리에서 진행 중·완료 이슈는 옛 제목/파트/에픽을 그대로 유지한다.
임베딩·후보 색인·유사도 실험·재학습(119·146·168·170·171·172·173·174·236),
인프라 에픽 116과 하위 9건, AI 이력 에픽 117은 어떤 필드도 수정하지 않는다.
인프라 환경 준비·배포가 혼재한 258·291도 보수적으로 제외한다. 이 항목들은 이전 표기가 남는다.
기능 비교 RAG의 미착수 업무는 적용 대상이며 임베딩 제외와 혼동하지 않는다.
110은 입력·후보 서비스 전체의 범위 표기와 분류 안내만 명확히 하며 그 안의 임베딩 개별 업무는 변경하지 않는다.
116·117에 남은 과거 분류 안내는 보호된 기록이지 최신 규칙이 아니다. 신규 비보호 업무는 본 규칙을 따른다.
작업 중 사용자가 111·115·117 제목과 여러 마감일을 직접 수정했음을 확인했다.
해당 변경은 되돌리지 않으며 위 표는 사용자 변경까지 포함한 관측 값이다.
특히 진행 중 에픽 111의 설명에는 과거 유지·유입·이탈 범위가 남지만 해당 미착수 업무는 326으로
분리되어 확장으로 관리한다. 과거 설명만 보고 현재 MVP 요구를 되돌리지 않는다.
분류 라벨이 없는 과거 업무가 있으므로 파트 라벨 검색 결과가 전체 진행 업무를 망라하지 않는다.

새 에픽의 담당자는 기존 대표 업무의 담당자를 계승했으며 기존 업무 배분은 바꾸지 않았다.
생성 시 활성 스프린트 연결은 AGENTS.md의 등록 규칙에 따른 것이며 해당 주 완료 약속이 아니다.

## 조회 예시

미착수 백엔드 업무:

```jql
project = S15P21A506 AND statusCategory = "To Do" AND labels = "백엔드"
ORDER BY parent ASC, priority DESC
```

기능 비교의 미완료 업무(파트 무관):

```jql
project = S15P21A506 AND parent = S15P21A506-112 AND statusCategory != Done
ORDER BY assignee ASC, key ASC
```

미완료 에픽 중 이전 분류 제외:

```jql
project = S15P21A506 AND issuetype = 10000 AND statusCategory != Done
AND (labels IS EMPTY OR labels NOT IN ("이력보존")) ORDER BY key ASC
```

예시는 저장 필터·보드 설정을 생성한 것이 아니다. 기존 완료/진행 업무까지 보려면 담당자나
기능 에픽 검색을 함께 사용한다. 새 업무는 에픽 1개와 실제 담당 파트 라벨을 지정한다.
검수/운영 라벨을 임의로 개발 브랜치 part에 사용하지 않는다. 코드 변경이면 실제 수정 파트,
기획이면 `plan`, 일반 문서라면 `docs` 등 AGENTS.md의 허용 part를 사용한다.

## 연동 확인 범위

GitLab의 Jira 연결은 [이슈 키 참조](https://docs.gitlab.com/integration/jira/)를 사용한다.
따라서 기존 이슈 키·브랜치명·커밋·MR을 유지하는 방식으로 정리한다.
서버 측 개발 패널의 재동기화 성공까지 이 사실만으로 보장하지 않는다.

이번 연결 도구에는 Component 생성·보드·자동화 관리 기능이 없어 파트는 라벨로 기록했다.
Component를 추후 도입한다면 [기본 담당자 설정](https://support.atlassian.com/jira-software-cloud/docs/configure-jira-components/)
및 자동 재배정 영향을 먼저 확인한다. 현재 보드 필터·자동화가 옛 에픽이나 제목 문자열에
의존하는지는 설정 화면에서 별도 확인이 필요하며 이번 작업에서 변경하지 않았다.
