# Jira 분류 운영 규칙

확정: 2026-09-11 사용자 승인 / S15P21A506-321.

## 네 가지 구분

| 구분 | 기록 위치 | 의미 |
| --- | --- | --- |
| 업무 성격 | 제목 접두사 | `[기능]` MVP, `[확장]` 확장, `[인프라]` 공통 기반, `[기획]`, `[운영]` |
| 제품 범위 | 상위 에픽 | 입력·후보, 생태계, 기능 비교, PDF, 커뮤니티 등 결과 단위 |
| 담당 파트 | 라벨 | 프런트엔드·백엔드·데이터·AI·인프라·기획·문서·검수·운영 |
| 개인 책임 | 담당자 | 승인된 개인 업무 배분. 라벨 변경으로 재배정하지 않는다. |

Story/Task/Bug는 기존 이슈 유형으로 구분한다. `[기능]` 버그도 가능하다.
파트·행위·보류 여부를 새 접두사로 만들지 않는다. 상태는 Jira 상태 필드에 둔다.
범위 보류·미확정 조건은 해당 업무 본문의 조건으로 명시하고 제목 접두사에 섞지 않는다.

공통 기반이 백엔드 코드로 구현될 수도 있다. 예를 들어 공통 tarball 안전 처리 모듈은
`[인프라]` + `백엔드` 라벨, 기능 비교에 그 모듈을 적용하는 작업은 `[확장]` + `백엔드`다.
같은 에픽 안에서도 확장 전용 교차 검수(250)는 `[확장]`을 유지한다.

에픽의 명칭·연결은 개발 완료나 기획 승격을 뜻하지 않는다.

## 안전한 변경과 예외

1. 대상 이슈와 실제 산출물을 읽고 에픽·접두사·파트를 결정한다.
2. 수정 직전 상태·제목·현재 에픽을 확인한다. 진행 중·완료이거나 동시 변경을 발견하면 제외한다.
3. 기존 키·담당자·상태·스프린트·마감일·우선순위·이슈 유형·이슈 간 링크를 보존한다.
4. 제목·에픽·라벨만 수정한다. 에픽 범위 본문을 고칠 때에는 옛 내용을 이력 부록에 보존한다.
5. 재조회하여 변경 필드와 보호 필드를 대조한다. 분류와 무관한 코드·기획 결함 수정은 별도 작업이다.

2026-09-11 정리에서 진행 중·완료 이슈는 옛 제목/파트/에픽을 그대로 유지한다.
특히 진행 중 에픽 111의 설명에는 과거 유지·유입·이탈 범위가 남지만 해당 미착수 업무는 326으로
분리되어 확장으로 관리한다. 과거 설명만 보고 현재 MVP 요구를 되돌리지 않는다.
분류 라벨이 없는 과거 업무가 있으므로 파트 라벨 검색 결과가 전체 진행 업무를 망라하지 않는다.

새 에픽의 담당자는 기존 대표 업무의 담당자를 계승했으며 기존 업무 배분은 바꾸지 않았다.
생성 시 활성 스프린트 연결은 AGENTS.md의 등록 규칙에 따른 것이며 해당 주 완료 약속이 아니다.

## 조회 예시

미착수 백엔드 업무:

```jql
project = S15P21A506 AND statusCategory = "To Do" AND labels = "백엔드"
ORDER BY parent ASC, priority DESC
```

기능 비교의 미완료 업무(파트 무관):

```jql
project = S15P21A506 AND parent = S15P21A506-112 AND statusCategory != Done
ORDER BY assignee ASC, key ASC
```

미완료 에픽 중 이전 분류 제외:

```jql
project = S15P21A506 AND issuetype = 10000 AND statusCategory != Done
AND (labels IS EMPTY OR labels NOT IN ("이력보존")) ORDER BY key ASC
```

예시는 저장 필터·보드 설정을 생성한 것이 아니다. 기존 완료/진행 업무까지 보려면 담당자나
기능 에픽 검색을 함께 사용한다. 새 업무는 에픽 1개와 실제 담당 파트 라벨을 지정한다.
검수/운영 라벨을 임의로 개발 브랜치 part에 사용하지 않는다. 코드 변경이면 실제 수정 파트,
기획이면 `plan`, 일반 문서라면 `docs` 등 AGENTS.md의 허용 part를 사용한다.

## 연동 확인 범위

GitLab의 Jira 연결은 [이슈 키 참조](https://docs.gitlab.com/integration/jira/)를 사용한다.
따라서 기존 이슈 키·브랜치명·커밋·MR을 유지하는 방식으로 정리한다.
서버 측 개발 패널의 재동기화 성공까지 이 사실만으로 보장하지 않는다.

이번 연결 도구에는 Component 생성·보드·자동화 관리 기능이 없어 파트는 라벨로 기록했다.
Component를 추후 도입한다면 [기본 담당자 설정](https://support.atlassian.com/jira-software-cloud/docs/configure-jira-components/)
및 자동 재배정 영향을 먼저 확인한다. 현재 보드 필터·자동화가 옛 에픽이나 제목 문자열에
의존하는지는 설정 화면에서 별도 확인이 필요하며 이번 작업에서 변경하지 않았다.
