# 설계 — 지표별 관측기간·기준일 표시 계약

- Jira: S15P21A506-197 (`[공통] [설계] 지표별 관측기간·기준일 표시 계약`)
- 작성: 2026-09-18
- 적용 범위: 보고서 **생태계 변화** 탭의 네 패널 — Downloads 추이 · Dependents 추이 ·
  Version Share · 유지·유입·이탈
- 이 문서는 **표시 계약**이다. 새 wire 를 여기서 확정하지 않는다 — API 형태를 바꿔야 하면
  Notion API 명세 정본과 Swagger 를 먼저 고친다(AGENTS.md 2번).

---

## 0. 한 줄 요약

**네 지표는 기간이 서로 다르고, 앞으로도 다르다.** 하나의 기간 선택기로 묶으려는 시도를
하지 않는다. 각 패널이 **자기가 덮는 구간을 스스로 표시**한다.

---

## 1. 왜 필요한가 — 깊이가 실제로 다르다

2026-09-18 운영 API 실측 (출처: S15P21A506-391 본문).

| 지표 | react | express | lodash |
| --- | --- | --- | --- |
| Downloads 추이 | 105주 (2024-09-02~) | 105주 | 105주 |
| Dependents 추이 | 229주 (2022-05-08~) | **31주 (2026-02-13~)** | 229주 |
| 유지·유입·이탈 | 1y·3y·5y 프리셋 | 〃 | 〃 |

같은 화면의 두 차트가 이미 105주와 31주다. **이 문서가 만드는 문제가 아니라 이미 있는
사실**이고, `S15P21A506-374` 에서 조회 상한을 없애 "가진 것을 전부 보여 준다"로 바꾼 뒤로는
숨길 수도 없다.

차이가 나는 이유가 지표마다 다르다는 점이 중요하다.

- **추이 두 종**이 얕은 것은 우리 주간 수집이 2024-09 에 시작했기 때문이다. **매주 자란다.**
  패키지별로도 다른 것은 그 패키지가 수집 대상(다운로드 상위 10만)에 언제 들어왔는지가 달라서다.
- **유지·유입·이탈**의 5년은 우리 수집이 아니라 **npm 릴리스 이력 전체**에서 나온다. 진짜 5년이다.
- 따라서 3년 구간은 2027년쯤 저절로 맞고, **5년만 끝까지 다르다.** 기다려서 해결되지 않는다.

## 2. 지표별 계약

### 2-1. Downloads 추이

| 항목 | 값 |
| --- | --- |
| 응답 | `GET /api/packages/downloads` → `TrendResponse` |
| `metric` | `downloads` |
| `unit` | **`weekly`** — 값 하나가 그 주의 **합계**다. 일 평균이 아니다 |
| 구간의 뜻 | `from`·`to` 생략은 **"보유한 전부"** (`SnapshotWindow`, S15P21A506-374) |
| 끝의 기준 | **오늘이 아니라 최신 스냅샷**이다 |
| 버전 분해 | 없음 (`major` 가 `null` 이고 직렬화에서 빠진다) |

**표시 규칙**

- 축 라벨과 툴팁에 **"주간 합계"** 를 명시한다. 단위를 적지 않으면 일 단위로 읽힌다.
- 구간은 `points` 의 **첫·마지막 `snapshot_at`** 으로 적는다. 요청한 `from`·`to` 가 아니다 —
  요청 구간이 관측 시작보다 앞서면 서버가 가진 데까지만 온다.

**기준일 달력이 불규칙해도 서버는 월요일 주간 격자로 답한다** (S15P21A506-403)

기준일 달력 229개는 deps.dev Projects 의 실제 스냅샷 날짜이며 2026-02 이후로는 월요일 주간이 아니다
(금·화·목이 섞이고 간격이 1~18일이다). 그런데 DB 의 `downloads` 는 `[직전 기준일, 이번 기준일)`
**구간 합계**(S15P21A506-278)라서 그대로 내보내면 간격에 따라 값이 흔들린다 — 1일 간격이면 하루치,
18일 간격이면 18일치가 한 점이 되어 "주간 합계" 라벨이 거짓이 되고 급락·급등이 그려진다.

- 점은 **월요일**이다. 값은 예전과 같이 그 날짜 직전 7일 `[M-7, M)` 의 합계다. 기준일이 월요일
  주간이던 구간은 값이 한 자리도 바뀌지 않는다.
- 구간 합계를 구간 일수로 나눈 **일평균으로 펼쳐** 7일치를 다시 더한다. 구간 안의 일별 분포가
  균등하다는 가정이라 **근사값**이며, 총량은 보존한다.
- 그 패키지의 행이 없는 기준일 때문에 7일이 덮이지 않은 주는 **점을 내보내지 않는다.** 0 이나
  부분합으로 채우지 않는다.
- 화면과 PDF 가 같은 서비스 경로(`PackageService.getDownloadsTrend`)를 쓰므로 함께 맞는다.
  구현은 `WeeklyTrend`(`backend/.../domain/packages/`).

### 2-2. Dependents 추이

| 항목 | 값 |
| --- | --- |
| 응답 | `GET /api/packages/dependents` → `TrendResponse` |
| `metric` | `dependents` |
| `unit` | `null` — 개수이므로 단위가 없다 |
| `sum_over_versions` | **`true`** — 버전별 합계다. 프로젝트 수가 아니다 |
| 버전 분해 | `major` 별로 **같은 `name` 이 여러 줄** 나온다 |

**월요일 격자·보간** (S15P21A506-403) — 의존 수는 그 날짜 시점의 재고이고 완만하게 변한다. 서버가
`(name, major)` 시리즈마다 **자기 관측 범위 안에서** 월요일마다 양옆 관측치를 날짜 비율로 선형
보간해 내려준다. 기준일이 월요일이면 관측값 그대로다. 첫 관측 이전과 마지막 관측 이후는 지어내지
않는다(major 마다 관측 시작이 다르다). 그래서 이 카드의 선은 관측 범위 안에서 끊기지 않는다.

**기본 모드는 변화율**(구간 시작 = 100%)이고 실제값(로그축)으로 전환할 수 있다. 규모가 다른
패키지를 나란히 놓는 비교 화면에서 먼저 궁금한 것은 "누가 더 빨리 늘었나" 이기 때문이다.
Downloads 는 실제값 하나로 고정한다.

**표시 규칙 — 여기가 이 문서에서 가장 조용히 틀리는 자리다**

- **`major` 필터를 바꾸면 증감의 기준일도 함께 바뀐다.** 증감은 "고른 major 들의 합" 위에서
  다시 계산되고, major 마다 관측 시작이 다르므로 **첫 유효 기준일이 필터에 따라 움직인다.**
  필터를 바꿨는데 기준일 표시가 그대로면 화면이 거짓말을 한다.
- 그래서 증감 옆의 기준일은 고정 문자열이 아니라 **현재 선택 상태에서 실제로 쓰인 두 점의
  날짜**를 그린다. 구현은 이미 그렇게 되어 있다 — `adapter.ts` 의 `deltaOf()` 가 값과 함께
  `from`·`to`(증감을 낸 양 끝 스냅샷)를 돌려주고, major 선택이 바뀌면 다시 센다.
  **이 계약은 그 동작을 규칙으로 고정하는 것**이며, 셋 중 하나라도 어기면 깨진다.
  ① 값과 기준일을 같은 계산에서 함께 얻을 것 ② 화면에 그린 것과 **같은 창(windowed)**
  시리즈로 셀 것 ③ 결측(`null`)은 빼고 셀 것.
- `major` 가 `null` 인데 `metric` 이 `dependents` 면 **자료가 없는 것**이다. `not_found` 와 다르다
  (이름은 존재한다).
- major 선택기는 **패키지마다 독립**이다. 패키지끼리 major 구성이 다르므로 전역 선택기를
  상단에 두지 않는다(`model.ts` 주석과 같은 이유).

### 2-3. Version Share

| 항목 | 값 |
| --- | --- |
| 응답 | `GET /api/packages/version` → `VersionShareResponse` |
| `snapshot_at` | **최신 DB 스냅샷의 달력 날짜** |
| `basis` | `dependents` |
| `sum_over_versions` | `true` |

**표시 규칙**

- `snapshot_at` 은 **"이 달력 날짜에 DB 가 가진 값"** 이라는 뜻이다.
  **"이 날짜까지의 지표가 완료됐다"는 보장이 아니다.** 이 구분을 문구로 드러낸다.
  → 권장: "2026-08-31 DB 기준" (○) / "2026-08-31 집계 완료" (×)
- 이 카드의 기준일은 **개요(`PackagesOverviewResponse.snapshot_at`)와 같은 날짜여야 한다.**
  그래서 이 패널만 개요 응답을 기다린다(`ecosystem-report-tab.tsx`).

### 2-4. 유지·유입·이탈

**MVP 표시 자료에서 제외한다.** 확장 범위이며 `S15P21A506-391` 에서 별도 화면으로 다룬다.

MVP 화면에 끌어오지 않는 이유는 배치 문제가 아니라 **의미가 섞이기 때문**이다.

- 이 지표는 **상태 전이**(어떤 프로젝트가 계속 썼나/새로 썼나/그만 썼나)이고,
  Dependents 추이는 **총수 증감**(버전별 합계가 늘었나 줄었나)이다.
- **`유입 - 이탈 = 증감` 이 성립하지 않는다.** 한쪽은 이름으로 센 프로젝트 수이고
  다른 쪽은 버전별 합계라 부풀려져 있다 (`DEC-DEPENDENCY-DELTA-20260910-01`).
- 둘을 한 카드에 나란히 놓거나 같은 축에 그리면 사용자가 뺄셈을 시도한다. **섞지 않는다.**

시계열이 아니라 **두 시점의 비교 결과 하나**라는 점도 다르다. 그래서 임의 구간을 못 받고
프리셋 셋(1y·3y·5y)이다. 주 단위 선택으로 바꿀 수 없다.

### 2-5. 이탈 사유 (S15P21A506-396)

| 항목 | 값 |
| --- | --- |
| 응답 | `GET /api/packages/removal-reasons` → `RemovalReasonsResponse` |
| `metric` | `removal_reasons` |
| `unit` | **`transitions`** — 값 하나가 **전이 건수**다. 패키지 수가 아니다 |
| 구간 | 위와 같은 프리셋 셋(`1y`·`3y`·`5y`)이고 `t1`·`t2` 가 **같은 값**이다 |
| 버전 분해 | 없음. `kind` 분해도 없다 — 한 패키지가 한 줄이다 |

**위 2-4 와 같은 구간을 쓰면서 단위만 다른 유일한 쌍이다.** 그래서 한 화면에 나란히 놓을
수는 있지만 **더하거나 나눌 수는 없다.**

- `outflow` 는 "T1 엔 쓰고 T2 엔 안 쓰는 **패키지가 몇 개**인가" 이고
  `removals` 는 "그 사이 **빼는 행위가 몇 번** 있었나" 다.
- 한 의존자가 뺐다 넣었다 다시 뺐으면 `outflow` 는 1, `removals` 는 2다.
  **`no_replacement / outflow` 같은 비율은 해석할 수 있는 수가 아니다.**
- 같은 응답 안의 `dependents`(의존자 수)와 `removals`(전이 건수)도 단위가 다르다.
  둘을 함께 주는 것은 그 차이를 보이기 위해서다.

응답이 `unit` 을 **값으로** 싣는 이유가 이것이다 — 문서나 주석은 받는 쪽 코드에 닿지
않는다. 화면은 이 값을 캡션에 그대로 써서 "전이 건수" 임을 사용자에게도 알린다.

기준일이 두 지표에서 같은 것은 우연이 아니다. 적재기가 `dependent_transition` 에서
`t1`·`t2` 를 가져오므로 구조적으로 같은 값이다 (`pipeline/removal_reasons/load.py`).

## 3. 자료가 없을 때 — 세 가지를 구분한다

**고정 날짜나 기획서의 예시 날짜를 실측값처럼 채우지 않는다.** 이것이 이 절의 전부다.

| 상태 | 응답 모양 | 화면 |
| --- | --- | --- |
| 값이 0 | 점의 `value` 가 `0` | 0 으로 그린다 |
| 관측이 없음 | **점 자체가 없다** — Downloads 에서 7일이 덮이지 않은 주. Dependents 는 관측 범위 안의 빈 주를 서버가 보간하므로 해당 없음 | 선을 잇지 않는다. 0 으로 채우지 않는다 |
| 기준일을 모름 | `snapshot_at` 이 `null` (적재 전) | 날짜 자리를 비우거나 "집계 대기 중" |
| 이름이 없음 | `not_found` 배열 | "찾을 수 없는 이름" |

- 없는 점을 `0` 으로 채우면 **있지도 않은 급락**이 그려진다. 서버가 행을 빼서 보내므로
  클라이언트는 x축을 **인덱스가 아니라 `snapshot_at` 값**으로 잡아 선을 맞춘다(명세 §4).
- 패키지는 있는데 스냅샷이 없으면 **지표만 `null`** 이고 `not_found` 가 아니다. 0 으로 채워
  보내면 다운로드가 0 인 패키지처럼 보인다(명세 0.5).
- 구간에 점이 하나도 없어도 **200 에 빈 결과**다. 오류가 아니다(명세 §6).

## 4. 알려진 구멍 — 추이 응답에 구간 필드가 없다

`TrendResponse` 의 최상위 필드는 `metric` · `unit` · `sum_over_versions` · `series` ·
`not_found` 뿐이다. **이 응답이 덮는 구간을 알려주는 필드가 없다.**

지금은 클라이언트가 `points` 의 첫·마지막 `snapshot_at` 으로 **역산**한다. 대부분은 맞지만
한 곳에서 무너진다 — **점이 0개면 구간을 알 방법이 아예 없다.** 그래서 "이 구간에 관측된
스냅샷이 없습니다" 까지만 말할 수 있고, **어느 구간을 물었는지**는 화면이 말하지 못한다.

`VersionShareResponse` 는 `snapshot_at` 을, `TransitionsResponse` 는 `t1`·`t2` 를 응답에
싣는다. **추이 두 종만 없다.**

- **이 문서에서 고치지 않는다.** wire 변경이므로 Notion API 명세 정본을 먼저 고쳐야 하고,
  `S15P21A506-126`·`-304` 의 통합·차트 작업을 건드리지 않는 것이 이 이슈의 전제다.
- 지금의 표시 계약은 **역산으로 충분한 범위**까지만 정의한다. 점이 0개인 경우는
  "구간 미표시 + 빈 상태 문구" 로 둔다.
- 후속으로 다룰 값어치가 있으면 별도 이슈로 낸다. 제안 형태: `TrendResponse` 에
  `from`·`to` 를 실어 **서버가 실제로 쓴 구간**을 그대로 돌려준다.

## 5. 화면 배치 규칙

```
다운로드 추이                  2024-09-02 ~ 2026-08-31
의존 수 추이                   2022-05-08 ~ 2026-08-31
버전 분포          2026-08-31 DB 기준
유지·유입·이탈   [3년 v]       2023-08-31 ~ 2026-08-31
```

1. **기간 선택기를 페이지 상단에 두지 않는다.** 상단에 두면 네 패널을 다 모는 것처럼 보인다.
   유지·유입·이탈의 프리셋 선택기는 **그 카드 안에** 둔다.
2. **각 패널이 자기가 덮는 구간을 글자로 단다.** 추이는 x축이 말해 주지만 글자로도 적는다 —
   축만 보면 "가진 게 없는 것"과 "안 그린 것"이 구분되지 않는다.
3. **한쪽에 맞춰 다른 쪽을 자르지 않는다.** 가장 얕은 지표에 맞춰 나머지를 자르면 가진
   자료를 버리는 것이고, 가장 깊은 쪽에 맞춰 늘리면 왼쪽이 통째로 빈다.
4. 네 줄이 나란히 보이면 사용자가 스스로 안다. **숨기려다 실패하는 것보다 낫다.**

| 1 | 세 지표의 관측 시작이 서로 다른 패키지 | 한 기간 선택기로 묶는 회귀 |
| 2 | **major 를 바꾸면 증감의 첫 유효 기준일이 바뀌는 패키지** | §2-2 의 조용한 오표시 |
| 3 | 구간에 점이 0개인 패키지 | 0 으로 채우기 / 빈 상태 오분류 |
| 4 | `snapshot_at` 이 `null` (적재 전) | 고정 날짜를 실측값처럼 채우는 회귀 |
| 5 | 존재하지만 자료가 없는 이름 + `not_found` 이름을 **함께** | 둘을 같은 문구로 뭉개는 회귀 |
| 6 | major 가 하나뿐인 패키지 | 선택기를 그리지 않는 분기 |

2번이 이 목록의 본체다. 나머지는 빈 화면으로 드러나지만 **2번만 값이 맞아 보이는 채로
틀린다.**
