## 3. 아키텍처 / 데이터 흐름

### 3.1 저장 계층: JPA를 쓰지 않는다

`backend/.../domain/packages/PackageQueryRepository.java` 상단 주석에 이 저장소 전체의
결정이 이미 적혀 있다: *"JPA 를 쓰지 않는다... JPA 를 써도 전부 native query 가 되어
엔티티는 껍데기만 남는다."* 실제로 코드베이스 전체(`grep -r "@Entity"`)에 JPA Entity가
하나도 없고, 모든 저장소가 `JdbcTemplate` + native SQL + `RowMapper` + `record` DTO
조합이다. `spring-boot-starter-data-jpa`는 의존성에는 있지만(Flyway 연동/트랜잭션
매니저 용도로 추정) Entity 매핑에는 쓰이지 않는다.

Jira 314·구현계획 문서는 "community_snapshot Entity"라는 표현을 쓰지만, `community_snapshot`은
단일 행 upsert(`INSERT ... ON CONFLICT DO UPDATE`) + advisory lock + JSONB CHECK라는,
JPA가 오히려 불리한 연산이라 이 프로젝트의 기존 결정과도 방향이 같다. **"Entity"를 JPA
`@Entity`가 아니라 "저장 모델(record)"로 해석해 `CommunitySnapshotRepository`를
`PackageQueryRepository`와 같은 패턴(JdbcTemplate 직접 사용)으로 구현한다.**

### 3.2 게시(upsert) — `pipeline/snapshot/postgres.py`의 lock 기법을 Java로 이식

이 저장소에는 이미 "원자적 게시 + advisory lock" 문제를 푼 선례가 있다 — `pipeline/snapshot/`
(269 작업, Python)이다. 기법을 그대로 옮긴다:

```text
외부 I/O(수집·검증·요약) — 이미 메모리에서 끝난 상태로 이 계층에 들어옴
  -> SET LOCAL lock_timeout='2s'; SET LOCAL statement_timeout='5s';   -- 락 걸기 전에 먼저 설정
  -> SELECT pg_try_advisory_xact_lock(hashtextextended('community:snapshot:' || :packageId, 0))
  -> INSERT INTO community_snapshot (...) VALUES (...)
     ON CONFLICT (package_id) DO UPDATE SET ...
  -> commit (실패 시 rollback, 이전 행 그대로 보존)
```

269와의 차이 — 그대로 베끼지 않고 문제 성격에 맞춰 조정한 지점:

| | 269 (`pipeline/snapshot/postgres.py`) | 314 (community) | 조정 이유 |
| --- | --- | --- | --- |
| 락 범위 | `pg_advisory_lock`(세션, 명시적 해제) | `pg_advisory_xact_lock`(트랜잭션 스코프, commit/rollback 시 자동 해제) | 269는 배치 전체 동안 단일 writer를 보장해야 하지만, 314는 package 하나의 짧은 upsert 트랜잭션 안에서만 겹치지 않으면 된다 — 커밋 시 자동 해제되는 xact 버전이 "짧은 트랜잭션 안에서만"이라는 Jira 요구와 더 맞는다 |
| 락 키 | 고정 문자열 `'snapshot:reference'` (전역 1개) | `'community:snapshot:' \|\| package_id` (package별) | 269는 reference 테이블 전체가 대상이라 전역 락 하나면 충분하지만, community는 package마다 독립적으로 갱신되므로 package_id를 키에 섞어 서로 다른 package의 갱신을 막지 않는다 |
| timeout 값 | `lock_timeout=2s`, `statement_timeout=30s` | `lock_timeout=2s`, `statement_timeout=5s` | 기법(락 걸기 전에 먼저 timeout 설정)은 동일. 값은 Jira 314 본문이 이미 못박은 숫자(짧은 upsert 트랜잭션이라 30s보다 훨씬 짧아야 함)를 그대로 쓴다 |

`hashtextextended`로 문자열 키를 해시하는 방식은 269 그대로 재사용한다 — 정수 락 키를 직접
고르면 다른 도메인이 우연히 같은 정수를 써서 충돌할 수 있는데, 이름 있는 문자열을 해시하면
그 위험이 없다는 것이 269가 이미 검증한 이유다.

### 3.3 격리 테스트 DB — `pipeline/snapshot/test_integration.py`/`test_history.py`를 Java로 이식

구현계획 문서·Jira 314가 말하는 "격리 test DB(`pickage_community_test_<run_uuid>`)"는 발명이
아니라 이미 이 저장소에 있는 패턴이다. `pipeline/snapshot/test_integration.py`가 정확히 이렇게
한다:

```python
self.database = "pickage_269_test_" + uuid.uuid4().hex
self.sql(f'CREATE DATABASE "{self.database}";', database="postgres")
self.addCleanup(self.drop_database)
# ... 필요한 V__ 파일만 적용 ...

def drop_database(self):
    if not re.fullmatch(r"pickage_269_test_[0-9a-f]{32}", self.database):
        raise ValueError("Refusing to drop a database outside this test's namespace")
    self.sql(f'DROP DATABASE "{self.database}";', database="postgres")
```

Python은 `docker exec ... psql`로 기존 컨테이너에 접속하지만 Java 쪽은 JDBC를 쓰므로 접속
방식만 다르고 나머지 구조(이슈 번호가 들어간 이름, DROP 전 정규식으로 이름 재검사, 테스트
프레임워크의 cleanup 훅에 등록)는 그대로 옮긴다.

`DisposableTestDatabase`(신규, `backend/src/integrationTest/.../support/`) 설계:

1. `application-local.yaml`의 `postgres` 관리자 접속(`jdbc:postgresql://localhost:15432/postgres`,
   `postgres`/`pickage`)으로 `CREATE DATABASE "pickage_314_test_<uuid>"` 실행
2. 새 DB에 대해 `Flyway.configure().dataSource(...).load().migrate()`로 `db/migration`의
   V1~V5를 전부 적용 (전체 migration을 적용해야 "빈 DB 전체 migration" 완료 기준을 충족한다 —
   269는 필요한 파일만 골라 적용했지만 314는 `package` FK가 있어 V1이 필수고, 어차피 전체
   적용이 "빈 DB 부터 최신까지" 시나리오 자체다)
3. JUnit 5 `AfterEach`/`try-with-resources`로 정리 시 `pickage_314_test_[0-9a-f]{32}` 정규식
   재검사 후 `DROP DATABASE`
4. `backend/src/test`(단위)에는 절대 두지 않는다 — 기존 소스셋 분리 원칙(`build.gradle`의
   "위치가 곧 분류다") 그대로 `integrationTest`에만 둔다

이 유틸은 `support` 패키지에 둬 이름에 `community`를 넣지 않는다 — 269가 남긴 것과 같은 성격의
문제(원자적 게시 테스트)를 다른 도메인이 나중에 또 풀 수 있으므로, 이 Phase가 "커뮤니티 전용"이
아니라 "이 저장소의 두 번째 사례"로 재사용 가능하게 만든다.

### 3.4 정리 배치 트리거 — `@Scheduled` 채택 판단 (미확정, 확인 필요)

이 저장소의 주기 배치는 지금까지 전부 **앱 밖의 cron이 1회성 잡을 띄우는 방식**이었다
(`compose.yaml`의 유사도 배치 주석: "운영에서는 EC2 #1의 cron이 배치 시각마다 새로 띄우는
1회성 잡"). Spring `@Scheduled`는 이 코드베이스에 선례가 없다(`grep -r "@Scheduled"` 결과 없음).

그럼에도 이번엔 `@Scheduled`를 기본으로 제안한다 — 외부 cron 패턴의 근거("켜고 끄는 주체가
문제")는 유사도 배치처럼 GPU/Spark 다중 노드 조율이 필요한 작업에서 나온 것이고, community
정리는 `api` 컨테이너 하나 안에서 테이블 하나를 `DELETE ... LIMIT 500`하는 가벼운 작업이라 그
조율 문제가 없다. 다만 이것은 이 Spec에서 새로 판단한 것이라 **승인 시 이 판단 자체를 다시
확인**한다. 외부 cron + 내부 관리용 endpoint 방식을 원하면 이 절만 바꾸면 된다(다른 절과
독립적).

### 3.5 조회

`package_id`로 한 행을 읽고 JSONB `result`를 typed record로 역직렬화한다. `fresh_until`·
`serve_until`은 저장하지 않고 `collected_at` + 설정값(24h/7d, Phase 4가 `CommunityProperties`로
관리 예정)으로 이 계층 호출자가 계산한다 — 이 Phase는 `collected_at`과 TTL 판정에 필요한
순수 함수만 제공하고, 실제 사용은 Phase 4가 한다.

## 4. 예외 및 엣지 케이스 (Jira "세부 항목" 매핑)

- [ ] **migration 번호**: 착수 시점 `origin/develop`에 V1~V4 존재 확인 완료(§6) → `V5__community.sql`
      사용. V1~V4는 수정하지 않는다.
- [ ] **테이블 정의**: `package_id INT PK/FK(ON DELETE CASCADE)`, `snapshot_id UUID NOT NULL UNIQUE`,
      `payload_version SMALLINT NOT NULL CHECK > 0`, `collected_at TIMESTAMPTZ NOT NULL`,
      `data_status VARCHAR(30) NOT NULL CHECK (허용값)`, `result JSONB NOT NULL CHECK (json object)`,
      `collected_at` 인덱스. V1/V4 스타일대로 큰따옴표 quoted identifier + `COMMENT ON COLUMN`.
- [ ] **재시작 복원**: typed JSON에 `policy_version`/`lookback_days`/`summary_retry_at`,
      `source_issue_id`/`source_comment_id`/`association`/`is_issue_author`를 보존 — payload
      record 설계에 포함.
- [ ] **원문 미저장**: raw body·raw comment·prompt·외부 response·URL·원문 hash는 어떤 필드에도
      넣지 않는다. payload record에 그런 필드 자체를 만들지 않는 것으로 강제한다.
- [ ] **트랜잭션 경계**: 외부 I/O는 트랜잭션 밖(이 계층 호출 전에 이미 끝남), 게시만 짧은
      트랜잭션. lock timeout 선설정 순서 준수, rollback 시 이전 행 보존을 통합테스트로 검증.
- [ ] **TTL/정리**: 24h fresh / 7d 비노출 판정 함수, 전체 요약 실패(FAILED) 완료+5분 재시도 판정
      함수, 매시간 최대 500행 정리 배치. GET 시점 TTL 검사는 정리 배치 실행 여부와 무관하게
      항상 `collected_at` 기준으로 다시 계산한다(정리 지연이 만료 결과 노출로 이어지지 않게).
- [ ] **격리 테스트 DB**: 빈 DB 전체 migration, 기존 DB upgrade, 제약(FK/UNIQUE/CHECK/index),
      강제 rollback, 재시작 fixture. `pipeline/snapshot/test_integration.py`의
      `pickage_269_test_<uuid>` 패턴을 `DisposableTestDatabase`로 Java 이식(§3.3). 이슈 번호를
      살려 `pickage_314_test_<uuid>` 명명, DROP 전 정규식 재검사도 동일하게 적용.
- [ ] **공용 seed 의존성**: 해결 안 되면 통합 seed gate 미통과로 남긴다. 임의로
      `deploy/local/seed/*.sql`을 고치지 않는다.
