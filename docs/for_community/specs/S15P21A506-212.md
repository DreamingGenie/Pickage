**건드리지 않는다.** `GitHubRepositoryClient`의 `send()`·`checkRateLimit()`는 private라

## 3. 아키텍처 / 데이터 흐름

### 3.1 이슈 선정 (github-active-v1)

```text
GET /search/issues?q=repo:{owner}/{repo}+is:issue+updated:>={180일 전}
    &sort=comments&order=desc&per_page=30
  -> incomplete_results=true 면 SEARCH_INCOMPLETE 제한 기록(계속 진행)
  -> total_count == 0 (raw 0) 이면 365일로 한 번만 확장해 재시도
  -> 받은 상위 30건에서 PR(pull_request 필드 존재)·locked=true·user.type="Bot" 제외
  -> 남은 것 중 댓글 수 desc, 동률이면 updated_at desc, 그다음 issue number desc로
     "이 30건 안에서만" 재정렬
  -> 상위 2건 선택. 필터 후 0건이어도 페이지·기간을 추가로 늘리지 않는다
     (raw 0 이후의 365일 확장과는 다른 경우 — Jira 212 세부 항목)
```

### 3.2 댓글 수집 — 최신 100개 확정

```text
GET .../comments?per_page=100&page=1
  -> Link 헤더에 rel="last" 없음(= 전체 <=100개) -> 이미 전체가 최신 100개, COMPLETE
  -> rel="last" 있음(page L) ->
       GET .../comments?per_page=100&page=L       (2번째 호출)
       GET .../comments?per_page=100&page=L-1      (3번째 호출, L>1일 때만)
       두 페이지의 댓글을 합쳐 id(십진 문자열이지만 비교는 수치로) 내림차순 정렬 후 상위 100개
  -> 호출 사이 댓글 증감·page 실패로 100개를 확정 못 하면:
       일부라도 확보 -> TRUNCATED, limitations에 사유
       하나도 확보 못함 -> FAILED
```

최대 3회 호출로 끝난다(Jira 212 세부 항목과 일치). id는 `String`으로 보존한다 — Phase 1의
`MessagePayload.sourceCommentId`도 이미 `String`이라 downstream(JS 프론트)의 큰 정수
정밀도 손실을 여기서부터 피한다.

### 3.3 rate limit — Search와 core는 다른 quota

Search API(`/search/issues`)는 10/분(비인증)·30/분(인증)으로 core(5,000/시간)와 별도다.
`GitHubIssueSearchClient`는 이 Phase 전용 rate-limit 판정을 갖고, `GitHubIssueCommentsClient`는
213의 `GitHubRepositoryClient`와 같은 core quota를 쓰지만 별도 클래스 인스턴스로 판정한다
(§2 결정 참고). 두 클라이언트 모두 213이 이미 만든 `GitHubRateLimitException`·
`UpstreamFetchException`·`BoundedHttpReader`(패키지 간 공개 타입)는 그대로 재사용한다 —
새로 만드는 것은 HTTP 호출 그 자체와 rate-limit 판정 조건문뿐이다.
