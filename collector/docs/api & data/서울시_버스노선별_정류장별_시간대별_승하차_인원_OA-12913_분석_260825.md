## 3. 인증 및 호출 제한

### 3-1. Open API 명세 (공식 문서 + 2026-08-26 1,000행 호출 검증)

- 서비스명: **`CardBusTimeNew`** — 공식(포털 Open API 탭)
- 인증 방식: **일반 인증키**, query 아닌 URL path 세그먼트로 전달 — 공식
  ```
  http://openapi.seoul.go.kr:8088/(인증키)/(TYPE)/CardBusTimeNew/(START_INDEX)/(END_INDEX)/(USE_YM)/(RTE_NO 선택)/
  ```
- API 키 발급처: `data.seoul.go.kr` 마이페이지 인증키 안내 — 공식
- 기본 일일 호출 한도: **미확인**. 서울 열린데이터광장 공식 이용안내는 실시간 지하철 API의 1,000회 한도만 명시하며, 이 일반 API의 일일 횟수를 명시하지 않는다. 이번 진단은 provider 한도 주장이 아닌 내부 20회 상한으로 수행했다.
- 1회 최대 조회건수: **1,000건** — 공식(위 이용안내 원문 및 개별 서비스 에러 메시지 `ERROR-336` 동일 명시)
- 이용 제약: *"이용 제약 없이 계속 사용하시려면 활용사례(갤러리)에 인증키와 함께 컨텐츠를 등록하세요"* — 갤러리 미등록 시 정확한 제약 수치는 **미확인**(공식 문서에 수치 없음)

### 3-2. 실제 접근성 — **포트별 상이 (2026-08-26 호출 관측)**

과거 조사에서는 8088 연결 실패가 관측됐지만, 2026-08-26 재관측에서는 8088이 성공하고 8080이 timeout이었다. 따라서 포트별 네트워크 상태를 분리 기록한다.

| 시도 경로 | 방식 | 결과 |
|---|---|---|
| `openapi.seoul.go.kr:8088` | 서울시 Open API 첫 페이지 1,000행 호출 | **HTTP 200 / `INFO-000`, 정상 응답** |
| `openapi.seoul.go.kr:8080` | 동일 요청의 포트 변경 | **timeout** |
| Claude Code 클라우드 세션 (Chrome 브라우저 실제 내비게이션) | 브라우저 직접 접속 | 페이지 로드 실패 (`chrome-error://`), 상호작용 불가 상태로 전환 |
| **조사자 로컬 PC (SSAFY 교육망으로 추정)** | PowerShell `Invoke-WebRequest`, 15개 테스트 케이스 전체 | **전부 `TIMEOUT/NOCONN`, 각 약 21초** — 로컬 실제 네트워크에서도 동일하게 실패 |

대조군과 새 관측을 함께 보면 DNS·호스트는 정상이고 포트별 상태가 다르다. `:8088`은 현재 호출 가능하지만 `:8080`은 timeout이므로 수집기는 8088을 사용하고 포트 장애를 별도로 모니터링한다.

- [x] API 키로 실제 1,000행 호출 — **8088에서 HTTP 200 / `INFO-000` 성공**. 8080 timeout은 별도 포트 장애로 기록한다.

## 4. 요청 방법 (공식 문서 기준, 실호출 미검증)

- HTTP Method: **GET**
- Endpoint: `http://openapi.seoul.go.kr:8088/(인증키)/(TYPE)/CardBusTimeNew/(START_INDEX)/(END_INDEX)/(USE_YM)/(RTE_NO)/`
- 응답 형식: **XML(기본) / XML파일 / 엑셀파일(xls) / JSON** — `TYPE` 파라미터로 선택. 공식 예시는 XML 사용
- 요청 파라미터 (공식 "요청인자" 표 전문):

| 파라미터 | 타입 | 필수여부 | 설명 |
|---|---|---|---|
| `KEY` | String | 필수 | 인증키 |
| `TYPE` | String | 필수 | `xml`/`xmlf`/`xls`/`json` |
| `SERVICE` | String | 필수 | `CardBusTimeNew` 고정 |
| `START_INDEX` | INTEGER | 필수 | 페이징 시작위치(데이터행 시작번호) |
| `END_INDEX` | INTEGER | 필수 | 페이징 종료위치 |
| `USE_YM` | STRING | 필수 | `YYYYMM` |
| `RTE_NO` | STRING | 선택 | 노선번호 필터 |

- 오류 코드 (공식 "메시지 설명" 표 전문 — **파라미터 계약 이해에 중요, 실동작은 미검증**):

| 코드 | 의미 |
|---|---|
| `INFO-000` | 정상 처리 |
| `INFO-100` | 인증키가 유효하지 않음 |
| `INFO-200` | 해당하는 데이터가 없음 |
| `ERROR-300` | 필수 값 누락 |
| `ERROR-301` | 파일타입값 누락/유효하지 않음 (TYPE) |
| `ERROR-310` | 해당 서비스를 찾을 수 없음 (SERVICE) |
| `ERROR-331`/`332`/`333` | START_INDEX/END_INDEX 값 오류 |
| `ERROR-334` | 요청종료위치가 시작위치보다 작음 |
| `ERROR-335` | 샘플키(`sample`) 사용 시 1회 최대 5건, 인덱스 1~5만 허용 |
| `ERROR-336` | **한 번에 최대 1,000건** 초과 (END−START ≤ 1000) |
| `ERROR-500`/`600`/`601` | 서버·DB·SQL 오류 |

  - 자정 이후(00시)는 **역일(calendar day) 00시**이며 "익일 새벽 운행분"이 아니다. 즉 이 데이터는 **운행일(service day)이 아니라 역일 기준**으로 집계된다 — ASOS 보고서 §6에서 지적한 "운행일과 역일 경계가 다르다"는 원칙이 여기서도 적용되며, 심야버스(`서울심야버스`, 00~05시대 운행)의 심야 승하차가 **자정을 넘어도 다음 날짜의 00~04시 구간에 배분될 개연성이 높다** — 단, 이는 추정이며 확정하려면 특정 노선의 자정 전후 시간대별 값을 심야 운행 스케줄과 대조해야 한다(**미확인**, §12 TODO)
- 갱신 주기: **월 1회, 매월 5일 전월 데이터 확정** — 공식, 실측 정확히 일치
- 수집시각과 제공시각의 차이: 대상월 종료 후 최소 3일(등록일자 기준), 최대 약 1개월+5일(월초 조회 시)

## 7. 식별자 — **기존 분석 보고서와의 대조 (핵심 발견)**

- 노선 식별자: **`RTE_NO`만으로는 유일하지 않다.** 202607 표본에서 **같은 `RTE_NO`에 서로 다른 `RTE_NM`이 붙는 경우가 16건** 확인(파일 분석 전수조사) — 전부 **양방향 노선(왕복 기점·종점이 다른 텍스트로 표기)** 패턴이다.

  | RTE_NO | RTE_NM 후보 |
  |---|---|
  | `N37` | `N37번(진관공영차고지~송파공영차고지)`, `N37번(송파공영차고지~진관공영차고지)` |
  | `N31` | `N31강동(강동공영차고지~국민대)`, `N31정릉(국민대~강동공영차고지)` |
  | `N51`, `N75`, `N16` 등 | (동일 패턴) |

  → **방향 구분 코드가 별도 필드로 존재하지 않고, `RTE_NM` 텍스트 파싱으로만 방향을 알 수 있다.** 내부 표준화 시 `(RTE_NO, 파싱된 기점, 파싱된 종점)`을 복합키로 쓰거나, 이 데이터만으로는 방향을 신뢰성 있게 특정할 수 없다고 간주해야 한다.
- 정류장 식별자: **`STOPS_ID`(9자리)와 `STOPS_ARS_NO`(5자리) 두 종류가 동시 제공된다.**
  - `STOPS_ID` 예시 `100000001` — 이미 검증된 `서울특별시_버스도착정보조회_서비스_15000314_분석_260825.md`의 `stId`(예 `111000299`, "정류소 고유 ID, 문서상 9자리")와 **자릿수·명명 패턴이 일치**한다
  - `STOPS_ARS_NO` 예시 `01001` — 같은 보고서의 `arsId`(예 `12390`, "정류소 안내용 번호")와 **자릿수·용도가 일치**한다
  - → **`STOPS_ID ≈ stId`, `STOPS_ARS_NO ≈ arsId`일 가능성이 높다(강한 정황 증거, 실제 값 교차조회로 100% 확정은 아직 안 됨 — §12 TODO).** 맞다면 이미 그 보고서가 제안한 `canonical_stop_crosswalk(provider, stId, arsId, ...)` 설계를 이 데이터로 바로 채울 수 있다
  - 다만 **`STOPS_ID` 고유값 12,534개와 `STOPS_ARS_NO` 고유값 12,362개가 다르다** — 즉 일부 표준ID가 같은 ARS번호를 공유하거나 그 반대 케이스가 존재한다(1:1이 아님). 정확한 불일치 패턴은 **미확인**(§12 TODO)
- 다른 API와 ID가 동일한지: `STOPS_ID`/`STOPS_ARS_NO` 가설상 일치(위 참고), `RTE_NO`는 `서울시_버스노선_기본정보_항목정보_OA-15262` 보고서의 `routeId`(예 `"100100124"`, 12자리 내부 코드)와는 **형식이 다르다** — `RTE_NO`(`N37`, `100` 등)는 사용자 표기용 노선번호이지 `routeId` 내부 코드가 아니다. 노선 매핑이 필요하면 `RTE_NM`의 노선번호 부분과 `서울시버스노선ID정보` 마스터의 매핑을 거쳐야 한다
- 내부 표준 ID 매핑 필요 여부: **예** — 정류장은 `STOPS_ID`/`STOPS_ARS_NO` 교차검증 후 크로스워크 테이블에 바로 편입 가능할 것으로 보이며, 노선은 `RTE_NO`+`RTE_NM` 파싱을 거쳐 `routeId`로 매핑해야 한다

## 8. 수집 계획 (설계안 — **Open API가 아니라 파일 다운로드 기준으로 재설계**)

- **수집 방식: 월별 파일 다운로드(파일 적재) 1차, Open API 보조 검증.** 8088 첫 페이지 1,000행 호출은 성공했지만 전체 43,171행 페이징 계약이 미검증이므로 파일 경로를 운영 기준으로 유지한다.
  - 포털 "파일내려받기" 섹션에 월별 CSV가 개별 파일로 게시된다(2026년 07월분 확인: `2026년_버스노선별_정류장별_시간대별_승하차_인원_정보(07월).csv`, 15.45MB)
  - 다운로드는 표준 HTTPS(443)로 이뤄지며 인증키·서버측 API 호출이 필요 없다 — **실질적으로 quota/호출한도 개념 자체가 무관해진다**
- 수집 주기: **월 1회, 매월 6~10일경**(공식 갱신일 5일 + 며칠 여유) 최신 월 파일 존재 확인 후 다운로드
- 수집 범위: 신규 게시되는 최신 월 1개 파일 + (최초 1회) 과거 월 전체 backfill. 과거 몇 년치까지 파일로 제공되는지는 **미확인**(§12 TODO, 파일 목록 전체 스크롤 필요)
- 원문 저장 여부: **저장**. CSV 원본을 그대로 보관(공공누리 제1유형이라 재배포·가공 제약 없음)
- 저장 위치(설계안): 원문 `raw/seoul_bus_boarding/ym=YYYYMM/원본파일명.csv`, 파싱본 RDB `bus_stop_boarding_hourly`
- 재시도 정책(설계안): 파일 다운로드 실패 시 지수 백오프. **매월 5일 직후 파일이 아직 안 올라왔을 수 있으므로, 존재 확인 후 재시도**(빈 목록이면 다음날 재확인)
- 중복 판정 기준: `(USE_YM, RTE_NO, RTE_NM, STOPS_ID)` 복합키. 단, §7에서 확인했듯 `RTE_NO` 단독은 유일하지 않으므로 **`RTE_NM`까지 포함**해야 방향이 다른 두 레코드가 합쳐지지 않는다
- **인코딩 주의**: 다운로드한 CSV는 **CP949(EUC-KR 계열)** 인코딩이었다 — UTF-8로 그냥 열면 완전히 깨진다(파일 분석 확인). 수집기는 반드시 `cp949` → `utf-8` 변환을 거친다
