### 핵심 판정

이 API는 실시간 버스 도착 API가 아니라 **월 1회 갱신되는 정류장별 도착·출발 이력 API**다. Journey Reliability에서는 버스 `WAIT`, `RIDE`, 정차시간, 배차간격의 historical distribution 후보로 사용할 수 있다. 단일 행이나 단일 월 데이터를 `P(on_time)` 또는 추천 출발시각으로 직접 변환하지 않으며, ID·시간·coverage 검증과 temporal hold-out을 통과한 파생분포만 Reliability Engine에 제공한다.

## 1. 개요

- 제공기관: **버스정보시스템(BIS)**
  - 제공부서: 서울특별시 미래첨단교통과
  - T-DATA 담당자 표시: 김석곤
- 공식 문서: [배차 정류장별 이력 data_id=1068](https://t-data.seoul.go.kr/dataprovide/trafficdataviewopenapi.do?data_id=1068)
- 데이터 분류: **버스 / Open API / JSON**
- 데이터 유형: **과거 이력**
  - 정류장별 도착·출발 일시가 포함된 배차 이력이다.
  - 갱신주기는 월 1회이므로 현재 버스 위치나 실시간 ETA가 아니다.
  - 계획시간표 자체도 아니며, `planId`만으로 계획시각을 알 수 없다.
- 프로젝트 활용 목적:
  - 노선·운행·정류장 순서별 버스 도착·출발 이력 적재
  - 시간대·요일·노선·정류장별 `BUS_WAIT`·`BUS_RIDE` 경험분포 생성
  - 정차시간, 구간 운행시간, 실제 배차간격의 품질 플래그 포함 통계 생성
  - 별도 계획 데이터와 결합해 계획 대비 residual 후보 생성
- 적용 기능:
  - [x] 현재 출발 시 도착확률 — historical baseline 입력으로만 사용; 현재 교통 context는 별도 실시간 API 필요
  - [x] 목표 도착시각 기준 출발 추천 — 후보별 historical `WAIT`·`RIDE` 분포 입력으로 사용; 현재 스냅샷은 사용하지 않음

> 이 API는 최종 `P(on_time)`이나 추천 출발시각을 제공하지 않는다. 프로젝트의 두 기능은 각각의 API·result 계약을 유지하고, 이 데이터는 내부 leg distribution source로만 공유한다.

## 2. 제공 범위

- 지역 범위:
  - T-DATA는 서울 교통데이터 통합 제공 플랫폼이며, 이 데이터의 원천은 서울시 BIS다.
  - data_id=1068 상세 페이지에는 포함 행정구역이나 서울시 외 회차 구간 포함 여부가 명시되지 않는다.
  - 따라서 행정경계 coverage는 정류장 기준정보와 실제 고유 `sttnId`를 대조해 확정한다.
- 노선·운영기관 범위:
  - `routeId` 필터를 제공하지만 노선 유형, 운영회사, 시내·마을·광역버스 포함 범위는 공식 상세 페이지에 없다.
  - 응답에 노선명·운영기관 필드가 없으므로 BIS 노선 마스터와 조인해야 한다.
- 제공 기간:
  - 공개일: `2021-12-01`
  - 공식 샘플 기준일: `20211219`
  - 실제 조회 가능한 최초·최종 `stdrDe`는 **미확인**이다.
  - 샘플 날짜를 데이터 보유 시작일로 해석하지 않는다.
- 과거 이력 제공 여부: **예**
  - 데이터셋 제목과 설명이 정류장별 도착·출발 이력임을 명시한다.
- 데이터 갱신 주기: **월 1회**
  - 2026-08-25 확인 당시 공식 페이지 수정일도 `2026-08-25`였다.
  - 페이지 수정일은 데이터의 최신 `stdrDe`나 월별 확정일을 의미하지 않는다.
- 실제 데이터 지연시간: **미확인**
  - 월별 배치의 생성일, 전월 마감일, 수정 재배포 정책이 공개되지 않았다.
  - 실제 키 발급 후 매 수집 시점의 `max(stdrDe)`와 `fetched_at` 차이를 기록해 측정한다.

## 3. 인증 및 호출 제한

- 인증 방식:
  - T-DATA에서 발급한 `apikey` 사용
  - 공식 요청인자 표에서 `apikey`는 유일하게 필수로 표시된다.
  - invalid key를 query string의 `apikey`로 보냈을 때 gateway가 해당 키를 인식해 `404`를 반환했다. 따라서 query-string 전달은 gateway 인식까지 확인됐고, 유효 키의 정상 호출 계약은 아직 미검증이다.
- API 키 발급처:
  - T-DATA에 서울시 통합계정으로 로그인
  - data_id=1068 상세 페이지에서 **활용신청**
  - 신청 결과와 키는 `나의 데이터 신청관리`의 신청데이터·인증키 발급현황에서 확인
- 기본 일일 호출 한도: **개발자 활용신청 기준 하루 최대 1,000건 요청**
- 초당 호출 한도: **공식 미공개**
- 호출량 증액 가능 여부: **공식 미공개**
  - 대량 초기 backfill 전에 담당부서 또는 T-DATA 문의 채널로 확인한다.
- 이용요금:
  - T-DATA 정책은 공공데이터의 무료 제공을 원칙으로 한다.
  - data_id=1068에 별도 과금 표시는 없다.
- 이용약관·라이선스:
  - 데이터셋 표시 조건: **저작자표시(BY)**
  - 이용·변경·2차적 저작물 작성이 가능하되 저작자, 저작물 제목, 출처를 표시해야 한다.
  - 수집 시 상세 페이지 URL, 취득일, 라이선스 상태를 provenance에 저장한다.

### 보안 규칙

- `apikey`를 프론트엔드, URL 예시의 실제 값, 저장소, 분석 로그에 노출하지 않는다.
- backend collector에서만 호출하고 query string·proxy·APM 로그의 키를 마스킹한다.
- `403`·`404` 인증 오류에 키를 바꾸며 반복 호출하지 않는다.

## 4. 요청 방법

- HTTP Method: **GET — gateway 도달 확인, 유효 키 성공 미검증**
  - 공식 페이지는 method를 명시하지 않는다.
  - 2026-08-25 익명 `GET`이 API gateway까지 도달한 사실만 확인했다.
  - `GET`과 query-string `apikey`는 gateway 인식까지 확인했지만, 유효 키의 성공 응답 전에는 정상 호출 계약으로 확정하지 않는다.
- 공식 Endpoint:

```text
http://t-data.seoul.go.kr/apig/apiman-gateway/tapi/BisTbisClCaralcSttn/1.0
```

- 운영 후보 Endpoint:

```text
https://t-data.seoul.go.kr/apig/apiman-gateway/tapi/BisTbisClCaralcSttn/1.0
```

공식 URL은 HTTP지만 실제 호출에서는 HTTPS로 `302` 리디렉션됐다. collector는 실제 키로 HTTPS 직접 호출을 검증한 뒤 canonical endpoint로 고정한다.

- 응답 형식: **JSON**
- 필수 파라미터:

| 파라미터 | 설명 | 예시 | 공식 필수 여부 | 수집기 기준 |
| --- | --- | --- | --- | --- |
| `apikey` | T-DATA 인증키 | `{API_KEY}` | 필수 | 필수, 로그 마스킹 |
| `startRow` | 시작행번호 | `1` | 미표기 | 필수로 사용 |
| `rowCnt` | 한 페이지 결과 수 | `100` | 미표기 | 검증된 최댓값 이하로 필수 사용 |
| `stdrDe` | 기준일, `yyyyMMdd` | `20211219` | 미표기 | 날짜 파티션을 위해 필수 사용 |
| `routeId` | BIS 노선 ID | `100100012` | 미표기 | 노선 파티션을 위해 필수 사용 |

공식 표의 변수 크기는 `apikey=100`, `startRow=4`, `rowCnt=10`, `stdrDe=8`, `routeId=10`으로 표시된다. 이를 숫자 최댓값이나 페이지 상한으로 임의 해석하지 않는다.

### 요청 예시

다음 URL은 gateway 인식이 확인된 **GET/query-string 형식**이며, 유효 키의 성공 검증이 남아 있다.

```http
GET https://t-data.seoul.go.kr/apig/apiman-gateway/tapi/BisTbisClCaralcSttn/1.0?apikey={API_KEY}&startRow=1&rowCnt=100&stdrDe=20211219&routeId=100100012
Accept: application/json
```

### 인증 전 관측 응답

```http
HTTP/1.1 302 Found
Location: https://t-data.seoul.go.kr/apig/apiman-gateway/tapi/BisTbisClCaralcSttn/1.0

HTTP/1.1 403
X-Gateway-Error: API not public.
Content-Type: application/json
```

```json
{
  "responseCode": 403,
  "message": "관리자에게 문의 바랍니다.",
  "trace": ""
}
```

이 응답은 endpoint 도달과 인증 필요성만 증명한다. 정상 데이터 응답의 스키마는 증명하지 않는다.

## 5. 응답 데이터

공식 출력표는 snake_case와 camelCase를 혼용하고, 공식 샘플은 camelCase를 사용한다. raw parser는 실제 키 응답을 확보하기 전까지 두 표기를 모두 받아들이되 원문 키를 보존한다.

| 공식 출력 필드 | 샘플 JSON 키 | 의미 | 공식 타입 | 샘플 | 저장 여부·내부 타입 |
| --- | --- | --- | --- | --- | --- |
| `stdr_de` | `stdrDe` | 기준 일자 | `CHAR(8)`, 필수 | `20211219` | 예, `service_date_raw` string |
| `route_id` | `routeId` | 노선 ID | `NUMBER(9)`, 필수 | `100100012` | 예, string |
| `run_sn` | `runSn` | 운행순번 | `NUMBER(9)`, 필수 | `1` | 예, raw string + nullable integer |
| `sttn_sn` | `sttnSn` | 정류장순번 | `NUMBER(9)`, 필수 | `1` | 예, raw string + nullable integer |
| `plan_id` | `planId` | 운행계획 ID | `NUMBER(9)`, 필수 | `1` | 예, string |
| `start_dt` | `startDt` | 출발 일시 | `DATE`, 선택 | `20211219041000` | 예, raw string + parsed local datetime |
| `sttn_id` | `sttnId` | 정류장 ID | `NUMBER(9)`, 선택 | `207000427` | 예, string |
| `rm` | `rm` | 비고 | `VARCHAR(1000)`, 선택 | 샘플에 없음 | 예, nullable string |
| `arvlDt` | `arvlDt` | 도착 일시 | `DATE`, 선택 | `20211219041000` | 예, raw string + parsed local datetime |

공식 샘플 미리보기에서는 `NUMBER`·`DATE` 필드도 JSON 문자열로 표시된다. 이는 성공 응답 전체 계약으로 일반화하지 않고, 식별자는 산술 대상이 아니므로 문자열을 canonical raw type으로 사용한다.

### 공식 응답 예시

공식 페이지의 샘플 미리보기는 한 개의 논리 행을 다음과 같이 표시한다.

```json
{
  "routeId": "100100012",
  "stdrDe": "20211219",
  "sttnSn": "1",
  "sttnId": "207000427",
  "runSn": "1",
  "planId": "1",
  "arvlDt": "20211219041000",
  "startDt": "20211219041000"
}
```

### 성공 응답에서 미확인인 계약

- 최상위 JSON이 배열인지 객체인지
- 데이터 배열 필드명
- 총 건수·현재 페이지·다음 페이지 필드
- `rowCnt` 최대값과 마지막 페이지 판정 방법
- snake_case와 camelCase 중 실제 키 표기
- 선택 필드의 `null`, 빈 문자열, 누락 표현
- 정상·오류 코드 표

페이지의 `메시지 설명` 탭은 2026-08-25 직접 렌더링해 확인했을 때 비어 있었다. 별도 화면 캡처 artifact는 보존하지 않았다. 실제 키 최초 호출의 status, header, body, hash를 계약 fixture로 저장해야 한다.

## 6. 시간 데이터 해석

- 제공기관 데이터 생성시각 필드:
  - 별도의 응답 생성시각·배치 생성시각 필드는 없다.
  - `stdrDe`는 기준일, `arvlDt`는 도착 일시, `startDt`는 출발 일시다.
- 예측시각 또는 실제시각 여부:
  - 공식 명칭과 설명은 도착·출발 **이력**으로 분류한다.
  - ETA나 예정시각 필드는 아니다.
  - 다만 BIS가 해당 시각을 어떤 이벤트·보정 로직으로 확정하는지는 문서에 없으므로 `ground_truth actual`이 아니라 **provider-recorded historical event time**으로 취급한다.
- 시간대: **공식 미공개**
  - 샘플은 `yyyyMMddHHmmss`로 해석 가능한 14자리 문자열이다.
  - 원문을 보존하고, 실제 서울 BIS 데이터 확인 후 `Asia/Seoul` 해석을 승인한다.
- 자정 이후 운행일 처리 방식: **공식 미공개**
  - `stdrDe`를 provider service-day 원문으로 보존한다.
  - `arvlDt`·`startDt`의 달력 날짜가 다음 날이어도 수집기에서 임의로 `stdrDe`를 변경하지 않는다.
  - 유효한 심야 표본으로 `stdrDe`, `planId`, `runSn`의 경계 규칙을 검증한다.
- 수집시각과 제공시각의 차이:
  - 행에 source publish timestamp가 없어 API delivery lag를 직접 계산할 수 없다.
  - 월별 수집마다 `fetched_at - max(event_time)`과 `fetched_at_date - max(stdrDe)`를 각각 기록하되, 첫 값은 사건 발생 이후 경과시간이지 API 처리 지연의 정확한 값은 아니다.
- 시간표 기준인지 실제 관측값인지:
  - 시간표가 아니라 이력성 운행 이벤트다.
  - `planId`는 계획 식별자일 뿐 계획 도착·출발 시각을 제공하지 않는다.
  - 계획 대비 지연을 계산하려면 별도 운행계획·시간표 데이터가 필요하다.

> 이 문서에서는 `arvlDt`·`startDt`를 계획값이나 예측값으로 부르지 않는다. 동시에 제공기관의 이벤트 확정 로직이 공개되기 전에는 물리적 도착·출발의 절대적 ground truth라고도 부르지 않는다.

## 7. 식별자

- 노선 식별자: `routeId`
  - 숫자로 보여도 string으로 보존한다.
  - 노선명·운영기관은 별도 BIS 노선 마스터와 조인한다.
- 차량·열차 식별자: **없음**
  - data_id=1068에는 `vehId`가 없다.
  - `(stdrDe, routeId, planId, runSn)`을 운행 인스턴스 후보 키로 사용하되 실제 유일성을 먼저 검증한다.
  - 차량 단위 분석에는 관련 data_id=1069의 `vehId`가 필요하다.
- 정류장·역 식별자: `sttnId`
  - `sttnSn`은 정류장 ID가 아니라 운행·경로 안의 순번이다.
- 방향 식별 방식:
  - 명시적인 상·하행 또는 방향 필드가 없다.
  - 동일 `routeId`의 `planId`·`sttnSn` 순서와 노선 경로 마스터를 결합해 방향을 파생해야 한다.
  - 회차·단축운행·분기 노선은 순번만으로 임의 추론하지 않는다.
- 다른 API와 ID가 동일한지: **공식 보장 미확인**
  - 동일 BIS 계열의 route/station master와 조인 후보지만, 실제 중복률·미매핑률을 측정하기 전에는 동일 ID 계약으로 승격하지 않는다.
- 내부 표준 ID 매핑 필요 여부: **필요**
  - `provider=tdata-bis`, `provider_route_id`, `provider_stop_id`, 유효기간을 포함한 crosswalk를 둔다.
  - 노선번호·정류장명만으로 자동 매핑하지 않는다.

## 8. 수집 계획

- 수집 방식: **월별 배치 backfill + 재검증 수집**
  - 실시간 폴링 대상이 아니다.
  - 초기 적재는 날짜·노선 파티션으로 제한하고 quota 내에서 재개 가능한 job으로 실행한다.
- 수집 주기:
  - 월 1회 정규 수집
  - 정규 수집 7일 뒤 같은 파티션을 한 번 재조회해 보정·재배포 여부 확인
  - 정확한 월 배포일을 3개월 이상 관측한 뒤 schedule 확정
- 수집 범위:
  - 프로젝트 서울 corridor에 필요한 버스 노선과 날짜부터 시작
  - coverage와 quota가 검증된 뒤 전체 노선·장기 기간으로 확장
  - 요청마다 `stdrDe`, `routeId`, `startRow`, `rowCnt`를 명시
- 원문 저장 여부: **예**
  - 응답 body, HTTP status/header의 허용 목록, 요청 fingerprint, `fetched_at`, hash를 저장
  - 인증키와 전체 query string은 저장하지 않음
- 저장 위치 설계안:

```text
raw/bus-stop-operation-history/provider=tdata/dataset=1068/ingestion_date=YYYY-MM-DD/stdr_de=YYYYMMDD/route_id={routeId}/start_row={startRow}/body_sha256={sha256}.json.gz
```

- 재시도 정책:
  - timeout·connection reset·HTTP `429`·`5xx`: exponential backoff + jitter, 최대 3회
  - HTTP `401`·`403`·`404`: 자동 재시도 금지, 키·활용승인·요청 계약 점검
  - 하루 900회에서 신규 backfill 중단, 100회를 재시도·검증 여유로 보존
  - 날짜가 바뀌어도 실패 cursor를 자동 초기화하지 않음
- 중복 판정 기준:
  - raw: `body_sha256`가 같아도 각 수집의 provenance는 보존
  - normalized: 정류장 이벤트 후보 키와 event timestamp를 함께 비교
  - 같은 키에 값이 달라지면 중복 제거가 아니라 `revision`으로 저장

### 최초 키 발급 후 계약 테스트 순서

1. 최소 범위 `rowCnt=1`, 샘플 `stdrDe`·`routeId`로 유효 키 `GET` 성공과 정상 응답 계약 확인
2. HTTP status, content type, body bytes, JSON 최상위 구조, 필드 casing 저장
3. `rowCnt=1/10/100`과 `startRow=1/2`로 페이지 의미 확인
4. 필터 누락·잘못된 날짜·없는 노선으로 오류 계약 확인
5. 같은 요청을 근접 시각에 반복해 응답 안정성·수정 여부 확인
6. 하루 quota가 request 단위인지 endpoint·key 단위인지 portal usage에서 대조

  1. 원문 JSON과 원문 키를 먼저 저장한다.
  2. sample의 camelCase와 명세의 snake_case를 alias map으로 정규화한다.
  3. 모든 provider ID는 string으로 저장한다.
  4. `stdrDe`는 8자리, event time은 14자리인지 검증하고 실패 행을 quarantine한다.

  8. 실제 API 가용기간과 결측분포를 확인하기 전에는 통계 산출 자격을 `STRUCTURE_ONLY`로 둔다.
- 다른 데이터와 결합할 키:
  - BIS 노선 마스터: `routeId`
  - BIS 정류장 마스터: `sttnId`
  - 차량운행별 이력 data_id=1069: `stdrDe + routeId + planId + runSn`
  - 노선 경로·방향: `routeId + planId + sttnSn` 후보
  - 시간표·운행계획: provider `planId` 또는 검증된 route/service-day/run crosswalk
- 모델 입력 변수:
  - 시간대·요일·공휴일·노선·방향·정류장/구간
  - 구간 운행시간, 정차시간, 배차간격, 이전 구간 residual
  - sample count, missing rate, revision rate, source age
  - corridor coverage와 identity confidence

  - 공식 drop-in 대체 API는 확인되지 않았다.

  - 실제 키 없이는 gateway `403`으로 차단됨

  - 성공 response envelope·paging metadata가 공개되지 않음
  - 명세 필드 casing과 샘플 JSON casing이 다름
  - 선택 필드의 null 계약과 오류코드 표가 없음
  - 보유기간·월 배포일·실제 data lag·시간대·service-day 경계가 미공개
  - 차량 ID와 방향 필드가 없어 단독으로 정확한 trip/vehicle identity를 확정할 수 없음
