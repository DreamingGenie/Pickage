## 1. 개요

- 제공기관: 서울특별시
  - 제공부서: 교통실 교통기획관 미래첨단교통과
  - 원본시스템: 서울시 교통정보 시스템(TOPIS)
  - 저작권자: 서울시
- 공식 문서: [OA-12601 데이터셋](https://data.seoul.go.kr/dataList/OA-12601/A/1/datasetView.do)
- 데이터 분류: 교통 / 지하철 / Open API / 원본형태 DB
- 데이터 유형: **실시간**
  - 호출 시점의 열차 위치 관련 역·상태 스냅샷을 제공한다.
  - 정적 기준정보, 운행시각표, 과거 운행이력 API가 아니다.
- 프로젝트 활용 목적:
  - 현재 운행 중인 열차의 노선·역·방향·상태·종착역을 실시간 feature로 사용
  - 반복 관측으로 역 진입·도착·출발 전이와 구간 운행시간·배차간격을 **추정**
  - 도착정보 API의 Prediction과 결합하여 Actual 후보 및 residual 생성
  - 신선한 현재 상태를 현재 출발 분석과 이동 중 reforecast의 보조 근거로 사용
- 적용 기능:
  - [x] 현재 출발 시 도착확률 — **실시간 상태 보정용 보조 입력으로 조건부 적용**
  - [ ] 목표 도착시각 기준 출발 추천 — 이 API만으로는 불가하며 장기 이력·시간표·WAIT·환승·보행 분포가 추가로 필요

> 이 API는 ETA, 도착예정시각, 확정 도착시각을 직접 제공하지 않는다. 두 프로젝트 기능의 최종값을 이 API 응답만으로 계산하거나 표시하지 않는다.

## 3. 인증 및 호출 제한

- 인증 방식:
  - 서울 열린데이터광장 **실시간 지하철 인증키**를 URL 경로의 `KEY`에 넣는다.
  - Header/OAuth 방식이 아니다.
  - 문자열 `sample`은 공개 테스트 키이며 운영용 무인증 호출을 뜻하지 않는다. 임의의 잘못된 키는 `INFO-100`을 반환했다.
- API 키 발급처:
  - [서울 열린데이터광장 인증키 신청·관리](https://data.seoul.go.kr/together/mypage/actkeyMain.do)
  - [실시간 지하철 전용 신청 화면](https://data.seoul.go.kr/together/mypage/actkeyMetroReq_ss.do) — 로그인 session 필요
- 기본 일일 호출 한도: **인증키 1개당 1,000회/일**
- 1회 조회 한도: 공식 안내상 최대 **1,000건/회**
- 초당 호출 한도: **공식 미공개**
- 호출량 증액 가능 여부:
  - 일반적인 숫자 단위 증액 절차와 처리 SLA는 미공개다.
  - Open API 이용안내는 활용사례와 인증키를 갤러리에 등록하라고 안내하고, FAQ는 실제 공개 서비스가 심사·승인 완료되면 호출 제한 없이 사용할 수 있다고 설명한다.
  - 심사 기준·처리기간·승인 보장은 미공개다.
  - 승인 여부를 release 전제로 두지 않고 기본 한도 내 축소 운영안을 유지한다.
- 이용요금: **별도 API 호출 과금표·유료 플랜은 확인되지 않음**
  - 공공누리 제1유형 일반증서는 이용조건 준수 시 해당 공공저작물을 무료로 이용할 수 있다고 설명한다.
  - 공공저작물 이용조건과 API 호출량·지속 제공 SLA는 별개이므로 정책 변경을 주기적으로 확인한다.
- 이용약관·라이선스:
  - 데이터셋 표시: **공공누리 제1유형** — 출처표시 조건으로 상업적 이용과 변경 가능
  - 결과 노출 시 “서울특별시 공공데이터” 사용 사실을 명시한다.
  - 인증키를 타인에게 제공·공개·공유하지 않는다.
  - 서비스 범위·횟수 제한·중단 가능성과 데이터 정확성 비보증 조건을 수용해야 한다.

## 4. 요청 방법

- HTTP Method: `GET`
- Endpoint:

```text
http://swopenAPI.seoul.go.kr/api/subway/{KEY}/{TYPE}/realtimePosition/{START_INDEX}/{END_INDEX}/{subwayNm}
```

- 응답 형식: **JSON / XML**
  - JSON과 XML은 공개 샘플로 확인했다.
  - API 화면의 공통 형식 설명에는 `xmlf`, `xls`도 나타나지만 FAQ는 실시간 지하철의 XLS 미지원을 안내하므로 수집기는 JSON/XML만 사용한다.
  - CSV는 제공하지 않는다.
- 필수 파라미터:

| 파라미터 | 설명 | 예시 | 필수 여부 | 주의사항 |
| --- | --- | --- | --- | --- |
| `KEY` | 실시간 지하철 인증키 | `sample` | 필수 | `sample`은 smoke test 전용, 운영에서는 발급키 사용 |
| `TYPE` | 응답 형식 | `json`, `xml` | 필수 | 대소문자와 지원 형식 확인 |
| `SERVICE` | 서비스명 | `realtimePosition` | 필수 | 고정 literal |
| `START_INDEX` | 요청 시작 위치 | `0` | 필수 | 공식 OA-12601 샘플은 `0/5`; 운영키의 index 경계는 별도 테스트 필요 |
| `END_INDEX` | 요청 종료 위치 | `5` | 필수 | 1회 최대 1,000건, 공개 sample은 실제 관측상 정확히 `0/5`만 성공 |
| `subwayNm` | 지하철 노선명 | `1호선` | 필수 | URL encoding 필요, 여러 노선 결합 문법은 공식 지원되지 않음 |

### 요청 예시

운영용 형식:

```http
GET http://swopenAPI.seoul.go.kr/api/subway/{SEOUL_SUBWAY_REALTIME_KEY}/json/realtimePosition/0/1000/1호선
```

공개 샘플 smoke test:

```http
GET http://swopenAPI.seoul.go.kr/api/subway/sample/json/realtimePosition/0/5/1호선
```

> 공식 예시는 HTTP URL이고 이번 환경에서 HTTPS 연결은 확인하지 못했다. 인증키가 URL 경로에 있으므로 frontend/browser에서 직접 호출하지 않고 backend collector에서만 호출한다. 운영 전 안전한 전송 경로와 배포망의 DNS·TLS·proxy 정책을 별도 검증한다.

## 5. 응답 데이터

## 6. 시간 데이터 해석

- 제공기관 데이터 생성시각 필드: **[공식]**
  - 별도의 생성시각 필드는 없다.
  - `lastRecptnDt`와 `recptnDt`는 공식 설명상 **최종 수신 날짜·시각**이다.
- 예측시각 또는 실제시각 여부: **[공식 설명 + 내부 해석]**
  - `recptnDt`는 예측 도착시각도, 확정 역 도착시각도 아니다.
  - **[해석]** 공급자가 해당 열차 위치·상태를 최종 수신한 source timestamp로 취급한다.
  - **[설계안]** `trainSttus`는 `observed_status`로 저장하고, 연속 전이로 만든 도착·출발은 관제 확정값과 구분되는 `inferred_event`로 관리한다.
- 시간대: **[공식 미공개 + 내부 설계안]**
  - 응답 문자열에 UTC offset이 없고 공식 문서도 시간대를 명시하지 않는다.
  - 서울 교통 데이터와 실제 샘플의 현지시각 일치를 근거로 내부에서는 `Asia/Seoul`로 파싱하되 `timezone_assumed=true`를 보존한다.
- 자정 이후 운행일 처리 방식: **[공식 미확인 + 내부 설계안]**
  - 공식 미확인이다.
  - `lastRecptnDt`를 원문 보존하고, 내부 `service_date`는 시간표·운행일자 cutoff 규칙을 적용한 뒤 별도로 생성한다.
  - `trainNo`는 날짜가 바뀌면 재사용될 수 있다고 가정하고 단독 영구 ID로 사용하지 않는다.
- 수집시각과 제공시각의 차이: **[관측 + 내부 설계안]**

```text
source_lag_seconds = received_at - parsed(recptnDt, assumed Asia/Seoul)
```

  - `requested_at`, `headers_received_at`, `body_completed_at`을 HTTP 경계에서 각각 기록한다.
  - 2026-08-25 샘플의 18~29초 lag는 관측값이며 노선·시간대별 P50/P95/P99를 장기 측정해 freshness 기준을 정한다.
  - 음수 lag는 0으로 덮지 않고 `future_source_time` 품질 플래그를 남긴다.
- 시간표 기준인지 실제 관측값인지: **[공식 필드 의미에 따른 판정]**
  - 시간표 기준값이 아니다.
  - 현재 열차의 수신된 위치·운행 상태 스냅샷이다.

> 이 API에는 도착시간 필드가 없다. `recptnDt`를 계획값·도착예측값·실제 도착시각 중 하나로 오인하지 않는다. 도착·출발시각은 반복 관측에서 만든 **추정 이벤트**이고, 계획 대비 지연은 별도 시간표를 결합한 파생값이다.

## 7. 식별자

- 노선 식별자: `subwayId`; 사람이 읽는 보조값은 `subwayNm`
- 차량·열차 식별자: `trainNo`
  - 운행 열차번호이며 물리 차량 편성 ID나 장기간 불변 ID로 보장되지 않는다.
  - 선행 0을 보존하기 위해 문자열로 저장한다.
- 정류장·역 식별자:
  - `statnId`: 현재 위치 상태가 연결된 역
  - `statnTid`: 종착역
  - `statnNm`, `statnTnm`: 표시·crosswalk 보조용 이름
- 방향 식별 방식: `updnLine`
  - `0`: 상행/내선
  - `1`: 하행/외선
  - 순환·분기 노선에서는 방향값만으로 선로 경로를 확정하지 않고 종착역·역 순서 master를 함께 사용한다.
- 다른 API와 ID가 동일한지:
  - **공식 cross-API 동일성 보장은 확인하지 못했다.**
  - `subwayId`, `statnId`, `trainNo`/`btrainNo`는 연관 도착 API와 제한적으로 조인 가능하지만 실제 노선·시간대별 acceptance test가 필요하다.
  - 프로젝트의 2026-08-23 제한된 2·3호선 관측에서는 도착정보와 위치정보의 `trainNo` join이 100%였으나 전체 노선·장기 보장은 아니다. 근거는 [DECISION_SHEET_260824_v0.2](../../../docs/DECISION_SHEET_260824_v0.2.md)을 따른다.
  - 특히 `statnTid`는 OA-12601에서 **종착역 ID**, OA-15799에서 **대상 역의 다음 역 ID**로 설명된다. 필드명만 보고 공통 모델에 자동 매핑하면 안 된다.
- 내부 표준 ID 매핑 필요 여부: **필요**
  - provider 원문 ID와 내부 `canonical_line_id`, `canonical_station_id`, `service_instance_id`를 분리한다.
  - `provider + subwayId + statnId + mapping_version`을 crosswalk 기본키로 사용한다.
  - 열차 운행 instance 후보는 `service_date + subwayId + trainNo + updnLine + terminal_station_id`로 구성하고 충돌을 검증한다.

## 8. 수집 계획

> 이 절의 cadence, quota 배분, 저장 경로, 재시도·중복 규칙은 모두 **프로젝트 설계안**이며 제공기관 SLA나 공식 권장값이 아니다.

- 수집 방식: **backend 주기적 폴링**
  - frontend·사용자 단말이 제공기관 API를 직접 호출하지 않는다.
  - quota ledger와 in-flight coalescing을 가진 중앙 collector가 호출하고 사용자 요청은 최신 내부 snapshot을 읽는다.
- 수집 주기:
  - 기본 1,000회/일로 전 노선 상시 수집은 불가능하다.
  - 공식 명세 16개 노선을 30초마다 호출하면 `16 × 2,880 = 46,080회/일`이다.
  - 16개 노선을 1,000회 안에서 균등 호출하면 재시도 0회 기준 노선당 약 **23.04분 간격**이 최솟값이라 실시간 상태 전이 수집에 부적합하다.
  - 실시간 지하철 인증키의 1,000회는 위치·도착 API가 함께 쓰는 공유 예산으로 관리한다. endpoint마다 1,000회가 따로 있다고 가정하지 않는다.
  - P0 위치 수집안: 대상 2개 노선, 30초, 하루 총 90분 window = `2 × 180 = 360회/일`; 나머지 640회는 도착정보 수집·재시도·수동 검증·비상 여유를 포함한 공유 quota ledger에서 배분한다.
  - 지속 서비스 cadence는 활용사례 승인 여부와 7일 이상 freshness·유효 event yield 측정 후 결정한다.
- 수집 범위:
  - 초기: 승인된 시연 경로와 검증 corridor에 필요한 노선(기존 조사 기준 2·3호선)
  - 이후: active journey와 Claim Gate 대상 노선을 우선하고, coverage 확대 수집은 quota 여유가 있을 때만 수행
  - 여러 노선명을 한 요청에 결합하지 않고 노선별 호출한다.
- 원문 저장 여부: **예**
  - 이용정책이 허용되는 범위에서 JSON/XML 원문, HTTP 메타데이터, body hash를 함께 보존한다.
  - 인증키는 URL·로그·파일명에서 마스킹한다.
- 저장 위치:

```text
raw/subway-position/format={json|xml}/ingestion_date=YYYY-MM-DD/hour=HH/line_id={subwayId}/fetched_at={timestamp}.{json|xml}.gz
```

  - Bronze: 불변 원문과 수집 메타데이터
  - Silver: canonical ID, 파싱 timestamp, 상태 enum, freshness·quality flag
  - Gold: 추정 도착/출발 event, 구간시간, 배차간격, residual, 분포
- 재시도 정책:
  - 연결 실패·timeout·5xx·업무코드 `ERROR-500/600/601`: 지수 백오프+지터, 기본 최대 2회, 일일 재시도 예산 내에서만 수행
  - `INFO-100`, `ERROR-300/301/310/331~336`: 자동 재시도 금지, 설정·요청 계약 오류로 알림
  - `INFO-200`: 빈 정상 결과 후보로 저장하되 동일 노선 직전 성공·운행시간과 대조해 outage 여부 판정
  - HTTP 200이어도 본문 `code`가 정상이 아닐 수 있으므로 `http_status == 200 && code == INFO-000`을 함께 검사한다.
- 중복 판정 기준:
  - 원시 행 PK: `fetch_id + rowNum`
  - Silver idempotency 후보:

```text
subwayId + trainNo + statnId + updnLine + statnTid + recptnDt + trainSttus
```

  - 동일 열차가 같은 역·상태로 여러 poll에 반복되는 것은 정상 snapshot이다. 원문을 삭제하지 않고 파생 event 생성 단계에서만 중복 전이를 제거한다.
  - payload hash만으로 의미 중복을 판정하지 않는다.

## 9. 전처리 및 활용

- 생성할 데이터:
  - [x] 구간 운행시간 — 동일 운행 instance의 역 전이로 추정
  - [x] 정차시간 — `진입 → 도착 → 출발` 전이를 포착한 경우에만 구간값/interval로 추정
  - [x] 실제 배차간격 — 동일 역·노선·방향의 연속 열차 event 간격으로 추정
  - [x] 계획 대비 지연 — 공식 시간표와 service instance 매핑 후 파생
  - [ ] 사고·운행장애 이벤트 — 원인·장애 코드 필드가 없어 이 API만으로 생성하지 않음
- 전처리 규칙:
  1. ID·열차번호·enum 원문은 모두 문자열로 수신하고 선행 0을 보존한다.
  2. `lastRecptnDt`, `recptnDt` 원문과 파싱 결과를 함께 저장한다.
  3. `trainSttus`, `directAt`, `lstcarAt`, `updnLine`을 versioned enum으로 매핑하고 미지 값은 버리지 않는다.
  4. `received_at - recptnDt`로 lag를 계산하고 `fresh`, `stale`, `future_source_time`, `timezone_assumed`를 부여한다.
  5. out-of-order·동일 timestamp·상태 역행을 허용한 뒤 상태기계에서 유효 전이만 event로 승격한다.
  6. polling 간격 때문에 실제 시각을 점으로 알 수 없으면 이전·다음 관측 사이 interval을 보존한다.
  7. `statnId`가 동일하다는 이유만으로 열차가 정차 중이라고 판정하지 않고 `trainSttus`와 전후 관측을 결합한다.
  8. 서비스 운행일과 캘린더 날짜를 분리하고, 모델 학습 시 미래 관측값이 prediction 시점 feature에 섞이지 않도록 leakage를 차단한다.
- 다른 데이터와 결합할 키:
  - 역·노선 기준정보: `subwayId + statnId`
  - 실시간 도착정보: `subwayId + trainNo/btrainNo + direction + observed time window`
  - 시간표: `service_date + subwayId + trainNo + direction + station sequence`
  - 내부 경로 leg: `canonical_line_id + canonical_station_id + direction + sequence`
- 모델 입력 변수:
  - 노선, 현재 위치 역, 종착역, 방향, 열차상태, 급행/특급, 막차 여부
  - 요일, 공휴일, 시간대, service date, 출퇴근 시간대
  - source lag, snapshot age, 최근 상태전이, 최근 구간시간, 최근 배차간격
  - 시간표 대비 residual, 노선·역·시간대별 support, 결측·stale 품질 플래그
  - 도착정보 API의 ETA·상태, 환승·보행·WAIT 분포

## 10. 데이터 품질 및 제약

- 결측값 발생 조건:
  - 미운행·운행 종료·해당 노선 데이터 없음
  - 원천 수집 지연·장애·일부 노선 미지원
  - sample 키의 5행 제한 또는 page 범위 오류
  - JSON의 `beginRow`, `endRow`, `curPage`, `pageRow`는 실제 샘플에서 `null`
- 중복 데이터 가능성:
  - 동일 열차가 동일 역·상태로 여러 poll에 반복된다.
  - `recptnDt`가 갱신되지 않은 stale snapshot이 반복될 수 있다.
  - 동일 응답 안 행 중복 여부와 장기 중복률은 운영키 전체 응답으로 추가 측정해야 한다.
- 잘못된 값 또는 특수값:
  - HTTP 200이 업무 성공을 뜻하지 않는다. 잘못된 키도 HTTP 200 본문 `INFO-100`으로 관측됐다.
  - `trainNo`의 선행 0을 정수 변환하면 ID가 훼손된다.
  - `trainSttus=3`은 “전역출발”이므로 현재 역에 도착했다는 뜻이 아니다.
  - `directAt=7`은 특급이다. boolean으로 축소하면 안 된다.
  - 공급자 시계와 collector 시계 차이로 future/stale timestamp가 발생할 수 있다.
- 데이터 제공 제외 구간:
  - OA-12601 자체의 완전한 역·지리 coverage 제외 목록은 공식 미공개다.
  - 문서에 없는 노선·역은 검증 전까지 미지원으로 처리한다.
- 실시간 데이터 과거 보관 여부: **서울 열린데이터광장은 과거 이력을 보관·제공하지 않음**
- API 장애 시 대체 데이터:
  - OA-12764/OA-15799 도착정보, 공식 시간표, 마지막 성공 snapshot을 provenance와 함께 사용한다.
  - 마지막 snapshot은 freshness threshold를 넘으면 `STALE`로 표시하고 현재 관측처럼 사용하지 않는다.
  - 위치 API 장애 중에는 현재 열차상태 기반 feature와 inferred Actual을 비활성화하고 `NOT_COMPUTED` 또는 reference fallback으로 강등한다.
- 확인된 문제:
  1. 데이터셋 공지에 과거 2호선 장애와 현재 정상화가 명시돼 있어 노선별 부분 장애가 실제로 발생할 수 있다.
  2. 공식 sample URL은 `0/5`인데 일반 Open API 문서는 통상 1 기반 index를 설명한다. 공개 sample은 이번 관측에서 정확히 `0/5`만 성공하고 `1/5`, `0/6` 등은 `ERROR-336`을 반환했다.
  3. 실제 JSON envelope가 공식 공통 출력 표의 `list_total_count/RESULT` 형태와 다르다.
  4. JSON `total`은 같은 분의 반복 호출에서 `74~77`로 변했다. 이는 snapshot 변동이지 고정 노선 총량이 아니다.
  5. 공식 전용 refresh SLA, 실제 지연 SLA, 초당 호출 한도가 없다.
  6. 공식 endpoint 예시는 HTTP이고 HTTPS 연결은 이번 환경에서 확인되지 않았다. URL 경로 키 노출 위험 때문에 backend 전용 호출과 운영 전송경로 검증이 필수다.
  7. 연관 API와 동일한 `statnTid` 필드명이 서로 다른 의미로 문서화돼 있다.
  8. `trainNo`의 장기 안정성·일자 간 유일성·물리 차량 대응 관계가 문서화돼 있지 않다.

  - 측정 경계는 client의 GET 직전부터 response body 완료까지다.
  - 이번 조사에서는 raw response·HTTP header·body hash를 별도 artifact로 보존하지 않았다. 따라서 위 값은 현재 환경의 관측 기록이며, 제3자 재현 증거로 승격하려면 동일 경계의 원문 artifact를 다시 수집해야 한다.
- 확인한 특이사항:
  - 반환 행의 `recptnDt`는 수집시각보다 18~29초 이전이었다.
  - 1호선과 2호선 `0/5` sample 호출이 모두 성공했다.
  - XML 응답 구조도 정상 확인했다.
  - sample 키는 5행 smoke test용이며 운영 전체 응답·page 동작을 대표하지 않는다.
  - 잘못된 키는 HTTP 200과 함께 본문 `INFO-100`을 반환하므로 본문 코드 검사가 필수다.
  - HTTPS 443은 이번 환경에서 timeout이 발생했으나 영구 미지원으로 단정하지 않고 배포 환경에서 재검증한다.

## 12. 결정 사항 및 TODO

### 결정 사항

- 이 API를 **현재 열차 위치·상태 feature와 Actual 후보 생성용 보조 source**로 채택한다.
- 제공값을 확정 도착·출발 event로 표현하지 않고 `observed_status`와 `inferred_event`를 구분한다.
- 사용자-facing ETA, `P(on_time)`, Recommended Departure의 단독 source로 사용하지 않는다.
- 기본 quota에서는 전 노선 상시 수집을 시도하지 않고 선택 노선·시간 window에 예산을 배분한다.
- HTTP 상태와 업무코드, provider source time과 collector time, provider ID와 canonical ID를 각각 분리 저장한다.
- frontend 직접 호출과 인증키가 포함된 URL 로깅을 금지한다.
