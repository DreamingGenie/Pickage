### 핵심 판정

이 파일은 버스 위치·도착시각 원시 이력이 아니라, `기준일 × 노선 × 정류장 × 예측방식`별 **정확도 count 집계**다. `평균`, `신뢰도`, `지수평활`, `퓨전` 방식별 2분 이내·초과 count와 오차 방향 후보 count를 제공한다.

따라서 다음 용도로는 적합하다.

- 노선·정류장별 도착예측 신뢰도 prior
- 알고리즘별 2분 이내 적중률 비교
- live ETA를 확률화할 때의 calibration feature
- 표본 수와 coverage를 반영한 품질 Gate

반면 개별 예측값·실제 도착시각·오차 크기 분포가 없으므로 구간 운행시간, MAE/RMSE, residual 분포 또는 실제 도착 이벤트를 복원할 수 없다.

## 1. 개요

- 제공기관: **버스정보시스템(BIS)**
  - 제공부서: 서울특별시 미래첨단교통과
  - T-DATA 담당자 표시: 김석곤
- 공식 문서: [정확도 통계(정류장) data_id=75](https://t-data.seoul.go.kr/dataprovide/trafficdataviewfile.do?data_id=75)
- 데이터 분류: **버스 / 파일데이터 / CSV**
- 데이터 유형: **과거 이력·정확도 집계**
  - 포털 갱신주기는 월 1회다.
  - 로컬 파일의 record grain은 일자·노선·정류장별 통계다.
  - 실시간 위치, 현재 ETA, 운행시간표 또는 개별 arrival event가 아니다.
- 프로젝트 활용 목적:
  - route-stop별 버스 도착예측의 2분 이내 적중률 계산
  - 평균·신뢰도·지수평활·퓨전 방식의 global/local 성능 비교
  - 표본 수가 작은 정류장을 shrinkage한 hierarchical calibration feature 생성
  - live 버스도착정보의 ETA를 `P(on_time)` 입력 분포로 변환할 때 품질·불확실성 보정
  - 노선유형·정류장유형·coverage·결측 flag를 모델 품질 변수로 사용
- 적용 기능:
  - [x] 현재 출발 시 도착확률 — **live ETA의 route-stop별 calibration 보조값으로 조건부 적용**
  - [x] 목표 도착시각 기준 출발 추천 — **후보 여정의 버스 ETA 불확실성 보정값으로 조건부 적용**

> 이 데이터가 직접 `P(on_time)`이나 추천 출발시각을 제공하는 것은 아니다. 3일치 파일만으로 사용자 지표를 생성하지 않으며, 장기 이력·live ETA·실제 운행 관측과의 temporal validation을 통과한 파생 통계만 사용한다.

## 2. 제공 범위

- 지역 범위:
  - 공식 설명은 BIS의 **정류장별** 정확도 통계다.
  - 모든 서울 정류장·모든 운수회사 포함 여부와 제외 기준은 공개되지 않았다.
  - 로컬 파일에는 서울시 노선뿐 아니라 관련 API code 기준 인천·경기 노선유형 후보도 포함돼 있다.
- 노선·운영기관 범위:
  - 로컬 파일 전체: 노선 ID `1,333개`, 정류장 ID `23,534개`, 노드순번 `242개`
  - 서울시 버스노선 ID 파일 723개 중 711개가 직접 join됐고 노선명이 711/711 정확히 일치했다.
  - 정확도 파일 전체 노선 중 서울시 노선 master와 join되는 비율은 711/1,333, 약 `53.34%`다.
  - 관련 API는 노선유형 `1=공항`, `2=마을`, `3=간선`, `4=지선`, `5=순환`, `6=광역`, `7=인천`, `8=경기`, `10=관광`을 설명한다.
  - 로컬 파일에는 관련 API enum에 없는 `노선유형=15`가 6,258행 존재하며 `N37`, `N26`, `N62` 등의 노선명이 관측됐다. 정확한 code 의미는 미확인이다.
- 제공 기간:
  - 데이터셋 공개일: `2021-12-01`
  - 공식 페이지 수정일: `2026-08-17`
  - 로컬 CSV 기준일: `2026-08-23`~`2026-08-25`, 연속 3일
  - 공개일·페이지 수정일은 파일의 실제 최초·최종 기준일을 의미하지 않는다.
- 과거 이력 제공 여부: **예, 로컬 파일에 일자별 집계 존재**
  - 다만 현재 확보된 파일은 3일뿐이고 포털의 전체 file inventory·retention·과거 version 보관정책은 미확인이다.
- 데이터 갱신 주기: **월 1회**
  - 월 1회는 파일 publication cadence다.
  - 각 파일이 한 달 전체, rolling 기간 또는 일부 날짜를 포함하는지는 공식 화면에서 확인되지 않았다.
- 실제 데이터 지연시간:
  - 제공기관 생성시각·게시시각 필드가 없어 정확한 지연시간은 계산할 수 없다.
  - 로컬 파일 수정시각은 `2026-08-27 08:52:27 KST`, 최대 `기준일`은 `2026-08-25`로 달력상 2일 차이다.
  - 파일 수정시각은 로컬 저장시각 후보이며 provider publication timestamp가 아니므로 2일을 SLA나 확정 지연으로 사용하지 않는다.

### 로컬 파일 무결성

| 항목 | 관측값 |
| --- | --- |
| 크기 | `68,541,265 bytes` |
| SHA-256 | `44FE1FB9E6BB8AE46D4AE58BE895769A61D448287469624DB878C0D14E5DAE43` |
| 행·열 | header 1행 + 데이터 `247,486행`, `34열` |
| 인코딩 | UTF-8 계열, BOM 오염 있음 |
| 구분자 | comma `,` |
| quote 문자 | double quote `"` |
| 줄바꿈 | CRLF `247,487개`, bare LF 없음 |
| row width | 전 데이터 행 34 field, ragged row 0 |
| 숫자 parsing | 최종 23개 measure field 모두 integer 변환 성공, 실패 0 |

### 인코딩 주의사항

- 파일 시작 bytes가 `EF BB BF EF BB BF`로 BOM이 2회 연속 존재한다.
- 첫 header뿐 아니라 **모든 데이터 cell의 앞에 U+FEFF가 1개씩 존재**한다.
- 일반적인 `encoding=utf-8-sig`는 파일 첫 BOM만 제거하므로 충분하지 않다.
- header와 모든 string cell에 `lstrip('\ufeff')`를 적용한 뒤 type casting해야 한다.
- 원본 bytes와 checksum은 변환 전 그대로 보존한다.

## 6. 시간 데이터 해석

- 제공기관 데이터 생성시각 필드: **없음**
  - `기준일`은 집계 대상 날짜다.
  - 파일 생성시각·게시시각·최종수정시각은 row에 없다.
- 예측시각 또는 실제시각 여부:
  - 개별 예측시각이나 실제 도착시각이 없다.
  - 예측 정확도 결과를 날짜·노선·정류장 단위로 집계한 통계다.
  - 어떤 ETA와 어떤 실제 도착 기준을 비교했는지, 오차의 sign을 `예측-실제`와 `실제-예측` 중 어느 방향으로 계산했는지는 미공개다.
- 시간대: **공식 미공개**
  - `기준일`에 timezone offset이 없다.
  - 서울 BIS 자료라는 근거로 `Asia/Seoul` 후보를 둘 수 있으나, raw date와 timezone assumption을 분리한다.
- 자정 이후 운행일 처리 방식: **공식 미공개**
  - 심야버스 `Nxx`가 `노선유형=15`로 관측되지만, 자정 이후 건수를 전일/당일 중 어디에 귀속하는지 알 수 없다.
  - `기준일`을 provider service-day 원문으로 보존하고 임의 이동하지 않는다.
- 수집시각과 제공시각의 차이:
  - 로컬 파일 저장시각과 최대 기준일의 달력 차이만 계산할 수 있다.
  - provider publish timestamp가 없어 transport lag·processing lag·월 배치 지연을 분리할 수 없다.
- 시간표 기준인지 실제 관측값인지:
  - 시간표 계획값이 아니다.
  - 개별 actual event도 아니다.
  - prediction과 provider reference 결과를 비교해 생성한 **집계 accuracy statistic**으로만 취급한다.

> 도착시간 구분: 이 파일에는 **계획 도착시간, 예측 도착시간, 실제 도착시간이 모두 없다.** 2분 이내/초과 count는 예측 성능 집계이며, `제공건수`는 그 평가 분모 후보다. 개별 ETA residual이나 실제 도착시각을 복원할 수 없다.

## 7. 식별자

- 노선 식별자: `노선ID`
  - string으로 저장한다.
  - 로컬 `서울시버스노선ID정보(20260804).csv`와 711개 ID가 직접 join됐고 노선명도 711/711 일치했다.
  - 서울 master 723개 중 711개, 약 `98.34%`가 정확도 파일에 존재했다.
  - 정확도 파일은 경기·인천 노선까지 포함해 전체 1,333개 중 서울 master join은 약 `53.34%`다.
- 차량·열차 식별자: **없음**
  - 개별 차량·운행 인스턴스별 분석은 불가능하다.
- 정류장·역 식별자: `정류장ID`
  - `정류장번호`는 표시번호이며 leading zero를 보존하는 string이다.
  - `노드순번`은 ID가 아니라 노선 안의 순번이다.
- 방향 식별 방식: **명시적 방향 field 없음**
  - `노선ID + 노드순번`과 노선경로 master를 결합해 방향을 파생해야 한다.
  - 왕복·분기·회차 노선에서 순번만으로 상·하행을 임의 추론하지 않는다.
- 다른 API와 ID가 동일한지:
  - 서울시 노선 master와의 route ID direct join은 이 파일에서 실측됐다.
  - 버스도착·위치 API의 route ID와도 동일한지 전체 coverage를 별도로 검증한다.
  - `정류장ID`와 버스도착 API의 `arsId`, 노선정류장 ID가 동일하다는 공식 보장은 없다.
- 내부 표준 ID 매핑 필요 여부: **필요**
  - 서울 route는 direct join 결과를 versioned evidence로 저장한다.
  - 인천·경기 노선유형과 설명 누락 647행은 별도 master가 필요하다.
  - `internal_route_id`, `internal_stop_id`, direction, valid period를 포함한 crosswalk를 둔다.

## 8. 수집 계획

- 수집 방식: **월별 파일 다운로드·적재**
  - API polling이나 사용자 요청 시 실시간 수집 대상이 아니다.
- 수집 주기:
  - 포털 공식 주기에 맞춰 월 1회 파일 목록을 확인한다.
  - 동일 파일이 교체될 수 있으므로 다음 달 수집 시 직전 file도 한 번 재다운로드해 checksum 변경 여부를 확인한다.
  - 실제 publication day는 3개월 이상 관측해 schedule을 확정한다.
- 수집 범위:
  - portal selector에 노출되는 전체 파일명·기간·크기 inventory를 먼저 manifest로 저장한다.
  - 초기에는 프로젝트 평가기간과 겹치는 파일부터 적재한다.
  - 이 파일의 3일 범위를 월 전체로 오인하지 않고 각 파일의 `min/max 기준일`을 기록한다.
- 원문 저장 여부: **예**
  - 다운로드 bytes를 수정하지 않고 checksum과 함께 Bronze에 저장한다.
  - 정규화본은 별도 Silver dataset으로 생성한다.
- 저장 위치 설계안:

```text
raw/bus-arrival-accuracy/
  provider=tdata/dataset=75/downloaded_date=YYYY-MM-DD/
  sha256={sha256}/정확도_통계.csv
```

  - manifest: source URL, portal modified date, file selector label, local filename, bytes, SHA-256, downloaded_at, encoding, row/column count, min/max 기준일, parser/schema version
- 재시도 정책:
  - download timeout·connection reset·5xx: exponential backoff + jitter, 최대 3회
  - 인증·로그인 요구, 권한 오류, file selector 변경: 자동 반복 금지, 접근 계약 점검
  - partial download는 임시 위치에 저장하고 expected byte 또는 checksum·CSV width 검증 전 final path로 promote하지 않는다.
  - 월별 포털 file inventory가 비어 있으면 마지막 파일을 최신으로 가장하지 않고 수집 실패를 기록한다.
- 중복 판정 기준:
  - raw file: SHA-256 동일 여부
  - row 후보 key: `기준일 + PART_KEY + 매체유형 + 노선ID + 정류장ID + 노드순번`
  - 로컬 파일에서는 full-row duplicate와 후보-key duplicate가 모두 0이었다.
  - 이후 파일에서 같은 후보 key의 metric이 바뀌면 중복 제거가 아니라 provider revision으로 저장한다.

## 9. 전처리 및 활용

- 생성할 데이터:
  - [ ] 구간 운행시간 — event time·거리·실제 통과시간 없음
  - [ ] 정차시간 — arrival/departure event 없음
  - [ ] 실제 배차간격 — vehicle/run/event 식별자 없음
  - [ ] 계획 대비 지연 — 계획시각·actual 시각 없음
  - [ ] 사고·운행장애 이벤트 — 사건 field 없음
- 생성할 정확도 feature:
  - [x] 예측방식별 2분 이내 적중률
  - [x] route-stop별 sample count와 uncertainty
  - [x] 오차 방향 비율 후보
  - [x] 보정계수 적용 count 비율 후보 — 의미 확인 후 사용
  - [ ] MAE·RMSE — 오차 magnitude가 없어 생성 불가
  - [ ] 개별 residual 분포 — 개별 예측·actual pair가 없어 생성 불가
- 전처리 규칙:
  1. 원본 bytes·SHA-256을 먼저 저장한다.
  2. 모든 header와 cell에서 leading U+FEFF를 제거한다. 중간 BOM은 삭제하지 않는다.
  3. 중복 header는 column ordinal을 포함해 `지수평활2분이하건수__1/__2`, `지수평활2분초과건수__1/__2`로 임시 alias한다.
  4. 제공기관 확인 전 position 25/26을 음수·양수 field로 영구 rename하지 않는다.
  5. ID·code·정류장번호는 string, 최종 23개 measure는 nullable integer로 parsing한다.
  6. `제공건수 > 0`과 8개 count pair 합계가 분모와 같은지 검증한다.
  7. 각 적중률은 `2분이하건수 / 제공건수`로 계산하고 분모·기간·coverage를 함께 저장한다.
  8. 소표본 row는 raw rate를 그대로 사용하지 않고 route/stop hierarchy shrinkage 또는 최소표본 Gate를 적용한다.
  9. 설명 field 5개가 모두 빈 row도 ID와 metric은 보존하고 `MISSING_MASTER_ATTRIBUTES` flag를 붙인다.
  10. `오차누계`·`소요시간누계`가 all-zero인 현재 file에서는 feature에서 제외한다.
  11. 네 보정계수 field가 동일한 현상을 품질 flag로 기록하고 공식 의미 확인 전 algorithm별 feature로 사용하지 않는다.
  12. 날짜 순서를 유지한 temporal hold-out으로 calibration 효과를 검증한다.
  13. 미래 파일이나 같은 날짜의 revision이 과거 예측 평가에 유입되지 않도록 `available_at` 기준으로 dataset을 자른다.
- 다른 데이터와 결합할 키:
  - 서울시 노선 master: `노선ID ↔ ROUTEID`
  - 버스도착·위치 API: 검증된 `routeId/busRouteId`, 별도 stop crosswalk
  - 노선정류장 master: `노선ID + 정류장ID + 노드순번 + valid_time`
  - live ETA evaluation: `internal_route_id + internal_stop_id + direction + evaluation_date`
- 모델 입력 변수:
  - algorithm별 `within_2m_rate`, `over_2m_rate`, 표본 수
  - 오차 sign bucket 비율 후보, 확인 후 correction count ratio
  - 노선유형, 정류장유형, 노드순번, 요일, 기간 recency
  - master mapping confidence, metadata missing, coverage stability, schema version
  - route/stop hierarchical prior와 posterior uncertainty

- 실시간 데이터 과거 보관 여부: **해당 없음**
  - 이 데이터 자체가 월별 배포되는 과거 accuracy 집계다.

  - 기존 T-DATA file을 최신값으로 가장하지 않고 source age를 표시한다.
  - 대체 dataset은 data_id=75와 같은 metric 정의라고 가정하지 않는다.
- 확인된 문제:
  1. 인코딩 BOM 오염을 제거하지 않으면 ID·숫자·header join이 실패한다.

  7. 지역 노선 master와 정류장 crosswalk가 없다.
