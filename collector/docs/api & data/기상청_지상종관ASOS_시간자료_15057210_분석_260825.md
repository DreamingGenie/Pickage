## 1. 개요

- 제공기관: **기상청** (관리부서: 국가기후데이터센터) — 공식
- 공식 문서: https://www.data.go.kr/data/15057210/openapi.do
- 데이터 분류: **과학기술 > 과학기술연구** — 공식
- 데이터 유형: **과거 이력** — 호출 관측
  - 정적 아님(시간마다 새 관측 추가), 실시간 아님(D-0 전량 거부).
  - 종관기상관측(ASOS) 장비의 **실측값**이며 예보·계획값이 아니다.
- 프로젝트 활용 목적 — **1차 목적은 오프라인 상관분석이다**:
  - **날씨 관측 DB를 구축**하고, 별도 구축한 **교통수단 지연 DB**와 관측 시각 기준으로 조인
  - 강수·적설·강풍·시정 조건과 지연 사이에 **통계적으로 방어 가능한 상관관계가 존재하는지 검정**
  - 상관이 확인된 조건에 한해, 그 결과를 `WAIT`/`RIDE` 분포 층화와 `계획 대비 지연`의 공변량으로 승격
  - 유의하지 않으면 **날씨 변수 채택 자체를 기각**한다
- 적용 기능:
  - [ ] **현재 출발 시 도착확률** — **실시간 입력으로는 불가**. D-0 데이터가 존재하지 않아 계산 시점의 realtime context를 만들 수 없다(§2 참조). 단, 상관분석으로 검증된 날씨 조건별 historical baseline을 이 기능이 참조하는 형태로는 **간접 기여**한다. 추론 시점의 날씨가 필요하면 `초단기실황`을 별도 도입한다(§10).
  - [x] **목표 도착시각 기준 출발 추천** — **가능**. 정의상 historical only이므로 D-1 지연이 제약이 되지 않는다.
  - [x] **(선행) 날씨-지연 상관분석** — **이 API의 실제 1차 용도.** 회고 분석은 항상 과거를 조회하므로 D-1 지연이 무관하고, 이력이 1931년까지 있어 **날씨 쪽은 병목이 되지 않는다.**

> 이 API는 `P(on_time)`이나 추천 출발시각을 제공하지 않는다. Reliability Engine의 leg distribution을 조건부로 나누는 **공변량 소스**로만 쓴다.

## 2. 제공 범위

- 지역 범위: **전국 ASOS 지점** — 호출 관측
  - 지점번호 90~259, 400~510 대역을 스윕해 **50개 지점이 정상 응답**했다.
  - **서울특별시 행정구역 내 지점은 `108`(서울) 단 1개다.** ← 프로젝트 최대 제약
  - 수도권 인접 지점: `98` 동두천, `99` 파주, `112` 인천, `119` 수원, `201` 강화, `202` 양평, `203` 이천 — 전부 서울 밖
  - 지점 좌표(위경도)는 이 API가 제공하지 않는다 — **미확인**, 별도 `지상기상관측 지점정보` 서비스 필요
- 노선·운영기관 범위: **해당 없음** (교통 API가 아님)
- 제공 기간: **지점별 상이. 서울(108)은 최소 1931-01-01부터 조회됨** — 호출 관측

  | 요청일 | resultCode | 반환 건수 |
  |---|---|---|
  | 2025-01-01 | 00 | 24 |
  | 2010-01-01 | 00 | 24 |
  | 1990-01-01 | 00 | 24 |
  | 1970-01-01 | 00 | 24 |
  | 1960-01-01 | 00 | **15** (부분) |
  | 1950-01-01 | 00 | 24 |
  | 1940-01-01 | 00 | **14** (부분) |
  | 1931-01-01 | 00 | **12** (부분) |
  | 1907-01-01 | 03 NO_DATA | 0 |
  | 1904-04-01 | 03 NO_DATA | 0 |

  포털 설명의 "1904년 4월부터"는 **서울 지점에는 해당하지 않는다**(NO_DATA 확인). 1960년 이전은 하루 24시간이 채워지지 않는 부분 관측이다.
- 과거 이력 제공 여부: **예** — 이 API의 본질
- 데이터 갱신 주기: 공식 "시간, 일". 실측상 **일 단위 배치로 D-1까지 확정 공개**
- 실제 데이터 지연시간: **D-0 전량 미제공 (확정)** — 호출 관측

  | 요청 대상 | 결과 |
  |---|---|
  | D-0 (2026-08-25, 오늘) | `resultCode=99` / `전날 자료까지 제공됩니다.` |
  | D-0 부분일 (오늘 00~23시) | `resultCode=99` — **당일 00시 데이터조차 불가** |
  | D-1 (2026-08-24) | `00` NORMAL, 24건, 마지막 `2026-08-24 23:00` |
  | D-2 (2026-08-23) | `00` NORMAL, 24건 |
  | D+1 (미래) | `resultCode=99` |

  2026-08-25 약 13:00 조회 시 최신 관측은 `2026-08-24 23:00` → **관측 후 약 14시간 경과**. 조회 시각에 따라 lag은 최대 약 48시간까지 벌어진다. 자정 직후에도 D-1이 즉시 열리는지는 **미확인**.

## 3. 인증 및 호출 제한

- 인증 방식: **query string `serviceKey`** — 호출 관측
  - 키는 Encoding(URL-encoded)/Decoding 두 형태로 배포된다. 프로젝트 키는 64자리 hex(특수문자 없음)라 두 형태가 동일하다.
- API 키 발급처: data.go.kr — **서비스별 활용신청 필요**
  - 프로젝트 기존 data.go.kr 키가 이 서비스에서 그대로 동작함을 확인했다(활용신청 승인 상태).
- 기본 일일 호출 한도: **개발계정 10,000회** — 공식. 실제 차단 동작은 **미검증**
- 초당 호출 한도: **공식 미공개**. 검증 중 168회를 지연 없이 연속 호출했고 `429`·throttling은 관측되지 않았다 — 호출 관측
- 호출량 증액 가능 여부: **가능** — 운영계정 전환(활용사례 등록 후 신청) — 공식
- 이용요금: **무료** — 공식
- 이용약관·라이선스: **공공저작물 출처표시 (제1유형, KOGL)** — 공식. 출처 표시로 2차 저작·상업 이용 가능
- **건수 제한(별도)**: 1회 요청 최대 **999건**. `numOfRows=1000` 이상은 `resultCode=99` / `데이터요청은 한번에 최대 1,000건을 넘을 수 없습니다.` — 호출 관측 (안내 문구는 1,000이지만 실제 경계는 999)

## 4. 요청 방법

- HTTP Method: **GET**
- Endpoint: `https://apis.data.go.kr/1360000/AsosHourlyInfoService/getWthrDataList`
- 응답 형식: **JSON / XML**. `dataType` 생략 시 **XML**이 기본 — 호출 관측
- 필수 파라미터:

| 파라미터 | 설명 | 예시 | 필수 여부 |
|---|---|---|---|
| `serviceKey` | data.go.kr 인증키 | (secret) | **필수** |
| `dataCd` | 자료 분류 코드 | `ASOS` | **필수** |
| `dateCd` | 날짜 분류 코드 (시간자료) | `HR` | **필수** |
| `startDt` | 조회 시작일 `YYYYMMDD` | `20260701` | **필수** |
| `startHh` | 조회 시작시 `HH` (00~23) | `00` | **필수** |
| `endDt` | 조회 종료일 `YYYYMMDD` (**D-1까지**) | `20260731` | **필수** |
| `endHh` | 조회 종료시 `HH` (00~23) | `23` | **필수** |
| `stnIds` | 지점번호 (**단일값만**) | `108` | **필수** |
| `dataType` | `JSON` / `XML` (생략 시 XML) | `JSON` | 옵션 |
| `numOfRows` | 한 페이지 결과 수 (**최대 999**) | `999` | 옵션 |
| `pageNo` | 페이지 번호 | `1` | 옵션 |

- **`stnIds`는 다중 지점을 지원하지 않는다** — `108,112` 및 URL 인코딩한 형태 모두 `resultCode=02 DB_ERROR` — 호출 관측
- `startHh`/`endHh`는 **양 끝 포함(inclusive)** — `07~09` 요청 시 07:00, 08:00, 09:00 3건 — 호출 관측

### 요청 예시

```
GET https://apis.data.go.kr/1360000/AsosHourlyInfoService/getWthrDataList
    ?serviceKey={KEY}
    &dataType=JSON
    &dataCd=ASOS
    &dateCd=HR
    &startDt=20260701&startHh=00
    &endDt=20260731&endHh=23
    &stnIds=108
    &numOfRows=999&pageNo=1
```

## 6. 시간 데이터 해석

- 제공기관 데이터 생성시각 필드: **없음**. 배치 생성시각·확정시각을 응답에서 알 수 없다 — 호출 관측
  - 설계안: 수집기가 `fetched_at`을 직접 기록해 provenance로 남긴다.
- 예측시각 또는 실제시각 여부: **실제 관측시각**. `tm`은 해당 시각에 관측된 실측값이다 — 공식·호출 관측
- 시간대: **응답에 timezone 표기가 없다**. KST(UTC+9)로 해석한다 — **추정**
  - 근거: 국내 기상청 관측자료이고, D-1 경계가 KST 자정과 일치한다.
  - 설계안: 저장 시 명시적으로 `Asia/Seoul` tz-aware로 변환해 적재한다.
- 자정 이후 운행일 처리 방식: **`24:00` 표기는 존재하지 않는다.** 하루는 `00:00`~`23:00` 24건이며, 이틀 연속 요청 시 `2026-08-23 23:00` → `2026-08-24 00:00`으로 자연 연결된다(중복 0건) — 호출 관측
  - **주의**: 대중교통 `운행일`은 자정을 넘겨 익일 새벽까지 이어지지만, 이 API의 날짜 경계는 **역일(calendar day)** 기준이다. 두 경계가 다르므로 조인 시 운행일이 아니라 **실제 관측 시각(tm)** 으로 붙인다.
- 수집시각과 제공시각의 차이: **최소 약 14시간 ~ 최대 약 48시간** (§2 참조)
- 시간표 기준인지 실제 관측값인지: **실제 관측값** — 확정

> 도착시간 계획값/예측값/실제값 구분 원칙은 이 API에 직접 적용되지 않는다(교통 데이터가 아님). 다만 **이 API가 제공하는 값은 전부 실측 관측값**이며, 예보값과 절대 혼용하지 않는다. 향후 `초단기실황`·`단기예보`를 도입할 경우 관측/예보를 다른 컬럼·다른 provenance로 분리한다.

- 정류장·역 식별자: **없음**

## 8. 수집 계획 (설계안)

- 수집 방식: **파일 적재(1회 backfill) + 주기적 폴링(일 1회 증분)**
  - 사용자 요청 시 수집은 **금지**. D-1 데이터라 실시간 경로에 넣을 이유가 없다.
- 수집 주기: **일 1회, 03:00 KST 배치** — D-1 확정분 24건 수집
- 수집 범위:
  - **backfill**: 지점 `108`, 교통 이력 데이터(T-DATA 1068 등)가 실제로 확보되는 기간과 **동일 구간만**. 교통 데이터 없는 기간의 날씨는 조인 대상이 없어 가치가 0이다.
  - 999건 제한 → **1년치 = 9회 호출**(8,760시간 ÷ 999). 5년 backfill도 45회로 하루 한도(10,000) 내에서 여유롭다.
  - 증분: 1일 1회 × 1지점 = **일 1회 호출**. quota 부담이 사실상 없다.
- 원문 저장 여부: **저장**. 응답 JSON 원문을 `fetched_at`, 요청 파라미터와 함께 보관 (KOGL 제1유형이라 보관·재배포 제약 없음)
- 저장 위치: 원문은 object storage(`raw/kma_asos_hourly/stn=108/dt=YYYY-MM-DD/`), 파싱본은 RDB `weather_observation_hourly`
- 재시도 정책:
  - `resultCode=00` 외 전부 실패 처리. 특히 **`99`는 재시도해도 무의미**(날짜 범위 오류)하므로 즉시 중단하고 알림.
  - `02 DB_ERROR`, HTTP 5xx, timeout → **지수 백오프 3회** (2s/8s/32s)
  - `403 SERVICE_KEY_IS_NOT_REGISTERED_ERROR` → 재시도 금지, 운영자 알림
- 중복 판정 기준: **`(stnId, tm)` 유니크**. 2026-07 한 달 744건에서 `tm` 중복 0건 확인(호출 관측). upsert로 적재하되, 기상청이 사후 QC로 값을 정정할 가능성이 있어 **덮어쓰기 시 이전 값을 이력 테이블에 남긴다**.

## 9. 전처리 및 활용

- 생성할 데이터:
  - [ ] 구간 운행시간 — **이 API로 생성 불가** (교통 데이터 아님)
  - [ ] 정차시간 — **생성 불가**
  - [ ] 실제 배차간격 — **생성 불가**
  - [ ] 계획 대비 지연 — **직접 생성 불가.** 단 다른 API가 만든 지연값을 **설명하는 공변량**을 제공한다.
  - [ ] 사고·운행장애 이벤트 — **생성 불가.** `dmstMtphNo`(현상번호)는 기상현상이지 운행장애가 아니다.

  > 이 API는 파생 교통지표를 하나도 만들지 않는다. 역할은 **다른 데이터가 만든 지표에 조건을 붙이는 것**뿐이다.

- 전처리 규칙 — 설계안:
  1. **모든 빈 문자열 → `NULL`** 변환. 숫자 필드는 이후 float 캐스팅.
  2. **강수량 `rn` 3분류 (가장 중요)** — 호출 관측 교차표 근거 (2026-07 서울 744시간):

     | `rn` | `rnQcflg` | 건수 | 해석 |
     |---|---|---|---|
     | 빈값 | 빈값 | 319 | **무강수** → `0.0`으로 대체 |
     | 빈값 | `9` | 236 | **결측(QC 플래그)** → `NULL` 유지, 0으로 대체 금지 |
     | `0.0` | 빈값 | 74 | **미량 강수(trace)** → `0.0` |
     | `0.0` | `9` | 1 | 결측 취급 |
     | `>0` | 빈값 | 114 | **정상 강수** (최대 43.2mm) |

     **`rn`의 빈값을 일괄 0으로 채우면 결측 236건(31.7%)이 "비 안 옴"으로 오염된다.** 반드시 `rnQcflg`와 함께 판정한다.
  3. 파생 변수: `is_rain = rn > 0`, `rain_bucket ∈ {none, light(<1mm), moderate(1~5mm), heavy(≥5mm)}`, `is_snow = dsnw > 0`, `low_visibility = vs < 1000`
  4. 결측 시간대는 **보간하지 않는다**. 해당 시간의 교통 관측은 `weather_available=false`로 표시하고 날씨 조건부 분포에서 제외한다.
- 다른 데이터와 결합할 키: **관측시각을 시 단위로 내림한 값(KST)** 단일 키 (§7 참조)
- 모델 입력 변수 — 설계안, **채택 확정 아님**:
  - 1순위: `rain_bucket`, `is_snow`, `ws`
  - 2순위: `ta`(폭염·한파 구간), `vs`
  - **검정 선행**: 각 변수가 leg 지연 분포를 유의하게 이동시키는지 hold-out으로 확인하고, 유의하지 않으면 **변수를 버린다**. 서울 전역 단일값이라 설명력이 낮을 가능성을 미리 인정한다.

  | 상황 | HTTP | 응답 |

  | `numOfRows` ≥ 1000 | 200 | `resultCode=99` / `데이터요청은 한번에 최대 1,000건을 넘을 수 없습니다.` |
  | 존재하지 않는 지점(`99999`) | 200 | `resultCode=03` / `NO_DATA` |

| **합계** | **8,016** | **1,350 (16.8%)** | **541** | **141 (7.0%)** | **65** | **15** | **117** |

**교통 데이터 1개월당 기대 표본**: 러시아워 강수 약 13시간, **≥1mm 약 6시간**, ≥5mm 약 1.4시간.

**결론**:
- **순방향 수집만으로는 불가.** 마감(2026-09-25)까지 1개월이면 유의미한 비(≥1mm)가 온 러시아워가 **약 6시간**뿐이다. 어떤 통계 처리로도 방어 가능한 상관 주장을 만들 수 없다.
- **T-DATA 1068이 공개일(2021-12)까지 backfill되면 성립한다.** 4년 반이면 ≥1mm 러시아워 약 260시간으로 충분하다.
- 따라서 **T-DATA 1068의 최초 조회 가능 `stdrDe` 확인이 이 연구 전체의 선행 게이트다.** 이 API 수집기 구현보다 먼저 처리한다.
- **적설(117시간)은 전부 12~1월에 몰려 있다.** 눈은 비보다 지연 효과가 클 가능성이 높지만 9월 마감 프로젝트로는 순방향 수집으로 닿을 수 없다. backfill이 되면 오히려 더 뚜렷한 신호원이 될 수 있다.

### 분석 설계상 주의 (설계안)

1. **군집 구조 — 표본 수 부풀리기 금지.** 같은 시간대에 같은 비를 맞은 차량들은 서로 독립이 아니다. 운행 건수를 그대로 N으로 쓰면 신뢰구간이 가짜로 좁아진다. **실질 표본은 독립적인 강수 이벤트 수**(위 표)이므로, 이벤트 단위 집계 또는 군집 표준오차(cluster-robust SE)를 사용한다.
2. **교란변수 통제 필수.** 강수는 계절·기온·일조와 얽혀 있고, 지연은 날씨와 무관하게 시간대·요일에 강하게 좌우된다. 단순 "비 온 날 vs 안 온 날" 평균 비교는 거의 확실히 가짜 상관을 만든다. **같은 노선 · 같은 시간대 · 같은 요일 유형 안에서** 비교한다.
3. **단일 지점의 편향 방향은 알려져 있다.** 국지성 강수를 "무강수"로 오분류하는 것은 측정오차이며, 편향 방향은 **0쪽(효과 축소, attenuation)** 이다. 실무적 함의:
   - 효과가 **검출되면** 보수적 추정이므로 실재할 가능성이 높다.
   - 효과가 **검출되지 않으면** "효과 없음"과 "측정오차에 묻힘"을 구분할 수 없다.
   - 이 비대칭을 결과 해석과 사용자 claim에 반드시 명시한다.
4. **결측 16.8%를 0으로 채우지 않는다.** §9의 `rn` × `rnQcflg` 3분류를 그대로 적용한다.

### 우선순위

**중간.** 수집 비용은 극히 낮다(일 1회 호출, quota 무부담). 다만 선행 게이트(T-DATA backfill 깊이)가 열리지 않으면 수집기를 만들어도 분석이 성립하지 않으므로, **게이트 확인 → 교통 이력 파이프라인 → 이 API 수집기** 순서를 지킨다.
