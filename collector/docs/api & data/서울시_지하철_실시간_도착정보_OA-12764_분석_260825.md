# 서울시 지하철 실시간 도착정보 (OA-12764)

> 조사·검증 기준: 2026-08-25 KST  
> 대상: 역명으로 조회하는 `realtimeStationArrival` API

## 1. 개요

- 제공기관: 서울특별시
  - 제공부서: 교통실 교통기획관 미래첨단교통과
  - 원본시스템: 서울시 교통정보 시스템(TOPIS)
- 공식 문서:
  - 데이터셋: <https://data.seoul.go.kr/dataList/OA-12764/F/1/datasetView.do>
  - API 명세: <https://data.seoul.go.kr/dataList/openApiView.do?infId=OA-12764&srvType=A>
- 데이터 분류: 교통
- 데이터 유형: **실시간**
  - API: 현재 역별 열차 도착예측·운행상태 스냅샷
  - 보조 XLSX: 비정기 갱신되는 정적 역·호선 ID 기준정보
  - 과거 도착 이력: 제공하지 않음
- 프로젝트 활용 목적:
  - 선택 경로의 출발·환승역에 접근 중인 열차의 ETA와 상태를 현재 여정 재예측에 반영
  - 반복 수집으로 지하철 `Prediction → Actual interval → Residual`을 생성해 station×line×direction×time bucket 분포를 구축
  - `P(on_time)`와 P50/P90 계산의 지하철 leg 입력을 보강
- 적용 기능:
  - [x] 현재 출발 시 도착확률
  - [ ] 목표 도착시각 기준 출발 추천

현재 출발 시 도착확률에도 **보조 입력으로만** 사용한다. 이 API는 전체 OD 경로시간, 환승시간, 보행시간, 확률분포를 제공하지 않는다. 목표 도착시각 기준 출발 추천은 이 API 단독으로 계산할 수 없으며, 자체 장기 수집 이력·운행시간표·환승/보행 분포와 후보 출발시각별 재평가 Gate가 필요하다.

## 2. 제공 범위

- 지역 범위:
  - 공식 설명: 서울시 이외의 역구간은 미제공. 예시로 광명·서동탄·춘천을 명시
  - 확인된 불일치: 최신 역정보 XLSX에는 소요산·동두천·양주 등 서울 밖 역도 포함된다. 이는 **기준정보 포함 범위**일 뿐 해당 역의 API 응답 보장을 뜻하지 않는다.
- 노선·운영기관 범위:
  - 공식 명세가 열거한 호선 ID: `1001`~`1009`, `1061`, `1063`, `1065`, `1067`, `1075`, `1077`, `1081`, `1092`, `1093`, `1032`
  - 최신 XLSX에서 확인한 19개 호선 ID: `1001`~`1009`, `1032`, `1063`, `1065`, `1067`, `1075`, `1077`, `1081`, `1092`, `1093`, `1094`
  - 운영기관별 완전한 제공 범위나 SLA는 공식 명세에 없다. 호선 ID 목록을 운영기관 보장 목록으로 해석하지 않는다.
- 제공 기간:
  - API: 호출 시점의 현재 스냅샷만 제공
  - 공개일자: 2015-02-28. 이는 API 공개일이며 데이터 이력 시작일이 아니다.
  - 보조 역정보 파일 목록: 페이지에서 2024-08-12~2026-08-04 버전을 확인했지만 모두 역 기준정보 버전이다.
- 과거 이력 제공 여부: **없음**
  - 공식 FAQ는 실시간 데이터가 API-to-API, 대용량·분 단위 제공이라 과거 데이터를 별도 적재하지 않아 제공할 수 없다고 설명한다.
- 데이터 갱신 주기:
  - API 응답의 고정 갱신 주기/SLA: 미공개
  - FAQ 표현: 분 단위 제공
  - 포털 메타데이터의 `비정기(자료변경시)`는 데이터셋 설명·보조파일 갱신 주기이며 실시간 응답 cadence가 아니다.
- 실제 데이터 지연시간:
  - 공식 수치 SLA: 미공개
  - 2026-08-25 11:06:17 KST 단일 JSON 표본 5행에서 `received_at - recptnDt`는 약 **28~601초**, 중앙값 약 **42초**
  - 이 값은 한 시점·샘플 키·서울역 표본이며, 클라이언트와 공급자 시계 차이도 포함할 수 있다. 운영 SLA로 일반화하지 않는다.

## 3. 인증 및 호출 제한

- 인증 방식: URL 경로에 실시간 지하철 전용 `KEY`를 넣는 API Key 방식
- API 키 발급처:
  - [서울 열린데이터광장 인증키 신청](https://data.seoul.go.kr/together/mypage/actkeyMain.do)
  - 데이터셋 API 화면의 `인증키 신청 (지하철)` 경로 사용
- 기본 일일 호출 한도: 인증키 1개당 최대 **1,000회/일**
- 초당 호출 한도: 공식 문서에서 확인하지 못함
- 1회 조회 한도: 최대 **1,000건**
  - `sample` 키는 최대 5건이며 서울역만 조회 가능
- 호출량 증액 가능 여부:
  - 공식 안내는 “이용 제약 없이 계속 사용”하려면 인증키와 함께 활용사례(갤러리)에 콘텐츠를 등록하라고 한다.
  - 자동 증액 수치, 심사 기준, 처리 SLA는 미공개다.
- 이용요금: 공식 페이지에서 별도 과금표나 “무료” 문구를 확인하지 못함. 인증키 기반 공개 API이지만 무과금이라고 단정하지 않고 운영 전 재확인한다.
- 이용약관·라이선스:
  - 데이터셋 표시: 공공누리 1유형, 출처표시, 상업적 이용 및 변경 가능
  - 이용약관: 저작자·출처 표시를 조건으로 자유이용을 원칙으로 하며, 결과 노출 시 “서울특별시 공공데이터” 사용 사실을 표시해야 함
  - 인증키는 타인에게 제공·공개·공유할 수 없음
  - 확인 필요: TOPIS 일반 안내는 Open API를 “비영리 목적”으로 설명한다. 데이터셋별 공공누리 1유형과 표현이 충돌하므로 상업 서비스 전 서울 열린데이터광장 담당부서에 적용 조건을 확인한다.

보안상 API 키를 브라우저에서 직접 사용하지 않는다. 공식 endpoint가 HTTP이고 키가 URL 경로에 포함되므로 백엔드 수집기에서만 호출하고, 요청·프록시·오류 로그에서 키를 마스킹한다.

## 4. 요청 방법

- HTTP Method: `GET`
  - 공식 표에 Method 열은 없지만 공식 샘플 URL과 실제 호출로 확인
- Endpoint:

```text
http://swopenAPI.seoul.go.kr/api/subway/{KEY}/{TYPE}/realtimeStationArrival/{START_INDEX}/{END_INDEX}/{statnNm}
```

- 응답 형식:
  - 지원: JSON, XML, XML 파일(`xmlf`), XLS(`xls`)
  - 미지원/미명시: CSV
- 필수 파라미터:

| 파라미터 | 타입 | 설명 | 예시 | 필수 여부 |
| --- | --- | --- | --- | --- |
| `KEY` | String | 실시간 지하철 전용 인증키 | `sample` | 필수 |
| `TYPE` | String | 응답 형식 | `json`, `xml`, `xmlf`, `xls` | 필수 |
| `SERVICE` | String | 서비스명 | `realtimeStationArrival` | 필수 |
| `START_INDEX` | Integer | 조회 시작 행 | `0` | 필수 |
| `END_INDEX` | Integer | 조회 종료 행 | `5` | 필수 |
| `statnNm` | String | 조회할 지하철역명 | `서울` | 필수 |

역명은 단순 표시명과 다를 수 있다. 공식 페이지는 응암→응암순환(상선), 공릉→공릉(서울산업대입구), 남한산성입구→남한산성입구(성남법원, 검찰청), 대모산입구→대모산, 천호→천호(풍납토성), 몽촌토성→몽촌토성(평화의문) 등의 입력 특례를 안내한다.

### 요청 예시

```http
GET http://swopenAPI.seoul.go.kr/api/subway/sample/json/realtimeStationArrival/0/5/%EC%84%9C%EC%9A%B8
```

실제 키는 예시에 넣지 않는다. 2026-08-25 테스트에서 공식 HTTP URL은 정상 응답했으며, HTTPS URL은 이 환경에서 20초 안에 응답하지 않았다. 이는 HTTPS 미지원 확정이 아니라 단일 네트워크 관측이다.

## 5. 응답 데이터

공식 명세의 핵심 행 필드는 21개다. 실제 JSON에는 페이지 메타데이터와 nullable 확장 필드가 추가로 나타났다. 파서는 추가 필드를 허용하고 핵심 필드 누락·null을 품질 플래그로 처리해야 한다. 아래 표의 “원문/source string 저장”은 전체 HTTP response body 보관이 아니라 **승인된 sanitized record 안에 해당 공급자 필드값을 보존**한다는 뜻이다.

## 6. 시간 데이터 해석

- 제공기관 데이터 생성시각 필드: `recptnDt`
- 예측시각 또는 실제시각 여부:
  - `barvlDt`: **예측 ETA**, 단위 초
  - `recptnDt`: ETA/상태 정보를 생성한 시각
  - `arvlCd`: 도착·출발 등 상태 분류
  - 실제 도착시각 필드: 없음
- 시간대:
  - 공식 명세는 시간대를 명시하지 않고 `yyyy-MM-dd HH:mm:ss` 형태의 offset 없는 문자열을 반환한다.
  - 수집기는 우선 `Asia/Seoul`로 파싱하되 `timezone_assumption=KST_UNDOCUMENTED`를 남기고 원문을 보존한다.
- 자정 이후 운행일 처리 방식:
  - 공식 문서에 없음
  - `recptnDt`의 달력 날짜와 내부 `service_date`를 분리하고, 막차·심야 운행일 규칙은 시간표와 운영기관 규칙을 결합한 뒤 결정한다.
- 수집시각과 제공시각의 차이:

```text
source_lag_seconds = received_at - parsed_recptnDt
adjusted_eta_seconds = max(0, barvlDt - source_lag_seconds)
```

  - 공식 페이지도 현재시각과 `recptnDt` 차이만큼 열차가 더 진행한 것으로 보정하라고 안내한다.
  - 두 번째 식은 `barvlDt > 0`, 시계 동기화, 허용 freshness, 노선별 ETA 품질 Gate를 통과할 때만 사용한다.
  - 음수 lag나 과도한 lag는 0으로 숨기지 않고 `future_source_time`, `stale_source_time`으로 표시한다.
- 시간표 기준인지 실제 관측값인지:
  - 시간표가 아님
  - 확정 실제 도착시각도 아님
  - 현재 시스템의 **도착예측과 운행 상태 스냅샷**

> `barvlDt`는 계획값이나 확정 실제값이 아니라 예측값이다. `arvlCd=1`도 특정 초의 확정 도착시각을 직접 제공하지 않으므로, 반복 관측 사이의 interval-censored Actual 이벤트로만 생성한다.

## 7. 식별자

  - 같은 역명이 여러 호선에 반복된 그룹은 109개이며 `서울`은 5개 레코드다.
  - 내부 키는 최소 `provider + subwayId + statnId`로 구성하고 역명 단독 조인을 금지한다.
  - 최신 XLSX에는 `1094` 신림선이 있으나 공식 API enum에는 없고, enum의 `1061` 중앙선은 XLSX에 독립 행이 없다. 매핑 버전을 저장해야 한다.

## 8. 수집 계획

- 수집 방식: **사용자 요청 시 수집 + 선택 역·검증창의 주기적 폴링**
  - 현재 사용자 결과: 동일 역의 동시 요청을 in-flight coalescing하고 짧은 freshness window 안에서만 재사용
  - 모델용 이력: 승인된 station×line×direction 검증창만 폴링
- 수집 주기:
  - 초기 파일럿: 단일 역 120초 간격, 720회/일
  - 예산: 정규 720회 + 재시도·수동 검증 230회 + 비상 여유 50회
  - 여러 역 상시 폴링이나 30~60초 폴링은 기본 1,000회/일을 초과하므로 호출 제한 해제·증액 확인 전 금지
- 수집 범위:
  - 1단계: 승인된 Route A 및 검증 corridor의 출발·환승·도착 station×line
  - 2단계: selected route에 포함된 역을 bounded window로 수집
  - 서울 전체 역의 무차별 상시 수집은 하지 않음
- 원문 저장 여부: **조건부 예 — sanitized raw만**
  - 서울 지하철 Arrival은 프로젝트 Provider Policy상 sanitized raw 보관이 가능하지만, 운영 전 `ProviderPolicyRegistry`에 조건·검토일·출처표시를 등록
  - 원형 provider response body는 persistent Bronze에 저장하지 않고 승인된 sanitized transform 결과만 저장
  - 저장 요청 메타데이터는 service·index·정규화 역명으로 제한하고 전체 URL·인증키·사용자 위치·세션 식별자는 제거
  - 원형 body가 재현 증거로 필요하면 운영 Bronze와 분리된 evidence artifact로 별도 승인·보관
  - Share 결과에는 raw와 `btrainNo`를 포함하지 않음
- 저장 위치:
  - 논리 경로: `bronze/seoul-subway-arrival/station/service_date=YYYY-MM-DD/hour=HH/{fetch_id}.json.gz`
  - 정규화: `silver/subway_arrival_observation`
  - 물리 저장소와 TTL: 배포 ADR/G5에서 확정 전 `TBD`
- 재시도 정책:
  - 네트워크 timeout, HTTP 5xx, `ERROR-500`/`ERROR-600`/`ERROR-601`만 지수 백오프+jitter로 최대 2회
  - `INFO-100`, `ERROR-300`~`ERROR-336`은 설정·요청 오류이므로 자동 재시도하지 않음
  - 재시도도 일일 quota에 포함하고, 950회 사용 시 자동 재시도·비필수 수집 중단
- 중복 판정 기준:
  - 원문 응답: `body_sha256`
  - 행 보존키: `fetch_id + rowNum`
  - 의미 중복 후보: `requestedStatnNm + subwayId + statnId + updnLine + btrainNo + recptnDt + arvlCd + ordkey`
  - 동일 행 반복은 공급자 캐시 반복일 수 있으므로 삭제하지 않고 `duplicate_of`와 source lag를 기록

수집기는 요청 직전 `requested_at`, 응답 헤더 수신 `headers_received_at`, 본문 완료 `received_at`을 각각 기록한다. API 키가 포함된 원본 URL은 저장하지 않고 service·index·정규화 역명만 별도 필드로 저장한다.

## 9. 전처리 및 활용

- 생성할 데이터:
  - [x] 구간 운행시간
  - [x] 정차시간
  - [x] 실제 배차간격
  - [ ] 계획 대비 지연
  - [ ] 사고·운행장애 이벤트

앞의 세 항목도 API가 직접 제공하는 값이 아니라 반복 관측에서 추정하는 **interval-censored derived data**다. 계획 대비 지연에는 운행시간표가 추가로 필요하고, 사고·운행장애에는 명시적 이벤트 소스가 필요하다.

- 전처리 규칙:
  1. 모든 ID와 열차번호를 문자열로 변환하고 sanitized record 안에 source string과 정규화 값을 함께 보존
  2. `recptnDt`와 수집기 시각을 분리 저장하고 source lag 계산
  3. `barvlDt`는 정수 파싱하되 `0`을 결측이나 도착으로 단정하지 않고 `arvlCd`·메시지·노선별 품질과 결합
  4. 동일 station×line×direction×train을 수집 순서로 정렬하고 out-of-order를 허용
  5. 프로젝트 Actual 계약에 따라 동일 identity에서 `arvlCd != 1 → arvlCd = 1`의 최초 전이만 도착 Actual interval로 생성
  6. `arvlCd=2`는 출발 상태 관측으로 별도 저장하며 도착 Actual로 만들지 않음. 정차시간 추정에 쓰려면 도착→출발 연결 규칙을 별도 검증
  7. 확정 초 단위 Actual이 아니라 `(previous_seen_at, first_seen_at]` 구간과 midpoint·interval width를 함께 저장
  8. `subwayList`와 `statnList`는 split·trim·형식검사 후 각각 매핑하며 배열 위치를 무조건 zip하지 않음
  9. 명세 외 필드는 파싱 단계에서 거부하지 않되 Provider Policy가 허용한 경우만 sanitized extensions에 보존하고, 모델 feature 승격은 schema review 후 수행
- 다른 데이터와 결합할 키:
  - 역 마스터: `subwayId + statnId`
  - 일괄 도착정보 OA-15799: `subwayId + statnId + updnLine + btrainNo + recptnDt` 후보
  - 시간표: `serviceDate + subwayId + stationId + direction + trainNo` 후보
  - 내부 canonical node: versioned `NodeRef(provider, providerId, line, direction, mappingVersion)`
- 모델 입력 변수:
  - `barvlDt`, source lag, `arvlCd`, train status, last-car flag
  - station×line×direction, 종착역, 열차종류
  - 시간대, 요일, service date, 공휴일, 막차 인접 여부
  - 최근 실제 배차간격·정차시간·구간시간, residual quantile
  - freshness, missingness, duplicate/cache 반복률, interval width

`arvlMsg2`·`arvlMsg3` 자유 텍스트는 표시·진단용으로 먼저 보존한다. 공식 코드나 검증된 parser 없이 핵심 모델 feature나 사고 이벤트로 직접 사용하지 않는다.

## 10. 데이터 품질 및 제약

- 결측값 발생 조건:
  - 해당 역에 현재 반환할 열차가 없음(`INFO-200` 포함)
  - 공급자/운영기관이 특정 노선·구간·필드를 제공하지 않음
  - 실제 JSON의 `subwayNm`, `subwayHeading`, `trainCo`처럼 항상 null일 수 있는 확장 필드
  - stale cache, API 장애, 역명 불일치, 서울 외 구간
- 중복 데이터 가능성:
  - 동일 `recptnDt` 행이 여러 poll에서 반복될 수 있음
  - 한 역에 여러 호선·방향·열차가 동시에 반환되는 것은 정상
  - 동일 역명은 여러 `subwayId/statnId`에 존재하므로 이름 기준 중복 제거 금지
- 잘못된 값 또는 특수값:
  - `barvlDt=0`은 도착·출발·운행 상태와 함께 나타날 수 있어 공통적인 “0초 후 도착”으로 해석할 수 없음
  - `btrainNo`는 `0064`처럼 선행 0 또는 `A...` 영문을 포함
  - `recptnDt`는 응답 수신시각보다 수분 오래될 수 있음
  - HTTP 200과 업무 결과 코드가 불일치할 수 있음
  - 자유 텍스트 메시지와 코드가 충돌할 가능성을 허용
- 데이터 제공 제외 구간: 공식 설명상 서울시 외 역구간. 실제 적용 범위는 발급 키로 경계역 테스트 후 확정
- 실시간 데이터 과거 보관 여부: API를 통한 과거 이력 제공은 없음. 제공기관의 내부 별도 보관 여부는 확인하지 못했으며, 프로젝트 활용 이력은 자체 수집해야 함
- API 장애 시 대체 데이터:
  - 현재 ETA: OA-15799 일괄 도착정보 또는 실시간 열차 위치정보를 제한적으로 사용
  - 장기 분포: 마지막 검증된 empirical/timetable prior
  - 주의: 관련 API는 같은 TOPIS 원천일 수 있어 독립 장애 대체재가 아니다.
  - freshness Gate 미통과 시 `INSUFFICIENT_DATA`/`NOT_COMPUTED`로 축소하고 stale 값을 현재값처럼 표시하지 않음
- 확인된 문제:
  1. API 정확한 갱신주기·지연 SLA·초당 한도·시간대·자정 운행일 규칙이 미문서화
  2. 공식 호선 enum과 최신 역 XLSX 불일치: `1061`/`1094` drift
  3. 공식 “서울 외 미제공” 설명과 서울 외 역을 포함한 XLSX 범위가 불일치
  4. 공식 출력 표는 21개 핵심 필드지만 실제 JSON에는 10개 페이지/nullable 필드가 추가됨
  5. 공식 샘플은 `START_INDEX=0`을 쓰지만 `ERROR-335` 설명은 sample 인덱스를 1~5라고 적어 문구가 일치하지 않음
  6. 공식 endpoint는 HTTP이며 HTTPS 실측은 timeout. 키가 URL 경로에 있어 전송·로그 보안 검토 필요
  7. 데이터셋의 공공누리 1유형과 TOPIS 일반 페이지의 “비영리 목적” 문구가 충돌
  8. 단일 응답 안에서도 `recptnDt`가 크게 분산되어 원자적 스냅샷으로 볼 수 없음
