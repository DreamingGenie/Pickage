## 2. 제공 범위

- 지역 범위:
  - 공공데이터포털 표기: 전국
  - 공식 활용가이드의 제한: **남한**, 북한·국외 미제공
  - 공간 단위: 약 5 km × 5 km 동네예보 격자
  - 공식 격자 범위: `nx=1..149`, `ny=1..253`
- 노선·운영기관 범위: 해당 없음
  - 버스·지하철 노선, 운영기관, 정류장, 역, 차량 정보를 제공하지 않는다.
  - 서울 교통에 사용하려면 경로·정류장 좌표를 별도로 KMA 격자에 매핑해야 한다.
- 제공 기간:
  - 포털 표준 메타데이터의 시간범위는 `현재`다.
  - `base_date`로 날짜를 지정할 수 있지만, 이 endpoint가 보장하는 과거 조회기간은 공식 문서에 없다.
  - KMA API허브의 별도 역사자료 보유기간을 이 data.go.kr endpoint의 보장기간으로 간주하지 않는다.
- 예보 범위:
  - 초단기예보: 발표시점부터 6시간 이내
  - 단기예보: 2024-11-28 14:00 KST 이후 가이드 기준, 발표회차에 따라 글피 또는 그글피까지 제공
  - `02·05·08·11·14시` 회차: +3일까지 1시간, +4일은 3시간 간격
  - `17·20·23시` 회차: +4일까지 1시간, +5일은 3시간 간격
- 과거 이력 제공 여부: **보장 없음**
  - 조회 파라미터가 과거 날짜를 받을 수 있다는 사실과 장기 보관 SLA는 다르다.
  - 학습용 forecast vintage는 자체 수집 또는 별도 공식 역사자료 계약이 필요하다.
- 데이터 갱신 주기:
  - 서비스 개요: `수시(일 8회)` — 단기예보 기준
  - 초단기실황: 매시 정시 기준자료, `:10` 이후 제공; 가이드는 10분마다 최신정보 갱신도 명시
  - 초단기예보: 매시 `:30` 생성, `:45` 이후 제공
  - 단기예보: `02:00, 05:00, 08:00, 11:00, 14:00, 17:00, 20:00, 23:00`, 각 `:10` 이후 제공
- 실제 데이터 지연시간:
  - 명세상 초단기실황 약 10분, 초단기예보 약 15분, 단기예보 약 10분의 nominal availability lag
  - 이는 기준시각부터 API 제공 개시까지의 일정이며 실제 네트워크·수집 지연이 아니다.
  - 인증키 정상 호출을 수행하지 못해 실제 end-to-end 지연은 미측정이다.

공식 격자 XLSX `최종 업데이트 파일_20260701`을 직접 분석한 결과, 행정구역 매핑 3,838행, 고유 격자 1,632개가 있었다. 이 중 `1단계=서울특별시`는 453행, 고유 격자 30개다. 같은 격자에 여러 행정구역 행이 연결되므로 행정구역 행 수를 API 호출 격자 수로 사용하면 안 된다.

## 3. 인증 및 호출 제한

- 인증 방식: query parameter의 URL-encoded `ServiceKey`
  - 현재 포털은 `ServiceKey`, 가이드 표는 `serviceKey`를 사용한다.
  - 2026-08-25 invalid-key 테스트에서는 두 표기 모두 인증키로 인식됐다.
  - 같은 가이드 일부 예제의 `authKey`는 현재 `apis.data.go.kr` gateway에서 인증키로 인식되지 않았다.
- API 키 발급처:
  - [공공데이터포털 활용신청](https://www.data.go.kr/data/15084084/openapi.do)
  - 포털 로그인 후 개인 또는 프로젝트 서비스키로 활용신청
  - 개발단계·운영단계 모두 자동승인으로 표시됨
- 기본 호출 한도: **포털의 개발계정 신청 가능 트래픽 10,000**
  - API 상세 화면에는 이 수치의 초기화 주기가 명시되지 않는다. 일일 적용 여부와 실제 승인량은 발급 계정의 마이페이지에서 다시 확인한다.
- 초당 호출 한도: **공식 활용가이드 명세상 상세기능별 최대 30 TPS**
  - gateway가 적용하는 burst/window 규칙은 공개되지 않았으므로 애플리케이션은 이보다 낮은 내부 rate limit을 둔다.
- 호출량 증액 가능 여부: 가능
  - 운영계정은 활용사례 등록 후 트래픽 증가 신청 가능
  - 자동 증액량·처리시간·승인 SLA는 공개되지 않음
- 이용요금: 무료
- 이용약관·라이선스:
  - 포털 화면: 공공저작물 출처표시 제1유형
  - 표준 메타데이터: `제3자 권리 포함 : 저작권 표시, 공공저작물 : 출처표시 (제 1유형)`
  - 출처와 원문 URL을 표시하며, 원문 장기 보관·cache·재배포는 `ProviderPolicyRegistry`에서 별도 승인한다.
  - 인증키와 인증키가 포함된 완성 URL은 로그·DB·클라이언트에 저장하지 않는다.

## 6. 시간 데이터 해석

- 제공기관 데이터 생성시각 필드:
  - 격자 item에는 별도 `generatedAt`이 없다.
  - `baseDate + baseTime`은 발표·기준 시각이다.
  - `getFcstVersion.version`은 수정 파일의 생성시각이다.
  - 수집시각은 collector가 `collected_at`으로 별도 기록해야 한다.
- 예측시각 또는 실제시각 여부:
  - `getUltraSrtNcst.obsrValue`: 대표 AWS **관측값**
  - `getUltraSrtFcst.fcstValue`, `getVilageFcst.fcstValue`: `fcstDate + fcstTime` 대상 **예측값**
  - `baseDate + baseTime`: 관측·예보의 기준 또는 발표시각
  - 어느 필드도 대중교통 계획·예측·실제 도착시각이 아니다.
- 시간대: **KST (Asia/Seoul)**
- 자정 이후 운행일 처리 방식:
  - 기상 API는 교통 운행일이 아니라 KST 민간력 날짜를 사용한다.
  - `baseDate/baseTime`과 `fcstDate/fcstTime`을 각각 완전한 timestamp로 조합한다.
  - `fcstTime=0000`을 이전 날짜의 24시로 임의 변환하지 않는다.
- 수집시각과 제공시각의 차이:
  - `source_available_at`: 공식 회차별 제공 개시시각
  - `collected_at`: 우리 수집기가 응답을 받은 시각
  - `ingested_at`: 저장 완료 시각
  - `collection_lag = collected_at - source_available_at`
  - `forecast_horizon = forecast_at - base_at`
- 시간표 기준인지 실제 관측값인지:
  - 초단기실황은 기상 관측값
  - 초단기·단기는 기상 예보값
  - 교통 시간표·교통 도착예측·교통 실제 관측값은 없음

| 기능 | base time | 공식 제공 개시 | 값의 성격 |
| --- | --- | --- | --- |
| 초단기실황 | 매시 `HH00` | `HH:10` 이후 | 대표 AWS 관측 |
| 초단기예보 | 매시 `HH30` | `HH:45` 이후 | 6시간 이내 예보 |
| 단기예보 | 1일 8회 `0200`부터 3시간 간격 | 각 회차 `:10` 이후 | 단기예보 |

> `fcstDate/fcstTime`은 계획값도 실제 관측값도 아닌 **예측 대상시각**이다. 당시 사용 가능했던 예보를 재현하려면 forecast target뿐 아니라 `baseDate/baseTime`, `version`, `source_available_at`, `collected_at`을 함께 보존해야 한다.

## 8. 수집 계획

- 수집 방식: **사용자 요청 시 수집 + 검증용 주기적 폴링**
  - Leave-now: 현재 여정의 고유 격자만 요청하고 같은 base run/grid 호출을 dedupe
  - historical weather artifact 실험: 공식 제공 개시 직후 대상 corridor의 필요한 회차만 주기 수집
  - 전체 37,697개 격자를 무차별 polling하지 않음
- 수집 주기:
  - 초단기실황: 필요한 경우 매시 `:10` 이후 최신 base run
  - 초단기예보: 필요한 경우 매시 `:45` 이후 최신 base run
  - 단기예보: 1일 8회 각 `:10` 이후
  - 예보버전: 최초 적재 시와 vintage 확정 전 조회해 수정 여부 확인
- 수집 범위:
  - 초기: 서울 Route A/Claim Gate corridor의 고유 격자
  - 확대: coverage와 quota budget을 확인한 뒤 실제 지원 route geometry 범위
- 원문 저장 여부: **ProviderPolicyRegistry 승인 후에만 저장**
  - 승인 전 persistent raw storage·cross-session cache·재배포 default-deny
  - 승인 후 인증키를 제거한 response body, request metadata, hash, version을 immutable 저장
  - frontend·분석 결과에 원문 전체나 ServiceKey를 노출하지 않음
- 저장 위치:
  - Bronze: `bronze/kma/vilage_fcst_info/endpoint={op}/base_date={date}/base_time={time}/grid={nx}-{ny}/`
  - Silver observation: `silver/weather_observation`
  - Silver forecast vintage: `silver/weather_forecast_vintage`
  - 격자 매핑: `silver/kma_weather_grid`
  - 물리 저장소·TTL은 ProviderPolicy/배포 ADR 승인 전 미정
- 재시도 정책:
  - HTTP 5xx, timeout, 업무코드 `01/04/05`: exponential backoff+jitter로 제한 재시도
  - `03 NODATA`: 공식 제공 개시 전인지 먼저 확인하고, 개시 직후에만 bounded retry
  - `10/11`: 파라미터 수정 전 재시도 금지
  - `20/21/30/31/32/33`: 인증·권한·키 상태 수정 전 재시도 금지
  - `22`: 당일 quota 소진으로 처리하고 다음 quota window 또는 승인 후 재개
  - 초당 제한 오류 `23`이 gateway에서 반환되면 rate limiter와 jitter를 강화
- 중복 판정 기준:
  - 실황 natural key: `endpoint + base_at + nx + ny + category`
  - 예보 natural key: `endpoint + base_at + forecast_at + nx + ny + category`
  - revision key: natural key + `filetype + version`
  - fetch provenance: `fetch_id + collected_at + response_sha256`
  - 같은 natural key의 값이나 version이 다르면 중복 삭제하지 않고 forecast revision으로 보존

## 9. 전처리 및 활용

- 생성할 교통 데이터:
  - [ ] 구간 운행시간
  - [ ] 정차시간
  - [ ] 실제 배차간격
  - [ ] 계획 대비 지연
  - [ ] 사고·운행장애 이벤트

이 API에서 생성하는 것은 교통 운행지표가 아니라 **기상 실황 fact, forecast vintage, 공간·시간 weather feature**다.

- 전처리 규칙:
  1. `baseDate/baseTime`, `fcstDate/fcstTime`, `version`을 문자열로 보존하고 KST timestamp를 별도 생성
  2. `nx`, `ny`를 정수 검증하고 `provider + gridSystem + nx + ny + gridVersion`으로 식별
  3. `category`, raw value, unit, parsing status를 함께 저장
  4. `obsrValue/fcstValue`는 먼저 raw 문자열로 보존한 뒤 category별 parser로 typed value 생성
  5. `+900 이상`, `-900 이하`를 missing sentinel로 처리하고 원문도 보존
  6. `-`, `null`, `0`의 무강수·무적설 의미는 `RN1/PCP/SNO`에만 적용하고 모든 변수의 0으로 일반화하지 않음
  7. `PTY`, `SKY`는 연속형 숫자가 아니라 versioned categorical dictionary로 변환
  8. 같은 예보 target의 여러 base run을 섞지 않고 forecast vintage로 유지
  9. Leave-now에는 `source_available_at <= calculatedAt`인 vintage만 사용하고 이후 수정본으로 과거 계산을 덮어쓰지 않음
  10. 정류장·역·경로 좌표를 공식 격자 변환식 또는 versioned 격자 mapping으로 변환
  11. 날씨 미제공·결측 시 0으로 대체하지 않고 feature absence와 fallback reason을 기록
- 다른 데이터와 결합할 키:
  - 공간: `route/leg geometry -> WeatherGridRef(nx, ny, mappingVersion)`
  - 시간: `base_at`, `forecast_at`, `source_available_at`, `service_date/time_bucket`
  - 교통 outcome: `canonical_leg_id + actual/residual timestamp`
  - forecast revision: `filetype + version`
- 모델 입력 변수 후보:
  - `PTY`, `POP`, `PCP/RN1`, `SNO`
  - `TMP/T1H`, `TMN`, `TMX`, `REH`
  - `WSD`, `VEC`, `UUU`, `VVV`
  - `SKY`, `LGT`
  - forecast horizon, base run age, revision indicator, route-grid coverage
  - raw 9/10자리 날짜·시각 문자열이나 `nx/ny` 크기 자체는 연속형 weather feature로 사용하지 않음

## 10. 데이터 품질 및 제약

- 결측값 발생 조건:
  - 관측장비가 없는 해양지역 또는 장비 결측
  - `+900 이상`·`-900 이하` missing sentinel
  - 해상 격자의 기온군, 강수확률, 강수량·적설, 습도 masking
  - 신규 회차 제공 전 조회하거나 특정 category가 해당 endpoint·회차에 없는 경우
- 중복 데이터 가능성:
  - pagination·재시도로 같은 item을 다시 받을 수 있음
  - 동일 base run의 수정본이 새 `version`으로 제공될 수 있음
  - 여러 행정구역이 같은 `nx/ny`를 공유하므로 행정구역별 호출은 중복을 만든다.
- 잘못된 값 또는 특수값:
  - `RN1/PCP/SNO`는 수치와 `강수없음`, 범주 문자열, `-`, `null`, `0`이 혼재할 수 있음
  - `PTY/SKY`는 코드값이며 숫자 크기에 연속 의미가 없음
  - 초단기예보 `POP`은 2026-06-23부터 추가된 schema-evolution 항목이므로 이전 vintage에서 결측인 것이 정상일 수 있음
  - 공식 가이드의 성공코드는 필드표 `00`, XML 예제 `0`으로 불일치
  - 예보버전 요청의 `basedatetime` 항목크기는 10으로 적혀 있지만 공식 예시는 12자리 `YYYYMMDDHHmm`이며, 응답 `version`도 항목크기 4와 달리 14자리 예시임
  - 공식 가이드 초단기예보 시간표의 19시 행에 `Base_time=19030`이라는 5자리 오기가 있음
  - 가이드 표 일부 예보시간 범위도 인접 회차 규칙과 불일치하므로 시간표를 기계적으로 복사하지 않고 `HH30` 규칙과 실응답으로 검증해야 함
- 데이터 제공 제외 구간:
  - 활용가이드상 북한·국외
  - 교통 노선·차량·역·정류장·ETA·실제 운행결과 전체
  - 해상 격자의 일부 요소
- 실시간 데이터 과거 보관 여부: 공식 보장 없음
  - `base_date` 요청 가능 여부만으로 forecast vintage history를 보장하지 않는다.
  - 과거 모델링을 위해서는 당시 수신한 base run과 version을 자체 보관해야 한다.
- API 장애 시 대체 데이터:
  - 최신 검증 weather snapshot이 freshness 기준을 넘으면 사용하지 않음
  - weather feature를 제외하고 historical-only transit baseline으로 fallback
  - 별도 KMA API허브 데이터는 키·스키마·라이선스·시간계약을 검증하기 전 자동 대체하지 않음
- 확인된 문제:
  1. 현재 포털은 HTTPS, 공식 ZIP 가이드는 HTTP를 표시함
  2. 키 이름이 `ServiceKey`, `serviceKey`, `authKey`로 문서 안에서 혼재함
  3. 성공 업무코드가 `00`과 `0`으로 불일치함
  4. 포털 설명의 예보기간과 2026-07 가이드의 연장 예보기간이 다름
  5. API 상세 화면과 표준 메타데이터 JSON의 등록·수정일은 2021-06-28이지만 연결 활용가이드는 2026-07 버전임
  6. 공식 과거 조회·보존기간과 실제 end-to-end latency SLA가 없음
  7. `basedatetime`·`version`의 명세상 항목크기와 예시 길이가 불일치함
  8. 초단기예보 `POP` 도입 경계가 활용가이드와 KMA API허브에서 각각 11시 이후·12 KST 이후로 다르게 표현됨
  9. 유효키 JSON 응답의 실제 타입·성공코드·row ordering을 아직 검증하지 못함

4. 구현 endpoint는 현재 포털의 HTTPS와 `ServiceKey`를 사용한다.
5. 날씨 격자를 transit ID에 섞지 않고 versioned `WeatherGridRef`와 공간 association으로 연결한다.
6. forecast target만 저장하지 않고 base run, version, nominal availability, 수집시각을 보존한다.
7. weather feature 미제공·stale·mapping 실패 시 0으로 채우지 않고 historical-only transit baseline으로 fallback한다.
8. ProviderPolicy 승인과 hold-out value-add 검증 전에는 사용자 결과에 “날씨 반영” claim을 하지 않는다.
